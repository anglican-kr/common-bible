# 글쓰기 — 문체와 용어

사용자에게 보이는 모든 글에 적용한다. 답, 원장과 PR 본문, 문서, 커밋 메시지, 코드 주석의 한국어가 모두 들어간다. 매 세션 지킬 요약은 CLAUDE.md 「컨벤션」에 있고, 여기에는 교정 사례(「함정」)와 용어 목록, 릴리스 노트의 문체가 있다. 앱 화면의 문구는 pitfalls §29를 따른다.

## 용어

사용자가 고친 낱말이다. 왼쪽 말을 쓰지 않고 오른쪽 말을 쓴다.

| 쓰지 않는 말 | 쓰는 말 | 근거 |
| --- | --- | --- |
| 살아있는 문서(living document) | 현행 문서, 현행 설계 문서 | 사용자 지적, 2026-05-11 |
| 발화(fire, trigger) | 걸리다, 작동하다, 트리거되다 | 사용자 지적, 2026-05-08 |
| 만성(chronic) | 지속적인, 반복되는 | 사용자 지적, 2026-05-08 |
| 선재(pre-existing) | 이전부터 있던, 기존 | 사용자 지적, 2026-05-11 |
| 무음(silent) | 조용한, 조용히(「조용히 실패」) | 사용자 지적 |
| 줄임 명칭(shortened label) | 짧은 명칭, 짧은 이름 | 사용자 교정, 2026-05-27 |
| 소비자(consumer) | 컨슈머 | 사용자 지적, 2026-06-21 |
| 고아(orphaned) | 쓰이지 않는, 호출되지 않는, 남은 | 사용자 지적, 2026-06-21 |
| 저본(底本, source text) | 바탕 본문(정확성이 필요한 자리는 원전) | 사용자 지적, 2026-06-01 · 06-15 |
| 모서리 사례(edge case) | 엣지 케이스 | 사용자 지적, 2026-07-12 |
| 막힌 축일(blocked feast) | 밀린 축일, 더 높은 날에 밀린 | 사용자 지적, 2026-07-17 |
| 이긴다, 진다(우선순위) | 선순위, 후순위 | 사용자 정정, 2026-07-06 |
| 스트랭글러 패턴, 미스노머 같은 음차 | 평이한 한국어(점진 교체, 이름이 역할과 맞지 않음) | 사용자 지적, 2026-06-06 · 06-08 |
| 머리명사, 한정어 같은 낯선 번역어 | 꾸밈을 받는 중심 명사, 절 번호 앞의 문서 이름 | 사용자 질문, 2026-07-06 · 10-23 |
| 영역 문서 | 주제 문서 | 사용자 결정, 2026-10-23 |
| 꾸러미, 창 객체 꾸러미(aggregate) | 네임스페이스 객체(모듈의 함수를 `window.appBookmark = { … }`처럼 이름 하나 아래 모은 객체) | 사용자 결정, 2026-10-23 |
| (상한이) 듣지 않는다 | 작동하지 않는다 | 사용자 질문, 2026-10-23(pitfalls §40) |
| 판, 판 번호(앱의 version) | 버전 | 사용자 교정, 2026-10-23 |
| 꼴 | 표기, 형식, 저장 구조, 경우 | pitfalls §36 |

- 다른 분야(의학, 언어학, 법률, 신학)의 한자어를 비유로 가져오지 않는다. 「이 한자어의 원래 영어가 뭐였지?」가 떠오르면 직역일 가능성이 높다.
- 영어 관용구를 직역하지 않는다. 정착된 외래어(콜백, 트리거, 이벤트, 리디렉션)는 그대로 쓴다.
- 코드 주석에서 쓰던 말을 사용자에게 보이는 글에 그대로 옮기지 않는다.

## 릴리스 노트

- 독자는 성공회 신자와 일반 사용자다. 기술 용어, 약어, 내부 이름(`inert`, 포커스 트랩, 디바운스)을 피하고, 사용자가 느끼는 변화(속도, 편의, 모양)를 일상 언어로 쓴다. 「지연 로딩」은 「앱이 빠르게 열립니다」처럼 결과로 쓴다. 개발자를 위한 내용은 따로 짧게 둔다. 모든 문장은 마침표로 끝낸다.
- 본문 첫머리에 「X.Y.Z 이후 누적된 변경」 같은 범위 설명을 두지 않는다. 첫 제목부터 바로 시작한다. 범위는 태그와 GitHub의 비교 화면이 보여 준다.
- 태그 메시지도 같은 문체로 쓴다. 릴리스 절차는 `workflow.md` 「릴리스」.

## 함정

### pitfalls §29 — 알림 문구는 결과부터 — 된 것과 안 된 것, 다음 할 일은 화면의 단추 이름으로 (사용자 교정, 2026-10-17)

한 번의 누름이 둘 이상을 하는 동작(연결 해제 + Drive 파일 삭제)이 일부만 실패하면, 문구가 무엇이 실패했는지만 말하고 무엇이 이미 끝났는지는 빠뜨리기 쉽다. 다음 할 일을 「…에서」처럼 자리로 흐리게 가리키면 사용자가 어디를 눌러야 할지 모른다.

**사례:**
- `docs/changes/2026-10-17-sync-signout-inflight.md` — 「파일도 삭제」가 파일을 지우지 못했을 때의 스낵바 초안 「Drive의 동기화 파일을 삭제하지 못했습니다. 다시 연결한 뒤 연결 해제에서 다시 삭제해 주세요.」에 사용자가 「여기 한국어 문장 어색하다?」 — 「다시」가 두 번, 「연결 해제에서」는 어디인지 흐리고, 연결 해제는 이미 됐다는 사실이 없다. 고친 문구: 「연결은 해제했지만 Drive의 동기화 파일은 삭제하지 못했습니다. 다시 연결한 뒤 「파일도 삭제」를 눌러 주세요.」

**규칙:**
- 한 동작이 둘 이상을 하면 된 것과 안 된 것을 함께 말한다(「연결은 해제했지만 … 삭제하지 못했습니다」).
- 다음 할 일은 사용자가 화면에서 보는 단추 · 메뉴 이름 그대로 쓴다(「파일도 삭제」를 눌러 주세요).
- 한 문장에 같은 부사(「다시」)를 되풀이하지 않는다 — 보내기 전에 소리 내어 읽듯 한 번 읽는다.

### pitfalls §31 — 영어 · 한국어가 섞인 문장 — 영어 단어 뒤의 조사 · 용언은 붙여 쓴다 (사용자 교정, 2026-10-17)

영어 단어(코드 이름 · 파일명 · 약어 포함) 바로 뒤의 조사와 용언을 띄어 썼다 — 「`sync.json` 을」, 「OFFLINE 으로」, 「push 되면」. 맞춤법대로 조사와 「-하다 · -되다」는 앞말에 붙는다.

**사례:**
- PR #354(`docs/changes/2026-10-17-sync-signout-inflight.md`)의 `architecture.md` 현행화 중 사용자 교정: 「영어, 한국어가 혼용된 문장에서 영어 단어 뒤에 오는 한국어 조사, 용언은 띄어쓰지 말 것」. 그 PR에서 쓰거나 고친 줄의 418곳과 data 저장소 README · CLAUDE.md(data#33)의 88곳을 붙였다.

**규칙:**
- 조사(을/를 · 이/가 · 은/는 · 의 · 에 · 로/으로 · 와/과 · 도 · 만 · 마다 …)와 서술격 조사는 영어 단어 · 코드 이름에 붙인다: 「`sync.json`을」, 「OFFLINE으로」, 「PR마다」, 「`false`일 때」, 「SYNCING이라」.
- 「-하다 · -되다」 용언도 붙인다: 「push되면」, 「dedup해」, 「push된다」.
- 뒤가 명사 · 관형사 · 독립된 말이면 띄운다: 「HTTP 실패」, 「Google 태그」, 「(`storage` 이벤트) 이 탭도」(「이 탭」의 「이」), 「`pollSync()`를 한 번」(「한 번」의 「한」).
- 기계로 고칠 때는 조사 목록으로 후보를 뽑되, 낱말일 수 있는 「이 · 나 · 도 · 만 · 면 · 일 · 한」은 하나씩 본다. ASCII 그림 안의 줄은 글자 수가 줄어 테두리가 어긋나므로 다시 맞춘다.
- 문서 · 원장 · PR 본문 · 커밋 메시지 · 코드의 한국어 주석과 테스트 이름 · 답글에 모두 적용한다. 이 교정 전에 쓴 문서에는 띄어 쓴 곳이 많이 남아 있다(머지된 원장은 고칠 수 없다).

### pitfalls §32 — 숫자 구간에 물결표(~)를 쓰지 않는다 — 하이픈으로 (사용자 교정, 2026-10-17)

GitHub 마크다운(GFM)은 물결표 하나짜리 쌍(`~…~`)도 취소선으로 읽는다. 한 단락에 구간이 둘 있으면 그 사이가 지워져 보인다.

**사례:**
- PR #354 원장의 `44~50(…), 51~54(…)` 같은 표기 — PR 페이지에서 가운데가 취소선이 됐다. 사용자 교정: 「한국어 문장에서 흔히 숫자 구간 표현에 쓰이는 물결 표시(`~`)는 마크다운 서식 오류를 자주 유발하므로 다른 표현으로 대체 바람」 · 「차라리 영어식 표현인 하이픈이 적절할 듯」.

**규칙:**
- 숫자 · 번호 구간은 하이픈: 「44-50」, 「Phase 2a-2j」, 「1583-9999」. ID 구간은 접두어를 한 번만: 「ADR 001-038」(「ADR-001-038」은 ID처럼 읽힌다).
- 날짜처럼 값 안에 하이픈이 있으면 말로 잇는다: 「2026-05-10부터 10-17까지」, 이어진 이틀은 「2026-05-09 · 05-10」.
- 근삿값도 산문에서는 「약」으로: 「약 6,000줄」. 표의 줄 수 칸(`~330`)처럼 칸마다 하나면 짝이 생기지 않고, 코드 블록 · 인라인 코드 안(`~/projects` 경로)은 서식이 없어 괜찮다.

### pitfalls §36 — 「꼴」을 쓰지 않는다 — 한 낱말이 여러 뜻을 맡아 읽기 어렵다 (사용자 교정, 2026-10-20)

「앱이 쓰는 꼴」 · 「저장될 꼴」 · 「어긋난 꼴」 · 「버린 꼴」처럼, 「꼴」 한 낱말이 문자열의 표기, 데이터의 구조, 예(경우), 버린 설계를 모두 맡았다. 같은 문서 안에서도 뜻이 바뀌어, 읽는 사람이 자리마다 뜻을 짐작해야 했다.

**사례:**
- PR #359 머지 직후 사용자가 ADR-040을 열어 보고 「문서에서 "꼴"이 무엇을 의미하는 지 이해하기 어렵네」라고 했다. 저장소 전체에 144군데(「글꼴」 제외 — 문서 · 주석 · 테스트 이름 · 픽스처 · 도구, 그리고 화면 문구 하나)가 있었고, 사용자 「"꼴"이 쓰인 곳을 찾아서 이해하기 쉽게 수정 바람」으로 자리마다 고쳤다(원장 `docs/changes/2026-10-20-plain-wording-kkol.md`).

**규칙:**
- 그 자리의 뜻을 쓴다. 문자열을 적는 방식(절 범위 「16」 · 「1-5」, 날짜 「12.25」)은 「표기」, 값 · 객체의 모양은 「형식」, 저장소에 실제로 쓰이는 모양은 「저장 구조」, 규칙에 어긋난 예나 사정이 같은 날은 「경우」, 버린 설계는 「안」, 일하는 방법은 「방식」이다. 「X 꼴로 줄인다」는 「X처럼 줄인다」로 쓴다.
- 「글꼴」(폰트)은 바른 낱말이다. 성서 본문의 「꼴」(「네모꼴」 · 「망하는 꼴」)은 본문이므로 건드리지 않는다.
- 보내기 전에 `grep -n "꼴" <파일> | grep -v 글꼴`로 남은 것이 없는지 본다.

### pitfalls §37 — 한국어답게 쓴다 — 완결된 문장으로, 간결하게, 그 분야의 용어로 (사용자 교정, 2026-10-21)

원장과 문서에 명사를 가운뎃점(·), 줄표(—), 「A = B」, 겹친 괄호로 이어 붙인 문장이 많았다. 읽는 사람이 낱말 사이의 관계를 짐작해야 했다. 반대로 풀어 쓰려다 문장이 늘어지거나, 용어 대신 긴 설명을 쓰는 것도 읽기 어렵다.

**사례:**
- 머지된 원장 `docs/changes/2026-10-21-verse-range-link.md`의 「리뷰 반영」 첫 문단. 사용자가 「한국어를 한국어답게 쓰자. 읽어도 무슨 소린지 이해하기 어렵네」라고 했다. 머지된 원장이라 고치지 못한다.
  - 전: 「사용자 「서브 에이전트로 리뷰」. 결과를 보기 전에 범위 · 기준 · 횟수를 정했다 — 읽기 전용 리뷰어 셋(A 주소 · 라우팅, B 모듈 이동 · 부팅 · 테스트, C 문서), 고친다 = 이 PR이 만든 결함 · 덜 고친 것 · 사실 오류, 넘긴다 = main부터 · 문체 · 재현 못 한 가정, 2회차는 고친 줄만 보고 3회차는 없다.」
  - 후: 「사용자가 서브에이전트 리뷰를 요청했다. 결과를 보기 전에 범위와 기준을 정했다. 리뷰어는 읽기 전용으로 셋을 두고, 각각 주소와 라우팅, 모듈 이동과 부팅과 테스트, 문서를 맡겼다. 이 PR이 만든 결함, 덜 고친 부분, 사실 오류는 고친다. main부터 있던 문제, 문체, 재현하지 못한 추정은 후속으로 넘긴다. 리뷰는 2회까지 하며, 2회차는 수정한 줄만 본다.」
- 「개정 블록을 본문에 녹인다」는 비유였다. 사용자가 「녹일지는 무슨 뜻이니」라고 물었다. 「개정 내용을 본문에 반영하고 개정 블록을 삭제한다」로 쓴다.
- 고쳐 쓴 글이 「그 절이 원래 있던 장」처럼 용어를 풀어 늘어졌다. 사용자가 「한국어 문장은 완결된 형태이지만 간결해야 해. 도메인에 맞는 용어를 쓸 것」이라고 했다. 「본래 장」으로 쓴다.

**규칙:**
- 문장은 완결된 형태로 쓰되 간결하게 쓴다. 한 문장에는 한 가지를 말한다.
- 명사를 나열하지 않는다. 조사와 서술어로 관계를 밝힌다. 「고친다 = 결함」이 아니라 「결함은 고친다」다.
- 가운뎃점은 짧은 낱말 두세 개를 나란히 둘 때만 쓴다. 줄표로 덧말을 잇지 않고, 괄호를 겹치지 않는다.
- 그 분야의 용어를 쓴다. 문서 작업은 「반영」 · 「삭제」 · 「갱신」, 성서는 「본문」 · 「장절」 · 「본래 장」이다. 이 저장소에 자리 잡은 말(「옮겨 실린 절」, 「그리스어 추가 본문」)은 그대로 쓴다. 쉽게 쓰겠다고 용어를 긴 설명으로 바꾸지 않는다.
- 비유로 말하지 않는다.
- 사용자의 말은 「사용자가 …라고 했다」로 인용한다.
- 「A 주소 · 라우팅」처럼 기호를 붙여 부르지 않는다.
- 보내기 전에 소리 내어 읽듯 한 번 읽는다. 조사와 서술어 없이 이어진 줄, 같은 말을 되풀이한 줄은 고친다.

### pitfalls §40 — 주제 문서도 개발을 모르는 독자가 읽을 수 있게 쓴다 (사용자 교정, 2026-10-23)

주제 문서는 Claude가 작업할 때 읽는 문서라, 함정의 사례를 코드 줄과 함수 이름과 영어 기술 용어로 적었다. 사용자는 개발을 전문으로 하지 않아서, 그 글을 읽고 무슨 일이 있었는지 알 수 없었다.

**사례:**
- PR #373(`docs/changes/2026-10-23-prose-small-topics.md`)에서 오디오 주제 문서의 pitfalls §15를 고쳐 쓴 글. 사용자가 두 가지를 짚었다.
  - 「크기가 0이 들어가 LRU 상한이 사실상 듣지 않는다」에 사용자가 「"듣지 않는다." 이해하기 어렵네. LRU 상한선이 무력화된다는 의미?」라고 했다. 「약이 듣다」에 기댄 표현이었다. 「상한이 작동하지 않는다」로 고쳤다.
  - 사례 H1의 「`sw.js:139`가 `byteSize = cl ? Number(cl) : 0`로 적었다」에 사용자가 「기술을 모르는 독자가 이해할 수 있게 무슨 용도인지 기술 바람. H2, H3 또한 기술 용어를 중심으로 서술되어 있어 이해하기 어려움. 네가 볼 문서지만, 나도 좀 이해할 수 있으면 좋겠다」라고 했다.
- 같은 PR에서 캐시 무효화를 풀어 쓴 「판 번호를 올리면」에 사용자가 「판 번호 -> 버전」이라고 고쳤다.

**규칙:**
- 문서의 독자는 Claude와 사용자 둘이다. 사용자가 읽고 무슨 일이 있었는지, 왜 문제인지 알 수 있게 쓴다.
- 코드 이름과 줄 번호는 지우지 않는다. 그 코드가 무엇을 하는지 한국어로 먼저 쓰고, 이름은 괄호에 둔다: 「mp3를 저장하면서 크기를 적는 코드(`sw.js:139`)」.
- 결과는 사용자가 겪는 일로 쓴다: 「막 재생하려던 mp3가 지워져 재생이 끊긴다」, 「저장해 둔 성경 본문까지 사라진다」.
- 처음 나오는 기술 용어(Cache API, IndexedDB, Content-Length)는 무엇인지 한 번 덧붙이고, 그다음부터는 용어만 쓴다. 용어를 설명으로 바꾸지 않으므로 pitfalls §37과 부딪치지 않는다.
- 다른 뜻에 기댄 동사(「듣다」)를 쓰지 않는다. 「작동한다」, 「적용된다」로 쓴다.
