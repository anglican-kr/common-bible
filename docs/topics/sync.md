# Drive 동기화, OAuth

소유 코드: `js/drive-sync.js`, `js/sync/*.js`

북마크와 설정을 사용자의 Google Drive(앱 전용 숨은 폴더 appdata)에 동기화하는 일과, 로그인(OAuth PKCE)과 토큰 교환을 다룬다. 토큰 교환은 서버의 nginx가 대신 해 준다(BFF). 동기화 저장소의 형식과 병합 규칙은 이 문서가, 북마크 자체는 북마크 주제 문서(`topics/bookmark.md`)가 다룬다.

## 지금 동작

- **동기화로 받은 결과를 저장하지 못하면 드라이브에 올리지 않는다** (2026-10-26, ADR-015 D7, known-issues §15.4).
  - 기기의 저장 공간이 차면 병합 결과의 저장이 거절된다. 올릴 자료를 만드는 함수(`buildSyncPayload`)는 기기에 저장된 문서를 읽는다. 그래서 2026-10-26 전에는 병합 결과를 저장하지 못해도 기기에 남은 옛 문서를 올려, 드라이브의 파일을 다른 기기의 변경이 빠진 문서로 덮어썼다. 두 기기를 흉내 낸 e2e에서 다른 기기가 올린 북마크가 드라이브에서 사라졌다(그 기기가 다시 동기화하면 돌아온다). 화면에는 「다른 기기에서 변경된 데이터를 불러왔습니다.」가 떴다.
  - 이제 저장하지 못하면 올리지도, 동기화 캐시(드라이브 파일의 id와 마지막으로 맞춘 버전을 기억해 두는 값)를 쓰지도 않고 동기화를 마친다. 다음 동기화가 다시 내려받아 병합한다.
  - 안내는 「저장 공간이 가득 차 다른 기기에서 변경된 데이터를 불러오지 못했습니다. 쓰지 않는 북마크를 지우면 다시 동기화합니다.」이고(사용자 결정 2026-10-26), 저장 공간이 아닌 까닭이면 「다른 기기에서 변경된 데이터를 불러오지 못했습니다.」다. 동기화할 때마다 실패하면 그때마다 알린다.
  - 다른 기기의 변경이 없다고 판단돼도 올리지 않는다. 「다른 기기의 변경」은 수정 시각이 커졌는지로 판단하는데, 수정 시각이 같은 두 사본은 병합이 기기 id 순서로 원격 쪽을 고를 수 있어 기기에 저장된 문서가 병합 결과와 다를 수 있다(PR #445 리뷰). 그래서 이 기기에만 있는 편집은 저장 공간이 생길 때까지 드라이브에 올라가지 않는다. 다른 기기의 변경이 없으면 알리지 않는다. 사용자 결정 2026-10-26.
  - 병합 결과를 저장한 뒤 옛 키 쓰기가 거절돼도 동기화를 이어 간다. 옛 키는 키마다 따로 써서, 하나가 거절돼도 나머지를 쓴다(`applyToLegacyKeys`). 그전에는 이 거절이 동기화의 예외가 되어 「동기화 중 오류가 발생했습니다. 설정에서 재연결해 주세요.」가 뜨고 동기화가 멈췄다. 저장 공간이 찬 동안은 다시 연결해도 같은 오류가 났다.
- **북마크의 Google Drive 동기화** (ADR-011).
  - 로그인은 PKCE 방식 하나만 쓴다(2026-05-08). 토큰을 교환하는 요청은 nginx BFF가 대신 보낸다(ADR-017).
  - Google OAuth 앱 검수를 통과했다(2026-05-19). 그래서 로그인을 유지하는 토큰(refresh token)의 유효 기간(TTL)이 영구가 됐다. 코드 변경 0.
  - 자세한 내용은 `docs/archive/design/pkce-migration.md`, ADR-017, `docs/archive/audit/2026-05-07-pkce-refresh-token.md`에 있다.
- **저장할 때 앞뒤 순서가 그대로인 항목은 순서 값과 수정 시각을 그대로 둔다** (2026-10-26, ADR-011 Phase 2c 「순서 값」).
  - 그 전에는 저장할 때마다 같은 폴더 안의 순서 값을 0부터 다시 매겼다. 그래서 하나를 지우거나 옮기면 뒤의 손대지 않은 항목까지 새 수정 시각을 받아, 다른 기기에서 그 항목을 고친 것을 동기화에서 이겼다(PR #438 리뷰, 사용자 결정).
  - 이제는 옮기거나 새로 넣은 항목만 새 값을 받는다. 다만 북마크를 한 칸 아래로 옮기면, 옮긴 북마크 대신 바로 아래에 있던 북마크가 새 시각을 받는다. 한 칸 아래로 옮긴 것과 바로 아래에 있던 북마크를 한 칸 위로 올린 것은 저장 결과가 같아 가릴 수 없기 때문이다.
  - 값이 같은 항목은 id 순서로 놓는다. 두 기기가 동시에 서로 다른 항목을 맨 앞으로 옮기면 둘 다 같은 값을 받는데, 그전에는 기기마다 순서가 다르게 보였다.
- **동기화 저장소는 기본 속성 이름의 id에도 멈추지 않는다** (2026-10-26, known-issues §15.2).
  - 저장소(`js/sync/store-v2.js`)는 북마크를 id를 키로 하는 일반 객체에 둔다. 일반 객체는 `toString`, `constructor` 같은 기본 속성 이름에 물려받은 함수로 답한다. 그래서 그런 id가 하나만 있어도 새로 고친 뒤 장 화면부터 그려지지 않았다(2026-10-19 실측).
  - 이제 부모 id로 묶을 때는 `Map`을 쓰고, id로 찾을 때는 그 객체가 직접 가진 항목만 본다. 같은 원인으로 기기끼리 병합할 때 한쪽에만 있는 그런 id의 북마크가 빠지던 것과, 그런 id의 북마크를 지워도 삭제 기록이 남지 않던 것도 함께 고쳤다.
  - `__proto__` id는 저장하지 않는다. 이 id를 일반 객체에 넣으면 항목이 되지 않고 객체의 프로토타입이 바뀐다. 병합도 이 id를 건너뛴다(ADR-011 「설정 병합 전방 호환」). 그 id의 폴더는 폴더만 빼고, 안의 항목은 폴더가 있던 자리로 올려 저장한다. 고치기 전 판은 폴더만 잃고 안의 항목을 부모 id `__proto__`로 남겼는데, 그런 항목은 맨 위 항목 뒤에서 읽는다. 그 항목의 순서 값은 옛 폴더 안에서 매긴 것이라, 맨 위 항목 사이에 섞으면 손대지 않은 맨 위 항목의 수정 시각까지 올라 다른 기기의 수정을 이긴다. 둘 다 그대로 두면 목록에 보이지 않다가 다음 저장 때 삭제 기록이 되어 모든 기기에서 지워졌다(PR #438 리뷰).
  - 이런 id는 가져오기 검사(ADR-040)가 막는다. 그러나 검사가 없는 판(1.6.4 이하)에서 들인 기록은 동기화로 들어온다. 고치기 전 판을 쓰는 기기는 그 id에서 여전히 멈추므로 검사는 그대로 둔다.

## 함정

### pitfalls §12 — 로그인 방식을 바꾸면, 주소에서 인증 정보를 지우는 코드가 새 자리를 놓친다

Google 로그인을 마치면 브라우저는 앱 주소로 돌아오면서 인증 정보를 주소 뒤에 붙여 온다(OAuth callback). 정보가 붙는 자리는 로그인 방식(flow)마다 다르다. 옛 방식(Implicit Flow)은 `#` 뒤(fragment, `#access_token=...`)에, 지금 방식(PKCE)은 `?` 뒤(query string, `?code=...`)에 붙인다. 앱은 정보를 읽은 뒤 주소에서 지워야 한다. 지우는 코드가 한 방식의 자리만 생각하고 짜였다면, 방식을 바꾼 뒤 새 자리의 인증 정보가 주소창, 브라우저 기록, 로그에 남아 새어 나갈(leak) 수 있다.

**사례 (Phase 2h PKCE 마이그레이션 — Bugbot PR #54-2):**

- `3a7c8ab` — Implicit Flow 시절, 페이지를 열 때 한 번 도는 로그인 처리 코드(IIFE)는 확인에 실패한 경우(`bad_state`, `no_state`, `state_mismatch`)에 주소를 `history.replaceState(null, "", location.pathname + location.search)`로 고쳤다. `#` 뒤만 지우고 `?` 뒤(search)는 남기는 코드다. 그때는 인증 정보가 `#` 뒤에 왔으므로 안전했다. PKCE로 바꾼 뒤에는 정보가 `?code=...&state=...`로 오므로, 같은 코드가 인증 코드(auth code)를 주소창에 남겼다.

**규칙:**

- 로그인 방식을 바꿀 때는, 주소를 지우는 코드가 새 방식이 정보를 붙이는 자리까지 지우는지 따로 확인한다.
- 기본 원칙: 앱이 주소의 `?` 뒤나 `#` 뒤를 라우팅에 쓰지 않는다면, 로그인 확인에 실패한 경우에는 `location.pathname`만 남기고 search와 hash를 둘 다 지우는 것이 가장 안전하다.
- 회귀 방어: 로그인 처리 코드(IIFE)가 끝난 뒤 `location.search`/`location.hash`에 `?code=`, `#access_token=` 같은 값이 남지 않는지 e2e 테스트로 직접 확인한다.

### pitfalls §13 — 로그인 방식을 옮길 때는 방식마다 저장소 키를 따로 쓴다

로그인을 시작할 때 앱은, 돌아왔을 때 확인할 값을 브라우저 저장소(sessionStorage, localStorage)에 적어 둔다. 옛 방식과 새 방식이 같은 키를 쓰면, 새 코드를 머지해 배포하는 순간 로그인 도중이던 사용자의 콜백이 엉뚱한 방식으로 처리되거나 아예 처리되지 않는다. 방식마다 다른 키를 써서, 서로의 값을 절대 읽지 않게 해야 한다.

**사례 (Phase 2h PKCE 마이그레이션):**

- 단계 2-4에서 Implicit Flow는 `bible-drive-redirect-state`, PKCE는 `bible-drive-redirect-state-pkce` 키를 썼다. 단계 4를 머지한 순간 로그인 도중이던 PKCE 콜백은 새 코드도 같은 `-pkce` 키를 읽어 정상으로 처리됐다. 로그인 도중이던 Implicit 콜백은 새 코드가 읽지 않았고, sessionStorage는 탭을 닫으면 지워지므로 저절로 사라졌다.
- 단계 4에서 함수 이름을 `beginRedirectAuthPKCE`에서 `beginRedirectAuth`로 바꿀 때, **변수 이름만 새 이름으로 바꾸고 저장소 키 값은 일부러 `-pkce` 접미사를 그대로 두었다.** 둘을 함께 바꾸면 로그인 도중이던(in-flight) 콜백이 처리되지 않는다.

**규칙:**

- 서로 다른 로그인 방식이나 라우팅 방식에는 처음부터 다른 저장소 키를 준다.
- 키 이름을 바꾸는 이행은 두 단계로 한다. (1) 새 키를 쓰기 시작하고, 옛 키는 읽기만 한다. (2) 옛 키를 지운다. 한 PR에 함께 넣지 않는다.
- 더 쓰지 않는 localStorage 키는 단계 5처럼 따로 정리하는 단계에서 지운다. 로그인 처리 코드(IIFE)에 `localStorage.removeItem(...)`을 더해, 기존 사용자의 기기에서 지우는 것이다. 몇 릴리스 뒤에는 이 정리 코드도 없앤다.

### pitfalls §28 — 실패를 「없음」이나 「성공」과 같은 값으로 돌려주면, 동기화가 오류를 성공으로 친다 (2026-10-17)

Drive와 주고받는 함수(전송 함수)가 실패를 정상 결과와 같은 값(`null`, `doc: null`)으로 돌려주면, 그 값을 받은 코드는 정상적인 경우(「파일 없음」, 「원격 없음」)로 처리한다. 실패가 성공이 되어, 다시 시도하지도 사용자에게 알리지도 않는다. 같은 함수 안에서 한 경우만 실패 검사를 빠뜨려도 같은 일이 생긴다.

**사례**(원장 `docs/changes/2026-10-17-sync-signout-inflight.md`의 머지 전 검토 1번과 3번, 사용자가 돌린 `/code-review`의 3-6번):
- `findSyncFileId`(`js/sync/transport.js`)는 Drive에서 동기화 파일을 찾는 함수다. 어떤 실패든 `null`(「파일 없음」)을 돌려줬다. 그래서 파일 id를 기억해 두지 않은 상태에서 목록 요청이 잠깐 실패하면, 앱이 파일이 없다고 보고 새로 만들었다. 이미 있는 sync.json 옆에 하나가 더 생길 수 있었다. 이제 `{ fileId, fileIds, status }`를 돌려주고, 동기화 한 번(사이클)은 실패인지를 먼저 가른다.
- 내려받기가 403, 429, 400으로 실패해도 `doc: null`을 돌려줘 「원격 없음」으로 읽혔고, 동기화가 끝난 것(SYNC_DONE)으로 처리됐다. 다시 시도하지 않았고, redirect 시도 횟수까지 0으로 돌렸다.
- v1 문서를 v2로 올리는 업로드에만 `!ok` 검사가 없었다. 그래서 서버 오류(5xx)가 나도 「동기화됨」으로 처리했다(캐시를 기록하고 SYNC_DONE). 다른 업로드 경우에는 모두 검사가 있었다.
- 내려받는 도중 연결이 끊겨 응답 본문을 읽지 못하면(`res.json()`이 reject), 상태 코드는 2xx인데 결과가 `{ doc: null, status: 200 }`이라 「원격 없음」 성공으로 끝났다. 찾기에서 고친 결함이 내려받기에 남아 있던 것이다(main부터). 테스트 하네스의 기본 스텁이 바로 그 응답을 정상으로 써서 유닛 테스트가 잡지 못했다. 이제 status 0(실패)이다.
- 실패하면 백오프(간격을 늘려 가며 다시 시도) 다섯 번 뒤 OFFLINE 상태로 보냈다. 그런데 OFFLINE은 브라우저의 `online` 이벤트로만 빠져나온다. 인터넷에 연결된 기기에서 HTTP 실패(429, 5xx)가 이어지면 그 이벤트가 오지 않아, 그 세션 내내 동기화가 멈췄다.
- 「파일도 삭제」의 결과는 `true`와 `false` 둘뿐이었다. 그래서 연결돼 있지 않아 아무것도 하지 않은 경우도 `false`가 되어, 「삭제하지 못했습니다」라는 거짓 안내가 떴다. 반대로 목록의 첫 파일만 지운 경우에도 `true`가 나와, 겹친 sync.json이 남아도 「지웠다」고 했다.
- 2026-10-26(known-issues §15.4): 동기화 저장소에 쓰는 함수(`store-v2.js saveLocal`)가 저장 공간이 차서 거절된 쓰기를 알리지 않았다. 동기화는 병합 결과가 저장된 것으로 보고 「불러왔습니다」를 띄웠고, 기기에 남은 옛 문서를 드라이브에 올렸다. 이제 저장 결과를 셋으로 돌려준다(`"saved"`, `"full"`, `"failed"`, ADR-015 D7).

**규칙:**
- 「없음」과 「실패」는 다른 값으로, 상태 코드와 함께 돌려준다. 받는 코드는 실패인지를 먼저 가른 뒤에 「없음」을 읽는다. 본문을 읽지 못한 2xx도 실패다.
- 한 함수 안의 여러 경우가 같은 실패 분류를 쓰는지 나란히 놓고 본다. 한 경우만 빠뜨리기 쉽다. 테스트 하네스의 기본 스텁이 「실패 같은 성공」(`doc: null`, 200)이면 그 응답이 정상으로 굳는다.
- 되돌릴 수 없는 작업의 결과는 셋으로 가른다. 됨(`true`), 확인 못 함(`false`), 할 일 없음(`null`)이다. 사용자에게는 「확인 못 함」만 알린다. 「됨」은 확인한 만큼만 말한다. 그 범위는 목록의 모든 항목, 기억해 둔 id, 이 페이지가 만든 id다. 목록에는 방금 만든 파일이 늦게 보일 수 있다.
- 다시 시도할지는 서비스의 안내를 따른다. Drive는 403 rate limit, 429, 5xx를 지수 백오프로 다시 시도하라고 안내한다([오류 처리 안내](https://developers.google.com/workspace/drive/api/guides/handle-errors), 2026-10-17 확인). 이 앱은 상태 코드로만 갈라 실패를 모두 백오프(최대 다섯 번)한다. 그래도 실패하면 네트워크 실패만 OFFLINE으로 보내고, HTTP 실패는 IDLE로 돌아가 다음 요청 때 다시 시도한다. 다시 해도 소용없는 400과 그 밖의 403은 다섯 번에서 멈춘다. 403의 이유를 읽어 가르지는 않는다.
- 실패로 들어가는 상태마다 빠져나오는 길을 적고, 그 길이 오지 않는 경우가 없는지 본다. 온라인인 채로 `online` 이벤트를 기다리는 OFFLINE이 그런 경우다.
- 저장소에 쓰는 함수도 결과를 돌려준다. 거절된 쓰기를 성공처럼 처리하면, 그다음 단계(올리기, 다시 그리기)가 기기에 남은 옛 값을 읽어 드라이브에 올리거나 화면에 그린다. 설정과 읽던 위치의 저장은 아직 결과를 돌려주지 않는다(known-issues §35).

## 남은 일

- **known-issues §15.5** **앱이 모르는 필드만 바뀐 항목은 동기화되지 않는다**(main부터).
  - 가져오기는 앱이 모르는 필드를 지우지 않고 그대로 둔다. 다음 버전의 앱이 더한 필드가 살아남게 하려는 것이다.
  - 그런데 동기화 저장소가 항목이 바뀌었는지 볼 때 쓰는 내용 키(`store-v2.js _contentKey`)는 아는 필드만 비교한다. 그래서 모르는 필드만 바뀐 항목은 수정 표시(`_u`)가 오르지 않아 다른 기기로 가지 않는다.
  - 다음 버전의 앱이 필드를 더할 때 함께 본다.

### known-issues §32 — 한 기기에서 지운 폴더에 다른 기기가 넣은 북마크가 지워진다 (2026-10-26)

PR #438 리뷰 중에 실제 `store-v2.js`의 `mergeDocs`로 두 기기를 흉내 내 확인했다. 지금 앱(main)에서도 똑같이 생긴다.

- A 기기가 폴더를 지우면 폴더와 안의 항목에 삭제 기록이 붙는다. 그사이 B 기기가 그 폴더에 북마크를 더하면, 병합 결과에서 폴더는 지워지고 새 북마크는 부모 id만 남는다.
- 부모가 없는 항목은 목록을 맨 위부터 그릴 때 나오지 않는다. 그리고 병합 결과를 받은 기기 가운데 어느 기기든(A도) 다음에 저장할 때 삭제 기록이 되어 모든 기기에서 지워진다. 사용자에게는 방금 넣은 북마크가 말없이 사라진 것으로 보인다.
- **고칠 방향**(정하지 않음): 부모를 잃은 항목을 맨 위 항목 뒤에서 읽는다(부모 id가 `__proto__`인 항목을 읽는 방식과 같다). 또는 지운 폴더를 되살린다. 사용자가 고른다.

### known-issues §33 — 동기화 자료가 커질 때 넘을 수 있는 한도 (2026-10-26)

지금 쓰는 양은 아래 한도보다 훨씬 작다. 북마크가 수천 개로 늘거나 절 노트처럼 큰 자료를 동기화에 넣게 되면 이 절을 다시 본다. 구글 문서는 2026-10-26에 확인했다.

- **파일 하나는 5MB까지만 한 번에 올릴 수 있다.** 앱은 `sync.json`을 요청 한 번으로 통째로 올린다(`transport.js uploadSyncFile`, `uploadType=media`와 `uploadType=multipart`). 구글은 이 방식을 5MB 이하 파일에 쓰고, 더 큰 파일은 나눠 올리는 방식(`uploadType=resumable`)을 쓰라고 안내한다([업로드 안내](https://developers.google.com/workspace/drive/api/guides/manage-uploads)). 5MB를 넘는 파일을 보내면 어떤 오류가 오는지는 문서에 없다.
- **기기 저장소가 드라이브보다 먼저 찬다.** 앱은 북마크를 브라우저 저장소에 두 벌 저장한다(옛 키와 동기화 저장소, `storage.js saveBookmarks`). Safari는 이 저장소를 5MiB까지 주고 글자 하나를 2바이트로 센다(`topics/bookmark.md` 「지금 동작」). 앱이 만드는 것과 같은 필드와 식별자로 임의의 북마크를 만들어 잰 크기는 아래와 같다. 기기 저장소의 개수는 다른 키를 빼지 않은 값이다.

  | | 드라이브의 `sync.json` | Safari 기기 저장소 |
  | --- | --- | --- |
  | 북마크 하나, 메모 없음 | 약 230바이트 | 약 740바이트 |
  | 북마크 하나, 한글 100자 메모 | 약 530바이트 | 약 1,140바이트 |
  | 5MB에 드는 개수, 메모 없음 | 약 23,000개 | 약 7,000개 |
  | 5MB에 드는 개수, 100자 메모 | 약 10,000개 | 약 4,600개 |

  기기 저장소가 꽉 차면 북마크를 저장하지 못했다고 스낵바로 알린다(2026-10-26부터, ADR-015 D7).
- **숨은 폴더도 사용자의 구글 저장 공간을 쓴다.** 무료 계정은 15GB를 Gmail, 드라이브, 구글 포토가 함께 쓰고, 「hidden app data」도 여기에 센다([Google One 도움말](https://support.google.com/googleone/answer/9312312)). 공간이 꽉 찬 계정에 올리면 구글은 403 오류(`storageQuotaExceeded`)를 돌려준다([오류 처리 안내](https://developers.google.com/workspace/drive/api/guides/handle-errors)). 앱은 403의 이유를 읽지 않으므로 다른 실패처럼 다섯 번 다시 시도하고, 그래도 실패하면 다음 동기화 요청 때 처음부터 다시 시도한다(`state-machine.js`, pitfalls §28). 그동안 사용자에게 무엇이 보이는지는 확인하지 않았다.
- **요청량에도 한도가 있다.** 구글은 요청량을 할당 단위로 센다. 파일 고치기는 50, 목록 보기는 100, 내려받기는 200단위다. 사용자 한 명은 1분에 325,000단위, 앱 전체(Google Cloud 프로젝트)는 1분에 1,000,000단위, 하루에 4억 단위까지 쓸 수 있다([사용량 한도](https://developers.google.com/workspace/drive/api/guides/limits)). 동기화 한 번이 목록 보기, 내려받기, 올리기를 모두 해도 약 350단위이므로 앱 전체로 1분에 약 2,800번이다. 구글은 한도를 넘는 사용에 2026년 안에 요금을 매길 예정이고, 시행 90일 전에 알린다고 적었다. 2025-11부터 2026-04 사이에 이 API를 쓴 프로젝트는 옛 한도를 그대로 쓴다. 이 앱의 프로젝트가 어느 쪽인지는 Google Cloud 콘솔에서 확인하지 않았다.
- **할 일**: 위 상황이 오면 기기 저장소를 IndexedDB(브라우저의 더 큰 저장소)로 옮기는 일(ADR-015)과, 5MB를 넘는 파일을 나눠 올리는 방식을 함께 정한다.

### known-issues §34 — 옛 버전의 목록을 처음 옮길 때 저장 공간이 모자라면 목록이 계속 비어 보이고, 다음 저장이 옛 목록을 지운다 (2026-10-26)

- 동기화 저장소가 생기기 전의 버전(북마크가 나온 2026-04-25부터 ADR-011 Phase 2c를 구현한 05-04까지)은 북마크를 옛 키(`bible-bookmarks`)에만 저장했다. 지금 앱은 시작할 때 이 목록을 동기화 저장소로 한 번 옮긴다(`store-v2.js migrateLegacyIfNeeded`). 동기화 저장소의 사본은 옛 키보다 크다.
- 앱은 옮기는 저장이 거절됐는지 확인하지 않는다. 목록은 동기화 저장소를 읽으므로 빈 목록이 보인다.
- 장을 하나 열면 읽던 위치가 동기화 저장소에 저장된다(`saveLastRead`). 옮기는 함수는 동기화 저장소의 키가 있는지만 보고 옮겼다고 판단하므로, 그 뒤로는 옮기기를 다시 시도하지 않는다. 저장 공간을 비워도 목록은 계속 비어 보인다.
- 그 상태에서 북마크 하나를 저장하면 동기화 저장소와 옛 키가 모두 그 하나로 바뀌어, 옛 목록이 지워진다.
- 2026-10-26에 WebKit의 셈을 흉내 낸 저장소(5 MiB, 한글이 든 값은 한 글자 2바이트)에서 실제 동기화 저장소 코드(`store-v2.js`)와 저장소 모듈(`storage.js`)을 실행해 확인했다. 메모 없는 북마크가 옛 키에만 7,000개면 옮겨지고, 8,000개면 위와 같다. 이 변경 전의 앱에서도 같다.
- 그 9일 동안 북마크를 그만큼 저장해 둔 채, 그 뒤 처음으로 앱을 업데이트하는 기기만 해당한다.
- **고치는 법**(정하지 않음): 옮겼는지를 동기화 저장소의 키가 있는지로 판단하지 않는다. 옮기는 저장이 거절되면 옛 키의 목록을 보이고, 옮길 수 있을 때까지 저장을 막고 알린다.

### known-issues §35 — 설정과 읽던 위치를 저장할 때는 동기화 저장소 쓰기가 거절돼도 알리지 않는다 (2026-10-26)

- 설정(`storage.js saveFontSize` 등)과 읽던 위치(`saveReadingPosition`)는 각자의 키에 먼저 쓰고, 그다음 동기화 저장소에 쓴다(`syncStoreV2.saveSetting`, `saveLastRead`). 앱은 동기화 저장소 쓰기의 결과(ADR-015 D7)를 확인하지 않는다.
- 저장 공간이 차서 동기화 저장소 쓰기가 거절되면, 그 값은 이 기기의 키에만 남고 다른 기기에 동기화되지 않는다. 나중에 동기화가 병합 결과를 저장하면 동기화 문서에 남은 옛 값이 이 기기의 키에도 다시 써질 수 있어, 이 기기에서도 다음 시작 때 옛 값으로 돌아간다. 사용자는 알 수 없다.
- 반대로 동기화가 받은 설정을 이 기기의 키에 쓰다 거절되면(`applyToLegacyKeys`), 이번 화면에는 반영되지만 다음 시작 때 옛 값이 보인다. 원격이 다시 바뀌어 병합할 때까지 그대로다.
- 2026-10-26 북마크 저장 실패 안내(known-issues §15.4)의 범위를 정할 때, 사용자가 북마크와 동기화 결과까지만 다루기로 했다.
- **고치는 법**(정하지 않음): 북마크처럼 결과를 확인하고 알릴지, 읽던 위치처럼 자주 저장하는 값은 알리지 않을지 함께 정한다. 앱이 시작할 때 설정을 동기화 저장소에서 읽게 할지도 함께 본다.
