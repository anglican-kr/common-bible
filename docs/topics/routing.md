# 라우팅, 뷰, 탭 바, 오버레이

소유 코드: `js/app/routing.js`, `js/app/views.js`, `js/app/tabbar.js`, `js/app/tab-history.js`, `js/app/overlay.js`, `js/app/reading-context.js`

주소 해석과 화면 전환(History API), 장 화면과 성서 목록을 그리는 뷰, 하단 탭 바와 탭별 위치 복원, 모달과 시트가 함께 쓰는 오버레이를 다룬다.

- **모바일 하단 탭 바** (2026-06-03, ADR-029).
  - 흩어져 있던 내비게이션을 모바일 화면 아래에 떠 있는 탭 바 하나로 모았다. 탭은 홈, 검색, 북마크, 설정 넷이고, iOS의 Liquid Glass처럼 캡슐 모양이다. 탭마다 전체 화면을 쓰는 라우트다.
  - 북마크 전체 화면은 ⋯ 팝업 메뉴와 행 스와이프로 관리한다. 메뉴에는 새 폴더, 내보내기, 가져오기, 정렬(정렬 기준, 오름차순과 내림차순), 선택이 있다. 행을 양쪽으로 밀면 수정과 삭제가 나온다.
  - ⋯ 메뉴의 「선택」은 여러 항목을 골라 한 번에 처리하는 선택 모드(`#bm-select-bar`)다. 공유는 `SITE_BASE` 링크를 만들어 `navigator.share`로 보내고, 이동은 폴더 선택 창에서 옮길 곳을 고르고, 삭제는 안에 든 것까지 함께 지운다(cascade). 폴더를 지울 때도 내용물까지 지운다.
  - 데스크톱은 기존 헤더와 드로어를 그대로 쓴다.
  - **모바일과 데스크톱은 화면 너비와 포인터 종류로 구분한다**(2026-06-09 개정). 너비가 768px 이하이거나 손가락으로 쓰는 화면(`(max-width:768px), (pointer:coarse)`)이면 모바일이다. 너비가 769px 이상이고 마우스처럼 정밀한 포인터를 쓰면(`(min-width:769px) and (pointer:fine)`) 데스크톱이다. 그래서 가로로 돌린 폰과 태블릿(아이패드 포함)도 탭 바를 쓴다.
  - 자세한 내용과 개정 이력은 ADR-029와 ADR-010에 있다.
- **모핑 탭 바** (2026-06-04, ADR-030).
  - 탭 이름을 지우고 아이콘만 남겼다. 검색은 따로 떨어진 원형 단추가 됐다.
  - 검색 원형 단추를 누르면 알약 모양 입력창으로 바뀐다(모핑).
  - 읽기 화면에서 본문을 스크롤해 내려가면 탭 바가 홈과 검색 원형 단추로 줄어든다. 오디오를 재생하는 중이면 오디오 플레이어도 그 사이로 작게 들어간다.
  - 리퀴드 글라스 질감을 절제해 넣고, 탭 사이를 미끄러지는 표시(`positionTabIndicator`)를 두었다. 절 선택 막대(`#verse-select-bar`)도 탭 바와 같은 모양으로 맞췄다.
  - 자세한 내용과 개정 이력은 ADR-030에 있다.
- **탭별 위치 복원(탭 히스토리)** (2026-06-05, 2026-06-10 개정, ADR-031).
  - 탭(홈, 검색, 북마크, 설정)을 오가다 돌아오면 마지막 화면(라우트)과 스크롤 위치를 되살린다(`js/app/tab-history.js`, `scrollRestoration="manual"`).

  - 「본문 바로가기」는 화면 전환으로 처리하지 않고 본문으로 포커스만 옮긴다.

## 함정

### pitfalls §2 — 상대 경로는 하위 주소에서 새로 고치면 깨진다, 같은 버그가 2회 났다

앱은 History API로 주소를 바꾸므로, 사용자가 `/bible/john/3` 같은 하위 주소에 있을 수 있다. 상대 경로(`./data/...`, `data/...`)는 지금 주소를 바탕으로 해석된다. 그래서 하위 주소에서 새로 고치면 엉뚱한 곳(`/bible/john/data/...`)에서 파일을 찾아 받지 못한다.

**사례 (같은 버그가 두 번 났다):**
- `45eba01`: `index.html`의 상대 경로를 절대 경로로 고쳤다.
- `730aafe`: 같은 버그가 `js/app.js`의 `DATA_DIR`과 `fetch` 호출의 경로에도 있어 따로 고쳤다.

**규칙:**
- 모든 자원 경로는 `/`로 시작한다(예: `/data/books.json`, `/assets/icons/...`).
- 데이터는 상수 `DATA_DIR`을 거쳐서만 받는다.
- 확인: 개발 서버에서 `/bible/john/3` 같은 하위 주소로 바로 들어가, 모든 자원이 200 OK로 오는지 본다.

관련 ADR은 `009-history-api-routing.md`다.

### pitfalls §33 — 이미 받은 모듈도 `import()`를 기다리면 화면이 한 번 번쩍인다 (리뷰, 2026-10-18)

앱은 캘린더처럼 처음 쓸 때 받는 모듈을 `await import(…)`로 불러온다. 이 기다림은 모듈을 이미 받아 둔 뒤에도 바로 끝나지 않는다. Chromium에서는 브라우저가 다른 일 하나(태스크)를 처리한 뒤에야 끝난다. 먼저 예약해 둔 `setTimeout(0)`이나 `postMessage`가 먼저 실행된다(실측). WebKit(Playwright 26.4)은 바로(마이크로태스크로) 끝내서 이 깜박임이 없었다(5번 중 5번, 2회차 리뷰). 엔진마다 다르므로 기다리지 않는 쪽으로 짠다.

기다리는 사이에 브라우저가 화면을 한 번 그릴 수 있어서, `await` 앞에서 바꿔 둔 화면(「불러오는 중…」)이 매번 번쩍인다. 데이터가 이미 메모리에 있는 다시 그리기는 원래 화면을 그리기 전에 끝나던 일이라, 사용자에게는 새로 생긴 깜박임이다.

**사례:**
- PR #355: 캘린더와 전례독서 모듈을 처음 열 때 받도록 바꾸면서, `routing.js`가 그 화면을 그릴 때마다 `await loadViewModule(() => Promise.all([import(…)]))`를 거쳤다. 그래서 달 이동, 칩, 세그먼트, 날짜 이동마다 `renderLoading()`의 「불러오는 중…」이 한 프레임 그려졌다. 달 이동 40번 중 40번이었다(main은 0번). 그 프레임에 스크롤 위치가 맨 위(0)로 바뀌었다가 포커스 복원이 되돌렸고, 데스크톱에서는 접힌 머리가 펼쳐졌다가 다시 접혔다. 마지막 상태만 보는 e2e는 통과했다.

**규칙:**
- 처음 받은 뒤에는 `import()`를 기다리지 않는다. 받은 모듈(또는 쓸 함수)을 변수에 두고 바로 쓴다. 성공한 것만 둔다. 실패를 두면 다시 시도하지 않기 때문이다(`routing.js` `loadedViews`).
- 깜박임은 마지막 상태로는 보이지 않는다. 프레임마다(rAF) 그 요소가 있었는지 세어 본다(`tests/e2e/test_liturgical_lazy_load.py`의 `WATCH_LOADING_FRAMES`).
- 반대로 기다림이 사라지면 「중간 상태」에 기대던 테스트가 깨진다. 같은 PR에서 「오늘 → 다음날 → 전날」 테스트가 `?track=` 없는 중간 주소를 기다리다 실패했다. 트랙이 있는 주일에는 이동과 주소 고치기가 한 태스크 안에 끝나기 때문이다. 주소는 경로만 비교한다.

### pitfalls §34 — WebKit은 미리 받은 모듈(`modulepreload`)을 새로 고쳐도 다시 받지 않아, 미리 받기가 실패하면 그 탭이 막힌다 (리뷰, 2026-10-18)

페이지가 `<link rel="modulepreload">`로 모듈을 미리 받아 두면, WebKit은 그 모듈을 그 탭의 메모리에 남긴다. 새로 고쳐도(`location.reload()`), 같은 주소로 다시 가도 그것을 다시 쓰고 서버에 요청하지 않는다. 미리 받기가 실패했으면 실패가 남아 그 탭에서는 화면이 열리지 않는다(새 탭에서만 열린다). 성공했으면 서버의 파일이 바뀌어도 옛 것이 돈다. 같은 페이지의 다른 파일(`routing.js`, `style.css`)은 새로 고칠 때 바뀌었는지 다시 확인한다(304). Chromium은 새로 고치면 다시 받는다.

**사례:**
- PR #355: 공유 링크로 처음 들어온 캘린더와 전례독서가 늦게 그려지는 문제(1회차 리뷰)를 `pre-fetch.js`의 `modulepreload`로 줄였다(느린 4G에서 늦어지는 시간이 198ms에서 51ms로 줄었다). 2회차 리뷰가 WebKit(Playwright 26.4)에서 calendar.js의 첫 요청을 503으로 실패시켜 보았다. 「다시 불러오기」를 세 번 눌러도, 20초 뒤에 새로 고쳐도 서버 요청은 1회 그대로였다. 미리 받기가 없는 버전은 새로 고치면 다시 받아 열렸다. 서비스 워커가 없는 WebKit 세션(iOS 인앱 브라우저 등)으로 공유 링크를 여는 경우가 바로 미리 받기가 도우려던 경우라서, 미리 받기를 되돌렸다(사용자 결정 2026-10-18).

**규칙:**
- 「새로 고침이 고친다」에 기대는 실패 복구가 있는 모듈에는 `modulepreload`를 적용하지 않는다. 적용하려면 WebKit에서 「실패 → 새로 고침 → 회복」을 먼저 확인한다.
- 미리 받기와 캐시의 동작은 엔진마다 다르다. Chromium으로만 도는 e2e로는 보이지 않으므로, 그런 변경은 WebKit으로 한 번 돌린다. 이 클론의 호스트에는 Playwright WebKit에 필요한 라이브러리가 없어서, 2회차 리뷰어는 필요한 패키지를 임시 폴더에 풀고 `PLAYWRIGHT_BROWSERS_PATH`, `PLAYWRIGHT_SKIP_VALIDATE_HOST_REQUIREMENTS=1`로 띄웠다.

## 남은 일

- **known-issues §10.1** **iOS 18.4 미만에서는 탭한 뒤 다시 그린 화면에 포커스 링이 남을 수 있다. 기기 확인 대기.**
  - WebKit은 손가락으로 탭해도 링크에 포커스를 주지 않는다. 그래서 위치 복원이 스크립트로 준 포커스를 `:focus-visible`로 보고 포커스 링을 그린다(WebKit 소스, 성서 목록 책 카드에서 같은 일을 고친 `43db624`).
  - #350 리뷰에서, 포인터로 누른 뒤의 복원은 `focus({ focusVisible: false })`로 링 없이 두게 했다. 그런데 이 옵션은 Safari 18.4부터 된다.

### known-issues §20 — 노트 탭(ADR-026) 재개 (2026-10-22)

2026-06-03에 1.6.0 계획(ADR-026의 메뉴 라우팅, 노트, 하단 내비, 캘린더)을 멈추고 디자인을 먼저 손보기로 했다. 노트 작업은 원격 브랜치 `release/1.6.0`(`2cda731`)에 main에 없는 커밋 여섯으로 남아 있다. ADR-026 Stage 0, 1a-①, 1a-②, 1b, 동기화 멈춤 수정, 토큰 정렬이며 PR #168과 #174-#177, 약 2,600줄이다. ADR-026 문서도 그 브랜치에만 있다. 캘린더는 ADR-038(#348)로 새로 구현했으므로 그 브랜치의 캘린더는 낡았다. 사용자가 2026-10-22에 노트 탭을 계속하기로 했다.

### known-issues §27 — 제목 헤더의 설정 버튼이 어느 화면 폭에서도 보이지 않는다 (2026-10-23)

설정 버튼은 두 곳에 있다. 데스크톱은 위쪽 행(`#settings-anchor`)의 버튼을 쓴다. 모바일은 처음에 제목 헤더에 넣는 버튼(`.title-settings-btn`)을 썼다(ADR-024). 그 뒤 하단 탭 바(ADR-029, 2026-06-04)가 모바일 설정을 맡으면서 제목 헤더의 버튼도 숨겼다. 그래서 지금은 CSS 규칙 두 개가 이 버튼을 모든 폭에서 숨긴다.

- 데스크톱(`min-width: 769px`이고 `pointer: fine`): `.title-settings-btn`을 숨긴다(ADR-024).
- 모바일(`max-width: 768px`이거나 `pointer: coarse`): `.title-settings-btn`과 `.title-home-btn`을 숨긴다(ADR-029).

그런데 화면을 그릴 때마다 이 버튼을 여전히 만든다. `settings-ui.js`의 `buildSettingsTrigger()`가 버튼을 만들고, `views.js`의 네 화면과 `search.js`의 두 화면이 제목 헤더에 넣는다. 보이지 않는 버튼이라 사용자가 겪는 문제는 없지만, 쓰지 않는 코드일 가능성이 크다. ADR 문장 정리(#385) 때 코드와 견줘 찾았다.

- **조사할 것**: 두 규칙 어디에도 해당하지 않는 환경이 있는지 본다(예: 폭 769px 이상인데 포인터가 fine도 coarse도 아닌 경우). 그런 환경이 없으면 버튼을 만들고 넣는 코드를 지운다.
- **함께 고칠 곳**: 제목 글자가 헤더 버튼에 가려지지 않게 양쪽 여백을 재는 코드(`views.js`의 `measureTitleCompactness`)가 이 버튼도 센다. 숨은 버튼은 폭이 0이라 건너뛴다. 그 주석은 모바일에서 기어가 제목 행 오른쪽 끝에 있고 북마크가 `right: 2.4rem`이라고 적었는데, 지금 배치와 다르다. `tests/unit/views.test.js`에는 이 버튼을 누르면 장 선택 팝오버가 닫히는지 보는 테스트가 있다. 버튼을 지우면 이 둘과 CSS 규칙 두 개, ADR-024 「결정」 4를 함께 고친다.
