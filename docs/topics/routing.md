## 함정

### pitfalls §2 — SPA 경로 해석 오류 — 2회 반복 재발

상대 경로(`./data/...` 또는 `data/...`)는 현재 URL을 기준으로 해석되므로, History API 라우팅으로 하위 URL(`/bible/john/3`)에서 새로고침하면 자원 로드가 깨진다.

**사례 (같은 버그 형태가 2번 반복):**
- `45eba01` — `index.html`의 상대 경로를 절대 경로로 수정.
- `730aafe` — 같은 버그가 `js/app.js`의 `DATA_DIR` 및 fetch 경로에 또 있어 별도 커밋으로 수정.

**규칙:**
- 모든 자원 경로는 `/`로 시작 (예: `/data/books.json`, `/assets/icons/...`).
- 데이터 페치는 상수화된 `DATA_DIR`을 통해서만 접근한다.
- 검증: 개발 서버에서 `/bible/john/3` 같은 하위 URL에 직접 진입했을 때 모든 자원이 200 OK인지 확인.

관련 ADR: `009-history-api-routing.md`.

### pitfalls §33 — 이미 받은 모듈도 `import()`는 한 태스크 뒤에 풀린다 — 다시 그리는 길에서 기다리지 않는다 (리뷰, 2026-10-18)

`await import(…)`는 모듈이 이미 모듈 맵에 있어도 바로(마이크로태스크로) 풀리지 않는다 — Chromium에서는 태스크 하나 뒤에 풀린다(먼저 건 `setTimeout(0)` · `postMessage`가 먼저 돈다 — 실측). WebKit(Playwright 26.4)은 마이크로태스크로 풀어 이 깜박임이 없었다(5번 중 5번 — 2회차 리뷰). 엔진마다 다르니 기다리지 않는 쪽으로 짠다. 그 사이에 브라우저가 한 프레임을 그릴 수 있어, `await` 앞에서 바꿔 둔 화면(「불러오는 중…」)이 매번 번쩍인다. 데이터가 메모리에 있는 다시 그리기는 원래 그리기 전에 끝나던 일이라, 사용자 눈에는 새로 생긴 깜박임이다.

**사례:**
- PR #355 — 캘린더 · 전례독서를 처음 갈 때 받게 바꾸면서 `routing.js`의 분기가 매번 `await loadViewModule(() => Promise.all([import(…)]))`를 거쳤다. 달 이동 · 칩 · 세그먼트 · 날짜 이동마다 `renderLoading()`의 「불러오는 중…」이 한 프레임 그려졌다 — 달 이동 40번 중 40번(main 0번). 그 프레임에 스크롤이 0으로 눌렸다가 포커스 복원이 되돌리고, 데스크톱에서는 접힌 머리가 펼쳐졌다 접혔다. 최종 상태만 보는 e2e는 통과했다.

**규칙:**
- 처음 받은 뒤의 길에서는 `import()`를 기다리지 않는다 — 받은 모듈(또는 쓸 함수)을 변수에 두고 바로 쓴다. 성공만 둔다 — 실패를 두면 다시 시도하지 않는다(`routing.js` `loadedViews`).
- 깜박임은 최종 상태로는 보이지 않는다 — 프레임마다(rAF) 그 요소가 있었는지 세어 본다(`tests/e2e/test_liturgical_lazy_load.py`의 `WATCH_LOADING_FRAMES`).
- 반대로 기다림이 사라지면 「중간 상태」에 기대던 테스트가 깨진다 — 같은 PR에서 「오늘 → 다음날 → 전날」 테스트가 `?track=` 없는 중간 주소를 기다리다 실패했다(트랙 있는 주일, 이동과 주소 고치기가 한 태스크 안에 끝난다). 주소는 경로만 비교한다.

### pitfalls §34 — WebKit의 `modulepreload`는 새로 고쳐도 다시 받지 않는다 — 실패한 미리 받기가 그 탭을 막는다 (리뷰, 2026-10-18)

`<link rel="modulepreload">`로 받은 모듈은 WebKit에서 그 탭의 메모리에 남아, 새로 고침(`location.reload()`)도 같은 주소로 다시 가기도 그것을 다시 쓴다 — 서버에 요청이 가지 않는다. 미리 받기가 실패했으면 실패가 남아 그 탭에서는 화면이 열리지 않고(새 탭에서만 열린다), 성공했으면 서버의 파일이 바뀌어도 옛 것이 돈다. 같은 페이지의 다른 파일(`routing.js` · `style.css`)은 새로 고칠 때 304로 재검증된다. Chromium은 새로 고침이 다시 받는다.

**사례:**
- PR #355 — 공유 링크로 처음 들어온 캘린더 · 전례독서가 늦게 그려지는 것(1회차 리뷰)을 `pre-fetch.js`의 `modulepreload`로 메웠다(느린 4G +198 → +51ms). 2회차 리뷰가 WebKit(Playwright 26.4)에서 calendar.js 첫 요청을 503으로 실패시키자, 「다시 불러오기」를 세 번 눌러도 20초 뒤 새로 고쳐도 서버 요청이 1회 그대로였다. 미리 받기가 없는 판은 새로 고침이 다시 받아 열렸다. 서비스 워커가 없는 WebKit 세션(iOS 인앱 브라우저 등)으로 공유 링크를 여는 — 미리 받기가 도우려던 바로 그 — 경우라 되돌렸다(사용자 결정 2026-10-18).

**규칙:**
- 「새로 고침이 고친다」에 기대는 실패 복구가 있는 모듈에는 `modulepreload`를 걸지 않는다. 걸려면 WebKit에서 「실패 → 새로 고침 → 회복」을 먼저 확인한다.
- 미리 받기 · 캐시 동작은 엔진마다 다르다 — Chromium만 도는 e2e로는 보이지 않는다. 그런 변경은 WebKit으로 한 번 돌린다. 이 클론의 호스트에는 Playwright WebKit이 쓰는 라이브러리가 없어, 2회차 리뷰어는 필요한 패키지를 스크래치에 풀고 `PLAYWRIGHT_BROWSERS_PATH` · `PLAYWRIGHT_SKIP_VALIDATE_HOST_REQUIREMENTS=1`로 띄웠다.

### known-issues §20 — 노트 탭(ADR-026) 재개 (2026-10-22)

2026-06-03에 1.6.0 계획(ADR-026의 메뉴 라우팅, 노트, 하단 내비, 캘린더)을 멈추고 디자인을 먼저 손보기로 했다. 노트 작업은 원격 브랜치 `release/1.6.0`(`2cda731`)에 main에 없는 커밋 여섯으로 남아 있다.
