# ADR-037: 감사성찬례 전례독서 데이터 모델 · 교회력 계산 엔진

- 일시: 2026-07-04
- 상태: **승인됨 — 구현 완료**. 데이터(D1-D3)와 엔진(A1, B1)을 모두 구현했다. 엔진을 쓰는 화면은 ADR-038(A2-A4)이, 열린 물음은 설계서 §9가 다룬다.
- 관련: ADR-036(교회력 데이터 모델과 본기도. 전례일 키와 부활절 계산의 기준), ADR-035(절의 일부를 고르고 이어진 절을 합쳐 그리는 방식. 독서 본문을 그리는 바탕), ADR-010(북마크의 `verseSpec` 문법), ADR-021(콘텐츠 해시 매니페스트와 서비스 워커 캐시), ADR-013(유닛 테스트 하네스), ADR-038(캘린더, 전례독서 화면, 검색 UI), ADR-039(전례시편 DSL, 파서, `lps` 스키마. 데이터 저장소에 있고 D1의 기준이다)
- 설계 문서: [`docs/design/liturgical-engine.md`](../design/liturgical-engine.md). A1과 B1의 구현 설계(모듈 배치, API 형태, 단계, 테스트 계획)다. 이 문서 §6이 정한 계약을 구현 수준으로 풀어 썼다. 계약은 엔진이 호출하는 쪽에 지키기로 한 약속이고, 받는 값, 돌려주는 값, 동작을 정한다. 설계서가 이 문서 §6과 다르게 하거나 더 정한 다섯 가지(마커 블록 셋, 프리로드와 동기 `resolveDate`, 데이터 두 묶음, 조회 함수의 입력, `Candidate` 래퍼)는 설계서 §1.3이 근거와 함께 적었다. 넷째와 다섯째는 이 문서 §6의 계약도 그렇게 고쳤다.

## 요약

이 ADR은 감사성찬례 전례독서의 데이터 모델과, 날짜에서 그날의 전례일과 본문을 찾는 교회력 엔진을 정한다.

1. **독서 데이터**(이 문서 §1): `lectionary/eucharist-readings.json` 파일 하나에 담긴 평면 배열이다. 레코드 하나가 전례일, 독서 트랙, 대안 세트의 조합 하나이고 자기 전례일 키를 가진다. `id`는 전례일 키로 만든 안정 슬러그다.
2. **독서 파서**(이 문서 §2): 전례일 키 파싱(`coords.py`)을 본기도 파서와 함께 쓰고, 모든 독서 범위의 절이 실제로 있는지 절 단위로 대조한다.
3. **전례시편**(이 문서 §3): 공동번역 시편과 다른 번역이라 별도 책 `lps`로 두고, 손으로 편집하는 마크다운을 기준으로 삼는다.
4. **표 데이터**(이 문서 §4): 연중 주차는 기도서 구간표에서, 설과 추석은 KASI 표에서 찾는다.
5. **검색 인덱스**(이 문서 §5): 워커는 독서 전체 대신 작은 색인을 읽는다. 색인에는 독서가 없는 날까지 모든 전례일, 독서 세트, 독서 자리를 단 구간, 성인, 비슷한 말 표가 있다. 끊긴 범위는 이어진 구간마다 한 행이다.
6. **교회력 엔진**(이 문서 §6): 다른 모듈에 의존하지 않는 `js/app/liturgical-engine.js`다. `resolveDate`가 그날의 후보 전부와 지정 전례일을 내고, `findReadings`와 `findCollects`가 본문을 찾는다. 규칙의 기준은 설계서다.
7. **파이프라인과 캐시**(이 문서 §7): 데이터 저장소의 빌드가 산출물을 만들고, 앱은 `/data/lectionary/`를 데이터 캐시에 둔다.
8. **입력의 동결**(이 문서 §8): 파이프라인 입력은 지금 동결하지 않는다. 데이터가 더 바뀌지 않을 때 동결한다.

## 배경

주일, 평일, 축일, 재일의 감사성찬례 독서(제1독서, 시편, 제2독서, 복음)와 본기도를 날짜로 찾아 읽게 하려면, 독서 데이터와 그날이 어떤 전례일인지 계산하는 엔진이 필요했다. 화면(캘린더, 전례독서 화면, 검색)은 ADR-038이 정한다.

원료는 서울교구 홈페이지에서 내려받은 기사다(데이터 저장소 `common-bible-data/liturgical/`. 838기사이고, `articles.json`의 `readings[]`와 HTML 캐시에 독서 전문이 있다). 본기도의 데이터 모델은 ADR-036이 정했고, 독서는 별도 파일 `eucharist-readings.json`과 교회력 엔진이 다룬다고 미뤄 두었다(ADR-036 §2).

독서 본문을 그리는 방식은 이미 있었다. ADR-035의 `appendVerses`(절의 일부만 그리기)와 이어진 절 합치기는, 입력을 교회력 계산 결과로 바꾸면 같은 경로로 그릴 수 있다. 남은 것은 그 입력인 데이터와 엔진이었다.

## 결정

### 1. `eucharist-readings.json` — 전례일 키 스키마 평면 배열 (데이터 저장소 `lectionary/`)

레코드 하나는 전례일, 독서 트랙, 대안 세트의 조합 하나다. ADR-036 §1처럼 평면 배열이고, 레코드마다 자기 전례일 키를 가진다. 독서는 해마다, 요일마다 실제로 다르므로 본기도와 달리 요일과 주기를 가로질러 합치지 않는다.

```json
{
  "_meta": { "source": "seoul.anglican.kr 감사성찬례-전례독서 태그", "articles": 838 },
  "_vocab": { "…": "ADR-036 §4와 동일 + slot" },
  "entries": [
    {
      "id": "ordinary-10-sun-A-t1-s1",
      "kind": "temporal", "season": "ordinary", "week": 10,
      "type": "sunday", "weekday": null, "year": "A",
      "date": null, "lunar": null, "name": null, "aliases": null,
      "title": "연중10주일",
      "reading_track": 1,
      "set_no": 1, "set_total": 1, "set_note": null,
      "readings": [
        { "slot": "first",  "bookId": "gen",  "refs": [{ "chapter": 12, "verseSpec": "1-9" }], "label": "창세 12:1-9" },
        { "slot": "psalm",  "bookId": "lps",  "refs": [{ "chapter": 33, "verseSpec": "1-12" }], "label": "시편 33:1-12" },
        { "slot": "second", "bookId": "rom",  "refs": [{ "chapter": 4, "verseSpec": "13-25" }], "label": "로마 4:13-25" },
        { "slot": "gospel", "bookId": "matt", "refs": [{ "chapter": 9, "verseSpec": "9-13,18-26" }], "label": "마태 9:9-13, 18-26" }
      ],
      "_sources": [{ "id": "26662" }]
    }
  ]
}
```

- **`id`는 전례일 키로 만든 안정 슬러그다.** 다시 만들어도 같다. ADR-036 §10이 잠정 순번 `id`를 키로 쓰지 말라고 한 것의 해법이고, 검색 결과와 주소(`/lectionary/d/<slug>`)가 이 `id`를 가리킨다. 슬러그는 전례일 키, 트랙, 세트 번호만으로 정해진다(위 예시의 `ordinary-10-sun-A-t1-s1`).

  | 전례일 키 | 슬러그 |
  | --- | --- |
  | 절기 격자 | `{season}-{week}-{sun\|요일코드\|feast\|fast}[-{고유명}]-{year}-t{track}-s{set}` |
  | 고정일(양력) | `d{MMDD}-{이름}-…` |
  | 음력 명절 | `lunar{M-D}-{이름}-…` |
  | 그 밖(고유명) | `{kind}-{season}-{이름}-…` |

- **`refs` 배열이 장 경계를 적는다.** `1고린 3:18-4:5`는 `[{chapter:3, verseSpec:"18-23"}, {chapter:4, verseSpec:"1-5"}]`다. 끝이 열린 범위는 빌드할 때 실제 장 JSON의 마지막 절로 닫고, 이것이 검증을 겸한다.
- **`verseSpec` 문법은 북마크(ADR-010)와 같다**: `"all" | "3" | "1-17" | "1-5,10-15" | "3a"`. 반절의 상, 하는 `a`, `b`로 적고, 범위 안의 반절은 나눈다(`"46하-55"`는 `"46b,47-55"`, 범위 끝이 `"2:4상"`이면 그 장은 `"1-3,4a"`). 전례독서의 `a`, `b`는 줄 글자가 아니라 상과 하이고, 그 경계는 `lectionary/half-verses.json`이 정한다(ADR-038 §3 「구현」).
- **대안 세트 explode.** 「또는」 대안(`(또는 …)`, 줄 안의 `또는`)이나 괄호 선택 확장(`9:35-10:8(9-23)`)이 있으면 완전한 세트를 통째로 복제하고, 원본 세트와 대안을 적용한 세트를 `set_no`와 `set_total`로 구별한다. 조건부 대안(`(주의 변모 주일로 지키는 경우, …)`)은 별도 세트로 두고 조건 원문을 `set_note`에 적는다. 화면은 늘 완전한 세트 하나를 그린다(ADR-038).
- **시편 슬롯.** 기본은 전례시편 `bookId:"lps"`다(이 문서 §3). 송가는 전례에서 실제로 낭송하는 기도서 번역을 그린다. 그 번역은 성무일과 송가 책 `cant`에 있고(데이터 저장소 ADR-039 v2), 송가인 시편 슬롯은 `cant`와 `canticle` 키로 그것을 가리킨다(설계서 §5.6). 인쇄본이 적은 성구 범위(`이사 12:2-6`, `루가 1:46하-55`)는 절 번호 체계가 달라 쓸 수 없으므로 송가 전체를 낭송하고, 그 성구는 `scripture_ref`에 남긴다. 기도서에 없는 송가만 공동번역 성구로 폴백한다. 시편이 아닌 본문(다니엘, 요나, 토비트)도 `slot:"psalm"`에 두고 일반 성서의 `bookId`를 쓴다. 버린 원안은 「검토한 대안 — 송가 본문」에 있다.
- **본기도는 필드가 아니라 전례일 키로 조인한다.** 같은 전례일 키로 `eucharist-collects`를 ADR-036 §2, §4의 폴백 규칙으로 찾는다. 송영은 ADR-036 §3대로 따로 두고 앱 상수로 붙인다. 시편 끝의 영광송과는 다른 것이다.
- **파일은 하나다**(`lectionary/eucharist-readings.json`, 약 300-400KB 예상). `search-dc.json`보다 작고 캘린더와 전례독서 화면이 전체를 쓰므로 나눠서 얻는 것이 없다.
- **슬롯 배정.** 칸 이름(`slot`)은 자리가 아니라 내용으로 정하고, 읽는 쪽도 자리가 아니라 `slot` 이름으로 읽는다. 대안 줄을 빼면 기본 독서는 늘 네 칸(제1독서, 시편, 제2독서, 복음)이나 세 칸(제2독서가 없다)이지만, 마지막 칸이 복음서가 아니면 복음이 없는 날로 보고 `second`에 두며 리포트에 표시한다. 이 규칙이 잡아낸 유일한 레코드(12.31 예수 이름 전야)는 저녁기도였고 데이터에서 뺐다. 잘못 실린 레코드를 잡아낸 규칙이므로 그대로 둔다.
- **트랙은 연중 주일에만.** 제목 끝의 `1`, `2`가 늘 `reading_track`인 것은 아니다. RCL 트랙은 연중 주일에만 있고, 재의 수요일, 성 금요일, 부활대축일의 `2`는 그날의 다른 독서라 대안 세트(`set_no`)로 둔다. 트랙으로 실으면 없는 축이 생기고 앱이 「독서 2」라고 잘못 이름 붙이기 때문이다. 이 세트도 화면에서는 독서 카드로 고르지만 앱이 기억하지 않는다(ADR-038 §3). 거꾸로 왕이신 그리스도 주일 가해와 다해는 제목에 번호가 없고 시편만 「또는」이어도 트랙이다. 연중 주일의 「또는」은 앞쪽이 구약 연속 독서, 뒤쪽이 복음 주제이고 시편도 그렇다(2024 책자 일러두기, RCL Proper 29).
- **세트 번호는 결정적이어야 한다.** `set_no`를 기사의 배열 순서로 매기면 다시 내려받을 때마다 `id`와 독서의 짝이 바뀐다(ADR-036 §10의 잠정 순번과 같은 문제). 그래서 옛 연도판(`2019.9.29.`)을 뒤로 보내 기준이 언제나 `s1`이 되게 하고, 인쇄된 세트 번호 순, 본 독서가 대안보다 앞인 차례로 정렬한다. 옛 연도판도 버리지 않는다(ADR-036 §7 「밀린 독서 보존」).
- **같은 전례일 키에 기사가 여럿이면** 독서를 견준다. 같으면 중복 기사라(`부활4주`와 `부활4주일`) 하나로 합치고 `_sources`에 둘 다 남긴다. 다르면 그날의 다른 세트라 세트 번호를 이어 붙인다.
- **원본 사이트의 결함은 HTML 캐시를 근거로 고치고, 근거를 `readings-report.txt`에 남긴다.**
- **에스델 하위 절은 아직 적을 수 없다.** `에스 4:17(12-16)`은 그리스어 에스델 추가 본문의 하위 절(우리 데이터의 `alt_ref` 12-16)을 가리키는데, `verseSpec` 문법에 하위 절 표기가 없다. 그래서 17절 전체를 싣고 `label`에 인쇄본 표기를 남긴다. 문법을 넓힐지는 북마크(ADR-010)와 함께 정한다(설계서 미결39).

### 2. 독서 문자열 파서 — `liturgical/parse_readings.py` (신규)

- **전례일 키 파싱은 본기도 파서와 함께 쓴다.** ADR-036의 `normalize.py`에서 제목을 전례일 키로 읽는 부분을 `liturgical/coords.py`로 빼냈다. 전례일 키가 한 코드에서 나와야 그날의 독서와 본기도가 맞는다.
- **책 이름은 `book_mappings.json`의 한글 별칭 표로 `bookId`로 바꾼다.** 표에 없던 별칭(`사무상/하`, `열왕상/하`, `역대하`, `마카상/하` 등)은 `aliases_ko`에 더하고, 그러면 성서 검색의 `in:` 토큰도 함께 좋아진다.
- **저녁기도와 아침기도 기사는 뺀다.** 감사성찬례가 아니므로 따로 모아 리포트한다(Phase 4 성무일과의 원료).
- **산출물**은 `lectionary/eucharist-readings.json`과 검증 리포트 `readings-report.txt`다. 검색 인덱스는 교회력 표의 파서가 끝난 뒤에 따로 만든다(이 문서 §5). 리포트는 해석하지 못한 문자열 0건을 목표로 한다.
- **리포트에는 제목 정규화의 결과를 모두 싣는다.** 정규화한 `title`과 전례일 키를 원본 기사 제목과 나란히 전례 순서로 적어, 잘못 분류한 것을 눈으로 찾게 한다. 본기도 리포트(`normalize.py`)의 TITLE MAP 섹션과 같은 형식이다.
- **독서 범위의 절이 실제로 있는지는 절 단위로 대조한다.** 장의 마지막 절만 견주면 장 중간에 빠진 절을 놓친다. 그렇게 견주던 리포트가 「오류 0」을 내는 동안 루가 1:68과 히브 1:12가 성경 데이터에 없어(`source/luke.md`의 `[68]` 마커가 빠졌다), 전례독서, 인용, 북마크, 딥링크가 그 절을 찾지 못했다.

### 3. 전례시편 — 별도 책 `lps` (계응 구조, 새 마크다운 DSL)

감사성찬례의 시편은 공동번역 시편(`ps`)과 다른 번역이고, 선창과 응답이 번갈아 오는 계응 구조다. 몇 년 전에 개정본이 나왔는데 내려받은 본문은 개정 전 것이라, 손으로 편집할 수 있는 마크다운을 기준으로 둔다.

- **DSL, 파서(`src/liturgical_psalter.py`), 산출 스키마의 기준은 데이터 저장소 ADR-039다.** 이 ADR은 그 문법을 다시 적지 않는다.
- **◯, ¶ 같은 전례 기호와 표시용 줄바꿈은 저장하지 않고 그릴 때만 보인다.** 자판으로 입력하기 어렵고, 파일에는 뜻의 구조만 둔다.
- **산출 `bible/lps-{n}.json`은 기존 장 JSON과 같은 스키마에 필드만 더한다.** 그래서 `appendVerses`가 그대로 그린다.
- **영광송은 파일에 저장하지 않고 앱 상수로 붙인다.** 150회 되풀이하지 않고 한 곳에 둔다.
- **`books.json`에 `{"id":"lps", "division":"liturgical", …}`를 더한다.** 책 목록 탭이 `division`으로 거르므로 이것만으로 읽기 화면의 책 목록에서 숨는다. 검색은 이 책을 성서와 따로 된 성시 색인으로 찾는다(ADR-046).

### 4. 표 데이터 — 연중 주간 구간표 · 음력

- **`ordinal-weeks`.** 연중 주일과 주간이 어느 날짜 사이에 오는지는 성공회 기도서의 구간표를 따른다. ADR-036 §11이 주차를 끝에서 거꾸로 세던 어려움을 표 조회로 바꾼 것이다. 원본은 사용자가 타이핑하는 텍스트 `liturgical/ordinal-weeks.txt`(`6주: 2/11-2/17, 5/24-5/30`. 구간 둘은 쉼표로 나눈다)이고, 파서가 `lectionary/ordinal-weeks.json`(`{week, windows:[{from, to, anchor}]}`)으로 바꾼다. 한 주간은 구간을 둘까지 가진다(공현 후 연중과 성령강림 후 연중). 엔진은 날짜가 연중 절기 구간 안일 때만 이 표를 찾는다.

  **구간마다 조회 기준 `anchor: "doy" | "date"`를 둔다.** 표의 구간은 1/7부터 7일씩 끊은 블록이라 2월이 28일일 때만 맞고, 윤년에는 2/29가 3월 날짜를 하루씩 밀어 공현 후 구간이 어긋나기 때문이다. 2052년(부활절 4/21)에 날짜 그대로 찾으면 8주 구간(2/25-3/3)이 8일이 되어 2/25와 3/3이 둘 다 8주로 나오지만, 3/3은 세례주일부터 세어 아홉째 주일이라 9주가 맞다(9주 구간 3/4-3/7은 그해 비어 있다).

  | 구간 | `anchor` | 조회 방식 | 같은 뜻 |
  | --- | --- | --- | --- |
  | 공현 후 (1-9주) | `doy` | 월/일이 아니라 **연중 일수**(2/29를 셈)로 맞춘다 | 세례주일(1주)부터 앞으로 센다 |
  | 성령강림 후 (6-34주) | `date` | **월/일 그대로** 맞춘다 | 대림 직전 주일(34주)부터 뒤로 센다 |

  뒤 구간은 연말(대림 1주일)을 기준으로 하고 7일짜리 블록이 늘 주일을 하나씩 담으므로, 날짜 그대로 찾아도 윤년에 안전하다. 표의 검증은 주제 문서 「교회력 데이터」의 「연중 주간 구간표」 항목에 있다.
- **`kasi-lunar.json`.** 설(음 1/1)과 추석(음 8/15)의 양력 날짜를 2025-2050년까지 KASI 기준으로 찾는 표다(ADR-036 §9).

### 5. 전례독서 검색 인덱스 — `lectionary/search-lectionary.json`

데이터 저장소의 `liturgical/build_lectionary_search.py`가 만든다. 독서, 월별 축일, 이동 축일, 성인 공통의 파서가 끝난 뒤에 실행한다. 워커는 약 400KB의 독서 전체를 파싱하지 않고, 이 색인으로 비교만 한다. 무엇을 어떻게 찾는지는 ADR-044가 정한다.

```json
{ "obs":      [ { "key": "advent-1-sun", "name": "대림1주일", "aliases": [], "kind": "temporal", "date": null, "rank": null, "order": 0, "common": null } ],
  "sets":     [ [obsIdx, "advent-1-sun-A-t1-s1", "A", null, 1, "대림1주일 (가해)"] ],
  "cov":      [ [setIdx, bookIdx, chapter, vStart, vEnd, slot] ],
  "books":    ["isa", "…"],
  "saints":   [ { "name": "그레고리", "title": "나지안조의 그레고리(주교, 389년)", "obs": [obsIdx] } ],
  "synonyms": { "주님 부활 대축일": "부활대축일" } }
```

- **`obs`는 전례일 목록이고, 독서가 없는 날도 넣는다.** 월별 축일 표와 이동 축일 표의 날(아래의 사계재 넷은 빼고)에 더해, 표에 없지만 독서가 있는 날(절기 격자의 주일과 평일, 성주간 평일, 사계재의 지향별 날, 12월 17-24일)이 들어간다. 이름 검색이 찾는 것은 독서 세트가 아니라 전례일이기 때문이다(ADR-044 §3).
  - 같은 날을 가리키는 이동 축일과 격자의 날(이동 축일 표의 대림1주일과 격자의 `advent-1-sun`)은 전례일 하나로 합친다.
  - `key`는 표의 식별자다. 표에 없는 날은 독서 세트 식별자에서 주기, 트랙, 세트를 뗀 값이다(`advent-1-sun`).
  - `order`는 전례년 순서다. 고유 시기(대림, 성탄, 사순, 성주간, 부활, 연중 1-34주)를 먼저 두고, 월별 축일을 날짜순으로 그 뒤에 둔다.
  - `common`은 고유 독서 없이 공통 독서를 쓰는 월별 축일의 공통 분류다. 그 밖에는 `null`이다.
  - 이동 축일 표의 사계재 넷(규칙 `ember_wfs`, 「춘계재」 등)은 넣지 않는다. 사계재의 날은 지향별 날 열여섯으로 찾는다(ADR-044 §3, 사용자 결정 2026-11-21). 계절의 전례일을 넣으면 같은 날이 계절 이름과 지향 이름으로 두 번 나온다. 넣지 않을 전례일은 키가 아니라 규칙으로 골라, 표의 키 이름이 바뀌어도 따라간다.
  - `aliases`는 표의 별칭에 더해 검색만 쓰는 별칭을 담는다. 사계재의 지향별 날 열여섯에는 네 계절을 함께 부르는 「사계재」를 넣는다(ADR-044 §3). 교회력 엔진이 읽는 표에는 넣지 않는다. 엔진이 사계재의 독서를 이름으로 맞춰 찾기 때문이다.
- **`sets`는 독서 세트 목록이다.** 칸은 차례로 전례일 번호, 독서 세트 식별자(`eucharist-readings.json`의 `id`), 주기, 트랙, 세트 번호, 라벨이다.
  - **라벨에 트랙과 대안 세트를 함께 적는다.** 전례일 이름은 트랙 표기를 뗀 이름(ADR-036 §2)이라, 그대로 두면 트랙 1과 2, 대안 세트들이 같은 이름으로 뭉친다. 그래서 트랙이 있으면 라벨에 `독서 N`을(`연중10주일 (가해, 독서 2)`), 대안 세트가 여럿이면 `set_note`나 `대안 N`을 함께 적는다. 표시하는 자리마다의 규칙은 ADR-038 §3-1에 있다.
- **`cov`는 이어진 구간마다 한 행이다.** `refs`의 범위 하나를 한 행(`[min, max]`)으로 합치면 끊긴 범위 사이의 절이 딸려 들어가, 그날 읽지 않는 절이 그날의 독서로 검색된다(`시편 80:1-7,17-19`가 `80:1-19`가 되어 8-16절이 대림1주일(나해)로 잡혔다).
  - 마지막 칸은 독서 자리다(0 제1독서, 1 시편, 2 제2독서, 3 복음). 결과에 어느 독서에서 찾았는지 보이기 위해서다.
  - 송가는 성구 표기(`scripture_ref`, 예: `루가 1:68-79`)로 행을 하나 더 둔다. 그래야 성서의 구절로 송가를 읽는 날을 찾는다.
  - 공통 독서는 넣지 않는다(ADR-044 §2).
- **`saints`는 성인 목록이다.** 성인의 이름이나 칭호로 찾으면 그 성인의 축일을 낸다.
- **`synonyms`는 다른 교회와 다른 번역의 이름을 앱의 표기로 잇는 표다.** 데이터 저장소의 손으로 쓰는 표 `liturgical/search-synonyms.md`에서 만들고, 줄마다 출처를 적는다(ADR-044 §3).
- 지역 축일은 사람마다 소속교회가 달라 색인에 넣지 않는다. 앱이 검색할 때 더한다(ADR-044 §3).

### 6. 교회력 계산 엔진 — `js/app/liturgical-engine.js` (신규, 다른 모듈에 의존하지 않음)

엔진은 다른 모듈에 의존하지 않는(leaf) 순수 로직 모듈이고 DOM을 쓰지 않는다. 순수 로직은 `// ── BEGIN LITURGICAL_CORE ──` 블록에 두어 ADR-013의 `vm` 하네스로 유닛 테스트한다. 이 절은 계약과 까닭만 적는다. 규칙의 기준은 설계서의 규칙 마커 문장이고, 마커 블록, 데이터를 미리 받는 방식, 데이터 묶음은 설계서 §3.3, §3.4, §3.5가 더 정했다.

- **계산 계층**은 부활절(`easterDate(y)`, ADR-036 §11), 부활절에서 센 이동 축일(`E−46` 재의 수요일부터 `E+56` 삼위일체까지), 대림 1주일, 주일과 평일의 주기, 연중 주차, 설과 추석을 계산한다(설계서 §4). 연중 주차는 절기 구간을 먼저 정한 뒤 연중 구간에서만 구간표로 찾는다(이 문서 §4). 날짜 연산은 로컬 `new Date(y,m,d)`와 `"YYYY-MM-DD"` 문자열로 해, UTC 오프셋 때문에 날짜가 어긋나는 일을 막는다.
- **조회 계층**의 `resolveDate(dateStr)`는 `{coord, candidates:[Candidate…], official}`를 돌려준다(설계서 §5.5).
  - **후보는 그날 지킬 수 있는 전례일 전부다.** 격자의 절기 위치, 월별 축일(sanctoral)의 `date`와 `lunar`, 이동 축일(temporal) 행의 규칙, 기준일에서 나오는 고유명 특수일(성주간, 재의 수요일 후 X요일 등), 다른 날짜에서 옮겨 온 축일이다. 옮겨 온 축일은 연도마다 한 번 계산해 캐시한 색인에서 읽는다(→ 설계서 R-6.5-year-pass). 이것이 없으면 밀린 축일은 어디에서도 찾을 수 없다. 옮겨 간 축일은 원래 날짜에 `transferred_out`으로 남는다.
  - **후보의 원소는 `Observance`가 아니라 `Candidate` 래퍼** `{observance, status, from?, to?, displacedBy?, evening?}`다. 후보에 「어디서 왔나」를 실어야 하는데, 정의 표의 행인 `Observance`에 엔진이 계산한 값을 넣지 않기 위해서다(설계서 §1.3, §5.5).
  - **후보 전례일 집합을 모두 남긴다**(ADR-036 §7 「밀린 독서 보존」). 지정 전례일은 엔진이 `official`로 정하고, 화면은 우선순위를 다시 계산하지 않는다. 화면은 `candidates`를 전례일 스위처로 늘 보이고 `official`을 초기 선택으로 삼으며, 낮은 등급을 숨기거나 합치지 않는다(자리마다의 규칙은 ADR-038 §3). 기념일 후보는 본문 조회가 빈 결과다.
  - **저녁 전례**(성 토요일 저녁의 부활밤, 12.24 저녁의 성탄 밤)는 드리는 날의 후보 맨 끝에 `evening: true`로 실리고, 그날의 `official`, 색, 재분류에 참여하지 않는다. 그래서 성 토요일의 `official`은 성 토요일이다(→ 설계서 R-6.1-evening).
  - **후보 표시 순서**는 교회력에 따른 축일과 재일, 옮겨 지키는 축일, 나머지(연중 평일과 연속 독서)다. 대축일, 주요축일, 사계재에 연중 주간 독서를 전례에서 쓰지 않더라도 후보는 모두 낸다. 읽는 목적에 맞게 고르는 것은 사용자의 몫이다.
- **본문 조회 `findReadings(resolved, candidate)`와 `findCollects(resolved)`는 절기 위치를 받지 않는다.** `LiturgicalCoord`는 절기 축(`season`, `week`, `weekday`, `year`)만 담아서, 전례일이 가진 이름(`name`), 고정일(`date`), 음력일(`lunar`)로 색인된 본문을 찾지 못한다. 경로마다의 규칙은 설계서 §5.6에 있고, 버린 함수 형태는 「검토한 대안 — 조회 함수의 입력」에 있다.
  - `findReadings`는 고른 후보(`Candidate`) 하나의 세트를 `reading_track`과 `set_no`마다 묶어 낸다. 화면이 후보마다 호출하므로 `official`로 제한되지 않는다. `ResolvedDate`도 받는 것은, 성탄절기 본문 16건이 `date`로만 구별되는데 격자 전례일에는 `date`가 없어 물어본 날짜가 `resolved.date`에만 있기 때문이다.
  - `findCollects`는 `ResolvedDate` 전체를 받는다. 둘째 축(겹친 전례일들의 본기도)은 여러 전례일에 걸쳐 있어 지정 전례일 하나로 만들 수 없기 때문이다. 그 축은 전례일마다 묶은 `{candidate, collects}` 배열이라, 화면은 고른 후보의 본기도만 보이고 다시 조회하지 않는다(ADR-038 §3 「구현」).
  - 폴백은 ADR-036 §2, §4의 규칙이다(`weekday`, `year`가 `null`이면 공통, 배열이면 포함, 더 구체적인 레코드가 앞선다).
  - **고유 독서가 없는 성인**은 `sanctoral_class`로 `commons.json`의 분류별 공통 독서 세트를 찾아, 고유 독서와 같은 묶음 형식에 출처 표지 `common: "<분류>"`를 붙여 낸다(트리거, 자격, 배타 규칙은 설계서 §5.6).
- **데이터는 `/data/lectionary/*.json`을 처음 쓸 때 받아 모듈에 캐시한다**(`data-fetch.js`와 같은 방식, 묶음은 설계서 §3.5).
- **우선순위와 옮김은 A1(코어) 다음 단계인 B1이다.** ADR-036 D5가 분류 필드를 채워 입력이 생겼다(버린 범위안은 「검토한 대안 — 우선순위와 옮김 엔진의 범위」).
  - 데이터가 주는 것은 `rank`, `precedence`, `priority_group`, `transferable`, `transfer_to`, `outranks_sunday`, `color`, `color_alt`다. `transfer_to`는 여섯 값으로 밀려 옮김과 선택 봉헌을 한 열에 담는다(→ 설계서 R-6.2-destinations).
  - 엔진은 절기 위치만으로 정해지지 않는 판정 넷을 한다(설계서 §6.3). 금요일 소재일(→ 설계서 R-6.3-friday-fast), 성주간과 부활 8일(→ 설계서 R-6.3-holy-week-guard, R-6.3-guard-destination), 지정 전례일의 색을 덮어쓸 때의 기간 보호(→ 설계서 R-6.4-color-order), 옮길 날 평가(설계서 §6.5)다. 기간이 걸린 셋은 같은 함수 `spansOf(year)`(설계서 §4.10)로 기간을 얻는다. 셋이 날짜를 따로 견주면 경계가 어긋나도 테스트가 잡지 못하기 때문이다.
  - 우선순위가 같을 때 지정 전례일은 `id`가 아니라 범주 순서로 정한다(→ 설계서 R-6.2-tie-ladder).
  - 옮겨 온 축일은 그날 우선순위가 같은 고유 후보를 밀어내고, 그렇게 밀린 축일도 옮길 수 있으면 이어서 옮긴다(연쇄, → 설계서 R-6.2-chain-model). 연쇄의 범위를 좁히던 규칙 R-6.2-chain-scope는 폐기했다.
  - `transfer_to`의 주일 종류(공현, 모든 성인, 승천, 주의 봉헌, 주의 변모)는 밀려 옮김이 아니라 선택 봉헌이다. 옮겨 지키지 않으면 원래 날짜는 그대로 두고 목적지 주일에 `optional` 후보로만 넣으며, 옮겨 지키기로 하면 실제로 옮긴다(설계서 §6.2 활성화 계약).

### 7. 파이프라인·캐시 편입

- 데이터 저장소 `build.yml`의 감시 경로와 빌드 단계에 전례시편 파서와 독서 파서를 더한다. 산출 경로는 감시 경로 밖에 두어, 빌드가 자기 산출물 때문에 다시 실행되지 않게 한다.
- `gen_manifests.py`가 `lectionary/*.json`을 `bible-manifest.json` 대상에 더한다(`lps`는 `bible/*.json` glob으로 들어간다). 그래서 ADR-021의 무효화를 그대로 따른다.
- 앱의 서비스 워커가 캐시를 고르는 함수(`sw.js cacheNameFor`)는 `/data/lectionary/`를 DATA_CACHE로 보낸다. 콘텐츠 해시 무효화(`manifest-sync`)는 DATA_CACHE에서만 지우기 때문이다. 이 라우팅이 다시 빠지지 않도록 「매니페스트가 추적하는 접두사는 전부 DATA_CACHE로 간다」를 `tests/unit/sw.test.js`가 대조한다.
- 데이터 저장소의 검증 테스트는 주제 문서 「교회력 데이터」의 각 항목에 있다.

### 8. 파이프라인 입력의 동결 — 지금은 하지 않는다 (2026-09-13 제기)

`common-bible-data`는 입력만 손으로 쓰고 출력은 모두 만든다. 내려받은 `articles.json`과 손으로 입력한 `articles-supplement.json`을 파서가 `lectionary/*.json`으로 만들고, `pipeline.yml`의 어긋남 검사가 이 구조를 지킨다. 전례독서 데이터가 완성되면 처음의 입력은 필요 없으므로, 언제 입력을 접고 출력을 기준으로 삼을지가 물음이다(상태는 설계서 미결40).

**지금은 동결하지 않는다.** 데이터를 다시 써야 하는 미결이 남아 있고, 그 가운데 하나는 스키마를 바꾼다.

| 미결 | 무엇을 바꾸나 | 스키마 |
|---|---|---|
| 설계서 미결5 **사계재 계절 기계 키** | 이동 축일 4행과 본문 16건 **양쪽에 필드를 더한다** | **예** |
| 설계서 미결13 재의 수요일 `transferable`(닫힘 2026-11-05, data#54) | 규칙 열의 값 | 아니오 |
| 설계서 미결35 분류 — 맥추감사주일 · 노동자의 날 | 맥추감사주일은 등급 칸, 노동자의 날은 **행을 새로 만든다**(층위와 색까지 정해야 하고, 행 수 facts가 바뀐다) | 아니오 |
| 설계서 미결34 본기도 기도서 대조 | `corrections` 추가 | 아니오 |
| 설계서 미결37 송영 A/B | `ending` 다시 배정 | 아니오 |

사계재 기계 키는 독서 엔트리 전체(설계서 §5.2 facts `readings.total`)를 다시 만드는 일이라, 입력과 파서가 없으면 손으로 옮겨야 한다. 지금 조인이 한국어 이름의 부분 문자열에 기대고 있어(설계서 §5.4) 그 필드는 언젠가 들어온다.

**동결하면 둘을 잃는다.**
- **어긋남 검사.** 이 저장소의 실질적인 품질 검사는 이것 하나다(2026-09-13 data PR#25에서 매니페스트 해시 누락을 실제로 잡았다). 다시 만들 수 없게 되면 손으로 고친 것을 검증할 수 없다. pytest는 스키마와 일관성을 볼 뿐, 「이 값이 어디서 왔는가」를 보지 않는다.
- **출처 추적.** 레코드마다 `_sources`가 있고, `corrections` 10건은 스크랩에 옮겨 적기 오류가 있어서 생겼다. 기도서 대조(설계서 미결34)에서 더 나올 것이므로, 출처를 구별하지 못하면 같은 오류를 두 번 고친다.

**동결하는 때는 「완성됐을 때」가 아니라 「더 안 바뀔 때」다.** 다음 셋이 모두 참이어야 한다.
1. 스키마를 바꾸는 미결(사계재 기계 키)이 닫혔다.
2. 사제 확인을 기다리는 항목(검토 문서 §6)이 모두 회신됐다.
3. 기도서 대조가 끝나 `corrections`가 더 늘지 않는다.

**그때도 버리지 않고 동결한다.** 입력과 파서를 `archive/`로 옮기고, 출력을 기준으로 삼으며, 어긋남 검사를 스키마 검증으로 바꾸는 ADR을 하나 낸다. 스키마를 옮겨야 하면 `archive/`를 꺼내 다시 실행(replay)할 수 있어야 한다. ADR-036 §5가 규칙 문자열을 빌드할 때 한 번 구조화한 것과 같은 방향으로 한 걸음 더 가는 것이다.

**지금 준비할 수 있는 것**은 `articles-supplement.json`의 `corrections`(10건)를 별도 파일로 나누는 일이다. 그 배열은 보충이 아니라 교정 장치이고 스키마도 다르다(`{ids, day, collect, why}`). 나눠 두면 동결할 때 한 번 쓰는 원료(`archive/`로 갈 것)와 계속 남는 기준이 파일 경계로 드러난다.

## 검토한 대안

버린 선택지는 여기에 「날짜 · 이유 · 근거 · 재검토 조건」과 함께 남긴다(설계서 §1.4 편집 원칙).

### 독서 데이터 기준 형태
- **A. 전용 전례일 키 스키마 (채택)**: 전례일 키, 시편 대체본, 본기도 조인, 검색 축을 한 스키마에서 해결한다. 본문은 `verseSpec`을 다시 써서 ADR-035의 경로로 그린다.
- **B. 북마크 내보내기 파일 형식**: 기존의 가져오기와 읽기 화면을 그대로 쓸 수 있지만, 전례일 키가 폴더 이름 문자열에 실려 검색, 캘린더 링크, 엔진 조회가 모두 문자열 파싱에 기댄다. 채택 안 함.

### 전례시편 저장
- **A. 별도 책 `lps` + 새 DSL (채택)**: 독서가 일반 성구처럼 `{bookId, chapter, verseSpec}`로 가리키고, 마크다운 손편집이 개정본으로 바꾸는 길이 된다. 계응 구조는 기존 ADR-006의 운문 형식과 달라(절 안의 선창과 응답 쌍, 무번호 구절) 별도 파서가 안전하다. 기존 `parser.py`를 바꾸지 않으므로 회귀 위험이 없다.
- **B. 독서 세트에 본문을 직접 넣기**: 같은 시편이 여러 전례일에 겹쳐 실리고, 개정하면 모두 다시 만들어야 한다. 채택 안 함.

### 송가 본문
- **A. 성무일과 송가 책 `cant`(기도서 번역) (채택 2026-07-13, D2 — data#12)**: 이 문서 §1 「시편 슬롯」.
- **B. `lps` 부록 장(151+)에 `canticle` 식별자를 두고 `scripture_ref`(출처 성구)를 함께 적기(원안)**: 채택 안 함 2026-07-13 · 이유: 송가는 `cant`에 기도서 번역 기준으로 들어 있고(데이터 저장소 ADR-039 v2), 전례에서 실제로 낭송하는 본문이 그 번역이다 · 재검토: 없음.

### 연중 주차 산정
- **A. 기도서 구간표 조회 (채택)**: 기준인 기도서와 1:1로 맞고, 데이터로 검증할 수 있다.
- **B. 왕이신 그리스도(연중34주)에서 거꾸로 세기**: ADR-036 §11의 초안이다. 구현할 수는 있지만 기도서 표와 어긋날 위험을 코드가 지게 된다. 표가 있으므로 채택 안 함.

### 검색 인덱스
- **A. 수치 `cov` 역인덱스와 전례일 목록 `obs` (채택)**: 워커에 `verseSpec` 파서를 복제하지 않아도 되고 용량이 작다.
- **C. 독서 세트만 담은 이름 목록(`names`)**: 처음 만든 구조다. 채택 안 함 2026-11-16 · 이유: 독서 세트가 없는 날(월별 축일 149개 가운데 102개, 성인 112명)을 이름으로 찾을 수 없고, 어느 독서에서 찾았는지 알 수 없었다(설계서 `docs/design/lectionary-search.md` §2) · 재검토: 없음.
- **B. 워커가 독서 데이터 전체를 읽기**: 파싱 코드가 겹치고 용량이 5배다. 채택 안 함.

### 조회 함수의 입력
- **A. `findReadings(resolved, candidate)`, `findCollects(resolved)` (채택 — 2026-08-29, 2026-09-01, 2026-09-13, 2026-09-17)**: 이 문서 §6.
- **B. 절기 위치를 입력으로 — `findReadings(coord)`(원안)**: 채택 안 함 2026-08-29 · 이유: `LiturgicalCoord`는 절기 축만 담아 이름일, 고정일, 음력일로 색인된 본문을 찾지 못한다(2026-08-29 실측), 근거: 설계서 §1.3, §5.6 · 재검토: 없음.
- **C. 독서는 고른 전례일 하나만 받는다(2026-08-29)**: 채택 안 함 2026-09-01 · 이유: 성탄절기 본문 16건이 `date`로만 구별되는데 격자 전례일에는 `date`가 없다. 물어본 날짜는 `resolved.date`에만 있다 · 재검토: 없음.
- **D. 둘째 인자를 `Observance`로**: 채택 안 함 2026-09-13 · 이유: `resolveDate`가 후보를 `Candidate`로 내므로 호출하는 쪽이 가진 것은 그것이고, 규칙이 `observance.id`를 바로 읽으면 `undefined`가 되어 본문 인덱스를 놓친다, 근거: 설계서 §5.6 · 재검토: 없음.

### 우선순위와 옮김 엔진의 범위
- **A. A1(코어) 다음 B1으로 구현 (채택 2026-07-27)**: 이 문서 §6.
- **B. 우선순위와 옮김(transfer) 엔진을 이번 범위에서 뺀다(원안. 분류 필드가 ADR-036 2차 보류로 모두 null이라 입력이 없었다)**: 채택 안 함 2026-07-27 · 이유: ADR-036 D5가 분류 필드를 채워 입력이 생겼다 · 재검토: 없음.

## 미결 사항

이 절은 번호를 더 발급하지 않는다 — 열린 물음의 원장은 설계서 §9 다(설계서 §1.4, 2026-10-10 부터). 항목마다 닫혔으면 결론 한 줄, 열려 있으면 `→ 설계서 미결n` 으로 승계 대상을 적는다 — 이 목록이 대응표다. 승계한 항목의 상태·확인 주체·잠정 답은 설계서의 그 항목이 기준이다.

1. ◐ **송영 A vs B 구분 규정** → 설계서 미결37.
2. ✅ **ordinal-weeks 표 입력** — 닫힘(2026-07-13) · 34주 · 구간 38개 입력 완료, 파서·검증까지 D3 구현(본 ADR §4). 표가 computus와 어긋나지 않음을 1900-2100년 대조로 확인했다.
3. ✅ **조건부 세트 3건**(주의 변모 주일로 지키는 경우)의 캡션 표현 — 닫힘(2026-10-12, 설계서 미결38) · 조건이 독서 카드 이름(「…로 지킬 때」) · D2에서 조건 원문을 `set_note`에 보존했다 · 기준: ADR-038 §3 「구현」.
4. ✅ **스크랩에 없는 시편 편** — 닫힘(2026-07-13) · 전례시편 150편 전편 입력 완료(D1).
5. ✅ **교회력 격자의 빈 칸 6개** (사순5주 나해 · 연중5·8주 나해 · 연중9주 가·다해 · 연중10주 다해 — 원료에 그 날 기사가 없었다) — 닫힘(2026-08-29) · 두 방법을 자리마다 나눠 썼다. 재수집 2칸(사순5주 나해 · 연중5주 나해) — 사이트에 기사는 있는데 태그가 없어 목록 크롤에 안 걸린 것이라 `fetch.py EXTRA_ARTICLES`로 되찾았다(본기도까지 함께 왔다). 손입력 4칸(연중8주 나해 · 연중9주 가·다해 · 연중10주 다해) — 사이트에 아예 없어 기도서를 보고 `articles-supplement.json`에 넣었다. 독서는 2026-07-25·26에(data `bac174e` 계열), 남아 있던 본기도 4건은 2026-08-29에(data `91ee123`) 채웠다 — 주일 본기도는 주기마다 본문이 실제로 달라(ADR-036 §2, 연중 33주 전부 가·나·다해가 다르다) 다른 해에서 복사할 수 없다. 본기도 334 → 338, `readings-report.txt`의 격자 빈 칸 0칸, 주일 본기도 격자도 0칸(같은 날 늦게 `_review` 21건 판별 교정으로 중복 10건이 병합돼 338 → 328).
6. ◐ **에스델 하위 절 표기** — `verseSpec` 문법 확장 여부 → 설계서 미결39.
7. ✅ **날짜를 모르는 성인일 3건**(성 십자가 발견 · 사도 성 바르톨로메오 — 전례일 키에 `date`가 없어 엔진이 날짜로 찾을 수 없었다) — 닫힘(2026-07-27, D5) · 월별 축일 표(`sanctoral.json`)를 조인해 날짜를 역주입한다(`classification.backfill_date`, 독서·본기도 파서가 공유). 이름도 기도서 표제로 맞춘다 — 스크랩의 「사도 성 바르톨로메오 **축일**」 대신 표의 「사도 성 바르톨로메오」(ADR-036 §2 `name` = 대표명). 이름이 다르면 같은 날의 표 id와 독서 id가 서로 달라진다.
8. ◐ **파이프라인 입력을 언제 동결하는가 — 출력 JSON 을 기준으로 (2026-09-13 제기)** → 설계서 미결40. 판단의 이유와 뒤집는 조건은 본 ADR §8.

## 후속 (구현 시)

- 저녁기도와 아침기도 기사는 Phase 4 성무일과의 원료로 따로 모아 둔다(이 문서 §2). 성무일과 전례독서의 데이터는 ADR-042가 다룬다.
