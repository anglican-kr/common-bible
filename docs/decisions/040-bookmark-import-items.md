# ADR-040: 북마크 가져오기의 항목 검사 — 어긋난 항목만 빼고 들인다

- 일시: 2026-10-18
- 상태: 승인됨 — 구현 완료 (2026-10-18)
- 관련: ADR-010(북마크 기능 — 저장 모양), ADR-011(북마크 동기화 — Phase 2a 내보내기 · 가져오기), ADR-012(타입 검사 — 묶음 ③에서 드러남)

## 결정

북마크 가져오기(⋯ 「가져오기」)는 파일의 항목을 하나씩 검사해 **어긋난 항목만 빼고 들인다.** 뺀 개수는 확인 대화상자가 병합 · 덮어쓰기를 고르기 전에 알린다(「올바르지 않은 항목 M개는 빼고 가져옵니다.」). 들일 수 있는 항목이 하나도 없으면 대화상자를 열지 않고 스낵바로 알린다(「가져올 수 있는 항목이 없습니다. 파일에는 올바르지 않은 항목 M개만 들어 있습니다.」).

- **올바른 항목은 앱이 북마크를 처음 저장한 날(2026-04-25)부터 써 온 모양이다**(ADR-010 「데이터 스키마」). 그래서 이 앱이 내보낸 파일은 모두 통과한다.
  - 모든 항목 — 객체, `id`는 비어 있지 않은 문자열로 파일 안에서 처음 나온 것, `type`은 `bookmark` 또는 `folder`.
  - 폴더 — `name` 문자열, `children` 배열(안의 항목도 같은 규칙). `expanded` · `createdAt` · `updatedAt`은 있으면 타입만 본다.
  - 북마크 — `bookId`는 성서 목록에 있는 책, `chapter`는 1부터 그 책의 장 수까지의 정수, `verseSpec`은 `all`이거나 모든 구간이 읽히는 절 범위, `label` 문자열. `note` · `createdAt` · `updatedAt`은 있으면 타입만 본다.
  - 모르는 필드는 그대로 둔다 — 다음 판 앱이 더한 필드가 살아남는다.
- **빼는 단위** — 어긋난 폴더는 그 안의 것까지 함께 빼고, 다른 자리로 옮겨 살리지 않는다. 같은 `id`가 다시 나오면 앞의 것만 들인다(한 id에 두 행이 대답하면 이동 · 삭제 · 동기화가 깨진다).
- **보이는 안내** — 가져오기가 멈출 때(JSON이 아님 · 북마크 파일 형식이 아님 · 들일 항목 없음 · 성서 목록을 불러오지 못함)는 스낵바로 알린다. 스낵바는 같은 글을 라이브 영역에도 넣는다(DESIGN.md §10 「라이브 리전」). 그전에는 라이브 영역에만 넣어, 눈으로는 아무 일도 없어 보였다.
- 구현 — `js/app/bookmark-modals.js` `_sanitizeImportItems`(순수 함수 — `IMPORT_EXPORT` 마커 블록, `tests/unit/bookmark.test.js`) · `openImportModal(items, skipped)`.

## 맥락

`_validateImportData`는 파일에 `bookmarks` 배열이 있는지만 본다(겉모양 — 유닛 테스트가 `{ bookmarks: [{}] }`를 통과로 못박았다). 그 너머의 항목은 검사 없이 저장소로 들어갔다.

- `[null]`이면 개수를 세다 예외가 나고 아무 안내 없이 끝났다.
- 책 · 장 · 절 범위가 빠진 항목은 덮어쓰면 그대로 저장돼, 북마크 목록에 「undefined undefined:undefined」 줄을 만들고 모아 읽기를 「본문을 불러오지 못했습니다 — 네트워크 연결을 확인한 뒤 다시 시도해 주세요」(원인과 다른 안내)로 만들었다. 저장된 항목은 동기화로 다른 기기에도 퍼진다.

타입 검사 묶음 ③(2026-10-18 — 원장 `docs/changes/2026-10-18-typecheck-batch-3.md`)에서 이 믿음이 `openImportModal`의 캐스트 한 줄로 드러나 known-issues §14로 넘겼고, 같은 날 사용자가 방향을 정했다.

## 검토한 대안

- **파일 전체 거절 — 항목이 하나라도 어긋나면 아무것도 들이지 않는다** — 기각 2026-10-18(사용자가 처음 고른 쪽 — 「파일 전체 무결성을 보장하는 것이 더 안전한 듯」) · 이유: 두 방식 모두 어긋난 항목은 저장소에 들이지 않아 앱이 깨질 위험은 같고, 차이는 사용자가 잃는 것이다. 백업 500개 가운데 1개만 깨져도 499개를 앱 안에서 되살릴 길이 없고(JSON을 손으로 고쳐야 한다), 다음 판 앱이 새 항목 종류(예: 노트 — `release/1.6.0` 브랜치의 ADR-026)를 내보내면 파일 전체가 거절된다. 북마크는 서로를 가리키지 않는 기록이라 일부만 들어와도 목록이 어긋나지 않는다. 「다 들어왔다」는 착각은 확인 대화상자가 뺄 개수를 먼저 보여 줘 막는다 · 재검토: 서로를 가리키는 자료(예: 북마크를 참조하는 노트)가 가져오기에 들어올 때 — 그때는 일부만 들이면 끊긴 참조가 생긴다.
- **어긋난 항목을 고쳐서 들이기(빠진 `verseSpec`을 `all`로 채우는 식)** — 기각 2026-10-18 · 이유: 앱이 쓴 적 없는 모양을 추측해 고치면 사용자가 모르는 북마크가 생긴다. 뺀 개수를 알리는 편이 정직하다 · 재검토: 옛 판 앱이 실제로 다른 모양을 썼던 사례가 나오면(그 모양만 옮겨 들인다).
- **절이 본문에 실제로 있는지까지 검사** — 기각 2026-10-18 · 이유: 북마크마다 장 파일을 받아야 한다. 본문에 없는 절은 장 화면과 모아 읽기가 이미 다룬다(모아 읽기는 「표시할 본문이 없습니다」) · 재검토: 없음.

## 검증

- 유닛 `tests/unit/bookmark.test.js`의 `_sanitizeImportItems` 7건 — 앱이 저장하는 모양 그대로의 트리는 바뀌지 않고, 규칙마다 어긋난 꼴은 빠지고 세어진다. 규칙을 하나씩 깨는 변이 다섯(절 범위 · 같은 id · 폴더째 세기 · 장 수 상한 · 선택 필드)을 모두 잡는다.
- e2e `tests/e2e/test_bookmark_export_import.py` — 일부만 어긋난 파일(대화상자의 두 문장, 덮어쓴 뒤 올바른 항목만), 모두 어긋난 파일(스낵바, 목록 그대로), JSON이 아님 · 형식이 아님(스낵바가 눈에 보인다).
