# ADR-005: 검색 인덱싱 전략

- 일시: 2026-03-29
- 상태: 승인됨

## 맥락

성경 전체(35,482절)를 대상으로 전역 전문 검색을 구현해야 한다. 프레임워크 없는 Vanilla JS SPA에서, 외부 서버 없이 클라이언트에서 모든 검색이 이루어져야 한다.

고려 사항:
- 검색할 본문의 규모: 35,482절, 약 6.5MB(클린 텍스트 기준)
- 오프라인 동작 필수(PWA)
- 외부 라이브러리 의존성 최소화(프로젝트 원칙)
- 한국어 텍스트의 특성: 형태소 분석 없이도 부분 문자열 매칭이 쓸모 있다

## 검토한 대안

### A안: 외부 검색 라이브러리 (lunr.js, Fuse.js, FlexSearch 등)

- 장점: 성숙한 토크나이저, 퍼지 매칭, 가중치 랭킹
- 단점:
  - 한국어 형태소 분석을 지원하지 않거나 별도 플러그인이 필요하다.
  - 번들 크기가 늘어난다(lunr 약 8KB, Fuse 약 15KB, FlexSearch 약 6KB).
  - 라이브러리 버전 관리 부담이 있다(CDN 의존 또는 vendoring).
  - 인덱스 형식이 라이브러리에 종속된다.

### B안: 빌드할 때 역색인(Inverted Index) 생성

- 장점: 검색할 때 O(1)로 토큰을 찾아 응답이 빠르다.
- 단점:
  - 한국어 토크나이저를 구현해야 한다(형태소 분석기 또는 n-gram).
  - 형태소 분석기 없이 n-gram을 쓰면 인덱스가 크게 불어난다(2-gram 기준 20MB 이상으로 추정).
  - 부분 문자열 검색("빌라도"로 "빌라도에게"를 찾는 경우)에 맞는 n-gram 크기를 고르기 까다롭다.
  - 구현과 유지보수가 복잡하다.

### C안: 플랫 JSON 배열 + 선형 스캔 (채택)

- 장점:
  - 구현이 매우 단순하다(`String.includes` 한 줄).
  - 인덱스 형식이 직관적이고 라이브러리에 종속되지 않는다.
  - 한국어 부분 문자열 매칭에 자연스럽게 맞는다(형태소 분석 불필요).
  - 인덱스 크기가 원본 텍스트 크기와 같다(추가로 불어나지 않는다).
  - Web Worker에서 실행하므로 메인 스레드를 막지 않는다.
- 단점:
  - 검색 시간이 O(n)이다(35,482절 전체를 훑는다).
  - 랭킹이나 관련도 정렬이 없다(나오는 순서가 곧 성경 순서다).

### 단일 인덱스 파일 `search-index.json` (2026-04-11까지)

- 처음에는 플랫 JSON 배열 하나(`search-index.json`, 6.6MB)에 절마다 `{b, c, v, t}` 행을 담았다(아래 「처음 인덱스 구조」).
- 채택 안 함(2026-04-11). 이유: 검색 알고리즘 자체는 약 16ms로 충분히 빨랐지만, 파일이 하나라서 두 가지 문제가 있었다.
  - 첫 검색 대기: 검색 워커가 전체 파일을 받아야 첫 검색을 할 수 있었다. 신약 7,940절만 있어도 대부분의 검색에서 쓸 만한 결과가 나오는데, 구약 23,430절까지 기다려야 했다.
  - 확장성: 교회력과 성무일과 텍스트를 더하면 파일 하나가 계속 커진다. 새 콘텐츠를 더할 때마다 전체 인덱스를 다시 빌드하고 다시 받아야 했다.
  - 행마다 키 이름(`b`, `c`, `v`, `t`)이 35,484번 되풀이되는 것도 낭비였다.

### 따옴표를 같은 글자로 보기 (2026-11-06)

- 곧은 따옴표와 곱슬 따옴표를 한 글자로 맞춰 비교하는 안이다. 글자 수가 그대로라 강조 표시를 고치지 않아도 된다.
- 채택 안 함(2026-11-06). 이유: 「빛이 생겨라! 하시자」처럼 따옴표 없이 기억한 문구가 따옴표를 사이에 둔 본문(`“빛이 생겨라!” 하시자`)을 찾지 못한다. 성서 본문에 따옴표가 1만 개 넘게 있어 이런 경우가 자주 생긴다. 아래 「따옴표를 무시하는 일치」를 채택했다.
- 재검토 조건: 따옴표가 든 문구만 골라 찾아야 할 일이 생길 때.

### 인덱서가 모든 조각 사이에 공백을 넣지 않기 (2026-11-07)

- 조각을 공백 없이 모두 이어, 본문의 공백 접기를 두지 않는 안이다.
- 채택 안 함(2026-11-07). 이유: 시의 줄과 새 문단 사이에서 낱말이 붙는다. 원문에 이미 공백이 둘인 163절은 그대로 남아 본문의 공백 접기가 어차피 필요하다. 인용 조각 뒤와 여는 따옴표로 끝난 조각 뒤만 공백 없이 잇는 안을 채택했다(아래 「일치 규칙」).
- 재검토 조건: 산문과 운문의 경계에서도 화면이 공백 없이 이어 그리게 될 때.

### 여러 장을 한 화면에 이어 보여 주기 (2026-11-07)

- `사무상 18:6-9, 19:1-7`을 전례독서 화면처럼 한 화면에 이어 그리는 안이다.
- 채택 안 함(2026-11-07, 사용자 결정). 이유: 이어 읽기에는 가장 좋지만 새 주소와 새 화면이 필요해서, 제목줄, 복사, 오디오, 뒤로 가기의 동작을 모두 새로 정해야 한다. 여러 장에 걸치는 표기는 전례독서 표기 2,006개 가운데 101개로 드물다.
- 재검토 조건: 구절을 이어 읽는 화면을 바라는 요청이 생길 때. 구절을 장별로 나누는 코드는 그대로 쓸 수 있다.

### 첫 장을 열고 나머지 구간을 안내하기 (2026-11-07)

- 첫 장을 열어 강조하고, 화면에 「19장 1-7절로 이동」 안내를 띄우는 안이다.
- 채택 안 함(2026-11-07, 사용자 결정). 이유: 안내를 놓치면 나머지 구간을 보지 못하고, 장 화면에 새 요소가 생긴다.
- 재검토 조건: 없음.

### 상, 하 표시대로 절의 반쪽만 보여 주기 (2026-11-07)

- `사도 2:42-47상`에서 47절의 앞 절반만 강조하는 안이다.
- 채택 안 함(2026-11-07, 사용자 결정). 이유: 절을 나누는 위치는 전례독서 화면이 쓰는 반절 표에만 있다. 장 화면의 주소에 적는 글자(`3a`)는 데이터의 반쪽 절이나 시의 줄을 가리키므로 뜻이 다르다. 장 화면은 앞뒤 절과 함께 읽는 곳이라 절 전체를 강조해도 찾는 자리를 알 수 있다.
- 재검토 조건: 장 화면에서 절의 일부를 강조해야 할 일이 생길 때.

## 결정

**C안 채택**: 빌드할 때 Python 스크립트(`search_indexer.py`)로 인덱스를 만들고, 실행 중에는 Web Worker에서 선형 스캔으로 검색한다. 2026-04-11부터 인덱스는 파일 넷으로 나눈 컬럼형 형식이다(아래 「청크 분할과 컬럼형 형식」).

### 근거

1. **검색할 본문이 충분히 작다**: 35,482건을 `String.includes`로 훑는 선형 스캔은 요즘 기기에서 수십 밀리초 안에 끝난다. Web Worker에서 실행하므로 UI도 멈추지 않는다.
2. **한국어 특성**: 한국어는 조사가 붙는 교착어라서("빌라도"가 "빌라도에게", "빌라도가"로 바뀐다) 부분 문자열 매칭이 역색인보다 오히려 자연스럽다. 역색인은 형태소 분석 없이는 이런 변형을 놓친다.
3. **의존성 0**: 프로젝트 원칙(서버 의존성 없음, 외부 라이브러리 최소화)에 맞다.
4. **유지보수 단순성**: 인덱스 필드가 `{b, c, v, t}` 넷뿐이라 디버깅과 수정이 쉽다.

### 처음 인덱스 구조 (2026-03-29)

```json
{
  "meta": {
    "aliases": { "창": "gen", "창세": "gen", "창세기": "gen", ... },
    "books": { "gen": { "ko": "창세기", "bo": 0 }, ... }
  },
  "verses": [
    { "b": "gen", "c": 1, "v": 1, "t": "한처음에 하느님께서 하늘과 땅을 지어내셨다." }
  ]
}
```

- `meta.aliases`(301개): 절 참조 검색("창세 1:3")에서 한국어 약어를 bookId로 바꾼다.
- `meta.books`: 정렬 인덱스(`bo`)와 한국어 이름. 결과를 성경 순서로 보여 주는 데 쓴다.
- `verses[].t`: `¶`를 지우고 `\n`을 공백으로 바꾼 클린 텍스트. 프롤로그(집회서 머리말)는 뺀다.

### 청크 분할과 컬럼형 형식 (2026-04-11)

#### 파일 분할

단일 `search-index.json`을 파일 넷으로 나눴다.

| 파일 | 내용 | 크기 |
|------|------|------|
| `data/search-meta.json` | aliases + books 메타데이터 | 약 9KB |
| `data/search-nt.json` | 신약 7,940절 | 약 1.3MB |
| `data/search-dc.json` | 외경 4,114절 | 약 700KB |
| `data/search-ot.json` | 구약 23,430절 | 약 3.8MB |

받는 순서는 NT, DC, OT다. NT를 받는 즉시 첫 검색을 할 수 있다(progressive search). 앞으로 교회력 텍스트는 `search-lectionary.json` 같은 청크를 더하는 것만으로 넓힌다.

#### 컬럼형 형식과 RLE

행마다 키 이름을 되풀이하지 않도록 열(컬럼) 단위로 담는다.

```json
{
  "books": ["matt", "mark", "luke", ...],
  "b": [[0, 1071], [1, 678], ...],
  "c": [1, 1, 1, ..., 2, 2, ...],
  "v": [1, 2, 3, ...],
  "t": ["한처음에...", "땅은 아직...", ...]
}
```

- `b`: RLE 인코딩이다. 같은 책이 이어지는 구간을 `[bookIndex, count]` 쌍으로 줄인다.
- Worker에서 `Uint16Array`로 펴서 메모리를 아낀다.

#### Progressive search

Worker 프로토콜에 `partial-results` 메시지를 더했다.

1. 첫 청크(NT)를 다 받으면 그 청크만 검색해 `partial-results`를 보낸다.
2. 나머지 청크를 다 받으면 전체를 검색해 `results`를 보낸다.

앱은 `partial-results`를 받으면 로딩 스피너를 중간 결과로 바꾸고, 마지막 `results`가 오면 전체 결과로 갱신한다.

#### 검색 알고리즘

바뀌지 않았다. C안(선형 스캔과 `String.includes`)을 그대로 쓴다.

#### 하위 호환성 (2026-04-11 당시)

- `sw.js`의 `CACHE_NAME` 버전을 올려 옛 `search-index.json` 캐시를 자동으로 지웠다.
- `search-meta.json`은 SHELL_FILES에 넣었다(오프라인에서 바로 쓴다).
- 청크 파일은 네트워크 우선 방식으로 캐시했다(그때의 `data/bible/*.json`과 같은 전략).

### 검색 연산자 `in:` (2026-05-05)

#### 맥락

검색 결과가 73권 전체에서 섞여 나와, 특정 책 안에서 키워드를 찾으려면 결과를 사람이 다시 걸러야 했다. 또 컴팩트 모달을 열 때 칩으로 연산자를 알려 주면 따로 배우지 않아도 쓸 수 있다.

#### 문법

`키워드 in:<책-별칭>` 형식이다. `in:` 토큰은 쿼리 어디에 와도 되고, 여러 개를 쓰면 책의 합집합(OR)으로 처리한다. `in:`과 별칭 사이의 공백은 무시한다. `in: 요한`도 `in:요한`과 같다.

```
사랑 in:요한               → 요한 복음서에서 "사랑" 검색
사랑 in: 요한              → 동일 (공백 허용)
은혜 in:롬 in:갈           → 로마서 + 갈라티아서에서 "은혜" 검색
in:요한                    → 키워드 없음 → 검색 차단 (안내 표시)
사랑 in:없는책             → unmatched 별칭 → 검색 차단 + notice
```

별칭 매칭은 기존 `search-meta.aliases` 사전을 그대로 쓴다. 매칭에 실패한 토큰은 `unmatchedScopes` 페이로드로 메인 스레드에 전해, 결과 영역 위에 안내 문구로 보인다.

#### 구현

- `js/search-worker.js`의 `parseQuery(raw)`가 `IN_RE = /(?:^|\s)in:\s*(\S+)/g`로 토큰을 뽑는다(콜론과 별칭 사이의 공백을 받아들인다).
- `gatherResults`에 `restrictBooks: Set<bookId>` 인자를 더했다. 비어 있지 않으면 그 책만 통과한다.
- `unmatchedScopes`가 있으면 검색하지 않고 빈 결과와 알림만 돌려준다.

#### UI (2026-05-05 당시)

- 컴팩트 모달 아래에 `+ in:` 칩(`#search-sheet-chips` 안의 `.search-chip`)을 두었다. 누르면 입력창 끝에 ` in:`을 넣고, 커서를 `:` 뒤에 둔다.
- `pointerdown.preventDefault`로 입력창의 포커스를 지켜 IME가 깜박이지 않게 했다.
- 지금의 검색 화면 구성은 ADR-033에 있다.

### 따옴표를 무시하는 일치 (2026-11-06)

#### 맥락

성서 본문이 곧은 따옴표(`"` `'`)에서 곱슬 따옴표(`“ ” ‘ ’`)로 바뀌었다(데이터 저장소 #60). 일치 판정과 강조 표시가 따옴표를 다른 글자와 똑같이 비교하므로, 곧은 따옴표로 친 검색어는 바뀐 본문을 찾지 못한다. 또 「빛이 생겨라! 하시자」처럼 따옴표 없이 기억한 문구는 본문(`“빛이 생겨라!” 하시자`)과 글자가 하나 달라 바뀌기 전에도 찾지 못했다.

#### 일치 규칙

검색어와 본문 모두에서 따옴표 여섯 가지(`"` `'` `“` `”` `‘` `’`)를 지우고 비교한다(사용자 결정 2026-11-06). 버린 안은 위 「검토한 대안」의 「따옴표를 같은 글자로 보기」에 있다.

- 성서 본문에는 아포스트로피가 없어(데이터 저장소의 2026-11-06 조사) 홑따옴표까지 지워도 잃는 일치가 없다.
- 본문과 검색어 모두 따옴표를 지운 뒤 이어진 공백을 한 칸으로 접는다. 검색어는 앞뒤 공백도 지운다. 그래서 따옴표만 친 검색어(`"`, `" '`)는 빈 검색어가 되고 결과 없음으로 다룬다. 빈 문자열과 공백 한 칸은 거의 모든 절에 들어 있기 때문이다.
- 본문의 공백도 접는 까닭은 따옴표를 지우면 공백이 둘 남는 본문이 있기 때문이다. 옛 색인은 인용으로 나뉜 조각 사이에 공백 한 칸을 넣어, 갈라 3:8이 `아브라함에게 “ 너로`로 저장되어 있었다. 접지 않으면 `아브라함에게 너로`가 그 절을 찾지 못했다(2026-11-06 확인). 이런 절이 신약에 148절이고, 원문에 이미 공백이 둘인 절이 163절(구약 69, 신약 93, 외경 1)이다. 인덱서를 고친 뒤에도(바로 아래) 원문의 163절 때문에 접기는 필요하다.
- 인덱서는 한 절의 조각을 공백 한 칸으로 잇되, 장 화면이 같은 줄에서 앞 조각에 붙여 그리는 곳은 공백 없이 잇는다(사용자 결정 2026-11-07). 인용 조각 바로 뒤(`받으리라.”는 복음`, `바치는 것이라는 말을`, `주님, 우리는`)와 여는 따옴표로 끝난 조각 바로 뒤(`“너로`)다. 새 문단이나 산문과 운문의 경계는 화면에서 줄이 바뀌므로 공백을 둔다. 이전에는 모든 조각 사이에 공백을 넣어서, 화면에 보이는 대로 이어 친 문구(`받으리라.”는 복음`)가 찾아지지 않는 절이 66절 있었다.
- 강조 표시는 따옴표를 지운 글자에서 찾은 범위를 원래 본문의 위치로 되돌려 감싼다. 찾은 구간 양끝에 붙은 본문의 따옴표는 강조에서 빠지고, 구간 가운데의 따옴표는 함께 강조된다.
- 장 화면은 한 절을 조각(인용 앞뒤, 시의 줄마다)으로 나눠 그린다. 그래서 조각을 그려진 그대로 이은 글에서 한 번 찾고(새 색인의 글), 찾지 못하면 조각 사이에 공백 한 칸을 둔 글에서 찾는다(옛 색인의 글). 앱과 데이터 저장소가 따로 배포되어 어느 색인이든 쓰일 수 있기 때문이다. 조각마다 그 구간과 겹치는 부분만 감싸고, 조각 경계를 넘는 일치도 강조된다.
- 검색 인덱스에는 따옴표가 그대로 남는다. 따옴표를 지우면 결과 목록의 발췌에서도 따옴표가 사라진다. 인덱스에서 달라지는 것은 조각을 잇는 공백뿐이다.

#### 구현

- 검색 워커(`js/search-worker.js`)와 화면 코드(`js/app/search.js`)가 따옴표를 지우는 함수(`normalizeForMatch`, 검색어용 `normalizeQuery`)와 일치 범위를 찾는 함수(`findMatchRanges`)를 같은 코드로 한 벌씩 둔다. 워커는 모듈을 가져올 수 없는 클래식 스크립트라 화면 모듈과 코드를 나눠 쓰지 못한다(`IN_RE`도 같은 방식으로 두 벌이다). 두 벌의 코드가 글자까지 같은지 `tests/unit/search.test.js`가 확인한다.
- 워커는 청크마다 따옴표를 지우고 공백을 접은 소문자 본문을 처음 검색할 때 한 번 만들어 둔다.
- 인덱서(`common-bible-data`의 `src/search_indexer.py`)의 `segments_text`가 조각을 잇는다. 색인은 그 저장소의 파이프라인이 만들고, 인덱서를 바꾼 PR은 다시 만든 색인과 `bible-manifest.json`을 함께 올린다(`pipeline.yml`의 drift 검사).
- 화면은 `js/app/views.js`의 `pieceTrailingSpace`가 조각 끝의 공백을 정한다. 칩이 뒤따르는 조각, 부호만 있는 조각, 여는 따옴표로 끝나는 조각에는 공백이 없다. 인덱서와 같은 글이 되도록 두 곳의 규칙을 맞춰 둔다.
- 장 화면의 강조는 `highlightTextNodes`(`js/app/search.js`)가 맡는다. 한 절의 본문 조각(글 노드)을 받아 위 규칙대로 찾고, 조각마다 겹치는 부분을 `<mark>`로 바꿔 넣는다. 결과 목록의 발췌는 같은 분할 함수(`splitPiecesByMatches`)를 쓴다.

### 구절 표기와 구절 바로가기 (2026-11-07)

#### 맥락

검색창은 `창세 1:3`과 `창세 1:3-11`만 구절로 읽었다. 그 밖의 표기는 낱말 검색으로 넘어가 「검색 결과가 없습니다」가 나왔다(`요한 3:16, 18-19`에서 발견). 전례독서의 표기를 그대로 치면 자주 만나는 일이다. 전례독서 표기 2,006개 가운데 1,382개만 구절로 읽었다. 이 결정으로 1,996개를 읽는다. 나머지 10개는 송가 이름(`창조송가 1-3`), 괄호 설명이 붙은 송가(`루가 1:68-79 (즈가리야 송가)`), 에스델 추가 본문의 번호(`에스 4:17(12-16), 17(23-25)`)다.

#### 읽는 표기

검색어 **전체가** 다음 형식일 때만 구절로 읽는다. 책 이름 뒤에 장과 절이 오고, 책 이름은 맨 앞에 한 번만 쓴다.

| 표기 | 예 | 뜻 |
| --- | --- | --- |
| 장 | `시편 116`, `시편 42, 43` | 그 장 전체 |
| 절과 범위 | `창세 1:3`, `창세 1:3-11` | 그 장의 그 절 |
| 쉼표로 이은 절 | `요한 3:1, 3, 5-7, 9` | 장을 적지 않은 구간은 바로 앞 구간의 장이다 |
| 뒤에 장을 다시 적은 구간 | `사무상 18:6-9, 19:1-7` | 장마다 나눈다 |
| 장을 넘는 범위 | `이사 61:10-62:3`, `마태 9:35-10:1, 5-8` | 앞 장은 그 절부터 끝까지, 사이의 장은 전체, 끝 장은 1절부터 그 절까지. 뒤따르는 구간은 끝 장의 절이다 |

- **쉼표는 이 형식 안에서만 구분자다.** 낱말 검색에서는 쉼표도 본문 글자로 찾는다. 35,483절 가운데 11,175절에 쉼표가 있다. 숫자가 든 절은 1절뿐이고 「책 이름과 숫자」가 든 절은 없어서(2026-11-07 실측) 두 쓰임이 부딪히지 않는다.
- **절의 반쪽 표시는 지우고 절 전체를 연다.** 전례독서의 「상」 「하」, 절 선택 복사의 「ㄱ」 「ㄴ」, 북마크 모아 읽기의 로마자 소문자가 해당한다.
- **장과 절 번호는 세 자리까지다.** 주소의 검사(ADR-040)와 같은 상한이다. 장 번호가 0이거나 끝 장이 시작 장보다 앞이면 구절로 읽지 않는다.

#### 화면

- **한 장이면 예전과 같다.** Enter를 치면 그 장을 열어 해당 절을 강조하고, 검색 주소로 바로 들어오면 구절 바로가기 카드를 보인다.
- **여러 장이면 장마다 카드를 하나씩 보인다.** Enter를 쳐도 이동하지 않는다. 어느 장을 먼저 열지 앱이 정할 수 없기 때문이다.
- 카드 제목은 「사무엘상 18장 6-9절」로 쓴다. 장의 끝까지면 「이사야 61장 10절부터」, 장 전체면 「창세기 2장」이다.

#### 구현

- 검색 워커의 `tryVerseRef`가 표기를 읽어 장마다 `chapter`와 `verses`를 돌려준다(`parts`). 장의 끝을 모르므로 끝까지 가는 구간은 끝 번호를 999로 적는다. 주소가 받는 가장 큰 번호이고, 가장 큰 절 번호는 176이다. 장 화면이 이 끝을 실제 마지막 절로 자르고 주소도 고친다(ADR-040).
- 앱의 `verseRefTargets`(`js/app/search.js`)가 `verseNumberSpec`으로 절 목록을 오름차순으로 합쳐 주소를 만든다. 순서가 뒤섞인 주소는 장 화면이 강조하지 않기 때문이다(ADR-040). 워커는 모듈을 불러올 수 없어 이 일을 앱에서 한다.
- 워커는 책의 장 수를 모른다. 그래서 없는 장(`요한 99`)도 구절로 읽고, 장 화면이 「해당 장을 찾을 수 없습니다」를 보인다. `요한 99:1`이 예전부터 그렇게 동작했다.
- `tests/unit/search-worker.data.test.js`가 전례독서의 표기를 모두 읽어 저장된 장과 절(`refs`)과 대조한다.

### 성능 한계와 앞으로의 대응

검색할 본문이 기도서와 성무일과 등으로 넓어져 10만 건을 넘으면 선형 스캔의 지연이 느껴질 수 있다. 그때 B안(역색인)이나 `Intl.Segmenter` 기반 토크나이저 도입을 다시 검토한다.
