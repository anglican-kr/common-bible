# ADR-027: Source markup DSL 위치 잡기 + `<parallel>` element 도입

- 일시: 2026-05-31
- 상태: 승인됨 — **구현 완료** (2026-05-31, 1.5.x 트랙). 화면은 footnote anchor 방식이다(§2 「화면」). range 중첩을 허용한다(§2 「검증 규칙」). 실제 source/*.md에 `<parallel>` 마커를 다는 콘텐츠 작업은 콘텐츠 자문과 묶어 따로 진행한다(지금 `source/2sam.md` 5장에 셋이 있다)
- 관련 ADR: ADR-006(운문 segments 형식), ADR-018(`js/app/views-routing.js` 본문 렌더 위치), ADR-022(인용·주석과 per-parallel tradition), ADR-020(저장소 4분할. 이 결정도 app과 data 두 저장소를 모두 고친다)

이 ADR은 두 결정을 한 묶음으로 다룬다. (1) `source/*.md` 마크업의 위치를 마크다운과 자체 도메인 DSL의 혼합으로 문서에 적는다. (2) 그 DSL에 `<parallel>` element를 새로 둔다. 구현은 parser.py의 block 마커 인식, JSON 스키마 확장, `js/app/parallels.js`의 ※ 앵커 렌더, 데이터 검증 테스트, 유닛 테스트로 이루어졌다. 처음 「현재 상태」 기록은 구현을 뒤의 일로 적고 `js/app/parallels.js`(가칭)가 단락 배너를 그린다고 적었지만, 같은 날 구현을 마쳤고 화면은 배너가 아니라 ※ 앵커가 되었다.

## 맥락

### 1. 비표준 element 이야기

ADR-022가 들인 `<cite>`·`<note>` 마크업을 쓰다 보니 한 가지 의문이 자연스럽게 생겼다.

- `<cite>`는 HTML5 표준 엘리먼트지만, 우리가 쓰는 속성(`src`·`parallels`·`tradition`)은 HTML5 정의를 벗어난다.
- `<note>`는 HTML5 규격에 아예 없다(DocBook과 TEI의 element다).
- ADR-022 §2의 per-parallel tradition(2026-05-31)까지 더해 cite 태그의 속성이 더 늘었다.

이 위에 새 `<parallel>` 엘리먼트까지 더할지 고민하던 차에, 「HTML 표준이 아닌데?」라는 질문이 다시 나왔다.

### 2. 그러나 source는 브라우저가 렌더하지 않는다

`source/*.md`의 마크업이 브라우저에 직접 보이는 경로는 0이다.

```
source/*.md   (작성 시점)
  → Python parser.py (도메인 토큰 인식)
  → output/parsed_bible.json
  → split_bible.py
  → data/bible/{book_id}-{chapter}.json   (런타임 입력)
  → JS app (DOM 빌드)
  → 브라우저
```

곧 `<note>`·`<cite src="...">`·`<parallel>` 같은 토큰은 한 번도 HTML 엘리먼트로 쓰인 적이 없다. 늘 파서가 읽는 마크업 토큰이고, 출력 DOM은 따로 만든다. 예를 들어 `<note>X</note>[^id]`는 `<span class="note-anchor" role="button">X</span>`로 그린다. 처음에는 `<button class="note-anchor">X</button>`로 적었지만, 주석 앵커는 줄바꿈 때문에 span을 쓴다(ADR-022 §6).

### 3. 디지털 성서 인코딩의 관행

디지털 성서와 학술 텍스트 인코딩 표준은 모두 도메인에 맞춘 마크업을 쓴다. HTML 표준에 매이지 않는다.

- **USFM** (SIL/UBS): 성경 저작의 사실상 표준. `\v 1 본문 \f + 각주 \f*`, `\xt 마르 12:29`, `\r section reference` 같은 백슬래시 마커를 쓴다.
- **USX**: USFM의 XML 변형. `<note caller="+">…</note>`, `<char style="xt">마르 12:29</char>`.
- **OSIS** (SBL): 성서 XML 표준. `<reference>`, `<note>`, `<milestone>`.
- **TEI** (Text Encoding Initiative): 학술 텍스트 표준. `<note>`, `<seg>`, `<linkGrp>`.
- **JATS**, **DocBook**: 학술 출판. 모두 그 용도에 맞춘 element를 쓴다.

이 프로젝트의 방식, 곧 마크다운(CommonMark 호환)과 자체 도메인 DSL도 이와 같다. 도메인 DSL의 엘리먼트 이름은 뜻을 가장 잘 드러내는 이름을 골라도 된다.

### 4. 표현의 한계 — 절 단위 `<cite>`와 단락 단위 병행 본문이 맞지 않는다

ADR-022의 `<cite>`는 절 단위 인용 마커다(§3, 절 경계를 넘을 수 없다). 그런데 사무엘상하, 열왕기상하, 역대상하 사이에는 같은 사건을 두 번 서술하는 **단락 단위 병행 이야기**가 많다.

- 1역대 11:1-9 ∥ 2사무 5:1-10 (다윗의 왕 즉위)
- 1역대 13 ∥ 2사무 6 (법궤 이동)
- 1역대 17 ∥ 2사무 7 (다윗 언약)
- 그 밖에 수십 건

이것을 지금의 `<cite>`로 표현하면 다음 문제가 생긴다.
- 9절짜리 병행이면 `<cite parallels="2사무 5:1-10">…</cite>`를 아홉 번 되풀이해야 한다(중복 제거로 칩은 1회만 뜨지만 마크업 부담은 그대로다).
- 뜻이 정확하지 않다. 병행 이야기는 인용이 아니라, 두 책이 따로 서술한 같은 사건이다.
- 어디까지가 병행인지를 데이터로 적을 자리가 없다. 칩은 「여기부터 어디까지」가 병행인지 알 수 없다.

ADR-022의 `<cite>` 모델은 신약의 짧은 구약 인용에는 잘 맞지만, 구약 역사서 사이의 긴 병행 이야기에는 모자란다. 따로 element가 필요하다.

## 결정

### 1. Source DSL 위치 잡기 (문서에 적기)

`source/*.md` 마크업은 **마크다운(CommonMark)과 이 프로젝트가 스스로 정의한 XML 모양의 도메인 DSL**을 섞은 형식이다.

- 파이프라인: source, Python parser, JSON, JS DOM 순서로 간다. 브라우저는 source의 마크업 토큰을 직접 그리지 않는다.
- DSL element가 「HTML 표준을 지키는지」는 설계 제약이 아니다. USFM, USX, OSIS, TEI 같은 디지털 성서와 학술 텍스트 인코딩 표준의 관행대로, 뜻을 가장 잘 드러내는 이름을 고른다.
- 지금 정의된 DSL element:
  - `<cite src="..." parallels="..." tradition="...">…</cite>`: 절 안의 인라인 인용 마커(ADR-022)
  - `<note>X</note>[^id]`: 절 안의 인라인 앵커를 명시적으로 감싸는 마커(ADR-022 §1)
  - `<parallel src="..." range="..." [tradition="..."]/>`: 절 사이의 블록 단위 병행 본문 마커(이 ADR)
- 앞으로 더할 element는 별도 ADR이나 ADR-022/027의 개정으로 등록한다.
- **새 element를 들이는 절차**: 새로 만들기 전에 USFM 마커 목록과 USX/OSIS element 목록을 한 번 훑어, 같은 뜻이 이미 표준에 있는지 확인한다. 있으면 (a) 이름과 속성을 그 표준에서 빌려 익히는 길을 짧게 하고, (b) 해당 ADR의 「선례」 절에 OSIS/USFM 대응을 적는다. 우리만의 발명은 표준에 정확히 맞는 것이 없을 때로 한정한다.

`<cite>`가 HTML5 표준 element 이름과 겹치는 것은 의도한 우연이다. 인용이라는 뜻에 자연스럽게 맞고, 표준 element 이름을 다시 쓰면 익히는 부담이 줄어든다. 다만 우리 속성(`src`·`parallels`·`tradition`)은 HTML5 정의를 넘어선 이 앱만의 확장임을 밝혀 둔다.

### 2. `<parallel>` element — 단락 단위 병행 본문 마커

#### 마크다운 표현

```markdown
<parallel src="2사무 5:1-10" range="11:1-9"/>
[1] 온 이스라엘이 헤브론에 모여서 다윗을 찾아와 말하였다…
[2] …
[9] …본문 끝
[10] 다른 단락 시작 (병행 끝)
```

- **스스로 닫히는 단일 토큰**(`<parallel ... />`)이다. 절 사이 빈 줄이나 바로 앞 한 줄에 두고, **다음 절 마커 `[N]` 바로 앞**에 나오면 그 절부터 `range`까지를 병행 단락으로 본다.
- 이 마커는 본문을 감싸지 않는다. 단락의 경계를 표시하고 메타데이터를 나르는 역할만 한다. 본문은 그 아래 일반 절 마커(`[N]`)로 그대로 쓴다.

#### 선례 — OSIS와 USFM 대응

이 element는 새로 발명한 것이 아니라, 두 표준의 정확한 대응물을 우리 마크업 규칙으로 옮긴 것이다.

- **USFM `\r` (section reference / parallel reference)**: 단락 머리 뒤에 병행 본문의 출처를 한 줄로 적는 마커다. 가장 직접적인 대응이다. USFM의 `\r`가 *「이 단락이 어느 본문과 병행인지」*를 적는 자리이고, 우리 `<parallel>`도 같은 역할을 한다.
- **OSIS `<reference type="parallel">`**: `<div type="section">` 안에 둘 수 있는 상호 참조의 한 종류다. OSIS는 상호 참조를 `quotation`·`crossReference`·`parallel`·`commentary` 등으로 나눈다. 우리의 ADR-022(`<cite>`)와 ADR-027(`<parallel>`)의 구분도 같은 축을 따른다.

이 선례 덕분에 element 이름과 속성을 따로 만들 필요가 없었다. `<parallel>`은 OSIS의 type 이름 그대로이고, `src`/`range` 속성도 USFM `\r` 내용과 같은 정보 단위다.

#### 속성

| 속성 | 필수 | 뜻 |
|---|---|---|
| `src` | ✓ | 병행 출처. `<cite src>`와 같은 형식과 문법(`약어 장:절-절` / `약어 장:절-장:절`). 여러 출처는 세미콜론(`;`)으로 나눈다: `src="2사무 5:1-10; 1역대 11:1-9"`. |
| `range` | ✓ | 지금 책, 지금 장 안의 적용 범위. `장:절-절`이나 `장:절-장:절`(장을 넘는 경우). 지금 장 안이라도 `장` 접두사를 적는다(예: `range="11:1-9"`). 한 장 전체는 `range="11"`. |
| `tradition` | △ | 선택. `<cite tradition>`과 같은 뜻(보여 주기만 하는 라벨). per-parallel tradition은 src 항목 끝에 인라인 `[전통]`으로 적는다(ADR-022 §2, 2026-05-31과 같다). |

#### 검증 규칙

- `range`의 시작 절은 마커 바로 뒤에 나오는 첫 `[N]`과 같아야 한다(교차 확인). 다르면 parser가 ValueError를 낸다.
- `range`의 끝 절은 같은 장 안에 실제로 있어야 한다(chapter_count 검증).
- `src`의 각 항목은 `<cite src>`처럼 책 약어, 장, 절 범위가 실제로 있는지 검증한다.
- `<parallel>`은 스스로 닫히는 블록 마커라, 물리적으로 겹쳐 넣는(nesting) 것은 원래 불가능하다.
- **range가 겹치는 것(한 range가 다른 range의 일부)은 허용한다**(2026-05-31). 큰 단락과 그 안의 더 좁은 단락이 서로 다른 출처와 병행하는 경우가 실제 콘텐츠에 흔하다. 예: 2사무 5:11-25가 1역대 14:1-16과 병행이면서, 그 가운데 5:14-16만 1역대 3:5-8과도 따로 병행한다.
- 앱은 같은 절에서 시작하는 마커 둘의 ※ 앵커를 그 절 앞에 나란히 그리고, 각 앵커는 따로 툴팁을 연다(`tests/unit/parallels.test.js`). 다만 parser는 절 없이 마커 둘이 이어지는 것을 오류로 막으므로(「마커 두 개가 연속 등장」), 지금 데이터에서는 이 경우가 생기지 않는다(known-issues §29).

#### JSON 스키마

병행 마커는 절 데이터 안이 아니라 **장 단위 메타데이터**로 따로 둔다. 단락 범위 단위의 정보이지 절이나 segment 단위가 아니기 때문이다.

`data/bible/{book_id}-{chapter}.json`의 선택 필드:

```json
{
  "book_id": "1chr",
  "chapter": 11,
  "verses": [ ... ],
  "parallels": [
    {
      "src": ["2사무 5:1-10"],
      "range": "11:1-9"
    },
    {
      "src": ["2사무 23:8-39"],
      "range": "11:10-47"
    }
  ]
}
```

- `parallels`는 선택이다(없으면 키 자체를 뺀다). 한 장에 병행 단락이 여럿 있을 수 있다.
- `src`는 늘 배열이다. 출처가 하나여도 `["..."]`다. 출처마다 사본 전통이 있으면 `[{ref, tradition}]` 형태로, ADR-022 §2와 같다.
- `range`는 문자열이고, 위 마크다운의 `range` 값 그대로다.

#### 화면

- **앵커**: `range` 시작 절 바로 앞에 작은 `※` 글리프(`.parallel-anchor`, 위첨자)를 넣는다. 사본 주석(`.note-anchor--variant`)과 같은 글리프로 일부러 맞췄다. 「이 자리에 보조 정보가 있다」는 신호를 한 종류로 모은다. 사본 주석(`<note></note>[^id]`)이 이미 쓰는 `※`를 그대로 다시 쓰므로, 사용자가 익힐 기호가 늘지 않는다.
- **툴팁**: 앵커를 누르면 `note-tooltip`을 다시 쓴다. 머리는 `range`(예: `5:1-10`)이고, 본문은 `<sourceLink> 참조` 형태다(예: `1역대 11:1-9 참조`). 출처가 여럿이면 `<link1> · <link2> 참조`로 잇는다. 사본 전통 라벨은 링크 글자 앞에 붙인다(`(칠십인역 시편 16:8)`).
- **본문 안의 출처 링크를 누르면**: 그 ref의 cite-sheet가 열리고 툴팁은 닫힌다(떠 있는 화면이 두 겹이 되는 것을 피한다). 출처가 여럿이면 사용자가 보고 싶은 ref를 골라 시트에 띄운다. 한 앵커에서 여러 병행 본문을 견줄 수 있다.
- **범위를 보이는 따로 된 표시는 쓰지 않는다**: 처음에는 range 안의 절들에 왼쪽 띠를 두는 안도 있었다. 앵커가 시작 위치를 보이고 툴팁 글자(`5:1-10`)가 끝 위치를 밝히므로, 더 보탤 표시가 필요 없다고 보고 뺐다.
- **토글**: 인용 칩, 주석과 같은 `bible-cite-show` localStorage 토글로 함께 켜고 끈다. 설정 항목을 따로 더하지 않는다.
- **데스크톱과 모바일 공통**: 앵커는 인라인 위첨자라 어느 화면 크기에서도 같다. 툴팁은 기존 note-tooltip의 앵커를 따라가는 위치 로직을 그대로 쓴다(위쪽을 먼저 쓰고, 자리가 모자라면 아래로 뒤집힌다).
- **접근성**: 앵커는 `<button class="parallel-anchor">`다(네이티브 button이라 Enter/Space가 저절로 작동한다). `aria-label`은 `"5:1-10 병행 본문 안내"`다. 툴팁 본문의 링크도 `<button class="parallel-tooltip-ref">`이고, `aria-label`은 `"<ref> 본문 보기"`다.

#### `<cite>`와의 관계

- `<cite>`와 `<parallel>`은 뜻이 일부 겹치지만(둘 다 다른 본문 위치를 가리킨다), 분명히 다른 층에서 작동한다.
  - `<cite>`: 한 절 안의 인용 한 조각. segment 단위이고, 인라인 칩으로 보인다.
  - `<parallel>`: 한 단락 전체의 병행 이야기. 장 단위이고, 단락 첫 절 앞의 ※ 앵커로 보인다(처음 계획은 블록 배너).
- 한 장 안에 둘이 함께 있을 수 있다. 병행 단락 안의 절에 `<cite>`가 있으면 그 칩도 그대로 그린다. 그래서 한 단락 안에 `<parallel>`의 ※ 앵커와 cite 칩이 함께 보일 수 있다(둘이 가리키는 것이 다르다).
- 데이터 스키마도 나뉜다. `<cite>`는 `segment.cite`·`segment.parallels`·`segment.tradition`, `<parallel>`은 `chapter.parallels`다. 호환성 충돌이 없다.

### 3. Parser 전략

- `parser.py`가 줄 단위 상태 기계로 절을 나눌 때, `<parallel ... />`만 있는 줄을 **블록 마커**로 알아본다. 바로 뒤 첫 절 마커 `[N]`의 절 번호와 `range` 시작이 같은지 검증한 뒤 장 단위 메타데이터에 저장한다.
- `<parallel>` 자체는 어떤 절 안에도 들어가지 않는다(절 밖의 줄에만 나온다).
- 절 안에서 `<parallel>`이 발견되면 ValueError를 낸다(구문 위반).
- `split_bible.py`가 장 JSON을 쓸 때 `parallels` 필드를 그대로 옮긴다.

### 4. 데이터 검증

`common-bible-data/tests/test_parallels.py`(신규):
- `<parallel>`의 src 각 항목과 range가 ADR-022 §2의 src 형식 문법을 따른다.
- src의 약어가 books.json에 실제로 있다.
- src와 range의 모든 장과 절이 실제 책 범위 안에 있다.
- range 시작 절이 마커 바로 뒤 첫 절과 같다(교차 확인).
- 같은 장 안 parallels 사이에 겹침이 없다. 이 항목은 range 중첩을 허용하면서(2026-05-31) 뺐다.
- 인라인 사본 전통 표기를 검증한다(ADR-022 §2와 같다).

`tests/test_citations.py`의 `<cite>` 검증은 그대로다. `<cite>`와 `<parallel>`은 따로 논다.

### 5. 앱 유닛 테스트

`tests/unit/parallels.test.js`(신규, 가칭). 처음 계획은 배너를 기준으로 했다.
- 장의 `parallels` 메타를 읽어 배너 DOM 만들기
- 배너 위치(range 시작 절 바로 앞)가 정확한지
- 배너 라벨(출처 하나, 여럿, 출처마다의 사본 전통)의 형식
- 누르면 openCiteSheet를 부르는지(mock으로 위임 확인)
- 토글이 꺼지면 배너를 그리지 않는지

화면이 ※ 앵커로 바뀌어, 지금 테스트는 range 해석, 툴팁 본문 만들기, 앵커 만들기, 시작 절에서 시작하는 병행 찾기, 앵커와 링크를 눌렀을 때의 동작을 확인한다.

## 검토한 대안

| 대안 | 채택하지 않은 이유 |
|---|---|
| `<aside class="parallel">` (표준 HTML element로 돌아가기) | source 마크다운은 브라우저 렌더 경로에 없으므로 표준 HTML을 지키는 것은 설계 제약이 아니다(결정 1). DSL의 일관성을 먼저 보고 `<parallel>`을 바로 쓴다. |
| 기존 `<cite>`에 `range` 속성 더하기(다시 쓰기) | cite의 뜻(인용)과 병행 이야기의 뜻이 다르다. 한 element가 둘을 맡으면 뜻이 흐려진다. JSON 스키마도 절 segment 단위와 장 단위로 층이 달라 자연스럽게 나눌 수 있다. |
| 마크다운 제목 규칙(`#### 병행: 2사무 5:1-10`) | source 본문에 제목이 섞여 읽는 흐름이 깨진다. 운문과 산문 안에 두기도 어색하다. 파서가 패턴을 알아보기도 불안하다(`####`가 뜻이 있는 접두사인지 일반 제목인지 헷갈린다). |
| HTML 주석(`<!-- parallel: ... -->`) | 주석이라 IDE나 뷰어에서 보이지 않는다. 작성자가 뜻 있는 데이터인 줄 모르고 지울 위험이 있다. 조용히 망가진다. |
| 절을 감싸기(`<parallel>[1] 본문 [2] 본문 ... </parallel>`) | `<cite>`의 절 경계 규칙(ADR-022 §3)과 부딪친다. 파서는 줄 단위인데 여러 줄을 감싸면 상태 기계의 부담이 크다. 스스로 닫히는 단일 토큰이 더 깔끔하다. |

### 단락 머리 배너 (2026-05-31, 같은 날까지)

- 처음 디자인은 병행 단락 앞에 `<aside class="parallel-banner">` 머리 배너를 두는 것이었다.
- 채택 안 함 2026-05-31(dev 검토) · 이유: (a) 한 장에 병행이 여럿이면 어느 절들이 그 병행 단락인지 잘 구분되지 않았고, (b) 배너가 본문 사이에 끼어들어 읽는 흐름을 끊었다. 그래서 **footnote anchor 방식**으로 바꿨다(§2 「화면」).

### 같은 장 안 range 겹침 금지 (2026-05-31, 같은 날까지)

- 처음 검증 규칙은 같은 장 안의 parallels가 겹치지 않아야 한다고 했다.
- 채택 안 함 2026-05-31 · 이유: 사무엘하 5장처럼 큰 단락과 그 안의 좁은 단락이 서로 다른 출처와 병행하는 경우를 발견했다. 의도된 좁은 range를 데이터에서 막지 않도록 규칙을 뺐다(§2 「검증 규칙」).

## 결과

- ADR-022의 `<cite>` 모델이 다루지 못하던 단락 단위 병행 이야기를 표현할 수 있다.
- 1sam, 1kgs, 2kgs, 1chr, 2chr의 수십 건에 이르는 책 사이 병행을 마커 하나로 적는다.
- DSL 위치를 문서에 적었으므로, 앞으로 element를 더할 때 「표준 HTML인가」 논쟁이 다시 생기지 않는다.
- `<cite>`와 `<parallel>`의 뜻을 나눠, 마크업의 의도가 데이터와 화면 양쪽에 일관되게 이어진다.
- 콘텐츠 작업(2cor.md, mark.md, 역사서 등)은 이 ADR의 머지와 파이프라인 구현을 마친 뒤 따로 진행한다.
