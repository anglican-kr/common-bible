# ADR-061: 앱과 데이터를 따로 배포하고, 데이터 형식 번호로 둘을 맞춘다

- 상태: 승인됨 — 구현 중. 앱의 준비(§6)는 이 저장소, 데이터 폴더와 배포 스크립트(§1, §4, §5)는 서버 저장소, 형식 번호와 사이트맵과 CI(§2, §4, §5, §6)는 데이터 저장소가 맡는다. 전환(§8)을 마치면 구현 완료로 바꾼다
- 관련: ADR-021(콘텐츠 해시 매니페스트, 데이터 동기화), ADR-051(dev와 main, 운영에 내는 순서), ADR-052(빌드 식별자. §5 「다음 단계」를 이 ADR이 대체한다), ADR-020(저장소 분할)

## 요약

1. **서버의 데이터 폴더**(§1): 데이터를 앱 빌드와 따로 `/var/www/data-<데이터 커밋>`에 풀고, 링크 `data-dev`와 `data-prod`가 두 사이트의 데이터를 정한다. nginx가 `/data/`를 그 링크에서 내주므로 앱이 부르는 주소는 그대로다.
2. **데이터 형식 번호**(§2): 데이터는 `data-version.json`에 형식 번호를, 앱은 `version.json`에 읽을 수 있는 번호의 목록을 적는다. 내용만 고치거나 파일과 칸을 더하면 번호는 그대로다.
3. **형식을 바꾸는 순서**(§3): 칸을 빼거나 이름이나 뜻을 바꾸면 번호를 올리고, 두 번호를 다 읽는 앱을 먼저 낸 뒤 데이터를 낸다.
4. **배포의 확인**(§4): 배포 스크립트는 그 사이트의 앱이 읽지 못하는 데이터와, 그 사이트의 데이터를 읽지 못하는 앱을 올리지 않는다. 데이터를 올리기 전에 그 사이트의 앱 커밋으로 앱의 실데이터 유닛 테스트를 돌린다.
5. **데이터를 운영에 내는 순서**(§5): 데이터 저장소 main에 머지하면 CI가 dev.anglican.kr의 데이터만 바꾼다. 실제 기기에서 확인한 뒤 사람이 `deploy-data.sh promote`로 운영의 데이터만 바꾼다. 앱 버전, 릴리스 PR, main 앞당기기를 거치지 않는다.
6. **앱 쪽**(§6): `books.json`과 `search-meta.json`은 캐시의 사본을 먼저 내고 뒤에서 새로 받아, 데이터만 낸 배포 뒤에도 다음 실행부터 바뀐다. dev의 버전 줄은 데이터 커밋을 `data-version.json`에서 읽는다. 사이트맵은 데이터 배포가 만든다.
7. **앱 저장소의 데이터 서브모듈**(§7): 남긴다. 운영에 갈 데이터가 아니라 앱을 개발하고 시험하는 데이터를 가리킨다. 포인터를 올리는 자동 PR(`sync-data.yml`)도 그대로 둔다.
8. **전환**(§8): 앱의 준비를 운영에 낸 뒤, 지금 운영과 내용이 같은 데이터를 데이터 폴더에 올리고 nginx를 바꾼다. 사용자에게 달라지는 것은 없다.

## 배경

ADR-052 §5가 다음 단계로 적어 둔 일이다. 사용자 기기의 데이터는 이미 앱과 따로 갱신된다(ADR-021). 앱을 열 때 매니페스트의 지문을 견줘 바뀐 파일만 지우고, 처음 쓸 때 다시 받는다. 묶여 있는 것은 배포다.

1. 앱 커밋이 서브모듈 포인터로 데이터 커밋을 정하고, 서버의 `build-deploy.sh`가 앱과 데이터를 zip 하나, 빌드 폴더 하나로 만든다. `promote`가 둘을 함께 운영에 낸다.
2. 그래서 본문의 오탈자 하나도 앱 릴리스와 같은 순서(ADR-051 §3)를 밟는다. dev에 아직 운영에 낼 수 없는 앱 변경이 있으면 데이터 수정도 나가지 못한다.
3. `books.json`과 `search-meta.json`은 셸 캐시에 미리 받아 두는 파일이라, 기기에서는 서비스 워커가 새로 설치될 때만 바뀐다. 데이터만 따로 내면 이 둘이 낡은 채 남는다.
4. 앱과 데이터는 함께 바뀌는 일이 많다. 2026-08-01부터 11-28까지 앱 저장소의 데이터 포인터 변경 63번 가운데 15번은 앱 PR이 앱 코드와 함께 올린 것이었다(주로 교회력과 전례독서). 따로 내려면 둘이 맞는지 가리는 약속이 있어야 한다.

## 결정

### 1. 서버의 데이터 폴더

| 무엇 | 어디 |
| --- | --- |
| 데이터 빌드 | `/var/www/data-<데이터 커밋 7자>`. 안에 `data/`(앱이 부르는 경로 그대로)와 `sitemap.xml`이 있다 |
| 사이트가 쓰는 데이터 | 링크 `/var/www/data-dev`(dev.anglican.kr), `/var/www/data-prod`(bible.anglican.kr) |
| 되돌릴 곳 | 링크 `/var/www/data-dev-previous`, `/var/www/data-prod-previous` |
| 오디오 | 지금처럼 `/var/www/audio` 하나를 두 사이트가 함께 쓴다 |

- nginx는 사이트마다 데이터 링크를 변수(`$data_root`)로 정하고, `/data/` 아래의 JSON과 `/sitemap.xml`을 그 링크에서 내준다. `/data/audio/`는 `/var/www/audio`에서 내준다. 앱이 부르는 주소(`/data/...`)는 바뀌지 않는다.
- 앱 빌드 폴더에는 데이터를 넣지 않는다. 까닭: promote는 운영이 dev와 같은 빌드 폴더를 가리키게 하므로, 앱 빌드 안에 둔 데이터나 링크는 두 사이트가 나눠 쓰게 된다.
- 데이터 빌드도 앱 빌드처럼 링크 교체 한 번으로 바뀌고, 되돌리기도 링크 교체다. 링크가 가리키는 넷과 최근 셋을 남기고 옛 데이터 빌드를 지운다.
- 구현의 세부는 서버 저장소의 `scripts/deploy-data.sh` 머리 주석과 nginx 설정 예시에 있다.

### 2. 데이터 형식 번호

- 데이터 저장소의 `data-version.json`에 형식 번호를 적는다(`{"format": 1}`). 배포할 때 데이터 커밋을 더한 사본을 데이터 빌드에 넣는다(`{"format": 1, "commit": "82c056b"}`). 커밋은 자기 해시를 담을 수 없으므로 저장소의 파일에는 적지 않는다(ADR-052 §1과 같은 까닭).
- 앱의 `version.json`에 읽을 수 있는 형식 번호의 목록을 적는다(`{"version": "2.3.0", "data_formats": [1]}`). 목록이 없는 옛 앱은 1만 읽는 것으로 본다.
- 번호는 1에서 시작한다. 이 ADR을 쓸 때의 데이터 형식이 1이다.

| 바뀐 것 | 번호 | 예 |
| --- | --- | --- |
| 내용만 | 그대로 | 본문의 오탈자, 독서표의 장절, 본기도의 글 |
| 파일이나 칸을 더함 | 그대로 | 새 축일 칸, 새 책(`books.json`의 항목), 새 색인 파일 |
| 칸을 빼거나 이름이나 뜻을 바꿈, 파일을 빼거나 옮김 | 올린다 | 독서 세트의 구조를 바꿈 |

- 칸을 더해도 번호를 올리지 않는 까닭: 앱은 모르는 칸을 읽지 않으므로 옛 앱이 그대로 돈다. 새 칸을 쓰는 앱은 그 데이터가 그 사이트에 나간 뒤에 내거나, 칸이 없어도 동작하게 쓴다.

### 3. 형식을 바꾸는 순서

번호를 올리는 변경은 두 단계로 낸다.

1. 옛 번호와 새 번호를 다 읽는 앱을 만들고 `data_formats`에 두 번호를 적는다(`[1, 2]`). 이 앱을 dev와 운영에 낸다.
2. 새 번호의 데이터를 dev와 운영에 낸다.
3. 옛 번호를 읽는 코드는 다음 앱 릴리스에서 지우고 목록에서도 뺀다(`[2]`).

- 1과 2 사이에는 시간을 둔다. 사용자 기기의 앱은 서비스 워커가 새로 설치되고 사용자가 업데이트를 누를 때 바뀌므로, 1을 운영에 낸 뒤에도 한동안 옛 앱이 남는다. 그 앱은 2의 데이터를 읽지 못한다.
- 번호를 올리는 데이터 PR은 1을 운영에 낸 뒤에 머지한다. 먼저 머지하면 §4의 확인이 배포를 막아, 그동안 내용만 고친 데이터도 낼 수 없다.

### 4. 배포의 확인

| 명령 | 확인 |
| --- | --- |
| `deploy-data.sh dev`와 CI의 dev 배포 | 데이터 커밋이 데이터 저장소의 `origin/main`에 있다. dev.anglican.kr의 앱(`/version.json`의 `data_formats`)이 그 형식을 읽는다 |
| `deploy-data.sh promote` | dev가 가리키는 데이터 빌드가 그 커밋을 로컬에서 빌드한 것과 파일마다 같다. 운영의 앱이 그 형식을 읽는다. 앱 `origin/main`의 실데이터 유닛 테스트가 그 데이터로 통과한다 |
| `deploy.sh dev`, `prod`, `promote`(앱) | 그 사이트가 데이터 빌드를 내고 있고(`/data/data-version.json`에 `commit`이 있다), 그 형식(`format`)을 이 앱의 `data_formats`가 읽는다. 전환 전 사이트에는 데이터를 뺀 앱을 올리지 않는다 |
| `deploy-data.sh rollback` | 확인하지 않는다. 되돌리는 일은 막지 않는다 |

- 실데이터 유닛 테스트는 앱 저장소의 `tests/unit/*.data.test.js`와 `tests/unit/sw.test.js`다. 엔진, 전례독서, 캘린더, 인용, 검색이 실제 데이터로 도는지와, 매니페스트가 가리키는 경로를 서비스 워커가 데이터 캐시로 보내는지 본다. 형식 번호는 약속을 어긴 것(칸 이름을 바꾸고 번호를 올리지 않은 경우)을 잡지 못하므로 테스트로 한 번 더 본다.
- 데이터 저장소의 CI는 PR과 main push에서 앱 `origin/dev`와 `origin/main`으로 같은 테스트와 번호 확인을 돌린다. dev 배포는 `origin/dev`로 통과해야 한다. `origin/main`의 결과는 운영에 낼 수 있는지 미리 알려 준다.
- 데이터 빌드도 이름이 출처의 증명이 아니다. CI 키로 같은 형식의 폴더를 만들 수 있으므로 promote는 내용으로 확인한다(ADR-052 §4와 같은 까닭).

### 5. 데이터를 운영에 내는 순서

1. 데이터 저장소에서 PR을 main에 머지한다. `build.yml`이 산출물을 빌드하고 검증해 커밋한다(지금과 같다).
2. 같은 실행이 §4의 호환 검사를 돌리고, 통과하면 그 커밋을 dev.anglican.kr의 데이터로 올린다(`deploy-data.sh dev-ci`). CI의 서버 키는 데이터의 dev 링크 말고는 바꾸지 못한다.
3. 실제 기기에서 dev.anglican.kr을 확인한다.
4. 사람이 `deploy-data.sh promote`로 운영의 데이터 링크를 dev의 데이터 빌드로 바꾼다.

- 앱 버전을 올리지 않고 업데이트 알림도 뜨지 않는다. 기기는 다음에 앱을 열 때 매니페스트를 견줘 바뀐 파일을 다시 받는다(ADR-021).
- 운영에 사람이 내는 까닭: 데이터도 본문과 전례 자료를 바꾸므로, 앱처럼 dev에서 실제 기기로 본 뒤에 낸다.
- dev에 아직 운영에 내지 않은 앱 변경이 있어도 데이터는 따로 나간다. 데이터 수정에는 ADR-051 §5의 「되돌리는 PR」이 필요 없다.

### 6. 앱 쪽

- **`books.json`과 `search-meta.json`**: 운영에서도 셸 캐시의 사본을 먼저 내고, 뒤에서 새로 받아 그 사본을 바꾼다. 데이터만 낸 배포 뒤 다음 실행부터 새 목록을 쓴다. 설치할 때 미리 받는 것은 그대로라 오프라인에서 여는 첫 실행도 그대로다. 네트워크를 먼저 기다리지 않는 까닭: 앱이 열릴 때 이 두 파일을 기다리므로, 느린 연결에서 앱이 늦게 열린다.
- **버전 줄**: dev.anglican.kr의 설정 맨 아래에 보이는 데이터 커밋(ADR-052 §3)을 `/data/data-version.json`의 `commit`에서 읽는다. 없으면 `version.json`의 `data_commit`을 쓴다(전환 전 빌드).
- **사이트맵**: 데이터에서 만드는 파일이라 데이터 배포가 만들어 데이터 빌드에 넣는다(`sitemap.xml`). 만드는 스크립트는 데이터 저장소로 옮기고, 앱 저장소의 `sitemap.xml`과 스크립트는 전환 뒤에 지운다. 앱 빌드에 두면 데이터만 낸 배포에서 각 장의 수정일이 낡는다.
- 구현은 `docs/topics/cache-release.md` "앱과 데이터를 따로 배포하기"에 있다.

### 7. 앱 저장소의 데이터 서브모듈

- `data/` 서브모듈과 자동 PR(`sync-data.yml`)은 그대로 둔다. 로컬 개발 서버, e2e, 실데이터 유닛 테스트가 이 데이터를 쓰고, 자동 PR이 문서의 실측치를 데이터와 대조한다.
- 뜻만 바뀐다. 포인터는 「운영에 갈 데이터」가 아니라 「앱을 개발하고 시험하는 데이터」다. 운영의 데이터는 서버의 `data-prod` 링크가 정한다.
- 앱 빌드는 데이터를 담지 않으므로, 앱 빌드의 `version.json` 사본에 데이터 커밋(`data_commit`)을 적지 않고 서브모듈을 받지 않은 폴더에서도 빌드할 수 있다. 앱 커밋(ADR-052 §2)은 지금 규칙 그대로다.

### 8. 전환

1. 앱: §6의 `books.json`과 `search-meta.json` 처리, 버전 줄, `data_formats`를 넣은 릴리스를 운영에 낸다.
2. 데이터: `data-version.json`, 사이트맵 스크립트, CI의 호환 검사와 dev 배포를 머지한다.
3. 서버: 데이터 빌드를 올리고 dev의 nginx를 바꿔 dev.anglican.kr에서 확인한 뒤, 운영의 데이터 링크를 만들고 운영의 nginx를 바꾼다. nginx 설정은 두 사이트가 함께 쓰므로, 운영은 데이터 링크를 만들기 전까지 지금의 앱 빌드 폴더를 데이터 자리로 쓴다. 그다음 데이터를 뺀 배포 목록으로 앱을 배포한다.
4. 앱: 저장소의 `sitemap.xml`과 사이트맵 스크립트를 지우고, 규칙 문서(CLAUDE.md 「데이터 수정과 릴리스」, `docs/workflow.md` 「릴리스」)를 새 순서로 고친다.

- 3에서 처음 올리는 데이터가 지금 운영과 내용이 같으면, nginx를 바꾸기 전후에 사용자가 받는 파일이 같다.
- 3이 끝나기 전에는 ADR-051 §3의 순서로 데이터를 낸다.
- 서버에서 할 일의 순서는 서버 저장소 README 「앱과 데이터를 따로 배포하기」에 있다.

## 검토한 대안

1. **앱 빌드 폴더 안에 데이터 링크를 둔다**(2026-11-28 버림). promote는 운영이 dev와 같은 폴더를 가리키게 하므로 링크를 사이트마다 다르게 할 수 없다.
2. **데이터 주소에 형식 번호를 넣어 두 벌을 낸다**(`/data/v2/`, 2026-11-28 버림). 형식을 바꾸는 동안 옛 앱과 새 앱이 함께 돌 수 있지만, 서버와 오프라인 저장(17.5MB)에 데이터가 두 벌이고 매니페스트와 캐시 경로도 두 벌이다. 형식을 바꾸는 일은 드물다. 재검토 조건: 형식을 바꾸는 일이 잦아지거나, §3의 기다림 동안 옛 앱이 깨지는 일이 실제로 생기면.
3. **앱이 실행 중에 데이터 형식 번호를 견줘, 읽지 못하면 업데이트를 권한다**(2026-11-28 미룸). §3의 기다림을 짧게 할 수 있지만, 형식을 바꾸는 일이 드물어 이번에 넣지 않는다. 재검토 조건: 위 2와 같다.
4. **호환 검사가 통과하면 CI가 운영까지 낸다**(2026-11-28 버림). 빠르지만 실제 기기로 확인하는 단계가 없다. 재검토 조건: 데이터만 고친 배포가 잦아져 사람이 내는 일이 부담이 되면.
5. **앱 저장소의 자동 포인터 PR을 멈추고, 앱 PR이 필요할 때만 포인터를 올린다**(2026-11-28 버림). dev에 데이터 커밋이 쌓이지 않지만, 앱 개발과 e2e가 옛 데이터로 시험되고 문서의 실측치 대조가 멈춘다.
6. **`books.json`과 `search-meta.json`을 네트워크에서 먼저 받는다**(2026-11-28 버림). 데이터만 낸 배포가 바로 보이지만, 앱이 열릴 때 기다리는 파일이라 느린 연결에서 앱이 늦게 열린다. 매니페스트 2종은 앱이 열린 뒤에 읽어 네트워크에서 먼저 받아도 된다.
7. **두 파일을 매니페스트에 넣고 데이터 캐시로 옮긴다**(2026-11-28 버림). 다른 데이터와 같은 방식이지만, 매니페스트를 견주는 일이 앱이 이 파일을 읽은 뒤라 한 번은 옛것을 쓰는 것이 같고, 설치할 때 미리 받는 처리를 데이터 캐시에 새로 만들어야 한다.
8. **사이트맵을 앱 빌드에 남긴다**(2026-11-28 버림). 고칠 것은 적지만 데이터만 낸 배포에서 각 장의 수정일이 낡는다.
