# ADR-032: 컴포넌트·뷰 층 모듈화 — 동작 스캐폴딩의 단일화

- 일시: 2026-06-06
- 상태: 승인됨 — 구현 완료(2026-06-06)
- 관련 ADR: ADR-018(app.js 도메인 모듈 분할), ADR-019(ESM 일괄 채택), ADR-013(유닛 테스트 전략), ADR-028(디자인 시스템. `DESIGN.md` 토큰 단계), ADR-010(북마크 UI), ADR-022(인용과 주석 바텀 시트), ADR-029/030(탭 바와 오버레이 방식)

## 맥락

화면 디자인 층은 이미 자리를 잡았다. ADR-028이 색, 간격, 타이포, 반경, elevation, 모션을 `DESIGN.md`와 `:root`의 토큰 단계로 하나로 모았고, 토큰을 전부 쓰는 일까지 마쳤다. 그러나 그 토큰을 입는 **클라이언트 JS의 뷰 구현은 제각각**이다. 문제의 핵심은 마크업(겉모습)이 아니라 **동작(behavior)을 받치는 코드의 복제**다. 같은 수명 관리 코드를 모듈마다 손으로 다시 짜고 있어, 한 번 고친 버그가 다른 사본에서 되살아나고 파일이 커진다.

### 증상 1 — 오버레이의 수명 관리가 가장 많이 겹친다

`trapFocus`, `setInert`, Escape 리스너, 열기/닫기, 포커스 복원을 한 묶음으로, 오버레이가 뜨는 곳마다 따로 다시 구현하고 있다. 직접 세어 보니(`grep`) `trapFocus`를 호출하는 곳만 **12곳**이다(줄 번호는 2026-06-06 기준).

| 파일 | 오버레이 | trapFocus 위치 |
|---|---|---|
| `bookmark.js`(2,957줄) | 드라이브 연결 해제 모달 | `:823` |
| | 북마크 드로어(바텀 시트) | `:1034` |
| | 저장 모달 | `:2112` |
| | 새 폴더 모달 | `:2130` |
| | 병합 모달 | `:2234` |
| | 확인 모달 | `:2296` |
| | 장 삭제 선택 모달 | `:2374` |
| | 가져오기 모달 | `:2500` |
| `install.js` | 설치 안내 모달 | `:426` |
| `citations.js`(1,140줄) | 인용 본문 바텀 시트 | `:966` |
| `settings-ui.js` | 설정 팝오버 | `:800` |
| `views-routing.js`(2,324줄) | 읽기 헤더 팝오버 | `:482` |

곧 **모달 7 + 드로어 1 + 시트 1 + 팝오버 2 + 설치 모달 1**이다. 저마다 포커스 트랩을 정리하는 핸들(`_bmSaveModalTrap`, `_driveDisconnectTrap`, `installModalTrap`, `_sheetTrapCleanup`, `cleanupTrap` …)을 모듈 변수로 들고, 열 때 직전 포커스를 저장했다가 닫을 때 되돌리는 배관을 되풀이한다. 게다가 **일관성마저 깨져 있다.** 배경 비활성화(`setInert`)는 `bookmark.js`와 `install.js` 두 곳만 감싸서 쓰고(`setBookmarkBackgroundInert`, `setBackgroundInert`), 팝오버와 시트는 `setInert`를 거치지 않는다. 이것이 `bookmark.js`와 `views-routing.js`가 커진 주된 원인이고, 접근성(WCAG 2.1 AA) 회귀가 한 사본에만 슬그머니 들어올 위험을 키운다.

### 증상 2 — 바텀 시트의 드래그 리사이즈 배관이 겹친다

`bookmark.js` 드로어와 `citations.js` 시트가 저마다 pointerdown/move/up, 높이 제한, 스냅 애니메이션을 따로 구현한다. 함께 쓰는 것은 순수 판정 함수 `dragReleaseAction(h, vh)`(close/snap-min/stay, `helpers.js:137`) **하나뿐**이다. 이 함수 자체가, 두 사본이 기준값을 따로 두다가 close 분기에 영영 닿지 못했던 Bugbot 회귀에서 생겼다(주석 참조). 곧 포인터 배관은 여전히 두 벌이라, 같은 종류의 버그가 다시 생길 자리가 남아 있다.

### 증상 3 — 빈 상태 마크업이 겹친다

`bm-empty`(`bookmark.js:1626`, 아이콘과 제목과 안내)와 `search-empty-state`(`search.js:341`)가 사실상 같은 구조(아이콘, 제목, 부제)를 다른 클래스와 다른 코드로 짠다. CSS도 `.bm-empty*`와 `.search-empty-state`로 갈라져 있다(`style.css:1667`, `:4718`).

### 이미 있는 것 — 기본 도구는 있고, 컴포넌트 추상화만 없다

`js/app/helpers.js`(`window.appHelpers`)에 낮은 수준의 기본 도구가 모여 있다. `el`(태그, 속성, 자식으로 DOM을 만든다), `clearNode`, `setInert`, `trapFocus`, `dragReleaseAction`이다. 빠진 것은 그 위에 얹는 **컴포넌트 단위 추상화**뿐이다. 수명 관리를 한 곳에 가두는 컨트롤러와, 되풀이되는 화면 조각을 순수 함수로 만드는 빌더다. 프레임워크가 필요한 것이 아니라, `el()` 바로 위의 얇은 층이 비어 있다.

## 결정

`el()` 위에 **얇은 바닐라 컴포넌트 층**을 들인다. 프레임워크를 들이는 것이 아니라, 기존 ADR-018(IIFE와 `window` 네임스페이스) / ADR-019(ESM) 방식을 그대로 따르는 **의존성 없는** 모듈이다. 화면 모양은 계속 `DESIGN.md` 토큰을 입고, 이 층은 **동작과 구조를 다시 쓰는 일**만 맡는다.

### 1. overlay/dialog 컨트롤러 팩토리 — 수명 관리를 한 곳에 가둔다 (가장 큰 이득)

열기, 닫기, Escape, `inert`, 포커스 트랩, 포커스 복원을 한 묶음으로 팩토리 하나에 가둔다. 대략의 약속은 다음과 같다(세부는 구현하며 정한다).

```
const ctl = createOverlay(el, {
  onOpen?, onClose?,          // 생명주기 훅
  inertSelectors?,           // 배경 비활성화 대상 (setInert 위임)
  initialFocus?, returnFocus?,// 열 때 포커스 이동 / 닫을 때 복원(기본 = 직전 활성요소)
  closeOnEsc = true,
  closeOnBackdrop?,
});
ctl.open(); ctl.close(); ctl.isOpen;
```

안에서 `trapFocus`·`setInert`를 호출하고 정리도 스스로 하므로, 모듈마다 흩어진 `_*Trap` 핸들, 직전 포커스 저장 변수, Escape 리스너 등록과 해제가 사라진다. 모달 7, 드로어, 시트, 팝오버 2, 설치 모달이 **모두 이 컨트롤러 하나를 함께 쓴다**. 덤으로 `setInert`(배경 비활성화)가 **모든** 오버레이에 똑같이 적용되어 접근성이 고르게 된다.

### 2. sheet 팩토리 — overlay 컨트롤러와 dragReleaseAction을 묶는다

(1) 위에 드래그 리사이즈 바텀 시트의 포인터 배관(pointerdown/move/up, 높이 제한, 스냅 애니메이션)을 한 번만 구현하고, `dragReleaseAction`의 close/snap-min/stay 판정을 붙인다. `bookmark.js` 드로어와 `citations.js` 시트가 이 팩토리를 함께 쓴다. 순수 판정 함수만이 아니라 **배관까지** 하나로 모아, 증상 2의 버그가 생길 자리가 없어진다.

### 3. 화면 조각 빌더 — 순수 함수로 DOM을 돌려준다(유닛 테스트가 쉽다)

부수 효과 없이 인자를 받아 DOM 노드를 돌려주는 작은 빌더들이다. DOM만 다루므로 ADR-013 유닛으로 바로 검증할 수 있다(JSDOM/vm 하네스).

- `button({ variant, label, onClick, … })`: `DESIGN.md` 컨트롤 토큰을 입은 버튼 변형.
- `iconButton({ icon, label, … })`: 44px 터치 영역의 아이콘 버튼(헤더와 바에서 함께 쓴다).
- `emptyState({ icon, title, subtitle })`: 증상 3의 `bm-empty`/`search-empty-state`를 합친다.
- 목록 행 빌더: 북마크, 검색 결과 등 되풀이되는 행의 공통 골격.

빌더는 **구조와 토큰 클래스만** 맡고, 데이터 연결과 이벤트 배선은 호출하는 쪽에 둔다(지나친 추상화를 피한다).

### 점진 교체 — 한 곳씩 바꾼다

새 층을 만든 뒤 **오버레이 하나씩** 옮긴다. 한꺼번에 갈아엎지 않고 옆에 새 컨트롤러를 세워 하나씩 바꾸며, 단계마다 앱이 깨지지 않게 한다. 단계마다 e2e(ADR-013의 나눔: DOM이 많은 일과 라우팅은 e2e가 맡는다)를 통과시키고, 옮긴 빌더에는 유닛을 더한다. 오버레이 컨트롤러를 먼저 세우고(가장 큰 중복 제거), 모달, 드로어, 시트, 팝오버 순서로 받아들인 뒤 빌더로 화면 조각을 정리한다. **코드 뼈대를 만들어 주는 도구(스캐폴드 CLI 등)는 컴포넌트의 약속이 실제로 써 보며 안정된 뒤에만** 검토한다(약속이 흔들리는 동안 생성기는 빚만 늘린다).

## 검토한 대안

- **(a) 프레임워크 도입 (Lit / Preact / Web Components 등)**: 컴포넌트 모델, 반응성, 수명 관리를 그냥 얻는다. 그러나 ADR-001(빌드 단계 0 Vanilla SPA)과 ADR-019(빌드 0 ESM)의 핵심 전제를 깬다. 번들러, 런타임 의존, 익히는 부담, SW 미리 넣기 목록 변경이 따라온다. 우리가 겪는 문제는 「반응성이 없다」가 아니라 「수명 관리 코드가 복제된다」여서 도구가 지나치다. 의존성 없음 원칙(이 프로젝트의 배포와 캐시 단순성의 뿌리)을 지키는 편이 비용에 비해 이득이 크다. **채택 안 함.**
- **(b) 지금대로 두기(아무것도 하지 않음)**: `bookmark.js`(2,957)와 `views-routing.js`(2,324)가 계속 커지고, 접근성과 드래그 버그가 사본마다 따로 회귀한다(증상 2의 Bugbot 사례가 이미 있었다). 노트, 캘린더 같은 뒤의 기능(ADR-026 계열)이 같은 오버레이 방식을 또 한 벌 복제하게 된다. **채택 안 함.**
- **(c) 마크업만 도우미로 만들기**: `el()` 위에 화면 조각 빌더(증상 3)만 더하고 수명 관리는 건드리지 않는 안이다. 가장 싸지만 **가장 큰 비용인 오버레이 수명 관리(증상 1, 2)를 그대로 둔다**. 빌더는 결정 (3)에 이미 넣었지만, 그것만으로는 모자란다는 것이 조사 결론이다. 일부만 채택했다(전체로는 채택 안 함).

## 영향

- **코드량과 가독성**: `bookmark.js`·`views-routing.js`·`citations.js`·`install.js`의 수명 관리 상용구가 컨트롤러로 옮겨 가 줄고, 도메인 로직만 남아 읽기 쉬워진다.
- **접근성**: `inert`, 포커스 트랩, 포커스 복원이 모든 오버레이에 똑같이 적용되어, WCAG 2.1 AA 회귀가 생길 자리가 한 곳으로 모인다.
- **테스트(ADR-013)**: 빌더는 순수 함수라 유닛 케이스가 늘고, 오버레이와 시트의 연결은 계속 e2e가 맡는다(나눔 유지).
- **디자인 일관성(ADR-028)**: 빌더가 `DESIGN.md` 토큰 클래스를 한곳에서 입혀, 토큰에서 벗어날 자리가 줄어든다(컴포넌트가 토큰을 쓰는 하나뿐인 통로가 된다).
- **뒤의 기능**: 노트, 캘린더(ADR-026 계열) 등이 새 오버레이를 공유 컨트롤러로 바로 구현한다.
- **위험**: 점진 교체 중에는 새 방식과 옛 방식이 함께 있는 구간이 생긴다. 단계마다 e2e로 회귀를 막고, 한 번에 오버레이 하나만 옮겨 위험을 좁힌다. 빌더의 지나친 추상화는 「구조와 토큰만, 배선은 호출하는 쪽」 원칙으로 막는다.

## 구현 (2026-06-06, 단계별 커밋)

점진 교체로 마쳤다. 처음 안과 달라진 점도 함께 적는다.

1. **오버레이 컨트롤러** `js/app/overlay.js`(`window.appOverlay.createOverlay`): 결정 (1) 그대로다. `closeOnEsc` 기본값은 **꺼 두었다**. 막 옮긴 오버레이가, 모두 옮길 때까지 기존의 쌓인 Escape 라우터(bookmark.js, app.js)에 계속 맡기기 위해서다. 지금도 기본은 꺼짐이고, 북마크, 설치, 검색의 일부 오버레이가 켠다. **모달 9종**(북마크 새 폴더, 확인, 저장, 병합, 가져오기, 장 삭제, 드라이브 해제, 설치)과 **드로어**, **인용 시트**, **팝오버 2종**(설정, 장 선택)까지 흩어진 12곳을 모두 받아들였다.
2. **Escape를 한 곳으로**: 팝오버는 app.js의 중앙 조정자가 `window.close{Settings,ChapterPopover}`에 맡기고(직접 hidden으로 바꾸지 않는다), 모달은 모듈마다의 쌓인 라우터가 컨트롤러의 close를 호출한다.
3. **sheet 팩토리**: `attachSheetDrag`/`attachSheetResize`(드래그와 리사이즈 pointer 배관에 `dragReleaseAction`을 묶음). 드로어와 인용 시트가 함께 쓴다(겹치던 약 105줄을 지웠다).
4. **비동기(애니메이션) 닫기 — 처음 안보다 넓혔다**. 처음에는 드로어의 수명 관리를 「비동기로 숨기므로 따로 둔다」고 하려 했다. 사용자가 부드러운 전환을 선호해 방향을 바꿨다. `createOverlay`에 `closeTransition(panel, finalizeHide)`와 다시 열기 순서 검사를 더해 **드로어를 완전히 받아들였고**, **인용 시트에도 같은 슬라이드 in/out**을 적용했다. 이제 애니메이션 시트가 한 방식을 함께 쓴다(노트, 캘린더 같은 뒤의 기능도 다시 쓴다).
5. **화면 조각 빌더 — 일부만 채택했다**. `emptyState({icon,title,subtitle,tag,role})`(helpers.js)로 북마크와 검색의 빈 상태를 하나의 `.empty-state` 컴포넌트로 맞췄다(DESIGN.md §6). **button/iconButton은 미뤘다.** gear/home/back/bookmark 버튼이 저마다 글리프, 클래스, 동작이 달라, `el()` 위의 빌더가 실제 중복을 줄이지 못하고 지나친 추상화가 되었다(§3 평가 결과). 목록 행 빌더도 같은 이유로 미뤘다.

검증: 유닛 644 통과(overlay 23과 emptyState 3 등 신규 포함, 그때 수), `tsc` 0 error(두 설정 모두), e2e는 오버레이, 시트, 팝오버, 빈 상태 흐름이 통과했다(신규 `tests/e2e/test_cite_sheet.py` 포함).
