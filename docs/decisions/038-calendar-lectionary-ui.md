# ADR-038: 교회력 캘린더 · 전례독서 뷰 · 검색 이원화 UI

- 일시: 2026-07-04
- 상태: **승인됨 — 구현 중** (렌더 기반 완료 2026-07-27, A3 독서 뷰 완료 2026-10-12, A2 캘린더 탭 1단계(탭, 월간) 2026-10-15, A2 2단계(주간, 목록), 검색 이원화 A4 남음)
- 관련: ADR-037(전례독서 데이터·엔진 — 본 UI의 입력), ADR-036(본기도·전례일 키), ADR-035(북마크 읽기 뷰 — 렌더 패턴 원형), ADR-029/030/031(탭 바·모핑·탭 히스토리), ADR-032(오버레이·뷰 레이어), ADR-033(검색 옵션), ADR-034(라우팅 분할)

## 배경

ADR-037의 데이터·엔진 위에 만드는 세 UI: ① 교회력 캘린더 탭, ② 전례독서 본문 뷰, ③ 검색 이원화(성서 본문 / 전례독서). 모두 기존 확장 지점(라우팅 `parsePath`/`route`, 탭바 `syncTabBarActive`, `appendVerses` 렌더, 검색 워커 메시지)을 따른다.

## 결정

### 1. 캘린더 탭 — 홈 옆 두 번째 위치

`index.html` `#tab-bar`에 `<a data-tab="calendar" href="/calendar">`를 **홈 바로 다음(두 번째)**에 추가. 노트 탭(비활성 숨김)은 보존 — 나중에 부활 예정. `tabbar.js syncTabBarActive`의 세그먼트 매핑에 `calendar` 추가(폭·인디케이터는 개수 기반 자동 — 보이는 탭 넷 + 검색이 320px 폭에서 넘쳐 좁은 폭에서는 탭 슬롯이 줄어든다, DESIGN.md §7). 아이콘은 기존 스트로크 스타일(광학 크기 정규화 규칙 준수) 캘린더 글리프. **탭의 이름(접근 가능한 이름)과 화면 제목은 「캘린더」**(사용자 결정 2026-10-15). 탭 동작은 홈 탭과 같다(ADR-031) — 다른 탭에서 오면 마지막 캘린더 화면(전례독서 `/lectionary/…` 포함)으로 돌아오고, 캘린더 탭에서 다시 누르면 이번 달(`/calendar`)이다. **데스크톱(넓은 화면, 마우스)은 탭 바가 없어 헤더 윗줄(검색창 옆)에 같은 곳으로 가는 캘린더 단추**를 둔다 — 없으면 주소 말고는 들어갈 길이 없다(사용자 승인 2026-10-15). 단추의 동작은 탭과 같다 — 다른 화면에서 누르면 마지막 캘린더 화면, 캘린더 화면에서 누르면 이번 달(사용자 결정 2026-10-15 — PR #348 리뷰가 1단계 구현이 늘 이번 달로 가는 것을 찾았다). 탭, 단추는 수정 키 클릭(⌘, Ctrl — 새 탭)을 가로채지 않는다.

### 2. 캘린더 뷰 — 월간·주간·목록 3뷰 (`js/app/calendar.js` 신규)

- **라우트**: `/calendar`(월간, 이번 달), `/calendar/YYYY-MM`(월간), `/calendar/w/YYYY-MM-DD`(주간), `/calendar/list`(목록 — 오늘부터 8주, 이름 없는 평범한 평일은 건너뛴다). `routing.js parsePath()` 분기 + `route()` 디스패치(ADR-034 관례). 1단계(2026-10-15)는 월간 둘, 주간, 목록은 2단계.
- 상단에 **뷰 전환 세그먼트**(월간|주간|목록). 이전/다음 이동 + "오늘" 버튼.
- 순수 함수 `buildMonthGrid`·`buildWeekStrip`·`buildAgendaList`(ADR-013 유닛 대상) — 엔진 `resolveDate`를 주입받아 셀/행 데이터를 만든다.
- **셀 = 날짜 + 그날의 전례색 점 + 이름 하나**(사용자 승인 2026-10-15). 색은 엔진이 낸 그날의 색 `colors`(사계재 날 축일이면 [자, 백]을 함께 적는다 — ADR-036 §8, 설계서 R-6.4-color-order, R-6.4-ember-color)이고 선택 대체색(장미, 청)은 그리지 않는다(DESIGN.md §2 「전례색」). 이름은 엔진의 `official` — 대표가 이름 없는 격자 평일이면 그날 지키는 이름 있는 후보(사계재, 기념일), 주일과 고유명 평일(성주간 월-수, 재의 수요일 후 목-토 — 엔진이 그 격자 전례일에 단 표지 `properWeekday`로 구별한다; 절기 위치는 성 목, 금, 토 격자와 같아 뷰가 절기 위치로 가리지 않는다, 설계서 §5.5)은 격자 이름이고, 번호 붙은 주일은 「대림1주」, 「연중29주」처럼 줄인다. 나머지 후보(동시 봉헌, 기념만 하는 후보, 옮겨 지킬 수 있음, 옮겨 감)는 주간, 목록 **줄**에 전례독서 목록과 같은 상태 표시로 싣는다(기념만 하는 후보는 이름만, 2026-11-04) — 선택 봉헌은 월간 칸에 보이지 않는다. 전례년 첫날(대림 1주일)에는 새 주일 주기 표지(칸 「나해」, 링크 이름과 줄 「나해 시작」 — 설계서 미결3 닫힘). **독서 성구, 라벨은 싣지 않는다**(설계서 미결41 닫힘) — 달력은 캘린더 묶음(정의 표)만 받는다(설계서 §3.5).
- 셀/행 탭 → `/lectionary/YYYY-MM-DD`. 데스크톱도 동일 전체화면 뷰(ADR-035 `/read` 선례 — 드로어 폴백 없음).

**구현(A2 1단계 — 2026-10-15, 탭, 월간).** `js/app/calendar.js`가 본 ADR §1, §2의 월간 화면을 구현한다 — 순수 모델(`CALENDAR_MODEL` 마커 블록: `buildMonthGrid`, `calendarDay`, 칸 이름, 링크 이름)과 DOM을 나눴고, 모든 컨트롤(이전/다음 달, 「오늘」, 칸)이 링크라 전역 `<a>` 인터셉터가 이동한다(뒤로, 공유, 키보드 그대로 — §3과 같은 계약. 계약은 코드가 그것을 쓰는 쪽에 지키기로 한 동작의 약속이다). 엔진은 바꾸지 않았다(`liturgicalYearOf`는 이미 공개). 정한 것:

- **6주 × 7일, 일요일 시작**: 달마다 줄 수가 같아 이전/다음 달로 넘겨도 표가 뛰지 않는다(설계서 §4.9 의 42칸 — 엔진 연도 캐시로 부활절 계산은 해마다 한 번). `<table>` 7열 `table-layout: fixed` 라 이름이 길어도 칸이 넓어지지 않는다(1.6.0 달력이 폰에서 넘치던 함정 — DESIGN.md §6). 칸 전체가 `/lectionary/<날짜>` 링크이고 오늘 칸은 `aria-current="date"`. 링크 이름은 「오늘, 10월 15일 목요일, 아빌라의 데레사, 백색」처럼 날짜, **칸에 보이는 이름**(주일 「연중24주」, 사계재 날 「추계재」 — 이름 없는 평일 칸은 대표 이름)과 그 상태 표시(「· 기념일」, 「· 7월 25일에서 옮겨 옴」), 전례년 표지, 색 이름을 글자로 싣는다 — 보이는 글자가 접근 가능한 이름 안에 있어야 음성 제어가 그 글자로 누르고(WCAG 2.5.3), 색만으로 전하지 않는다.
- **달 이동 뒤 포커스는 누른 컨트롤로 돌아간다**: 이전, 다음 달, 「오늘」은 표 전체를 다시 그리므로, 누른 자리를 기억했다가 새 머리 줄의 같은 컨트롤에 포커스를 둔다. 키보드, 스크린 리더 사용자가 Enter 만 거듭 눌러 달을 넘긴다(WCAG 2.4.3). 계산 범위 끝에서 그 단추가 없으면 「오늘」로(단추의 `data-focus-fallback`). 자리를 재고 돌려주는 것은 라우터다(ADR-031 §5 — 전례독서, 구분 탭, 검색 페이지와 같다); 이 뷰는 키만 단다.
- **앞뒤 달 칸은 날짜와 색 점만**(이름 없이 흐리게 — 링크 이름에는 남는다). 계산 범위(1583-9999) 밖의 칸은 링크가 없다.
- **전례독서 화면의 머리에는 위 단계 컨트롤이 없다**(사용자 결정 2026-11-03): 캘린더로는 탭 바의 캘린더 탭(데스크톱은 헤더 윗줄의 캘린더 단추)이 간다. 독서 화면도 캘린더 화면이라 누르면 이번 달이다(§1). 머리의 제목 자리는 그날의 날짜 이동 줄이다(§3 「구현」). 실패 화면의 머리도 컨트롤 없이 「전례독서」 제목이다(머리는 `views.js` 하나가 그린다). 버린 꺾쇠는 「검토한 대안 — 전례독서 화면의 위 단계」에 있다.
- **모듈은 그 화면에 처음 갈 때 받는다**(동적 `import()` — 2026-10-17, 원장 `docs/changes/2026-10-17-lazy-liturgical-modules.md`). 캘린더 탭은 캘린더, 전례독서, 엔진 셋을, 전례독서 화면은 뷰와 엔진 둘을 **한꺼번에** 요청한다(차례로 받으면 첫 방문에 왕복이 한 번 더 든다 — 사용자 결정 2026-10-18; Chromium 실측이고, WebKit은 앱 안에서 처음 갈 때 묶음의 의존 모듈을 한 번 더 요청해 이득이 없다 — `docs/known-issues.md` §13). 성서만 읽는 세션은 셋(원본 약 210KB, gzip 약 70KB)을 싣지 않는다. 이득과 대가는 서비스 워커 캐시가 없는 첫 방문에만 있다(2026-10-17 실측 — CPU 4배 저속, 운영처럼 gzip): 첫 화면 DOMContentLoaded 느린 4G −390ms, 빠른 4G −59ms, 첫 방문에 성서 화면에서 캘린더 탭 → 표 느린 4G +527ms, 빠른 4G +114ms. 재방문의 부팅 시간은 어느 쪽이든 측정 오차 안이었다(브라우저가 쓰지 않는 함수 본문의 컴파일을 미룬다). **주소로 바로 들어와도**(공유 링크 — `/calendar`, `/lectionary/<날짜>`) 모듈은 `route()`가 돈 뒤에 받는다 — 첫 방문이면 모듈 태그로 싣던 때보다 늦게 그려진다(느린 4G 캘린더 +198ms, 전례독서 +160ms, DevTools 「느린 4G」 프리셋 그대로는 +500ms, +426ms). 비용으로 받아들인다 — `<head>`에서 `modulepreload`로 미리 받으면 그 차이가 거의 없어지지만(+51, −6ms), WebKit은 실패한 미리 받기를 그 탭에 남겨 새로 고쳐도 다시 받지 않는다(사용자 결정 2026-10-18 「미리 받기를 되돌린다」 — 「검토한 대안 — 모듈 로드」 E, coding-pitfalls §34). `index.html`에는 셋의 태그가 없고 `routing.js`의 분기가 `renderLoading()` 다음에 불러온다. 받은 모듈은 기억해 두어 다시 그릴 때(달 이동, 전례독서 목록, 날짜 이동)는 `import()`를 기다리지 않는다 — 이미 받은 모듈도 `import()`는 한 태스크 뒤에 풀려 「불러오는 중…」이 한 프레임씩 그려졌다(2026-10-18, coding-pitfalls §33). 지정자는 글자 그대로 — `tests/unit/sw.test.js`가 오프라인 목록, 부팅 그래프, 한꺼번에 묶음을 대조한다. 오프라인용으로는 서비스 워커가 셋을 미리 받는다(`SHELL_FILES` — 교회력 표는 처음 쓸 때 캐시하므로, 오프라인에서 열리는 것은 온라인에서 한 번 연 화면이다). 받지 못하면(캐시 없이 연결이 끊김, 배포 사이의 어긋남으로 이음이 깨짐) 또는 그리다 오류가 나면(버그, 이음은 되지만 맞지 않는 어긋남) 뷰의 실패 화면은 그 모듈 안에 있어 쓸 수 없으므로, 라우터가 두 화면과 같은 실패 화면(`views.js` — 같은 제목, 머리)을 그리고 다음 행동은 「다시 불러오기」다 — 페이지를 새로 고친다(사용자 결정 2026-10-17 — DESIGN.md §6 「전체 화면 실패」, 버린 안은 「검토한 대안 — 모듈 로드」, 「모듈을 받지 못했을 때」). 배포 사이의 어긋남은 운영에서 서비스 워커가 제어하는 페이지에는 거의 없다 — 셋이 그 판의 셸 캐시에서 오고, 새 판은 「업데이트」를 눌러 새로 고칠 때 바뀐다. 남는 것은 서비스 워커가 없는 세션과 dev 호스트다(dev, localhost는 셸을 네트워크 우선으로 받고 `deploy.sh dev`는 버전을 올리지 않는다 — dev 배포를 확인할 때는 새로 고친 뒤 본다).
- **좁은 화면(약 320px)에서는 탭의 기본 착지를 목록으로**(사용자 제안 2026-10-15 — 2단계에서 목록 화면과 함께). `/calendar` 주소 자체는 폭과 무관하게 월간이다 — 공유한 주소가 기기마다 다른 화면이 되지 않게.
- 성 토요일 칸은 「성 토요일」이다 — 저녁 전례(부활밤, 성탄 밤)는 그날의 대표가 아니라 독서 화면에서 고르는 후보다(사용자 결정 2026-10-15 — 본 ADR §3 「구현」, 설계서 R-6.1-evening, #349). 1단계를 처음 보였을 때는 엔진이 부활밤을 그날의 대표로 내 「부활밤」이었다(설계서 미결20).

### 3. 전례독서 본문 뷰 (`js/app/lectionary.js` 신규)

- **라우트 — 날짜 기반이 기준**: `/lectionary`(오늘), `/lectionary/YYYY-MM-DD`. 상태는 쿼리 `?obs=&track=&set=&collect=`. **보조 라우트** `/lectionary/d/<slug>`(ADR-037 안정 슬러그) — 날짜 없는 검색 결과의 착지점이라 **A4(검색 이원화)에서 구현한다**(2026-10-12 — 그전엔 뷰의 「잘못된 날짜」 안내). 근거: 날짜 URL은 공유 즉시 의미가 확정되고 엔진이 절기 위치를 재계산하므로 데이터 개정에도 안정.
- **탭 분류: 캘린더 탭 소속**: 캘린더에서 날짜를 골라 들어가는 하위 화면이므로 캘린더 컨텍스트 유지(ADR-035의 `/read`=홈 선례와 다른 선택 — 봉독 자체가 목적인 `/read`와 달리 이 뷰는 날짜 탐색의 하위).
- **본문 순서: 본기도 → 제1독서 → 성시 → 제2독서 → 복음.**
- **본기도 블록 — 두 축을 구분한다**:
  - 같은 전례일의 **자유선택 대체안**(`collect_no`)은 **제목 옆 번호**로 택1(`?collect=N` — 목록의 N번째). `lectionary.js buildCollectNumbers`가 그린다(「검토한 대안 — 본기도 대체안의 표시」). 대안 세트와 트랙은 독서 카드로 고른다(아래 「구현」).
  - 서로 다른 전례일이 겹친 날(당일 + 성인축일 + 교회 축성일/축복일)에도 **고른 전례일의 본기도만** 보인다(사용자 결정 2026-10-12 — 「검토한 대안 — 본기도 열거 범위」). 엔진이 전례일별로 키잉해 주므로(ADR-037 §6, 2026-09-17) 뷰는 스위처로 고른 원소를 찾을 뿐 재조회하지 않는다 — 다른 전례일의 본기도는 그 전례일을 눌러야 보인다.
  - **송영은 앱 상수 3종** 중 고른 본기도의 `ending`(없으면 A) 하나를 **본기도 끝에 1회만** 부착(ADR-036 §3 — A·B 의 선택 원칙은 설계서 미결37. 시편 끝의 영광송과 별개 용어).
- **독서 렌더 — ADR-035 경로 재사용**: 필요한 장 JSON 전부 선로드(중복 제거) → stale 체크 → 동기 DOM 커밋(`bookmark-read.js` 패턴). 독서별 섹션 제목(label) + refs의 장별 `<article>` + `appendVerses(…, {hideCites:true})`(장 경계 병합·절 부분집합). 절 필터 로직(`_specCoversVerse` 등)은 `verse-spec.js`(다른 모듈에 의존하지 않는 모듈)로 올려 내보내고(export) bookmark-read와 공유(복제 금지).
- **계응 시편 조판**: `lps` 장의 `response` 세그먼트(응답 반행)·`versicle` 절(무번호 ¶)을 `appendVerses`가 additive로 처리 — 선창 끝의 `◯` 표지(응답 반행은 선창과 같은 색이다 — 사용자 결정 2026-11-03, 「검토한 대안 — 응답 반행의 색」). **영광송 상수는 `appendVerses`가 아니라 독서 뷰(A3)가 붙인다**(2026-07-27) — 편 낭송 끝 1회이므로 발췌 단위가 정해지는 자리가 그쪽이다. 송가는 시편 장/절 표기 옆에 명칭을 함께 적는다(예: `루가 1:46하-55 (성모송가)`). 기도서가 성구를 적는 송가(성모송가, 즈가리야 송가, 이사야 첫째 송가)의 라벨은 어느 날이나 「성구 (이름)」 표기 하나이고, 성구를 적지 않는 하느님 찬미송가는 이름만 적는다(사용자 결정 2026-11-05).
  - **렌더 기반은 독서 뷰보다 먼저 구현했다**(2026-07-27). `appendVerses` 가 계응 시편을 그리지 못하면 독서 뷰의 시편 슬롯이 성립하지 않기 때문이다 — `response`(응답 반행 + 선창 끝 `◯`)·`versicle`(`¶`)·`section`(`(N)` 소제목) additive 처리, `_specCoversVerse`·`_chapterMaxVerse` 를 `verse-spec.js` 로 승격. 영광송 부착은 이 렌더 기반에 들지 않는다(위).
  - **절 인스턴스 식별**(2026-07-27 — 예정에 없던 선행 과제). 절 부분집합 렌더의 중복 제거 키가 번호 기반이어서 같은 번호의 절이 유실되고 있었다(77개 장 130절 — 전례시편 69편의 `¶` 구절, 에스델 4장 31절). 이 상태로 독서 뷰를 만들면 시편의 `¶` 구절이 화면에서 사라진 채로 굳는다. `verse-spec.js` 에 `verseInstanceKey(s)` 를 두고 렌더·중복 제거·DOM id 가 같은 키를 쓰게 했다.
- **대안 세트·트랙 전환**: 「또는」이 있는 날은 달라지는 항목 수와 상관없이 **독서 카드** 두 장으로 세트를 통째로 고른다(사용자 결정 2026-11-05 — 아래 「구현」의 「독서 카드」, 「검토한 대안 — 대안 세트의 표시」). 트랙과 세트 모두 「또는」의 앞쪽끼리, 뒤쪽끼리 묶고 섞어서 새 조합을 만들지 않는다(기도서에 없는 관행, 사용자 확정 2026-11-05). 괄호 선택 구절 세트는 바탕에 합쳐 긴 본문 + 〔 〕 주석이다(사용자 결정 2026-10-12, 설계서 미결38 닫힘). 독서와 본기도를 함께 고르는 날(5.1, 사계재 금요일)은 카드가 아니라 전례독서 목록의 줄로 고른다(사용자 결정 2026-11-05, 「검토한 대안 — 짝지어진 독서와 본기도의 선택」). `reading_track` 1/2가 있는 날의 카드 이름은 「연속 독서」, 「복음 주제」다(화면에 「트랙」이라는 말을 쓰지 않는다, 사용자 결정 2026-11-05). **트랙은 마지막으로 고른 것을 localStorage에 기억해 날짜, 해와 무관하게 기본값으로 삼는다**(사용자 결정 2026-10-13 — 「한번 선택하면 계속 일관성 있게 같은 트랙이 기본값」. ADR-036 §2 독서 연속성을 해를 넘어 잇는 방식이고, 바꾸려면 카드를 다시 누른다 — 버린 전례년 단위 기억은 「검토한 대안 — 트랙 기억의 단위」). 부활주일처럼 `reading_track`이 없는 날의 카드는 기억하지 않는다(사용자 결정 2026-11-05, 같은 절). **공통 독서**(엔진이 `common: "<분류>"` 표지를 붙인 그룹 — 고유 독서 없는 성인, ADR-037 §6, 2026-09-17)와 공통 본기도에는 분류 라벨(「순교자 공통 독서」)을 달지 않는다 — 머리의 제목이 어느 전례일의 독서인지 보인다(사용자 결정 2026-11-03, 「검토한 대안 — 공통 독서의 분류 라벨」). 공통 독서는 당분간 보이지 않는다 — 공통 독서만 있는 후보는 전례독서 목록에 없고 주소(`?obs=`)로 가리켜도 기본 독서를 보인다. 공통 독서가 그날의 기본 독서인 날(평일 독서가 없는 날)만 그대로다(같은 날 사용자 결정, `HIDE_COMMON_READINGS` — 「검토한 대안 — 성인 공통 독서의 표시」).
- **전례일 스위처**: 후보 전례일이 여럿이면(축일∧평일 겹침 등) 다른 후보를 머리 제목 아래에 한 줄씩 링크로 보인다(`?obs=`. 이 목록의 이름은 **전례독서 목록**이다 — 사용자 결정 2026-11-04, 「검토한 대안 — 전례일 스위처의 표시」). 고른 후보는 제목이라 목록에 없고, 제목은 고른 전례일의 이름이다. 목록은 제목 영역의 맨 아래(색과 해, 문장, 이름 줄 다음)에 온다. 글은 아래 「전례독서 목록의 글」이다. 후보가 하나만 남는 날은 고를 것이 없어 목록이 없다(사용자 결정 2026-11-03, 「검토한 대안 — 후보가 하나뿐인 날의 칩 줄」). 후보가 여럿이어도 아래 예외를 빼고 하나만 남으면 그렇다(2026-11-04 — 왕이신 그리스도 주일, 대림1주일). 예외 둘(같은 날 사용자 결정): 기리는 성인(아래 「본기도」의 성인)은 머리 제목 아래에 회색 작은 글씨로 「이름 축일」을 한 줄씩 보이고(본기도와 같은 차례, 다른 전례일을 눌러도 그대로), 그날 지키는 기념일도 그 아래에 「이름 기념일」로 보이며(고유 본기도와 독서가 없어 눌러도 본문 없는 화면뿐이었다 — 성주간에 생략된 기념일은 어느 줄에도 없다), 공통 독서만 있는 후보는 당분간 목록에 없다(위 「공통 독서」). 기념만 하거나 생략하는 후보도 고유 독서가 있든 없든 목록에 없고 누를 수 없는 글이다 — 그날 눌러서 화면을 옮길 까닭이 없다(사용자 결정 2026-11-04, 「검토한 대안 — 기리는 성인의 표시」 C). 기리는 성인은 위 이름 줄(12.29 토마스 베켓, 7.26 안나와 요아킴 등)이고, 그 밖은 같은 줄에 이름만 보인다(성 십자가 발견, 라틴 문 앞의 사도 성 요한, 사도 성 베드로의 탈옥). 「· 기념만」 문구는 두지 않는다. 고유 독서가 있는데 글로 보이는 날은 2025-2050년에 52일(주일 31일, 평일 21일)이고, 그 독서는 그날 화면에서 볼 수 없다. 그 축일을 지키는 해의 날짜에서 본다. 본기도는 평일에 밀린 기리는 성인(16일)만 기본 독서의 본기도 뒤에 이어 보인다(아래 「본기도」). 지역 축일(`national` — 삼일절, 광복절)만 예외로 기념만 하는 날에도 목록의 링크다. 주일에 지키지 않더라도 그날 독서를 볼 수 있게 한다(같은 날 사용자 결정). 2025-2050년에 9일이고, 누르면 그 독서와 본기도를 보인다. 2.11 병자를 위한 기도일도 기념만 하는 해에 줄이 있다(아래 「병자를 위한 기도일의 대체 독서」). 눌러도 빈 화면이거나 다른 후보와 같은 화면인 후보도 목록에 없다(사용자 결정 2026-11-04, 「검토한 대안 — 본문 없는 후보와 같은 본문의 격자」). 독서도 본기도도 없는 후보가 그렇다. 이동 축일이 그날의 주일이나 평일 자리를 맡아 본문이 축일 쪽에만 있는 격자(왕이신 그리스도 주일의 연중 34주일, 성지주일의 사순 주일 등)와 본문 없는 날 셋(가정주일, 평화통일주일, 세계평화를 위한 기도일)이다. 본문 없는 날은 이름 줄에서 기념일 줄 밑에 이름만 한 줄로 보인다. 그날 지키는 이름 있는 후보와 독서, 본기도가 똑같은 격자(대림1주일의 대림 1주일 격자)도 목록에 없다. 생략된 후보나 옮겨 간 후보와는 견주지 않는다(PR #467 리뷰). 옮겨 간 축일도 원래 날짜의 목록에 없다. 머리 제목 아래 「성 니콜라 축일을 12월 7일로 옮김」으로 알리고(색과 해 줄 다음, 기리는 성인 줄보다 먼저. 이름이 「날」로 끝나면 「모든 별세자의 날을 11월 3일로 옮김」), 그 독서는 옮겨 간 날에 있다(사용자 결정 2026-11-04, 「검토한 대안 — 옮겨 간 축일의 표시」). 감춘 후보를 주소로 가리켜도 기본 독서다. 표시 순서는 ADR-037 §6의 ① 축일/재일, ② 옮겨 지키는 축일, ③ 나머지다. **전례독서 목록은 고를 본문이 있는 후보 전부를 보이고**(위의 예외) `official`은 **초기 선택**일 뿐이다 — 전례상 사용되지 않는 후보(축일에 밀린 연중 독서)도 모두 보이고, 앱이 낮은 등급을 숨기거나 한 이름으로 합쳐 내지 않는다(ADR-036 §7 밀린 독서 보존, 설계서 §5.5, ADR-037 §6). 독서자의 목적에 맞는 선택은 사용자 몫.

  - **기념일 후보**(2026-09-17): 본기도·독서가 빈 결과다(설계서 §2, §5.6 — 04.05 마틴 루터 킹, 09.14 성가수도회, 11.01 초대주교). 2026-11-03부터 제목 아래 「이름 기념일」 줄로 보인다(위 「전례일 스위처」). 초기 선택이 아니다(→ 설계서 R-6.1-ineligible).
  - **사계재 후보**(2026-09-17 — 지향, → 설계서 R-6.1-ineligible): 후보로는 남되 초기 선택이 아니다. 전례독서 목록의 이름과 고른 뒤의 제목은 그날 본문의 제목이다(사용자 결정 2026-11-05, `choiceNameOf`). 수요일은 「성직자의 성소를 위한 동계재」, 금요일은 「성직후보자의 성소를 위한 동계재」와 「수도자의 성소를 위한 동계재」 두 줄, 토요일은 「모든 신자의 성소를 위한 동계재」다. 누르면 그 성소 본기도와 독서를 보인다 — 서울교구 2024 면이 인쇄한 것과 같은 본문이다. 캘린더 칸은 지금처럼 짧은 이름(「동계재」)이다(같은 날 사용자 결정). **사계재를 누르면 헤더 색은 그 후보의 색(`observance.color` 자)이다**: 「재일 독서를 읽을 때만 자색, 어차피 선택 독서」(2026-09-17). 그날 자체의 색(`resolved.color`)도 자다 — 축일이 지정 전례일이면 축일 색이 대표이고 `colors`가 [자, 축일 색]으로 병기한다(2026-10-10 사용자 결정 — 책자 2025, 2026대로, → 설계서 R-6.4-ember-color). 색 필드는 셋이다(2026-10-10 사용자 결정 — 버린 안은 「검토한 대안 — 병기 색의 자리」) — `color`는 그날의 대표색 하나, `colors`는 병기 목록(사계재 날 축일이 지정 전례일이면 둘, 책자의 [자/백] 순), `colorAlt`는 선택 대체색(장미색, 청색 — 데이터 `color_alt`와 같은 `null | 스칼라 | 배열` 3형, 대림 3주일은 둘 다)이다. 병기를 그리는 뷰는 `colors`를 읽는다 — 병기가 없는 날은 `[color]`다.
- **축성일 줄**(사용자 결정 2026-11-04): 머리 제목 아래 이름 줄의 맨 아래(기리는 성인, 기념일, 본문 없는 날 다음)에 그날 축성되거나 축복된 교회를 보인다. 종류마다 한 줄이고, 교회 이름을 쉼표로 이은 뒤 「축성일」이나 「축복일」을 한 번만 붙인다(9.1은 「일산성당, 초지성당, 행신성당 축성일」, 4.21은 「강릉성당 축성일」과 「세종성당, 청주산남성당 축복일」 두 줄). 축성일 줄이 먼저다. 「북.」으로 시작하는 성당(북한에 있던 성당, 2026-11-04 기준 36곳)은 보이지 않고, 주보성인도 보이지 않는다. 다른 전례일을 눌러도 그대로다. 본당을 고르는 설정과 그 본당의 등급 격상(ADR-036 B2 `scope` 오버레이)과는 따로이고, 이 줄은 모든 본당을 보인다. 자료는 데이터 본당 표(`local-observances.json`)이고, 엔진 `findDedications`가 양력 월일로 찾는다(설계서 §3.5, 미결2 닫힘). 본당 표를 받지 못하면 줄 없이 그린다. 캘린더 칸에는 보이지 않는다.
- **대체 독서 표시**(사용자 결정 2026-11-05, 2026-11-06): 설정에서 끄면(기본값) 기본 독서가 대축일, 주요축일, 고유 독서가 있는 축일인 날에 그날의 평일, 주일 줄을 전례독서 목록에서 숨긴다(`isAlternateReading`). 사계재, 옮겨 지킬 수 있는 축일, 옮겨 지킬 수 있는 축일이 평일에 온 날의 평일 줄(「· 주의 봉헌 축일 대체 독서」, 2026-11-06), 이름이 있는 줄, 삼일절과 명절의 평일 줄은 늘 보이고, 주소로 가리키면 그 독서를 보인다. 2025-2050년에 908줄이다. 자세한 것은 ADR-041 §4다. 세례명 성인의 줄(§5), 소속교회의 축성일(§6), 09.29 대한성공회 설립 기념일을 이름 줄로 옮기는 것(§6)도 ADR-041이 정한다.
- **선택 봉헌, 옮겨진 축일, 명절 — 두 독서를 나란히**(2026-09-19 사용자 확정). 옮길지는 지역 교회 사제가 정하는데 **독자는 그 결정을 모를 수 있다.** 그래서 앱이 설정으로 정하지도, 한쪽을 기본으로 깔고 다른 쪽을 링크로 숨기지도 않고 — **두 독서를 선택지로 나란히 내어 독자가 고르게 한다**(버린 안은 「검토한 대안 — 선택 봉헌 · 옮겨진 축일의 표시」). 어느 쪽이 `official` 인지는 표시하되 선택을 대신하지 않는다. `activated` 는 v1 에서 빈 집합이다(설계서 미결15).
  - **당일**(예: 8.6 주의 변모): 「주의 변모 독서」 / 「가까운 주일로 옮겨 지키는 경우 — 이날은 평일 독서」를 설명과 함께 나란히. 목적지는 엔진이 `nearby_sunday` 로 계산한 날짜다 — 2026 은 오는 주일 8.9, 2024 는 직전 주일 8.4, 2025 는 8.3. 안내는 「오는」·「지난」 없이 날짜만 쓴다(「8월 9일로 옮겨 지킬 수 있음」, 2026-11-06).
  - **목적지 주일**(2026 이면 8.9): 「연중 19주일 독서」 / 「주의 변모 독서(8.6 에서 옮겨 지키는 경우)」를 나란히(엔진의 `optional` 후보).
  - **규칙상 축일을 옮겨 온 날**(예: 12.7 니콜라)도 마찬가지다 — 그날의 후보들을 선택지로 낸다.
  - **명절**(설·추석 — 설계서 미결29): 명절이 지정 전례일인 날도 그날의 평일 독서를 나란히 낸다. 책자가 세 해(2024·2025·2026) 여섯 사례에서 초기 독서를 고유·평일로 번갈아 두었고, 네 사례에서는 다른 쪽을 함께 적었다 — 2026 두 사례는 한쪽만 실었다(사례별 표기는 검토 문서 X-11, X-12와 보관 문서의 설계서 미결29 절). 초기 선택이 달라지므로 두 독서를 항상 낸다.

**구현(A3 — 2026-10-12, #346).** `js/app/lectionary.js`가 본 ADR §3을 구현한다 — 순수 모델(`buildLectionaryModel`: 초기 선택, 트랙, 세트, 본기도, 전례독서 목록, 헤더 색, URL)과 DOM 렌더를 나눴고(`LECTIONARY_MODEL` 마커 블록이 유닛 대상), 모든 컨트롤이 링크라 전역 `<a>` 인터셉터가 이동한다(뒤로, 공유, 키보드 그대로). 엔진은 `optionalDestOf` 노출 하나만 더했다. 구현하며 정한 것은 아래다 — 2026-10-12에 사용자가 하나씩 확정했다(coding-pitfalls §21, 원장 `docs/changes/2026-10-12-lectionary-view.md`).

- **초기 선택은 `official`이되, 지정 전례일의 독서가 공통(`common`)뿐이면 그날의 격자(주일, 평일) 독서가 초기 독서다**: 책자대로(사용자 확정 2026-10-12, 설계서 미결25 닫힘). 머리의 제목은 고른 전례일의 이름이라 처음에는 이 초기 선택(그날의 기본 독서)의 이름이다 — 11.6 레오나드 날은 「연중 31주 금요일」이고 레오나드는 제목 아래 이름 줄에 보인다(사용자 결정 2026-11-03, 11-04, 「검토한 대안 — 머리의 전례일 이름」). 대표색은 여전히 지정 전례일(그날)의 색이다; 본기도는 고른 전례일의 것이라 초기 화면에는 격자의 본기도가 보인다(아래 「본기도는 고른 전례일의 것만」 — `collectsFor(selected)`, 유닛 「사계재 날」 케이스). 9.16 니니안, 10.12 윌프리드가 실례.
- **본기도는 고른 전례일의 것만** 보인다(사용자 결정 2026-10-12) — 대체안은 제목 옆 번호 「1 · 2 · 3」(사용자 결정 2026-11-05, 「검토한 대안 — 본기도 대체안의 표시」), 송영은 고른 본기도의 `ending`(없으면 A) 하나. 예외: 기본 독서를 볼 때는 그 본기도 다음에 **기리는 성인**의 본기도(대체안이 여럿이면 첫째)를 잇고, 송영은 마지막 성인 본기도의 `ending`으로 한 번 단다(사용자 결정 2026-11-03, `memorialOf`). 기리는 성인은 성인 유형(공통 본기도의 유형 — `commons.json`의 `classes`)이 있는 월별 축일 후보다. 기본 독서가 평일(격자)인 날 — 지정 전례일인 성인 축일에 고유 독서가 없어서(위 「초기 선택」) — 그날 지키는 성인 축일 모두와, 밀려서 그날 기념만 하는 축일(옮겨 온 축일과 겹친 12.29 토마스 베켓)이다. 다만 주일에는 성인 본기도를 잇지 않는다(사용자 확인 2026-11-04). 주일과 겹쳐 기념만 하는 성인(7.26 안나와 요아킴)은 이름 줄에만 보이고, 송영은 주일 본기도의 것이다. 삼일절처럼 유형이 성인 유형이 아닌 행(`national`)은 잇지 않는다. 같은 날 성인이 둘 이상이면, 유형이 같고 공통 본기도를 쓰는 성인은 그 본기도 하나에 이름을 모으고(「A와 B를」), 유형이 다르면 유형 정의 차례(순교자, 성직자, 선교사, 신학자·교육자, 수도자, 성인 일반)로 잇는다 — 2.14 발렌틴(순교자)과 키릴과 메토디우스, 12.31 실베스터(성직자)와 위클리프(신학자). 그날 지키는 성인 축일이 둘 이상이고 색이 다르면 머리의 색도 같은 차례로 「적색 또는 백색」이다(2.14). 공통 본기도의 이름 뒤 「을(를)」은 이름의 받침에 맞춰 고른다(엔진 `fillCommonName`, 같은 날). 같은 날의 다른 전례일(성인축일, 축성일 …) 본기도는 그 전례일을 눌러야 보인다 — 엔진 `findCollects`의 ② 축(서로 다른 전례일이 겹쳐 따라오는 본기도)은 열거하지 않고 전례일별 키잉만 쓴다 — 전례독서 목록이 고른 원소를 찾는 데(버린 열거안은 「검토한 대안 — 본기도 열거 범위」).
- **두 독서는 전례독서 목록으로 고른다**(사용자 결정 2026-11-03): 선택 봉헌, 옮겨진 축일, 명절의 두 독서는 전례독서 목록(상태 표시 「· 12월 6일에서 옮겨 옴」, 「· 8월 6일에서 옮겨 지킬 수 있음」)로 고르고, 따로 「두 독서 가운데 고르기」 카드를 두지 않는다 — 줄로 이미 고를 수 있다. 기본 독서는 지금처럼 지정 전례일이다(12.7은 옮겨 온 성 니콜라). 카드에만 있던 설명(「이날의 평일 독서」, 「오는 주일(8월 9일)로 옮겨 지키는 경우」)은 없어졌다. 버린 카드는 「검토한 대안 — 두 독서를 나란히 놓는 방식」에 있다. 2026-11-06부터 그 설명을 줄과 제목 아래 안내로 다시 보인다(사용자 결정). 원래 날짜의 평일 줄은 「연중 18주 목요일 · 주의 변모 축일 대체 독서」이고, 제목 아래 안내는 축일이면 「8월 9일로 옮겨 지킬 수 있음」, 평일이면 「주의 변모 축일 대체 독서」다(ADR-041 §4).
- **헤더 색은 고른 본문의 색을 따른다**(사용자 결정 2026-10-12 — 뷰만): 고른 후보가 자기 색을 가진 **비격자** 후보이고 그 색이 그날의 대표색과 다르면 그 색(그 후보의 대체색 `color_alt` 가 있으면 함께 — 사계재 자, 성 토요일 저녁의 부활밤 백, 생략된 성인), 그 밖은 그날의 `colors`(병기) + `colorAlt` 그대로(사계재 날 성인 [자, 백]). 격자는 절기 바탕색을 들고 있을 뿐이라 제외. 엔진의 그날 색은 낮의 것이다 — 성 토요일 홍(저녁 전례는 색에 참여하지 않는다, 설계서 R-6.1-evening).
- **병자를 위한 기도일의 대체 독서**(사용자 결정 2026-11-07, 설계서 미결51): 2.11의 본기도와 독서(기도서 103쪽 「병자」)는 그날의 대체 독서다. 등급은 축일 그대로라 평일이면 그날의 대표이고 캘린더 칸에도 이 이름이 보이지만, 기본 독서는 그날의 평일, 주일 독서다. 데이터의 표시(`alternate_readings`)가 있는 축일은 고유 독서가 있어도 기본 독서로 고르지 않는다(`initialCandidate`). 전례독서 목록에 「병자를 위한 기도일 · 대체 독서」 줄이 있고, 누르면 제목이 그 이름으로 바뀌고 제목 아래에 같은 말 「대체 독서」가 보인다. 이름 있는 줄이라 설정 「대체 독서 표시」와 상관없이 보인다. 기념만 하는 해(2025-2050년에 주일 2029, 2035, 2046, 설날 2032, 재의 수요일 2043)에도 지역 축일처럼 줄을 둔다. 2.11이면 어느 해든 읽을 수 있게 넣은 독서이기 때문이다. 본기도의 이름 자리는 괄호 안의 공백으로 두고 조사는 「을/를」로 적는다. 이름이 비어 받침을 알 수 없기 때문이다. 공백은 줄바꿈 없는 공백(U+00A0)이라 줄어들거나 줄이 나뉘지 않는다. 전례색은 비어 있어 그날 색을 따른다(설계서 미결30).
- **전례독서 목록의 글**(§3-1, 설계서 미결42 닫힘 — 사용자 확정 2026-10-12, 2026-11-04): 괄호 설명을 전부 뗀 이름(「토마스 크랜머」) + 상태 표시(「12월 6일에서 옮겨 옴」, 「옮겨 지킬 수 있음」, 「저녁」). 이름은 밑줄 링크이고, 상태 표시는 보조 글자색이며, 끝에 ›가 있다. 칩에 있던 주기와 독서 N은 붙이지 않는다 — 제목 아래 줄과 독서 카드에 있다. 긴 줄은 말줄임 없이 낱말 사이에서 줄을 바꾸고(1900-2100년에 가장 긴 글은 30자로 「모든 성인의 날 · 11월 1일에서 옮겨 지킬 수 있음」과 「모든 성인의 날 · 10월 31일로 옮겨 지킬 수 있음」이다), 전체 이름은 `title` 속성이다. 고른 후보의 상태는 이름이 제목으로 올라가므로 제목 아래에 안내한다. 안내는 상태 표시와 같은 말을 마침표 없이 쓴다 — 「12월 6일에서 옮겨 옴」, 「8월 6일에서 옮겨 지킬 수 있음」, 「주의 변모 축일 대체 독서」. 상태 표시 「저녁」만은 홀로 짧아 안내가 「저녁 전례」다(`selectedNoteOf`, 사용자 결정 2026-11-06: 원래 날짜와 옮겨 간 날의 안내를 같은 형식으로, 간결하게). 옮겨 지킬 수 있는 축일의 원래 날짜는 「8월 9일로 옮겨 지킬 수 있음」, 옮겨 간 축일의 원래 날짜는 「성 니콜라 축일을 12월 7일로 옮김」이다. 기념만 하거나 생략하는 후보는 링크가 아니라 이름 줄의 글이고(위 「전례일 스위처」), 기념만 하는 후보에는 상태 표시를 붙이지 않는다. 「· 생략」이 실제로 보이는 날은 1900-2100년에 없다 — 성주간에 생략되는 성인(안셀름, 조오지, 토마스 크랜머)은 공통 독서뿐이라 전처럼 보이지 않는다.
- **독서 카드**(사용자 결정 2026-11-05. 괄호 선택 구절은 2026-10-12, 설계서 미결38 닫힘): 「또는」 대안(대안이 있는 슬롯만 바꾼 완전한 세트 — ADR-037 §1; 파서 표지 「원본 세트 N」이든 표지 없음이든)과 트랙은 본기도 아래, 제1독서 바로 위의 카드로 고른다(모델 `readingCards`, 화면 `buildReadingCards`). 슬롯 하나만 다른 날도 같다. 카드는 링크이고 세트나 트랙을 통째로 고른다. 이름은 연중 트랙이 「연속 독서」, 「복음 주제」(2024 책자 일러두기의 「구약성서의 연속 독서」, 「복음 본문 주제에 따른 독서」)이고, 조건부 세트는 바탕이 전례일 이름, 조건이 조건 문구(「…로 지킬 때」라는 문구로 통일 — 데이터의 「…로 지키는 경우」도 그렇게 보인다)이며, 그 밖은 「독서 1」, 「독서 2」다. 제목이 다르면 제목으로. 모든 슬롯의 성구를 적어 고르기 전에 무엇을 읽을지 보인다. 두 카드에서 다른 성구는 `--text`에 굵기 500, 같은 성구는 `--text-secondary`다(「검토한 대안 — 다른 성구의 표시」). 이름 아래에 가로선을 두어 성구와 나눈다. 고른 카드의 테두리는 고르지 않은 카드와 같은 1px이고 `--accent`의 60%다(「검토한 대안 — 고른 카드의 테두리」, 모두 사용자 결정 2026-11-05). 같은 슬롯끼리 줄이 맞도록 카드가 부모의 줄을 나눠 쓴다(`subgrid`). 조건 카드를 고르면 제목과 문서 제목만 조건의 이름(「주의 변모 주일」)으로 바뀌고 색과 본기도는 그대로다(`conditionTitle`, 2025, 2026 책자는 이날을 「사순 2주일 [자]」로 적는다). **접기**: 처음에는 펼쳐 보이고, 「접기」를 누르면 카드 대신 「독서」 제목 옆에 이름 알약이 남으며, 이름이 「독서 N」이면 본기도와 같은 번호가 남는다. 그 자리에서 바로 바꿀 수 있다. 한 번 접으면 모든 날에 접힌 채로 기억한다(`bible-lectionary-cards-folded`). 접힘은 고른 독서가 아니라 보는 사람의 화면 설정이라 주소에 적지 않고, 화면을 다시 그리지도 않는다. 기도서 표로 세면 슬롯 하나만 다른 곳이 39행(주일 16, 주간 12, 축일 11)과 사계재 수요일 4건이고, 슬롯 둘 이상이 다른 곳이 85행(연중 주일 76, 부활주일 3, 성령강림주일 3, 승천일, 성 금요일, 성 토요일)이다. 주일 16행 가운데 왕이신 그리스도 주일 가해와 다해 2행은 시편만 다르지만 트랙이다. 2025-2050년에 카드가 보이는 날은 트랙 614일(왕이신 그리스도 주일 18일 포함)과 세트 674일(둘 이상 다른 날 130일, 하나만 다른 날 544일)이고, 카드가 셋 이상인 날은 없다. 괄호 선택 구절 세트(한 슬롯만 더 긴 세트)는 카드로 만들지 않고 바탕에 합쳐 **긴 본문 + 선택 구절 〔 〕 + 「짧게 읽으면 …」 주석**으로 그린다(`readingOptions`, `optionalVerseTest`).

- 본문이 빈 화면은 기본 독서 후보 자신이 빈 날에만 나온다. 본문 없는 후보는 전례독서 목록에 없고 주소로 가리켜도 기본 독서이기 때문이다(위 「전례일 스위처」, 2026-11-04). 실데이터에는 그런 날이 없다. 제목은 고른 후보가 기념일이면 「기념일 — 본문 없음」, 그 밖은 「고유 본문 없음」이다. 설명 문구는 사용자 결정(2026-10-24 — 화면 글에 「관측일」을 쓰지 않는다)이다. 기념일은 「기념일은 고유 본기도와 독서를 두지 않습니다.」, 본문 없는 축일(`minor_feast` — 세계평화를 위한 기도일, 설계서 미결51)은 「독서 본문 없이 기념하는 축일입니다.」, 그 밖은 「따로 정한 독서가 없습니다.」이고, 전례독서 목록이 있는 날에만 뒤에 「다른 독서를 선택하세요.」를 붙인다(2026-11-04 — 줄이 없으면 고를 것이 없다). 전례독서 목록의 `aria-label` 은 「이날의 다른 전례」다. 독서는 없고 본기도만 있는 날(데이터 누락)은 「독서 없음」(설명 「독서는 없고 본기도만 있습니다.」) — 2026-10-12 실측된 세 칸(사순 2주 화, 수, 부활 4주 토)은 data#30 으로 채워져 지금 데이터에는 없고, `lectionary.data.test.js` 의 전수 검사가 빈 누락 목록을 지킨다.
- **절 발췌는 번호만으로 고르지 않는다**(2026-10-13 자체 리뷰 — `selectVerses`, `trimHalfVerses`): 다른 장에서 옮겨 실린 절(`chapter_ref` — 이사 40의 41:6-7)은 뺀다. 번호 체계가 둘인 장(다니 3 — 그리스어 추가 본문 `lxx_only` 24-90 ∧ 히브리 뒷부분 24-33)은 spec이 그리스어에만 있는 번호를 덮으면 그리스어 체계(히브리 절은 `alt_ref`로), 아니면 히브리 체계다 — 「다니 3:25, 34-43」(사순 3주 화)은 아자리야의 기도, 「다니 3:14-20, 24-25, 28」(사순 5주 수)은 히브리 본문(로마 성서정과 Dn 3:25, 34-43, Dn 3:14-20, 91-92, 95와 같다). 두 결과가 RCL(NRSV 번호) 계열 독서표와 같은 본문이라 이 규칙으로 **완결**이다(사용자 결정 2026-10-13 — 「RCL 과 일치하면 완결」: 사순 3주 화는 잉글랜드 CW 「Song of the Three 2, 11-20」, 사순 5주 수는 CW 「Dan 3.14-20, 24-25, 28」). 데이터의 다니 3 참조는 이 둘뿐이고, 새 참조가 생기면 실데이터 테스트가 멈춘다. 반절(상 → `a`, 하 → `b`)은 데이터의 경계 표(`lectionary/half-verses.json`, 원료는 데이터 저장소 `liturgical/half-verses.md`)대로 그린다(사용자 결정 2026-10-22). 표는 반절마다 줄 경계(상은 그 줄까지, 하는 그 줄부터)나 줄 안의 경계 문구(상은 문구까지, 하는 문구부터)를 준다. 한 줄로 그려지는 절도 문구에서 나눈다. 경계의 기준은 서울교구 게시글의 본문이고, 게시글이 절 전체를 싣거나 없는 곳은 문장 경계로 정했다. 반절 참조는 60곳(전례독서 59, 성인 공통 1)이다. 엔진이 독서 묶음과 함께 표를 싣고(`findHalfVerse`), `lectionary.js trimHalfVerses`가 줄을 걷거나 줄 안의 글자를 자른다. 자른 절의 번호는 독서 제목, 복사 출처, 게시글과 같게 「35하」 「4상」으로 보인다(사용자 결정 2026-10-22). 표에 없거나 「전체」인 반절(로마 3:22하)은 절 전체를 그린다. 표를 받지 못해도(업데이트 뒤 처음 오프라인으로 열 때) 화면은 열리고 절 전체를 그린다. 엔진이 이 표만 실패를 받아들이고, 다음 진입마다 이 표만 뒤에서 다시 받는다(설계서 §3.5, PR #365 리뷰). 에스델 4:17의 하위 절은 설계서 미결39 그대로(4:17 인스턴스를 다 그린다).
- **본기도, 대안 세트의 순서와 `?collect=`**(2026-10-13 자체 리뷰): 한 날짜에 다른 전례일의 것이 섞여 오면(5.1 노동자의 날 ∧ 사도 성 필립보와 성 야고보 — 설계서 미결18, 35) 고른 전례일 이름의 것을 앞에 둔다 — 5.1은 사도 축일이 먼저이고, 지역 축일인 노동자의 날은 독자가 원하면 고른다(사용자 결정 2026-10-13). **독서 세트와 본기도가 같은 제목으로 1:1 짝지어지는 날은 전례독서 목록의 줄 하나가 둘을 함께 고른다**(사용자 결정 2026-10-13, 2026-11-05 — 「대안 독서는 사도 축일, 본기도는 노동자의 날」 같은 교차 조합은 없다; 실데이터에서는 5.1과 사계재 금요일 넷 — 2025-2028 전수, `linkCollects`). 세트마다 한 줄이고 그 세트의 제목이 줄 이름이며, 누르면 그 제목이 머리의 제목이 된다. 그날은 `?set=`이 본기도까지 정하고 `?collect=`는 읽지도 쓰지도 않으며, 본기도 칸에 번호가 없다(버린 안은 「검토한 대안 — 짝지어진 독서와 본기도의 선택」). `?collect=`는 본기도 목록의 몇 번째(1부터 — `?set=`과 같은 규칙)이다.
- **본문 복사**(2026-10-13 자체 리뷰 — `views.js bindCopyAttribution` 공유): 뷰 루트에 한 번 묶어 독서 섹션마다 「본문 — 출처」 블록을 빈 줄로 잇는다. 본기도, 카드, 헤더 글자까지 고르면 가로채지 않는다(브라우저 기본 복사). 글자가 한 자 이상 겹친 절만 센다. 번호는 고른 절의 정수 연속 구간(줄 글자 없음 — 장 본문과 같은 계약, 병합 절은 두 끝, 건너뛴 절은 쉼표)이다. 반절로 그린 절은 「35하」 「21상」으로 적는다. 예는 「전례시편 104:24-34, 35하」, 「집회서 51:12하-20상」이다(2026-10-22, `halfVerseRanges`). 장 경계는 그 장의 실제 마지막 절에서 다음 장 1절로 이어질 때만 「42:11-43:1」. 송가는 「송가 이름 + 절」. 번역 표기는 성서가 「(공동번역성서)」, 전례시편, 송가가 「(대한성공회 기도서)」다(기도서 번역 — ADR-037 §1, §3; 사용자 결정 2026-10-13 — 장 본문 `/lps`, `/cant`와 절 선택 복사 버튼도 같다, `verse-spec.js citationSource`). **전례 표기 ◯, ¶, 「(N)」은 복사에 남긴다**(사용자 결정 2026-10-13 — 주보 등 전례 용도에 쓰인다): ¶ 뒤에 한 칸, 「(N)」은 제 줄에 두고, 부의 첫 절부터 고르면 그 「(N)」도 싣는다(`serializeVerseRange` — 버린 안은 「검토한 대안 — 전례시편 복사의 출처 · 표기」). 시편 끝 영광송까지 고르면 그 시편 블록의 출처 줄 앞에 싣는다(머지 전 검토 2026-10-14). 출처 번호의 예외 둘(머지 전 검토 2026-10-14 — 장 본문, 전례독서 공통, `bindCopyAttribution`): **이 번역에 없는 절 번호(마르 9:44, 46)는 건너뛴 절이 아니라 사이에 두어도 한 구간**이다(사용자 결정 2026-10-14 — 「9:43-48」, 「9:1-50」, main과 같다; `<article data-absent>`). 다른 장에서 옮겨 실린 절(`verse-cross-ref` — 이사 40의 41:6-7)과 그리스어 추가 본문 절(`verse-lxx` — 다니 3의 (24)-(90))의 번호는 그것만 고른 게 아니면 출처에 넣지 않는다(「이사야 40:19-20」, 「다니엘 3:1-33」). 그 절만 골랐으면 그 번호를 쓰되, 옮겨 실린 절은 본래 장으로 적는다(「이사야 41:6-7」, 사용자 결정 2026-10-21). 본래 장은 줄의 `data-chapter-ref`에서 읽는다. 채택하지 않은 안은 「검토한 대안 — 옮겨 실린 절만 고른 복사의 출처」에 있다. 절 선택 막대의 복사도 같은 규칙을 따른다(2026-10-21, ADR-010 「세그먼트와 저장 표기」).
- **실패, 범위**: 교회력 자료나 화면 모듈을 받지 못하면(또는 그리다 오류가 나면) 이 뷰의 실패 화면 — 「전례독서 자료를 불러오지 못했습니다」와 다음 행동 「다시 불러오기」, 앞 화면의 헤더, 제목을 남기지 않는다(본 ADR §2 「구현」의 모듈 로드). 깨진 날짜(「잘못된 날짜입니다」), 1583-9999 밖의 연도(「교회력을 계산할 수 없는 날짜입니다」), 교회력에 없는 날은 다음 행동 「이번 달 캘린더」(부제 「「이번 달 캘린더」를 눌러 다른 날짜를 골라 주세요.」). 어느 실패든 머리는 컨트롤 없는 「전례독서」 제목이고(2026-11-03, §2 「구현」), 라이브 영역은 제목과 안 된 것을 함께 읽는다(DESIGN.md §6 「전체 화면 실패」 — 2026-10-18; 그전엔 단추가 없었고 모듈 실패 화면만 휴대폰에서 숨는 집 단추였다). 범위의 기준은 엔진이다(`isComputableDate`; `resolveDate`도 범위 밖에 null을 내 옮김 계산을 거치지 않는다 — 그전엔 0100년대에서 엔진의 날짜 이동이 같은 날을 돌려줘 탭이 멈췄다). 커밋 뒤 라이브 영역은 「날짜 — 이름 전례독서」를 읽는다(이름은 고른 전례일의 짧은 이름). 범위 끝(1583-01-01의 전날, 9999-12-31의 다음날)에는 날짜 이동 단추가 자리만 남는다 — 캘린더의 달 이동과 같은 세 칸(`dateNavParts`)이다(2026-10-17; 그전엔 그 실패 화면으로 가는 링크였다).
- **날짜 이동 줄은 머리의 제목 자리에 있다**(사용자 결정 2026-11-03): ‹ 날짜 「오늘」 ›를 「전례독서」 대신 `#page-title`에 그려 스크롤해도 보인다(`commitTitleDateNav` — 본문 맨 위에는 날짜 줄이 없다). 「전례독서」는 문서 제목에 남는다. 보이는 날짜는 요일 없이 YY.MM.DD이고(「26.12.28」, 사용자 결정 2026-11-05), 날짜 글자만 화면 가운데에 두고 「오늘」은 그 오른쪽에 둔다(같은 결정). 폭이 모자라면 왼쪽 빈칸이 줄어 날짜가 왼쪽으로 옮겨 가고, 줄을 바꾸지 않는다. 스크린 리더는 숨긴 전체 날짜를 읽는다. 날짜가 바뀐 다시 그리기는 맨 위에서 시작한다 — 읽던 자리에서 누르기 때문이다. 이 단추들은 `#app` 밖이라 라우터가 포커스만 돌려주고 스크롤은 뷰에 맡긴다(ADR-031 §5). 같은 날의 전례독서 목록, 독서 카드는 누른 자리를 지킨다. 버린 배치는 「검토한 대안 — 날짜 이동 줄의 자리」에 있다.
- **본문 제목 줄은 없다**(사용자 결정 2026-11-03): 「모든 별세자의 날 독서」처럼 고른 전례일의 이름을 독서 위에 다시 적지 않는다 — 머리의 제목이 같은 이름이다. 본기도 뒤 송영은 본기도 본문과 같은 색이다(같은 날 사용자 결정).
- **다시 그린 뒤 포커스는 누른 컨트롤로 돌아간다**(2026-10-17 — PR #348 리뷰) — 날짜 이동(전날, 다음날, 「오늘」), 전례독서 목록, 독서 카드와 접은 알약, 본기도 번호는 화면 전체를 다시 그리므로, 누른 자리(`data-focus-key` — `prev`, `next`, `today`, `choice:<i>`, `track:<n>`, `set:<i>`, `folded:track:<n>`, `folded:set:<i>`, `collect:<i>`)를 기억했다가 새 화면의 같은 컨트롤에 포커스를 둔다(WCAG 2.4.3). 전례독서 목록은 누른 줄이 제목으로 올라가 사라지므로 줄의 자리를 키로 쓴다 — 후보가 둘이면 Enter를 거듭 눌러 오갈 수 있다(2026-11-04). 그 컨트롤은 누른 때의 화면 위치에 다시 선다 — 새 장을 받아야 하는 다시 그리기(세트, 트랙, 전례독서 목록, 날짜)는 스켈레톤이 먼저 그려져 스크롤이 맨 위로 눌렸고, 컨트롤이 아래로 밀리거나 아래쪽 컨트롤이면 화면 밖으로 나갔다(2.4.7). 페이지 맨 위에서 눌렀으면 스크롤하지 않고 맨 위에 남는다 — 고른 후보의 문장이 줄 위에 생겨도 제목과 머리 사이의 여백이 줄지 않는다. 그때 줄은 문장만큼 내려간다(2026-11-04, ADR-031 §5). 자리를 재고 돌려주는 것은 라우터다(ADR-031 §5 — 캘린더의 달 이동, 구분 탭, 검색 페이지와 같다); 이 뷰는 키만 단다. 같은 자리가 없으면(위 범위 끝) 앞뒤 단추의 `data-focus-fallback`인 「오늘」로. 새 탭으로 여는 클릭은 라우터가 가로채지 않아 자리도 남지 않는다(`isModifiedClick`). 다시 그리는 사이 독자가 포커스를 다른 데(머리의 검색 칸, 팝오버)로 옮겼으면 돌려주지 않는다 — 누른 링크와 함께 포커스가 body로 떨어졌을 때만이다(PR #350 리뷰 — 그 칸에서 이어 치던 글자와 Enter를 빼앗았다).

### 3-1. 표시 라벨 규칙 — 트랙·주기 병기

데이터의 `title`은 주기·트랙 표기를 뺀 정규화 이름(ADR-036 §2)이다. 따라서 **전례독서 엔트리를 이름으로 나열하는 모든 자리**에서는 표시 계층이 라벨을 조합한다:

- **라벨 = `title` (+ 주기 라벨) (+ 트랙 이름)**: `reading_track`이 비-null이면 반드시 트랙을 함께 적는다. 트랙 이름은 독서 카드와 같다(2026-11-05). 예: `연중10주 (가해, 연속 독서)` / `연중10주 (가해, 복음 주제)`. 이 규칙이 없으면 트랙 1·2가 같은 이름으로 표시돼 구분할 수 없다.
- 적용 자리: **캘린더 목록(아젠다) 뷰**에서 하루의 독서 세트를 나열할 때, **검색 결과 카드**. (월간·주간 셀은 대표 교회력일명만 — 트랙 구분은 셀에 넣지 않고 독서 뷰의 독서 카드가 담당. 전례독서 목록도 이름만 적고, 누른 뒤 제목 아래 줄과 독서 카드가 주기와 트랙을 보인다 — 2026-11-04.)
- **독서 뷰 본문 제목에는 트랙을 표시하지 않는다**: 트랙 선택은 독서 카드가 담당하므로 본문 제목까지 반복하지 않는다.
- 검색 결과에서 같은 교회력일의 두 트랙이 모두 매치되면 한 카드로 묶고 매치된 트랙을 표기(예: "연속 독서, 복음 주제 포함"), 한 트랙만 매치되면 그 트랙을 함께 적는다(예: "복음 주제에 포함") — 질의한 성구가 어느 트랙 독서인지가 유용한 정보다.

### 4. 검색 이원화

- **검색 화면 상단에 탭**: `[성서 본문 | 전례독서]`. URL `?mode=lectionary`(기본 bible) — ADR-031 탭 복원·공유 일관성을 위해 상태를 URL에 인코딩(ADR-033과 동일 원칙). `search.js renderSearchView/renderSearchResults`에 mode 분기; lectionary 모드에서는 책 픽커 대신 안내 placeholder("교회력일 이름 또는 창세 1:1").
- **워커 확장**(`search-worker.js`): `{type:"search", mode:"lectionary", q}` — ① 장절 질의면 기존 `tryVerseRef`(보강된 별칭 포함)로 파싱 후 `search-lectionary.json`의 `cov` 스캔 → 포함하는 교회력일 목록, ② 아니면 `names` 부분 문자열 매치(별칭 포함). 결과 카드 = 교회력일 라벨 + 매치 슬롯 표시 + `/lectionary/d/<slug>` 링크.
- 기존 성서 검색 경로(청크·RLE·`in:` 토큰)는 무변경.

### 5. SW·캐시

`sw.js cacheNameFor`에 `/data/lectionary/` → DATA_CACHE 라우팅 추가. 무효화는 bible-manifest 편입(ADR-037 §7)으로 ADR-021 흐름 자동.

## 검토한 대안

버린 선택지는 여기에 「날짜 · 이유 · 근거 · 재검토 조건」과 함께 남긴다(설계서 §1.4 편집 원칙).

### 캘린더 탭 배치
- **A. 홈 옆 두 번째 신규 탭 (채택, 사용자 결정)**: 노트 탭은 보존(나중 부활). 노트가 숨김 상태라 실표시 4탭 유지.
- B. 노트 탭 자리 대체 — 노트 부활 시 재배치 필요. 채택 안 함.

### `/lectionary` 탭 분류
- **A. 캘린더 탭 (채택)**: 날짜 탐색의 하위 화면.
- B. 홈 탭(ADR-035 `/read` 선례) — 봉독 맥락은 같으나 진입·복귀 동선이 캘린더. 채택 안 함.

### 독서 뷰 URL
- **A. 날짜 기준 + 슬러그 보조 (채택)**: 공유 안정 + 검색 착지 모두 해결.
- B. 슬러그 단독 — "오늘의 독서" 진입마다 절기 위치 계산 후 리다이렉트 필요. 채택 안 함.

### 검색 이원화 UI
- **A. 검색 화면 상단 탭 (채택, 사용자 결정)**: 한 화면에서 축 전환.
- B. 별도 검색 뷰(/calendar 내 검색) — 검색 동선 분산. 채택 안 함.

### 선택 봉헌 · 옮겨진 축일의 표시
- **A. 두 독서를 선택지로 나란히 (채택 2026-09-19, 사용자 확정)**: 본 ADR §3.
- **B. 앱 설정으로 옮길지 정한다**: 채택 안 함 2026-09-19 · 이유: 옮길지는 대개 지역 교회의 사제가 정하는데 독자는 그 결정을 모를 수 있다 · 재검토: 본당 설정이 생기면(설계서 미결15 — 엔진의 `activated` 계약은 그때를 위해 남긴다).
- **C. 기본 독서 + 대안 링크(한쪽을 기본으로 깔고 다른 쪽은 링크로)**: 채택 안 함 2026-09-19 · 이유: B 와 같다 — 독자가 사제의 결정을 모를 수 있으므로 숨긴 쪽이 그날의 실제 전례일 수 있다 · 재검토: B 와 같다.
- 「`official` 만 / 후보 전부」 설정 — 채택 안 함 2026-09-17 → ADR-036 「검토한 대안 — 밀린 독서의 노출」.

### 병기 색의 자리
- **A. `colors` 배열을 새로 둔다 (채택 2026-10-10, 사용자 결정)**: 본 ADR §3, 설계서 §5.5. `color`는 그날의 대표색 하나, `colors`는 그날의 병기 목록(병기가 없으면 `[color]`)이다 — 사계재 날의 색(설계서 미결26)이 어느 모델로 닫히든 같은 구조로 담을 수 있어 골랐다. 그 미결은 모델 (b)로 닫혔다(2026-10-10): 격자가 지정 전례일인 사계재 날의 `color`는 절기색이 아니라 자이고, 축일이 지정 전례일이면 `color`는 축일 색 그대로 `colors`가 자를 병기한다(값의 규칙은 → 설계서 R-6.4-ember-color). 픽스처 README가 이미 `colors` 키로 병기 기대값을 적고 있었다.
- **B. `colorAlt` 를 병기 둘째 색으로 재사용**: 채택 안 함 2026-10-10 · 이유: `colorAlt` 는 데이터 `color_alt` 와 같은 뜻(선택 대체색 — 대림의 청색, 대림 3주일과 사순 4주일의 장미색)이라 한 필드가 두 뜻을 갖게 되고, 대림, 성모 날의 병기처럼 대체색과 병기 색이 한 날에 함께 필요하면 담을 자리가 없다. 병기가 셋 이상이면(사계재 + 축일 + 절기) 아예 못 담는다 · 재검토: 없음.
- **C. 정하지 않고 `colorAlt`, `colors` 를 다 열어 둔다**: 채택 안 함 2026-10-10 · 이유: 타입이 결정을 미루는 대신 값을 쓰는 단계(A2, A3)가 어느 쪽을 읽을지 모호해진다 · 재검토: 없음.

### 구현 순서
- **A. 렌더 기반 → 독서 뷰 → 캘린더 탭 → 검색 (채택 2026-07-27)**: 본 ADR 「후속」.
- **B. A2(캘린더 탭) → A3(독서 뷰) → A4(검색)(원안)**: 채택 안 함 2026-07-27 · 이유: 캘린더 셀이 전부 `/lectionary/…` 로 링크하므로 캘린더를 먼저 내보내면 배포본에 죽은 링크가 생기고, 계응 시편을 그리지 못하면 독서 뷰의 시편 슬롯이 성립하지 않는다 · 재검토: 없음.

### A3 와 A2 사이의 진입점
- **A. URL 과 탭 분류만 (채택 2026-10-12, 사용자 확정)**: 캘린더 탭(A2)이 설계된 진입이고 바로 다음 PR 이다. 그사이 홈에 임시 카드를 두면 A2 에서 다시 걷어야 한다.
- **B. 홈 책 목록에 「오늘의 독서」 카드**: 채택 안 함(잠정) 2026-10-12 · 이유: 홈 화면 변경이 내비, 접근성 e2e 를 건드리고 A2 뒤 제거 비용이 든다 · 재검토: A2 가 늦어지면.
- **C. 캘린더 탭 버튼만 먼저(오늘의 독서로)**: 채택 안 함(잠정) 2026-10-12 · 이유: 탭 바 폭, 아이콘, e2e 가 A2 몫이고, 캘린더 아이콘이 독서를 여는 것은 뜻이 어긋난다 · 재검토: 없음.

### 두 독서를 나란히 놓는 방식
- **A. 전례일 스위처로만 고른다 (채택 2026-11-03, 사용자 결정)**: 본 ADR §3 「구현」. 상태 표시가 옮겨 온 날, 옮겨 지킬 수 있음을 보인다.
- **C. 카드 둘 + 본문 하나(2026-10-12부터 11-03까지)**: 채택 안 함 2026-11-03 · 이유: 칩으로 이미 고를 수 있어 같은 선택이 두 번 보였다(사용자 결정). 카드에만 있던 설명(「이날의 평일 독서」, 「오는/지난 주일(날짜)로 옮겨 지키는 경우」 — 엔진 `optionalDestOf`로 계산)과 「공식」 표지가 없어졌다 · 재검토: 그 설명이 필요하다는 요청이 있으면. 2026-11-06에 설명만 요청되어 카드 없이 줄의 상태 표시와 제목 아래 문장으로 되살렸다(§3 「두 독서는 전례독서 목록으로 고른다」).
- **B. 두 본문을 동시에 그린다**: 채택 안 함(잠정) 2026-10-12 · 이유: 길이가 두 배이고 세트, 트랙, 본기도 대체안 축과 곱해져 상태가 늘어난다 · 재검토: 사용자가 비교 봉독을 원하면.

### 본기도 열거 범위
- **A. 고른 전례일의 본기도만 (채택 2026-10-12, 사용자 결정)**: 본 ADR §3 「구현」. 다른 전례일의 본기도는 그 전례일을 눌러 본다. 기본 독서가 평일인 성인 축일의 날은 예외로, 평일 본기도 다음에 그 성인의 본기도를 잇는다(2026-11-03, 사용자 결정).
- **B. 같은 날 함께 지키는 전례일(`proper`, `transferred_in`, `commemorated`)의 본기도를 뒤따라 열거**: 채택 안 함 2026-10-12(PM 잠정안이었다) · 이유: 사용자 결정 — 한 화면에 한 전례일의 본기도만 · 재검토: 사제가 「당일 + 성인축일 본기도 열거」를 요구하면(ADR-036 §3 의 전제).
- **C. 후보 전부(밀린, 옮겨 간, 옮겨 지키지 않는 선택 봉헌, 사계재 포함)**: 채택 안 함 2026-10-12 · 이유: 그날 드리지 않는 본기도까지 열거된다 · 재검토: 없음.

### 트랙 기억의 단위
- **A. 마지막 선택 하나를 날짜, 해와 무관하게 기본값으로 (채택 2026-10-13, 사용자 결정)**: 본 ADR §3, 「구현」.
- **B. 전례년마다 따로 기억(`{"<전례년>": 1|2}`) — 그해 첫 선택이 그해의 기본값**: 채택 안 함 2026-10-13(#346 이 잠시 구현했다) · 이유: 사용자 결정 — 「한번 선택하면 계속 일관성 있게 같은 트랙이 기본값」. 해가 바뀔 때마다 독서 1 로 돌아가 다시 골라야 했다 · 재검토: 해마다 트랙을 바꿔 쓰는 교회 관행이 확인되면.
- **C. 부활주일 같은 날의 트랙도 같은 기억을 쓴다**: 채택 안 함 2026-11-05 · 이유: 사용자 결정 — 연중 트랙은 구약 연속 독서와 복음 주제 가운데 고르는 것이고, 부활주일의 뒤쪽 트랙은 구약을 먼저 읽고 사도행전을 둘째로 읽는 것이라 뜻이 다르다. 같은 기억을 쓰면 연중에 복음 주제를 고른 사람에게 부활주일의 뒤쪽 트랙이 먼저 보인다 · 재검토: 없음.

### 전례시편 복사의 출처 · 표기
- **A. 출처는 「(대한성공회 기도서)」, 전례 표기 ◯, ¶, 「(N)」은 남긴다 (채택 2026-10-13, 사용자 결정)**: 본 ADR §3 「구현」.
- **B. 출처 괄호 없이 「전례시편 23:1-2」만**: 채택 안 함 2026-10-13(자체 리뷰의 잠정안이었다 — 「(공동번역성서)」가 틀려서 뺐다) · 이유: 사용자 결정 — 번역을 밝힌다 · 재검토: 없음.
- **C. 전례 표기를 복사에서 뺀다**(`docs/known-issues.md` §4 의 다른 갈래 — 제거 목록에 세 클래스) — 채택 안 함 2026-10-13 · 이유: 사용자 결정 — 「모두 표시하는 게 활용도가 높을 것」(주보, 전례 용도) · 재검토: 일반 독자용 복사를 따로 요구하면.

### 반절의 경계
- **A. 반절마다 경계를 표로 정의한다 (채택 2026-10-22, 사용자 결정)**: 본 ADR §3 「구현」. 사용자가 「전례독서 본문에서 '상', '하'가 있는 부분에 대해 각각 어떤 줄들을 가리키는지 줄 범위 값을 정의해 사용하는 건 어때?」라고 제안했다. 한 줄 절도 줄 안에서 나누고(권장안은 절 전체 유지였다), 기준은 서울교구 게시글이다.
- **B. 그 절이 정확히 두 줄이면 한 줄을 고른다**: 2026-10-13(자체 리뷰). 채택 안 함 2026-10-22 · 이유: 추측 규칙이라 전례독서의 반절 참조 59곳 가운데 한 줄 절 33곳과 세 줄 이상 절 14곳은 절 전체를 그렸다(「집회 51:12하-20상」의 20상은 게시글이 20절의 앞 두 줄만 싣는데 네 줄을 다 그렸다). 복사 출처도 정수 구간이라 「35하」를 「35」로 적었다 · 재검토: 없음.

### 옮겨 실린 절만 고른 복사의 출처
- **A. 본래 장으로 — 「이사야 41:6-7」 (채택 2026-10-21, 사용자 결정)**: 본 ADR §3 「구현」. 화면의 절 번호 표시(「41:6」)와 같다. 41장에는 6-7절이 없다(40장으로 옮겨 실렸다). 장 본문 복사와 절 선택 복사가 같게 적는다. 해당 절은 네 곳이다(이사 40장의 41:6-7, 욥 27장의 24:18-24, 잠언 5장의 6:22, 호세 14장의 13:14).
- **B. 열린 장으로 — 「이사야 40:6-7」**: 채택 안 함 2026-10-21 · 이유: 40장의 다른 본문을 가리킨다. #346 머지 전 검토(2026-10-14)에서 정한 규칙의 결과였다 · 재검토: 없음.

### 짝지어진 독서와 본기도의 선택
- **A. 전례독서 목록의 줄로 함께 (채택 2026-11-05, 사용자 결정)**: 본 ADR §3 「구현」. 독서 세트와 본기도가 같은 제목으로 1:1 짝지어지는 날(5.1, 사계재 금요일)만이고, 세트마다 한 줄이다. 줄을 누르면 그 세트의 제목이 머리의 제목이 되어, 무엇을 골랐는지 제목에 보인다. 「또는」 독서 1, 2와 본기도 1, 2, 3처럼 제목으로 구별되지 않는 대안은 여전히 따로 고른다.
- **B. 「독서 · 본기도」 단추 하나로 함께 (2026-10-13부터 11-05까지)**: 채택 안 함 2026-11-05 · 이유: 제목이 「동계재」에 머물러 고른 세트의 이름이 제목에 없고, 대안 세트와 본기도 대체안을 탭에서 옮긴 뒤 이 탭 단추만 남았다 · 재검토: 없음.
- **C. 독서 카드 두 장**: 채택 안 함 2026-11-05 · 이유: 카드는 본기도 아래에 있어 위의 본기도를 아래에서 바꾸게 되고, 제목도 따라가지 않는다 · 재검토: 없음.
- **D. 「대안 독서」, 「본기도」 세그먼트를 따로**: 채택 안 함 2026-10-13(자체 리뷰가 둔 안이었다) · 이유: 사용자 결정 — 교차 조합(사도 축일 독서 + 노동자의 날 본기도)이 없으므로 두 번 누르게 할 까닭이 없고, 한쪽만 바꾸면 쓰지 않는 조합이 화면에 생긴다 · 재검토: 교차 조합을 쓰는 사례가 확인되면.

### 대안 세트 세그먼트 위의 글자
- **A. 달지 않는다. 독서와 본기도를 함께 고르는 단추만 「독서 · 본기도」 (채택 2026-11-04, 사용자 결정)**: 본 ADR §3 「대안 세트·트랙 전환」. 2026-11-05에 대안 세트의 세그먼트를 독서 카드로, 이 단추를 전례독서 목록의 줄로 바꿔 세그먼트도 글자도 남지 않았다(「검토한 대안 — 짝지어진 독서와 본기도의 선택」).
- **B. 「대안 독서」 (A3부터 2026-11-04까지)**: 채택 안 함 2026-11-04 · 이유: 단추 이름(「독서 1 · 2」, 「…로 지킬 때」)과 겹치고, 2026-11-03에 트랙 세그먼트 위의 「독서」 글자를 같은 이유로 뺐다. 2025-2027년에 대안 세트 세그먼트와 트랙 세그먼트가 한 화면에 함께 나오는 날은 없어 글자 없이도 헷갈리지 않는다 · 재검토: 두 세그먼트가 한 화면에 함께 나오는 날이 생기면.
- **C. 글자를 빼고 단추 이름을 두 세트가 다른 곳으로(「시편 100 · 시편 95:1-7」)**: 채택 안 함 2026-11-04 · 이유: 무엇이 다른지 바로 보이지만, 세트끼리 다른 곳이 하나가 아닌 날도 있어 단추 이름을 정하는 규칙을 새로 만들어야 한다 · 재검토: 사용자가 단추 이름만으로 세트를 가리기 어렵다고 할 때.

### 대안 세트의 표시
- **A. 「또는」과 트랙을 모두 독서 카드 두 장으로 고른다. 접으면 제목 옆 알약이나 번호. 괄호 선택 구절은 바탕에 합쳐 긴 본문 + 〔 〕 (채택 2026-11-05, 사용자 결정. 괄호 선택 구절은 2026-10-12)**: 본 ADR §3 「구현」. 탭이나 토글로는 볼 수 없던 세트의 본문 목록을 고르기 전에 보인다. 항목이 하나인 날도 같은 카드와 알약이라 날마다 조작이 같다.
- **B. 달라지는 항목 수로 나눈다 — 하나면 항목 제목 옆 번호, 둘 이상이면 트랙**: 채택 안 함 2026-11-05(같은 날 먼저 정했다가 화면을 비교하고 바꿨다) · 이유: 사용자 결정 — 항목이 하나인 날도 카드로 고르는 편이 상호작용이 일관된다 · 재검토: 없음.
- **C. 탭, 토글, 알약만 두고 본문 목록은 보이지 않는다(탭 「독서 1 · 2」는 2026-10-12부터 11-05까지)**: 채택 안 함 2026-11-05 · 이유: 사용자 결정 — 어느 모양이든 세트를 이루는 본문이 고르기 전에는 보이지 않는다. 탭은 탭 화면이 없어 어색했다 · 재검토: 없음.
- **D. 여러 항목이 다른 날에도 항목마다 따로 고른다**: 채택 안 함 2026-11-05(대조하며 낸 안이었다) · 이유: 사용자 확정 — 앞쪽끼리, 뒤쪽끼리 읽는 것이 관행이고 섞어서 새 조합을 만들지 않는다. 기도서에는 적혀 있지 않다 · 재검토: 없음.
- **E. 세트마다 「1안 · 2안」 번호 라벨 + `set_note` 캡션 줄**: 채택 안 함 2026-10-12(PM 잠정안이었다) · 이유: 세그먼트만 보고 무엇이 다른지 알 수 없고, 괄호 선택 구절은 본문이 같은데 세트를 둘로 보인다 · 재검토: 없음.
- **F. 괄호 선택 구절 세트를 별도 세트로 두고 짧은 본문을 기본으로**: 채택 안 함 2026-10-12 · 이유: 사용자 결정 — 긴 본문을 중심으로 싣고 짧은 본문이 어디까지인지 주석으로 · 재검토: 없음.

### 다른 성구의 표시
- **A. `--text`에 굵기 500, 같은 성구는 `--text-secondary` (채택 2026-11-05, 사용자 결정)**: 본 ADR §3 「구현」. 네 모양을 캔버스에 나란히 그려 골랐다. 웹 글꼴을 쓰는 기기에서도 500으로 보이도록 글꼴 목록에 500을 더했다.
- **B. 굵기 600**: 채택 안 함 2026-11-05 · 이유: 사용자 결정 — 비교에서 500을 골랐다. 제목 「독서」, 카드 이름과 같은 굵기이고, 웹 글꼴을 쓰는 기기에서는 700으로 보인다 · 재검토: 없음.
- **C. 색 차이만(`--text`와 `--text-secondary`, #478)**: 채택 안 함 2026-11-05 · 이유: 사용자 의견 — 실제 아이폰에서 차이가 약했다 · 재검토: 없음.
- **D. 같은 성구를 `--text-tertiary`로 더 옅게**: 채택 안 함 2026-11-05 · 이유: 사용자가 비교한 안이지만 고르지 않았다. 대비가 라이트 3.07-3.25:1, 다크 2.99-3.24:1로 글자 기준 4.5:1에 못 미친다 · 재검토: 없음.
- **E. 다른 성구에 옅은 바탕**: 채택 안 함 2026-11-05 · 이유: 사용자가 시안 전에 뺐다. 카드 안에 색 덩어리가 생겨 고른 카드의 테두리와 눈길을 다툰다 · 재검토: 없음.

### 고른 카드의 테두리
- **A. `--accent` 60%, 1px (채택 2026-11-05, 사용자 결정)**: 본 ADR §3 「구현」. 카드 바탕과 페이지 바탕 모두에 대비 3:1 이상이다(WCAG 1.4.11).
- **B. `--accent` 50%, 1px**: 채택 안 함 2026-11-05 · 이유: 사용자가 처음 낸 값이지만 라이트에서 2.72:1과 2.56:1로 3:1에 못 미쳐, 60%와 나란히 견준 뒤 60%를 골랐다 · 재검토: 없음.
- **C. `--accent` 100%, 2px (#478)**: 채택 안 함 2026-11-05 · 이유: 사용자 의견 — 제목 글자와 색이 같아 보였다 · 재검토: 없음.

### 본기도 대체안의 표시
- **A. 제목 옆 번호, 고른 번호는 채운 원 (채택 2026-11-05, 사용자 결정)**: 본 ADR §3 「구현」. 「제1독서 1요한 2:22-28」처럼 제목과 같은 줄이라 줄이 늘지 않고, 선택지가 늘 보이며, 한 번 눌러 바꾼다. 번호를 쓰는 대체안의 이름이 2025-2050년에 모두 「본기도 N」이라 번호로 줄일 수 있다.
- **B. 세그먼트 「본기도 1 · 2 · 3」 (A3부터 2026-11-05까지)**: 채택 안 함 2026-11-05 · 이유: 기도문 한 문단을 바꾸는 선택에 한 줄을 통째로 썼고(제목과 기도문 사이에 49.5px를 더 썼다), 「본기도」가 제목과 단추에 되풀이됐으며, 좁은 폭과 큰 글자에서 단추 글자가 두 줄로 꺾였다 · 재검토: 없음.
- **C. 기도문 끝의 「또는 본기도 2」 줄**: 채택 안 함 2026-11-05 · 이유: 기도문 위는 가장 조용하지만 본기도 칸 전체 높이가 거의 줄지 않고, 기도문을 다 읽어야 대안이 있는 것을 안다 · 재검토: 없음.
- **D. 제목 메뉴 「본기도 1 ⌄」와 첫 구절 미리 보기**: 채택 안 함 2026-11-05 · 이유: 두 번 눌러야 하고, 해마다 14일 안팎 나오는 드문 조작이라 숨기면 찾기 어렵다 · 재검토: 대체안이 넷 이상인 날이 생기면.
- **E. 고른 번호를 고리로 표시**: 채택 안 함 2026-11-05 · 이유: 사용자 결정 — 채운 원을 골랐다 · 재검토: 없음.

### 캘린더 칸의 링크 이름
- **A. 칸에 보이는 이름(이름 없는 평일은 대표 이름) + 상태 표시, 전례년 표지, 색 이름 (채택 2026-10-15)**: 본 ADR §2 「구현」.

### 전례독서 화면의 위 단계
- **A. 머리에 위 단계 컨트롤을 두지 않는다 — 캘린더로는 캘린더 탭(데스크톱은 헤더의 캘린더 단추) (채택 2026-11-03, 사용자 결정)**: 본 ADR §2 「구현」.
- **B. 그 날짜가 든 달의 캘린더로 가는 꺾쇠 (2026-10-15부터 11-03까지)**: 채택 안 함 2026-11-03 · 이유: 캘린더로는 탭 바의 캘린더 탭이 가고, 머리의 제목 줄은 날짜 이동 줄이 쓴다(사용자 결정). 탭은 그 날짜의 달이 아니라 이번 달로 간다 · 재검토: 독서 화면에서 그 날짜의 달로 바로 돌아갈 길이 필요하다는 요청이 있으면.
- **C. 성서 목록으로 가는 집 단추(A3의 임시 — 캘린더 탭 전)**: 채택 안 함 2026-10-15 · 이유: 독서 화면은 캘린더 탭의 하위다; 다른 탭 머리의 집 단추는 성서 목록을 뜻하고 모바일에서 숨는다 · 재검토: 없음.

- **A. 머리의 제목 자리에 ‹ 날짜 「오늘」 › 를 통째로 (채택 2026-11-03, 사용자 결정)**: 본 ADR §3 「구현」. 스크롤해도 날짜를 보고 하루씩 옮길 수 있다.

- **C. 머리에는 날짜와 「오늘」만, ‹ › 는 본문 맨 위**: 채택 안 함 2026-11-03(같은 결정) · 이유: 하루씩 옮기려면 맨 위로 올라가야 한다 · 재검토: 없음.
- **D. 머리에 날짜와 「오늘」을 더하고 본문의 날짜 줄도 그대로**: 채택 안 함 2026-11-03(같은 결정) · 이유: 맨 위에서 날짜가 두 번 보인다 · 재검토: 없음.

### 머리 날짜의 표기
- **A. 요일 없이 YY.MM.DD (채택 2026-11-05, 사용자 결정)**: 본 ADR §3 「구현」. 폭 320px에 가장 큰 글자(24px)에서도 「오늘」과 한 줄에 들어가, 넘침을 재는 코드가 필요 없다(2026-11-05 Chromium 실측).
- **B. 「2026년 12월 30일 (수)」에서 연도를 자리에 맞게 「2026년」, 「26년」, 생략의 차례로 줄이기 (2026-11-03부터 11-05까지)**: 채택 안 함 2026-11-05 · 이유: 사용자가 요일 없는 짧은 표기로 바꾸었다. 연도를 빼도 넘칠 때는 「오늘」을 날짜 아래 줄로 내리고 날짜를 줄바꿈해야 했다(PR #463 리뷰) · 재검토: 머리에 요일을 다시 보여야 할 때.
- **C. 자리가 모자라면 연도를 바로 생략**: 채택 안 함 2026-11-03 · 이유: 사용자가 중간 단계 「26년」을 더했다 · 재검토: 없음.

### 날짜 이동 줄의 가운데 맞춤
- **A. 날짜나 달의 글자만 가운데, 「오늘」은 그 오른쪽 (채택 2026-11-05, 사용자 결정)**: 본 ADR §3 「구현」. 전례독서의 머리와 캘린더의 달 이동 줄이 같다. 가운데 칸의 양옆을 같게 나누어 「오늘」의 폭이 글자의 자리를 밀지 않는다.
- **B. 글자와 「오늘」을 묶어 가운데 (2026-11-05까지)**: 채택 안 함 2026-11-05 · 이유: 「오늘」의 폭만큼 글자가 가운데에서 왼쪽으로 옮겨 갔다 · 재검토: 없음.

### 캘린더 달의 표기
- **A. 가장 긴 달이 들어가지 않는 폭에서 모든 달을 YYYY.MM으로 (채택 2026-11-05, 사용자 결정)**: 가운데 칸이 12.25rem 이하일 때 CSS 조건(`@container`)으로 「2027.12」를 보이고, 스크린 리더는 「2027년 12월」을 읽는다. 측정 코드가 필요 없다.
- **B. 「2027년 12월」을 그대로 두기**: 채택 안 함 2026-11-05 · 이유: 폭 320px의 기본 글자에서 글자가 가운데에서 18px 벗어나고, 글자 크기 20px 이상에서는 두 줄로 꺾였다 · 재검토: 없음.
- **C. 달마다 들어가는지 재어 그 달만 줄이기**: 채택 안 함 2026-11-05 · 이유: 달을 넘길 때 표기가 「2027년 9월」과 「2027.10」으로 바뀐다 · 재검토: 없음.

### 머리의 전례일 이름
- **A. 고른 전례일의 이름 — 다른 후보를 누르면 제목도 바뀐다 (채택 2026-11-04, 사용자 결정)**: 본 ADR §3 「구현」. 처음에는 그날의 기본 독서를 고른 것이라 고유 독서가 없는 축일의 날은 평일 이름이다. 캘린더 칸은 그대로 지정 전례일 이름이다. 2026-11-03 첫 구현도 이 안이었는데, 그때는 고른 칩이 같은 일을 한다고 보아 아래 C로 되돌렸다.
- **B. 지정 전례일의 이름(A3부터 2026-11-03까지)**: 채택 안 함 2026-11-03 · 이유: 고유 독서가 없는 축일의 날에 성인 이름 아래 평일 독서가 보여, 성인의 독서처럼 읽혔다 · 재검토: 없음.
- **C. 그날의 기본 독서의 이름, 칩을 눌러도 그대로(2026-11-03부터 11-04까지)**: 채택 안 함 2026-11-04 · 이유: 12.24에 성탄 밤을 눌러도 제목이 「성탄 1일 전」이라 제목과 본문이 어긋났다. 이 안의 근거는 어느 독서가 보이는지를 고른 칩이 보인다는 것이었는데 칩이 없어졌다 · 재검토: 없음.

### 기리는 성인의 표시
- **A. 칩이 아니라 머리 제목 아래 회색 작은 글씨의 이름 줄, 성인마다 한 줄 (채택 2026-11-03, 사용자 결정)**: 본 ADR §3 「전례일 스위처」. 기념만 하는 성인은 고유 독서가 있어도 이 줄뿐이다(2026-11-04).
- **B. 칩(A3부터 2026-11-03까지)**: 채택 안 함 2026-11-03 · 이유: 기본 독서를 볼 때 성인 본기도가 이미 이어지고, 공통 독서는 당분간 보이지 않는다 · 재검토: 공통 독서를 다시 보이면.
- **C. 고유 독서가 있는 기념만 하는 성인은 칩으로 남긴다(2026-11-03부터 11-04까지)**: 채택 안 함 2026-11-04 · 이유: 기념만 하는 날에 눌러서 화면을 옮길 까닭이 없다(사용자 결정). 11-03에는 이 성인들(12.29 토마스 베켓, 7.26 안나와 요아킴, 2027-08-29 세례 요한의 참수, 2028-01-02 바실과 그레고리)의 고유 독서를 그날 보려고 칩을 남겼다. 이제 그 독서는 그날 화면에서 볼 수 없고, 그 축일을 지키는 해의 날짜에서 본다 · 재검토: 그날 그 독서를 찾는 요청이 있으면.

### 여러 성인의 본기도와 색
- **A. 유형이 같으면 공통 본기도 하나에 이름을 모으고, 다르면 유형 정의 차례로 잇는다. 색이 다르면 「적색 또는 백색」 (채택 2026-11-03, 사용자 결정)**: 본 ADR §3 「구현」.
- **B. 지정 전례일인 성인 하나의 본기도만, 색은 그 성인의 색(2026-11-03 첫 구현)**: 채택 안 함 2026-11-03 · 이유: 다른 성인의 본기도가 빠졌다(2.14 키릴과 메토디우스, 6.9 콜룸바, 12.31 위클리프) · 재검토: 없음.
- 차례는 처음에 「순교자, 신학자, 목자」로 정했다가, 유형을 열거한 차례(`commons.json`)를 따르기로 했다(같은 날). 그래서 성직자가 신학자보다 앞이다.

### 성인 공통 독서의 표시
- **A. 당분간 보이지 않는다 — 공통 독서만 있는 후보는 전례독서 목록에 없다 (채택 2026-11-03, 사용자 결정 「당분간」)**: 본 ADR §3. `lectionary.js HIDE_COMMON_READINGS` 하나로 켜고 끈다.
- **B. 칩으로 고르면 공통 독서(A3부터 2026-11-03까지)**: 보류 2026-11-03 · 이유: 사용자가 당분간 기본 독서만 보이기로 했다 · 재검토: 사용자가 공통 독서를 다시 보이기로 하면 상수를 끄고 이 결정을 고친다.

### 후보가 하나뿐인 날의 칩 줄
- **A. 그리지 않는다 (채택 2026-11-03, 사용자 결정)**: 본 ADR §3 「전례일 스위처」.
- **B. 칩 하나라도 그린다(A3부터 2026-11-03까지)**: 채택 안 함 2026-11-03 · 이유: 고를 것이 없고, 칩의 이름이 머리의 전례일 이름과 같다 · 재검토: 없음.

### 본문 없는 후보와 같은 본문의 격자
- **A. 고를 수 있게 두지 않는다. 본문 없는 날은 이름 줄에 이름만 한 줄 (채택 2026-11-04, 사용자 결정)**: 본 ADR §3 「전례일 스위처」. 독서도 본기도도 없는 후보, 그리고 이름 있는 후보와 독서, 본기도가 똑같은 격자다.
- **B. 후보 전부를 칩으로(A3부터 2026-11-04까지)**: 채택 안 함 2026-11-04 · 이유: 왕이신 그리스도 주일의 「연중 34주일 (가해)」처럼 누르면 빈 화면이거나, 대림1주일의 「대림 1주일 (나해)」처럼 같은 화면이었다. 후보 전부를 보이는 계약(ADR-036 §7)이 막으려던 것은 밀린 독서를 놓치는 일이고, 감춘 칩에는 볼 독서가 없거나 다른 칩과 같다 · 재검토: 본문 없는 후보에 고를 본문이 생기면(데이터가 본기도나 독서를 더하면 전례독서 목록으로 돌아온다).
- **C. 빈 격자 칩만 감춘다(처음 제안)**: 채택 안 함 2026-11-04 · 이유: 사용자가 본문 없는 날 넷도 칩 대신 이름 줄로 옮기고, 대림 1주일의 두 칩도 그날 기본 독서가 그해의 대림 1주일 독서라 필요 없다고 정했다 · 재검토: 없음.

### 병자를 위한 기도일의 독서

- **A. 고유 독서가 있는 축일로 넣는다**: 채택 안 함 2026-11-07 · 이유: 사용자 결정. 평일에 이 독서가 기본 독서가 되고 평일 독서가 설정 「대체 독서 표시」에 가려져, 원하는 것과 순서가 반대다 · 재검토: 2.11의 본문을 그날의 기본 독서로 정하면 `alternate_readings` 표시만 뺀다.

### 옮겨 간 축일의 표시
- **A. 원래 날짜에서 고르게 두지 않고 제목 아래 문장으로 알린다 (채택 2026-11-04, 사용자 결정)**: 본 ADR §3 「전례일 스위처」.
- **B. 흐린 칩 「성 니콜라 · → 12월 7일」(A3부터 2026-11-04까지)**: 채택 안 함 2026-11-04 · 이유: 사용자 결정. 그날 지키지 않는 축일이고, 그 독서는 옮겨 간 날에서 볼 수 있다 · 재검토: 본당 설정이 생기면(설계서 미결15).

### 공통 독서의 분류 라벨
- **A. 달지 않는다 (채택 2026-11-03, 사용자 결정)**: 본 ADR §3. 머리의 제목이 어느 전례일의 독서인지 보인다.
- **B. 대안 독서 세그먼트, 본문 제목, 본기도에 캡션(「순교자 공통 독서」, 「순교자 공통 본기도」) (2026-09-17부터 11-03까지)**: 채택 안 함 2026-11-03 · 이유: 같음 · 재검토: 공통 독서를 그 성인의 고유 독서로 잘못 아는 사례가 보이면.
- **C. 본문 제목은 빼고 공통 독서일 때만 한 줄을 남긴다**: 채택 안 함 2026-11-03(같은 결정) · 이유: 같음 · 재검토: B와 같다.

### 응답 반행의 색
- **A. 선창과 같은 색, 선창 끝의 ◯ 가 경계 (채택 2026-11-03, 사용자 결정)**: 본 ADR §3. 장 화면(`/lps`, `/cant`)과 영광송도 같다.
- **B. 흐린 색(`--text-secondary`) (2026-07-27부터 11-03까지)**: 채택 안 함 2026-11-03 · 이유: 한 절 안에서 줄마다 글자 색이 달라 보였다(사용자 결정) · 재검토: 없음.

### 저녁 전례(성 토요일의 부활밤 · 성탄 밤)
- **A. 저녁 전례는 그날의 대표가 아니라 후보 목록 끝 — 성 토요일의 대표는 성 토요일, 성탄 밤은 12.24 저녁 (채택 2026-10-15, 사용자 결정)**: 본 ADR §3 「구현」, 설계서 R-6.1-evening.
- **B. 지정 전례일은 부활밤, 그날 색 홍(보호가 덮는다)**: 채택 안 함 2026-10-15(2026-09부터 10-15까지의 잠정) · 이유: 머리 제목, 캘린더 칸은 「부활밤」인데 색은 적색이라 어긋나고, 2024-2026 책자는 낮을 「성(주간) 토요일 · 감사성찬례 없음」, 부활밤을 따로 적는다 · 재검토: 없음.
- **C. 시각(일몰 또는 18시 이후)에 따라 저녁 전례를 먼저 보이고 색을 바꾼다**: 보류(2026-10-15 — 사용자가 「하나의 방법」으로 제안, 결정 전), 걸리는 점: 같은 날짜 주소가 시각에 따라 다른 화면이 된다(공유, 뒤로 가기 — §3의 「트랙은 주소에 언제나 적는다」와 같은 문제), 일몰은 위치가 필요하다(권한) · 재검토: 「오늘」 화면에만 적용하고 고른 후보를 주소(`?obs=`)에 적는 방식을 사용자가 원하면.
- **D. 부활밤은 그날의 대표, 색에서만 빠지고 옮김 계산에서는 성 토요일의 주요축일을 민다(#349 첫 구현)**: 채택 안 함 2026-10-15 · 이유: 그날 판정(생략 축일을 민 것 = 보호 기간)과 옮김 계산(부활밤)이 다른 모델이 되었고(PR #349 리뷰), 사용자 「성 토요일은 부활밤에 밀리지 않아. 성 토요일은 무조건 토요일에 있어야 하고, 부활밤을 칩으로 표현하면 될 것 같은데?」 — 성 토요일이 데이터 prec 1(data#32)로 그날을 지키고 부활밤은 어떤 판정에도 들지 않는다(설계서 R-6.1-evening) · 재검토: 없음.

### 전례일 스위처의 표시
- **A. 제목 아래 전례독서 목록 — 다른 후보를 한 줄씩 링크로, 제목은 고른 이름 (채택 2026-11-04, 사용자 결정)**: 본 ADR §3 「전례일 스위처」. 후보가 여럿인 날 전체(2025-2050년에 1,617일)에 쓴다. 기리는 성인, 기념일, 본문 없는 날, 옮겨 간 축일을 칩에서 제목 아래 줄로 옮겨 온 방향을 잇는다.
- **B. 칩 줄(A3부터 2026-11-04까지)**: 채택 안 함 2026-11-04 · 이유: 칩이 제목과 같은 글자를 되풀이했고, 긴 이름을 말줄임으로 잘랐다. 사용자는 앞으로 칩을 줄이거나 없앨 생각이다(`docs/topics/design-system.md` 「확정 사실」) · 재검토: 없음.
- **C. 제목 안 링크 「성탄 1일 전 / 성탄 밤」(사용자 첫 제안)**: 채택 안 함 2026-11-04 · 이유: 「옮겨 지킬 수 있음」을 적을 자리가 없고, 후보가 셋이면 제목이 두 줄로 늘어나며, 「/」가 한 날의 두 이름처럼 읽힐 수 있다. 시안을 견주어 사용자가 A를 골랐다 · 재검토: 없음.
- **D. 종류 세그먼트 「낮, 저녁」, 「축일, 평일」**: 채택 안 함 2026-11-04 · 이유: 누르기 전에는 다른 전례의 이름이 보이지 않고, 종류 이름의 규칙을 새로 정해야 하며, 독서와 본기도 세그먼트와 위아래로 겹친다 · 재검토: 없음.
- **E. 제목 메뉴와 바텀 시트**: 채택 안 함 2026-11-04 · 이유: 눌러야 후보가 보여 12.24의 성탄 밤이나 밀린 독서를 놓치기 쉽다(ADR-036 §7) · 재검토: 후보가 넷 이상인 날이 생기면.
- **F. 기념만 하는 후보도 링크 줄로 둔다(같은 날 첫 구현)**: 채택 안 함 2026-11-04 · 이유: 그날 지키지 않는 독서로 화면만 옮겨 갔다(사용자 결정, 위 「기리는 성인의 표시」 C). 지역 축일(삼일절, 광복절)만 링크로 남겼다 · 재검토: 그날 그 독서를 찾는 요청이 있으면.
- **G. 기념만 하는 후보에 「· 기념만」 문구를 단다(A3부터 2026-11-04까지)**: 채택 안 함 2026-11-04 · 이유: 사용자 결정 · 재검토: 없음.

### 전례일 칩 줄의 배치
- **A. 줄바꿈 — 칩을 낱말처럼 이어 놓고 줄이 차면 다음 줄로 (채택 2026-10-15, 사용자 결정)**: 2026-11-04에 칩 줄과 함께 없어졌다(위 「전례일 스위처의 표시」). 전례독서 목록도 모든 후보가 늘 보인다.
- **B. 가로 스크롤(스크롤바 숨김 — A3 구현)**: 채택 안 함 2026-10-15 · 이유: 휴대폰에서 줄 끝의 칩이 숨는다(성 토요일의 「부활밤 · 저녁」이 320px 에서 12px, 생략 성인이 있는 해는 0px — PR #349 리뷰의 브라우저 실측) · 재검토: 없음.
- **C. 칩 줄은 두고 머리에 「오늘 저녁 · 부활밤 →」 줄**: 채택 안 함 2026-10-15 · 이유: 저녁 전례만 풀고 생략 성인처럼 다른 숨은 칩은 그대로 둔다 · 재검토: 줄바꿈으로도 저녁 전례를 놓치는 사용자가 있으면.
- **D. 저녁 칩을 대표 바로 다음으로**: 채택 안 함 2026-10-15 · 이유: 생략 성인이 맨 앞에 붙는 해(2042)에는 320px 에서 다시 거의 가려져 흐린 칩을 줄 끝으로 보내는 규칙까지 필요하다 · 재검토: 없음.

### 모듈 로드
- **A. 그 화면에 처음 갈 때 불러온다 — 동적 `import()`, 필요한 모듈을 한꺼번에 요청 (채택 2026-10-17, 한꺼번에 2026-10-18, 사용자 결정 「한꺼번에 받기로 진행」)**: 본 ADR §2 「구현」.
- **B. 모든 화면에서 받는다 — `index.html` 태그 + `routing.js` 정적 import(A3, A2 1단계의 구현)**: 채택 안 함 2026-10-17(2026-10-12부터 10-17까지의 방식 — 2026-10-15 사용자 승인 「지연 로드는 A2 뒤 별도 PR」) · 이유: 첫 방문의 부팅 경로가 셋(gzip 약 70KB — 부팅 JS의 약 21%)을 받아 느린 4G에서 첫 화면이 0.39초 늦었고, 교회력 기능(주간, 목록, 검색 이원화, 기도서)이 늘수록 그 경로가 커진다. 처음 이유로 든 「성서만 읽는 세션도 앱을 열 때마다 셋을 해석한다」는 재 보니 재방문의 부팅에서 측정 오차 안이었다(2026-10-17 — DOMContentLoaded −2ms, 스크립트 −4ms, CPU 4배 저속) · 재검토: 첫 방문의 캘린더 지연(아래 C)이 문제가 될 때 C부터 — 태그, 정적 import로 되돌리지는 않는다.
- **C. A + 첫 화면 뒤 한가할 때 미리 받기**: 보류 2026-10-18(같은 결정 — 사용자가 A를 골랐다), 걸리는 점: 첫 방문의 캘린더 지연은 대부분 없어지지만, 성서만 읽어도 셋을 싣는다(JS 메모리 약 53KB) · 재검토: 첫 방문에 캘린더를 바로 여는 사용자가 많다고 보이면.
- **D. 차례로 받기 — 캘린더 모듈을 받은 뒤 브라우저가 그 import를 찾아 받는다(2026-10-17 첫 구현)**: 채택 안 함 2026-10-18 · 이유: 첫 방문에 왕복이 한 번 더 든다 — 캘린더 탭 → 표 느린 4G +676ms(한꺼번에 +527ms), 빠른 4G +197ms(+114ms) · 재검토: 없음.
- **E. 주소로 바로 들어오면 `<head>`에서 `modulepreload`로 미리 받기(2026-10-18 구현, 같은 날 되돌림)**: 채택 안 함 2026-10-18(PR #355 2회차 리뷰, 사용자 결정 「미리 받기를 되돌린다」) · 이유: 바로 열기의 지연은 거의 없어졌지만(느린 4G 캘린더 +198 → +51ms, 전례독서 +158 → −6ms — 1회차 리뷰 뒤 측정), WebKit(Playwright 26.4 실측)은 미리 받기가 한 번 실패하면 그 탭에서는 새로 고쳐도 다시 받지 않아 「다시 불러오기」가 풀지 못했고(새 탭에서만 열림), 성공한 미리 받기도 새로 고칠 때 재검증 없이 다시 써 배포 뒤에도 옛 화면 모듈이 돌았다. 서비스 워커가 없는 WebKit 세션(iOS 인앱 브라우저 등)으로 공유 링크를 여는, 미리 받기가 도우려던 바로 그 경우다(coding-pitfalls §34) · 재검토: WebKit의 미리 받기 캐시가 바뀌거나, 실패해도 탭이 막히지 않는 미리 받기 방법이 확인되면.

### 모듈을 받지 못했을 때
- **A. 그 뷰의 제목, 실패 화면 + 「다시 불러오기」 — 페이지를 새로 고친다 (채택 2026-10-17, 사용자 결정)**: 본 ADR §2 「구현」, DESIGN.md §6 「전체 화면 실패」.
- **B. 자료 실패와 같은 문구 「네트워크 연결을 확인한 뒤 다시 열어 주세요.」, 단추 없이**: 채택 안 함 2026-10-17(사용자 결정 — 셋 가운데 A) · 이유: 브라우저는 실패한 모듈을 새로 고칠 때까지 기억해 화면을 다시 열어도 같은 실패일 수 있다 — 이를 바꾼 HTML 표준 변경(whatwg/html #10327, 2026-07 머지)이 엔진마다 반영 중이다(WebKit 2026-08-19 커밋, Chromium은 런타임 플래그 뒤 — 2026-10-17 확인) · 재검토: 주요 브라우저가 모두 실패를 기억하지 않게 되면.
- **C. 「네트워크 연결을 확인한 뒤 앱을 다시 열어 주세요.」, 단추 없이**: 채택 안 함 2026-10-17(같은 결정), 걸리는 점: 무엇을 해야 다시 열리는지(앱을 완전히 닫았다 열기, 새로 고침)를 독자가 알아야 한다 · 재검토: 없음.

### 실패 화면의 다음 행동
- **A. 자료나 화면 모듈을 받지 못했거나 그리다 오류가 나면 「다시 불러오기」, 날짜를 다시 골라야 하면 「이번 달 캘린더」 — 부제는 그 단추 이름으로 할 일을 말하고, 실패 화면은 `views.js` 하나가 그린다 (채택 2026-10-18, PR #355 리뷰, 사용자 「권장안 수용」)**: 본 ADR §2 「구현」, 본 ADR §3 「실패 · 범위」, DESIGN.md §6 「전체 화면 실패」.
- **B. A2, A3의 방식 — 캘린더는 어느 실패든 「이번 달 캘린더」, 전례독서는 단추 없이 「…골라 주세요」, 「…다시 열어 주세요」**: 채택 안 함 2026-10-18 · 이유: `/calendar/2027-03`의 자료 실패에서 「이번 달 캘린더」는 실패한 3월이 아니라 이번 달로 갔고, 부제가 화면에 없는 컨트롤을 가리켰다(coding-pitfalls §29) · 재검토: 없음.
