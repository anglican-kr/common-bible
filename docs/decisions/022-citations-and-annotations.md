## 맥락

공동번역성서 본문에는 두 종류의 보조 정보가 자연스럽게 따라온다.

1. **인용**: 한 구절이 다른 구절(주로 신약이 구약을, 외경이 구약을)을 그대로 인용하는 경우다. 인쇄 성경은 보통 인용 끝 괄호에 출처를 적는다(`사 53:5`).
2. **주석**: 번역자 주(원문의 뜻, 이문, 문화 배경 등)다. 인쇄본은 어절 옆에 위첨자 표시를 두고 장 끝에 각주를 단다.

지금 데이터 파이프라인(parser.py, split_bible.py)에는 두 정보를 담을 자리가 없다. `source/*.md`도 평문과 운문 블록 인용(`>`)만 표현하고(ADR-006), 본문 밖의 메타정보는 0건이다.

PWA가 Phase 1(읽기 앱)으로 완성된 지금, 이 두 정보를 **독서 몰입을 해치지 않으면서** 데이터와 화면 양쪽에 깔끔하게 얹는 결정이 필요하다.

## 결정

### 1. 마크다운 표현 — 뜻에 가장 맞는 표기

두 정보는 길이, 앵커 단위, 확장성이 다르다. 그래서 「전부 HTML 태그로 통일」하지 않고, 저마다의 모양에 가장 잘 맞는 표기를 쓴다.

**인용 — HTML5 `<cite>` 요소**

```markdown
그가 찔림은 우리의 허물 때문이요 <cite src="이사 53:5">그가 상함은 우리의 죄악 때문이라</cite>
```

- `<cite>`는 HTML5의 시맨틱 인용 요소라 뜻이 정확히 맞는다.
- 마크다운은 raw HTML을 그대로 통과시키므로 기존 parser를 크게 손대지 않아도 된다.
- GitHub PR diff에서 원문이 그대로 보여, 개발을 모르는 검토자(사목, 신학 자문)도 읽을 수 있다.

**주석 — 마크다운 footnote 문법**

```markdown
…그는 갈릴래아[^1-3]로 떠나셨다.

[^1-3]: 갈릴래아는 당시 로마의 직할령이 아닌 분봉왕 헤로데 안티파스의 통치 구역이었다.
```

- 표준 GFM/Pandoc 문법이고, footnote가 곧 주석이라 뜻이 정확히 맞는다.
- 정의를 장 끝(또는 단락 끝)에 모아 두어 본문 흐름이 깨지지 않고, diff가 깔끔하다.

**앵커 지정 — 자동 감지(기본)와 명시(선택)**:

기본은 **자동 감지**다. `[^id]` 표시 바로 앞의 어절(공백으로 나뉜 한 단어)을 앵커로 본다. 가장 흔한 경우다.

여러 어절을 앵커로 잡으려면 **`<note>...</note>`로 감싸 명시한다**.

```markdown
'<note>주님이신 너희 하느님</note>[^4-1]을 경배하고 그분만을 섬겨라.'

[^4-1]: 신명 6:13 에서 인용된 표현.
```

- `<note>`가 감싼 텍스트 전체가 앵커가 된다. 바로 앞 어절의 자동 감지를 대신한다.
- 쓰지 않으면 기존 자동 감지가 그대로 작동한다(하위 호환).
- `<note>`가 닫히지 않으면 parser가 분명한 오류를 낸다(데이터가 조용히 사라지는 것을 막는다). cite와 같은 정책이다.
- 감쌀 어절이 없는 주석(공백이나 빈 `<note>`, 예: 「이 구절에 어떤 사본은 다음을 추가」)은 앱이 절 끝에 ※ 표시를 둔다(§6).

- ID 규칙(두 층):
  - **source 마크다운**: `<장>-<번호>`(예: `1-3`). 책 단위 파일 안에서 하나뿐이어서, 표준 마크다운 footnote가 요구하는 파일 안 ID 유일성을 만족한다. `[^...]` 자체가 footnote 신호라 안의 접두사는 단순한 `<장>-<n>`으로 충분하다.
  - **장 JSON 출력**: 장 단위 파일이라 장 접두사를 떼고 `<번호>`만 문자열로 남긴다(예: `"3"`).
  - 번호는 **장 안에서만 차례로** 매긴다. 장이 바뀌면 1부터 다시 센다. 인쇄 성경의 footnote 관습과 같다.

### 2. `<cite>` 속성 규격

**`src` (필수)** — 인용 출처 위치. 다음 형식을 받는다.

| 형식 | 예시 | 뜻 |
|---|---|---|
| `<short_name_ko> <chap>:<verse>` | `이사 53:5` | 단일 절 |
| `<short_name_ko> <chap>:<v>-<v>` | `이사 53:5-7` | 같은 장 안 절 범위 |
| `<short_name_ko> <chap>:<v>,<v>[,<v>...]` | `판관 13:5, 7` | 같은 장 안 떨어진 여러 절(콤마 뒤 공백 허용) |
| `<short_name_ko> <chap>:<v>-<v>,<v>` | `이사 53:5-7, 9` | 범위와 콤마를 섞음(같은 장) |
| `<short_name_ko> <chap>:<v>,<chap>:<v>[...]` | `다니 9:27, 11:31, 12:11` | 같은 책 안 여러 장을 콤마로. 콤마로 나뉜 부분마다 `<chap>:` 접두사를 선택으로 붙일 수 있다 |
| `<short_name_ko> <chap>:<v>-<chap>:<v>` | `이사 8:23-9:1` | 장 경계를 넘는 범위 |

- `short_name_ko`는 `books.json`의 기존 필드를 그대로 쓴다(예: `창세`, `이사`, `마태`). 따로 약어 사전이 필요 없다.
- 여러 장을 콤마로 이을 때 각 부분은 `<chap>:<v>`나 `<v>`다. `<v>`만 쓰면 바로 앞 부분의 장이 아니라 맨 앞의 시작 장을 따른다. 예: `판관 13:5, 7`은 둘 다 13장이다. `다니 9:27, 11:31`은 9장 27절과 11장 31절이다.
- 장 경계를 넘는 범위와 여러 장 콤마를 섞는 드문 경우(`이사 8:23-9:1, 10:5` 같은)는 1차에서 지원하지 않는다. 필요하면 `<cite>` 둘로 나눈다.
- 처음에는 칩을 누르면 늘 첫 절로 이동하기로 했다(예: `다니 9:27, 11:31, 12:11`이면 `/dan/9#v27`). 지금 칩은 페이지를 옮기지 않고 시트를 연다(§6).
- ADR-003에서 다른 장에 옮겨 실린 절(호세 13:14, 잠언 6:22, 이사 41:6, 1역대 9:33, 욥 26:5, 욥 27)을 인용할 때 `src`는 학문적 출처 그대로 적는다(예: `호세 13:14`). 데이터 검증과 인용 시트는 해당 장 파일에 그 절이 없으면, 같은 책의 다른 장 파일(앞뒤 3장까지)에서 `chapter_ref == <장>`인 절을 더 찾는다. 그래서 공동번역 인쇄본의 실제 배치(예: 13:14가 hos-14 안 5절과 6절 사이)와 학문적 표기가 함께 맞는다. 이 목록은 데이터와 다르다(데이터에는 네 곳, known-issues §11.1).

**`parallels` (선택)** — 같은 내용이 구약 두 곳 이상에 거의 같은 표현으로 나올 때의 병행 참조(parallel reference)다. 인쇄 가톨릭과 성공회 성경의 `출애 20:13(신명 5:17)` 표기와 같다. 첫 출처가 `src`이고, 그다음에 나오는 같은 출처들이 `parallels`다.

형식: `src`와 같은 형식의 인용 위치를 하나 이상, **세미콜론(`;`)**으로 나눈다. 콤마는 같은 책 안의 여러 절을 뜻하므로(`판관 13:5, 7`) parallels 사이의 구분자는 `;`로 분명히 한다. 각 항목 끝에 선택으로 `[전통]` 접미사를 붙여 그 parallel의 사본 전통 라벨을 적을 수 있다(2026-05-31). JSON 스키마는 `parallels: {ref: string, tradition?: string}[]`다.

```markdown
<cite src="출애 20:13" parallels="신명 5:17">"살인하지 못한다."</cite>
<cite src="출애 20:13" parallels="신명 5:17; 마르 12:29">…</cite>  <!-- 다중 -->
<cite src="시편 16:8" parallels="시편 16:8 [칠십인역]; 사도 2:25">…</cite>  <!-- per-parallel tradition -->
```

화면:
- 칩: `(출애 20:13 · 신명 5:17)`(구분자 `·`, Phase 2에서 확정). parallel에 사본 전통이 있으면 그 ref 앞에 붙인다. `(시편 16:8 · 칠십인역 시편 16:8 · 사도 2:25)`
- 시트: 첫 출처와 parallel 본문들을 구분선으로 나눠 모두 보인다. 사용자가 구약 두 곳을 바로 견줄 수 있다. ref마다 머리에 그 ref의 사본 전통 라벨을 함께 보인다.

검증: `parallels`의 각 항목도 `src`와 같은 형식, 약어, 장, 절 범위 규칙을 따른다(`[전통]` 접미사는 ref와 떼어 검증한다). 첫 출처의 `tradition` 속성과 parallel의 `[전통]`은 **따로따로**다. 그래서 한 cite가 src는 마소라, 일부 parallel은 칠십인역인 섞인 표기를 자연스럽게 담는다.

**`tradition` (선택)** — 인용한 사본 전통. 없으면 기본값은 히브리 본문(마소라)이다.

| 권장 어휘 | 뜻 |
|---|---|
| `칠십인역` | LXX(그리스어 구약, 신약 인용 다수의 출처) |
| `마소라` | MT(히브리 본문, 기본값과 같다. 밝혀 적을 때만 쓴다) |
| `불가타` | Vulgate(라틴어 구약) |
| 그 밖 | 저자가 정하는 자유 문자열(`사해사본` 등) |

예시:
```markdown
<cite src="이사 40:3" tradition="칠십인역">"광야에서 외치는 이의 소리…"</cite>
```

용도는 **보여 주기만 하는 메타데이터(display-only)**다. 칩에서 그 ref 앞에 붙여 보인다(`(칠십인역 이사 40:3)`, §6). 이 절의 첫 예시는 뒤에 붙인 표기(`(이사 40:3 · 칠십인역)`)였지만, 구현은 앞에 붙인다. 앱은 공동번역 본문 한 종류만 보여 주므로 tradition은 라우팅에 영향이 없다.

### 3. 절 경계 규칙 — `<cite>` 하나는 한 절 안에서 닫힌다

`<cite>` 태그는 한 절 표시(`[N]`)가 시작된 뒤, 다음 절 표시 전에 열리고 닫혀야 한다. 한 인용이 여러 절에 걸치면 저자가 절마다 `<cite>`를 따로 쓰고 같은 `src` 값을 되풀이한다.

**이유**: parser가 줄 단위 상태 기계(state machine)로 절부터 나누므로, 절 경계를 넘는 `<cite>` 하나는 segment 단위의 뒤처리에서 정규식이 맞지 않게 된다. source에서 닫히지 않은 `<cite>`가 발견되면 `parser.py`가 분명한 오류로 실패해, 데이터가 조용히 사라지는 것을 막는다.

**예시** — 마태 4:15-16이 이사 8:23-9:1을 한 단위로 인용하는 경우:

```markdown
> [15] <cite src="이사 8:23-9:1">"즈불룬과 납달리, 호수로 가는 길,
> 요르단 강 건너편, 이방인의 갈릴래아.</cite>
> [16] <cite src="이사 8:23-9:1">"어둠 속에 앉은 백성이 큰 빛을 보겠고
> 죽음의 그늘진 땅에 사는 사람들에게
> 빛이 비치리라."</cite>
```

두 절에 같은 `src`를 적는다. 화면의 중복 제거 규칙(§6) 때문에 칩은 마지막 절(v16)에 한 번만 보인다.

**절 하나에 정확히 대응시킬 수 없는 경우**: 신약 인용이 구약의 한 절과 정확히 대응하지 않고 풀어 쓴 것이면, 저자는 가장 가까운 구약 위치를 src 하나로 적고 절마다 같은 src를 되풀이한다. 정확한 상호 참조 대응을 데이터에 지우지 않는다.

주석은 원래 어절 단위 앵커라 절 경계를 넘을 일이 없다. 따로 규칙이 필요 없다.

### 4. JSON 스키마 확장

**인용 — segment 단위 `cite` 필드**

기존 `segments[i]`에 선택 필드를 더한다.

```json
{
  "type": "prose",
  "text": "그가 상함은 우리의 죄악 때문이라",
  "cite": "이사 53:5"
}
```

`<cite>`가 segment의 일부만 차지하면, cite가 있는 segment와 없는 segment로 나눈다. 운문(`type: "poetry"`)의 한 행이 인용인 경우도 같다.

**주석 — verse 단위 `notes` 배열**

verse 객체의 선택 필드:

```json
{
  "number": 23,
  "segments": [...],
  "notes": [
    {
      "id": "3",
      "anchor": "갈릴래아",
      "anchor_occurrence": 1,
      "body": "갈릴래아는 당시 로마의 직할령이 아닌…"
    }
  ]
}
```

`anchor_occurrence`는 같은 어절이 절 안에 여러 번 나올 때 몇 번째 것인지 가리킨다(1부터 세고, 기본 1). 화면이 이 값을 무시해도 첫 번째 것에 붙으므로 동작한다.

`body`는 평문 문자열이다. 마크다운 인라인 서식(강조, 링크 등)은 1차 버전에서 지원하지 않는다.

### 5. 같은 절에 인용과 주석이 함께 있을 때

데이터로는 가능하지만 지금 콘텐츠에는 없다. 처음에는 「인용 칩을 본문 끝에 먼저, 그 아래 줄에 주석 단락」이라는 순서 규칙만 정해 두었다. 주석을 장 끝 단락 대신 어절 툴팁으로 바꾸면서(2026-05-24, §6) 주석 단락이 없어져, 칩과 주석이 자리를 다투지 않는다. 둘 다 같은 토글로 켜고 끈다.

### 6. 화면 정책 (Phase 2)

- 토글 하나 **「인용 본문·주석」**이 인용과 주석을 함께 다룬다. localStorage 키는 `bible-cite-show`(기본값 `"1"` = 표시)다. 설정 화면의 라벨은 ADR-023에서 「인용·주석 표시」로 다듬었다.
- **기본값은 ON**이다(Phase 2에서 확정). 이유: 콘텐츠를 쓰는 노력이 사용자 눈에 띄어야 하고, 칩을 눌러도 페이지가 바뀌지 않고 바텀 시트가 열려 읽기를 방해하지 않는다. 사용자는 일부러 끌 수 있다.
- 토글이 꺼지면 본문에 어떤 시각적 표시도 없다. WCAG 2.1 AA와 읽기 몰입 때문이다(절 번호를 aria-hidden으로 둔 결정과 같은 이유).
- 토글이 켜지면(기본):
  - 인용: cite segment 끝에 옅은 회색 칩 `(이사 53:5)`를 둔다. **칩을 누르면 바텀 시트가 열려 인용한 절들을 시트 안에서 보여 준다.** 페이지가 바뀌지 않으므로, 시트를 닫으면 읽던 자리 그대로다. 본문 글자에는 링크 스타일(밑줄, 색)을 쓰지 않는다.
    - **칩은 `<span role="button" tabindex="0">`으로 그린다(2026-05-29).** 브라우저가 `<button>`을 `display:inline-block`으로 강제해, 칩 라벨(tradition, src, 여러 parallels)이 길어지면 줄 중간에서 나뉘지 못하고 한 덩어리로 다음 줄에 떨어졌다. span은 주변 본문처럼 인라인으로 흘러, 긴 라벨이 `·` 구분자에서 자연스럽게 줄을 바꾼다. 주석 앵커(`_wrapAnchor`)가 같은 이유로 이미 span을 쓰던 선례를 따랐다. span에는 Enter/Space 기본 동작이 없으므로 `initCiteSheet`의 keydown 핸들러가 칩을 직접 작동시킨다.
    - **운문(`type: "poetry"`) 인용의 예외**: 인라인 칩은 시의 행 구조를 깨므로, 운문 끝에서 줄을 바꿔 따로 한 줄에 칩을 둔다. 들여쓰기는 운문 본문과 같거나 한 단계 더 들인다(Phase 2에서 확정).
    - **중복 제거(dedup)**: 이어진 절들이 모두 같은 `(src, tradition, parallels)` cite를 가지면, 그 묶음의 **마지막 절에만 칩을 1회** 보인다. 같은 인용이 절 경계로 나뉜 경우(§3)를 한 단위로 보이게 하려는 것이다. `parallels`는 각 항목의 `(ref, tradition)` 짝을 순서까지 견준다. 맨 ref가 같아도 parallel의 사본 전통 라벨이 다르면 묶음을 끊는다(2026-05-31). 그래서 비교 키는 `(src, src_tradition, [...(parallel ref, parallel tradition)])`다.
    - **사본 전통 표기**: `tradition` 속성이 있으면 칩의 첫 src 앞에 붙인다. parallels의 각 항목에 `[전통]`이 있으면 그 ref 앞에 같은 방식으로 붙인다(2026-05-31). 권장 모양은 `(칠십인역 이사 40:3 · 신명 5:17 · 칠십인역 시편 16:8)`이다. 구분자 `·`는 ref 사이에만 두고, 전통과 ref 사이는 공백 한 칸이다. 전통이 없는 ref는 아무것도 붙이지 않는다.

  - **인용 바텀 시트 (cite sheet)**: 칩을 누르면 열리는 모달 시트다. 페이지를 옮기지 않고 인용한 본문을 시트 안에서 보여 주어, 읽는 흐름이 이어진다(절 번호를 aria-hidden으로 둔 결정과 같은 이유).
    - **머리**: 시트 제목은 「인용된 구절」이고, 닫기 버튼이 있다. ref마다 작은 머리에 출처를 적는다(`이사 53:5`, 사본 전통이 있으면 앞에 붙여 `칠십인역 이사 40:3`). 처음에는 시트 머리에 출처와 `· 칠십인역`을 적기로 했다.
    - **기본 본문**: 인용한 절만 잘라 보인다. 절 번호, 운문과 산문 등은 앱 본문 렌더와 같은 양식을 다시 쓴다.
    - **넓혀 보기**: ref마다 머리에 「› 더 보기」 버튼이 있다. 누르면 같은 시트 안에서 그 장 전체로 넓히고, 인용한 절을 강조한다(여전히 페이지는 옮기지 않는다). 뒤로 버튼이나 ESC로 다시 목록으로 돌아온다(ADR-032). 처음에는 시트 아래에 `이 장 전체 보기` 동작을 두기로 했다.
    - **장 경계를 넘는 범위**(`이사 8:23-9:1`): 두 장을 구분선으로 나눠 한꺼번에 보인다. 페이지를 옮기지 않고 양쪽 맥락을 모두 보여 주므로, 해당 장으로 이동하는 것보다 낫다.
    - **콤마로 이은 여러 절**(`판관 13:5, 7`): 같은 장 안의 떨어진 절들을 시트에 모아 보인다(사이를 `…`이나 절 번호 간격으로 나눈다).
    - **모바일과 데스크톱**: 모바일은 화면 아래에서 끌어올리는 바텀 시트다. 데스크톱에서 cite sheet(`#cite-sheet`)는 **오른쪽에서 미끄러져 들어오는 사이드 패널**이다(`pointer: fine`이고 `min-width: 769px`일 때만). 위 `top: 2.5vh`, 높이 `height: 95vh`, 왼쪽 가장자리로 폭을 바꾸고, `--shadow-drawer` 그림자를 쓴다. 북마크 드로어(`#bookmark-drawer`), 검색 책 선택 시트(`.book-filter-sheet`)와 **같은 데스크톱 방식**(`bm-drawer-in-right`/`out-right`)이다. 폭이 769px 이상이어도 **터치 태블릿(`pointer: coarse`)은 모바일 바텀 시트를 쓴다.** 바뀌는 기준은 폭 하나가 아니라 폭과 포인터 종류다. 오버레이와 드래그 리사이즈 공용 배관은 ADR-032, 세 패널을 맞춘 결정은 ADR-033(2026-06-11)에 있다. `DESIGN.md` §5·§6도 맞췄다. 처음에는 데스크톱도 같은 시트를 알맞은 폭으로 보이기로 했다(검색 결과 시트를 다시 쓰고, 별도 popover 컴포넌트는 두지 않는다). 2026-06-21에 코드와 견줘 지금 방식으로 고쳐 적었다.
    - **접근성**: `role="dialog"` + `aria-modal="true"`, ESC로 닫기, focus trap, 닫으면 원래 칩으로 포커스를 돌려준다. 처음에는 뒤의 본문을 `inert`로 두기로 했다. 지금은 스크림 없이 포커스만 시트 안에 가둔다. 그래서 시트에 가리지 않은 본문의 칩을 다시 누르면 시트를 닫지 않고 내용만 바꾼다(`js/app/citations.js`, ADR-032).
    - **시트 안 본문에는 칩과 주석을 그리지 않는다**: 시트가 보여 주는 인용 본문은 늘 「출처·주석 토글 off」 상태로 그린다. 시트 안에 시트가 겹치는 것을 피하고, 깨끗한 원문을 먼저 보여 주기 위해서다. 더 깊이 보려면 시트를 닫고 그 본문으로 가서 거기서 칩을 누른다(드물고, 일부러 둔 부담이다).
  - 주석: 앵커 어절에 옅은 점선 밑줄을 둔다. **누르면 그 자리 가까이에 작은 툴팁 팝오버로 주석 본문을 보인다**(2026-05-24, dev 검토). 인쇄 footnote처럼 본문에서 아래로 갔다가 다시 돌아오는 부담 없이, 읽던 자리에서 바로 확인한다. 툴팁은 ESC나 바깥을 누르면 닫힌다. 모바일에서는 화면 폭에 맞춰 저절로 자리를 잡고, 위나 아래 공간이 모자라면 반대편으로 뒤집힌다. 붙일 어절이 없는 주석은 절 끝의 ※ 표시를 누르면 같은 툴팁이 열린다.
- 처음 들어올 때 코치마크를 1회 보인다. 인용 칩을 가리키며 「회색 인용 출처 버튼을 누르면 인용 본문이 시트로 열려요.」라고 안내한다(토글 기본이 ON이라 칩 자체가 발견의 계기다).
- **복사할 때 칩과 주석 표시를 뺀다(2026-05-31).** 절 복사(시스템 Cmd/Ctrl+C 드래그 선택과 절 선택 막대의 `복사` 버튼)는 인용 칩과 ※ 사본 주석 표시를 본문에서 뺀다. 두 경로가 함께 쓰는 직렬화 함수 `serializeVerseRange`(VERSE_SERIALIZE 블록)가 복제한 range에서 `.cite-chip`과 `.note-anchor--variant`를 지운다. 이것들은 읽기를 돕는 화면일 뿐 성서 본문이 아니다. 반면 어절을 감싸는 텍스트 앵커 주석(`.note-anchor`, 사본 주석이 아닌 것)은 실제 본문 단어를 감싸므로 그 textContent를 그대로 남긴다. 처음에는 `js/app/bookmark.js`에 있었고, 지금은 `js/app/verse-spec.js`에 있다. e2e 회귀: `tests/e2e/test_copy.py::test_copy_excludes_citation_chip_and_note_marker`.

처음에는 절 단위 앵커 이동(`/isa/53#v5`)이 라우터에 없으면 Phase 2에 함께 더하고, 범위 인용은 시작 절로 스크롤한 뒤 끝 절까지 잠시 강조하기로 했다. 칩이 페이지를 옮기지 않고 시트를 열게 되면서 인용에는 이 앵커가 필요 없어졌다. 지금 라우터에는 `#v5` 같은 절 앵커가 없고, 절 구간은 경로로 적는다(`/john/3/1-5,10-15`, 라우팅 주제 문서).

### 7. 데이터 검증 테스트 (Phase 1)

`common-bible-data/tests/`에 더한다.

- `<cite src>`가 `<short_name_ko> <chapter>:<verse>(-<verse>)?` 형식인지 정규식으로 검증한다.
- `src`의 약어가 `books.json`의 `short_name_ko`에 실제로 있는지.
- `src`의 장과 절이 그 책에 실제로 있는지(`chapter_count`와 그 장의 절 수 검사).
- footnote ID 형식: source의 `[^<장>-<n>]`가 형식에 맞고, 장 접두사가 실제 앵커 자리의 장과 같은지.
- footnote ID의 짝: 본문 앵커 `[^id]`가 모두 정의를 갖고(정의 없는 앵커 0), 정의한 ID가 모두 본문에서 쓰이는지(쓰이지 않는 정의 0).
- footnote 번호가 차례인지: 같은 장 안 ID가 1, 2, 3… 빈 번호 없이 이어지는지.
- footnote 앵커 어절이 실제로 같은 절 본문에 있는지.

## 검토한 대안

| 대안 | 채택하지 않은 이유 |
|---|---|
| 인용과 주석을 모두 HTML 태그(`<cite>` + `<note>`)로 통일 | 주석이 한 단락 분량이면 본문 한 줄이 아주 길어진다. 마크다운 소스의 가독성과 diff가 모두 나빠진다. |
| 인용과 주석을 모두 footnote 문법으로 통일 | 인용은 짧은 메타데이터(`사 53:5`)라 footnote 정의를 따로 두는 것은 지나치다. `<cite>`가 뜻이 더 정확하다. |
| `src`에 OSIS book_id(`isa`) 쓰기 | source/*.md를 읽기 어려워진다. 개발을 모르는 검토자(사목, 신학 자문)가 바로 읽지 못한다. `short_name_ko`가 이미 books.json에 있으므로 따로 대응시킬 부담이 없다. |
| 인용 칩과 함께 본문 글자에도 링크 스타일(밑줄, 색) 쓰기 | 본문 인용 글자가 무거워 보여 몰입이 줄어든다. 절 번호를 aria-hidden으로 둔 결정과 맞지 않는다. |
| 주석 토글과 인용 토글을 나누기 | 화면이 복잡해진다. 따로 둘 가치는 있지만 1차 버전에는 토글 하나로 충분하다. 사용자 의견이 오면 나누기를 검토한다. |
| 토글이 꺼져도 표시(별표, 위첨자)를 보여 발견을 돕기 | 「꺼짐은 아무것도 보이지 않음」 원칙에 어긋난다. 토글 위치는 코치마크 한 번으로 알린다. |
| 주석 정의에 마크다운 인라인 서식 허용 | 1차 버전은 단순하게 간다. 필요하면 뒤의 ADR에서 다룬다. |

### `tradition` 속성 없이 시작 (2026-05-23, 같은 날까지)

- 초안은 `tradition`/`lxx`/`mt` 속성으로 사본 전통을 표현하는 것을 필요 없는 기능(YAGNI)으로 보고 뺐다. 절 번호 차이를 맞추는 일은 데이터의 몫이라고 보았다.
- 채택 안 함 2026-05-23 · 이유: 실제로 신약의 구약 인용을 마크업하기 시작하니, 칠십인역을 먼저 따른 인용(특히 로마서, 히브리서)이 잦았다. 사용자에게 「이 신약 인용은 우리 공동번역과 다른 사본 전통을 따른다」고 알려야 했다. 절 번호 차이를 맞추는 책임은 여전히 데이터에 있지만, 보여 주기만 하는 라벨인 tradition은 인용 태그가 맡는 것이 자연스럽다. §2에 `tradition`을 선택 속성으로 되살렸다.

### 기본값 OFF (2026-05-23, 같은 날까지)

- 초안은 토글의 기본값을 끔(off)으로 두었다.
- 채택 안 함 2026-05-23 · 이유: Phase 2를 확정하며 기본값을 켬으로 바꿨다(§6의 이유).

### 장 끝의 주석 단락과 위첨자 번호 (2026-05-24까지)

- 처음 디자인은 앵커에 위첨자 ref 번호를 달고 장 끝에 「주석」 섹션을 두는 인쇄 학술 footnote 양식이었다.
- 채택 안 함 2026-05-24 · 이유: dev에서 확인해 보니, 본문 끝까지 스크롤했다가 다시 돌아오는 흐름이 디지털에서는 어색했다. 툴팁 양식으로 바꾸고 위첨자 번호와 아래 섹션을 모두 지웠다(§6).

### 인용 칩을 `<button>`으로 그리기 (2026-05-29까지)

- 처음에는 인용 칩을 native `<button>`으로 그렸다.
- 채택 안 함 2026-05-29 · 이유: 브라우저가 `<button>`을 `display:inline-block`으로 강제해 긴 라벨이 줄 중간에서 나뉘지 못했다. span으로 바꿨다(§6).

### 사본 전통은 첫 출처에만 (2026-05-31까지)

- 처음 §2는 「tradition은 첫 출처에만 적용하고, parallels의 사본 전통은 적지 않는다」는 제약을 일부러 두었다. 스키마는 `parallels: string[]`였다.
- 채택 안 함 2026-05-31 · 이유: 신약의 구약 인용 마크업이 진행되면서, src와 parallels가 서로 다른 사본 전통인 경우(예: 신약 본문은 칠십인역을 먼저 따르고, 그 구약 병행은 마소라 본문)가 잦았다. 그것을 적을 자리가 없는 것이 문제였다. parallels 각 항목 끝에 `[전통]` 접미사를 허용하고(예: `parallels="시편 16:8 [칠십인역]; 사도 2:25"`), 칩 라벨은 각 ref 앞에 그 ref의 사본 전통을 붙인다(`(이사 40:3 · 신명 5:17 · 칠십인역 시편 16:8)`). 스키마는 `parallels: {ref: string, tradition?: string}[]`로 올렸다. tradition은 여전히 **보여 주기만 하는 라벨(display-only label)**이다. 앱이 공동번역 한 본문만 보여 준다는 ADR-022의 원칙은 그대로다(라우팅이나 텍스트 출처를 바꾸지 않는다).

## 영향

### ADR-006 (운문 segments 형식, data 저장소)
- segment 객체에 선택 필드 `cite`를 더한다. 운문 한 행이 인용인 경우도 같은 방식이다.
- 데이터 저장소의 ADR-006 본문에 「segments 선택 필드」 절을 보강해야 한다.

### ADR-004 (데이터 파이프라인 테스트 전략)
- Level 1 완전성 검증에 cite와 footnote가 맞는지 보는 항목 5종을 더한다. ADR-004 본문을 고친다.

### ADR-009 (History API 라우팅)
- 처음에는 절 단위 앵커(`#v5`)가 라우터에 없으면 Phase 2에 더하고 ADR-009를 고치기로 했다. 칩이 시트를 열게 되면서 필요 없어졌다(§6).

### ADR-021 (콘텐츠 해시 매니페스트)
- 영향이 없다. cite와 notes는 기존 bible/*.json 안에 들어가므로 매니페스트가 해시 변화를 저절로 잡는다.

### 저장소별 작업 나누기 (ADR-020)
- `common-bible-data`: parser.py와 split_bible.py 확장, 검증 테스트, ADR-006 갱신, 픽스처 다시 만들기. 이 PR을 먼저 머지한다.
- `common-bible`: 이 ADR, Phase 2 화면(`js/app/views-routing.js` 렌더 분기 + `js/app/settings-ui.js` 토글 + CSS), 라우터 절 앵커, 유닛과 e2e 테스트, 서브모듈 포인터 올리기. 데이터 PR을 머지한 뒤에 한다. 화면 코드는 지금 `js/app/citations.js`에 있다.

## Phase

- **Phase 1** (데이터 파이프라인, `common-bible-data`):
  - parser.py: `<cite>` 추출(span과 src), `[^id]` 추출(앵커 어절, 몇 번째인지, 본문).
  - split_bible.py: 절 단위 JSON에 `cite` segment 필드와 verse `notes` 배열을 담고, 절 경계 분리 규칙을 구현한다.
  - 검증 테스트 5종.
  - ADR-006 갱신.
  - 시범 적용: 마태 1-2장이나 구약 인용이 많은 구간 1-2장에 `<cite>`와 주석 한두 개를 손으로 달아 파이프라인을 통과하는지 확인한다.
- **Phase 2** (앱 화면, `common-bible`):
  - 토글 위젯(`js/app/settings-ui.js`)과 localStorage 저장.
  - 본문 렌더 분기(`js/app/views-routing.js`): cite 칩과 주석 단락(주석 단락은 뒤에 툴팁으로 바뀌었다, §6).
  - CSS: 옅은 회색 톤과 들여쓰기, 링크 스타일은 칩에만.
  - 라우터 절 앵커(필요하면 ADR-009 개정, 뒤에 필요 없어졌다).
  - 처음 들어올 때 코치마크 1회.
  - 토글 이름 확정.
  - 유닛 테스트와 e2e.
- **Phase 3** (주해 저작, 장기):
  - 사목과 신학 자문을 받아 신약 전체에 `<cite>`와 주석을 손으로 쓴다.
  - 마크업 작업이 아니라 콘텐츠 저작이다. 일정과 검토 절차를 따로 둔다.

## 검증

Phase 1:
- 파이프라인 단위 테스트(시범 적용한 장에서 cite와 notes가 제대로 뽑히는지).
- Level 1 검증 5종 통과.
- `data/bible/*.json` 스키마가 ADR-018 모듈 분할 뒤의 클라이언트 렌더 코드 가정과 맞는지(더한 필드는 선택이라 기존 코드에 해가 없다).

Phase 2 (처음 계획):
- 유닛: 토글 상태 저장, 칩과 주석 렌더 분기, 링크 만들기(약어를 URL로).
- e2e: 토글 on/off의 시각 변화, 칩을 누르면 출처 페이지로 이동, 절 앵커 스크롤. 칩이 시트를 열게 바뀌어 뒤의 둘은 시트 동작 확인으로 바뀌었다.
- 접근성: 토글이 꺼지면 본문에 스크린 리더가 읽을 추가 내용이 없다. 토글이 켜지면 칩과 주석에 알맞은 role과 aria 라벨이 있다.
