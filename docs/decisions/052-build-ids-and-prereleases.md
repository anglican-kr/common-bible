# ADR-052: 배포한 빌드에 앱과 데이터의 커밋을 적고, 운영에 내기 전에 pre-release를 만든다

- 상태: 승인됨 — 구현 중. 서버 저장소의 빌드와 배포 검증(common-bible-server#6)과 이 저장소의 설정 화면, 문서를 고친다
- 관련: ADR-021(버전 파일과 서비스 워커 갱신), ADR-051(dev와 main, 운영에 내는 순서), ADR-020(저장소 분할)

## 요약

1. **빌드 식별자**(§1): 배포할 때 zip에 넣는 `version.json` 사본에 앱 커밋(`app_commit`)과 데이터 커밋(`data_commit`)을 더한다. 저장소의 `version.json`과 `sw-version.js`는 그대로 둔다.
2. **앱 커밋의 기준**(§2): 배포하는 앱 파일을 마지막으로 바꾼 커밋이다. 데이터만 바뀐 배포에서는 그대로다.
3. **화면**(§3): dev.anglican.kr에서만 설정 맨 아래에 "공동번역성서 2.2.4-9985216 · 데이터 1de377e"를 보인다. 운영은 지금처럼 버전만 보인다.
4. **pre-release**(§4): 버전을 올린 커밋을 dev.anglican.kr에 올리면 `X.Y.Z-<앱 커밋>` 태그와 GitHub pre-release를 만든다. 정식 `X.Y.Z` 태그와 Release는 운영에 낼 때 새로 만든다.
5. **다음 단계**(§5): 앱과 데이터를 따로 배포하는 일은 이번에 하지 않는다. 무엇이 남았는지 적어 둔다.

## 배경

1. dev.anglican.kr에 같은 버전을 여러 번 올리면 화면에서 어느 빌드인지 알 수 없었다. 배포 뒤 검증도 `version.json`의 버전만 견줘, 같은 버전의 다른 빌드로 바뀌었는지 가려내지 못했다.
2. 태그와 Release는 운영에 낼 때만 만들어, dev.anglican.kr에서 확인하는 빌드는 GitHub에 기록이 없었다.
3. 데이터는 앱 커밋의 서브모듈 포인터로만 가리킬 수 있었다. 데이터 저장소에는 태그도 버전도 없다. 데이터가 바뀌면 앱 저장소에 포인터 커밋이 생겨, 앱이 바뀌었는지 데이터가 바뀌었는지 커밋만으로는 알 수 없다.

## 결정

### 1. 빌드 식별자

- 서버 저장소의 `build-deploy.sh`가 zip을 만들 때 `version.json` 사본에 `app_commit`과 `data_commit`(짧은 해시)을 더해 넣는다. 예: `{"version": "2.2.4", "app_commit": "9985216", "data_commit": "1de377e"}`.
- 까닭: 커밋은 자기 해시를 담을 수 없다. 저장소의 파일을 고치면 커밋하지 않은 변경이 남아 다음 배포가 멈춘다(ADR-051 §4).
- `sw-version.js`에는 넣지 않는다. 까닭: 서비스 워커는 이 파일이 바뀌면 새로 설치된다. 해시를 넣으면 데이터만 낸 운영 배포에도 사용자에게 업데이트 알림이 뜬다. ADR-021 §4가 막은 일이다.
- 배포 뒤 검증은 버전과 함께 두 커밋도 비교한다. 식별자가 없는 옛 빌드로 promote하거나 되돌릴 때는 버전만 본다.
- 해시가 빌드의 내용을 정한다. `deploy.sh`는 커밋하지 않은 변경, 추적하지 않는 파일, 기록과 다른 데이터 서브모듈이 있으면 멈춘다(ADR-051 §4). 데이터 서브모듈을 받지 않은 폴더(`data/`를 심볼릭 링크로 채운 작업 폴더)는 데이터 커밋을 읽을 수 없어 빌드가 멈춘다.

### 2. 앱 커밋의 기준

- `app_commit`은 배포 목록(서버 저장소 `deploy-manifest.txt`)에서 `data/`와 `sitemap.xml`을 뺀 경로를 마지막으로 바꾼 커밋이다. `data_commit`은 데이터 서브모듈의 커밋이다.
- 까닭: 데이터가 바뀌면 `sync-data.yml`이 서브모듈 포인터와 `sitemap.xml`을 올리는 커밋을 앱 저장소에 만든다. 앱 커밋으로 HEAD를 쓰면 앱이 그대로여도 값이 바뀌어, 앱과 데이터를 나눠 적는 뜻이 없다.
- 문서만 바꾼 커밋도 배포 목록 밖이라 `app_commit`을 바꾸지 않는다.
- 서버의 빌드 디렉터리 이름(`bible-{version}-{HEAD}`)과 promote의 확인은 HEAD를 그대로 쓴다. promote는 dev.anglican.kr에서 확인한 바로 그 커밋이 main인지 보아야 한다.

| dev 배포 | `app_commit` | `data_commit` |
| --- | --- | --- |
| 2.2.4 릴리스 커밋 `9985216` | `9985216` | `1de377e` |
| 그 뒤 데이터 자동 PR만 들어온 dev | `9985216`(그대로) | 새 데이터 커밋 |
| 그 뒤 앱 수정 PR이 들어온 dev | 그 수정의 커밋 | 그대로 |

### 3. 화면

| 어디 | 설정 맨 아래의 버전 줄 | 링크 |
| --- | --- | --- |
| dev.anglican.kr과 로컬 | 공동번역성서 2.2.4-9985216 · 데이터 1de377e | 앱 커밋의 GitHub 페이지 |
| 운영(bible.anglican.kr) | 공동번역성서 2.2.4 | 그 버전의 Release |

- 운영에서 보이지 않는 까닭: 운영은 셸 파일을 캐시에서 먼저 꺼낸다. 데이터만 낸 배포는 서비스 워커를 새로 설치하지 않으므로, 사용자 기기의 `version.json`이 옛 것으로 남아 서버의 빌드와 다른 해시가 보인다. dev.anglican.kr은 셸 파일을 네트워크에서 먼저 받아 이 일이 없다.
- 로컬에서 받는 `version.json`은 저장소의 파일이라 해시가 없고, 버전만 보인다.
- 데이터 커밋에는 링크를 달지 않는다. 데이터 저장소가 비공개다.
- dev의 링크가 pre-release가 아니라 커밋으로 가는 까닭: 버전을 올리지 않은 시험 배포에는 pre-release가 없다(§4). 커밋 페이지는 늘 있다.
- 업데이트 알림의 버전과 링크는 바꾸지 않는다. 운영에서만 의미가 있고, 운영은 정식 태그다.
- 구현은 `docs/topics/cache-release.md` "빌드 식별자와 pre-release"에 있다.

### 4. pre-release

- 버전을 올린 커밋을 dev.anglican.kr에 올리면, 배포한 커밋에 annotated 태그 `X.Y.Z-<app_commit>`을 달고 GitHub pre-release를 만든다. 태그 이름은 `deploy.sh dev`가 끝에 출력하는 빌드 식별자다. 노트는 릴리스 PR의 릴리스 노트 초안을 쓴다.
- 같은 버전에 앱 수정을 더해 다시 올려 `app_commit`이 바뀌면 새 pre-release를 만든다. 데이터만 바뀌어 `app_commit`이 같으면 만들지 않는다.
- 버전을 올리지 않은 시험 배포에는 만들지 않는다. 까닭: 릴리스 목록이 시험 배포로 차서 정식 릴리스를 찾기 어려워진다.
- 운영에 낼 때(ADR-051 §3의 5) main을 앞당긴 커밋에 정식 `X.Y.Z` 태그와 Release를 새로 만든다. pre-release 태그는 옮기거나 고치지 않는다. 까닭: 올린 태그를 다시 쓰면 이미 받은 클론과 어긋난다.
- 릴리스 커밋 뒤에 데이터 포인터 커밋이 쌓인 dev를 올리면, 태그는 배포한 커밋(HEAD)에 달고 이름은 `app_commit`을 쓴다. 이름의 해시와 태그가 가리키는 커밋이 다르므로, 태그 메시지에 데이터 커밋을 함께 적는다.
- 변경 목록(`changelog.py`)과 정식 Release의 비교 링크는 직전 정식 태그와 비교한다. pre-release 태그와는 비교하지 않는다.

### 5. 다음 단계: 앱과 데이터를 따로 배포하기

이번에는 하지 않는다. 범위가 커서 따로 ADR을 쓴다. §2의 기준은 이 분리를 미리 따른다.

- 이미 나뉜 것: 사용자 기기의 데이터 캐시는 내용 해시로 낱개씩 갱신되어 앱 업데이트가 필요 없다(ADR-021). 검색 강조는 옛 색인과 새 색인을 모두 받는다(ADR-005). `bible-manifest.json`에는 `format` 번호가 있다.
- 아직 묶인 것: 앱 커밋이 서브모듈 포인터로 데이터 커밋을 고정한다. `deploy.sh`가 앱과 데이터를 한 zip, 한 빌드 디렉터리로 낸다. 데이터만 운영에 낼 때도 ADR-051 §3의 앱 릴리스 순서를 따른다.
- 나누는 방법의 후보: 서버에 데이터 디렉터리를 따로 두고(지금 `/var/www/audio`처럼) 교체와 되돌리기를 따로 한다. 앱은 데이터 커밋 대신 읽을 수 있는 데이터 형식 번호를 밝힌다.

## 검토한 대안

1. **`version` 값에 해시를 붙인다**(`"2.2.4+9985216"`, 2026-11-23 버림). 업데이트 알림과 설정의 링크가 `version`을 태그 이름으로 쓰고, 배포 검증과 `release.py`가 `version`을 버전 번호로 다룬다. 고칠 곳이 늘고 운영의 링크가 깨진다.
2. **`sw-version.js`에도 해시를 넣는다**(2026-11-23 버림). §1의 까닭.
3. **앱 커밋으로 HEAD를 쓴다**(2026-11-23 버림). §2의 까닭. 재검토 조건: 앱과 데이터를 따로 배포해 앱 저장소에 포인터 커밋이 생기지 않게 되면, HEAD와 같아진다.
4. **운영에서도 해시를 보인다**(2026-11-23 버림). §3의 까닭. 재검토 조건: 데이터만 낸 배포에서도 사용자 기기의 `version.json`이 새로 바뀌게 되면.
5. **pre-release 태그를 `X.Y.Z-rc.N`으로 짓는다**(2026-11-23 버림). 차례는 보이지만, 화면의 버전 줄과 태그를 맞춰 보려면 Release를 열어야 하고 번호를 세는 일이 하나 는다.
6. **정식 `X.Y.Z` 태그를 pre-release로 먼저 만들고 운영에 낼 때 정식으로 바꾼다**(2026-11-23 버림). 같은 버전을 고쳐 다시 올리면 태그를 옮겨야 한다.
