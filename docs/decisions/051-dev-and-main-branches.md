# ADR-051: 작업은 dev 브랜치에 모으고, main은 운영에 낸 코드만 담는다

- 상태: 승인됨 — 구현 완료(2026-11-22). 앱 저장소의 규칙, CI, 훅을 dev 기준으로 바꿨고(#633), dev 브랜치와 저장소 설정(dev 보호, 기본 브랜치), 데이터 저장소의 동기화 요청(common-bible-data#92), 서버 저장소의 배포 확인(common-bible-server#5)을 적용했다. §3의 순서로 운영에 내는 것은 2.2.4가 처음이다
- 관련: ADR-020(저장소 분할, 배포 스크립트의 위치), ADR-021(캐시 무효화와 릴리스 스크립트), ADR-052(빌드 식별자와 pre-release)

## 요약

1. **브랜치의 역할**(§1): `dev`는 머지한 모든 작업을 담고, `main`은 운영(bible.anglican.kr)에 낸 코드만 담는다. main은 운영에 낼 때만 바뀐다.
2. **작업 흐름**(§2): 토픽 브랜치는 `origin/dev`에서 따고 PR을 dev로 열어 squash로 머지한다. GitHub 기본 브랜치는 dev다. 데이터 자동 PR도 dev로 간다.
3. **운영에 내기**(§3): dev의 커밋을 dev.anglican.kr에서 확인한 뒤, dev에서 main으로 PR을 열어 필수 검사를 통과시키고 main을 그 커밋으로 그대로 앞당긴다. 머지 커밋도 squash도 쓰지 않는다. 그래서 main과 dev의 커밋이 같고, dev에서 확인한 빌드를 `deploy.sh promote`가 그대로 운영에 낸다.
4. **배포 스크립트의 확인**(§4): `deploy.sh`가 dev 배포는 dev에 있는 커밋만, 운영 배포는 main과 같은 커밋만 받는다.
5. **급한 수정**(§5): 급한 수정도 dev를 거쳐 §3의 순서로 운영에 낸다.

## 배경

지금까지는 모든 PR을 main에 머지하고, 운영에 낼 때 main의 그 시점을 dev.anglican.kr에 올려 확인한 뒤 운영으로 옮겼다(`deploy.sh dev`, `deploy.sh promote`). 그래서 다음 문제가 있었다.

1. main에는 운영에 아직 내지 않은 변경이 늘 섞여 있다. 운영에 지금 무엇이 있는지는 태그로만 알 수 있었다.
2. 데이터 자동 PR(`sync-data.yml`)도 main에 머지되므로 main은 하루에도 여러 번 바뀐다.
3. 배포 스크립트는 로컬 폴더의 지금 커밋을 그대로 빌드한다. 그래서 어느 브랜치의 커밋이든 dev.anglican.kr과 운영에 올라갈 수 있었다.

## 결정

### 1. 브랜치의 역할

| 브랜치 | 담는 것 | 바뀌는 때 |
| --- | --- | --- |
| `dev` | 머지한 모든 작업과 데이터 자동 PR | PR을 머지할 때마다 |
| `main` | 운영(bible.anglican.kr)에 낸 코드 | 운영에 낼 때만(§3) |

- 두 브랜치 모두 보호한다. 필수 검사(`Unit tests`, `Change ledger`), 관리자를 포함한 직접 push 금지, force push와 브랜치 삭제 금지, 리뷰 코멘트 해결은 두 브랜치가 같다. 저장소는 머지된 PR의 브랜치를 자동으로 지우는데, 운영 반영 PR의 브랜치가 dev 자체다. 보호된 브랜치는 지우지 않으므로 dev의 보호를 풀지 않는다.
- 까닭: main이 운영과 같으면, 운영에 무엇이 있는지를 브랜치 하나로 안다.

### 2. 작업 흐름

- 토픽 브랜치는 `origin/dev`에서 따고, PR은 dev로 연다. 머지는 지금처럼 squash다.
- GitHub 기본 브랜치는 dev다. PR을 열 때 기본 대상이 dev이고, 새로 받은 클론도 dev를 체크아웃한다.
- 데이터 저장소의 `build.yml`은 앱의 `sync-data.yml`을 dev에서 실행하라고 요청하고, `sync-data.yml`은 서브모듈 포인터를 올리는 자동 PR을 dev로 연다. 데이터 변경도 앱 코드와 함께 §3의 순서로 운영에 간다.
- 원장 규칙의 기준 브랜치는 dev다. dev에 머지된 원장은 고치지 않는다.

### 3. 운영에 내기

운영에 내는 일은 버전을 올릴 때든 데이터만 바뀌었을 때든 이 순서를 따른다.

1. 버전을 올리면 릴리스 PR(`release: X.Y.Z 릴리스`)을 dev에 머지한다.
2. dev의 그 커밋을 dev.anglican.kr에 올리고 실제 기기에서 확인한다. 그 버전에 정식 태그가 아직 없으면 그 빌드의 pre-release를 만들고, CI가 그것을 올린다(ADR-052 §4). 정식 태그가 있거나 데이터만 바뀌었으면 `deploy.sh dev`로 올린다.
3. dev에서 main으로 PR을 연다. 필수 검사가 그 커밋에서 실행된다.
4. 검사가 통과하면 main을 그 커밋으로 앞당긴다(`git push origin <커밋>:main`). GitHub는 그 PR을 머지된 것으로 닫는다.
5. 버전을 올렸으면 그 커밋에 정식 태그와 GitHub Release를 만든다. 그다음 `deploy.sh promote`를 실행한다.

- main은 앞당기기만 한다. 머지 커밋도 squash도 쓰지 않는다. 까닭: main과 dev의 커밋이 같아야, dev에서 확인한 빌드 디렉터리(`bible-{version}-{shortsha}`)를 promote가 그대로 운영에 가리킬 수 있다.
- 브랜치 보호는 PR에서 필수 검사를 통과한 커밋을 그대로 앞당기는 push를 받아들인다(#354와 data#33에서 확인했다).
- dev.anglican.kr에는 운영에 내기 전이 아니어도 dev의 커밋을 올려 볼 수 있다. 운영에 낼 커밋은 2에서 다시 올린다.

### 4. 배포 스크립트의 확인

서버 저장소의 `deploy.sh`가 빌드하거나 운영을 바꾸기 전에 origin을 새로 받아 견준다. 받지 못하면 멈춘다.

| 명령 | 받는 경우 |
| --- | --- |
| `deploy.sh dev` | 앱 폴더의 커밋이 `origin/dev`에 들어 있고, 커밋하지 않은 변경과 배포 목록 경로 아래의 추적하지 않는 파일이 없을 때 |
| `deploy.sh prod` | 앱 폴더의 커밋이 `origin/main`과 같고, 커밋하지 않은 변경과 배포 목록 경로 아래의 추적하지 않는 파일이 없을 때 |
| `deploy.sh promote` | dev.anglican.kr이 가리키는 빌드의 커밋이 `origin/main`과 같을 때 |
| `deploy.sh rollback` | 확인하지 않는다. 되돌리는 일은 막지 않는다 |

- 까닭: 순서를 잊어도 main에 없는 코드가 운영에 가지 않고, dev에 없는 코드가 dev.anglican.kr에 가지 않는다.
- 구현의 세부는 서버 저장소 `scripts/deploy.sh`의 머리 주석에 있다.

### 5. 급한 수정

- 급한 수정도 dev에 PR로 넣고 §3의 순서로 운영에 낸다.
- dev에 아직 운영에 낼 수 없는 변경이 있으면, 그 변경을 되돌리는 PR을 dev에 먼저 넣는다.

## 검토한 대안

1. **dev에서 main으로 머지 커밋을 만든다**(2026-11-22 버림). 저장소 설정에서 머지 커밋을 다시 허용해야 해서, 작업 PR에서도 실수로 머지 커밋을 고를 수 있다. main에만 있는 커밋이 운영에 낼 때마다 생겨, dev에서 확인한 빌드의 커밋과 main의 커밋이 달라진다. 재검토 조건: GitHub의 PR 머지 단추가 커밋을 그대로 앞당기는 방식을 지원하면, 4의 push 대신 그 단추를 쓴다.
2. **dev에서 main으로 squash 머지한다**(2026-11-22 버림). main에 새 커밋이 생겨 다음에 운영에 낼 때 dev와 main이 갈라지고 충돌한다.
3. **급한 수정을 main에서 딴다**(2026-11-22 버림). main에 먼저 넣으면 dev와 갈라져 다음에 운영에 낼 때 앞당길 수 없다. dev에 다시 합치려면 머지 커밋이 필요하다. 재검토 조건: 운영에 낼 수 없는 변경이 dev에 오래 머무는 일이 잦아지면.
4. **데이터와 서버 저장소에도 dev를 둔다**(2026-11-22 버림). 데이터 저장소의 main은 운영에 바로 가지 않는다. 앱 dev의 서브모듈 포인터가 어느 데이터를 쓸지 정하고, 그 포인터가 main에 가야 운영에 간다. 서버 저장소의 nginx 설정과 배포 스크립트는 브랜치가 아니라 사람이 서버에 적용한다.
