## 1. 개요

### 1.1 목적

날짜 하나를 받아 **그날이 교회력에서 무슨 날인지**를 계산하고, 그 좌표로 **감사성찬례 독서와 본기도를 조회**하는 순수 로직 모듈을 만든다. ADR-037 이 D1(전례시편) · D2(독서 데이터) · D3(연중 구간표)로, ADR-036 이 D4(교회력 정의 표) · D5(품계·전례색 분류)로 데이터를 모두 갖춰 두었고, 그 데이터를 읽는 쪽이 비어 있다. 이 엔진이 그 자리다.

지금 상태를 한 줄로: **데이터는 앱에 배포되고 있지만 아무도 열어보지 않는다.**

### 1.2 범위

| 단계 | 내용 | 본 문서 |
|---|---|---|
| **A1-a 계산 계층** | 부활절 computus, 파생 이동일, 대림 앵커, 절기 스팬, 연중 주차, 주일·평일 주기, 음력 조회, **기간 축 `spansOf`** | §4 |
| **A1-b 조회 계층** | 데이터 로드·캐시, 좌표 폴백 매칭, `resolveDate` 후보 집합, `findReadings`·`findCollects` | §5 |
| **B1 품계·이동** | precedence 충돌 해소, 이동 목적지 평가, 전례색 덮어쓰기, 특수 판정 | §6 |

**비범위** — UI 일체(ADR-038 A2~A4), 성무일과, 전례시편 렌더(ADR-038 A2 로 완료), `scope` 오버레이(ADR-036 B2 — 본당·교구별 등급 격상은 별도 단계).

### 1.3 상위 명세와의 관계

ADR-037 §6 이 이 모듈의 계약을 이미 정해 두었다. 본 설계가 §6 에서 **벗어나거나 더 정하는 것**은 다섯 가지이고, 각각 근거를 아래에 적었다.

1. 마커 블록을 하나(`LITURGICAL_CORE`)가 아니라 둘로 나눈다 → §3.3
2. `resolveDate` 를 async 가 아니라 **동기 함수**로 두고 프리로드를 분리한다 → §3.4
3. 데이터 파일을 **캘린더용 소형 묶음 · 독서용 대형 묶음**으로 갈라 따로 싣는다 → §3.5
4. 조회 API 의 입력이 좌표가 아니다 — `findReadings(resolved, candidate)` · `findCollects(resolved)` → §5.6. 둘이 갈리는 이유도 그 절에 적었다. §6 은 `findReadings(coord)` 로 적었으나 `LiturgicalCoord` 는 절기 축만 담아 이름일·고정일·음력일로 색인된 본문에 닿지 못한다(2026-08-29 실측). ADR-037 §6 의 계약도 함께 개정했다.
5. `candidates` 의 원소가 `Observance` 가 아니라 **`Candidate` 래퍼**다 — `{observance, status, from?, to?, displacedBy?}` → §5.5 · §6.5. 옮겨온 축일을 목적지 날짜에서 내려면 「어디서 왔나」와 「왜 왔나」를 함께 실어야 하는데, `Observance` 는 정의 표의 행을 그대로 담는 공유 타입이라 엔진이 합성한 값을 거기 얹지 않는다(§5.6 이 `occurrence` 를 거절한 것과 같은 이유). ADR-037 §6 의 계약도 함께 개정했다(2026-09-05, 미결9 해소).

**설계 원칙**: 데이터 결손은 전부 **빈 결과 + 계속 진행**으로 흡수한다. 엔진이 throw 하는 경우는 오직 ① 필수 데이터 파일 자체를 못 받았을 때 ② 프리로드 전에 동기 API 를 불렀을 때 ③ **코드 계약 위반** — 인자가 데이터가 아니라 **코드**인 자리에 모르는 값이 올 때(§4.10 `inSpan` 의 스팬 이름 — 2026-09-17 리뷰)다. 셋을 가르는 기준은 「빈 결과가 뜻을 갖는가」다: 표에 없는 날·비어 있는 필드·표기 이탈은 **운영 중 자연히 생기는 결손**이고 「그날은 아무 날도 아님」이 정상 답이므로 흡수하지만, 스팬 이름 오타처럼 코드·배포의 잘못은 조용히 넘기면 가드가 꺼진 채로 돌거나 뷰가 틀린 그림을 그리므로 **크게 실패해야 고쳐진다**. 조회·이동 계층(§5·§6)도 같은 구분을 따른다 — 데이터에서 온 값은 흡수, 코드가 정한 이름·키는 throw.

## 3. 배치와 계층

### 3.1 모듈 위치

`js/app/liturgical-engine.js` — **leaf**. ADR-034 의 leaf 정의는 "밖으로 나가는 의존 0"이고, `data-fetch.js`·`verse-spec.js` 가 그 자리에 있다.

```
leaf     : verse-spec.js · data-fetch.js · overlay.js · [liturgical-engine.js]
view     : views.js · bookmark-read.js · [lectionary.js] · [calendar.js]
orch     : routing.js · bookmark.js
```

- **허용 의존**: 없음(계산·조회 모두 자기 완결). 독서 본문을 그리는 것은 뷰의 몫이므로 `loadChapter`·`parseVerseSpec` 도 엔진이 아니라 `lectionary.js` 가 부른다.
- **금지**: `views.js`·`routing.js`·`lectionary.js`·`calendar.js` 를 import 하면 순환이다. 뷰가 필요로 하는 훅은 역import 대신 주입한다(ADR-034 의 `initBookmarkGestures` 선례).
- **window facade 를 붙이지 않는다.** 신규 모듈은 순수 ESM(`bookmark-core.js` 선례 — window 한 줄도 없음). 레거시 호출자가 생기기 전까지 `export {}` 만.

### 3.3 마커 블록을 둘로 나눈다 (§6 에서 벗어나는 점 ①)

ADR-037 §6 은 `LITURGICAL_CORE` 블록 하나를 지정했다. 둘로 나눈다:

- **`LITURGICAL_CORE`** — 날짜 산술, computus, 오프셋 전개, 절기 스팬, 연중 주차, 주기 산정, 기간 축(§4.10). 외부 입력이 `ordinal-weeks`·`kasi-lunar` 두 표뿐이라 prelude 스텁이 가볍다.
- **`LITURGICAL_LOOKUP`** — 좌표 폴백 매칭, 후보 집합 조립·정렬, 품계·이동·색 판정. 여기는 다섯 표를 전부 인자로 받는다.

**근거**: 한 블록에 다 넣으면 700줄짜리 슬라이스가 되고, 계산만 검증하고 싶은 테스트도 조회용 표 스텁을 전부 만들어야 한다. `verse-spec.js` 가 이미 `VERSE_SPEC` + `VERSE_SERIALIZE` 두 블록으로 같은 일을 한다. 두 블록은 같은 vm 컨텍스트에 차례로 실행할 수 있어(`bookmark-read.test.js` 가 `VERSE_SPEC` 을 먼저 실행하는 선례) 조회 테스트에서 계산 함수를 진짜로 쓸 수 있다.

블록 안 제약(ADR-013 하네스): `import`/`export` 금지, 함수는 반드시 `function` 선언(arrow `const` 는 vm 컨텍스트에서 못 꺼낸다), `document`·`window` 접근 금지, 모듈 상태 `let` 은 블록 밖에 두고 테스트가 prelude 로 재선언.

### 3.4 두 단계 API — 프리로드 후 동기 조회 (§6 에서 벗어나는 점 ②)

ADR-037 §6 은 `resolveDate(dateStr)` 만 적었다. 이를 **async 로 두지 않는다.**

```js
await preloadCalendar();          // 소형 표 5종
const day = resolveDate("2026-04-05");   // 동기 · 순수
```

**근거 셋**:

1. **캘린더 월간 뷰가 한 화면에 42칸을 그린다.** `resolveDate` 가 async 면 42개의 promise 를 조율해야 하고, ADR-038 §2 가 순수 함수로 규정한 `buildMonthGrid`·`buildWeekStrip`·`buildAgendaList` 가 async 로 오염된다.
2. **중복 fetch 가 구조적으로 사라진다.** `data-fetch.js` 의 캐시는 값 캐시라 같은 tick 에 여러 번 부르면 fetch 가 여러 번 나간다(현 코드의 알려진 한계). 42칸이 각자 로드를 시도하는 상황에서 이 한계가 그대로 드러난다. 프리로드를 분리하면 진입점이 한 곳이라 문제 자체가 성립하지 않는다.
3. **테스트가 쉬워진다.** 순수 동기 함수는 표를 인자로 넘겨 바로 검증할 수 있다.

프리로드 전에 동기 API 를 부르면 **명확한 오류를 던진다** — `throw new Error("preloadCalendar() must be awaited before resolveDate()")`. 조용히 빈 값을 주면 뷰가 "그날은 아무 날도 아님"으로 잘못 그린다.

내부적으로 프리로드는 **promise 를 캐시**한다(값이 아니라). 뷰 두 곳이 동시에 진입해도 fetch 는 한 번이다.

**실패한 promise 는 캐시하지 않는다.** `??=` 만 쓰면 일시적인 네트워크 오류로 한 번
reject 된 promise 가 영구히 남아, 사용자가 화면에 다시 들어와도 fetch 를 재시도하지
않고 같은 오류만 즉시 되던진다 — 오프라인에서 한 번 열면 온라인이 되어도 달력이 계속
깨진 채로 있는다는 뜻이다. 거부되면 캐시를 비워 다음 진입이 다시 시도하게 한다.

```js
function preloadCalendar() {
  return (calendarPromise ??= Promise.all([...])
    .then((t) => (calendarTables = t))
    .catch((e) => { calendarPromise = null; throw e; }));   // 재시도 가능하게
}
```

독서 묶음 프리로드(§3.5)도 같은 처리를 한다 — 캐시 대상이 둘이라 한쪽만 고치면
증상이 절반만 사라진다.

### 3.5 데이터를 두 묶음으로 가른다 (§6 에서 벗어나는 점 ③)

`/data/lectionary/` 전체는 약 2MB 다. 캘린더 한 달을 그리는 데 그 전부가 필요하지는 않다.

## 4. A1-a 계산 계층

모든 날짜는 로컬 `new Date(y, m - 1, d)` 와 `"YYYY-MM-DD"` 문자열로 다룬다. **`toISOString()` 으로 날짜 문자열을 만들지 않는다** — UTC 오프셋 때문에 KST 에서 하루 어긋난다(ADR-037 §6 이 명시적으로 지시). 포맷은 `padStart(2, "0")` 수동 조립(`bookmark-menu.js` 선례).

### 4.1 날짜 유틸

저장소에 날짜 유틸 공용 모듈이 없다. 엔진이 첫 소유자가 된다 — 전부 `LITURGICAL_CORE` 안의 순수 함수로.

| 함수 | 역할 |
|---|---|
| `parseDate(s)` | `"YYYY-MM-DD"` → `{y, m, d}`. 형식이 틀리면 `null`(throw 아님 — `search.js:199` 선례) |
| `toKey(y, m, d)` | → `"YYYY-MM-DD"` |
| `addDays(s, n)` | 날짜 문자열 덧셈 |
| `dayOfWeek(s)` | 0(일)~6(토) |
| `dayOfYear(s)` | 1~366. **윤년의 2/29 를 센다** — 연중 주차 `doy` 앵커가 이 정의를 전제 |
| `nearestSunday(s)` · `firstSundayAfter(s)` · `lastSundayBefore(s)` · `nthSunday(y, m, n)` | 이동 규칙 평가용 |

### 4.2 부활절 computus

**Anonymous Gregorian algorithm(Meeus/Jones/Butcher)**, 정수 연산 15줄(ADR-036 §11 채택). 서방 그레고리력 — 정교회 율리우스력 computus 가 아니다.

교회력 부활절은 **천문값이 아니다**. 교회력 춘분을 3월 21일로 고정하고 교회 보름표(epact)를 쓰므로 천문 계산과 어긋나는 해가 있다. 닫힌 산식이라 재구현이 안전하고 외부 데이터가 0 이다.

`easterDate(y)` → `"YYYY-MM-DD"`. 연도별 캐시(§4.9).

### 4.3 부활절 기준 오프셋

데이터의 `rule` 이 이미 `{kind: "easter_offset", days: -46}` 형태로 풀려 있다(ADR-036 개정①이 "빌드 시 1회 구조화"로 정한 결과, `temporal-feasts.json` 실측 확인). **엔진은 문법을 다시 파싱하지 않고 `rule.kind` 로만 분기한다.**

`easter_offset` 레코드는 실측 **12건**이다.

| 날 | 오프셋 |
|---|---|
| 주의 변모 주일 | E − 49 |
| 재의 수요일 | E − 46 |
| 성지(고난)주일 | E − 7 |
| 성 목요일 · 성 금요일 | E − 3 · E − 2 |
| 성 토요일 · **부활밤** | **둘 다 E − 1** |
| 부활대축일 | E + 0 |
| 승천 | E + 39 (목요일) |
| 성령강림 | E + 49 |
| 성삼위일체 | E + 56 |
| 그리스도의 성체 | E + 60 |

두 가지를 구별해 둘 것:

- **성 토요일과 부활밤이 같은 오프셋(E−1)을 갖는다.** `easter_offset → 레코드` 인덱스도 1:N 이어야 한다.
- **사순 1주일(E−42)은 이 표에 없다.** ADR-036 §11 이 오프셋으로 서술했지만 데이터에서는 이름 있는 이동 축일이 아니라 **격자 좌표**(`season: lent, week: 1, type: sunday`)다. 사순 스팬이 확정되면 주차로 나오므로 규칙이 필요 없다. 격자로 나오는 날을 규칙 표에 중복 등록하면 후보가 두 번 오른다.

**나머지 규칙 종류**(실측 `_meta.rule_kinds` **7종** — 2026-08-09 에 `ember_wfs` 가 더해졌다):

| `rule.kind` | 건수 | 부속 필드 | 예 |
|---|---|---|---|
| `easter_offset` | 12 | `days` | 위 표 |
| `nth_sunday` | 4 | `month`, `nth` | 가정주일 5월 2번째 · 추수감사 11월 3번째 |
| `first_sunday_after` | 1 | `month`, `day` | 주님의 세례 = 1.6 **이후** 첫 주일(엄격히 이후) |
| `nearest_sunday` | 1 | `month`, `day` | 대림 1주일 = 11.30 최근접 |
| `advent1_offset` | 1 | `days` | 왕이신 그리스도 = 대림1 − 7 |
| `last_sunday_before` | 1 | `month`, `day` | 평화통일주일 = 8.15 직전 주일 |
| **`ember_wfs`** | **4** | `anchor` (`easter_offset` 또는 `date`) | 사계재 — 2026-08-09 입력 |
| `date` | 0 | — | `_vocab` 에만 있고 미사용 |

`rule` 자체가 `null` 이면 **건너뛴다**(현재 해당 레코드 없음).

#### `ember_wfs` — 규칙 하나가 날짜 셋을 낳는다

다른 규칙은 전부 `규칙 1개 → 날짜 1개`인데 사계재만 다르다. **앵커 다음의 수·금·토 사흘**을 만든다.

```
춘계재  anchor = easter − 42 (사순 1주일)      → 그 주의 수·금·토
하계재  anchor = easter + 49 (성령강림)        → 그 주의 수·금·토
추계재  anchor = 09.14 (성 십자가)             → 다음 수·금·토
동계재  anchor = 12.13 (성 루시아)             → 다음 수·금·토
```

기준은 **로마 관행 준용**(사용자 확인 2026-08-09) — 표의 비고에 적혀 있던 통례와 같다.

구현 주의 둘:

1. **"다음"은 엄격히 이후다.** 앵커가 이미 수요일이면 그날이 아니라 **다음 주 수요일**부터 센다. `first_sunday_after` 가 "엄격히 이후"인 것과 같은 규약이다.
2. **한 레코드가 후보 셋을 낳으므로 요일로 갈라야 한다.** 독서·본기도는 사계재를 **지향(志向)별**로 나눠 두었고(「성직자의 성소를 위한 …계재」 등, 계절이 아니라 지향이 축이다) 계절은 본문을 가르지 않는다 — 지향 4종이 곧 본문 4종이다.

   **2026-08-29(data PR#17)로 요일 배정이 닫혔다.** 정본이 `calendar/ember.md` 한 곳으로 모이고 파서가 계절 × 요일로 펴면서 **16건 전부 `weekday` 를 갖는다**(종전 6건). 배정은 네 계절 공통 — **수=성직자 · 금=성직후보자·수도자(2본) · 토=모든 신자**.

   **다만 계절을 가리키는 기계 필드는 아직 없다.** 실측: 본문 레코드는 `season: null`(춘계재만 `lent`/`week 1` 인데 이건 *전례* 절기지 사계재 계절이 아니다) · `coord_name` 필드 자체가 없고, temporal 쪽 4행도 `coord_name: null` 이다. 사계재 계절은 **한국어 `name` 안에만 있다** — temporal `"하계재"`, 본문 `"성직자의 성소를 위한 하계재 수요일"`.

   → **오늘 가능한 조인은 이름 부분문자열뿐이다**: temporal 행의 `name` 이 본문 레코드의 `name` 에 포함되는가 + `weekday` 일치. 네 계절 이름이 서로의 부분문자열이 아니므로 동작은 하지만, 이름 표기가 바뀌면 조용히 끊어진다. **명시적 기계 키(양쪽에 `ember_season` 같은 필드)가 후속 과제다** — §9 미결5.

   금요일은 **후보가 둘**(성직후보자·수도자)이므로 하나를 고르지 말고 둘 다 낸다.

### 4.4 대림 앵커

**대림 1주일 = 11월 30일에 가장 가까운 주일** = 성탄일 전 네 번째 주일(ADR-036 §11). 세 표현은 동치다.

`advent1Date(y)` → 그해 **전례년 시작**. 왕이신 그리스도 주일 = `advent1 − 7`(연중 34주일).

**전례년 경계 주의**: 경계는 **달이 아니라 `advent1Date(y)` 그 날**이다. 대림1주일은 **11.27~12.03** 사이에 온다(1900~2100 실측: 각 날짜가 28~29회씩 고르게). 「12월부터 새 전례년」으로 잡으면 12월 1~2일을 **어떤 해에만 틀리게** 넣는다 — 2023-12-01 은 아직 전년 전례년(그해 대림1주일이 12.03)이고 2024-12-01 은 새 전례년이다. 매년 틀리면 금방 드러나는데 이건 해마다 갈려서 오래 숨는다. 반드시 `date >= advent1Date(y)` 로 비교할 것. 1월 1일의 전례년은 **전년도** 대림에 시작한 것이다. `liturgicalYearOf(dateStr)` 를 따로 두고 주일 주기 산정이 이 함수만 보게 한다.

### 4.5 절기 스팬 — 먼저 확정하고, 남는 자리가 연중

`season` 도메인은 **다섯**이다: `advent` · `christmas` · `ordinary` · `lent` · `easter`. **`epiphany` 는 없다**(ADR-036 §4 개정 2026-07-17에서 제거). 공현일(1.6)은 성탄절기 안의 sanctoral 대축일일 뿐이다.

| 절기 | 스팬 |
|---|---|
| `advent` | 대림 1주일 ~ 12.24 |
| `christmas` | 12.25 ~ **주의 세례 주일 전날** |
| `lent` | 재의 수요일 ~ 부활 전날 (마지막 한 주간이 성주간) |
| `easter` | 부활주일 ~ 성령강림주일 (50일) |
| `ordinary` | 나머지 전부 — ① **주의 세례 주일**(= 연중1주일) ~ 재의 수요일 전, ② 성령강림 다음 주간 ~ 대림 1주일 전 |

**주의 세례 주일은 연중시기의 첫날이다 — 좌표는 하나다**(2026-09-01 판정, 2026-09-13 회수·검증). 종전 서술은 이 날이 `christmas` 이면서 동시에 연중 1주일이라 **좌표를 둘** 내야 한다고 적었다(§9 미결10, 🔴). 그것이 아니라 좌표는 하나이고 **`ordinary` · week 1 · `sunday`** 다. `ResolvedDate` 스키마도 특례도 만들지 않는다. 근거 셋은 **전사에 명시된 규칙이 아니라 전사에서 도출한 것**이라 사제 확인 대상으로 둔다(검토 문서 Q11).

- **주요축일(가) 3항** — 「나머지 축일은 연중주일보다 우선하지만 **절기주일과 겹치면 다음날로 옮겨 지킨다**」. 이 날이 절기주일이면 규칙이 다음날로 옮기라 명령하는데, 이 축일은 정의가 「1.6 이후 첫 주일」이라 **옮길 자리가 없다**(데이터도 `transferable: false` · `transfer_to: null`). 연중주일일 때만 앞뒤가 맞는다 — 가 그룹에서 `outranks_sunday: false` 인 나머지 여섯은 전부 `transfer_to: next_day` 다.
- **전사가 그날을 「연중 첫 주일」이라 부른다(139행)** — 「예외: **연중 첫 주일인 주의 세례 주일**, 왕이신 그리스도 주일은 백색」. 녹색(= 연중시기) 규칙 **안의** 예외이고 짝인 왕이신 그리스도 주일은 연중34주일이다 — **연중시기의 첫 주일과 마지막 주일**을 묶은 문장이다. 그리고 **13행이 「주의 세례 주일 … 부터 재의 수요일 전까지」를 연중시기로 정의**한다(「부터」는 포함).

**반대 방향 증거도 있다 — 전사 자체가 이 하루를 양쪽에 적어 두었다**(2026-09-13 전수 확인). 성탄절기 쪽: **9행**(「성탄절기: 성탄일부터 주의 세례 주일(연중1주일)까지」) · **24행**(성탄절기 백색 목록에 「… 공현일, **주의 세례**」) · **107행**(백색 기간 「성탄일부터 주의 세례 주일까지」). 연중시기 쪽: **13행 · 139행**(위). 9행은 괄호로 「(연중1주일)」을 달아 스스로 겹침을 드러낸다. **색으로는 갈리지 않는다** — 어느 쪽으로 읽어도 그날은 백색이다(성탄절기 규칙으로든 139행 예외로든). 갈리는 것은 **절기 좌표와 그에 따른 승자**뿐이고, 그래서 판정이 필요했다.
- **데이터가 이미 그렇다** — `t-주님의-세례` 가 `season: "ordinary"` · `week: 1` · `type: "sunday"` 이고, 본문도 `ordinary-1-sun-주님의-세례-{A,B,C}` 로 실려 있다(2026-09-13 실측).

**종전 미결의 근거였던 「연중 주차 표가 세례주일을 1주로 두고 앞으로 센다」는 사실이 아니다.** 1주 구간은 **날짜 창 `01-07`~`01-13`**(anchor `doy`)이고 `first_sunday_after 1.6`(엄격히 이후)은 **1900~2100 전 연도에서 예외 없이** 그 창 안에 든다(2026-09-13 재검증 — 창 밖 0건). 두 정의가 구조적으로 같은 날을 가리키므로 특례 없이 표가 그대로 맞는다.

**이것이 승자도 정한다.** 격자를 `christmas` 주일로 합성하면 절기 주일이라 유효 prec **2** 가 되어 `t-주님의-세례`(prec 3)를 **이기고** 「성탄 N주일」이 `official` 이 된다 — 그런데 그 축일은 `transferable: false` 라 옮겨지지도 않는다. `ordinary/1`(연중 주일 5)로 합성해야 주님의 세례가 이긴다. 동률이 아니라 §6.2 ④ 사다리로는 풀리지 않으므로, **이 판정이 곧 그날의 승자 판정**이다.

판정 순서: **절기 스팬을 먼저 확정**하고, 어느 스팬에도 안 들면 `ordinary` + 구간표 조회. 연중 스팬 밖에서는 표를 보지 않는다.

### 4.6 연중 주차 — `anchor` 와 윤년 함정

`ordinal-weeks.json` 은 `{_meta, weeks}` 이고 `weeks[]` 원소가 `{week, windows: [{from, to, anchor}]}` 다. 34주 · 구간 38개. 실측 분포: **6~9주만 구간이 둘**(`doy` + `date`), 1~5주는 `doy` 하나, 10~34주는 `date` 하나. 구간 폭은 전부 7일이고 **9주의 `doy` 구간만 4일**(`03-04`~`03-07`)이다 — 사순이 시작되며 잘리는 자리다.

구간의 의미는 "**그 주간의 주일이 떨어지는 범위**"다. 평일은 자기 날짜로 찾지 않고 **그 주의 주일로 조회**한다.

| 구간 | `anchor` | 조회 |
|---|---|---|
| 공현 후 (1~9주) | `doy` | **연중 일수**로 맞춘다(2/29를 셈) |
| 성령강림 후 (6~34주) | `date` | **월/일 그대로** 맞춘다 |

**왜 갈리는가 (ADR-037 §4 개정 2026-07-13)**: 표의 구간은 1/7부터 7일씩 끊은 블록이라 **2월이 28일일 때만** 맞아떨어진다. 윤년에는 2/29 가 3월을 하루 밀어 8주 구간(2/25–3/3)이 8일이 되고, **2052년(부활절 4/21)에는 2/25 와 3/3 이 둘 다 그 구간에 든다**. 정답은 3/3 = **9주**(세례주일부터 세면 아홉 번째 주일)이고, 9주 구간(3/4–3/7)은 그해 빈 채로 남는다. 뒤 구간은 7일 날짜 블록이 항상 주일을 정확히 하나 품으므로 날짜 조회만으로 윤년에 안전하다.

**이 두 줄이 엔진에서 가장 틀리기 쉬운 자리다.** 2052년을 회귀 테스트로 못박는다(§7).

산정 방식이 **표 조회**임에 주의 — ADR-036 §11 의 "왕이신 그리스도(34주)에서 역산"은 ADR-037 이 B안으로 **기각**했다("기도서 표와 어긋날 위험을 코드가 지게 됨"). 구현자는 ADR-037 을 따른다.

### 4.7 주기 산정

- **주일 A/B/C** — **대림 시작 기준 3년 주기**. 달력년이 아니라 전례년(§4.4)에 걸린다.

  **기준 연도: 2026년 = 가해(A)**(사용자 확정 2026-08-29). 여기서 전체 주기가 결정된다 —
  전례년을 **그 해가 끝나는 달력년** `N` 으로 부르면 `N % 3` 이 **1 → A · 2 → B · 0 → C** 다.
  (2025 다해 · 2026 가해 · 2027 나해 · 2028 다해 …)

  경계는 1월 1일이 아니라 **대림1주일**이다. 실제 날짜로:

  | 날짜 | 주기 |
  |---|---|
  | 2025-11-29 (토) | 다해(2025) 마지막 |
  | 2025-11-30 (일, 대림1주일) | **가해(2026) 시작** |
  | 2026-11-28 (토) | 가해(2026) 마지막 |
  | 2026-11-29 (일, 대림1주일) | **나해(2027) 시작** |

  이 네 날은 회귀 테스트에 그대로 넣는다 — 오프셋이 하나 틀려도 예외 없이 다른 해 본문이
  나오므로, 경계에서 값이 바뀌는지를 직접 못 박아야 한다.
- **평일 I/II** — **홀·짝 달력년** 2년 주기.

두 축의 기준이 서로 다르다(ADR-037 §6 원문 그대로). 12월 대림 이후 날짜에서 주일 주기는 이미 넘어갔는데 평일 주기는 아직 안 넘어간 구간이 생긴다 — 의도된 동작이다.

연중 평일만 `I/II` 를 갖고, 그 밖 절기 평일·축일·재일은 대체로 `null`.

### 4.8 음력

`kasi-lunar.json` 은 `{_meta, years}` 이고 `years` 는 **문자열 연도 키 → `{"1-1": "MM-DD", "8-15": "MM-DD"}`** 2키 고정 맵이다(`_meta.range: [2025, 2050]`, `complete: true`, 결측 0). 성인력 레코드는 `date: null` + `lunar: "1-1"`(설) / `"8-15"`(추석)이고, 엔진이 `lunar` 를 보면 표에서 그해 양력 날짜를 끌어온다. `lunar` 값이 `years` 의 내부 키와 **문자 그대로 일치**하므로 변환 없이 조인된다 — 다만 표의 값은 `MM-DD` 하이픈이라 `MM.DD` 계열과 비교하려면 정규화가 필요하다(§5.2).

천문 계산을 내장하지 않는다. 한국 음력은 중국 농력과 기준 자오선이 달라(KST 135°E vs 베이징 120°E) 드물게 하루 어긋나므로 **반드시 KASI 표**여야 한다(ADR-036 §9).

### 4.9 연도 캐시

한 해의 부활절·대림 앵커·이동 축일 날짜는 **연도당 한 번만** 계산한다.

```js
/** @type {Map<number, YearAnchors>} */
const anchorCache = new Map();     // { easter, advent1, movable: Map<"MM-DD", Observance[]> } — 순수 계산 (A1-a)
/** @type {Map<number, TransferPass>} */
const transferCache = new Map();   // §6.5 이동 패스 — 항목은 언제나 완전한(seed 받은) 패스 (B1)
// TransferPass = {
//   arrivals:   Map<"YYYY-MM-DD", Candidate[]>,   // transferred_in — 옮겨 와서 이 날 지키는 것
//   departures: Map<"YYYY-MM-DD", Candidate[]>,   // transferred_out — 이 날을 떠난 고유 후보 (도착은 다시 밀리지 않는다 — §6.2 ②)
//   optionals:  Map<"YYYY-MM-DD", Candidate[]>,   // optional — 선택 봉헌 목적지 주일 (§6.2)
//   defects:    string[],                          // 이동 상한을 넘긴 축일 (§6.5) — 개발 빌드 표시용
// }
```

**캐시가 둘인 이유**(2026-09-05 리뷰): 연도 경계 처리(§6.5)가 **임시 패스**를 돌리는데, 그 결과를 `Y−1` 의 정식 항목으로 남기면 안 된다(seed 없이 만든 부분 패스라). **어느 패스든 `year` 앵커만 쓰지 않는다**(2026-09-13 정정): 다음 해 좌석(`nextYearSeats` — §6.5)이 `optionalObservancesOf(year + 1)` 을 보는데 그중 승천(`easter7_sunday`)은 **부활절 기준**이라 `year + 1` 의 앵커를 요구한다. 그래서 그 좌석은 **목적지 탐색이 실제로 해를 넘길 때만 지연 계산한다** — 그 전에는 다음 해 computus 를 돌리지 않는다. 앵커와 패스를 한 항목에 두면 「앵커는 있고 패스는 없는」 반쪽 항목이 생기고, 뒤의 `resolveDate(Y−1)` 가 그것을 완성된 것으로 재사용할 수 있다. 캐시를 가르면 `anchorCache` 는 어느 경로로든 채워도 되고(순수 파생값), `transferCache` 는 **완전한 패스만** 들어간다 — 부분 상태가 표현될 자리가 없다.

캘린더 월간 뷰가 42칸을 그리며 `resolveDate` 를 42번 불러도 computus 는 **최대 세 번** 돈다 — 한 해 `Y` 의 완전한 패스가 seed 를 위해 `Y−1` 앵커를 요구하고(§6.5 연도 경계), 42칸이 `Y`·`Y+1` 을 걸치면 `Y−1`·`Y`·`Y+1` 이다. 한 해만 걸리면 두 번. **다음 해 좌석이 지연 계산이라 이 셈이 유지된다**: 현재 표에서는 12월 이동이 해를 넘기지 않으므로 `nextYearSeats` 가 앵커를 요구하는 일이 없다. 표가 바뀌어 `Y+1` 패스의 12월 이동이 실제로 해를 넘기면 그 해만 `Y+2` 앵커가 더 필요해 **네 번**이 된다 — 드물고, 캐시되므로 한 번뿐이다. `anchorCache` 는 순수 파생값이라 무효화가 필요 없다. `transferCache` 는 선택 봉헌 활성화 집합(§6.2 `activated`)에 의존하는 **유일한** 입력이 있어, 그 설정이 바뀌면 통째로 비운다.

`transferCache` 의 항목은 §6.5 이동 패스의 결과다 — 그해 안에서 옮겨간 축일이 **어디에 도착했고 어디서 떠났는지**의 색인. PR 2 까지는 빈 패스이고 PR 3 이 채운다(§8). `Y` 의 항목은 `Y−1` 12월에서 넘어온 spill 을 seed 로 받아 만든다(§6.5 연도 경계). 그 seed 를 얻기 위한 `Y−1` 의 **seed 없는 임시 패스는 `transferCache` 에 넣지 않는다** — `Y−1` 항목이 따로 필요해지면 그때 `Y−2` spill 로 완전하게 만든다. 임시 패스가 쓰는 `Y−1` 앵커는 `anchorCache` 에 남아도 된다.

### 4.10 기간 축 — `spansOf(year)` (검토 문서 §3.1 채택, 2026-09-13)

절기(§4.5)와 **독립된 축**이다. 절기는 한 해를 빈틈없이 나누지만 기간은 **겹쳐 얹히고** 서로 포개진다. 앵커(부활 · 대림 · 성탄 · 세례주일)만으로 순수 계산하므로 데이터가 필요 없다 — `LITURGICAL_CORE` 안의 함수이고 `anchorCache` 와 같은 연도 캐시를 쓴다.

**반환은 스팬마다 `[from, to]` 구간의 배열이고, 구간은 그 달력년으로 잘려 있다**(9차 리뷰). 부활절 기준 스팬은 언제나 한 해 안에 들지만(부활은 3.22~4.25) **성탄 기간 둘은 해를 넘긴다** — 한 해에 두 조각으로 나타난다. 소비자는 범위를 직접 비교하지 않고 `inSpan(dateStr, name)`(구간 중 하나에 들면 참)으로 묻는다 — **표를 인자로 받지 않는다**(2026-09-17 리뷰): 스팬이 달력년으로 잘려 있으므로 어느 해의 표인지가 답을 바꾸고, 호출부가 루프 밖에서 `spansOf(Y)` 를 뽑아 들고 다니면 이웃 해 날짜에서 성탄 기간의 1월 조각이 통째로 거짓이 된다. 연도는 **날짜가** 정하고 반복 비용은 `spansCache`(§4.9 와 같은 연도 캐시)가 흡수한다. **모르는 이름은 throw** 한다 — 스팬 이름은 데이터가 아니라 코드라 오타는 결손이 아니라 결함이고, 조용히 `false` 를 내면 가드가 꺼진 채로 돈다(이 절이 없애려던 바로 그 어긋남이다).

| 기간 | 구간 (`spansOf(Y)` 기준) | 조각 | 소비자 |
|---|---|---|---|
| `holyWeek` | 성지주일 ~ 성 토요일 (E−7 ~ E−1) | 1 | §6.4 색 가드(전체 홍 — E−1 은 미결20) |
| `easterOctave` | 부활대축일 ~ 부활2주일 (E+0 ~ E+7) | 1 | §6.4 색 가드 |
| `transferGuard` | **성지주일 ~ 부활2주일** (E−7 ~ E+7) | 1 | §6.5 `guard(d)` — 위 둘의 합 |
| `ascensionToPentecost` | **승천 다음날** ~ 성령강림 전날 (E+40 ~ E+48) | 1 | §5.3 부활6주 금·토 본기도 병합의 근거(데이터 `_note`) |
| `dec17to24` | `Y`-12.17 ~ `Y`-12.24 | 1 | §5.4 의 날짜 전용 본문 범위 확인 |
| **`christmasToBaptism`** | **① `Y`-01-01 ~ 주의 세례 주일(`Y`) 전날** · **② `Y`-12-25 ~ `Y`-12-31** | **2** | §6.3 ① 소재일 제외 |
| **`christmasOctave`** | **① `Y`-01-01 ~ `Y`-01-01** · **② `Y`-12-25 ~ `Y`-12-31** | **2** | 배너 · 후속 |

**왜 자르나.** 성탄절기는 `Y−1`-12-25 에 시작해 `Y` 의 세례주일에 끝나고, 또 `Y`-12-25 에 다시 시작한다. 한 스팬을 구간 **하나**로 내면 어느 쪽을 고르든 그 해의 반대쪽 끝을 놓친다 — `Y−1`-12-25 부터로 두면 `Y` 의 12월이, `Y`-12-25 부터로 두면 `Y` 의 1월이 빠진다. §6.3 ① 이 「성탄절기 금요일은 소재일이 아니다」를 그 함수로 판정하므로 한쪽 끝이 통째로 틀린다. 잘라 두면 `spansOf` 가 `anchorCache` 와 같은 **달력년 단위**로 남고 인접 연도를 함께 조회할 필요가 없다. 두 조각의 경계(1월 · 12월)를 테스트가 양쪽 다 잡는다(C-P-4).

**`ascensionToPentecost` 가 E+39 가 아니라 E+40 에서 시작하는 것도 같은 종류의 경계다**(12차 리뷰) — 정본 전사가 「승천일 **이후** 성령강림주일 전까지」라 적었고, §5.3 의 근거 사례도 승천일이 아니라 **부활6주 금·토**(E+40 · E+41)가 승천 본기도를 쓰는 것이다. 승천일(E+39, 목)은 자기 고유 본기도를 가지므로 이 기간에 넣으면 그날의 본기도가 뒤바뀐다.

조각 ① 의 끝은 **주의 세례 주일 전날**이다(§4.5 — 세례주일부터 연중시기). 금요일만 보는 소비자(§6.3 ①)에게는 세례주일이 언제나 주일이라 포함·제외가 결과를 바꾸지 않지만, 경계는 §4.5 와 하나여야 한다. **주의 세례 주일은 `Y` 의 앵커만으로 나온다**(`first_sunday_after` 1.6 — 부활절과 무관). computus 횟수는 늘지 않는다(§4.9 최대 세 번 그대로).

**왜 한 함수로 모으나.** 지금 성주간 · 부활 8일 보호를 **세 곳이 각자 날짜 비교**로 갖고 있다 — §6.3 ①(소재일 제외) · §6.4(색 가드) · §6.5 `guard`. 셋 중 하나만 경계를 다르게 고치면 색과 이동이 어긋나는데, 테스트가 셋을 따로 보면 그 어긋남이 안 잡힌다. 하나로 모으면 경계가 한 곳이고 그 한 곳을 검사한다. romcal 도 `periods` 를 데이터가 아니라 코드로 계산한다.

**`periods.json` 에 넣지 않는다.** 그 표의 `_meta.model` 은 「품계 비교에 참여하지 않는 겹침 표시 — 고정 본기도 · 전례색 · 품계 없음」이고 항목이 고정 `MM.DD` 다(실측 1건, 그리스도인 일치 기도 주간). 보호 기간은 품계에 참여하고(합성 `guard` 가 유효 prec 1 이다) 부활절 기준이라 그 표의 계약과 스키마 둘 다에 맞지 않는다 — 넣으려면 규칙 문법과 파서가 데이터 저장소에 생겨야 한다. `ResolvedDate.periods` 는 지금처럼 **데이터 오버레이(배너용)** 로 남긴다. 이름이 비슷할 뿐 다른 축이고, `spansOf` 는 `candidates` 에도 `periods` 에도 실리지 않는다 — 엔진 내부 판정용이다.

**모든 파일이 객체 래퍼를 쓴다.** 배열 최상위는 하나도 없다.

| 파일 | 래퍼 |

**날짜 표기가 세 가지 섞여 있다.** 이것이 이 계층에서 가장 조용히 깨지는 자리다.

| 표기 | 쓰는 곳 |
|---|---|
| `MM.DD` (점) | `sanctoral.date` · `periods.from`/`to` · `readings`/`collects` 의 `date` |
| `MM-DD` (하이픈) | `ordinal-weeks` 의 `from`/`to` · `kasi-lunar` 의 값 |
| `M-D` (하이픈, 0 채움 없음) | `lunar` 필드의 값과 `kasi-lunar.years[y]` 의 키 |

→ **내부 표준을 하나 정하고 로드 시점에 정규화한다.** 비교 함수마다 표기를 분기하면 반드시 한 곳을 빠뜨린다.

그 밖에 못박아 둘 실측:

- **`id` 타입이 파일마다 다르다** — readings 는 문자열(`ordinary-9-sun-A-t1-s1`), collects 는 **정수**(1~327). 동점 정렬 키로 쓸 때 숫자·문자 비교를 섞지 않는다.
- **readings 의 `id` 접미 `-t1-` 을 트랙으로 읽으면 안 된다** — `reading_track: null` 인 745건에도 관례적으로 `t1` 이 붙어 있다. 트랙은 반드시 필드로 판정한다.
- **같은 `date` 에 여러 성인이 있다** — 13개 날짜가 2~3건씩(12.25 는 3건). `easter_offset: -1` 도 성 토요일·부활밤 2건이다. 날짜 인덱스는 **1:N Map** 이어야 한다.
- **`weekday`·`year`·`color_alt` 는 `null | 스칼라 | 배열` 3형이고 배열은 collects 에만 있다.** 원소가 하나인 배열(`["mon"]`)도 실제로 존재하므로 `typeof === "string"` 분기만으로는 틀린다 — `Array.isArray` → `includes`, `null` → 무조건 매치, 스칼라 → 등호 세 갈래가 모두 필요하다.
- **`penitential: true` 는 사계재 4건에만 있고 다른 레코드에는 키 자체가 없다.** 소재일 판정에서 `record.penitential === true` 로 읽어야 한다.
- **`ending` 은 A 317 · C 10 · B 0**(2026-09-01) — ADR-037 미결1(송영 A/B 구분 규정)이 데이터로도 미해결임이 확인된다.
- **`_review` 는 이제 0 건이다**(2026-08-29, data PR#17) — 21건을 전수 판별해 10건은 교정하고 나머지는 규칙으로 판정했다. 대신 **`_note` 가 1건**에 붙는다(부활6주 금·토: 승천대축일 본기도를 쓴다는 표시). 둘 다 사람이 읽는 메모라 엔진은 무시하고 통과시키되, `_review` 가 다시 나타나면 그 본문은 기도서 대조 전이라는 뜻이다.

### 5.3 폴백 매칭 — 구체성 점수

ADR-036 §4 의 규칙: `weekday`·`year` 두 필드가 **`null | 코드 | 코드 배열`** 로 동형이고, **더 구체적인 레코드가 우선**한다.

이를 점수로 구현한다. 각 축마다:

| 레코드 값 | 요청과의 관계 | 점수 |
|---|---|---|
| 단일 코드, 일치 | 가장 구체적 | 2 |
| 배열, 포함 | 중간 | 1 |
| `null` | 공통 | 0 |
| 그 밖 | 불일치 | **탈락** |

`season`·`week`·`type` 은 정확히 일치해야 한다(폴백 없음).

**총점이 높은 레코드가 이기되, 이기는 것은 「한 건」이 아니라 「한 층」이다.** 최고점 레코드를 **전부** 남기고 그 다음에 그룹으로 묶는다 — 같은 좌표에 **의도적으로 공존하는** 레코드가 있기 때문이다: 자유선택 대체 본기도(`collect_no`, 실측 34 엔트리)와 독서의 `set_no`·`reading_track` 세트(실측 `set_total > 1` 163건). 이들은 `weekday`·`year` 가 동일해 점수도 같으므로, 최고점에서 하나만 골라내면 §5.6 과 ADR-036 §2 의 반환 계약이 깨진다 — 뷰가 택1 탭으로 보여야 할 두 본기도 중 하나가 사라진다.

즉 순서는 **① 불일치 탈락 → ② 최고점 층만 남김 → ③ `collect_no` / (`reading_track`, `set_no`) 로 그룹화 → ④ 그룹 안에서 안정 정렬**이다.

```js
function matchScore(record, coord) { … }   // -1 = 불일치
```

**동점 처리를 반드시 결정해 둔다.** 위 ②에서 남은 동점은 **대부분 정상**이다(대체안·세트). 그룹이 갈린 뒤에도 같은 그룹 안에 동점이 남으면 그때가 데이터 결함 의심이다. 어느 경우든 배열 순서에 기대지 않고 **레코드 `id` 순**으로 안정 정렬한다(문자열은 사전순, 정수는 수치순 — §5.2 의 타입 차이). 정렬이 입력 순서에 의존하면 데이터 저장소가 재빌드할 때마다 결과가 흔들린다.

**왜 이런 폴백이 필요한가**: 한 주의 평일 본기도는 대개 하나이므로, 이름 없는 격자 평일은 `(season, week)` 단위로 모아 요일·주기를 가로질러 병합해 두었다(ADR-036 §2 개정). 실측으로 확인된 병합 사례:

- `사순3주` — 가·다해가 같고 나해만 달라 `year: ["A","C"]` 레코드 하나와 `year: "B"` 레코드 하나. **`year` 배열은 전 데이터에 이 1건뿐이다.**
- `부활6주` — `weekday: ["mon","tue","wed","thu"]` 와 `weekday: ["fri","sat"]` 로 갈린다. 이 경계가 **승천일**이다(승천 후 성령강림 전까지는 승천 본기도를 쓴다). ADR-036 §2 가 든 근거 사례가 데이터에 그대로 있다.
- `연중12주`·`연중21주` — 요일 구간이 갈리고 한쪽만 `year` 를 가진다.

같은 `(season, week)` 안에 **`weekday: null` 레코드와 배열 레코드가 공존**한다(연중3주: `weekday: null, year: null` 과 `weekday: ["mon"], year: "II"`). 구체성 우선 규칙이 없으면 그날 본기도가 뒤바뀐다 — 이 규칙은 선택이 아니다.

**중요한 예외 — `weekday: null` 이 항상 "그 주 평일 공통"을 뜻하지는 않는다.** 앞서 이 문서는 "독서 쪽에서 `null` 이 나올 일은 없다"고 적었으나 **실측이 이를 반증했다**: readings 의 `weekday` 는 **393건**이 `null` 이다(2026-08-29 실측). 다만 그 `null` 들은 폴백이 아니라 **고유명 날짜**다.

```
temporal-lent-성-토요일-t1-s1   name="성 토요일"    weekday=null  week=null
d1217-성탄-8일-전-t1-s1          name="성탄 8일 전"  weekday=null  date="12.17"
d1230-성탄주간-t1-s1             name="성탄주간"     weekday=null  date="12.30"
```

→ **판정 규칙**: `name` 또는 `date` 가 채워진 레코드는 폴백 해석을 하지 않고 **이름·날짜 조인 경로**로 보낸다(§5.4). `weekday: null` 을 무조건 "그 주 전체 공통"으로 읽으면 성 토요일 독서가 성주간 평일 전체에 퍼진다.

참고로 `성탄주간` 은 같은 `name` 에 **다른 `date`** 로 11개 날짜(12.30·12.31·1.3~1.5·1.7~1.12)에 복제돼 있다. 이름은 키가 아니고 날짜가 키다.

### 5.4 조인 전략 — 좌표가 정본, 이름은 보조

**본기도는 필드 참조가 아니라 좌표 조인이다** — readings 레코드에 collect 참조 필드가 없다. 같은 좌표로 `eucharist-collects` 를 §5.3 규칙으로 따로 조회한다(ADR-037 §1). 두 파일의 `id` 는 서로 무관하고(문자열 vs 정수) `reading_track` 은 collects 가 전부 `null` 이므로 **트랙 축은 readings 에서만 결정된다.**

정의 표(sanctoral·temporal-feasts)와 본문 표(readings·collects)를 잇는 키는 실측으로 갈렸다.

| 방향 | 키 | 근거 |
|---|---|---|
| **sanctoral ↔ readings/collects** | **`date`(`MM.DD`) + `lunar`** | 고유 본기도 52건 중 날짜 조인은 **본기도 52/52 · 독서 51/52 성공**(`date` 50 + `lunar` 2), 이름 조인은 35건만 성공. 독서에서 빠지는 하나는 프란시스 사베리오(12.03) — **고유 본기도 + 공통 독서**라 고유 독서가 없는 게 맞다(articles-supplement 의 `readings: null` 케이스). **다만 그것만으로는 이 날 독서를 못 찾는다** — `commons.json` 은 분류별 독서를 갖고 있는데(7분류 22세트, 사베리오의 `missionary` 는 3세트) §5.6 의 **성인 공통 독서 폴백**이 이 날을 맡는다(§9 미결11 해소 2026-09-17 — 종전에는 `findCollects` 폴백만 있고 독서 쪽 규칙이 없어, 데이터는 있는데 못 쓰는 자리였다). `lunar` 를 빼고 `date` 만으로 맞추면 설날·추석이 떨어져 나간다 |
| **temporal-feasts ↔ readings/collects** | **`coord_name` ↔ `name`**(`aliases` 도 키) | 정의 표가 조인용 이름 필드를 따로 들고 있다. 24건 중 `coord_name: null` 7건(대림1주일·가정주일·평화통일주일·사계재 4)은 이름 조인 대상이 아니다 — 대림1주일은 격자 좌표(`advent-1-sun-*`)로만 조회된다 |
| local-observances → commons | `dedication.common` / `observance.common` → `classes[키]` | 문자열 직접 참조 |
| local-observances → sanctoral | `patron_refs[].sanctoral_id` | 51건 전부 유효한 id 참조 |
| readings → canticles | `readings[].canticle` → `canticles[키]` | 5종(`magnificat` `benedictus` `ecce-deus` `benedicite` `te-deum`) |

**이름 조인이 왜 못 미더운가** — 같은 날인데 표기가 다르다.

| `sanctoral.name` | `collects.name` |
|---|---|
| `바실(주교, 379년)과 나지안조의 그레고리(주교, 389년)` | `바실과 나지안조의 그레고리` |
| `주의 봉헌` | `주의 봉헌 축일` |
| `성 세례 요한 탄생` | `성 세례요한 탄생 축일` |
| `성 미카엘과 모든 천사들` · `대한성공회 설립 기념일` (별개 2건) | `성 미카엘과 모든 천사들 / 대한성공회 설립 기념일` (슬래시로 합친 1건) |

**날짜 조인은 outer join 이어야 한다.** readings·collects 의 `date` 중 16개(12.17~12.24·12.30·1.3~1.12 일부)는 sanctoral 에 대응 행이 없다 — `성탄 8일 전`·`성탄주간` 처럼 **본문 표만 아는 날짜 좌표**다. 즉 그 `date` 는 "성인력 참조"가 아니라 **자기 좌표**이며, 성인력에 없다고 버리면 성탄 후 열이틀의 독서가 사라진다.

**그런데 날짜 인덱스는 1:N 이고, 그 N 을 좁히는 규칙이 아직 없다.** `findReadings(resolved, candidate)` 는 **고른 관측일 하나**의 본문을 내야 하는데 `date` 만으로는 그 날의 본문 전부가 나온다. 성인력에 두 행 이상인 날짜가 **13개**이고(2026-09-01 실측), 12.25 는 세 행(성탄 낮·밤·새벽) × 본문 6레코드다 — 낮을 물었는데 밤이 섞여 나오면 그건 결손이 아니라 **오답**이다. `name`·`aliases` 로 좁히는 것이 자연스러우나 그 이름 조인이 못 미더운 것은 바로 위 표가 말한 그대로다. 규칙과 잔여를 §9 미결12 에 못박았다.

**좁히기 규칙 ① — 날짜 전용 본문은 그날의 절기와 맞아야 한다**(사용자 확인 2026-09-01). **주의 세례 주일이 오면 그 뒤로 성탄주간 독서는 쓰이지 않는다.** 이 규칙은 전사에도 ADR 에도 적혀 있지 않아 누락돼 있었다.

기제는 간단하다. 레코드의 `season` 은 **고정값**인데 그날의 절기는 **계산값**이므로, 날짜로 뽑은 뒤 **레코드의 `season` 이 그날 계산된 절기와 같은 것만 남긴다.**

어긋날 수 있는 이유는 `1.7`~`1.12` 가 **공현 후 평일**이고 이 구간의 길이가 주의 세례 위치에 따라 **0~6일로 변하기 때문**이다 — 레코드는 날짜에 고정돼 있는데 구간은 움직인다.

| 세례일 | 성탄주간 레코드가 쓰이는 날 | 그 뒤 | 빈도(1900~2100) |
|---|---|---|---|
| 1/7 | **없음** | 1/8~1/13 = 연중1주 평일 | 29 |
| 1/8 | 1/7 | 1/9~ | 28 |
| 1/9 | 1/7~1/8 | 1/10~ | 28 |
| 1/10 | 1/7~1/9 | 1/11~ | 29 |
| 1/11 | 1/7~1/10 | 1/12~ | 29 |
| 1/12 | 1/7~1/11 | 1/13 | 29 |
| 1/13 | 1/7~1/12 | — | 29 |

세례가 1/7 인 해에는 공현 후 평일이 **아예 없다** — 1/8 부터 곧장 연중1주 평일이고 그날은 격자의 `ordinary-1-{mon..sat}` 이 맡는다. 반대로 `01.03`~`01.05` 는 **공현 전**이라 세례보다 뒤일 수 없어 언제나 성탄절기다.

**데이터가 이 경계를 이미 안다** — `01.13` 에는 성탄주간 레코드가 **없다**(2026-09-13 실측: `01.07`·`01.12` 에는 있다). 1/13 은 세례 당일이거나 이미 연중시기라 **공현 후 평일이 될 수 없는 유일한 날**이기 때문이다. 이 규칙은 미결12 의 1:N 좁히기 가운데 **날짜 전용 본문 갈래를 닫는다**(성인 1:N 잔여는 그대로 남는다).

**권장 인덱스** (프리로드 시 1회 구축):

1. `sanctoral`: `date → Entry[]`, `lunar → Entry[]` (둘 다 1:N)
2. `temporal-feasts`: `rule.kind → Entry[]`, `coord_name → Entry`
3. `readings`/`collects`: `date → Entry[]`, `(season, week, type) → Entry[]`, `name → Entry[]`
4. `ordinal-weeks`: **`doy` 인덱스와 `date` 인덱스를 분리** 구축(anchor 별로 비교 방식이 다르므로)

### 5.5 `resolveDate` — 후보 집합을 전부 보존한다

```js
/** @returns {ResolvedDate} */
function resolveDate(dateStr) → {
  date, coord,                 // 격자 좌표 (temporal)
  candidates: Candidate[],     // 그날 지킬 수 있는 관측일 전부 — 옮겨온 것 포함
  official: Candidate | null,  // 승자 (B1 — PR 3 전에는 null)
  periods: Period[],           // 겹쳐 얹히는 기간 (배너용)
  color, colorAlt,             // 승자 반영 최종 전례색 (B1)
}

/** @typedef {{
 *   observance: Observance,
 *   status: "proper" | "transferred_in" | "transferred_out" | "optional" | "commemorated" | "omitted",
 *   from?: string,          // 이 후보가 정의된 원래 날짜 "YYYY-MM-DD" — transferred_in·optional 에만. 계보가 아니라 기원.
 *                           //   optional 은 목적지가 원래 날짜보다 앞일 수 있어(2028-02-02 → 1.30) 미래 날짜가 온다
 *   to?: string,            // 이 날짜를 떠나 도착한 날짜 "YYYY-MM-DD" — transferred_out 에만
 *   displacedBy?: string,   // 밀어낸 것의 id — Observance.id 또는 §6.5 의 합성 id "guard:easter-octave".
 *                           //   **충돌**로 밀린 transferred_in·transferred_out·commemorated·omitted 에는 필수.
 *                           //   활성화된 선택 봉헌의 transferred_in·transferred_out 에는 **없다**(밀린 것이 아니라 택한 것 — §6.2).
 *                           //   소비자는 없음을 결함으로 보지 말고 「선택 이동」으로 읽는다.
 * }} Candidate */
```

**`Candidate` 는 래퍼다(§1.3 ⑤, 2026-09-05).** `status` 여섯 값은 **PR 2 가 공유 타입에 전부 선언**한다 — 뒤의 둘(`commemorated`·`omitted`)은 PR 3 이 만들어 내지만, 닫힌 union 을 PR 2 에서 넷으로 선언하면 PR 3 의 정상 값이 타입 오류가 되고 「형태 변경 없이」(§6.5 마지막 단락) 가 깨진다. 종전에는 `candidates: Observance[]` 였다. 그러면 옮겨온 축일을 목적지에서 낼 때 「12.28 에서 옮겨 왔다」를 실을 자리가 없고, 원래 날짜에서는 「12.29 로 갔다」를 실을 자리가 없다. `Observance` 에 필드를 더하는 것은 §5.6 이 `occurrence` 를 거절한 것과 같은 이유로 하지 않는다 — 정의 표의 행과 엔진이 합성한 값이 한 타입에 섞인다. 상태의 뜻:

| `status` | 뜻 | 누가 만드나 |
|---|---|---|
| `proper` | 그 날짜의 고유 후보(아래 ①~④)의 **초기 상태** — PR 2 에서는 전부 이 값이다. B1 은 승자가 아닌 고유 후보를 규칙에 따라 재분류한다: 이동하면 `transferred_out`, `commemorate_only`·C 그룹 「옮기기 어려우면」이면 `commemorated`, prec 7 이면 `omitted`. **재분류 뒤에도 `proper` 로 남는 것**은 ① 승자(`official`) ② 격자 주일·평일 후보(연중 평일 독서 — 어느 규칙도 옮기거나 생략하지 않으므로 「밀린 독서 보존」(ADR-036 §7)이 이 상태로 실현된다) ③ 고정일끼리의 동시 봉헌에서 진 쪽(9.29 설립 기념일 — §6.5, 미결18) ④ `transferable: false` 인 주요축일·대축일이 진 경우(현재 표에서 12.25 같은 대축일은 지지 않으므로 사례 없음 — 생기면 데이터 결함 신호) ⑤ 이동 상한 `MAX_SHIFT` 를 넘겨 옮기지 못한 것(§6.5 — `defects` 에 id 가 함께 실린다. 현재 표에서 사례 없음) ⑥ **지향·이름 줄 후보 — 사계재와 기념일**(§6.1 「승자 자격이 없는 후보」, 2026-09-17 확정): 언제나 `proper` 이고 승자가 아니다. 밀린 것이 아니라 `displacedBy` 도 없고 `omitted` 도 되지 않는다 | PR 2 (초기) · PR 3 (재분류) |
| `transferred_in` | 다른 날짜에서 옮겨 와 **이 날 지키는** 축일. `from` 을 가지고, 충돌 이동이면 `displacedBy` 도 가진다(활성화된 선택 봉헌은 `displacedBy` 없음). ADR-037 §6 표시 순서의 ② 「이동 축일」이 정확히 이 집합이다 | PR 3 (§6.5) |
| `transferred_out` | 이 날짜의 고유 후보였으나 **다른 날로 간** 축일 — 충돌로 밀렸으면 `to`·`displacedBy`, 활성화된 선택 봉헌이면 `to` 만. 승자가 될 수 없고 뷰는 「→ 12.29」로 안내한다. 도착한 축일은 다시 밀리지 않으므로(§6.2 ②) 옮겨 온 것이 이 상태가 되는 일은 없다 | PR 3 (§6.5) |
| `optional` | 「옮겨 지킬 수 있다」는 선택 주일 봉헌(§6.2)의 목적지 주일에 얹히는 후보. `from` 은 그 축일의 **원래 날짜**이고 목적지보다 뒤일 수 있다(주의 봉헌 2028: 2.2 → 1.30). 설정이 켜기 전에는 승자 판정에 참여하지 않는다. 별도 색인 `optionals` 에서 온다 — 도착·출발 색인과 섞지 않는다 | PR 3 (§6.2) |
| `commemorated` | 밀렸으나 옮기지 않고 기념만 하는 축일 — `transfer_to: commemorate_only`(추수감사주일) 또는 C 그룹의 「옮기기 어려우면」(§6.2 절차 ④). `displacedBy` 를 가진다 | PR 3 (B1) |
| `omitted` | 밀려서 그해 생략되는 prec 7 **축일**(`minor_feast` — §6.2 절차 ⑤, 기도서 「축일 … 겹치면 생략한다」). **기념일은 아니다**(2026-09-17 — 기념일은 언제나 `proper` 인 이름 줄 후보라 생략 상태가 없다, §6.1). 12.29 토마스 베켓이 어린이들 도착에 밀리는 경우. `displacedBy` 를 가진다. 후보에는 남는다 — 「밀린 독서 보존」 | PR 3 (B1) |

`from`·`to` 는 **계보가 아니라 기원과 목적지**다 — 한 축일은 많아야 한 번 옮기므로(§6.2 ②) 「직전 자리」와 「원래 날짜」가 같다.

**핵심 계약(ADR-036 §7)**: `precedence` 는 그날의 **공식 축일 하나**를 정하지만, 엔진은 **밀려난 축일 · 기념만 하는 축일 · 연중 평일 독서를 버리지 않는다.** **승자는 엔진이 정해 `official` 로 낸다**(B1, §6.1) — 뷰가 우선순위를 다시 계산하지 않는다. 뷰의 선택은 「**어느 후보를 볼지**」다 — 관측일 스위처 칩은 `candidates` **전부를 항상 노출**하고 `official` 이 **초기 선택**일 뿐이다(ADR-038 §3 · 사용자 확정 2026-09-17: 낮은 등급을 숨기거나 합쳐 내지 않는다). 종전에 여기 적었던 「기본은 `official` 만, 고급은 `candidates` 전부」 설정은 이 확정으로 **폐기**한다 — 기본에서 숨기면 사용자가 「축일에 밀린 기본 독서」를 놓치게 되는데, 그것이 바로 이 계약이 막으려던 결과다. 본문은 고른 후보 하나의 것만 그린다(후보마다 `findReadings` 를 부른다). 기념일 후보는 칩에는 남되 본문이 빈 결과다(§2 · §5.6 자격 ②).

후보를 모으는 곳 다섯: ① 격자 좌표(temporal) ② `date` 매치(sanctoral) ③ `lunar` 매치(KASI) ④ 규칙 파생(temporal-feasts 의 `rule` 평가) ⑤ **도착 이동** — `transfers.arrivals.get(date)`(§6.5). **① 의 `Observance` 는 합성이다** — 격자(연중 주일·절기 평일)는 정의 표에 행이 없어 엔진이 좌표에서 만든다: `id` 는 **`grid:<season>-<week|x>-<type>[-<weekday>]`**(예 2026-01-25 → `grid:ordinary-3-sunday`, 사순 2주 화요일 → `grid:lent-2-weekday-tue`, 성주간 평일처럼 `week: null` 이면 `x`), `name` 은 좌표의 표시명(「연중 3주일」), `precedence` 는 §6.1 사다리(절기 주일 2 · 연중 주일 5 · 평일 8). `grid:` 는 `guard:` 와 함께 **예약 접두사**라 정의 표 id 에 나타나지 않고, 뷰는 접두사를 보면 표를 찾지 않는다. 격자 후보도 실제 이동 사유가 된다 — 2026-01-25 바울로 회심(B, 6)을 연중 3주일이 밀어 1.26 으로 보내며 그 `displacedBy` 는 `grid:ordinary-3-sunday` 다(연중 주일은 temporal 표에 행이 없다). 이 규칙이 없으면 §6.5 의 `displacer.observance.id` 가 `undefined` 다. **`grid:` id 가 `displacedBy` 에 실제로 나타나는 것은 그 좌표에 temporal 행이 없을 때뿐이다** — 행이 있으면 §6.2 ④ 사다리로 temporal 이 이겨 그 행의 id 가 실린다(2025-11-30 안드레아의 `displacedBy` 는 `grid:advent-1-sunday` 가 아니라 `t-대림1주일`). ①~④ 가 그 날짜의 **고유** 후보(`status: "proper"`)이고 ⑤ 만 다른 날짜에서 온다. 같은 패스의 `departures.get(date)` 에 있는 고유 후보는 `status: "transferred_out"` 으로 바꿔 낸다(같은 축일이 한 날짜의 `arrivals`·`departures` 양쪽에 있을 수는 없다 — §6.5). 그리고 `transfers.optionals.get(date)` 를 `status: "optional"` 로 덧붙인다.

**격자와 temporal 행은 공존한다 — 대체가 아니다**(검토 문서 §4.3 공백 1 해소). temporal 표 24행 중 **18행**이 `season/week/type` 을 갖고(2026-09-13 실측), 그중 주일이 **다섯**(주님의 세례 · 주의 변모 주일 · 성지주일 · 대림1주일 · 왕이신 그리스도)이다. 사계재 4행은 좌표가 없는 대신 `ember_wfs` 로 같은 날에 닿는다. 그래서 그 날짜에는 ① 격자와 ④ 규칙 파생이 **후보를 둘** 올린다. 둘 다 남긴다 — 하나를 지우는 것은 이 문서의 「후보를 버리지 않는다」에 어긋나고, 뷰가 「연중 3주일 독서」와 「하계재 독서」를 함께 보여야 하는 근거도 여기다. 승자는 §6.2 ④ 범주 사다리가 정한다.

실측 동률은 **둘**이다(2026-09-13, `temporal-feasts.json` 24행 대조): **성지주일 · 대림1주일**(temporal prec 2 ∧ 격자 절기 주일 2)과 **사계재 4행**(temporal 8 ∧ 격자 feria 8). 사다리로 temporal 이 이기므로 `official` 은 성지주일(홍) · 대림1주일 · 하계재(자 · `penitential`)이고 격자 후보는 `proper` 로 남는다 — 격자가 이기면 **전례색이 자 · 녹으로 뒤집힌다**. 나머지 셋은 동률이 아니라 precedence 로 갈린다(주의 변모 주일 `null` · 왕이신 그리스도 3 vs 격자 연중 주일 5). **개정 2026-09-17(사용자 확정 — 미결23 해소)**: 사계재 4행은 예외다 — 승자 자격이 없어(§6.1 유효 precedence 9) 격자 평일이 이기고 사계재는 `proper` 후보로 남는다(§6.2 ④ 「사계재는 지향」). 기념일도 같다(미결24). 그래서 이 문단의 「하계재 `official` · 자」는 더는 맞지 않고, 사다리로 격자를 이기는 temporal 동률은 **성지주일·대림1주일 둘**뿐이다.


**⑤ 가 없으면 옮겨온 축일은 어디에서도 조회되지 않는다**(종전 §9 미결9). §6 이 「밀린 축일이 다음 빈 날로 간다」는 절차만 적고, 목적지 날짜를 열었을 때 그 축일을 후보에 올리는 경로를 정하지 않았기 때문이다. 이동은 **한 날짜를 보고는 알 수 없다** — 12.29 가 스테파노를 받는지는 12.26 이 주일인지에 달렸다. 그래서 색인은 연도 단위로 한 번 만들어 캐시에 두고(§4.9), `resolveDate` 는 그것을 읽기만 한다.

**§5.4 의 「성인력 행이 없는 날짜 본문 16건」은 여기서 다루지 않는다.** 실측하면 그 16 개가 전부 `12.17~12.24`(성탄 전 8일)·`12.30`·`1.3~1.12` — **성인일이 아니라 절기 평일**이다. 그날의 **관측일은 ① 격자에서 이미 나온다**(성탄절기 평일). 성인력에 줄이 없는 게 결손이 아니라 맞는 것이고(ADR-036 §6), 빠지는 것은 관측일이 아니라 **본문 조회 키**다 — 그 본문은 `date` 로 색인돼 있는데 **격자 관측일에는 `date` 가 없다**(절기 좌표에서 나온 것이라). 그러니 관측일만 넘겨서는 닿지 않고, 물어본 날짜가 남아 있는 `ResolvedDate` 를 함께 받아야 한다 — `findReadings(resolved, candidate)`(§5.6 시그니처). 후보 출처를 늘리는 건 잘못된 처방이다 — 관측일은 멀쩡히 있고 본문만 못 찾는 상황이라, 본문 인덱스를 후보로 올리면 「12월 19일」이라는 이름 없는 관측일이 하나 더 생긴다.

**후보 표시 순서(ADR-037 §6)**: ① 교회력에 따른 축일/재일 → ② 이동 축일 → ③ 나머지(연중 평일·연속). 대축일·주요축일·사계재에 연중 주간 독서가 전례상 쓰이지 않더라도 **후보는 모두 제공한다** — 목적에 맞는 선택은 독서자 몫.

### 5.6 `findReadings` · `findCollects`

- **두 조회 함수는 좌표를 받지 않는다** — `findReadings(resolved, candidate)` · `findCollects(resolved)`. **둘째 인자는 `Candidate` 다**(15차 리뷰 — 종전에 `observance` 로 적었다): `resolveDate` 가 `official`·`candidates` 를 `Candidate` 로 내므로 호출부가 쥐고 있는 것이 그것이고, 관측일은 `candidate.observance` 로 한 겹 안에 있다. 규칙이 `observance.id` 를 바로 읽으면 `undefined` 가 되어 본문 인덱스를 놓친다. ADR-037 §6 의 계약도 함께 개정했다. `LiturgicalCoord` 는 절기 축(`season`·`week`·`weekday`·`year`)만 담아서, 이름일(`name`)·고정일(`date`)·음력일(`lunar`)로 색인된 본문에 좌표만으로는 닿지 않는다. 관측일에는 그 세 키가 들어 있으므로 **고른 후보**의 관측일을 그대로 넘긴다(`official` 만이 아니다 — 뷰가 후보마다 부른다, §5.5) — 좌표만 넘기면 호출부가 같은 판정을 다시 하게 된다.
- **둘 다 `ResolvedDate` 를 받지만 이유가 다르다.** `findCollects` 는 **여러 관측일**이 필요해서고(`resolved.candidates` — 아래), `findReadings` 는 **그날의 실제 날짜**가 필요해서다. §5.4 의 성탄절기 16건은 `date` 로만 갈리는데 그 `date` 는 **본문 레코드 자신의 좌표**이지 격자 관측일이 들고 있는 값이 아니다 — 격자 관측일은 절기 좌표에서 나오므로 `date` 가 없고, 열여섯이 전부 `type: weekday` · `week: null` · `weekday: null` 이라 좌표로는 성탄주간 아홉이 한 덩어리로 뭉개진다(2026-09-01 실측). 물어본 날짜는 `resolved.date` 에만 있으니 거기서 `MM.DD` 를 떼어 §5.4 의 `date` 인덱스를 친다.

  **어느 날짜로 인덱스를 치는가는 관측일의 출처가 정한다.** 순서는 **① `candidate.observance.id` 가 `grid:` 접두사면(격자 합성 — §5.5) `resolved.date` 의 `MM.DD`** ② **그 밖에는 관측일(`candidate.observance`) 자신의 `date`·`lunar`·`name`** 이다. **키의 존재 여부로 가르면 안 된다**(13차 리뷰 — 10차에 그렇게 적었던 것을 정정한다): §5.5 가 격자 후보에도 표시용 `name` 을 **반드시** 주므로(「연중 3주일」), 「`date`·`lunar`·`name` 이 있으면 ①」로 쓰면 격자가 언제나 ① 로 빠져 `resolved.date` 를 영영 치지 않는다 — 2026-12-19 같은 날짜 전용 본문이 다시 이름·좌표 경로로 뭉개진다(§5.4 의 열여섯). `grid:` 는 예약 접두사라 정의 표 id 에 나타나지 않으므로 출처 판별이 결정적이다. 옮겨온 축일에서 둘이 갈리기 때문이다 — `resolveDate("2025-12-01")` 의 안드레아는 `resolved.date` 가 **목적지**(12-01)이고 `observance.date` 는 **기원**(`11.30`)인데, 본문은 기원 날짜에 색인돼 있다(실측: `date: "11.30"` 독서 1 · 본기도 1, `date: "12.01"` 은 **0건**). 목적지로 인덱스를 치면 옮겨온 축일의 독서가 빈 결과로 나온다 — **종전 미결9 가 후보 경로에서 고친 것과 똑같은 증상이 본문 경로에 남아 있던 자리**다. 이동은 축일을 **다른 날에 지키는** 것이지 다른 본문을 읽는 것이 아니다.

  **관측일에 날짜를 심어 인자 하나로 두는 안은 버렸다.** `Observance.date` 는 「이 관측일은 해마다 `MM.DD` 에 온다」는 뜻이고 §5.4 권장 인덱스 3 이 그 뜻으로 키를 잡는다. 격자 관측일에 「마침 물어본 날」을 같은 필드로 넣으면 한 필드가 두 뜻을 갖는다. 별도 필드(`occurrence`)를 두면 충돌은 피하지만, `Observance` 는 뷰·검색과 함께 쓰는 `types.d.ts` 공유 타입이라(§3.2) 엔진이 합성한 값을 거기 얹지 않는다.
- `findReadings(resolved, candidate)` → `reading_track` · `set_no` 별 **그룹**. `set_no` 정렬은 결정적이어야 하며(기사 배열 순서 금지) **옛 연도판을 뒤로**, 인쇄된 세트 번호 순, 본 독서가 대안보다 앞(ADR-037 §1 개정). 실측 분포(2026-08-29): `set_no` 는 1(841) · 2(81) · 3(1), `set_total > 1` 인 레코드가 163건.
- `reading_track` 은 **연중 주일에만** 있다 — 실측으로 비-null 175건이 전부 `(season: ordinary, type: sunday)` 였다(ADR-037 §1 개정 ③ 확인). 재의 수요일·성 금요일·부활대축일의 `2` 는 트랙이 아니라 **대안 세트**다. 엔진이 이를 "독서 2"로 이름 붙이면 안 된다.
- **독서 슬롯은 네 개지만 다 있지는 않다.** 실측(2026-09-01): `first` 922 · `psalm` 922 · `gospel` 922 · `second` 383. `second` 가 없는 539건은 대개 평일(526)이라 정상이다. **`gospel` 은 이제 빠짐없이 있다** — 종전에 복음이 없던 **단 하나**(12.31 거룩한 이름 예수 전야)는 뷰가 견뎌야 할 예외가 아니라 **잘못 실린 레코드**였고, 저녁기도로 판정돼 빠졌다(data PR#23). 그래도 뷰는 **위치가 아니라 `slot` 이름으로 읽어야 한다**(ADR-037 §1 개정 ②) — 마지막 칸이 늘 복음인 것은 지금 데이터가 그럴 뿐이다. 데이터 쪽 검증도 개수를 세지 않고 「남은 레코드에는 전부 복음이 있다」를 직접 단언한다(data `tests/test_lectionary.py`) — 복음 없는 레코드가 다시 들어오면 성무일과가 새어 든 것이거나 원료가 깨진 것이다.
- 시편 슬롯의 `bookId` 는 전례시편 `lps`, 송가일 때는 `cant` + `canticle` 키가 붙는다.
- `findCollects(resolved)` → **`ResolvedDate` 를 받는다**(관측일 하나가 아니라). 두 축을 **구분해서** 반환하기 때문이다(ADR-038 §3): ① 같은 관측일의 자유선택 대체안(`collect_no` — 뷰가 택1 탭) ② 서로 다른 관측일이 겹쳐 따라오는 본기도(뷰가 순서대로 열거). **②는 정의상 여러 관측일에 걸친 축**이라 승자 하나만 넘기면 만들 수 없다 — `resolved.candidates` 가 있어야 한다. **② 는 관측일별로 키잉한다**(2026-09-17 — 스위처가 고를 수 있어야 한다): 원소가 `{candidate, collects}` 이고 순서는 `candidates` 순이다. 뷰는 `?obs=` 로 고른 후보의 것을 ① 자리(택1 탭)에 두고 나머지를 ② 로 열거한다 — 그래서 `findCollects` 는 여전히 `resolved` 하나를 받고 후보를 인자로 받지 않는다: 스위처는 **반환값을 재배열할 뿐 재조회하지 않는다**. 기념일 후보의 항목은 빈 `collects` 다(§2). `findReadings` 가 후보 **하나**를 따로 받는 것도 이 때문이지 실수가 아니다: 독서는 **고른 후보 하나**의 세트를 내면 끝이라 후보 전부가 필요 없다 — 뷰가 후보마다 부르므로 `official` 로 제한되지 않는다(2026-09-17 정정, 종전 「승자 하루」). 대신 그날의 날짜가 필요해 `resolved` 를 같이 받는다(위).
- **송영은 본문에 없다** — 레코드의 `ending` 이 앱 상수 3종 중 하나를 가리키고, 열거 **마지막 1회만** 부착한다(ADR-036 §3 개정). 엔진은 코드만 넘긴다. 실측(2026-09-01)은 A 317 · C 10 · **B 0** — 합 327.
- **성인 공통 본기도 폴백** — `has_proper: false` 인 성인은 `sanctoral_class` 로 `commons.json` 의 분류별 공통을 참조하고, 본문의 `{name}` 자리에 성인 이름을 넣는다. 이름이 **배열**이므로 `A와 B` 로 연결한다(안나와 요아킴).

  | 고유 **본기도** 보유(`has_proper: true`) | 52 | 본기도 공통은 필요 없다. `apostle`(14) · `evangelist`(3) · `lord`(12) 는 **전원**이 여기 속한다. **독서까지 보유한다는 뜻은 아니다** — 52건 중 프란시스 사베리오(12.03)는 고유 독서가 없어 공통 독서를 **탄다**(아래 「성인 공통 독서 폴백」 — §9 미결11 해소). `has_proper` 는 본기도 축의 플래그다 |
  | 공통으로 폴백 | 81 | `martyr` 33 · `pastor` 24 · `monastic` 9 · `teacher` 6 · `saint` 6 · `missionary` 3 — **여섯 분류 모두 `commons.classes` 에 있다** |
  | 기념일(`commemoration`) | 16 | 본기도·독서가 애초에 없다(§2) |

  `commons.classes` 가 8개(위 여섯 + `dedication` · `anniversary`)뿐이어서 `apostle`·`evangelist`·`lord`·`national` 이 빠진 것처럼 보이지만, **그 분류의 성인은 전원 고유 본기도를 가지므로 공통을 탈 일이 없다.** 뒤의 둘은 성인이 아니라 본당 축성일·교구 설립일용이다.
- **같은 날짜에 성인이 둘 이상이면 각각 만든다** (사용자 확정 2026-09-17). 그날의 성인 후보 **각각**에 대해 본기도·독서를 만들고, 어느 것을 볼지는 **독자가 고른다**(ADR-038 §3 관측일 스위처 — 기본 선택은 `official`). 엔진이 승자만 남기고 나머지의 본문을 지우지 않는다 — B1 이 `omitted` · `commemorated` 로 재분류한 후보도 `candidates` 에 남는 이유가 이것이다(§5.5). 계약을 그 모양으로 맞춘다: `findReadings` 는 후보 하나를 받으므로 뷰가 후보마다 부르면 되고, `findCollects(resolved)` 의 둘째 축은 **관측일별로 키잉**해 스위처가 고른 것을 앞세운다(아래 `findCollects` 항 — 종전 문면은 축을 구분만 했지 관측일을 식별하지 않아 스위처가 고를 수 없었다). **기념일은 예외다** — 후보(칩)로는 남되 본기도·독서는 빈 결과다(§2 · 아래 자격 ②): 세계평화 기도일(01.01)과 거룩한 이름 예수가 그 실례로, 칩은 둘이고 본문은 하나뿐이다. 03.01 이 실례다 — 삼일절은 고유 독서, 데이빗은 `pastor` 공통(아래) — 둘 다 만들고 독자가 택한다. 09.29(미카엘 ∧ 설립 기념일) · 08.15(성모안식 ∧ 광복절) · prec 7 쌍 7건(02.14 발렌틴 ∧ 키릴·메토디우스 …)도 같다 — 낮은 등급을 숨기거나 한 이름으로 합쳐 내지 않는다. 미결6 · 미결18 의 「뷰가 어떻게 내나」 갈래가 이것으로 닫히고, 미결12 의 좁히기가 실패하는 자리에서도 조용한 택1이 아니라 **후보 전부**를 내는 것이 같은 방향이다.
- **성인 공통 독서 폴백** (§9 미결11 해소, 2026-09-17). 본기도와 **같은 표**(`commons.classes[cls].readings`)를 **같은 키**(`sanctoral_class`)로 탄다. 다만 **트리거가 다르다** — 본기도는 `has_proper` 이고, 독서는 **「이 관측일의 고유 독서가 없다」**다. `has_proper` 는 파서가 본기도 레코드 실매칭으로 덮어쓰는 **본기도 축의 사실**이라(data `parse_sanctoral.check_propers` — 표의 ✓ 열이 아니라 데이터가 정한다) 독서에는 못 쓴다: 프란시스 사베리오(12.03)가 `has_proper: true` 인데 독서는 0건이다. 두 축은 따로 판정한다.

  **트리거는 「날짜 인덱스가 비었는가」가 아니다.** 실측(2026-09-17)으로 `has_proper: false` 인 성인 **넷**이 자기 날짜에 **남의 본문**을 두고 있다 — 루시안(01.08) · 실베스터 · 위클리프(12.31)는 `성탄주간`(격자 절기 평일의 날짜 전용 본문, §5.4), 데이빗(03.01)은 `삼일절`(같은 날짜의 다른 성인력 행). 날짜 인덱스가 비었을 때만 폴백하면 이 넷은 공통을 못 타고 남의 독서를 받는다 — 결손이 아니라 **오답**이다. 그러므로 「고유 독서가 없다」는 §5.4 의 1:N 을 **이 관측일 것으로 좁힌 뒤**의 판정이다(미결12 와 맞물린다). 미결12 가 어떻게 닫히든 다음 둘은 이 관측일 것이 아니다: ① **`type: weekday` 인 날짜 전용 본문**(성탄주간 · 성탄 N일 전 — 격자 후보의 것, 좁히기 규칙 ①과 같은 계열. 성인력 행이 있는 날짜에 걸린 것은 01.08 · 12.21 · 12.31 셋뿐이고 셋 다 성인의 것이 아니다) ② **같은 날짜의 다른 관측일 이름에 조인되는 본문**. 오늘 데이터는 이 둘만 걷어내면 149행 전부가 결정된다 — 성인력 행이 둘 이상인 날짜에서 공통 분류 성인이 고유 독서를 갖는 경우는 성모안식(08.15) · 모든 성인(11.01) 둘뿐이고 둘 다 이름 조인이 된다.

  **반대 방향도 잡아야 한다 — 이름 조인 실패가 폴백으로 새면 안 된다.** 성 세례 요한 탄생(06.24, `saint` · 주요축일 · prec 3)은 고유 독서가 있는데 레코드 이름이 `성 세례요한 탄생 축일` 이라 **띄어쓰기 하나로** 이름 조인이 빠진다(§5.4 표). 좁히기를 이름으로만 하면 이 날은 「고유 없음」으로 읽혀 **성인 일반 공통**이 붙는다 — 주요축일에 공통 독서가 나오는 것이라 단순 결손보다 나쁘다. 그 날짜에 성인력 행이 **하나뿐**이니 ①을 걷어낸 나머지는 전부 그 관측일 것이다 — **이름 조인은 행이 둘 이상인 날짜에서만 묻는다.** 이름 조인의 불안정 자체는 미결12 의 `sanctoral_id` 참조가 근본 해법이다.

  **자격.** 후보의 `status` 와 무관하게 관측일로 판정한다(옮겨온 `transferred_in` 도 같은 관측일이고, 본문은 기원 날짜에 색인돼 있다 — 위 날짜 선택 순서 ②). 전부 참일 것: ① `candidate.observance.sanctoral_class` 가 `commons.classes` 에 있다 ② `rank` 가 `commemoration` 이 아니다(§2 — 기념일은 설계상 본문이 없다. 오늘은 16건 전부 `sanctoral_class: null` 이라 ①에서 이미 걸리지만 규칙은 등급으로 적는다) ③ 좁힌 고유 독서가 0건이다 ④ `classes[cls].readings` 가 비어 있지 않다. 하나라도 거짓이면 **빈 배열**이다 — `apostle` · `evangelist` · `lord` · `national` 은 공통이 없고(전원 고유 독서 보유 — 빠지면 결손 신호), `anniversary` 는 독서 세트가 0 이라 빈 배열이 맞다(「고정 전례독서 없음 — 그날 절기 주일 독서를 쓴다」, data `calendar/commons.md`). 그날 절기 독서를 `findReadings` 가 대신 찾아 주지는 않는다 — 격자 후보가 `candidates` 에 `proper` 로 이미 있으므로(§5.5 「후보를 버리지 않는다」) 뷰가 그 후보를 고르면 된다. B2 가 `local-observances` 를 실으면(미결2) 키가 `dedication.common` · `observance.common`(§5.4 표)으로 바뀔 뿐 규칙은 같다.

  **고유와 공통은 배타다.** 고유 독서가 하나라도 있으면 공통은 내지 않는다 — 기도서의 공통은 「고유가 없는 성인」을 위한 것이지 대안이 아니다. 섞으면 뷰의 「대안 독서」 세그먼트에 기도서에 없는 선택지가 생긴다.

  **반환 형태는 고유와 같다.** 세트 하나가 그룹 하나 — `reading_track: null` · `set_no: k` · `set_total: N` · `set_note: null` · `readings: slots`. 슬롯 객체 `{slot, bookId, refs, label}` 는 본문 표와 **동형**이라(같은 파서 경로 — `parse_commons` 가 `parse_readings` 의 슬롯 배정·검증을 재사용한다) 그대로 넘긴다. `set_no` 는 인쇄 순서(`set`)를 그대로 쓰므로 §5.3 의 결정성 요구를 이미 만족하고, ADR-038 §3 의 「대안 독서」 세그먼트(`set_total > 1`)가 그대로 먹는다. 여기에 **출처 표지 `common: "<class_key>"`** 를 얹는다(고유는 `null`) — 뷰가 「순교자 공통 독서」로 캡션을 달 수 있게. 본기도 폴백은 `{name}` 치환으로 출처가 드러나지만 독서에는 자리표시가 없어 이 표지가 유일한 단서다. 합성 그룹의 `id` 는 **`common:<class>-s<set>`**(결정적 — `common:` 은 관측일 id 의 `grid:` · `guard:` 처럼 정의 표·본문 표 id 에 나타나지 않는 예약 접두사). **조용히 한 세트를 고르지 않는다** — 기도서가 「다음 중 하나」로 인쇄한 것이라 전부 내고 뷰가 고른다(첫 세트가 기본).

  **커버리지**(2026-09-17 실측): 폴백을 타는 관측일은 **82** — `has_proper: false` 이면서 분류가 공통에 있는 81(`martyr` 33 · `pastor` 24 · `monastic` 9 · `teacher` 6 · `saint` 6 · `missionary` 3) + 사베리오. 공통 분류이면서 고유 독서를 가진 **13**(스테파노 · 죄 없는 어린이들 · 토마스 베켓 · 세례 요한 탄생 · 성모안식 · 모든 성인 …)은 타지 않는다. 기념일 **16** 은 빈 결과. 이 세 수(82 · 13 · 16)가 실데이터 테스트의 불변식이다(§7).

  **데이터 쪽 후속(선택).** `has_proper` 를 파서가 실매칭으로 정하듯 **`has_proper_readings`** 도 같은 방식으로 발행하면 트리거 ③이 엔진 판정이 아니라 **데이터 사실**이 된다 — 미결12 의 좁히기에 기대지 않고, 표기 드리프트(06.24)도 파서 리포트에 `[주의]` 로 잡힌다. `check_propers` 가 이미 그 형태라 독서 파일을 한 번 더 읽으면 된다.

## 6. B1 품계 · 이동 · 전례색

A1 이 끝난 뒤 별도 PR. 데이터가 `rank` · `precedence` · `priority_group` · `transferable` · `transfer_to` · `outranks_sunday` · `color` · `color_alt` 를 준다.

### 6.1 품계 사다리

`precedence` 는 **정수, 낮을수록 우선**.

| prec | rank | 해당 |
|---|---|---|
| 0 | `regional_festival` | 설·추석 |
| 1 | `principal` | 대축일 7 + **성 목요일**(2026-08-29 확정 — 성삼일 첫날이라 prec 1 이지만 재일은 아니다) + 대재일 2(재의 수요일·성 금요일) |
| — | (A 특례) | 거룩한 이름 예수·주의 봉헌·주의 변모 — `outranks_sunday: true`, **1과 2 사이** |
| 2 | `privileged_sunday` | 절기 주일 |
| 3 | `major_feast` A | 연중 주일보다 선순위 |
| 4 | `major_feast` C | 연중 주일보다 선순위, 어려우면 기념만 |
| 5 | `sunday` | 연중 주일 |
| 6 | `major_feast` B | 어느 주일과 겹쳐도 다음날 이동 |
| 7 | `minor_feast` · `commemoration` | 축일은 겹치면 **생략**(이동 없음) · **기념일은 승자 자격 없음**(아래, 2026-09-17) |
| 8 | `feria` | 절기 평일 · 소재일 |

주의할 점 셋:
- **재일은 한 등급이 아니다** — 대재일은 prec 1, 소재일은 prec 8. `type: "fast"` 가 같아도 `rank` 가 갈린다.
- **"모든 주일이 축일보다 우선"을 단일 규칙으로 두지 않는다** — 절기 주일과 연중 주일이 갈린다.
- **A > C > B 순서는 기도서가 직접 명시하지 않는다.** 주일과의 관계에서 도출한 잠정 순서이고 실제 겹침 사례가 나오면 재확인 대상이다(ADR-036 §6 개정).

**`rank` 로 우선순위를 비교하면 안 된다.** 실측에서 `major_feast` 가 precedence 3 · 4 · 6 세 값으로 갈린다(A · C · B 그룹). 비교는 반드시 `precedence` 로 하고 `rank` 는 표시·분류에만 쓴다. `minor_feast` 와 `commemoration` 은 둘 다 7 로 **동률**이다.

`precedence` 가 `null` 인 후보는 **정렬 최하위**, 승자로 뽑지 않는다. **그 집합은 `temporal-feasts` 의 여섯 행이다**(2026-09-13 실측 — 종전에 「collects 3건」이라 적었던 것을 정정한다. collects 는 본기도 표라 후보를 내지 않는다):

| 행 | 무엇인가 |
|---|---|
| 가정주일 · 평화통일주일 | 데이터 `note` 가 **강조 주일 — 절기 주일을 밀어내지 않음**으로 정의. 의도된 `null` |
| 맥추감사주일 · 여성선교주일 | 분류 미해소(ADR-036 미결10). collects 쪽 3건 중 둘이 같은 이름이다 |
| 성 토요일 | `rank: null` · 색 홍. 품계와 색이 독립 축인 사례이고, 이동 목적지 판정에서는 `guard` 가 덮는다(§6.5) |
| **주의 변모 주일**(E−49) | **나머지 다섯과 다르다** — 사순 직전 주일의 정체(변모 독서 · 색 백)인데 `null` 이면 `official` 이 격자 연중 주일이 되고 색이 녹이 된다. 지위 확인 대상(검토 문서 §4.3 공백 4 · §6 부수) |

`sanctoral` 149행에는 `precedence: null` 이 **없고**, `outranks_sunday: null` 도 두 표 모두 **0건**이다(A 특례 셋만 `true`) — 그러니 두 필드를 같은 집합으로 묶어 다루지 않는다. 「`precedence` 가 `null` 이면 `outranks_sunday` 도 `null`」은 collects 표에서만 성립하던 관찰이고 후보 판정에는 쓸 수 없다.

**승자 자격이 없는 후보가 둘 더 있다(2026-09-17 사용자 확정 — 미결23·24 해소).** 사계재(`rule.kind === "ember_wfs"`)와 기념일(`rank === "commemoration"`)이다. 둘 다 그날 위에 얹히는 **지향·이름 줄**이라 승자가 되지 않는다 — 데이터의 `precedence`(8·7)는 그대로 두고 승자 판정의 **유효값을 9**(feria 8 뒤)로 두어 어떤 실제 후보보다 뒤에 세운다. `precedence: null` 행과 같은 자리이되 뜻이 다르다 — null 은 「등급이 없다」, 9 는 「등급은 있지만 그날의 독서를 정하지 않는다」. 판별은 **구조 필드**로 한다(이름이 아니다 — 사계재는 규칙 종류, 기념일은 rank). 사계재만이면 격자와 prec 8 동률이라 §6.2 ④ 사다리 칸으로도 되지만 **기념일은 prec 7 이라 격자와 동률이 아니어서** 사다리로는 안 된다 — 그래서 유효값이다. 후보로는 남고(`proper` · `displacedBy` 없음 · `omitted` 도 되지 않는다) 본문은 사계재가 성소 본기도·독서, 기념일이 빈 결과다(§5.6 자격 ②). 축일(`minor_feast`, 같은 prec 7)은 이 집합이 **아니다** — 고유·공통 본문이 있어 절기 평일을 이기고, 더 높은 날에 밀리면 `omitted` 다(2026-12-07 암브로스 · 12-13 루시아). 소재일 여부(§6.3 ①) · 색(§6.4 — 그날 색은 절기색, 자색은 사계재 본문을 읽을 때의 색) · 이동 패스(둘 다 `transferable: false` 이고 유효값 9 라 아무것도 밀지 못한다)는 이 자격과 무관하다. 실데이터: 기념일 16행 전부 `transferable: false` · `has_proper: false` · 이름 조인되는 본문 0건, 같은 날짜에 다른 행이 없는 기념일 11행.

### 6.2 이동 목적지 — 충돌 이동과 선택 봉헌은 다른 것이다

`transfer_to` 여섯 값은 **두 종류**를 한 열에 담고 있다(2026-09-05 구분). 실측: sanctoral 32건 중 `next_day` 29 · 주일 종류 3, temporal 3건 중 `next_day` 1 · `easter7_sunday` 1 · `commemorate_only` 1.

| `transfer_to` | 종류 | 언제 | 목적지 |
|---|---|---|---|
| `next_day` | **충돌 이동** | 그날의 승자가 아닐 때(§6.5) | 다음날. **그날도 차 있으면 다음 빈 날로** — 엔진이 루프 |
| `nearby_sunday` | **선택 봉헌** | 충돌과 무관하게 언제나 | 가까운 주일(주의 봉헌 2.2). 그날이 수요일 이전이면 **직전** 주일, 목요일 이후면 **다음** 주일. 그날이 주일이면 목적지 없음 |
| `sunday_0102_0108` | 선택 봉헌 | 언제나 | 1.2~1.8 사이의 주일(공현). 1.6 이 주일이면 없음(2030·2036·2041·2047) |
| `sunday_1030_1105` | 선택 봉헌 | 언제나 | 10.30~11.5 사이의 주일(모든 성인). 11.1 이 주일이면 없음(2026·2037·2043·2048) |
| `easter7_sunday` | 선택 봉헌 | 언제나 | easter+42(승천). 승천이 늘 목요일이라 **매년** 생긴다 |
| `next_sunday` | 선택 봉헌 | 언제나 | **오는 주일**(8.6 주의 변모 — 2026-09-19 추가, 서울교구 전례독서 2026 「오는 주일로 옮겨 지킬 수 있다」, 사용자 확정). 그날이 주일이면 목적지 없음(2028·2034·2045). 2026 은 8.9(평화통일주일과 같은 날) |
| `commemorate_only` | 이동 없음 | 밀렸을 때 | 옮기지 않고 기념만(추수감사주일 — 주일로 정의된 C 그룹) |

**충돌 이동**은 결정적이다 — 그날 더 높은 관측일이 있으면 옮긴다. **선택 봉헌**은 기도서가 「옮겨 지킬 수 있다」고 적은 목회적 선택이라 엔진이 판단할 수 없다. 그래서 목적지 주일에 `status: "optional"` 후보를 **항상** 얹고, 원래 날짜의 고유 후보는 그대로 둔다 — 승천은 목요일에도 있고 부활7주일에도 `optional` 로 있다. `optional` 은 설정이 켜기 전에는 승자 판정에 참여하지 않는다. 어느 설정이 켜는가는 ADR-038 의 몫이다(§9 미결15). 이렇게 두 곳에 다 내는 것이 「조용히 하나를 고르지 않는다」는 이 문서의 태도와 맞고, 뷰의 기본은 승자만 보이므로 사용자에게 두 날이 다 축일로 보이는 일은 없다.

**활성화 계약 — 켜면 원래 날짜에서 떠난다**(2026-09-05 리뷰). 설정이 어떤 축일의 선택 봉헌을 켜면 그 축일은 **원래 날짜에서 목적지 주일로 실제로 옮긴다** — 두 번 지키지 않는다. 구체적으로 `computeTransfers(year, seed, activated)` 가 `activated: Set<observanceId>` 를 받아, 켜진 축일은 ① 원래 날짜에서 `transferred_out`(`to`: 목적지 주일, `displacedBy` 없음 — 밀린 것이 아니라 택한 것) ② 목적지 주일에서 `transferred_in`(`from`: 원래 날짜)으로 **도착 색인에** 들어가 그 주일의 순위에 참여한다(승천·공현·모든 성인은 prec 1 이라 그 주일의 승자가 되고, 주의 봉헌은 `outranks_sunday` 로 연중 주일을 이긴다) ③ 원래 날짜에서는 충돌 판정에 오르지 않으므로 **충돌 이동은 일어나지 않는다** — 2049 주의 봉헌을 켜면 1.31 주일 하나만 있고 2.3 은 생기지 않는다 ④ `optionals` 에는 실리지 않는다(켜진 것은 이미 도착이다) ⑤ **목적지가 이미 차 있어도 도착은 그대로 얹고, 다시 옮기지 않는다**(9차 리뷰). 0단계는 `isFree` 를 거치지 않으므로 그 주일에 더 높은 고유 후보가 있을 수 있다 — 2030-02-02 는 **토요일**이라 목적지가 02-03(일)인데 그날이 **설**(prec 0)이다. 이때 `official` 은 설이고 봉헌은 **승자가 아닌 `transferred_in`** 으로 남는다(후보를 버리지 않는다 · 명절 우선은 ADR-036 §7 ①). 도착을 다시 옮기면 `from` 이 원래 날짜가 아니게 되고 같은 날짜의 도착·출발 금지(§7 ⑧)도 깨지므로, 루프가 `transferred_in` 을 먼저 걸러낸다(§6.5). **목적지가 명절인데도 켜는 것이 목회적으로 맞는지는 별개 문제**이고 잠정으로 「켠 대로 둔다」를 쓴다 — §9 미결19. 꺼진 축일은 종전대로 원래 날짜 `proper` + 목적지 `optional`. **선택 봉헌 도착이 좌석 경합에서 우선한다.** 충돌 이동은 주일에도 앉을 수 있다 — 연중 주일은 prec 5 라 A(3)·C(4) 를 막지 못하므로(§6.1), 토요일에 명절 등 가변 후보에 밀린 A·C 는 다음날 연중 주일에 도착한다(현재 표에서 선택 봉헌 목적지 주일과 실제로 겹치는 사례는 2025~2050 에 없지만 원리상 배제되지 않는다). 그런 주일을 켜진 선택 봉헌도 노리면 **선택 봉헌이 이긴다**: 0단계가 날짜 루프 전에 그 주일의 `arrivals` 에 먼저 앉으므로 §6.2 ② 선착순에 의해 뒤의 충돌 도착은 `isFree` ② 에서 막혀 월요일로 간다. 이것은 우연이 아니라 **의도된 우선순위**다 — 목회적으로 택한 이동이 규칙에 밀린 이동보다 앞선다(§7 ⑦ 합성 케이스로 못박는다). **캐시**: `transferCache` 는 `activated` 에 의존하므로 설정이 바뀌면 통째로 비운다(§4.9) — 조합별로 키를 두지 않는다, 바뀌는 일이 드물고 패스는 싸다. `optional` 후보의 유일한 용도는 「이 주일에 옮겨 지킬 수 있음」 안내와 설정 진입점이다. 어느 UI 가 `activated` 를 채우는가는 ADR-038 의 몫이다(§9 미결15).

**선택 봉헌 종류의 축일도 충돌로 밀릴 수 있다.** 2049-02-02 는 설이고 주의 봉헌이다 — 명절(prec 0)이 이기고, 봉헌의 `transfer_to` 는 `nearby_sunday` 라 「다음날」을 말하지 않는다. 규정은 ADR-036 §7 ④ 가 준다 — 진 축일의 목적지는 **다음날, 가·나·다 공통**. 따라서 **충돌 이동의 목적지는 `transfer_to` 값과 무관하게 언제나 다음 빈 날**이고, `transfer_to` 는 그 위에 선택 봉헌 목적지를 **더** 정하는 열이다. 충돌 이동에 참여하는 조건은 `transferable: true` ∧ `precedence !== null` ∧ `transfer_to !== "commemorate_only"` 이 셋이다.

**주일로 정의된 날 특례**: 「11월 셋째 주일」·「공현 후 첫 주일」처럼 주일로 정의된 날은 월요일로 옮기면 정의가 깨진다. C 그룹이면 `commemorate_only`, 그 밖은 제자리(ADR-036 개정③). 데이터가 이미 그렇게 적혀 있으므로 엔진이 `rule.kind` 를 보고 다시 판정하지 않는다.

**충돌 해소 절차(ADR-036 §7)**: ① 명절 ∧ 주요축일 → 명절 우선 ② 재의 수요일 ∧ 설 → 재의 수요일을 뒤로(**데이터가 아직 `transferable: false`** — §2 · §9 미결13) ③ 주요축일끼리는 prec 순, 낮은 쪽 이동 ④ 진 축일은 다음 빈 날로, C 는 어려우면 기념만 ⑤ prec 7 은 이동이 아니라 생략.

**동률 tie-break(절차 ③ 이 정하지 않은 것).** 비교 키는 `precedence` 에 A 특례를 반영한 유효값이다 — `outranks_sunday: true` 는 1 과 2 사이(§6.1)이므로 정렬 키로는 1.5 를 쓴다. 같은 값이 남으면:

1. **도착 우선 — 연쇄 밀림.** 옮겨 온 후보(`transferred_in`)가 그 날짜의 같은 값 고유 후보(`proper`)를 **밀어낸다**. 그러면 밀린 고유 후보가 다시 다음날로 가고, 그 날의 같은 값 축일이 또 밀린다. 12.26 이 주일인 해(2027): 스테파노 → 12.27, 요한 → 12.28, 죄 없는 어린이들 → 12.29 — 셋이 **순서를 지키며 하루씩** 밀리고, 12.29 의 토마스 베켓(prec 7)은 생략된다. 12.27 이 주일인 해(2026)는 스테파노 제자리, 요한 → 12.28, 어린이들 → 12.29.

   **근거**: 기도서 문언이 「**다음날**로 옮겨 지킨다」다(`docs/reference/liturgical-calendar-rules.md` 주요축일 나-1 · 가-3 · 다-1). 연쇄 모델은 밀린 축일 **각각**이 문자 그대로 자기 다음날에 앉는다. 반대 모델(재위 우선 — 밀린 축일이 빈 날까지 건너뜀, 스테파노가 사흘 뒤 12.29 로)은 영국 성공회 Common Worship 규정(「스테파노·요한·어린이들이 주일에 들면 12월 29일로」)과 같은 결과를 내지만 「다음날」 문언과 어긋난다. 실제 관행의 증거는 미국 성공회 달력이다 — lectionarypage.net 2025~2027 이 정확히 연쇄로 표기한다(2027-12-27 스테파노(transferred) · 12-28 요한(transferred) · 12-29 어린이들(transferred); 2026-12-28 요한 · 12-29 어린이들; 2025-12-29 어린이들). 같은 페이지의 다른 이동(2025 안드레아 → 12.1, 2025 마르코 → 4.28, 2026 성모 방문 → 6.1, 2027 수태고지 → 4.5)도 §7 케이스와 전부 일치한다. 대한성공회의 실제 표기는 스크랩 원료에 실제 연도 날짜가 없어 확인하지 못했다 — **사제 확인 대상**(§9 미결17). 두 모델의 차이는 이 규칙 한 줄이라 뒤집기는 쉽다.
2. **도착한 축일은 품계와 무관하게 자리를 지킨다 — 선착순.** 이미 옮겨 와 앉은 축일이 있는 날은 뒤에 밀려온 축일에게는 **비어 있지 않다**, 그쪽 품계가 더 높아도. 밀린 축일들은 **기원 날짜 순**으로 줄을 선다(패스가 날짜 순으로 돌기 때문에 「먼저 처리된 쪽」과 같다). 기원 날짜까지 같으면 **품계 순, 그다음 ④ 범주 사다리 → `id` 사전순** — 곧 그날 `ranked` 의 순서 그대로라, 루프가 `ranked.slice(1)` 을 차례로 처리하는 것이 이 규칙의 구현이다(현재 표에는 같은 날 둘이 함께 밀리는 사례가 없다). **근거는 미국 성공회 달력 2008년이다** — 요셉(3.19 성주간 수, prec 6)이 부활2주 월요일 3.31 에, 수태고지(3.25 부활 화, prec 3)가 **그 다음날 4.1** 에 "(transferred)" 로 놓였다. 품계가 높은 수태고지가 먼저 온 요셉을 밀어내지 않았다. 2011년도 같다 — 마르코(4.25 부활 월) → 5.2, 필립보·야고보(5.1 부활2주일) → 5.3. 이 규칙의 결과로 **재이동은 일어나지 않는다** — 도착은 그날의 고유 후보보다 높은 자리에만 앉고(`isFree` ①), 뒤의 도착에는 밀리지 않으므로(②), 한 축일은 많아야 한 번 옮긴다. `isFree` ② 가 이 규칙의 구현이다(§6.5).
3. **규칙일 유지 · 고정일 이동** — 고유 후보끼리 같은 값이면 temporal(부활절 기준 규칙일)이 남고 sanctoral(고정 날짜)이 옮긴다. 실제 사례는 성체일 ∧ 성모 방문(2029·2040) · 성체일 ∧ 성 세례 요한 탄생(2038) 셋이고, 로마 교회력 우선순위표가 주님의 대축일을 성모·성인 대축일 위에 두는 것과 같은 결과다. **잠정 규칙 — 사제 확인 대상**(§9 미결14). 확인 전까지 코드는 이 규칙을 쓰되 유닛 케이스에 「잠정」이라 표시한다.
4. **범주 사다리 — `도착 > temporal 규칙일 > sanctoral 고정일 > 격자 > 합성 guard`.** 그래도 같으면 `id` 사전순(§5.3 과 같은 안정 정렬)이 마지막 안전망이다.
   **사계재는 지향이다 — 승자가 되지 않는다(2026-09-17 사용자 확정 · 미결23 해소). 기념일도 같다(같은 날 두 번째 확정 · 미결24 해소).** `rule.kind === "ember_wfs"` 인 temporal 후보(춘·하·추·동계재 4행 — 이름이 아니라 **규칙 종류**로 판별한다. 미결5 의 계절 키 부재와 무관하고, 규칙 하나가 날짜 셋을 낳는 종류는 이것뿐이다)는 **승자 자격이 없다**(§6.1 「승자 자격이 없는 후보」 — 유효 precedence 9, `precedence: null` 행과 같은 자리). 사다리 칸으로 풀 수도 있었지만(사계재는 격자와 prec 8 동률) **기념일**(`rank === "commemoration"`, prec 7)도 같은 자리에 두기로 해 동률이 아닌 것까지 덮는 유효값 방식을 쓴다. 그래서 사계재 날의 `official` 은 **그날의 절기 평일**이고(12.17~24 는 §5.6 ① 로 날짜 본문), 사계재는 `proper` 후보로 남아 성소 본기도·독서를 **필요에 따라** 고를 수 있게 한다 — 상태를 새로 만들지 않는다(§5.5 `proper` ⑥). **근거는 서울교구 달력 세 해다.** 2025·2026 면은 사계재 날에 평일 독서를 인쇄하고 「동계재 (성직자의 성소, 기도서 107쪽 참조)」로만 얹는다(검토 문서 X-5 ③ · X-6 ⑤). **2024 면은 반대로 사계재 독서를 그날 독서로 인쇄했다**(X-7 — 12.17~24 안의 12.18·20·21 에서도, 금요일은 성직후보자·수도자 두 단). 관행이 2025 부터 바뀐 것이고 두 방식이 다 실재하므로 **최신 관행을 초기 선택으로, 2024 방식은 후보 선택으로** 지원한다 — 어느 쪽이든 후보 집합은 같고 `official` 만 다르다. **따름정리 셋.** ① 색 — 그날의 `color` 는 §6.4 대로 승자(절기 평일)의 절기색이다: 하계재·추계재 **녹**, 춘계재·동계재 자. **자색은 사계재 본문을 읽을 때의 색이다**(사용자 확정 2026-09-17 「재일 독서를 읽을 때만 자색 — 어차피 선택 독서」): 사계재 후보가 `color: violet` 을 들고, 뷰는 사계재 칩을 고르면 그 후보의 색을 쓴다(ADR-038 §3). 부활밤의 백이 후보에 남는 것과 같은 모양이다. 축일이 이기는 날(2026-09-16 니니안 · 09-19 데오도르)은 그 축일 색 — 잠정, 교구 2026 달력 9월 면으로 확인(C-6.4-3). ADR-036 §8 「사계재일 자색」은 이 뜻으로 읽고, 미결11(Q6)의 「하계재·추계재 녹 vs 자」는 이 구분으로 닫힌다 — 그날 자체는 녹, 사계재 본문을 읽으면 자. 기념일은 색이 없다. ② 소재일 — 승자와 무관하다. 그날에 `penitential: true` 후보가 있으면 소재일이다(§5.2 · §6.3 ①). ③ 이동 패스 — 영향 없다. 사계재·기념일은 `transferable: false` 이고 유효값 9 라 아무것도 밀지 못하고 옮기지도 않으며, 축일이 사계재 날에 오면 축일이 이긴다(2026-09-16 니니안 prec 7 — 검토 문서 C-6.1-11). 기념일 실례: 2026-05-27 이천환 서품일 ∧ 하계재 ∧ 연중 8주 수 → `official` 격자, 둘 다 `proper`; 2024-12-21 김희준 서품일 ∧ 동계재 → `official` 격자(본문 `d1221-성탄-4일-전`); 2026-01-01 세계평화 기도일은 `proper`(`omitted` 아님) — C-6.1-12. 뒤집히면 이 단락과 §6.1 한 문단 · C-6.1-11 · C-6.1-12 · C-6.4-3 만 바뀐다.

   **`id` 사전순만으로는 왜 안 되나**(검토 문서 §3.3 채택). 격자와 temporal 행이 같은 좌표에 공존하고(§5.5) 실측 동률이 둘 있다 — 성지주일 · 대림1주일(prec 2 ∧ 격자 절기 주일 2), 사계재 4행(prec 8 ∧ 격자 feria 8). `id` 로 가르면 승자와 **전례색**이 문자열 우연으로 정해진다(성지주일 홍 vs 격자 자, 하계재 자 · `penitential` vs 격자 녹). romcal 이 `PRECEDENCES` 배열 순서로 같은 일을 한다.

   **①·②·③ 과의 관계 — 새 축이 아니라 같은 순서를 정렬로 말한 것이다.** 첫 칸 「도착」은 ① 이고, 「temporal > sanctoral」은 ③ 이다 — 이동 판정(③)과 승자 판정(④)이 **같은 범주 순서**를 쓴다. ② 선착순은 도착끼리의 순서라 이 사다리보다 **앞**에서 이미 정해진다. 마지막 칸 「합성 guard」는 §6.5 가 정렬 키에 따로 두던 `synthetic` 플래그를 **흡수한다** — 키가 둘이면 어긋날 자리가 생긴다.

   **사다리가 가르지 못하는 것 둘.** 둘 다 **같은 범주 안의 동률**이라 `id` 사전순으로 떨어지고, 그래서 미결로 남는다 — 사다리를 넣었다고 닫히지 않는다: ① **12.25 세 행**(성탄 낮 · 밤 · 새벽, 전부 sanctoral prec 1) — 날짜 뷰의 기본이 낮이라는 **명시 규칙**이 필요하다(미결12 와 같은 날짜) ② **prec 7 쌍 7건**(02.14 · 03.01 · 05.03 · 06.09 · 08.05 · 09.04 · 12.31, 전부 sanctoral 고정일) — 미결6.

   **`variesByYear`(§6.5)와 혼동하지 말 것** — 그쪽은 격자 주일과 temporal 규칙일을 **함께** 가변으로 묶어 「고정일끼리는 충돌이 아니다」를 판정하는 다른 축이다. 사다리는 둘을 가르고, `variesByYear` 는 둘을 묶는다.

### 6.3 좌표만으로 안 되는 판정 넷 (ADR-037 §6 개정)

1. **금요일 소재일** — 요일 축 병합 때문에 레코드 하나가 소재일과 비소재일을 함께 덮는다. 소재일은 **사순 주간 + 사계재일 + 성탄절기를 제외한 모든 금요일**이므로, "성탄절기 안의 금요일은 소재일이 아니다"를 엔진이 날짜로 판정해야 한다 — **`spansOf(year).christmasToBaptism`**(§4.10)으로 본다, 자체 날짜 비교를 두지 않는다.
2. **성주간·부활 1주간 보호** — prec 7 은 여기서 생략된다. ~~주요축일 B 는 애초에 겹칠 수 없다(겹치면 데이터 오류)~~ **정정(2026-09-05)**: 겹친다. 성 요셉 3.19 는 2035·2046 에, 성 마르코 4.25 는 2025·2030·2038·2041·2049 에, 필립보·야고보 5.1 은 2038 에 성주간 또는 부활 1주간에 떨어지고, 수태고지 3.25(A) 는 2027·2032·2035·2040·2043·2046 에 그렇다 — 2035·2046 은 **부활대축일 당일**이다. 데이터 오류가 아니라 이동 사례고, 기도서가 「대축일이나 성주간, 부활주간 8일과 겹치지 않는다」(주요축일 나-2)고 적은 대로 보호 기간을 「비어 있지 않은 날」로 다뤄 그 뒤로 보낸다(§6.5 `isFree` — 성지주일 ~ 부활2주일). 성주간 월~수와 부활 1주간 월~토는 격자에서 `feria`(prec 8), 성 토요일은 `rank: null` 로 나오므로 precedence 만 보면 빈 날로 오판한다 — 보호 기간이 별도 규칙이어야 하는 이유다.
3. **승자 색 덮어쓰기의 기간 가드** — §6.4.
4. **이동 목적지 평가** — 목적지가 비었는지 확인하는 루프.

### 6.4 전례색

결정 순서: **절기 기본색을 깔고 → 승자 관측일의 색이 덮고 → 기간 규정이 있는 날은 덮이지 않게 가드**한다(ADR-036 §8 개정).

- `color` = 정식 전례색 `white` `red` `green` `violet`. `color_alt` = 선택 대체색 `rose` `blue`(대림 3주일·사순 4주일의 장미색, 성모·대림의 청색). UI 는 정식 색을 기본으로 그린다.
- **품계와 전례색은 독립 축**이다 — 등급 칸이 비어도 색 칸은 채워질 수 있다. (오래 실제 사례였던 성 목요일은 2026-08-29 에 대축일로 확정돼 더는 예가 아니다. 원칙은 그대로다 — 표의 두 칸은 서로를 함의하지 않는다.)
- 가드 대상: 성주간 전체 홍색, 부활 1주간 — 개별 성인 축일 색이 이 기간을 덮으면 안 된다. 경계는 **`spansOf(year).holyWeek` ∪ `easterOctave`**(§4.10)이고 자체 날짜 비교를 두지 않는다.
- **E−1 은 가드가 승자를 덮는 유일한 자리다**(14차 리뷰). 그날의 후보는 `t-성-토요일`(prec `null` · 홍 · `lent`)과 **`t-부활밤`**(prec **1** · **백** · `easter`) 둘이고(§4.3 — `easter_offset: -1` 이 1:N), 승자는 prec 1 인 **부활밤**이다. 그런데 ADR-036 §8 개정 ① 은 「성주간은 전체가 홍색 — 성지주일부터 **성 토요일까지**」라 적었고 같은 절의 백색 기간은 「**부활밤**~성령강림 전날」이다. 둘은 **시간으로만** 갈린다(성 토요일 낮 홍 / 그날 밤 부활밤 백). **엔진은 날짜당 색 하나**를 내므로 잠정으로 **가드를 그대로 적용해 홍**을 낸다 — ADR 문언을 따르는 쪽이다. 부활밤의 백색은 `t-부활밤` 후보가 자기 `color` 로 들고 있으니 버려지지 않고, 시간 구분을 모델링할지는 **미결20**(ADR-038 과 함께).
- **사계재 날의 색은 승자(절기 평일)의 절기색이다**(2026-09-17 사용자 확정). 결정 순서에 단계를 더하지 않는다 — 사계재 후보가 `color: violet` 을 들고, 그 본문을 읽을 때 뷰가 그 색을 쓴다(「재일 독서를 읽을 때만 자색 — 어차피 선택 독서」, ADR-038 §3). 축일이 이기면 그 색(ADR-036 §8 ⑥ — 2026-09-16 니니안 · 09-19 데오도르, 잠정 · 교구 2026 달력 9월 면으로 확인). 기념일은 색이 없다(이름 줄). 소재일 여부는 색과 별개다(§6.3 ①).
- **사계재일 자색은 기도서 문면과 긴장 관계다**(ADR-036 미결11). §8 은 전통 관행으로 자색을 확정했으나 기도서는 사계재일 색을 규정하지 않고 「연중시기, 특별히 성령강림 주일 후 주간」을 녹색으로 지명한다. 하계재·추계재가 정확히 그 구간이다. **사제 확인 전까지 엔진은 데이터의 자색을 그대로 쓴다** — 코드에 임의 판단을 넣지 않는다. **→ 해소 2026-09-17(사용자 확정)**: 사계재는 승자가 아니고(§6.2 ④ 지향) 그날의 색은 절기색이다 — 하계재·추계재 녹. 자색은 사계재 본문을 읽을 때의 색이다(위 항목). 긴장은 사라진다 — 기도서 「성령강림 후 주간 녹색」은 **그날**의 색, ADR-036 §8 「사계재일 자색」은 **사계재 본문**의 색. **→ 재개 2026-09-18(미결26)**: 2026 책자는 사계재 날을 독서와 무관하게 [자]·[자/백]으로 인쇄한다 — 위 해소는 **잠정**이고, PR 2 가 `ResolvedDate` 색을 확정하기 전까지 두 모델(그날 절기색 / 그날 자 + 병기)을 미결26 에서 연다.

### 6.5 이동 패스 — 연도 단위로 한 번, 날짜 순으로 (§9 미결9 해소, 2026-09-05)

옮겨온 축일을 목적지 날짜에서 찾으려면 그해의 이동을 **전부 먼저** 계산해 둬야 한다. 12.29 가 스테파노를 받는지는 12.26 이 주일인지에, 그리고 12.27·12.28 이 이미 차 있는지에 달렸다 — 한 날짜만 보고는 답이 없다. 그래서 이동은 `resolveDate` 안에서 판정하지 않고, **연도 캐시를 채울 때 한 번** 돌리는 패스로 만든다(§4.9 `transfers`). `resolveDate` 는 색인을 읽기만 한다.

```js
/** @returns {TransferPass} */
const MAX_SHIFT = 30;   // 이동 상한(날). 실측 최장 15 — 2029·2040 수태고지 3.25(성지주일) → 4.9

/** @param {Set<string>} activated — §6.2 활성화 계약. 호출자가 반드시 넘긴다(연도 경계의 임시 패스도 같은 집합) */
function computeTransfers(year, seed /* Y−1 에서 넘어온 arrivals */, activated) {
  // seed 는 호출자(전년도 패스)의 것이다. new Map(seed) 는 Map 만 복제하고 Candidate[] 는 공유하므로
  // 0단계나 루프가 seed 에 이미 있는 날짜에 push 하면 **호출자의 배열이 변형된다** — 캐시 내용과
  // seed 도착 수가 평가 순서에 의존하게 된다(15차 리뷰). 배열까지 복제한다.
  const arrivals   = new Map([...seed].map(([d, cs]) => [d, [...cs]]));  // "YYYY-MM-DD" → Candidate[] (transferred_in)
  const departures = new Map();            // "YYYY-MM-DD" → Candidate[] (status transferred_out)
  const optionals  = new Map();            // "YYYY-MM-DD" → Candidate[] (status optional) — §6.2
  const defects    = [];

  // ── 0단계: 선택 봉헌 선색인 — 순위와 무관하고 목적지가 기원보다 **앞**일 수 있어(nearby_sunday 2028: 2.2 → 1.30)
  //    날짜 루프 안에서 처리하면 목적지를 이미 지나친 뒤라 늦는다. 루프 전에 한 해 전체를 먼저 깐다.
  for (const o of optionalObservancesOf(year)) {              // { observance, origin, dest } — §6.2 표의 네 종류
    if (activated.has(o.observance.id)) {                     // 켜진 것은 실제로 옮긴다 — optionals 가 아니라 도착. displacedBy 없음(택한 것)
      push(arrivals,   o.dest,   { observance: o.observance, status: "transferred_in",  from: o.origin });
      push(departures, o.origin, { observance: o.observance, status: "transferred_out", to: o.dest });
    } else push(optionals, o.dest, { observance: o.observance, status: "optional", from: o.origin });
  }

  // ── 1단계: 충돌 이동 — 날짜 순 단일 루프
  for (const d of daysOf(year)) {          // 1.1 → 12.31, 날짜 순 — 순서가 결과를 정한다
    const proper  = properCandidates(d)    // §5.5 ①~④, 이동 없음
      .filter((c) => !departures.get(d)?.some((x) => x.observance.id === c.observance.id));  // 켜진 선택 봉헌은 원래 날짜에 없다
    const arrived = arrivals.get(d) ?? [];
    const ranked  = rankByPrecedence([...proper, ...arrived, ...guard(d)]);  // §6.1 + §6.2 tie-break
    const staying = new Set(ranked);       // 이 날에 남아 있는 후보 — 떠난 것은 남을 밀어낼 수 없다
    for (const c of ranked.slice(1)) {     // 승자를 뺀 나머지, ranked 순 = §6.2 ② 「같은 기원이면 품계 순 → id 순」
      if (c.status === "transferred_in") continue;   // 도착은 다시 옮기지 않는다 — §6.2 ② (0단계 도착 포함)
      if (!movesOnConflict(c)) continue;   // transferable ∧ precedence≠null ∧ ≠commemorate_only (guard 도 여기서 걸러진다)
      const conflicts = (w) => staying.has(w) && outranks(w, c) && (variesByYear(w) || variesByYear(c));
      const isGuard = (w) => w.observance.id.startsWith("guard:");        // 예약 접두사로 판정 — Candidate 에 synthetic 필드는 없다 (§5.5)
      const displacer = ranked.find((w) => !isGuard(w) && conflicts(w))   // 실제 후보 우선 (성지주일 > guard). 격자(grid:)도 실제 후보다
                     ?? ranked.find((w) =>  isGuard(w) && conflicts(w));  // 실제 후보가 없을 때만 guard
      if (!displacer) continue;            // 남아 있는 것이 고정일뿐이면 충돌이 아니다 (아래)
      let dest = nextDay(d);
      const next = () => nextYearSeats(year, activated);   // 지연 — dest 가 해를 넘길 때만 계산된다 (§4.9)
      while (daysBetween(d, dest) <= MAX_SHIFT && !isFree(dest, c, arrivals, departures, next)) dest = nextDay(dest);
      if (daysBetween(d, dest) > MAX_SHIFT) { defects.push(c.observance.id); continue; }  // 상한 — 옮기지 않고 proper 로 남긴다 (§5.5 표 ⑤)
      const by = displacer.observance.id;  // 실제로 밀어낸 것 — ranked[0] 이 아닐 수 있다. Candidate 는 래퍼라 id 는 observance 아래
      push(arrivals,   dest, { ...c, status: "transferred_in",  from: d,  displacedBy: by });
      push(departures, d,    { ...c, status: "transferred_out", to: dest, displacedBy: by });
      staying.delete(c);                   // 떠났다 — 뒤의 패자 판정에서 빠진다
    }
  }
  return { arrivals, departures, optionals, defects };
}

//    1월을 목적지로 고를 수 있으므로, 켜진 선택 봉헌이 이미 앉은 자리(막기)와 비운 기원(열기)을
//    isFree 가 알아야 한다. 별도 맵이라 arrivals·departures 에 섞이지 않는다 — 캐시에도 들어가지
//    않고 spill 로도 새지 않으며 §7 ⑧ 불변식의 셈에도 참여하지 않는다.
function nextYearSeats(year, activated) {
  const nextArrivals = new Map(), nextDepartures = new Map();
  for (const o of optionalObservancesOf(year + 1)) {
    if (!activated.has(o.observance.id)) continue;            // 꺼진 것은 좌석을 차지하지 않는다 (§6.2)
    push(nextArrivals,   o.dest,   { observance: o.observance, status: "transferred_in",  from: o.origin });
    push(nextDepartures, o.origin, { observance: o.observance, status: "transferred_out", to: o.dest });
  }
  return { nextArrivals, nextDepartures };                    // isFree 가 year+1 날짜에서만 본다
}
```

**고정일끼리는 충돌이 아니다 — 동시 봉헌.** `c` 가 옮겨지는 조건은 「승자가 아니다」가 아니라 **「`c` 를 이기는 것 중에 겹침이 해마다 달라지는 것이 있다」**다. `variesByYear` 는 격자 주일 · temporal 규칙일 · 음력 명절 · 도착 · `guard` 에 참이고, sanctoral 의 고정 `date` 행에는 거짓이다. 조건은 **`w` 또는 `c` 어느 한쪽**이 가변이면 성립한다 — 제외하려는 것은 양쪽 다 고정일인 겹침뿐이다(가변인 `c` 가 고정일 `w` 에 지는 일은 현재 표에서 없지만 — 성체일이 6.24 세례 요한과 만나는 2038 은 §6.2 ③ 으로 성체일이 남는다 — 규칙은 데이터 우연에 기대지 않는다). `displacedBy` 는 이 조건을 만족하는 후보 중 **그 날에 남아 있는 것**(`staying`) 가운데 **실제 후보를 우선한 최상위**다 — `ranked[0]` 이 고정일이고 그 아래 격자 주일이 `c` 를 이기는 경우 `ranked[0]` 이 아니라 그 주일이 실제 원인이다. **남아 있는 것만 센다**: 고정일 승자 W · 가변 V · 더 낮은 고정일 C 가 함께 있으면 V 가 먼저 떠난 뒤 C 에게 남은 상대는 W 뿐이라 C 는 옮기지 않는다(떠난 V 를 세면 고정일끼리인 W·C 가 충돌로 둔갑한다). **실제 후보 우선**: `guard` 는 유효 prec 1 이라 정렬에서 성지주일(prec 2)보다 앞이지만, `displacedBy` 는 실제 후보 중 조건을 만족하는 것이 있으면 그것이다 — 2029·2040 수태고지(3.25 = 성지주일)의 `displacedBy` 는 `guard:easter-octave` 가 아니라 **성지주일**이고, `guard` 가 기록되는 것은 그날 고유 후보가 feria 뿐인 성주간·부활주간 평일(2035 요셉·2025 마르코)에서다. 이 조건이 없으면 **9.29 대한성공회 설립 기념일(prec 4)이 성 미카엘과 모든 천사들(prec 3)에 밀려 매년 9.30 으로 옮겨진다** — 시뮬레이션(2025~2050)으로 드러난 결함. 두 행은 정의상 매년 같은 날이고 본기도 데이터도 한 레코드(`성 미카엘과 모든 천사들 / 대한성공회 설립 기념일`, §5.4)로 합쳐 두었다 — 함께 지키는 날이지 밀린 것이 아니다. 같은 이치로 8.15 광복절 ∧ 성모안식, 9.14 성가수도회 ∧ 성 십자가, 11.1 고요한 주교 ∧ 모든 성인, 1.1 세계평화 기도일 ∧ 거룩한 이름 예수도 이동 대상이 아니다(어차피 낮은 쪽이 `transferable: false` 지만, 규칙은 데이터 우연에 기대지 않는다). 이 다섯 쌍의 `official` 을 무엇으로 두고 낮은 쪽을 `proper` 로 남길지 「생략」할지는 B1 절차 ⑤ 의 몫이다(§9 미결18).

**`guard(d)`** — 보호 기간의 가상 점유자. 스팬은 **`spansOf(year).transferGuard`**(§4.10 — 성지주일 ~ 부활2주일, easter−7 ~ +7, 기도서 「성주간, 부활주간 8일」 — 주요축일 나-2) 하나이고 여기서 날짜를 다시 비교하지 않는다. 그 안의 날에는 유효 precedence 1 · `transferable: false` 인 합성 후보 하나를 낸다. **동률에서는 실제 후보 뒤에 선다** — `rankByPrecedence` 의 정렬 키는 `(유효 precedence, §6.2 ④ 범주 사다리, id)` 이고 사다리의 **마지막 칸이 합성 `guard`** 라, 성 목요일·부활대축일처럼 실제 prec 1 후보가 있는 날은 그것이 `ranked[0]` 이고 `guard` 는 그 뒤다. 그래야 `displacedBy` 가 합성 id 가 아닌 실제 승자를 가리킨다. 그 `observance` 는 표에 없는 합성 객체로 **`id: "guard:easter-octave"` · `name: "성주간·부활 8일"`** 을 가진다 — 보호 기간에 밀린 축일(2035 요셉 · 2025 마르코)의 `displacedBy` 가 이 id 다. `guard:` 접두사는 정의 표의 id 에 나타나지 않는 예약 접두사이고, 뷰는 이 접두사를 보면 표를 찾지 않고 그 이름을 그대로 쓴다(「성주간·부활 8일에 밀려 4.28 로」). 보호 기간의 실제 승자(성 목요일·부활대축일 같은 temporal 행이나 격자 주일)가 따로 있으면 위 정렬 키로 그것이 `ranked[0]` 이 되어 `displacedBy` 는 그 실제 id 고, `guard` 가 `ranked[0]` 이 되는 것은 **그날 고유 후보가 feria 뿐인 성주간·부활주간 평일**에서다. 그 밖의 날에는 빈 배열. 이 점유자는 **기원 날짜의 순위**에도, 아래 **목적지 검사**에도 같은 함수로 들어간다 — 한쪽에만 두면 반쪽이다. 목적지에만 두면 성주간 평일에 **처음 놓인** B 축일이 그날의 `feria`(prec 8)를 이겨 `ranked[0]` 이 되고 아예 옮겨지지 않는다(2035-03-19 성 요셉 · 2025-04-25 성 마르코가 그렇다). 성 토요일이 `rank: null` 인 것도 이 점유자가 덮는다. 뷰에는 내지 않는다 — `resolveDate` 의 후보 출처 ①~⑤ 에 없다.

**`isFree(dest, c, arrivals, departures, next)`** — `c` 가 그 날짜에서 **이길 수 있으면** 빈 날이다. `next` 는 **지연 thunk** 다(§4.9 — 해를 넘기지 않으면 부르지 않아 다음 해 computus 가 돌지 않는다). **`dest` 가 해를 넘겼으면 `arrivals`·`departures` 대신 `next()` 의 두 맵**(`nextYearSeats(year, activated)` — 위)**을 본다**(13차 리뷰). 그 밖은 같다. 여기서 「고유 후보」는 본 루프와 **같은 집합**이다 — `properCandidates(dest)` 에서 `departures.get(dest)`(해를 넘겼으면 `next.nextDepartures.get(dest)`)에 있는 활성화된 선택 봉헌을 뺀 것(켜진 승천은 목요일에 없으므로 그 목요일을 노리는 다른 이동을 막지 않는다). 구체적으로 ① 그 고유 후보와 `guard(dest)` 중 `c` 보다 **높은**(유효값이 작은) 것이 없고 — 같은 값의 고유 후보는 도착 우선(§6.2 ①)으로 `c` 가 밀어내므로 막지 않는다 — ② **이미 도착해 있는 후보가 하나도 없다** — 품계를 보지 않는다(§6.2 ② 선착순. 2008 미국 성공회: 요셉이 3.31 을 지키고 수태고지가 4.1). 같은 날 기원의 둘은 품계 순 → `id` 순으로 먼저 처리된 쪽이 먼저 도착한다. `precedence: null` 후보와 `optional` 은 막지 않는다. `guard` 가 없으면 2027년 수태고지가 성 토요일에, 2035년에는 부활 월요일에 앉는다. 도착한 축일이 그 날짜의 prec 7 후보를 생략시키는 것(절차 ⑤)은 B1 의 `official` 판정에서 다룬다 — 패스는 좌석만 정한다.

**재이동은 없다.** `isFree` ① 로 도착은 그날의 어떤 고유 후보보다 높은 자리에만 앉고, ② 로 뒤의 도착에는 밀리지 않는다. 따라서 한 축일은 많아야 한 번 옮기고, **같은 날짜 `D` 에 도착한 축일이 그 `D` 의 출발에 다시 나타나지 않는다**(§7 ⑧ 불변식 — 기원 `d` 의 출발과 목적지 `dest` 의 도착은 당연히 같은 축일이다. 검사는 날짜별이다). 2035·2046 의 요셉(3.19 성주간 월)은 4.2 에 앉아 **그대로 있고**, 뒤에 밀려온 수태고지(3.25 = 부활대축일)가 4.3 으로 간다 — 2008 의 미국 성공회 배치(요셉 3.31 · 수태고지 4.1)와 같은 모양이다. 종전 초안은 높은 도착이 낮은 도착을 다시 밀게 해 「도착·재출발」 상태와 누적 상한이 필요했는데, 실제 관행이 그렇지 않아 둘 다 뺐다.

**패스가 결정적인 이유 셋.** ① 날짜를 오름차순으로 훑고, `next_day` 는 언제나 **앞으로만** 가므로 어떤 날짜 `d` 에 이르렀을 때 `arrivals.get(d)` 는 완성돼 있다 — 그 뒤에 도착할 것이 없다. ② 연쇄는 이 루프 자체다 — 도착이 그 날짜의 같은 값·낮은 값 **고유** 후보를 밀어내고(§6.2 ①), 밀린 것이 `transferable` 이면 루프가 `d` 에 이르렀을 때 `ranked` 에서 승자가 아니므로 다음날로 간다. 성탄 3축일이 하루씩 밀리는 것이 정확히 이 경로다(어린이들의 `from` 은 12.28, `displacedBy` 는 요한). 밀리는 것은 언제나 고유 후보다 — 도착은 밀리지 않는다(§6.2 ②). 같은 날을 노리는 도착 둘(2038 마르코·필립보와 야고보가 부활 8일을 건너 5.3 에 함께 닿으려는 경우)은 **기원이 이른 쪽**(마르코 4.25)이 5.3, 다음(필립보·야고보 5.1)이 5.4 다(2011 미국 성공회와 같은 배치). ③ 순서는 §6.2 tie-break 로 완전히 정해지고 배열 순서에 기대는 곳이 없다.

**연도 경계.** `next_day` 는 해를 넘길 수 있다 — 12월 말에 밀린 축일이 1월 초에 닿는 경우. 현재 데이터로는 일어나지 않지만(12.26~28 은 늦어도 12.29 에 앉고, 12.31 실베스터·위클리프는 prec 7 이라 옮기지 않는다), 표가 바뀌면 조용히 깨질 자리라 규칙을 못박는다. 캐시에 넣는 `Y` 의 패스는 `computeTransfers(Y, spill(Y−1), activated)` 이고, `spill(Y−1)` 은 `computeTransfers(Y−1, ∅, activated)` 의 arrivals 중 **날짜가 `Y` 이면서 `from` 이 `Y−1` 인 것**이다 — 임시 패스에도 **같은** `activated` 를 넘긴다(인자는 필수, 기본값 없음. 두 패스가 다른 집합을 보면 12월 결과가 어긋난다).

**다음 해 좌석은 모든 패스가 본다**(10·11·13차 리뷰를 거쳐 정리). 12월 이동의 목적지 탐색은 **다음 해 1월까지 넘어간다** — 그때 `isFree` 가 그 해의 켜진 선택 봉헌이 **앉은 자리**(막아야 한다)와 **비운 기원**(열어야 한다)을 알아야 한다. 켜진 공현(`sunday_0102_0108`, 목적지 1.2~1.8)이 1월 초에 앉거나, 켠 주의 봉헌이 기원 2.2 를 비우고 1월 말 주일에 앉는 경우가 그렇다(2028 은 1.30).

이것을 **임시 패스에만** 두면 틀린다(13차 리뷰). 정식 `Y` 패스도 12월 이동의 목적지를 `Y+1` 1월에서 고르므로, `Y+1` 좌석을 모르면 `departures[d].to` 가 이미 차 있는 날짜를 가리키고 **`Y+1` 캐시의 도착과 어긋난다**. 그래서 `nextYearSeats(year, activated)` 를 **모든 패스**가 쓴다 — 경계 계산 경로가 하나다.

**별도 맵인 이유**: 같은 `arrivals`·`departures` 에 넣으면 그것들이 캐시 항목에 섞이고 spill 로 새어 **도착이 둘**이 된다(11차 리뷰에서 실제로 그랬다). `nextArrivals`·`nextDepartures` 는 `isFree` 만 보고, 캐시에 들어가지 않으며, §7 ⑧ 의 셈에도 참여하지 않는다. `spill` 의 `from` 필터는 그 위의 이중 안전장치로 남긴다. 재귀는 늘지 않는다 — `optionalObservancesOf` 는 그해 앵커와 표만 보는 순수 함수라 패스를 요구하지 않는다(다만 `Y+1` 앵커는 필요하다, §4.9).

이 seed 없는 `Y−1` 패스는 **임시**다 — 12월 결과만 쓰고 버리며 캐시에 넣지 않는다(§4.9). `Y−1` 자체를 조회하게 되면 그때 `spill(Y−2)` 로 완전한 패스를 따로 만든다.

`Y−2` 없이 계산한 `Y−1` 의 12월이 완전한 패스의 12월과 같아야 재귀가 깊이 1 에서 끊긴다. **이것은 상한만으로 증명되지 않는다** — `MAX_SHIFT` 는 한 축일의 이동을 막지만, seed 가 밀어낸 고유 축일은 새 이동을 시작하고 그것이 또 다른 축일을 밀 수 있어 원리상 전파에 상한이 없다. 실제로는 전파가 **이동 가능한 축일이 연달아 놓인 날들**을 타고서만 이어지고, 도착이 아무것도 밀어내지 않는 첫 날(고유 후보가 `feria` 뿐인 날)에서 끊긴다 — 성인력에서 이동 가능 축일은 32건이 1년에 흩어져 있어 그런 사슬은 며칠을 넘지 못한다. 그래서 「깊이 1」은 **데이터에 대해 검증하는 불변식**으로 둔다. 단언은 **`spill` 자체의 동등성**이다(13차 리뷰 정정): 1900~2100 전 연도에서 **임시 `Y−1` 패스(seed 없음)가 내는 `Y` 행 spill** 과 **`spill(Y−2)` 를 받은 완전한 `Y−1` 패스가 내는 `Y` 행 spill** 이 같다. 종전에는 「`computeTransfers(Y, spill(Y−1), A)` 과 `computeTransfers(Y, ∅, A)` 가 2월 1일부터 같다」로 적었는데 **그것은 다른 성질을 잰다** — seed 의 영향이 1월에 갇힌다는 뜻이지 깊이 1 이 옳다는 뜻이 아니다. `Y−2` seed 가 `Y−1` 의 12월 배치와 넘어오는 spill 을 바꾸어도 두 `Y` 패스가 **1월 안에 다시 합류하면** 그 단언은 통과하면서 `resolveDate` 의 1월 결과는 틀릴 수 있다. 둘 다 둔다 — spill 동등성이 **깊이 1** 의 근거이고, 「2월 1일부터 같다」는 **seed 영향 범위**의 근거다(§7 ⑧). 표가 바뀌어 이 단언이 깨지면 그때 깊이를 늘리거나 완전한 전년도 패스를 재귀로 만드는 것이 답이고, 지금 코드는 검증된 가정 위에 서 있다. 이 단언이 성립하는 한 캐시 항목의 내용은 어느 해를 먼저 열었는지에 의존하지 않는다. 이 규칙은 **선택 봉헌 목적지에는 적용하지 않는다** — 그것들은 원래 날짜의 ±7일 안이고 해를 넘기는 날짜(1.6·2.2·11.1·승천)가 없다.

**이동 상한.** 한 번의 이동이 `MAX_SHIFT`(30일)를 넘으면 그 축일은 **옮기지 않고 `proper` 로 남기며** `defects` 에 id 를 적는다 — throw 하지 않는다. 이 분기에 이르는 `c` 는 언제나 고유 후보다 — 루프가 `status === "transferred_in"` 을 **먼저 걸러내기** 때문이다. 종전에는 이것을 `isFree` 로 논증했으나(도착은 모든 고유 후보보다 높은 ① 자리에, 다른 도착이 없는 ② 날에만 앉으므로 항상 `ranked[0]`) **그 논증은 0단계 도착에 구멍이 있다**(9차 리뷰) — 활성화된 선택 봉헌은 `isFree` 를 거치지 않고 목적지에 얹히므로 그 자리의 더 높은 고유 후보에게 질 수 있다. 2030-02-02(토) 주의 봉헌을 켜면 목적지가 02-03(일)인데 그날이 **설**(prec 0)이라 봉헌이 `ranked[0]` 이 아니다. 그래서 「도착은 다시 옮기지 않는다」를 논증이 아니라 **루프의 명시 분기**로 둔다. 그 결과 §7 ⑧ 의 단언도 「도착은 그 날의 승자」가 아니라 **「그 날짜를 떠나지 않은 도착은 그 날의 승자」**다(이미 그렇게 적혀 있다 — 0단계 도착만 예외이고 그것도 떠나지 않으므로, 아래 미결19 가 닫힐 때까지 이 케이스는 `I-2` 에서 뺀다). §2 의 설계 원칙(데이터 결손은 빈 결과 + 계속 진행 — throw 는 §2 의 세 경우뿐)을 지키는 것이고, 이론상 무한 루프는 없지만(연중 평일은 언제나 비어 있다) 상한이 없으면 표 결함이 조용히 먼 날짜로 번지기 때문에 둔다. `defects` 는 §9 미결1 이 말한 「개발 빌드에서 드러낼 데이터 결함 신호」의 첫 사례다 — 앱에서 어떻게 알릴지는 그 미결에 얹는다. 실측(2025~2050)으로 가장 긴 이동은 **수태고지 2029·2040 의 15일**(3.25 성지주일 → 4.9 — 2018 미국 성공회와 같다), 그다음 요셉 2035·2046 의 14일(3.19 성주간 월 → 4.2), 수태고지 2043 의 12일이다. 성탄 3축일은 각각 하루다. 한 축일은 한 번만 옮기므로(§6.2 ②) 누적 상한은 필요 없다. 유닛이 1900~2100 전 연도에서 이동 ≤ 15 를 단언한다(§7 ⑧).

**선택 봉헌**(§6.2)은 날짜 루프 **전에** 0단계로 한 해 전체를 선색인한다 — 순위에 의존하지 않고, `nearby_sunday` 의 목적지는 기원보다 **앞**일 수 있어(2028 주의 봉헌 2.2 → 1.30) 루프 안에서 처리하면 목적지를 이미 지나친 뒤다. 꺼진 것은 **별도 색인 `optionals`** 에 얹고 원래 날짜의 고유 후보를 옮기지 않는다 — 목적지 주일에 `status: "optional"` 을 **더한다**. `arrivals` 에 섞지 않는 이유: 도착·출발 색인은 「출발 수 = 도착 수 − seed 도착 수」·「도착은 그 날의 승자」 불변식(§7 ⑧)을 지는데, 선택 봉헌은 출발이 없고 승자도 아니라 섞이면 그 불변식이 매년(승천) 깨진다. `isFree` 는 `optionals` 를 보지 않는다(설정이 켜기 전에는 좌석을 차지하지 않는다).

**패스가 B1 소속인 이유와 PR 2 의 몫.** 패스는 `rankByPrecedence` 를 쓰므로 품계 비교(§6.1)가 있어야 돌아간다 — PR 3 이다. 그러나 `resolveDate` 의 반환 형태(`Candidate[]`·`official`)와 ⑤ 조회 경로는 PR 2 가 만든다. PR 2 의 `transfers` 는 `EMPTY_PASS()` — **네 필드를 모두 갖는** 빈 패스(`arrivals`·`departures`·`optionals` 빈 Map, `defects` 빈 배열)이고 모든 후보가 `proper` 다. §5.5 가 `optionals` 까지 읽으므로 둘만 만들면 PR 2 에서 `undefined` 접근이 난다. 이렇게 갈라야 PR 2 의 뷰·테스트가 PR 3 에서 형태 변경 없이 그대로 산다.

1. ◐ **동점 정렬 키** — **절반 닫혔다(2026-09-13)**: §6.2 ④ 를 **범주 사다리**(`도착 > temporal > sanctoral > 격자 > guard`)로 바꿔, 격자 ∧ temporal 동률(성지주일 · 대림1주일 · 사계재 4행)에서 승자와 전례색이 `id` 우연으로 갈리던 것을 없앴다. **남은 것은 같은 범주 안의 동률**이라 사다리가 가르지 못한다 — 12.25 세 행(미결12 와 같은 날짜) · prec 7 **축일 ∧ 축일** 5건(미결6 — 7건 중 축일 ∧ 기념일 2건은 2026-09-17 기념일 유효값 9 개정으로 동률에서 빠졌다). 이 잔여는 데이터 결함 신호가 아니라 **규정이 순서를 정하지 않은 자리**이므로 사제 확인으로 닫고, 그때까지 `id` 사전순으로 결정성만 지킨다. 함께 남는 것: 진짜 결함성 동점을 개발 빌드에서 어떻게 드러낼지 — 리포트 경로가 데이터 저장소에만 있어 앱에서 알릴 방법이 미정이다(§6.5 `defects` 가 같은 문제의 첫 사례). **개정 2026-09-17**: 사계재 4행과 기념일 16행은 **승자 자격이 없는 후보**가 됐다(§6.1 유효 precedence 9 — 미결23·24 해소). 남는 격자 ∧ temporal 동률은 성지주일·대림1주일뿐이다.
2. **`local-observances.json` 을 언제 싣는가** — B2 `scope` 오버레이 전까지 안 싣기로 했으나, 본당 지정이 설정에 생기면 캘린더 묶음으로 옮겨야 한다.
3. **전례년 경계의 사용자 표시** — 12월 말에 "가해"에서 "나해"로 넘어가는 것을 UI 가 어떻게 알릴지는 ADR-038 몫이지만, 엔진이 `liturgicalYearOf` 를 공개 API 로 낼지 정해야 한다.
4. ~~**`vigil`(전야) 모델**~~ **해소 2026-09-01** — 근거였던 12.31 거룩한 이름 예수 전야가 **감사성찬례가 아니었다**. 거룩한 이름 예수 축일(1.1) 전날의 **저녁기도**이고(사용자 확인), 그 레코드에만 복음이 없던 것이 그 증거였다 — 종전 923건 중 유일. 성무일과로 판정해 데이터에서 제외했다(data PR#23). **엔진이 만들 모델이 없다** — 전야는 모델의 빈틈이 아니라 잘못 실린 레코드였다. ADR-036 미결10 의 이 갈래도 함께 닫힌다.
5. ◐ **사계재 조인 — 절반 닫혔다**(2026-08-29, data PR#17 · ADR-036 미결13). **요일 배정은 확정**됐다(수=성직자·금=성직후보자·수도자·토=모든 신자, 네 계절 공통, 기도서 확인) 그리고 16건 전부 `weekday` 를 갖는다. **남은 것은 계절 식별자다** — 사계재 계절이 양쪽 모두 한국어 `name` 안에만 있어(temporal `coord_name: null`, 본문 `season: null`) 오늘의 조인은 이름 부분문자열에 기댄다(§5.4). 표기가 바뀌면 조용히 끊어지므로 **양쪽에 명시적 기계 키를 넣는 것이 데이터 쪽 후속 과제**다. 그때까지 엔진은 부분문자열 조인을 쓰되 그 취약함을 알고 써야 한다.
6. **`precedence: 7` 동률의 tie-break** — `minor_feast`(95 — 96 → **95** — 2026-09-19 안나와 요아킴 07.26 을 주요축일 나 그룹으로 옮긴 데이터 브랜치 `data/anne-joachim-major-feast` 반영 뒤, 미결27)와 `commemoration`(16)이 같은 값이다. 규정에 순서가 없어 §5.3 의 안정 정렬로 결정성만 확보했다. 실제로 두 날이 겹치는 사례가 있는지부터 확인해야 한다(없으면 문제도 없다). **사용자 확정 2026-09-17** — 겹치는 두 성인은 **둘 다 본기도·독서를 만들고 독자가 고른다**(§5.6). 남는 것은 기본 선택(승자) 순서뿐이라 규정 확인은 그대로 둔다. **정정 2026-09-19**: 7건 중 축일 ∧ 기념일 2건(05.03 · 09.04)은 §6.1 개정(기념일 유효값 9)으로 동률이 아니게 됐고 — 축일이 승자, 기념일 `proper` — 축일 ∧ 축일 **5건**(02.14 · 03.01 · 06.09 · 08.05 · 12.31)만 `id` 사전순 초기 선택으로 남는다.
7. ~~**`national` 4건의 본문 조인이 어긋난다**~~ **해소 2026-08-29** — 실측하니 **4건 모두 조인된다**(삼일절 03.01 · 광복절 08.15 는 `date`, 설날 · 추석은 `lunar` 1-1 · 8-15). 「2건만 나온다」는 `date` 만으로 맞춰 본 결과였다 — 음력 두 건이 떨어져 나갔던 것이다. §5.4 가 이미 키를 `date` + `lunar` 로 적고 있으니 규정은 그대로고, 집계가 틀렸다. **엔진 함의**: 날짜 인덱스를 만들 때 `lunar` 를 같은 인덱스에 넣지 않으면 이 네 날이 조용히 빈다.
8. ~~**주일 주기(A/B/C)의 기준 연도가 저장소 어디에도 없다**~~ **해소 2026-08-29** — **2026년 = 가해(A)**(사용자 확정). §4.7 에 기준 연도와 유도 규칙(`N % 3` → 1 A · 2 B · 0 C), 그리고 대림 경계 네 날(2025-11-29/30 · 2026-11-28/29)을 회귀 케이스로 적었다. 데이터에는 날짜와 주기를 함께 가진 레코드가 없어(고정일 「모든 성인의 날」 4건뿐) 실측 교차 검증은 못 했다 — **A1 구현 시 실제 연도의 주일 독서를 교구 달력과 대조해 확증할 것.**
9. ~~🔴 **옮겨온 축일을 목적지 날짜에서 찾는 경로가 없다**~~ **해소 2026-09-05** — §6.5 이동 패스를 신설했다. 연도 캐시에 `transfers`(도착·출발 색인)를 두고(§4.9), `resolveDate` 의 후보 출처에 ⑤ 도착 이동을 더하고(§5.5), 후보를 `Candidate` 래퍼(`status`·`from`·`to`·`displacedBy`)로 바꿨다(§1.3 ⑤). 패스는 날짜 순 단일 루프로 결정적이고, 해를 넘기는 이동은 `Y−1` 의 spill 을 seed 로 받아 깊이 1 재귀로 닫는다. 설계 과정에서 드러난 것 넷을 새 미결로 갈랐다 — 데이터의 재의 수요일 `transferable: false`(미결13), prec 3 동률(미결14), 선택 봉헌을 켜는 설정(미결15), 연쇄 모델의 사제 확인(미결17). §6.3 ② 의 「B 는 성주간에 겹칠 수 없다」도 실측으로 틀린 것이 드러나 정정했다. ADR-037 §6 의 `candidates` 계약을 함께 개정했다.
10. ~~🔴 **주님의 세례가 좌표를 둘 요구한다**~~ **해소 2026-09-01 → 확증 2026-09-18(2026 책자 일러두기, Q11 닫힘 — 사제 확인 불필요)** — 좌표는 하나이고 **`ordinary` · week 1 · `sunday`** 다. `ResolvedDate` 스키마도 특례도 만들지 않고, 절기 스팬을 「`christmas` = 12.25 ~ **주의 세례 전날**」로 고쳤다(§4.5). 근거 셋은 §4.5 에 적었다 — 주요축일(가) 3항이 「절기주일과 겹치면 다음날」인데 이 축일은 `transferable: false` 라 옮길 자리가 없다는 것, 전례색 예외가 이 날을 왕이신 그리스도 주일과 묶어 「**연중** 첫 주일」이라 부른다는 것, 정의 표·본문 좌표가 이미 `ordinary/1` 이라는 것. 종전 미결의 근거였던 「연중 주차 표가 세례주일을 1주로 두고 센다」는 **사실이 아니었다**(1주 창 `01-07`~`01-13` 에 1900~2100 전 연도가 든다 — 재검증 2026-09-13). **전사에 명시된 규칙이 아니라 도출한 것이라 사제 확인 대상**이다(검토 문서 Q11). 이 판정이 그날의 **승자**도 정한다(§4.5 끝 문단). **확증 2026-09-18 — 「2026 전례독서」(대한성공회 주교원 전례위원회 감수) 일러두기**: 「성탄절기 — 2025년 12월 25일부터 … 주님의 세례 축일(1월 11일) **전일까지**」 · 「연중시기 — 2026년 1월 11일(주님의 세례 축일, **연중 1주일**)부터」. 도출이 아니라 관구 공식 문서의 명시가 됐다 — Q11 닫힘(검토 문서 X-10 ①).

    **표현보다 먼저 정할 것이 승자다(2026-09-13 확인).** `t-주님의-세례` 행은 `ordinary/1/sunday` · prec **3** 인데(실측), §4.5 의 절기 스팬은 그날을 `christmas` 에 둔다. 격자를 스팬대로 **성탄절기 주일**로 합성하면 절기 주일이라 prec **2**(ADR-036 §6 개정 2026-07-17 ③ 이 성탄절기 주일을 절기 주일에 넣었다) — 격자가 temporal 행을 **이겨 「성탄 N주일」이 `official`** 이 되고 주님의 세례는 `transferable: false` 라 옮겨지지도 않는다. 데이터 행대로 `ordinary/1`(연중 주일 5)로 합성하면 주님의 세례가 이긴다. **동률이 아니므로 §6.2 ④ 사다리로는 풀리지 않는다.** 격자 합성 좌표를 무엇으로 둘지가 곧 답이고, PR 1 이 절기 스팬을 짜기 전에 닫아야 한다(§5.5 · 검토 문서 C-4.5-4).
11. ~~🔴 **`findReadings` 에 성인 공통 폴백이 없다**~~ **해소 2026-09-17** — §5.6 에 「성인 공통 독서 폴백」을 정의했다. 본기도와 같은 표·같은 키(`sanctoral_class` → `commons.classes[cls].readings`)를 타되 **트리거는 따로다** — 본기도의 `has_proper` 는 파서가 본기도 실매칭으로 정한 **본기도 축의 사실**이라 독서에 못 쓴다(사베리오 12.03: `has_proper: true` · 독서 0). 독서의 트리거는 「이 관측일의 고유 독서가 없다」이고, **「날짜 인덱스가 비었다」가 아니다** — 실측으로 루시안(01.08) · 실베스터 · 위클리프(12.31) · 데이빗(03.01) 넷이 자기 날짜에 남의 본문(`성탄주간` · `삼일절`)을 두고 있어 그 구현은 넷에게 오답을 준다. 그래서 판정은 §5.4 의 1:N 을 이 관측일 것으로 **좁힌 뒤**이고(미결12 와 맞물린다 — 다만 오늘 데이터는 `type: weekday` 날짜 전용 본문과 다른 행에 이름 조인되는 본문 둘만 걷어내면 149행 전부가 결정된다), 반대로 이름 조인 실패(06.24 세례 요한 탄생 — 띄어쓰기)가 폴백으로 새지 않도록 **행이 하나뿐인 날짜는 이름을 묻지 않는다.** 반환은 고유와 같은 그룹 형태에 `common: "<class>"` 표지와 `common:<class>-s<set>` id, 고유·공통 배타, `anniversary` 는 빈 배열(격자 후보가 그날 독서를 든다). 커버리지 82 / 13 / 16 이 실데이터 불변식(§7). 종전 지적 — `commons.json` 은 분류별 독서를 이미 갖고 있었다(7분류 22세트, `anniversary` 만 0 이고 그건 「고정 전례독서 없음」이 맞다). 규칙이 없어서 못 쓰는 것뿐이었다. 데이터 쪽 선택 후속: `has_proper_readings` 를 파서가 실매칭으로 발행하면 트리거가 데이터 사실이 된다.
12. 🔴 **날짜 인덱스가 1:N 인데 좁히는 규칙이 없다** — §5.4 의 `date → Entry[]` 는 그 날의 본문을 **전부** 준다. `findReadings(resolved, candidate)` 는 고른 관측일 **하나**의 본문을 내야 하므로 좁히는 규칙이 필요한데, 정해 두지 않았다. 실측(2026-09-01)으로 확인한 충돌은 다음과 같다.

    | 날짜 | 성인력 행 | 본문 레코드 | 무엇이 문제인가 |
    |---|---|---|---|
    | 12.25 | 3 (성탄 낮·밤·새벽) | 6 | 셋이 **다 본문을 가진다**. 낮을 물었는데 밤이 섞이면 결손이 아니라 **오답**이다 |
    | 08.15 | 2 (광복절·성모안식) | 3 | 마찬가지로 둘 다 본문을 가진다 |
    | 09.29 | 2 (대한성공회 설립 기념일·성 미카엘과 모든 천사들) | 1 | 그 한 레코드의 이름이 **`성 미카엘과 모든 천사들 / 대한성공회 설립 기념일`** — 슬래시로 합쳐져 **양쪽 다 이름 조인에 실패한다** |
    | 12.31 | 2 (실베스터·위클리프) | 1 | 그 레코드는 `성탄주간` 이라 **둘 중 누구의 것도 아니다.** 날짜만으로 집으면 엉뚱한 본문이 붙는다 |
    | 01.01 · 03.01 · 05.03 · 09.14 · 11.01 | 각 2 | 1~4 | 한쪽만 본문을 가진다 — 본문 없는 쪽을 물어도 있는 쪽 것이 나온다 |
    | 02.14 · 06.09 · 08.05 · 09.04 | 각 2 | 0 | 오늘은 무해하다(본문이 없다). 생기면 위 갈래로 옮겨간다 |

    **방향**: `date`(+`lunar`)로 뽑은 뒤 관측일의 `name`·`aliases` 로 좁힌다. 다만 그것으로 닫히지 않는 잔여가 위 표의 09.29·12.31 이다 — 전자는 **데이터의 이름이 두 관측일을 하나로 합쳐** 놓았고, 후자는 **날짜만 같은 남의 본문**이다. 이름 조인의 불안정성은 §5.4 가 이미 표로 적어 두었다. **본문 레코드에 안정적인 `sanctoral_id` 참조를 넣는 것이 근본 해법**이고 데이터 쪽 과제다(ADR-036 §10 「잠정 순번 id 를 키로 쓰지 말 것」과 같은 계열 — `local-observances` 는 이미 `patron_refs[].sanctoral_id` 로 그렇게 하고 있다). 그때까지 엔진은 이름 조인을 쓰되 **좁히기에 실패하면 빈 결과가 아니라 후보 전부를 내고 뷰가 고르게 할지**를 정해야 한다 — 조용히 하나를 고르는 것만은 하지 않는다. 규칙이 정해지면 §7 에 12.25 세 갈래와 09.29 를 회귀 케이스로 넣을 것. **사용자 확정 2026-09-17** 이 마지막 물음의 방향을 정했다 — 한 날짜의 성인 둘 이상은 각각의 본기도·독서를 **모두 만들고 독자가 고른다**(§5.6). 따라서 좁히기 실패 시에도 빈 결과나 조용한 택1이 아니라 **후보 전부**다. 남는 것은 어느 레코드가 어느 후보 것인지(09.29 합성 · 12.31 남의 본문)이고, 그건 여전히 `sanctoral_id` 참조가 근본 해법이다.
13. 🔴 **재의 수요일이 `transferable: false` 다(데이터)** — ADR-036 §7 규칙 2 와 temporal 행의 `note` 는 「설과 겹치면 다음날로」라 적었는데 규칙 열이 비어 있다. **2032-02-11 에 실제로 겹친다**(KASI 범위 안 유일). 엔진은 데이터가 말하는 대로만 옮기므로(§6.2) 그해 재의 수요일은 설에 밀린 채 옮겨지지 않는다. `transferable: true` · `transfer_to: "next_day"` 로 고치는 것이 데이터 저장소 과제 — `calendar/` 표에서 고치고 파서를 다시 돌리면 된다. 고치면 §7 ④ 의 skip 케이스를 켠다.

15. **선택 봉헌을 켜는 설정(UI 쪽)** — 엔진 쪽 계약은 정해졌다(§6.2 활성화 계약: `computeTransfers(…, activated)`, 켜면 원래 날짜에서 떠나 목적지 주일의 도착이 되고 충돌 이동은 생기지 않으며, `transferCache` 는 설정 변경 시 통째로 비운다). 남은 것은 **누가 `activated` 를 채우는가** — 본당 단위 일괄인지, 축일별(공현·모든 성인·승천·주의 봉헌 넷)인지, ADR-036 B2 `scope` 와 묶이는지. ADR-038 의 몫이다. 설정이 생기기 전까지 `activated` 는 빈 집합이고 뷰는 `optional` 을 「이 주일에 옮겨 지킬 수 있음」 안내로만 쓴다. **방향 확정 2026-09-19(사용자)**: 옮길지는 대개 **지역 교회의 사제가 정한다** — 앱이 설정으로 결정하지 않는다. 독자가 그 결정을 **모를 수 있으므로**(같은 날 두 번째 확정) 한쪽을 기본으로 깔고 다른 쪽을 링크로 숨기지 않는다 — v1 은 `activated = ∅` 고정이고 뷰는 **두 독서를 선택지로 나란히** 낸다: ① 당일(8.6) 「주의 변모 독서」 / 「오는 주일로 옮겨 지키는 경우의 평일 독서」 ② 목적지 주일(8.9) 「그 주일 독서」 / 「주의 변모 독서(옮겨 지키는 경우)」(`optional` 후보) ③ 규칙상 옮겨진 축일이 도착한 날도 후보들을 선택지로. `official` 은 표시만 하고 선택을 대신하지 않는다. ADR-038 §3 에 적었다. `activated` 계약은 본당 설정이 생길 때를 위해 남긴다.

20. **성 토요일 하루에 전례가 둘이다 — 시간 구분이 없다** — `easter_offset: -1` 에 `t-성-토요일`(prec `null` · 홍 · `lent`)과 `t-부활밤`(prec 1 · 백 · `easter`)이 함께 걸린다(§4.3). 품계로는 부활밤이 승자이고 ADR-036 §8 의 백색 기간도 「부활밤~」인데, 같은 절이 「성주간 전체 홍 — 성 토요일까지」도 말한다. **두 규정은 시간으로만 갈린다**(낮 홍 / 밤 백). 엔진은 날짜당 색 하나·승자 하나라 지금은 표현할 자리가 없다. 잠정은 **승자 = 부활밤 · 색 = 홍**(가드 유지, §6.4)이고, 부활밤의 백색은 후보의 `color` 로 남는다. 결정할 것: ① 뷰가 「낮/밤」을 가르는가(ADR-038) ② 가른다면 `ResolvedDate` 가 색을 둘 내는가 ③ 아니면 그날만 특례로 백을 내는가. 성무일과가 범위 밖(§1.2)인 것과는 다른 문제다 — 부활밤은 **감사성찬례**다. **사제 확인 대상**(검토 문서 Q10). **근거 추가 2026-09-18(책자)**: 4.4 성주간 토요일 칸은 **[홍] · 「감사성찬례 없음」** 이고 **「부활밤 예식 [백]」** 은 저녁 칸에 따로 실렸다(로마 6:3-11 · 시편 114 · 마태 28:1-10 — data #25 와 동일). **성탄밤도 같다** — 12.24 칸은 [자] 대림 평일이고 「성탄밤 [백]」(이사 9:1-6 · 시편 96 · 디도 2:11-14 · 루가 2:1-14)이 저녁 칸에, 12.25 칸에는 성탄새벽·성탄낮 두 단만 있다(2025·2026 두 해 다). 즉 책자는 **저녁 감사성찬례를 그날의 낮과 분리해 표기**하고 색도 따로 단다. 잠정 판정(성 토요일 홍 · 부활밤은 자기 백)과 맞고, 모델 물음 ①(뷰가 낮/밤을 가르는가)의 답이 「가른다」로 기운다. 함께 정할 것: 데이터의 `성탄 밤` 이 `12.25` 에 있는데 책자는 12.24 저녁이다 — 부활밤·성탄밤에 **저녁 전례 표지**(`evening: true` 류)를 두고 그 후보는 그날 낮의 승자·색을 정하지 않게 하는 것이 최소 변경. 「전야」로 적힌 것들(공현·봉헌·수태고지·승천·성령강림·삼위일체·성모 방문·성체·세례 요한·변모·성 십자가·모든 성인·거룩한 이름 예수)은 전부 저녁기도 칸의 **성무일과**라 미결4 대로 엔진 밖이다. **사용자 결정 대상**(Q10).

25. **고유 독서가 없는 축일(prec 7)의 초기 독서 — 책자는 평일 독서를 인쇄한다(2026-09-18, 서울교구 2026 달력 9월 면 · X-8)** — 9.15 키프리안 [홍] · 9.16 니니안 [자/백] · 9.19 데오도르 [자/백] 세 날 모두 **제목과 색은 성인 것, 독서는 연중 24주 평일 II 격자 것**(1고린 12:12-14 … / 12:31-13:13 … / 15:35-37 …)이다. 셋 다 `has_proper: false` 이고 데이터에 그날 독서가 0건이라 §5.6 폴백으로는 순교자·선교사·성직자 공통이 나온다. 책자 62쪽 「성인 공통」 머리글이 근거다 — 「성인은 교회력에 정한 우선순위 규칙을 따라 지켜야 한다. 아래에 있는 본기도 가운데에서 **집전자가 임의 선택하여** 이에 상응하는 성시, 성서 독서 등과 함께 사용할 수 있다」: 공통 본기도·독서는 **선택**이다. 그러니 미결11 의 폴백은 맞되(성인 칩의 본문으로) **그날의 초기 독서는 격자 평일**이다. 제안: `official` 은 그대로 성인(제목·색·본기도)이고, **초기 독서 선택**만 「`official` 의 독서가 §5.6 `common` 표지뿐이면 격자 칩을 먼저」로 둔다 — 뷰 규칙(ADR-038 §3)이라 엔진 계약은 바뀌지 않는다. 고유 독서가 있는 축일(10행 — 삼일절·광복절·성모 탄신 …)과 주요축일은 그대로 자기 독서. **사용자 결정 대상.** **책자 전체로 재확인(2026-09-18)**: 고유 독서가 없는 축일은 한 해 내내 평일 독서 + 성인 색(힐러리·안토니오·파비안·아그네스·빈센트·아퀴나스·아가타·도로테아·폴리갑·페르페투아·키릴·패트릭·크랜머·안셀름·조오지·카타리나·아타나시오·둔스탄·헬레나·베다·어거스틴·리처드·알반·에텔드리다·베네딕트·보나벤투라·마가렛·아리마태아 요셉·도미닉·로렌스·클라라·버나드·모니카·어거스틴·애단·그레고리·키프리안·니니안·데오도르·제롬·피데스·데니스·윌프리드·에드워드·데레사·익나시오·채드·알프레드·레오·마틴·마가렛·휴고·힐다·클레멘트·카타리나·루시안·바바라·루시아 …)이고, **고유 독서가 있는 축일은 그 독서**를 인쇄했다(라틴 문 앞의 요한 5.6 · 마리아와 마르타 7.29 · 베드로의 탈옥 8.1 · 세례 요한의 참수 8.29 · 성모 탄신 9.8 · 모든 별세자 11.2 · 성모시태 12.8). 예외 하나: **사베리오 2025-12-03 은 선교사 공통 1세트**(이사 52:7-10 · 시편 96:1-7 · 사도 1:1-9 · 루가 10:1-9)를 인쇄했는데 **2026-12-03 은 평일 독서**다 — 같은 책자 안에서 갈리므로 규칙으로 삼지 않는다. 제안은 그대로다(공통은 칩, 초기 독서는 격자).
26. **사계재 날의 색 — 책자는 독서와 무관하게 [자]다(2026-09-18, 9월 면 · X-8)** — 미결23 해소 때 「그날은 절기색, 사계재 본문을 읽을 때만 자색」으로 적었는데(사용자 확정 2026-09-17), 책자는 **9.18(추계재 금)을 격자 독서 그대로 인쇄하면서 색은 [자]**로 두었고, 축일과 겹친 **9.16·9.19 는 [자/백] 병기**(사계재 자 + 성인 백 — 격자의 녹은 나오지 않는다), 관측일이 없는 9.17 만 [녹]이다. 즉 색은 「어느 독서를 읽나」가 아니라 「그날 어떤 관측일이 있나」를 따른다. 제안(되돌림): ① 승자가 격자 평일이고 사계재 후보가 있으면 그날 `color` 는 **자** ② 승자가 축일이면 `color` 는 축일 색이고 사계재 자를 **병기**(`colorAlt` 재사용 또는 `colors` 배열 — PR 2 의 `ResolvedDate` 타입 선언 전에 정해야 한다) ③ 사계재 본문을 읽을 때의 색 규정은 그대로 두되 그날 색이 이미 자라 따로 필요 없다. `omitted` 후보(주일에 밀린 루시아·도착에 밀린 암브로스)는 색에 기여하지 않는다(12.13 [자] · 12.7 [백]과 일치). **사용자 확정 2026-09-17 을 뒤집는 것이라 결정을 다시 받는다.** 정해지면 §6.2 ④ 따름정리 ① · §6.4 · C-6.4-3 · ADR-036 미결11 · ADR-038 §3 이 바뀐다. **책자 전체(2026-09-18)**: 춘계재 2.25·27·28 [자](사순) · 하계재 5.27 **[백/자]** · 5.29 [자] · 5.30 [자] · 추계재 9.16 [자/백] · 9.18 [자] · 9.19 [자/백] · 동계재 12.16·18·19 [자](대림). 5.27 의 백은 니니안 같은 성인이 아니라 **그 주 전체가 [백]** 이기 때문이다(미결30) — 사계재 자는 그날의 다른 색에 **병기**되고, 다른 색이 절기 녹뿐이면 자만 남는다(9.18). 제안 ①·② 그대로.
