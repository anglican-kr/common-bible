## 요약

워크플로 다섯이 쓰는 GitHub 공식 액션을 최신 큰 버전으로 올렸다. `actions/checkout`과 `actions/setup-node`는 v4에서 v7로, `actions/setup-python`은 v5에서 v7로 올렸다. #436의 CI에 「v4는 지원이 끝나는 Node 20으로 실행된다」는 GitHub 공지가 떠서 시작했다. 그 공지는 #436의 변경과는 관계가 없다.

## 확정 · 근거

- **v7로 올렸다**(사용자가 맡김 2026-10-26). 처음에는 `checkout` v5로 올리자고 말씀드렸는데, 확인해 보니 세 액션 모두 최신이 v7이었다.
- **릴리스 노트에서 확인한 큰 변화와 우리 설정**
  - `checkout` v6은 인증 정보를 따로 된 파일에 저장한다. v7은 `pull_request_target`, `workflow_run` 이벤트에서 포크 PR을 받지 못하게 막는다. 우리는 이 두 이벤트를 쓰지 않는다.
  - `setup-node` v5부터는 `package.json`의 `packageManager` 칸이 npm이면 패키지 캐시를 저절로 켠다. 우리 파일에는 그 칸이 없어 지금은 켜지지 않는다. 그래도 `package-manager-cache: false`를 적어 앞으로도 끈 상태로 둔다. 시크릿을 쓰는 워크플로(`sync-data.yml`)가 캐시를 읽으면 오염된 캐시를 받을 위험이 생기기 때문이다.
  - `setup-python` v7은 `pip-install` 입력을 없앴다. 우리는 쓰지 않는다. 쓰는 버전(3.12)도 계속 지원된다.
- **버전은 큰 버전 이름(`v7`)으로 적었다.** 커밋 해시로 고정하면 더 안전하지만 올릴 때마다 손이 간다. GitHub가 직접 만드는 액션이라 지금처럼 큰 버전 이름으로 둔다.
- **머지 뒤에 확인할 것**: `sync-data.yml`은 받아 온 인증 정보로 브랜치를 push한다. `checkout` v6에서 인증 정보를 저장하는 방식이 바뀌었으므로, 머지 뒤 손으로 한 번 실행해 push가 되는지 본다. `engine-data.yml`은 main에 push될 때 실행되므로, 이 PR을 머지하는 것이 곧 첫 실행이다.
- **`prose.yml`도 함께 올렸다.** #436이 더한 워크플로로, 이 PR을 만드는 동안 #436이 먼저 머지되었다.
- **문서**: ADR-013과 설계서 07장에서 지금 상태를 말하는 문장은 버전이 요점이 아니어서 버전 번호를 뺐다. ADR-013에 있는 처음(PR #42) 설정 예시는 그때의 기록이라 그대로 두었다.
- **데이터 저장소**: 워크플로 셋(`validate.yml`, `pipeline.yml`, `build.yml`)도 `checkout@v4`, `setup-python@v5`를 쓴다. 데이터 저장소의 PR로 따로 올린다.

## 검증

- 워크플로 다섯을 YAML로 읽어, 액션 버전과 `package-manager-cache: false`(불리언)가 들어간 것을 확인했다.
- 이 PR의 필수 검사(`Unit tests`, `Change ledger`)가 새 `checkout`과 `setup-node`로 실행된다.
- 문서 검사(`node --test tests/unit/docs-*.test.js tests/unit/liturgical-fixtures.test.js`): 31개 통과. 교회력 사실 토큰 비교(`--strict-counts`): 바뀐 것 없음.
