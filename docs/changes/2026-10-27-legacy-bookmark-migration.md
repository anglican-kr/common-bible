## 요약

2026-05-04 전의 버전은 북마크를 옛 키(`bible-bookmarks`)에만 저장했다. 앱이 이 목록을 동기화 저장소로 옮기는 저장이 거절되면, 목록이 비어 보이고 다음 저장이 옛 목록을 지웠다(known-issues §34). 이제 옮겼는지를 동기화 저장소에 북마크 기록이 있는지로 판단하고, 옮기지 못한 동안에는 동기화 저장소를 읽는 함수(`store-v2.js loadLocal`)가 옛 키의 목록을 담아 돌려준다. 결정은 ADR-015 D7에 더했다.

## 확정 · 근거

- 사용자 결정(2026-10-27): 고치는 법은 옛 목록을 읽어 보이는 방식으로 했다. 옛 키를 비우고 옮기는 방식은 되돌리는 쓰기가 거절되면 목록의 하나뿐인 사본을 잃어 버렸고, 고치지 않고 기록만 두는 안도 버렸다. 옮기지 못한 동안 따로 알리지 않는다.
- 처음에는 옮기지 못한 동안에도 「여러 개를 골라 한 번에 지우면 저장된다」고 설명했다. 계산해 보니 지운 항목마다 삭제 기록이 남아, 북마크가 8,000개면 약 2,700개를 한 번에 지워야 했다. 이 사실을 알린 뒤 사용자가 다시 알리지 않기를 골랐고, 남는 불편은 known-issues §37로 적었다.
- 판단 기준을 「동기화 저장소에 북마크 기록(항목과 삭제 기록)이 하나도 없고 옛 키에 목록이 있음」으로 한 까닭: 지금 앱에서 이 상태가 생기는 것은 옮기기가 거절됐을 때뿐이다. 북마크를 모두 지우면 삭제 기록이 남고 옛 키에는 빈 목록을 쓴다. 줄어드는 쓰기는 저장 공간을 더 쓰지 않으므로, 저장 공간이 찬 까닭으로는 거절되지 않는다. 삭제 기록이 30일 뒤 지워져도 옛 키는 이미 빈 목록이다. 동기화 결과는 동기화 저장소에 저장한 뒤에만 옛 키에 쓴다.
- 같은 기준 덕분에, 고치기 전 버전이 이미 빈 목록의 문서를 만든 기기도 옛 목록이 다시 보인다. 그 뒤 북마크를 저장했거나 동기화 결과를 받은 기기는 옛 키가 이미 바뀌어 되살릴 수 없다.
- 옛 키에서 읽은 항목의 수정 시각은 앱을 한 번 연 동안 같은 값을 쓴다. 읽을 때마다 새 시각을 주면 같은 문서를 두 번 읽어도 결과가 달라진다.
- 기기 id를 저장하는 쓰기(`_getOrCreateMeta`)의 거절도 함께 처리했다. 이 쓰기가 오류를 내면 `app.js` 맨 위의 시작 코드가 거기서 멈춰, 그 뒤의 설정 적용과 시트 준비가 실행되지 않는다.
- 일부러 바꾸지 않은 것: 동기화 저장소의 값을 JSON으로 읽지 못하면 전처럼 빈 문서를 돌려준다. 옛 키는 늦은 두 번째 사본일 수 있고 삭제 기록이 없어서, 이것으로 채우면 다른 기기가 지운 북마크가 동기화에서 되살아날 수 있다.

## 검증

- 유닛 `node --test tests/unit/*.test.js`: 1,417개 가운데 1,416개 통과, 실패 0개. 건너뛴 1개는 원래 꺼 둔 교회력 픽스처(미결13)다. 타입 검사(`npm run typecheck`) 통과.
- `tests/unit/store-v2.test.js`에 옛 키의 목록 옮기기 테스트 7개를 더했다. 저장 공간이 찬 저장소를 흉내 내, 고치기 전 코드에 돌리면 4개가 실패한다(옮기기가 거절된 뒤의 목록, 저장 공간이 생긴 뒤의 옮기기, 이미 빈 목록이 된 문서, 기기 id 저장의 거절).
- e2e 전체 397개 통과(작업 폴더 서버, 포트 8093, 11분). 새 e2e는 옛 키에만 북마크 30개를 두고 동기화 저장소에 옛 목록보다 긴 쓰기만 거절한다. 고치기 전 코드에서는 북마크 화면을 처음 열 때부터 0개가 보여 실패했다. 흉내를 위해 `conftest.py`의 저장 공간 흉내에 「몇 글자보다 긴 쓰기만 거절」하는 선택지를 더했다.
- 옮기지 못한 기기가 한 번에 지워야 하는 수(known-issues §37)는 실제 `store-v2.js`를 Safari의 셈을 흉내 낸 저장소(5 MiB, 한글이 든 값은 한 글자 2바이트)에서 실행해 쟀다. 스크립트는 한 번 쓰는 것이라 저장소에 두지 않았다.
- 실제 Safari와 iPhone에서는 확인하지 않았다.
