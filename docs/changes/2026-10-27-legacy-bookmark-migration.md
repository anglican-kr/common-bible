## 요약

2026-05-04 전의 버전은 북마크를 옛 키(`bible-bookmarks`)에만 저장했다. 앱이 이 목록을 동기화 저장소로 옮기는 저장이 거절되면, 목록이 비어 보이고 다음 저장이 옛 목록을 지웠다(known-issues §34). 이제 옮겼는지를 동기화 저장소에 북마크 기록이 있는지로 판단하고, 옮기지 못한 동안에는 동기화 저장소를 읽는 함수(`store-v2.js loadLocal`)가 옛 키의 목록을 담아 돌려준다. 결정은 ADR-015 D7에 더했다.

## 확정 · 근거

- 사용자 결정(2026-10-27): 고치는 법은 옛 목록을 읽어 보이는 방식으로 했다. 옛 키를 비우고 옮기는 방식은 되돌리는 쓰기가 거절되면 목록의 하나뿐인 사본을 잃어 버렸고, 고치지 않고 기록만 두는 안도 버렸다. 옮기지 못한 동안 따로 알리지 않는다.
- 처음에는 옮기지 못한 동안에도 「여러 개를 골라 한 번에 지우면 저장된다」고 설명했다. 계산해 보니 지운 항목마다 삭제 기록이 남아 한 번에 많이 지워야 했다. 이 사실을 알린 뒤 사용자가 다시 알리지 않기를 골랐고, 남는 불편은 known-issues §37로 적었다. 숫자는 리뷰 뒤 1.2.1의 필드로 다시 쟀다(아래 「리뷰 반영」).
- 판단 기준을 「동기화 저장소에 북마크 기록(항목과 삭제 기록)이 하나도 없고 옛 키에 목록이 있음」으로 한 까닭: 지금 앱에서 이 상태가 생기는 것은 옮기기가 거절됐을 때뿐이다. 북마크를 모두 지우면 삭제 기록이 남고 옛 키에는 빈 목록을 쓴다. 줄어드는 쓰기는 저장 공간을 더 쓰지 않으므로, 저장 공간이 찬 까닭으로는 거절되지 않는다. 삭제 기록이 30일 뒤 지워져도 옛 키는 이미 빈 목록이다. 동기화 결과는 동기화 저장소에 저장한 뒤에만 옛 키에 쓴다.
- 같은 기준 덕분에, 고치기 전 버전이 이미 빈 목록의 문서를 만든 기기도 옛 목록이 다시 보인다. 그 뒤 북마크를 저장했거나 동기화 결과를 받은 기기는 옛 키가 이미 바뀌어 되살릴 수 없다.
- 사용자 교정(2026-10-28): 동기화 병합에서 쓴 「이긴다」를, 한쪽이 다른 쪽의 내용을 바꾸는 자리에서는 「덮어쓴다」로, 병합의 규칙을 말하는 자리에서는 「병합하면 ~이 남는다」로 고쳤다. 「병합이 고른다」는 병합을 고르는 주체로 삼는 비문이라 쓰지 않는다. 이 PR이 쓴 곳과 함께 ADR-011과 기존 유닛 테스트 이름의 같은 쓰임을 고쳤다. 병합을 고르는 주체로 쓴 기존 문장(ADR-010, ADR-011, ADR-015, `topics/bookmark.md`, `topics/sync.md`, 테스트 안내, 상태 기계 테스트 75번)도 「병합하면 ~이 남는다」로 고치고, `docs/writing.md` 「용어」와 문장 검사(`tools/prose/prose.py`)의 판단이 필요한 말에 넣었다.
- 일부러 바꾸지 않은 것: 동기화 저장소의 값을 JSON으로 읽지 못하면 전처럼 빈 문서를 돌려준다. 옛 키는 늦은 두 번째 사본일 수 있고 삭제 기록이 없어서, 이것으로 채우면 다른 기기가 지운 북마크가 동기화에서 되살아날 수 있다.

## 검증

- 유닛 `node --test tests/unit/*.test.js`: 1,421개 가운데 1,420개 통과, 실패 0개. 건너뛴 1개는 원래 꺼 둔 교회력 픽스처(미결13)다. 타입 검사(`npm run typecheck`) 통과.
- `tests/unit/store-v2.test.js`에 옛 키의 목록 옮기기 테스트 9개를 더했다. 저장 공간이 찬 저장소를 흉내 낸다. main의 코드에 돌리면 7개, 리뷰 전 첫 커밋의 코드에 돌리면 6개가 실패한다.
- e2e: 리뷰 반영 전과 뒤 모두 전체 397개 통과(작업 폴더 서버, 포트 8093, 각 11분). 새 e2e는 옛 키에만 북마크 30개를 두고 동기화 저장소에 옛 목록보다 긴 쓰기만 거절한다. 고치기 전 코드에서는 북마크 화면을 처음 열 때부터 0개가 보여 실패했다. 흉내를 위해 `conftest.py`의 저장 공간 흉내에 「몇 글자보다 긴 쓰기만 거절」하는 선택지를 더했다.
- 기기 id 쓰기와 동기화 저장소 쓰기를 모두 거절하는 브라우저(Chromium)에서 장을 열어 보았다. 고친 코드에서는 동기화 모듈(`window.driveSync`)이 있고 페이지 오류가 없다. 리뷰 전 첫 커밋의 코드에서는 「The quota has been exceeded.」 오류가 나고 동기화 모듈이 없다.
- 옮기지 못한 기기가 한 번에 지워야 하는 수(known-issues §37의 표)는 실제 `store-v2.js`를 Safari의 셈을 흉내 낸 저장소에서 실행해 쟀다. 측정 조건은 §37에 적었고, 스크립트는 한 번 쓰는 것이라 저장소에 두지 않았다.
- 실제 Safari와 iPhone에서는 확인하지 않았다.

## 리뷰 반영

PR을 열기 전 1회차. 서브에이전트 둘이 따로 보았다. 하나는 동작과 데이터 손실을, 다른 하나는 테스트와 문서를 보았다.

- **옛 목록 항목의 수정 시각**(실행해 확인): 첫 커밋은 앱을 연 동안 같은 시각을 주었지만, 앱을 열 때마다 새 시각이 됐다. 옮기지 못한 기기도 옛 목록을 드라이브에 올리므로, 다음 시작 때 새 시각을 받은 항목이 그사이 다른 기기의 수정과 삭제를 덮어썼다. 옮긴 설정처럼 0을 준다. 올릴지 정하는 조건에 항목 수 비교가 있어, 0이어도 옛 목록은 드라이브에 올라간다(`state-machine.js`).
- **옛 목록의 북마크가 아닌 항목**(실행해 확인): `null` 하나로 읽기 전체가 실패해 빈 문서가 됐고, 시작할 때마다 저장된 설정과 읽던 위치를 지웠다. 펼치기만 따로 보호하고, 읽은 것이 없으면 옮기지 않는다.
- **옮기지 못한 동안의 설정과 읽던 위치**(실행해 확인): 옛 목록을 담아 저장하다 거절되어, 옮긴 뒤 저장돼 있던 옛 값으로 돌아갔다. 이번 고침이 만든 문제다. 옛 목록 없이 저장한다.
- **기기 id 쓰기의 거절**(실행해 확인): 동기화 모듈이 `app.js`보다 먼저 기기 id를 읽어, 쓰기가 거절되면 동기화 모듈을 불러오지 못했다. 첫 커밋은 `app.js`만 막았다. 이제 그 id를 앱을 연 동안만 쓴다. 저장소 접근을 막은 브라우저에서 옮기는 함수가 오류를 내던 것(고치기 전부터)도 함께 막았다.
- **문서의 사실과 다른 문장**: 해당 버전을 1.1.0-1.2.1에서 1.2.0-1.2.1로 고쳤다(북마크는 1.2.0에 처음 들어갔다). 옮기기 문턱과 지워야 하는 수를 1.2.1의 필드와 제목 길이 둘로 다시 재 범위로 적었다. 「하나를 지워도 거절된다」를 「대개」로 고쳤다. 문턱에 아주 가까운 기기는 몇 개만 지워도 저장된다.
- **테스트**: e2e의 중간 단계가 이름대로 확인하지 않아, 장을 연 뒤 저장된 문서(북마크 기록 없음, 읽던 위치 있음)를 확인하게 했다. 「시작할 때 다시 저장하지 않는다」는 같은 문자열 비교로는 확인되지 않아 쓰기 횟수를 센다. 테스트 이름과 주석의 「판」을 「버전」으로 고쳤다.
- 고치지 않은 것: 삭제 기록만 남은 기기에서 늦은 옛 사본이 30일 뒤 되살아날 수 있다는 지적이다. 지금 버전에서 그런 상태가 생기는 경로를 리뷰어도 찾지 못했다.
- 테스트 안내(`tests/README.md`)의 파일별 테스트 수와 설명을 이 PR이 더한 테스트에 맞췄다. 앞선 커밋에서 빠뜨렸다.

2회차(Copilot).

- **이 기기에 없던 수정 시각 0의 항목**: 다른 기기의 변경을 판단하는 조건(`state-machine.js`)이 이 기기에 없던 항목의 시각을 0과 견주었다. 그래서 옛 목록을 처음 받는 기기에서는 변경으로 보지 않아, 병합 결과의 저장이 거절돼도 알리지 않았다. 저장에 성공해도 「불러왔습니다」를 알리지 않았다. 수정 시각을 0으로 바꾼 1회차가 만든 문제다. 이 기기에 없던 항목은 시각과 상관없이 변경으로 본다. 새 유닛 테스트(75a)는 고치기 전 조건에서 실패한다. 동기화와 저장 실패 e2e 45개가 통과했다.

3회차(Copilot).

- **올리기 조건**: 병합 결과를 드라이브에 올리는 조건은 기록 수가 늘었는지와 가장 큰 수정 시각이 커졌는지만 보았다. 드라이브에 되살린 항목과 그 옛 삭제 기록이 함께 있으면 병합에서 삭제 기록이 빠져 기록 수가 준다. 같은 병합에 옛 목록의 항목(수정 시각 0)이 들어오면 두 값이 모두 그대로라 그 항목을 올리지 않았다. 드라이브에 없거나 드라이브보다 새로운 기록이 병합 결과에 있으면 올리게 했다. 같은 조건으로, 드라이브의 값보다 새롭지만 드라이브의 가장 새 기록보다 오래된 설정이 올라가지 않던 것(main부터, main의 코드로 재현)도 고쳤다. 새 유닛 테스트(75b)는 고치기 전 조건에서 실패한다.
- 사용자가 개수와 시각만 보는 판단을 다시 설계해야 하지 않는지 물었다(2026-10-29). 병합 자체는 id마다 하지만, 병합 앞뒤에서 바뀐 것이 있는지를 빨리 판단하는 세 곳이 요약값을 썼다. 다른 기기의 변경(2회차)과 병합 뒤의 올리기(3회차)는 id마다 보게 고쳤다. 드라이브가 그대로일 때 이 기기의 변경을 가장 큰 시각으로만 판단하는 곳이 남아, 시계가 늦은 기기의 새 북마크가 올라가지 않는 것을 유닛 테스트 도구로 확인했다(main부터). 사용자 결정: 이 PR에서는 고치지 않고 다음 PR에서 다시 설계한다(known-issues §38). 수정 시각에 기대는 병합의 한계는 §39로 남겼다.
