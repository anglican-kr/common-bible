# fix: 공유 링크의 절 범위가 앱을 멈추지 않게 한다

## 요약

known-issues §15의 첫 항목이다(사용자 지시 2026-10-21 「known-issues §15 첫 항목 해결 작업 시작」). #359 리뷰에서 찾았고, 다음 PR로 먼저 고치기를 권했던 것이다.

라우터(`routing.js parsePath`)는 주소의 여러 구간(`/john/3/1-5,10-15`)을 절 하나하나로 펼쳐 정렬했다. 그래서 두 가지가 깨졌다.

- **큰 범위가 든 여러 구간** — `/john/3/1-4294967296,5`는 「Invalid array length」 예외로 `route()`가 끝나지 못했다. 처음 여는 링크면 시작 화면에서 멈췄고, 앱 안에서 가면 앞 화면에 머물렀다. `1-100000000,5`는 30초 넘게 멈춘 뒤 「Set maximum size exceeded」로 끝났다.
- **같은 구간을 되풀이한 주소** — 장은 열렸다. 그러나 오디오 북 설정(기본으로 켜짐)이 켜져 있으면 탭 바가 스크롤 프레임마다 주소를 다시 읽어(`tabbar.js collapseEnabled`) 그만큼 펼쳤다. `1-999`를 5,000번 되풀이한 주소는 한 번 해석하는 데 0.4초가 걸렸다(Chromium).

가져온 북마크는 #359의 절 범위 검사(ADR-040)가 막았지만, 공유 링크와 손으로 친 주소에는 검사가 없었다.

고친 것:

- 그 검사(`_isWellFormedSpec`)를 `bookmark-modals.js`에서 `verse-spec.js`의 `isWellFormedSpec`으로 옮겼다. 가져오기와 주소 해석이 함께 쓴다.
- `parsePath`의 여러 구간 갈래는 이 검사를 통과한 표기만 강조하고, 나머지는 강조 없이 장만 연다. 통과한 표기는 오름차순이고 겹치지 않으며 숫자가 999 이하라, 펼치는 양이 999절을 넘지 않는다.
- 구간 하나(`16` · `16-20`)는 펼치지 않으므로 예전대로 받는다. 거꾸로 된 범위는 바로 세우고, 장을 넘는 끝은 그 장의 마지막 절로 자른다(`views.js renderChapter`).
- 검사가 쉼표로 나누는 수에 상한을 두었다(`split(",", 1001)`). 그래서 주소가 아무리 길어도, 스크롤 프레임마다 도는 검사가 한정된 일만 한다.

## 확정·근거

- **known-issues가 든 예는 틀렸다.** 그 항목은 `/john/3/1-4294967296`을 예로 들었다. 그러나 구간이 하나인 주소는 펼치지 않는 갈래로 가서 멀쩡했다(1-36절로 잘려 열린다 — 2026-10-21 브라우저 확인). 멈추는 것은 쉼표로 구간이 둘 이상인 주소다. known-issues §15 머리 노트에 바로잡아 적었다.
- **동작이 바뀌는 경우 — 앱이 쓰지 않는 순서 · 겹침의 여러 구간.** `/john/3/20,16-18`처럼 순서가 뒤섞인 주소와 `1-5,3-7`처럼 겹친 주소는 그전에는 정렬해 강조했다. 이제는 강조 없이 장만 연다.
  - known-issues §15가 적어 둔 고치는 법(「`parsePath`가 가져오기 검사와 같은 표기만 강조하고 나머지는 장만 연다」 — #359 리뷰 반영 계획, 사용자 승인 2026-10-19)대로다.
  - 앱이 만드는 여러 구간 주소(북마크 · 공유 링크 · 장을 넘는 끝을 자른 주소)는 모두 이 표기라 영향이 없다. 가져오기 검사가 지금 앱의 절 범위 34,003개와 #205 전 앱의 60,384개로 확인한 기준이다(ADR-040 「검증」).
  - 정렬해 받기를 남기는 안은 ADR-040 「검토한 대안」에 이유와 재검토 조건과 함께 적었다 — 숫자와 구간 수에 상한만 두어도 겹친 구간은 한 번에 백만 절 가까이 펼친다.
- **옛 판 표기(`16aa` · `16-17a`)는 예전과 같다.** 검사는 받고(사용자 결정 2026-10-19), `parseVerseSpec`이 그 구간을 읽지 않아 강조되지 않는다.
- **동기화로 들어온 절 범위는 여전히 검사하지 않는다.** 그런 북마크를 열면 이제 장만 열린다. 그러나 그 북마크에 절을 합치면 `mergeVerseSpecs`가 멈춘다(Node 실측 — `1-2000000`은 2.8초, `1-20000000`은 4.7초 뒤 예외). 검사가 없는 판(1.6.4 이하)에서 가져와 동기화된 경우에만 생긴다. 그래서 이 PR에서 고치지 않고 known-issues §15에 새 항목으로 적었다.
- **ADR-010은 손대지 않았다.** 결정(절 범위를 주소 경로에 적는다)은 그대로다. 그리고 옛 개정 블록이 스무 개라(`**개정` 표지 — 인용 블록 18 · 목록 항목 2), 손대면 그것을 본문에 녹여야 한다(CLAUDE.md 「ADR 워크플로우」). 주소의 검사는 같은 검사를 정한 ADR-040에 적었다.
- **덤 — 조사 하나.** coding-pitfalls §35의 「저장 구조(…)을」을 「를」로 고쳤다. #360의 「꼴」 바꾸기에서 조사가 어긋난 곳이다. 그 PR이 바꾼 줄 전체를 같은 방식으로 훑었고, 어긋난 곳은 이것 하나였다(데이터 저장소 data#34에는 없었다).

## 검증

- **유닛** 1320(1319 통과 · 1 skip — 미결13 대기 픽스처), `npm run typecheck` 0, 문서 테스트 16.
  - `routing.test.js` 새 5건 — 큰 범위가 든 여러 구간 넷, 구간 1,001개 · 되풀이한 구간 셋, 순서 · 겹침 · 앞자리 0인 여섯, 옛 판 표기, 구간 하나의 큰 끝. 기존 「다중 세그먼트 정규화」는 앱이 쓰는 표기(`1-3,4,10-12` → `1-4,10-12`)로 바꿨다.
  - `bookmark.test.js` — 절 범위 검사 테스트 셋이 `VERSE_SPEC` 블록에서 함수를 받는다(가져오기 검사의 로더도 그 블록을 먼저 싣는다).
  - 고치기 전 코드(main의 `js/`)에서는 새 유닛 셋이 실패한다. 예전 동작을 지키는 둘(옛 판 표기 · 구간 하나)은 양쪽에서 통과한다.
- **e2e** `test_navigation.py` 22(+6) — 앱이 쓰는 여러 구간은 강조하고, 뒤섞인 순서는 장만 연다. 처음 여는 링크 셋(큰 범위 · 1억 절 · 같은 구간 1,600번 — 7,999자로, nginx가 기본으로 받는 요청 줄 8KB 안이다. nginx 문서의 `large_client_header_buffers 4 8k` — 넘으면 414 — 이고, 서버 저장소에는 따로 정한 값이 없다)과 앱 안의 이동(창세기 1장에서 `navigate`)에서, 요한 3장 36절이 그려지고 시작 화면이 걷히고 페이지 오류가 없다. main 판을 따로 띄워(포트 8091) 같은 테스트를 돌리면 새 경우 다섯이 실패한다.
- **e2e 전체** — 357 통과(9분 25초, `python3 scripts/serve.py 8080` 위).
- **브라우저 재현**(Chromium · Playwright, 고치기 전 → 뒤)
  - `1-4294967296,5` — 시작 화면에서 멈춤 → 장이 열리고 강조 없음.
  - `1-100000000,5` — 30초 넘게 멈춤 → 2.9초에 장이 열림.
  - 주소를 한 번 해석하는 시간 — `1-999` × 5,000은 397ms → 0.1ms, `1-36` × 20,000은 59ms → 0.2ms. 앱이 쓰는 표기 가운데 가장 큰 경우(1-999를 하나씩 999개)는 2.5ms다.
