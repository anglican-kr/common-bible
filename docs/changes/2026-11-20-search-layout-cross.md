## 요약

#612(휴대폰 검색 입력창을 검색 화면 위로)를 다시 검토해 찾은 것을 고친다. 창 폭이 휴대폰과 데스크톱 배치를 넘나들 때 검색 화면을 다시 그리지 않고 위쪽 입력창만 넣거나 빼서, 찾지 않은 채 친 글자와 결과, 스크롤 위치를 지킨다. 그 처리를 탭 바(`tabbar.js`)에서 검색(`search.js`)으로 옮기고, 휴대폰 배치의 조건을 한 곳에서만 정한다. 검색 화면에서 검색 원형을 누를 때의 맨 위로 가기도 바로 가게 한다.

## 확정 · 근거

- 사용자 지시(2026-11-20): 리뷰의 2-4번을 고친다. 1번과 띄어 쓴 조사(6, 7번)는 리뷰가 고쳤다. 5번(⊗를 누를 때 포커스가 잠깐 페이지 맨 앞으로 떨어지는 일)은 #616의 홈 탭 대비책이 막는다.
- 창 폭이 바뀔 때(2, 4번)
  - 전에는 탭 바가 검색 화면을 통째로 다시 그렸다(`route()`). 친 글자가 사라지고, 결과를 다시 찾고, 스크롤이 맨 위로 갔다.
  - 이제 `search.js`의 `onLayoutTierChange`가 검색 화면 맨 위에 위쪽 입력창을 넣거나 뺀다. 친 글자는 새 배치의 입력창으로 옮기고, 포커스가 옛 입력창에 있었으면 새 입력창으로 옮긴다.
  - 검색어도 고른 책도 없는 /search는 휴대폰에서 최근 검색 화면, 데스크톱에서 성서 목록이라 화면이 다르다. 이때만 다시 그리고 친 글자와 포커스를 옮긴다.
  - Chrome은 CSS가 숨긴 입력창의 포커스를 변경 알림보다 먼저 뺀다. 그래서 숨겨져 포커스를 잃은 검색 입력창을 `focusout` 때 적어 두고, 변경 알림에서 그것을 본다(Playwright Chromium에서 차례를 확인).
- 휴대폰 배치의 조건(3번)
  - `isMobile`과 북마크 몸짓(`bookmark-gestures.js`)이 같은 쿼리를 각자 적고 있었다. `helpers.js`에 `MOBILE_LAYOUT_QUERY`와 `isMobileLayout`을 두고 둘 다 그것을 쓴다.
  - 리뷰는 `isMobile`을 데스크톱 조건의 반대로 바꾸자고 했다. 그러나 CSS는 휴대폰 조건(`(max-width: 768px), (pointer: coarse)`)으로 상단 바의 검색창을 숨긴다. 반대로 바꾸면 두 조건 사이의 틈(포인터가 없는 넓은 화면, 확대로 폭이 768px과 769px 사이인 창)에서 입력창이 둘 보인다. 그래서 CSS와 같은 휴대폰 조건을 쓰고, 창 폭 처리도 그 조건의 변경을 듣는다. 전에는 데스크톱 조건의 변경을 들어, 틈에서 휴대폰으로 넘어가면 알림이 오지 않았다.
  - 그 틈에서는 탭 바와 상단 바의 검색창이 함께 보인다. CSS와 ADR-029를 고쳐야 하는 일이라 `docs/topics/routing.md` 「남은 일」에 적었다.
- 검색 원형의 맨 위로 가기(1번): `html`이 부드러운 스크롤이라, 결과를 내려 보다 검색 원형을 누르면 올라가는 중에 키보드가 떴다. 다른 화면처럼 바로 간다(`behavior: "instant"`).

## 검증

- `npm run typecheck` 통과, `node --test tests/unit/*.test.js` 1,960개 통과. `isMobile`의 유닛 시험은 함께 쓰는 조건(`isMobileLayout`)을 읽는지 보도록 고쳤다.
- e2e에 시험 하나를 더했다(`test_tabbar.py`의 `test_crossing_the_mobile_layout_keeps_the_search_view`).
  - 검색 결과 화면에서 데스크톱과 휴대폰을 오가도 검색 화면이 그대로이고(다시 그리면 사라지는 표시가 남는다), 친 글자와 포커스가 새 입력창으로 옮겨 간다. 주소도 그대로다.
  - 검색어 없는 /search에서도 친 글자와 포커스가 옮겨 간다.
  - 이 시험은 고치기 전의 `search.js`와 `tabbar.js`에서 실패한다.
- e2e `test_tabbar.py`, `test_search.py`, `test_top_bar.py`, `test_a11y_keyboard.py`, `test_bookmark.py` 204개를 작업 폴더 서버(8096)에서 돌려 203개가 통과했다.
  - 실패한 `test_unknown_book_leaves_no_recent_before_the_alias_map_loads`(#615에서 더한 시험)는 기다리던 「찾지 못했어요」 대신 「성서 자료를 불러오지 못했습니다」를 읽었다. 따로 여섯 번씩 돌리니 이 브랜치와 main의 코드에서 똑같이 한 번씩 실패해, 이 PR과 상관없이 가끔 실패하는 시험으로 보았다.

2회차(#618 코드 리뷰 다섯 건)
- 고침(사용자 지시 2026-11-21: 반드시 고친다): 창 폭이 바뀐 뒤 다음 쪽으로 가면 결과가 빠지거나 두 번 나왔다. 한 쪽의 결과 수를 쪽마다 그때의 창 높이로 다시 어림하는데, 쪽은 (쪽 번호 - 1) × 결과 수에서 시작하기 때문이다. 이 PR 전에는 배치가 바뀌면 화면을 다시 그려 휴대폰과 데스크톱을 넘나들 때는 맞았으나, 같은 배치에서 높이만 바꿔도 같은 일이 있었다. 같은 검색(낱말과 고른 책)의 쪽을 넘기는 동안에는 처음 어림한 수를 쓰고, 새 검색에서 다시 어림한다(`searchPageSize`). 유닛 시험 둘과 e2e 시험 하나(`test_paging_after_a_resize_keeps_the_page_size`)를 더했다. 쪽마다 다시 어림하도록 되돌리면 e2e 시험이 실패한다(2쪽 9건, 1쪽 8건).
- 고침: 이 PR이 주제 문서에 넣은 세 줄의 꼬리표에 「#612 리뷰」가 붙어 있었다. 1회차에서 「(#616 리뷰 2회차)」를 날짜로 바꾼 규칙과 같이 날짜만 남겼다. #616이 「남은 일」에 넣은 「#616 리뷰」도 함께 뺐다.
- 고침(사용자 지시 2026-11-21: 남은 셋도 고친다): 책 선택 시트를 연 채 배치가 바뀐 뒤 「적용」을 누르면, 시트를 연 검색창이 빠졌거나(위쪽 입력창) 숨어(상단 바 검색창) 친 글자를 읽지 못하고 포커스가 페이지 맨 앞이나 닫히는 시트에 남았다. 이 PR 전부터 있던 일이다. 이제 지금 배치가 보이는 검색창(`shownSearchField`)에서 글자를 읽고, 시트를 닫은 뒤 그 검색창의 깔때기에 포커스를 준다. e2e 시험 하나(두 방향, `test_book_filter_apply_after_the_layout_changed_uses_the_shown_field`)를 더했다. 고치기 전에는 두 방향 모두 실패한다.
- 고침: 공백만 친 채 휴대폰 배치로 바꾸면 새 위쪽 입력창에 ⊗가 보였다. 다른 곳처럼 앞뒤 공백을 뺀 값으로 본다. e2e 시험 하나(`test_crossing_to_mobile_with_only_spaces_hides_the_clear_button`)를 더했다.
- 고침: e2e 시험 이름의 「desktop tier」를 「mobile layout」으로 바꿨다. 창 폭 처리가 듣는 조건은 휴대폰 조건이다.
- 고친 뒤 타입 검사, 유닛 1,966개가 통과했다. e2e `test_tabbar.py`, `test_search.py`, `test_a11y_keyboard.py`, `test_top_bar.py` 193개 가운데 192개가 통과했다. 실패한 하나는 위 「검증」에 적은 가끔 실패하는 시험이고, 따로 세 번 돌려 모두 통과했다.

3회차(#618 코드 리뷰 두 건)
- 할 일로 남김(사용자 결정 2026-11-21): 검색어도 고른 책도 없는 /search에서 책 선택 시트를 연 채 배치가 바뀌면, 다시 그리기가 시트를 닫아 고르던 책이 사라지고 포커스가 페이지 맨 앞에 남는다. 이 PR 전부터 있던 일이다. `docs/topics/routing.md` 「남은 일」에 적었다. 리뷰는 `?in=mat`(책만 고름)에서도 생긴다고 했으나, 고른 책이 있으면 다시 그리지 않으므로 검색어도 고른 책도 없는 경우만 적었다.
- 정하지 않고 남김: 한 쪽 결과 수를 낱말과 고른 책으로만 기억해, 창을 키운 뒤 같은 낱말을 다시 찾아도 처음 어림한 수를 쓴다. 다른 검색 뒤 「뒤로」로 앞 검색의 2쪽에 돌아오면 다시 어림한다.
