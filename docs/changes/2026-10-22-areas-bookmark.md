## 요약

docs 재구성 시리즈의 셋째 PR이다. 정리 층 문서는 지금 장르와 시간순으로 짜여 있다. 그래서 북마크 작업 하나에도 status, known-issues, coding-pitfalls, ADR 여럿을 열어야 했다. 이 PR은 작업 영역마다 한 장을 두는 영역 문서(`docs/areas/`)를 시작하고, 북마크 영역을 시범으로 옮긴다. 다른 영역은 결과를 보고 다음 PR에서 한꺼번에 옮긴다.

- **영역 문서의 규칙**(`docs/areas/README.md`). 틀은 「지금 동작 → 결정 → 확정 사실 → 함정 → 남은 일」이다. 「소유 코드:」 줄로 그 영역이 소유하는 `js/` 파일을 적는다. 「pitfalls §N」과 「known-issues §N.m」은 영구 번호로 쓴다. 옮긴 항목은 옛 파일에 대장 줄을 남긴다.
- **북마크 영역 문서**(`docs/areas/bookmark.md`). 세 곳의 내용을 글자 그대로 옮긴 뒤(첫 커밋) 문장을 §37에 맞게 고쳐 썼다(넷째 커밋).
  - status.md 다섯 줄 → 「지금 동작」: 옛 판 저장값, 절 선택 둘, 가져오기, 모아 읽기.
  - coding-pitfalls §6, §38 → 「함정」. 옛 자리에는 절 제목과 대장 줄이 남는다.
  - known-issues §15.1 · 15.3 · 15.4 · 15.6 · 15.7 · 15.8, §16.1 · 16.2, §17.1, §19.1 → 「남은 일」. 옛 자리에는 대장 줄이 남고, 동기화 항목 §15.2 · 15.5는 번호를 달고 known-issues에 남는다(다음 PR에서 동기화 영역으로 간다).
- **검사.** `docs-wiki.test.js`에 셋을 더했다. 대장 줄과 영역 문서의 정의가 하나씩 맞는지, 영역 문서가 틀을 지키는지, 두 영역이 같은 `js/` 파일을 소유하지 않는지다. `docs-crossref.test.js`는 영역 문서도 참조 문서로 검사한다. status.md에서 옮긴 줄이 같은 검사를 계속 받게 하려는 것이다.
- **index.md**의 북마크 행은 영역 문서 하나를 가리킨다.
- **사실 토큰 비교 도구의 경계 수정.** `--kinds general`이 「ADR-035에」처럼 조사가 붙은 번호를 세지 못했다. 문장을 고쳐 쓰다 드러났다.

## 확정 · 근거

- 계획(사용자 승인 2026-10-22)의 PR 3이다. 계획대로 이 PR 뒤에 시리즈를 계속할지 사용자에게 묻는다.
- 대장은 새 문법을 만들지 않았다. 옛 파일의 절 제목을 그대로 두고 본문 자리에 대장 줄을 둔다. pitfalls §26(절을 비울 때 노트를 남긴다)과 같은 방식이라, 코드 주석 34곳과 머지된 원장의 옛 참조가 그대로 풀린다.
- pitfalls §35(외부 입력 검사)는 북마크 가져오기와 주소 처리에 걸쳐 있어 공통 함정에 남겼다. §21은 교회력 설계서가 사용자 결정의 출처로 가리키므로 교회력 영역으로 보낼 것이라 옮기지 않았다. 북마크 문서에서는 둘 다 한 줄로 가리킨다.
- status.md의 「주소의 절 범위」 줄은 라우팅 영역, 「북마크 + Google Drive 동기화」 줄은 동기화 영역이라 옮기지 않았다.
- 「소유 코드:」는 `js/app/bookmark*.js`와 `js/app/verse-spec.js`다. `storage.js`는 북마크 말고도 읽던 위치, 오디오, 화면 설정을 저장하므로 다음 PR에서 정한다.

## 검증

- **글자 그대로 옮겼는지**(첫 커밋): `docs_facts_snapshot.py --diff main HEAD`에 옛 세 파일과 영역 문서를 `--kinds general --strict-counts --from … --into …`로 넣었다. 옛 줄 725줄 가운데 724줄이 그대로 옮겨졌고, 빠진 줄은 0이다. 사라지거나 줄어든 토큰도 0이다.
- **의도적 변경**(줄 비교의 `--drop-file`): pitfalls §38 규칙 줄의 「(§35)」를 「(pitfalls §35)」로 한정했다. 영역 문서로 옮기자 어느 문서의 절인지 알 수 없게 됐기 때문이다. 교차 참조 검사가 설계서 §35로 풀려다 실패해 드러났다.
- **문장만 고쳤는지**(넷째 커밋): 앞 커밋과 `--kinds general --strict-counts`로 비교해 사라진 토큰과 줄어든 토큰이 0이다.
- **새 검사가 잡는지**: 정의 하나를 지우면 「대장은 가리키지만 정의가 없다」가, 같은 파일을 소유하는 임시 영역 문서를 두면 「함께 소유한다」가, 아무것도 고르지 않는 glob은 「고르는 파일이 없다」가 났다. 없는 항목 번호(known-issues §15.9)와 깨진 링크도 잡혔다. 시험 뒤 원래대로 되돌렸다.
- `npm test` 1365개(통과 1364, 실데이터 1 skip), `npm run typecheck` 통과. 기본(교회력) 사실 토큰 비교는 변화 0이다.
- **실사용 확인.** 같은 버그(known-issues §19.1, 합치기가 사용자가 고친 제목을 다시 짓는 문제)의 수정 준비를 새 서브에이전트 둘에게 맡겼다. 하나는 main 문서(임시 작업 트리), 하나는 이 브랜치에서 시작했다. 지시문은 경로만 달랐고, 둘 다 `docs/index.md`에서 시작했다.

  | | main(옛 구조) | 이 브랜치(영역 문서) |
  |---|---|---|
  | 읽은 횟수 | 14번(grep 포함, 일부만 읽은 것 6) | 10번(문서 8, 코드 2) |
  | 토큰 · 도구 호출 · 시간 | 99,660 · 17 · 94초 | 87,056 · 16 · 94초 |
  | 찾은 규칙 | 같음 | 같음 |

  개선은 있지만 크지 않다. 이 버그는 어느 쪽이든 ADR-010과 코드를 열어야 해서다. 차이는 이슈와 관련 규칙(pitfalls §38의 이름 규칙)을 한 문서에서 찾았다는 점이다. main 쪽은 known-issues, pitfalls, ADR을 grep으로 오갔다.
- **실사용 확인에서 찾은 문서의 빈틈**(다섯째 커밋에서 고침). 두 에이전트가 함께 짚은 것을 확인한 뒤 고쳤다.
  - known-issues §16.2의 예 「이사야 40:6-7」은 틀렸다. 북마크 제목은 짧은 책 이름을 쓴다(`bookmark-modals.js`의 `short_name_ko`). 「이사 40:6-7」로 고쳤다. 사실 토큰 비교에서 사라진 토큰은 이 하나다.
  - §19.1에 고칠 때 필요한 사실 넷을 더했다. 기본 이름의 장 전체 형식(「이사 7장」, `chUnit`), 기본 이름을 만드는 식이 세 곳에 따로 있다는 점, 고치면 함께 바꿀 ADR-010의 두 문장, 사용자가 고친 제목에 합치는 경우의 테스트가 없다는 점이다. 에이전트 하나는 「합친 제목을 확인하는 테스트가 없다」고 했지만 틀렸다. `test_merge_into_pre205_bookmark_keeps_its_verses`가 기본 이름의 경우를 확인한다.
  - index.md의 「어떤 작업이든」 행이 여전히 status, known-issues, pitfalls를 먼저 읽으라고 해서 북마크 행과 어긋났다. 영역 문서가 있으면 그것부터 읽으라고 고쳤다.
