## 요약

검색 속도를 높일 방법을 논의하며 실제 데이터로 재 보았다. 본문을 훑는 일은 이미 빠르고, 기다림은 앱을 연 뒤의 첫 검색과 전례일이 처음 나오는 검색에서 생긴다. 사용자는 오프라인 저장을 써서 느림을 느끼지 못했고 불편이 없다고 해, 지금은 코드를 고치지 않는다. 손볼 조건과 방법을 검색 주제 문서의 「남은 일」에 적었다. 앱 코드는 바꾸지 않는다.

## 확정 · 근거

- 검색 속도는 느리다는 보고가 나올 때 손본다(사용자 결정 2026-11-21).
- 브라우저에서 CPU를 4배 늦춰 잰 값이다(중급 휴대폰의 흔한 어림). 첫 방문(캐시 없음)과 두 번째 방문(서비스 워커 캐시)을 함께 적었다.

  | 경우 | 시간 |
  | --- | --- |
  | 앱을 연 뒤의 첫 검색(「사랑」) | 248-354ms |
  | 그다음 검색(「하느님」, 「빌라도」, 「가」, 「요한 3:16」, 「성 니콜라」, 「사순」) | 23-105ms |
  | 전례일이 처음 나오는 검색(「대림」) | 560-746ms. 같은 검색을 다시 하면 49-50ms |
  | 연도를 붙인 검색(「2027 부활」) | 124-137ms |

- 검색 워커가 3만 8천 절을 훑는 시간은 감속 없이 1-4ms였다(Node). ADR-005가 역색인을 다시 보자고 한 10만 절에도 멀어, 역색인, n-gram, 검색 라이브러리(ADR-005 A안, B안)는 권하지 않았다.
- 첫 검색이 느린 까닭: 검색 워커는 첫 Enter에서 만들어진다(`doSearch` 안의 `ensureSearchWorker`). 그때 색인 네 개(6.2MB)를 받아 풀고, 첫 검색에서 3만 8천 절의 비교용 글(`nArr`)을 만든다. 감속 없이 색인 풀기는 약 15ms, 비교용 글 만들기는 약 80ms였다(Node).
- 전례일 첫 검색이 느린 까닭: 화면 스레드에서 교회력 엔진을 불러와 자료를 푸는 데 89-146ms, 3년치 지키는 날의 표를 세는 데 95-108ms가 들었다(CPU 4배 감속). 그 뒤 줄마다 날짜를 계산하고 그린다. 3년 표 밖에서만 읽는 독서 세트는 939개 가운데 20개였고, 표를 2033년까지 넓히는 데 감속 없이 약 60ms가 들었다(Node).
- 권하지 않은 나머지: 쪽을 넘길 때 결과를 기억해 다시 훑지 않는 일은 아끼는 시간이 몇 ms다. 압축 방식을 바꾸는 일은 기기마다 처음 한 번만 효과가 있다. 엔진 계산을 워커로 옮기는 일은 구조 변경이라, 미리 계산하고도 입력이 끊길 때 검토한다.

## 검증

- 브라우저 측정: 데이터 서브모듈 포인터(`ba3bc7c`)의 산출물을 임시 폴더에 풀고 `scripts/serve.py`의 복사본으로 띄웠다. Chromium(Playwright)에서 CPU를 4배 늦추고(`Emulation.setCPUThrottlingRate`), 데스크톱 검색창에 검색어를 쳐 Enter를 누른 때부터 결과가 다 그려질 때까지 쟀다. 로컬 서버라 내려받는 시간은 빠졌다.
- 워커 안의 시간은 Node에서 `js/search-worker.js`를 통째로 돌려(파일을 읽는 가짜 `fetch`) 쟀다. 교회력 엔진은 `js/app/liturgical-engine.js`를 Node와 브라우저에서 불러 쟀다. 측정 스크립트는 저장소에 넣지 않았다.
- `node --test tests/unit/docs-*.test.js`로 문서 검사를 돌렸다. 문서만 바꾼 PR이라 e2e는 돌리지 않았다.
