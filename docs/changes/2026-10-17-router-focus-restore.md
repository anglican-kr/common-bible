# fix: 다시 그린 뒤 포커스를 라우터가 돌려준다 — 구분 탭 · 검색 쪽 링크까지 · 「본문 바로가기」는 라우트가 아니다 · 검색 쪽 안내 (known-issues §10 · §5)

## 요약

#350 리뷰가 넘긴 `known-issues.md` §10 의 남은 코드 둘(라우터 수준 포커스 복원 · 화면마다 잇던 네 걸음)과, 같은 뿌리인 §5 의 「본문 바로가기」를 고쳤다. 같은 날 앞선 PR #351(계산 범위 · 날짜 이동 줄 · 인용 시트 꺾쇠)의 뒤를 잇는 두 번째 PR 이다(사용자 결정 — 아래 「확정·근거」). 정본은 ADR-031 §5(신설).

### ① 다시 그린 뒤 포커스 — 라우터가 돌려준다

- **라우터 한 곳** — 전역 `<a>` 인터셉터가 이동 직전에 누른 링크의 자리를 재고(`helpers.js focusSpotOf` — 키 · 대체 키 · 화면 위치 · `#app` 안 위치 · 누른 방식), `route()` 가 시작하자마자 꺼내 비우며(`_pendingFocusSpot`), 새 화면이 커밋된 뒤 `finally` 에서 그 route 가 여전히 최신이면 `onRouteEnd` 다음에 돌려준다(`restoreFocusSpot`). 자리는 그것을 남긴 누름의 route 에만 쓰인다 — 뒤로 가기 · 탭 전환 · 리다이렉트는 자리 없이 시작하므로, #350 리뷰가 막은 「다시 그리지 못한 누름의 자리가 다음 렌더로 새는」 일이 구조로 사라졌다(`eventPhase` 판정이 필요 없다).
- **뷰는 표지만** — `data-focus-key`, 그리고 새 화면에 같은 컨트롤이 없을 수 있으면 넘겨받을 컨트롤의 `data-focus-fallback`. 캘린더 · 전례독서는 화면마다 잇던 네 걸음(`createFocusMemory` 만들기 · 커밋마다 루트에 `remember` · 렌더 시작에 `take` · 커밋 뒤 `restore`)을 걷어냈고, 범위 끝의 앞뒤 단추가 대체 「오늘」을 단다(`buildDateStep`).
- **새로 덮는 곳(main 부터 포커스가 body 로 빠졌다)** — 성서 목록의 구분 탭(`views.js buildDivisionTabs` — `div:<division>`; 탭 줄은 `#app` 밖 · sticky 라 위치는 그대로 두고 포커스만), 검색의 「← 이전 · 다음 →」(`search.js buildSearchPagination` — `page:prev|next`, 첫 · 마지막 쪽에서는 서로 대체). 뷰 루트 밖에 있거나 `await` 뒤에 그려져 화면마다 다는 방식으로는 덮지 못하던 곳이다.
- **함께 고친 순서** — 검색 결과 화면은 다 그린 뒤 `window.scrollTo(0, 0)`(루트의 smooth)을 불렀다. 위치 복원이 「이미 제자리」로 보고 지나가면 그 애니메이션이 이어져 누른 링크를 밀 수 있는 순서라 즉시 스크롤(`behavior: "instant"`)로 바꿨다.
- 위치 · 「포커스를 잃었을 때만」 · 마우스 · 탭은 링 없이 — #350 리뷰가 정한 동작은 그대로 옮겼다.

### ② 「본문 바로가기」는 라우트가 아니다

- 전역 `<a>` 인터셉터가 페이지 안 링크(같은 경로 · 쿼리의 `#id`)를 먼저 갈라(`inPageTargetId` — `IN_PAGE_LINK` 블록) `route()` 를 부르지 않고 대상으로 포커스만 옮긴다(`focusInPageTarget` — 대화형이 아닌 `<main id="app">` 이라 처음 쓸 때 `tabindex="-1"`). 그전엔 `route()` 로 같은 화면을 다시 그리기만 하고 포커스는 본문으로 가지 않았다(§5). 브라우저에 맡기지 않는 것은 주소에 「#app」이 붙어 기록 항목이 하나 더 생기기 때문이다. 본문은 컨트롤이 아니라 테두리를 그리지 않는다(`#app:focus { outline: none }` — 다음 Tab 이 본문 안에서 이어진다).

### ③ 검색 — 쪽을 말로 알리고, 결과 건수 줄은 제목 (제안 — 따로 뺄 수 있는 커밋)

- 쪽을 넘겨도 포커스는 누른 「다음 →」에 남으므로, 라이브 영역이 한 번 「"검색어" 검색 결과 N건, 전체 M쪽 중 K쪽」을 알린다(「2/5」는 분수로 읽힐 수 있어 말로). 결과 건수 줄은 `<h2 class="search-count">` 가 되어(모양은 그대로 — `font-weight: normal`) 포커스를 「다음 →」에 둔 채 제목 이동(VoiceOver 로터 · TalkBack)으로 새 결과 첫머리에 간다.

## 확정·근거

- **작업 지시(2026-10-17, 사용자)** — 「머지 후 남은 이슈 처리하자」에 세 가지를 물어 모두 권장안: 범위(§10 코드 다섯 + §5 둘 — 이 PR 이 그 가운데 라우터 수준 · 네 걸음 · 「본문 바로가기」), 검색 「다음 →」 뒤 포커스 = **누른 링크 그대로**(결과 목록 맨 위로 보내는 안 대신 — 마지막 쪽이면 「← 이전」), PR 둘로(앞 PR #351 머지 뒤 이 PR). 이어 「머지 후 다음 작업 시작」.
- **플랫폼 지침 대조(2026-10-17, 사용자 질문 「검색 포커스 규칙이 iOS HIG · Android UI 규칙과 부합하나」)** — 1차 출처로 확인: Apple App Store VoiceOver 평가 기준 「새로 고칠 때 읽던 위치가 예기치 않게 처음으로 돌아가면 안 된다」 · 「화면이 바뀌면 커서는 새 내용 영역으로」, UIKit `layoutChanged`(VoiceOver 가 옮겨 갈 요소를 함께 넘긴다), Material(1판) 「포커스를 가진 요소가 사라지면 어디로 갈지 정하라」 · 「중단 뒤 이어지면 전에 포커스가 있던 요소에」, Android 16 의 `announceForAccessibility` 지원 중단(live region 은 아껴서). 결론: 누른 컨트롤 그대로가 두 플랫폼의 기본 쪽이고, 둘이 함께 권하는 「바뀐 상태를 짧게 알리기」가 검색에 빠져 있었다 → ③ 을 제안했다. 사용자의 다음 말이 「머지 후 다음 작업 시작」이라 명시 승인은 아니어서 ③ 은 따로 뺄 수 있는 커밋으로 두었다.
- **판단 — 자리는 모듈 변수 하나, `route()` 가 시작에서 꺼낸다.** 인터셉터가 같은 호출 안에서 `navigate`/`route` 를 부르고 `route()` 의 첫 줄이 await 앞이라, 그 누름의 route 만 자리를 받는다. 인터셉터는 호출 뒤 `finally` 에서도 비운다(`pushState` 가 던지면 다음 route 로 새지 않게).
- **판단 — 「본문 바로가기」를 브라우저에 맡기지 않는다.** 맡기면 주소에 「#app」이 붙고 기록 항목이 하나 생긴다(뒤로 가기가 한 번 더 걸린다). MDN 은 같은 문서 안 이동의 `popstate` 를 「state 가 바뀌면」으로만 적어 그쪽 동작은 단정하지 않았다 — 직접 옮기는 쪽은 그 물음과 무관하다.
- **판단 — 구분 탭은 위치를 건드리지 않는다.** 탭 줄은 `#app` 밖 · sticky 라 스크롤과 무관하게 제자리다 — 스크롤 고정이 있으면 계산이 0 이 되고, 없으면 루트 안 위치가 없어(`offset: null`) 스크롤하지 않는다. 목록의 스크롤은 지금처럼 뷰가 정한다(ADR-031 §1 의 PUSH 의미론).
