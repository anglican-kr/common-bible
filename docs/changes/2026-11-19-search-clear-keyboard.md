## 요약

휴대폰 하단 검색 입력창의 검색어 지우기(⊗)가 키보드를 내린다. 포커스는 같은 입력창의 깔때기(책 선택)로 옮긴다. 전에는 늘 입력에 포커스를 주어, 결과 화면에서 지워도 키보드가 올라왔다. ADR-030 §3과 「검토한 대안」을 고쳤다.

## 확정 · 근거

- 사용자 요청(2026-11-19): 검색 결과 화면에서 검색창의 ⊗를 누르면 검색어가 지워지고 최근 검색 목록으로 돌아가는데, 그때 키보드가 올라오지 않으면 좋겠다. 아이폰에서 본 것이다. 원인은 지우기 단추가 늘 입력에 포커스를 주던 것(`tabbar.js`, 처음 구현부터의 동작)이다.
- 사용자 결정(2026-11-19): 입력 중에 지워도 키보드를 내린다. 입력 중에 지우는 것은 검색을 그만두는 뜻이다. 처음 연 PR은 입력 중이면 입력에 포커스를 남겼다(앞 세션의 제안).
- 구현하며 정한 것
  - 포커스는 깔때기로 옮긴다. 지우기 단추는 검색어가 없으면 숨겨져 포커스가 그 자리에 남을 수 없고, 아무 데도 두지 않으면 포커스가 페이지 맨 앞으로 떨어진다(WCAG 2.4.3). 책 선택 시트의 「적용」도 휴대폰 키보드가 결과를 가리지 않게 깔때기로 포커스를 돌린다(ADR-033 D3). 깔때기가 포커스를 받지 못하면 홈 탭이다.
  - 손가락이나 마우스로 누르면 깔때기에 포커스 테두리를 그리지 않고, 키보드로 누르면 그린다. 눌러서 생긴 테두리는 깔때기가 골라진 것처럼 보이고, 키보드 사용자에게는 테두리가 포커스의 자리를 알린다. `helpers.js`와 `calendar.js`가 같은 방식이다.
  - 단추의 `pointerdown` 기본 동작을 막는다(깔때기와 같다). 막지 않으면 누르는 사이에 입력의 포커스가 먼저 빠져 키보드가 내려가며 입력창이 움직이고, Android에서는 단추가 포커스를 가져간다.
  - 데스크톱 상단 바의 검색어 지우기(`search.js`)는 그대로 입력에 포커스를 준다. 화면 키보드가 없다.

## 검증

- `npm run typecheck` 통과, `node --test tests/unit/*.test.js` 1,957개 통과.
- e2e `test_tabbar.py` 19개를 작업 폴더 서버(8091)에서 돌려 통과했다. 지우기 단추를 쓰는 e2e는 이 파일뿐이다. 새 시험 `test_clear_lowers_the_keyboard_and_focuses_the_funnel`은 결과 화면에서 지울 때, 입력 중에 지울 때, 키보드로 단추를 누를 때 모두 포커스가 깔때기로 가는지, 결과 화면에서 지우면 최근 검색 화면을 다 그린 뒤에도 깔때기에 있는지, 누르는 사이에 입력의 포커스가 빠지지 않는지, 마우스로 누르면 테두리가 없고 키보드로 누르면 있는지 본다. `test_clear_falls_back_to_the_home_tab_when_the_funnel_cannot_take_focus`는 깔때기가 숨겨졌을 때 홈 탭으로 가는지 본다. 1회차에 `pointerdown`의 기본 동작 막기와 깔때기 포커스를 빼면 실패함을 확인했고, 2회차에 포커스 옵션(`focusVisible: false`)을 빼면 테두리 검사가 실패함을 확인했다.
- 아이폰의 화면 키보드는 이 환경에서 볼 수 없다. dev에 올린 뒤 실기기에서 확인한다.

## 리뷰 반영

1회차(로컬 `/code-review medium`, 2026-11-19). 사용자가 리뷰의 결함을 모두 고치기로 했다. 여섯 건을 이렇게 다뤘다.

- 1번: 단추의 `pointerdown` 기본 동작을 막았다(위 「구현하며 정한 것」).
- 2번, 5번: 입력 중이었는지 기억하던 값(`clearWhileTyping`)이 누름이 취소되면 남고, 하드웨어 키보드 사용자를 입력 중이 아닌 것으로 보았다. 사용자 결정으로 갈래가 없어져 그 값을 지웠다.
- 3번: 깔때기가 없을 때의 대체 경로가 아무 일도 하지 않아 포커스가 페이지 맨 앞으로 떨어질 수 있었다. 홈 탭으로 옮긴다.
- 4번: 깔때기에 포커스를 준 뒤 화면을 다시 그리면 깔때기가 숨겨져 포커스를 잃을 수 있다는 지적이다. 하단 입력창의 깔때기는 검색 모드에서 그 입력창에 포커스가 있으면 늘 보이므로(`syncOneField`) 지금은 생기지 않지만, 사용자 결정으로 고쳤다. `navigate`와 `navigateSearch`가 다시 그리기가 끝나는 때를 알리는 값(`Promise`)을 돌려주게 하고, 다 그린 뒤 포커스가 페이지 맨 앞이나 그려지지 않은 요소에 있으면 다시 옮겼다. 이 처리는 2회차에서 걷어냈다(아래).
- 6번: 시험에 입력 중에 지울 때와 키보드로 누를 때를 더하고, 누르는 사이에 입력의 포커스가 빠지지 않는지 본다.

2회차(로컬 `/code-review medium`, 2026-11-19). 사용자가 결함을 모두 고치기로 했다. 아홉 건을 이렇게 다뤘다.

- 1번, 3-6번: 1회차 4번을 고치려고 넣은, 다 그린 뒤 포커스를 다시 옮기는 처리를 걷어냈다. 그 처리는 자기가 가장 최근의 화면 이동인지 보지 않아, 지운 직후 사용자가 새 검색을 하면 늦게 끝난 앞의 처리가 포커스를 깔때기나 홈 탭으로 빼앗을 수 있었다(1번). 그 한 곳을 위해 앱 전체의 화면 이동 함수(`navigate`)가 돌려주는 값을 바꿨고(3번, 4번), 포커스를 잃었는지 가르는 검사가 레이아웃 상자 없이 포커스를 받는 요소까지 잃은 것으로 보았으며(5번), `search.js`에 이미 있는 「다 그린 뒤 깔때기로」 처리와 겹쳤다(6번). 입력창 안에 포커스가 있는 동안 `syncOneField`가 깔때기를 숨기지 않으므로, 다시 그려도 포커스는 깔때기에 남는다. 그래서 1회차 4번의 걱정은 이 처리 없이도 생기지 않는다. `navigate`, `navigateSearch`와 그 타입은 main 그대로이고, 지운 뒤 포커스를 옮기는 함수에서 깔때기가 그려졌는지 보던 검사(`getClientRects`)도 뺐다. 시험은 다시 그리는 사이에 깔때기를 억지로 숨기던 경우를 빼고, 최근 검색 화면을 다 그린 뒤에도 포커스가 깔때기에 있는지 본다.
- 2번: 손가락이나 마우스로 누르면 포커스 옵션(`focusVisible: false`)으로 깔때기에 테두리를 그리지 않는다(위 「구현하며 정한 것」). 이 옵션을 모르는 옛 브라우저(Safari 18.4, Chrome 145 이전)에서는 테두리가 그대로 보인다.
- 7번: ADR-030 §3에서 `pointerdown` 처리를 지우고 주제 문서를 가리키게 했다. 그 내용은 `routing.md`에 있다.
- 8번: ADR-030 「검토한 대안」에서 누가 정했는지를 지웠다. 이 원장의 「확정 · 근거」에 있다.
- 9번: 「다시 그리기의 약속」은 그 처리와 함께 코드와 문서에서 지웠다. `routing.md`의 그 줄은 지금 동작으로 고쳐 쓰고, 주제 문서의 틀(`docs/topics/README.md`)대로 날짜와 출처, 예전 동작을 뺐다.
