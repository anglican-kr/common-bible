## 요약

검색이 결과를 받지 못하면(검색 자료의 메타 파일이나 성서 색인을 받지 못하거나, 검색 워커가 오류를 내면) 본문 자리(`#app`)가 「검색에 실패했습니다.」 한 줄로 바뀌어, 휴대폰에서는 검색 화면 맨 위의 입력창까지 사라졌다(known-issues §48). 이제 캘린더, 전례독서, 성서 화면과 같은 전체 화면 실패를 결과 자리에 그린다. 제목은 「검색 자료를 불러오지 못했습니다」이고, 부제와 단추 「다시 불러오기」는 세 화면과 같다. 머리(「"사랑" 검색」), 휴대폰의 위쪽 입력창, 책 알약은 남는다(ADR-048 §6, DESIGN.md §6 「전체 화면 실패」).

본문은 세 화면과 같은 함수(`views.js`의 `commitFailure`)가 그린다. 이 함수가 그릴 자리(`target`)를 받게 했고, 넘기지 않으면 지금처럼 본문 자리 전체다. 쓰는 곳이 없어진 오류 한 줄 함수(`renderError`)와 `.error` 스타일은 지웠다.

## 확정 · 근거

- **사용자 결정(2026-11-23)**: 검색의 실패도 세 화면과 같은 전체 화면 실패로 그린다. 제목은 다른 화면의 「…자료를 불러오지 못했습니다」와 같은 틀의 「검색 자료를 불러오지 못했습니다」(마침표 없음)이고, 부제와 단추는 세 화면의 글과 단추를 그대로 쓴다. 머리는 검색 화면의 것이고, 휴대폰의 위쪽 입력창은 남겨 그 자리에서 검색어를 고쳐 다시 찾게 한다. 버린 두 안(오류 한 줄에 입력창만 남기기, 제목 「검색하지 못했습니다」)은 ADR-048 「검토한 대안」에 있다.
- **ADR-048에 §6으로 더했다.** 휴대폰의 검색 화면은 위쪽 입력창과 책 알약을 늘 보인다는 규칙(§1)이 이 ADR에 있고, 고친 증상이 그 규칙을 어긴 것이었다. 실패 화면의 모양은 DESIGN.md §6, ADR-038 §3, ADR-024 §6을 가리킨다. 검색 주제 문서의 「결정」에 ADR-048을 더했다.
- **구현하며 정한 것**
  - 실패 화면은 결과 자리(`.search-view-results`)에만 그린다. 본문 자리를 통째로 비우고 입력창을 다시 넣으면, 찾는 동안 입력창을 눌러 둔 사람의 포커스와 키보드가 사라지고, 레이아웃이 바뀔 때 입력창만 넣고 빼는 처리(`onLayoutTierChange`)가 검색 화면을 찾지 못해 검색을 다시 한다. `commitFailure`의 `target`은 기본값이 본문 자리라 세 화면의 동작은 그대로다.
  - 책 알약도 이름과 ×로 남긴다(수는 없다). ADR-048 §1이 휴대폰의 검색 화면은 입력창과 그 아래의 책 알약을 늘 보인다고 정했고, ADR-049 §1이 데스크톱도 검색 화면 본문 맨 위에 둔다고 정했다. ADR-049 §5 「결과 수를 모를 때」에 이 경우를 더했다.
  - 포커스는 옮기지 않는다. 다른 실패 화면과 같다. 휴대폰에서 Enter로 찾은 뒤에는 그전처럼 포커스가 페이지(`body`)에 있어 키보드가 다시 뜨지 않고, 데스크톱은 상단 바의 검색창에 남는다.
  - 실패 화면의 글은 `views.js`의 `FAILURE_TEXT` 블록에 `SEARCH_FAILURE_TEXT`로 두어 유닛이 본다. 다음 행동은 세 화면과 같은 `buildReloadButton`이다.
  - `renderError`와 `.error`는 검색만 썼으므로 함수, 창 전역 등록, 타입 선언(`js/types.d.ts`), CSS 규칙을 지웠다. 다른 e2e에서 `.error`가 없는지 보는 검사(`test_navigation.py`, `test_liturgical_lazy_load.py`, `test_lectionary_view.py`)는 그 화면들의 시험이라 그대로 두었다. 이제 `.error`를 그리는 코드가 없어 늘 참이다.
- **바꾸지 않은 것**
  - 실패한 검색어는 그전처럼 최근 검색에 남는다. ADR-014 D1이 다시 빼는 것은 모르는 책 이름과 다섯 권을 넘긴 검색뿐이다. 페이지 제목, 방문 기록, 탭 복원도 결과 화면과 같다.
  - 검색 워커는 받지 못한 메타 파일과 성서 색인을 페이지를 새로 고칠 때까지 다시 받지 않는다(`loadMeta`, `loadChunk`가 실패한 요청을 그대로 둔다). 그래서 자료를 받지 못한 실패는 검색어를 고쳐 다시 찾아도 그대로이고, 「다시 불러오기」가 다시 받는다. 이 PR의 범위 밖이라 고치지 않았다.
  - 검색 워커가 찾다가 오류를 낸 것도 이 화면이다. 자료를 받지 못한 것이 아니어도 제목은 「검색 자료를 불러오지 못했습니다」다. 성서 화면과 캘린더도 그리다 생긴 오류에 「…자료를 불러오지 못했습니다」를 쓴다.

## 검증

- 고치기 전에 재현했다(Chromium). `search-meta.json`이 500을 돌려주게 하고 요한의 복음서 3장에서 「사랑」을 찾았다. 데스크톱(1280×720)과 휴대폰(390×844, iPhone 사용자 에이전트) 모두 본문 자리가 「검색에 실패했습니다.」 한 줄이었고, 휴대폰에는 위쪽 입력창이 없었으며 포커스는 페이지(`body`)였다. 라이브 영역은 「"사랑" 검색」뿐이었다.
- 고친 뒤 같은 흐름에서 머리 「"사랑" 검색」, 실패 화면, 휴대폰의 입력창(「사랑」이 든 채)이 보이고, 라이브 영역은 「"사랑" 검색 — 검색 자료를 불러오지 못했습니다」였다. 320px과 390px 폭에서 가로 스크롤이 없었다.
- 유닛 `node --test tests/unit/*.test.js` 1,992건이 통과했다. 새 1건(`views.test.js`의 `SEARCH_FAILURE_TEXT`)이 실패 화면의 글을 본다.
- 타입 검사(`tsconfig.json`, `tsconfig.worker.json`)가 통과했다.
- e2e는 작업 폴더 서버(8092)에서 바꾼 코드를 지나는 파일만 골라 돌렸다. 열 파일 496건 가운데 495건이 통과했다(16분 14초). 남은 1건(`test_calendar_view.py`의 `test_view_button_switches_between_month_and_list_keeping_the_month`, 월간으로 돌아가는 주소를 30초 동안 기다리다 실패)은 이 변경이 지나지 않는 캘린더의 보기 전환이다. 혼자 세 번 돌려 모두 통과했고, 파일 전체 108건을 다시 돌려 모두 통과했다.
  - `test_search.py`(129건): 검색 화면. 옛 `test_worker_error_surfaces_to_ui`를 새 시험 12건으로 바꿨다. 메타 파일의 500과 오프라인, 첫 성서 색인의 500, 받는 동안의 결과 뒤에 오는 성서 색인의 500, 검색 워커의 오류(워커 스크립트 끝에 시험용 코드를 붙여 정한 쪽에서 던지게 했다), 데스크톱과 휴대폰의 머리와 검색창, 라이브 영역, 포커스, 최근 검색, 실패 화면에서 고쳐 다시 찾기와 「다시 불러오기」, 레이아웃 경계를 넘나들기, 다음 쪽의 실패와 뒤로 가기, 앞으로 가기, 책을 고른 검색과 알약의 ×, 탭 바로 나갔다 돌아오기다.
  - `test_a11y_axe.py`(17건): 실패 화면의 axe 검사 2건(데스크톱, 휴대폰)을 더했다.
  - `test_layout_tiers.py`(10건), `test_tabbar.py`(26건), `test_top_bar.py`(45건), `test_a11y_keyboard.py`(11건): 위쪽 입력창, 레이아웃 경계, 상단 바의 검색창을 다룬다.
  - `test_navigation.py`(32건), `test_liturgical_lazy_load.py`(11건), `test_calendar_view.py`(108건), `test_lectionary_view.py`(107건): 실패 화면의 본문을 그리는 `commitFailure`를 함께 쓴다.
- 변이 검사: `js/app/search.js`, `js/app/views.js`, `css/style.css`를 고치기 전의 것으로 되돌리고 새 e2e 14건(`test_search.py` 12건, `test_a11y_axe.py` 2건)을 돌리니 모두 실패했다. axe 2건은 실패 화면을 기다리다 실패했다. 유닛은 `FAILURE_TEXT` 블록에 `SEARCH_FAILURE_TEXT`가 없어 그 블록을 읽는 7건이 모두 실패했다. 되돌린 파일은 고친 것으로 복원했다.
- 시험으로 남기지 않고 Playwright로 본 것: 성시 색인이나 전례독서 색인을 받지 못하면 실패 화면이 아니라 성서 결과다(「성서 본문 709건 (1/89쪽)」). 메타 파일이나 첫 성서 색인을 받지 못한 뒤 자료가 돌아와도 새로 고치지 않고 다시 찾으면 같은 실패 화면이다. 주소로 바로 연 실패에서도 시작 화면이 내려간다. 입력 칸에 친 `in:`은 Enter로 찾으면 주소의 책(`in=`)이 되어 실패 화면에도 알약으로 남는다. 주소의 `q`에 `in:`이 든 채로 바로 열면 알약 없이 입력창의 글로만 남는다(별칭 표를 읽기 전에 그린 알약 줄은 그 책을 모른다. 결과를 받으면 워커가 센 책으로 다시 그리지만, 실패하면 다시 그리지 않는다). 검색 워커 스크립트를 받지 못하면(404) 실패 화면이 아니라 「검색 중…」에 머물고 시작 화면도 내려가지 않는다(이 PR 밖, 고치기 전과 같다).
- 문서 검사 `node --test tests/unit/docs-*.test.js` 23건이 통과했다. 바꾼 문서의 줄을 `tools/prose/prose.py lint`로 보았고, 남은 경고는 「검토한 대안」 줄의 가운뎃점과 상태 줄의 줄표처럼 이 문서들이 이미 쓰는 형식이다.
- iPhone 실기기와 WebKit에서는 보지 않았다.

## 리뷰 반영

1회차(`/code-review medium --fix`, 이번 변경의 결함 없음, 전부터 있던 것 하나, 사소한 것 둘):

- **검색 워커의 스크립트(`search-worker.js`)를 받지 못하면 「검색 중…」에서 멈춘다는 지적은 넘겼다.** 위 「검증」에 적은, 고치기 전과 같은 증상이다. 리뷰는 워커의 `error` 사건에서 진행 중인 검색을 실패로 끝내도록 고쳐 두었지만, 이 PR이 바꾼 곳이 아니어서 되돌렸다.
- **「다시 불러오기」 단추에 마우스를 올렸을 때의 배경(`.state-action > button:hover`)을 `@media (hover: hover)` 안으로 옮기자는 지적은 넘겼다.** 캘린더, 전례독서, 성서 화면이 함께 쓰는 전부터 있던 규칙이고, 이 단추는 누르면 바로 페이지를 새로 고치므로 터치한 뒤 배경이 남아 보이지 않는다. 리뷰가 고친 것을 되돌렸다.
- **워커 스크립트를 받지 못하는 경우를 e2e(`test_search_failure_causes`)에 더하자는 지적**은 첫 지적의 고침을 지키는 시험이라 함께 되돌렸다.
- 리뷰와 따로 Playwright로 확인한 것: 실패 화면 옆에 받는 동안의 결과, 묶음 알약, 결과 수 제목, 쪽 넘기기, 「검색 중…」이 남지 않는다. 라이브 영역은 「"사랑" 검색」, 받는 동안의 결과 수, 「"사랑" 검색 — 검색 자료를 불러오지 못했습니다」의 차례다. 찾는 동안 홈 탭으로 떠나면 홈이 그대로이고, 새 검색을 시작하면 새 검색어의 실패 화면 하나만 그린다. 찾는 동안 레이아웃 경계를 넘어도 실패 화면은 하나다. 실패 화면에서 ⊗는 최근 검색 화면으로 가고 포커스는 깔때기에 간다. 깔때기로 연 책 선택 시트의 「적용」은 새 책으로 다시 찾는다. 「다시 불러오기」는 쪽, 묶음, 책이 든 주소를 그대로 다시 연다. 320×568에서는 단추가 처음에 탭 바에 가리지만 스크롤하면 탭 바 위로 올라온다. 휴대폰의 실패 화면은 검색 화면의 여백(`.search-view`) 안이라 성서 화면의 실패 화면보다 양쪽이 16px씩 좁다(390px 폭에서 상자 326px, 성서 화면은 358px). 글꼴, 글자 크기, 단추는 같다.
- 관련 e2e 287건이 통과했다(`test_search.py`, `test_a11y_axe.py`, `test_navigation.py`, `test_liturgical_lazy_load.py`, `test_layout_tiers.py`, `test_tabbar.py`, `test_top_bar.py`, `test_a11y_keyboard.py`, 캘린더와 전례독서의 실패 화면 시험 6건).
