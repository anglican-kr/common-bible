## 요약

교회력 문서와 코드 주석에서 쓰던 낱말을 사용자 결정에 따라 바꿨다. 화면에 보이는 글은 바뀌지 않는다(이 낱말들은 화면 글에 없었다).

- **「관측일」은 「전례일」로.** 그날 걸리는 주일, 대축일, 축일, 기념일, 평일 하나하나를 가리키던 말(observance)이다. 543곳이다.
- **「승자」는 「지정 전례일」로.** 교회력이 그날 정하는 하나, 엔진의 `official`이다. 「승자 판정」, 「승자 자격」은 「지정 판정」, 「지정 자격」으로 썼다. 짝이던 「패자」는 「후순위 후보」로 썼다. 합해 330곳쯤이다.
- **「이동 패스」는 「이동 계산」으로.** 교회력 엔진이 한 해를 1월 1일부터 날짜 순으로 돌며 밀린 축일의 자리를 정하는 일이다. 줄여 쓴 「패스」도 바꿨고, 그 결과물은 「계산 결과」(「빈 계산 결과」)로 썼다. 256곳이다.
- **「지정 독서」는 「그 평일에 정한 독서」로.** 성주간 평일과 재의 수요일 후 목, 금, 토요일에 정해 둔 독서를 가리키던 말이다. 「지정 전례일」과 헷갈리지 않게 풀어 썼다. 18곳이다.
- **우선순위를 뜻하는 「이긴다」, 「진다」를 마저 바꿨다.** 2026-07-06에 「선순위」, 「후순위」로 정했는데, 교회력 쪽 코드 주석, 테스트, 검토 문서, ADR-036과 038, 설계서 뒷부분에 87곳이 남아 있었다. 「축일이 이기면」은 「축일이 지정 전례일이면」, 「격자를 이긴다」는 「격자보다 선순위다」, 「진 쪽」은 「후순위인 쪽」으로 썼다.

코드 이름(`observance`, `official`, `computeTransfers`, `TransferPass`, `EMPTY_PASS`, `winners.cases.json`, 픽스처 id의 `W-`)과 규칙 마커(`R-6.5-year-pass`)는 그대로 두었다.

## 확정 · 근거

- **이동 계산(사용자 결정 2026-10-24).** 사용자가 「이동 패스」를 「이동 경로」로 바꾸자고 했다. 「경로」는 한 축일이 옮겨 가는 길로 읽히기 쉽고, 문서에 「조회 경로」처럼 다른 뜻의 「경로」가 이미 있다. 그래서 「이동 경로」, 「이동 계산」, 「이동 정하기」를 예문과 함께 보였고, 사용자가 「이동 계산」을 골랐다.
- **지정 전례일(사용자 결정 2026-10-24).** 사용자가 「이긴다」를 바꾼 것과 같은 까닭으로 「승자」도 바꾸자고 했다. 사용자의 뜻은 이렇다. 교회력이 그날 정하는 것은 하나이고, 그날 함께 걸린 다른 후보의 독서는 대안 독서다. 처음에는 「지정 관측일」로 정했다. 이어서 사용자가 가톨릭 규범의 「전례일」(liturgical day)이 주일, 대축일, 축일, 기념일, 평일을 묶는 상위 개념이라며 이 말을 쓰자고 했다.
  - 영문판 「전례주년과 전례력에 관한 일반 규범」으로 확인했다. 제1편 「전례일」 아래에 주일, 대축일·축일·기념일, 평일이 있고, 등급표가 전례일 사이의 선후를 정한다(제59항). 같은 날 여러 거행이 겹치면 등급이 가장 높은 것을 지낸다(제60항).
  - 그날 지내지 못하는 기념일도 전례일이므로, 「전례일」은 「관측일」 전체와 같은 자리다. 그래서 「관측일」을 모두 「전례일」로 바꾸고, `official`은 「지정 전례일」로 불렀다. 사용자가 제안한 「오늘의 전례」는 오늘이 아닌 날짜를 설명할 때 어색하고 「저녁 전례」와 부딪혀, 예문과 함께 보인 뒤 사용자가 「지정 전례일」을 골랐다.
  - 사용자가 참고로 보인 다른 대화는 날짜의 결과를 「전례일」, 후보를 「거행」, 선택된 것을 「당일 거행」으로 나누는 안을 냈다(규범 제60항, litcal-roman). 대한성공회 기도서 원문과 2024-2027 책자에 「거행」이 한 번도 나오지 않고 「지킨다」를 쓴다는 점을 함께 보였고, 사용자가 지금 정한 방식을 골랐다. romcal도 날짜마다 후보 하나하나를 `LiturgicalDay`로 돌려준다.
  - 이 뜻을 교회력 주제 문서의 「확정 사실」에 적었다.
- **「지정 독서」를 풀어 쓴 것**은 「지정 관측일」 후보를 보일 때 함께 알렸다. 그 뜻(사용자 확정 2026-10-10)은 바뀌지 않는다.
- **「기간 관측일」은 「기간」으로 줄였다.** 일치 기도 주간처럼 여러 날짜에 걸쳐 얹히는 기간을 가리키는 말이라, 「기간 전례일」은 어색하다.
- **바꾸지 않은 곳.**
  - 다른 뜻으로 쓴 낱말: git의 「패스스펙」, 북마크 문서의 사용자 인용 「일단 패스」, 코딩 함정의 「의도하지 않은 패스」, 동기화 테스트의 「`_u`가 큰 쪽이 이긴다」, 북마크 ADR의 CSS 우선순위.
  - 「화면 글에 「관측일」을 쓰지 않는다」(ADR-038, `lectionary.js` 주석). 사용자 결정의 낱말 그대로다.
  - 옛 결정의 문구를 옮긴 인용(「승자 하루」, 「그날은 승자의 절기색 …」 등 넷)과, 다른 구현의 코드 주석을 옮긴 「켜기 전에는 평일이 이긴다」.
  - CI 설정(`.github/workflows/engine-data.yml`, `sync-data.yml`)의 단계 이름과 주석에 있는 「관측일」 셋. 워크플로 파일은 push 권한이 따로 필요할 수 있어 따로 고친다.
  - 머지된 원장, 보관 문서(`docs/archive/`).
  - 데이터 저장소(`liturgical/README.md`, `classification.py`, `normalize.py`, `parse_periods.py`, `calendar/*.md`, 테스트, 본기도 표와 기간 표의 `_meta`)에도 「관측일」, 「승자」, 「이동 패스」가 있다. 그 저장소에서 따로 고친다.
- **#408에서 놓친 낱말을 함께 고쳤다.** #381(2026-10-23)은 「병기」, 「경합」 같은 낱말을 ADR과 설계서를 고쳐 쓸 때 바꾸기로 넘겼다. #408에서 고쳐 쓴 §6.2와 §6.4에 「병기」 여섯 곳과 「좌석 경합에서는」이 남아 있어 「함께 적는다」, 「자리 다툼」으로 바꿨다. #406에서 고쳐 쓴 §5.3의 「이기되」도 「앞서되」로 바꿨다. §7 합성 케이스 이름 「좌석 경합」은 테스트 이름을 가리키는 인용이라 그대로 두었다.

## 검증

- 기계로 바꾼 뒤 바뀐 줄을 모아 하나씩 봤다. 손으로 고친 곳은 다음과 같다.
  - 「이동 이동 계산」으로 겹친 9곳.
  - 괄호나 굵은 표시 뒤에 남은 조사 18곳(「계산(§6.5)가」, 「지정 관측일(`official`)가」 등).
  - 「승자 성탄 낮」처럼 이름이 바로 붙어 어색해진 27곳.
  - 「진 쪽」 규칙이 「엔진 쪽」, 「꺼진 쪽」까지 바꾼 4곳은 되돌렸다.
  - 라이브 영역 문구 「날짜 — 전례일 전례독서」는 실제 코드대로 「날짜 — 이름 전례독서」로 고쳤다.
- 교회력 사실 토큰 비교 `python3 scripts/docs_facts_snapshot.py --diff main WORKTREE --strict-counts`에서 사라진 토큰과 줄어든 토큰이 0이다.
- `--docs 'docs/design/*.md' --docs 'docs/decisions/03[678]-*.md' --docs 'docs/topics/liturgical.md' --kinds general --strict-counts`에서 사라진 토큰은 바뀐 낱말이 든 인용이다. 모두 문서끼리 서로 가리키던 같은 문구를 함께 바꾼 것이다(「지정 전례일과 재분류의 판정」, 「본기도는 고른 전례일의 것만」, 「이동 계산이 결정적인 이유 셋」 등).
- `node --test tests/unit/docs-*.test.js tests/unit/liturgical-fixtures.test.js` 31개가 모두 통과했다. 테스트 이름과 주석을 바꿨으므로 `node --test tests/unit/liturgical-engine*.test.js tests/unit/calendar*.test.js tests/unit/lectionary*.test.js tests/unit/liturgical-fixtures.data.test.js tests/unit/helpers.test.js`(425개 통과, 1개 건너뜀)와 `npm run typecheck`도 돌렸고 통과했다. 픽스처 JSON 셋을 다시 읽어 보았고, 설명 문자열만 바뀐 e2e 파일 셋과 `tools/booklet`, `scripts/docs_facts_snapshot.py`도 문법 검사를 통과했다.
