## 요약

검색창에 검색어를 치고 Enter를 누르기 전에 깔때기로 책을 골라 「적용」을 누르면, 친 검색어가 지워지고 최근 검색 화면이 나왔다. 고른 책은 칩으로 남았지만 결과가 나오지 않았다(사용자 보고 2026-11-18, 휴대폰 홈 화면 앱의 탭 바 검색). 이제 「적용」은 시트를 연 검색창에 보이는 검색어를 고른 책 안에서 찾는다. ADR-033 D3의 「책 선택 시트」 항목을 이 규칙으로 고쳤다.

## 확정 · 근거

- 원인은 두 가지였다.
  - 「적용」이 주소의 검색어(`q`)만 이어받고 범위만 바꿨다(`navigateSearch`). Enter를 누르지 않고 친 검색어는 주소에 없어 빠졌다.
  - `route()`가 시트를 닫기 전에 검색창을 주소의 검색어로 다시 채운다. 탭 바 검색창은 포커스가 없을 때 다시 채우는데(`tabbar.js`의 `syncInputFromUrl`) 그때 포커스는 시트의 「적용」 단추에 있고, 데스크톱 상단 바의 검색창은 이동마다 다시 채운다(`routing.js`). 그래서 친 글자가 화면에서도 사라졌다. 휴대폰의 페이지 안 검색창도 빈 검색 화면을 다시 그리며 비워진다.
- 고친 방식: 「적용」이 이동하기 전에 시트를 연 검색창의 글을 읽는다.
  - 주소의 검색어와 다르면 Enter와 같은 커밋 함수(`commitTopSearch`)로 고른 책과 함께 찾는다. 최근 검색에 넣고 `in:<별칭>`을 칩으로 옮기는 것도 Enter와 같다.
  - 구절 표기는 장으로 바로 가지 않고 구절 바로가기 카드를 보인다. ADR-033 D3의 「필터를 바꾸면 `searchAutoNavigate`를 세우지 않는다」를 지킨다. 이를 위해 `commitTopSearch`에 범위와 바로 가기를 넘기는 선택 인자를 더했다.
  - 같으면 전처럼 범위만 바꾸고, 검색창이 비었으면 그 범위로 최근 검색 화면에 간다.
- 포커스: 찾았으면 시트를 연 깔때기로 돌아간다(시트가 닫히며 돌려준다). 탭 바에서 Enter를 누르면 키보드를 내리는 것처럼, 키보드가 결과를 가리지 않게 하려는 것이다. 검색어가 없으면 전처럼 검색창에 포커스를 두어 바로 칠 수 있게 한다.
- 버린 방식: 「적용」은 범위만 바꾸고 친 검색어를 검색창에 남겨 두어 Enter로 찾게 하는 것. 화면은 최근 검색인데 검색창에 검색어가 있어 찾은 것처럼 보인다. ADR-033 「검토한 대안」 A에 적었다.
- 사용자가 적은 순서(깔때기, 책, 그다음 검색어와 Enter)는 Chromium의 아이폰 흉내에서 결과가 맞게 나왔다. 실패한 것은 검색어를 먼저 치고 깔때기를 누른 경우이고, 보내 준 두 번째 화면(칩 「마르」, 빈 검색창, 최근 검색, 키보드)과 같은 상태가 된다. 아이폰 Safari에서만 생기는 다른 원인이 있는지는 기기에서 확인하지 못했다.

## 검증

- 유닛 전체 `node --test tests/unit/*.test.js` 1,910개 통과, 타입 검사 `npm run typecheck` 통과.
- 새 e2e(`tests/e2e/test_search.py`)
  - `test_book_filter_apply_searches_the_typed_query`(휴대폰 탭 바, 데스크톱 상단 바): 「사랑」을 치고 Enter 없이 마르코를 골라 적용하면 주소가 `q=사랑&in=mark`이고, 결과가 모두 마르코의 복음서이고, 검색창에 「사랑」이 남고, 최근 검색의 맨 위가 「사랑」이고, 포커스가 깔때기에 있다.
  - `test_book_filter_apply_keeps_a_typed_verse_reference_on_the_results`: 「요한 7:16」을 치고 요한을 골라 적용하면 장으로 가지 않고 구절 바로가기 카드를 보인다.
  - 세 경우 모두 고치기 전의 코드에서 실패하고 고친 코드에서 통과한다.
- e2e `test_search.py`, `test_tabbar.py`, `test_top_bar.py`(Chromium): 126개 가운데 125개 통과. 실패한 하나(`test_modifier_click_on_tab_leaves_no_scroll_restore_behind`, 수정 키로 탭을 눌러 새 탭이 5초 안에 열리기를 기다린다)는 따로 돌리면 고치기 전과 고친 뒤 모두 통과해, 긴 실행 중의 시간 초과로 본다. 검색 코드를 지나지 않는 시험이다.
- Chromium 아이폰 흉내로 다섯 흐름을 손으로 돌려 봤다. 검색 뒤 책 고르기, 검색어를 치고 책 고르기, 검색창을 지운 뒤 새 검색, 책을 바꾸기, 책을 먼저 고르고 검색. 모두 고른 책 안의 결과가 나온다.

## 리뷰 반영

1회차(코드 리뷰)
- 입력 칸에 `in:<별칭>`만 치고 「적용」을 누르면 별칭이 칩이 되고 찾을 낱말이 없어 최근 검색 화면에 가는데, 칸에 글이 있었다는 이유로 검색한 것으로 보아 포커스를 입력 칸에 두지 않았다. ADR-033 D3의 「검색어가 없으면 입력 칸으로」와 어긋난다. `commitTopSearch`가 찾은 낱말을 돌려주게 하고, 「적용」은 낱말을 찾았는지로 포커스를 정한다. e2e `test_book_filter_apply_with_only_a_typed_scope_focuses_the_field`(휴대폰, 데스크톱)를 더했고, 고치기 전 코드에서 실패하고 고친 코드에서 통과한다.
- 휴대폰의 페이지 안 검색창에서 연 시트로 찾으면 포커스가 문서 본문으로 빠지는 문제도 찾았다. 이 PR 전에도 같았고 범위 밖으로 보아 이 회차에서는 두었다(2회차에 고쳤다).
- 검증: 타입 검사 통과, 유닛 1,910개 통과, e2e `test_search.py -k book_filter` 7개 통과.

2회차(사용자 요청 2026-11-18: 1회차에서 둔 문제도 고친다)
- 휴대폰의 페이지 안 검색창(탭 바 검색을 열지 않고 들어온 검색 화면)에서 연 시트로 찾으면, 시트가 닫히며 그 검색창의 깔때기로 포커스를 돌려주지만 결과 화면이 검색창을 새로 그리며 옛 깔때기를 버려 포커스가 문서 본문으로 갔다. 키보드와 화면 낭독기 사용자가 자리를 잃는다(WCAG 2.4.3). 새로 친 검색어로 찾을 때와, 검색어는 그대로 두고 책만 바꿀 때 모두 그랬다.
- 고친 방식: 「적용」이 이 검색창에서 찾았으면 그 이동의 번호(`routeSeq`)를 적어 두고, 결과 화면을 그리는 함수(`renderSearchResults`)가 같은 이동을 그릴 때 새 검색창의 깔때기로 포커스를 옮긴다. 이동 번호로 맞추므로 사용자가 그사이 다른 화면으로 가면 아무 일도 하지 않는다. 포커스가 이미 다른 곳에 있으면 옮기지 않는다. 링크를 누른 자리로 포커스를 돌려주는 공용 장치(`restoreFocusSpot`)는 링크의 누름에서만 자리를 받고 스크롤도 맞추므로 쓰지 않았다.
- 새 e2e `test_book_filter_apply_from_the_in_page_bar_focuses_its_new_funnel`(새로 친 검색어, 책만 바꾸기): 고치기 전 코드에서 포커스가 문서 본문이라 실패하고, 고친 코드에서 통과한다.
- 검증: 타입 검사 통과, 유닛 1,910개 통과, e2e `test_search.py -k book_filter` 9개 통과. `test_search.py`, `test_tabbar.py`, `test_top_bar.py`를 함께 돌리면 130개 가운데 128개 통과다. 실패한 둘은 수정 키로 탭을 누르는 시험(위 「검증」의 것)과 데스크톱 북마크 패널을 닫은 뒤 포커스가 탭으로 오는지 보는 시험(`test_bookmark_tab_takes_focus_back_even_when_the_click_gave_it_none`)이다. 둘 다 검색 시트를 거치지 않고, 따로 돌리면 고치기 전과 고친 뒤 모두 통과하며, `test_top_bar.py`만 돌리면 34개 모두 통과한다.
