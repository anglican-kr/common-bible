# refactor: 캘린더 · 전례독서 모듈 지연 로드

## 요약

성서만 읽는 사람도 부팅 때 교회력 엔진 · 전례독서 뷰 · 캘린더 모듈을 받던 것(known-issues §6)을 고쳤다. 세 모듈은 이제 부팅 때 싣지 않고, `/calendar` · `/lectionary`에 처음 갈 때 `routing.js`가 동적 `import()`로 한꺼번에 불러온다. 재 보니 이득과 대가는 서비스 워커 캐시가 없는 **첫 방문에만** 있다 — 첫 화면이 느린 4G에서 0.39초 빨라지고, 첫 방문에 성서 화면에서 캘린더 탭을 열면 0.53초, 그 주소로 바로 들어오면 0.16-0.2초 늦어진다(바로 열기를 미리 받는 것은 WebKit 문제로 넣지 않았다 — 리뷰 반영 2회차). 재방문의 부팅 시간은 어느 쪽이든 측정 오차 안이었다 — 계획 때의 「앱을 열 때마다 해석 · 실행이 줄어든다」는 예상은 틀렸다(「확정·근거」 · 「검증」).

같은 PR에 넷을 더 담았다 — 받지 못했을 때의 화면(사용자 결정), 그 화면의 꼴을 DESIGN.md에 먼저 적고 기존 실패 화면을 거기에 맞춘 것, 본문 영역의 이름(덤), squash 머지 규칙의 문서화. 커밋은 항목마다 하나이고, 측정 뒤의 「한꺼번에 요청」이 하나 더 있다. 머지 전 `/code-review`(15건 + 덤 다섯)를 반영했다 — 다시 그릴 때의 번쩍임 · 세 벌로 갈라진 실패 화면 · 늦은 실패가 새 화면을 덮는 것 등(「리뷰 반영 (2026-10-18, 1회차)」). 고친 부분만 다시 본 2회차도 반영했다 — 1회차에서 넣은 바로 열기의 미리 받기는 WebKit에서 실패한 미리 받기가 그 탭을 막아 되돌렸다(「2회차」).

### ① 지연 로드 (`refactor:` 둘)

- **`routing.js`** — 정적 import 둘(`renderLectionaryView` · `renderCalendarView`)을 지웠다. 캘린더 분기는 `renderLoading()` 다음에 캘린더 · 전례독서 · 엔진 셋을, 전례독서 분기는 뷰와 엔진 둘을 `Promise.all`로 한꺼번에 요청하고(`import("./calendar.js")` …), 받은 뒤 `isStale()`을 본다 — 그사이 다른 화면으로 갔으면 조용히 끝난다. 지정자는 글자 그대로 둔다(아래 `sw.test.js`가 읽는다). 두 분기는 리뷰 반영에서 `openLazyView` 하나로 합쳤다.
- **한꺼번에 요청하는 까닭** — 첫 구현(커밋 「캘린더 · 전례독서 모듈을 그 화면에 처음 갈 때 불러온다」)은 `calendar.js` 하나만 import해, 브라우저가 그것을 받은 뒤에야 그 import(전례독서 · 엔진)를 찾아 요청했다. 첫 방문에 왕복이 한 번 더 들었다(캘린더 탭 → 표 느린 4G +676ms → 한꺼번에 +527ms). Chromium은 모듈 맵이 URL마다 한 번만 받아 의존 모듈을 겹쳐 적어도 그대로지만, WebKit은 앱 안에서 처음 갈 때 의존 모듈을 한 번 더 요청해 이득이 없다(2회차 리뷰 — known-issues §13). 사용자 결정(아래).
- **받는 것** — 캘린더 탭은 셋, 전례독서 화면은 뷰와 엔진 둘이다(캘린더는 필요 없다). 한 번 받으면 브라우저의 모듈 맵에 남아 화면을 옮겨도 다시 받지 않는다.
- **`index.html`** — 세 태그와 순서 주석 둘을 지우고, 왜 태그가 없는지를 주석 하나로 남겼다.
- **`sw.js`** — `SHELL_FILES`에는 셋을 남긴다 — 설치 때 미리 받아, 앱을 한 번 연 기기는 연결 없이도 그 화면의 모듈을 캐시에서 받는다. 교회력 표는 처음 쓸 때 캐시하므로 오프라인에서 열리는 것은 온라인에서 한 번 연 화면이다(첫 판의 「오프라인에서도 그 화면이 처음 열리도록」은 틀렸다 — 리뷰 12번). 세 줄을 한데 모아 이유를 주석으로 달았다.
- **받지 못했을 때** — 뷰의 실패 화면은 그 모듈 안에 있어 쓸 수 없다. 그래서 라우터가 같은 자리(뷰의 바깥 상자 `.calendar` · `.lectionary`) · 같은 제목(「캘린더」 · 「전례독서」) · 같은 머리와 뷰의 자료 실패 문구(「교회력 자료를 불러오지 못했습니다」 · 「전례독서 자료를 불러오지 못했습니다」)로 실패 화면을 그리고, 다음 행동 「다시 불러오기」를 단다 — 누르면 페이지를 새로 고친다. 부제는 「네트워크 연결을 확인한 뒤 「다시 불러오기」를 눌러 주세요.」(pitfalls §29 — 다음 할 일은 단추 이름으로). 공용 `renderError`는 쓰지 않는다 — 앞 화면의 헤더 · 제목을 남긴다(ADR-038 §3 「실패 · 범위」). 오디오 바도 내린다. 그리는 것은 `views.js`의 `renderLiturgicalLoadFailure`이고 두 화면 모듈도 같은 것을 쓴다 — 첫 판은 라우터의 사본 `renderViewLoadFailure`라 머리가 둘 다 집 단추였다(휴대폰에서 숨어 전례독서 쪽은 머리에 누를 것이 없었다). 리뷰 반영에서 하나로 모으고 전례독서는 「캘린더로」 꺾쇠로 고쳤다.
- **포커스 복원**(ADR-031 §5) — `route()`의 `finally`가 import를 기다린 뒤에도 같은 자리에서 돈다. 다시 그리기는 받아 둔 모듈로 기다리지 않고 그린다(`openLazyView`의 `loadedViews`) — 첫 판은 다시 그릴 때마다 `import()`를 기다려 「불러오는 중…」이 한 프레임 그려졌는데 여기에 「바뀌지 않는다」고 적었다(최종 상태만 보는 e2e로는 드러나지 않았다 — 리뷰 1번).

### ② 전체 화면 실패를 한 꼴로 (`style:`)

①의 「다시 불러오기」를 넣기 전에 DESIGN.md §6 「상태 컴포넌트」에 「전체 화면 실패」를 먼저 적었다(DESIGN.md 엄격 준수 — 새 규칙은 문서에 먼저). 머리 제목은 그 뷰의 것 · 아이콘 없는 빈 상태(제목은 안 된 것, 부제는 다음 할 일) · 다음 행동은 하나 `.state-action`(다른 화면으로 가면 링크, 그 자리에서 다시 하면 단추 — 같은 테두리 pill, 높이 `--touch-target` 44px). 이 규칙을 적고 보니 기존 실패 화면이 어긋나 있어, 글꼴과 단추 높이는 같은 커밋에서 맞췄다(둘 다 main부터 — 아래). 부제 · 다음 행동이 규칙과 어긋난 것(캘린더 자료 실패의 「이번 달 캘린더」가 실패한 달이 아니라 이번 달로 감 · 전례독서 실패 화면에 단추가 없음)과 규칙의 범위(성서의 잘못된 주소까지 넣었다)는 리뷰에서 드러나 리뷰 반영에서 맞췄다 — 첫 판의 「기존 두 화면을 맞췄다」는 글꼴 · 높이까지만 맞았다.

- **전례독서 실패 화면의 글자가 성서 본문 serif였다** — `.empty-state`가 글꼴을 정하지 않아 `.lectionary`(본문 serif를 그대로 받는 상자)의 글꼴을 물려받았다. 캘린더 실패 화면은 `.calendar`가 산세리프라 괜찮았다. `.empty-state`가 산세리프를 스스로 정한다. 전역 `.error`(`renderError`)도 같은 결함이라 함께 고쳤다.
- **캘린더 실패 화면의 「이번 달 캘린더」가 높이 26px 칩이었다**(§8은 44px) — 날짜 이동 줄의 「오늘」 pill(`.lect-today`)을 빌려 썼다. `.cal-error-link` + `.lect-today`를 `.state-action`으로 바꿨다(이제 높이 44px · 폭 104 → 126px). 날짜 이동 줄의 「오늘」은 그대로다.

### ③ 본문 영역의 이름 (`fix:` — 덤)

`<main id="app" aria-label="성경 본문">`은 모든 화면에서 같은 이름이라, #352 이후 「본문 바로가기」로 들어가면 캘린더 · 검색 · 설정에서도 「성경 본문」으로 읽혔다. 이름을 지웠다 — 페이지에 하나뿐인 main 랜드마크는 역할만으로 가려진다(근거는 아래). DESIGN.md §10에 규칙으로 적었다.

### ④ 머지는 squash (`docs:`)

사용자 결정(아래)을 CLAUDE.md 「브랜치 보호 / 작업 흐름」과 `docs/changes/README.md` 「규칙」에 적었다. 같은 절을 고치는 김에 실제 설정과 어긋난 두 곳도 맞췄다 — 필수 검사는 `Unit tests` 하나가 아니라 `Unit tests` · `Change ledger` 둘이고(REST로 확인), 검사를 통과한 PR head의 FF push는 보호 아래에서도 받아들여진다(#354 · data#33에서 실측). PR 본문 다시 맞추기는 REST로 적었다(`gh pr edit`은 GraphQL 오류로 실패한 적이 있다).

## 확정·근거

- **사용자 결정 — 받지 못했을 때는 「다시 불러오기」(새로 고침)** (2026-10-17). 계획 보고에서 셋을 보였다 — ① 「…앱을 다시 열어 주세요」(단추 없이) · ② 자료 실패와 같은 「…다시 열어 주세요」 · ③ 「다시 불러오기」 링크(새로 고침). 사용자 「불러오기 실패시 ③ 안이 좋겠다. DESIGN.md 검토 당연히 필요하고.」 버린 둘은 ADR-038 「검토한 대안 — 모듈을 받지 못했을 때」.
- **근거 — 브라우저는 실패한 동적 import를 기억한다.** HTML 표준은 실패한 모듈 가져오기를 모듈 맵에 남겨, 같은 지정자의 다음 import도 새로 고칠 때까지 같은 실패였다. 이를 바꾼 표준 변경 [whatwg/html #10327](https://github.com/whatwg/html/pull/10327) 「Don't cache HTTP errors in the module map」이 2026-07에 머지됐고(PR 페이지), 엔진마다 반영 중이다 — WebKit은 [bug 319492](https://bugs.webkit.org/show_bug.cgi?id=319492)가 2026-08-19 커밋(319474@main)으로 닫혔지만 실린 Safari 판은 확인하지 못했고, Chromium은 런타임 플래그 뒤(PR 페이지의 링크), Firefox는 [bug 2055211](https://bugzilla.mozilla.org/show_bug.cgi?id=2055211)의 상태를 확인하지 못했다(2026-10-17 확인). 그래서 화면을 다시 여는 것만으로는 풀리지 않을 수 있고, 새로 고침은 어느 브라우저에서나 모듈 맵을 비운다.
- **사용자 결정 — 모듈은 한꺼번에 요청한다** (2026-10-18). 측정 결과(아래 「검증」 — 이득 · 대가 모두 첫 방문에만, 재방문은 오차 안)를 보이고 셋을 물었다 — 한꺼번에 받기로 진행 · 한가할 때 미리 받기까지 · 지연 로드는 되돌림. 사용자 「한꺼번에 받기로 진행」. 버린 둘과 첫 구현(차례로 받기)은 ADR-038 「검토한 대안 — 모듈 로드」.
- **정정 — 계획 보고의 예상과 known-issues §6의 항목.** 계획 보고(2026-10-17)에서 「줄어드는 것은 앱을 열 때마다 해석 · 컴파일 · 실행하는 JS 약 210KB」라고 했는데, 재방문에 가까운 조건(로컬망 · CPU 4배 저속)에서 DOMContentLoaded −2ms · 스크립트 실행 −4ms로 오차 안이었다. 브라우저(V8)가 함수 본문의 컴파일을 처음 부를 때까지 미루기 때문으로 보인다(추정 — 측정은 숫자뿐이다). known-issues §6은 둘을 덜 적었다 — ① 모든 화면에서 실린 것은 전례독서 · 캘린더 둘이 아니라 엔진까지 셋이었다(원본 / gzip -9 — 엔진 112,795 / 36,023 · 전례독서 75,773 / 25,688 · 캘린더 21,414 / 8,444, 합 209,982 / 70,155바이트 — 부팅 때 싣는 메인 스레드 JS 969,355바이트의 약 22%). 「`lectionary.js`(약 70KB)」는 원본 크기였다. ② 「내려받는다」는 서비스 워커 캐시가 없는 첫 방문의 말이다 — 서비스 워커는 세 모듈을 오프라인용으로 미리 받으므로(설치 · 릴리스마다) 기기가 받는 바이트는 거의 그대로이고, 줄어드는 것은 첫 방문의 부팅 경로다.
- **사용자 결정 — 이제부터 브랜치에서 한 작업은 squash 머지**(2026-10-17, 앞 세션 — 「이제부터는 브랜치를 따서 작업한 건 스쿼시 머지를 하기로 하자」). 저장소 설정은 REST로 확인했다 — `squash_merge_commit_title` COMMIT_OR_PR_TITLE · `squash_merge_commit_message` COMMIT_MESSAGES · `delete_branch_on_merge` 켜짐 · 머지 커밋 꺼짐. 그래서 원장 `title:`이 main의 커밋 제목이 되고, 원장에 적은 커밋 SHA(이 원장의 것 포함)는 PR 페이지에만 남는다.
- **근거 — 하나뿐인 랜드마크에는 이름이 필요 없다.** W3C ARIA APG [「Landmark Regions」](https://www.w3.org/WAI/ARIA/apg/practices/landmark-regions/) 「General Principles of Landmark Design」 3단계: 「If a landmark is only used once on the page it may not require a label」, 같은 역할이 둘 이상이면 저마다 다른 이름(원문 확인 2026-10-17).
- **버전 어긋남은 좁다 — 서비스 워커가 있는 운영 페이지에서는.** 동적 import는 페이지를 연 뒤에 모듈을 받으므로, 그사이 배포가 끼면 새 모듈이 옛 모듈(이미 모듈 맵에 있는 `views.js` 등)과 이어질 수 있다. 서비스 워커가 제어하는 운영 페이지는 셋을 그 판의 셸 캐시에서 받고, 업데이트는 사용자가 「업데이트」를 눌러야 활성화되며(`SKIP_WAITING`) 활성화 직후 모든 탭이 `controllerchange`로 새로 고쳐진다(`js/app.js`) — 옛 셸 캐시를 지우는 것과 새로 고침 사이만 남는다. 남는 곳은 둘이다(리뷰 5번) — 서비스 워커가 없는 세션(지원하지 않음 · 설치 실패)과 dev 호스트다(`sw.js`의 `IS_DEV` — dev · localhost는 셸을 네트워크 우선으로 받고 `deploy.sh dev`는 버전을 올리지 않아, 배포 전에 연 탭이 새 모듈을 옛 모듈과 잇는다; dev 배포를 확인할 때는 새로 고친 뒤 본다). 이음이 깨지면 import가 거부돼 위 실패 화면이 되고, 이음은 되는데 맞지 않으면(새 모듈이 옛 도우미에 없는 함수를 부름) 그리다 오류가 난다 — 리뷰 반영에서 그것도 같은 실패 화면으로 보냈다(첫 판은 공용 오류 한 줄이라 앞 화면의 머리가 남았다). 둘 다 「다시 불러오기」가 고친다. 부제의 「네트워크 연결을 확인한 뒤」는 그대로 둔다 — 가장 흔한 원인이 연결이고, 어긋남이어도 할 일은 같다.
- **ADR-019는 고치지 않았다.** 결정(ESM 일괄 · 빌드 단계 0)과 어긋나지 않는다 — 「lazy load는 별도 의제」는 번들러를 두고 한 말이고(「검토한 대안」 표의 번들러 행), 네이티브 `import()`는 빌드를 더하지 않는다. 로드 지도는 `architecture.md` §4가 맡는다.
- **찾은 것(고치지 않음) — `scripts/serve.py`는 스크립트 위치가 아니라 실행한 폴더를 내준다.** `SPAHandler.directory`를 클래스에 적지만 `SimpleHTTPRequestHandler.__init__`이 인스턴스의 `directory`를 cwd로 덮는다. 저장소 루트에서 실행하는 한 문제없다(문서의 사용법이 그렇다). main 대조용 서버를 다른 폴더에서 띄우다 드러났다.
