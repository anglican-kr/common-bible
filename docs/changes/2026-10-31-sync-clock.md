## 요약

동기화는 북마크, 설정, 읽던 위치를 id마다 수정 시각(`_u`)으로 비교해 늦은 쪽을 남긴다. 그 시각을 기기 시계 그대로 기록해, 시계가 느린 기기에서 다른 기기의 편집을 받은 뒤 고친 것이 먼저 고친 사본에 덮어써졌다(known-issues §39). 이제 새 수정 시각은 기기 시각과 그 기록의 이전 수정 시각보다 1밀리초 늦은 시각 가운데 늦은 쪽이다(`store-v2.js _after`, ADR-011 Phase 2c 「수정 시각」). 수정 시각이 같으면 드라이브의 사본을 남긴다(Phase 2c 「같은 수정 시각」). 드라이브 파일이 그대로일 때(304) 올릴 변경은 가장 늦은 수정 시각 대신 문서 지문으로 판단한다(`fingerprint`, Phase 2i, known-issues §38 해소). 이 기기에 없는 북마크의 삭제 기록은 「다른 기기의 변경」으로 세지 않아, 앱을 열 때마다 뜨던 안내가 사라졌다. 고치기 전에 기기 시계에 기대지 않는 방법을 조사했고, 그 과정에서 구글이 앱에 ETag를 주지 않는다는 것을 확인했다(Phase 2j 추적 항목, known-issues §42).

## 확정 · 근거

- **먼저 조사했다**(사용자 지시 2026-10-30). 문제의 뿌리가 기기 시각끼리의 비교라는 지적에 따라, 코드를 고치기 전에 논리 시계, 실제 동기화 제품, 드라이브 API, 기준 사본 병합, 삭제 기록 정리를 조사했다. 채택하지 않은 방법과 다시 볼 조건은 ADR-011 「검토한 대안」의 「수정 시각」과 「304일 때 올릴 변경의 판단」에 있다.
- **개발 서버 시험**(2026-10-30, 사용자가 로그인해 진행). 내려받기 5번과 올리기 3번이 모두 200이었고 304는 없었다. 앱 코드가 읽은 `ETag`는 내려받기와 올리기 모두 `null`이었고, Network 탭의 내려받기 응답 헤더에는 `ETag` 줄이 없었다. `Date`는 브라우저에 노출됐다(`Access-Control-Expose-Headers`). 그래서 304 경로와 412 처리는 운영에서 실행되지 않는다.
- **병합 함수로 확인한 것**(2026-10-30, 실제 `store-v2.js`를 유닛 하네스로 실행).
  - known-issues §39가 재현됐다. 시계가 10분 느린 기기가 받은 뒤 고친 편집이 덮어써졌다.
  - 같은 까닭의 새 증상: 시계가 느린 기기에서 방금 받은 북마크를 지우면 다음 병합에서 다시 나타났다.
  - 30일 정리로 지운 삭제 기록은 다음 병합에서 드라이브 파일에서 돌아왔다.
  - 다른 기기의 올리기에 덮어써진 편집은 그 편집을 한 기기의 다음 동기화가 다시 올렸다.
  - `mergeDocs`는 문서 맨 위의 모르는 필드와 `bookmarks` 안의 모르는 필드를 버린다. 그래서 형식에 새 필드를 더하는 방법은 옛 버전과 함께 쓰기 어렵다.
- **기록마다 이전 수정 시각을 본다**(사용자 결정 2026-10-30). 문서 전체의 가장 늦은 시각을 기준으로 하면 304 경로까지 고쳐지지만, 시각이 빠른 기기 하나가 다른 기기가 새로 기록하는 시각을 모두 늦게 만들고, 서로 모르고 고친 두 편집의 결과를 상관없는 기록이 정한다. 삭제 기록은 지우는 북마크의 수정 시각보다 늦은 시각으로 기록한다. 새로 넣는 북마크와 저장된 삭제 기록에 가려진 북마크는 같은 id의 삭제 기록보다 늦은 시각으로 기록한다. 백업에서 되살린 북마크가 시각이 빠른 기기의 삭제 기록에 가려지지 않게 하려는 것이다. 숫자가 아닌 시각은 0으로 본다. 잘못된 값이 그 기록의 새 시각을 `NaN`으로 만들지 않게 하려는 것이다.
- **304 경로는 문서 지문으로 판단한다**(사용자 결정 2026-10-31). 지문은 북마크, 설정, 읽던 위치를 키 순서대로 적은 글의 cyrb53 해시다. 올린 갈래는 올린 문서의, 병합만 한 갈래는 병합 결과의 지문을 캐시한다. 지문을 계산하지 못하면(수천 단계로 중첩된 필드) 빈 값을 돌려주고, 304에서는 바뀐 것으로 보고 올린다. 옛 캐시 키는 지문을 쓰거나 캐시를 지울 때 지운다. 지문은 ETag보다 먼저 쓴다.
- **수정 시각이 같으면 드라이브의 사본을 남긴다**(사용자 결정 2026-10-31). 기록마다 늦은 시각으로 기록하면, 시각이 빠른 기기가 고친 기록을 시계가 느린 두 기기가 서로 모르고 고칠 때 둘 다 같은 시각을 받는다. 그전에 시각이 같을 때 쓰던 규칙(기기 id 순서)은 비교 상대가 마지막으로 올린 기기라, 한 기기만 자기 사본을 남기고 올리지 않아 기기마다 다른 사본이 남았다. 설정과 읽던 위치처럼 드라이브의 사본을 남기면 모든 기기가 같은 사본으로 맞춰진다. 내용으로 정한 순서로 고르고 다르면 올리는 안은 올리는 조건까지 바꿔야 해서 고르지 않았다. 같은 시각의 다른 사본은 「다른 기기의 변경」으로 세지 않는다. 목록은 병합할 때마다 다시 그리고, 옛 절 범위와 옮긴 표기가 같은 시각에 만나는 경우까지 안내할 일은 아니기 때문이다.
- **이 기기에 없는 북마크의 삭제 기록은 「다른 기기의 변경」으로 세지 않는다**(사용자 결정 2026-10-31, 이번 변경과 상관없는 기존 결함). 삭제 기록은 이 기기에 보이는 북마크를 지울 때만 센다. 다른 방법(기기에서 30일 정리를 하지 않기)은 삭제 기록 정책과 함께 정할 일이라 이번에 하지 않았다.
- **오프라인 기기는 드물다고 본다**(사용자 판단 2026-10-31). 비행기 모드의 휴대폰이나 와이파이에 연결되지 않은 노트북 정도가 예외라, 서로 모르고 고친 편집 같은 경우를 위해 설계를 복잡하게 하지 않는다.
- **정하지 않은 것**: 구글 시각 보정(known-issues §39 (나)), 삭제 기록 정책(§39), 쓰기 보호(§42). 기록마다 파일을 나누는 방법과 변경분만 담은 파일을 올리는 방법은 채택하지 않았다(ADR-011 「검토한 대안 — 수정 시각」).
- **일부러 바꾸지 않은 것**: 옛 절 범위 옮기기(`rewriteBookmarks`, pitfalls §38)와 옛 목록에서 읽은 항목(`_LEGACY_U`)은 수정 시각을 그대로 둔다. 「만든 날짜」와 「수정한 날짜」(`createdAt`, `updatedAt`)는 북마크 정렬에만 쓰는 값이라 기기 시각 그대로다. 저장되는 시각은 1970년부터 센 밀리초라 시간대와는 상관없다. 2^53 이상의 시각과 숫자 문자열 시각은 손상된 파일에서만 생겨 다루지 않았다. 지문 계산은 보통 사용자에게 1-2ms, 북마크 5,000개와 삭제 기록 5,000개에서 약 36ms다(데스크톱의 Node에서 잰 값).
- **함께 적은 것**: 북마크 개수에 상한을 두지 않고, 메모 길이 제한(known-issues §40)과 저장 공간이 차기 전에 미리 알리기(§41)를 할 일로 남겼다(사용자 결정 2026-10-31). 설정 화면에서 성서 본문을 모두 내려받는 기능(오디오 제외)도 할 일로 남겼다(§43, 사용자 결정 2026-10-31). 글쓰기(`writing.md` 「용어」): 「시계가 크게 앞선」은 「시각이 빠른」으로, 「시계가 늦은」은 「시계가 느린」으로 쓴다(사용자 교정 2026-10-31). 「빠른」은 기기에만 쓰고, 값과 사본에는 「늦은」, 「이른」을 쓴다. 「시각을 크게 찍는다」는 「이전 수정 시각보다 늦은 시각으로 기록한다」로 쓴다(사용자 결정 2026-10-31).

## 리뷰 반영

PR을 열기 전에 서브에이전트 셋이 따로 리뷰했다(2026-10-31). 시각 기록 동작, 지문과 304 경로, 테스트와 문서를 맡았고, 리뷰어에게는 코드와 요구만 주었다. 지적마다 코드로 확인한 뒤 고쳤다.

- **깊게 중첩된 필드에서 지문 계산이 호출 스택을 넘겨 동기화가 오류로 끝났다**(실행으로 확인, main은 정상). 계산하지 못하면 빈 값을 돌려주게 했다.
- **수정 시각이 같을 때 기기마다 다른 사본이 남았다**(실행으로 확인). 수정 시각이 같으면 드라이브의 사본을 남기게 했다(위 「확정 · 근거」).
- **30일 지난 삭제 기록이 있으면 앱을 열 때마다 안내가 떴다**(기존 결함, 실행으로 확인). 이 기기에 보이는 북마크를 지우는 삭제 기록만 세게 했다.
- **저장된 삭제 기록에 가려진 북마크를 같은 내용으로 다시 넣으면 계속 가려졌다**(옛 버전이 남길 수 있는 상태). 그런 북마크도 삭제 기록보다 늦은 시각으로 기록하게 했다.
- **테스트가 지키지 않는 동작**: 올리는 동안 고친 것(29c), 지문이 빈 값일 때(29d), 옛 캐시 키 지우기(32), 옮긴 북마크, 지문이 설정과 읽던 위치도 보는지를 테스트로 더했다.
- **문서**: 사실과 다른 문장 셋(아키텍처 문서의 캐시, ADR의 `If-Match` 동시성, ADR의 「maxU」)과 부정확한 문장 일곱을 고쳤다. 304 판단의 버린 후보를 ADR 「검토한 대안」에 더했다. 코드 주석 둘의 근거도 고쳤다.
- **고치지 않은 것**: 2^53 이상의 시각과 숫자 문자열 시각(손상된 파일에서만), 지문 계산을 ETag가 있을 때만 하는 것(보통 사용자에게 1-2ms라 급하지 않음).
