## 요약

동기화는 북마크, 설정, 읽던 위치를 id마다 수정 시각(`_u`)으로 비교해 늦은 쪽을 남긴다. 그 시각을 기기 시계 그대로 기록해, 시계가 느린 기기에서 다른 기기의 편집을 받은 뒤 고친 것이 먼저 고친 사본에 덮어써졌다(known-issues §39). 이제 새 수정 시각은 기기 시각과 그 기록의 이전 수정 시각보다 1밀리초 늦은 시각 가운데 늦은 쪽이다(`store-v2.js _after`, ADR-011 Phase 2c 「수정 시각」). 수정 시각이 같으면 드라이브의 사본을 남긴다(Phase 2c 「같은 수정 시각」). 드라이브 파일이 그대로일 때(304) 올릴 변경은 가장 늦은 수정 시각 대신 문서 지문으로 판단한다(`fingerprint`, Phase 2i, known-issues §38 해소). 이 기기에 없는 북마크의 삭제 기록은 「다른 기기의 변경」으로 세지 않아, 앱을 열 때마다 뜨던 안내가 사라졌다. 저장 공간이 차서 병합 결과를 저장하지 못하면 다른 기기의 변경이 없어도 알리고, 그 안내는 저장하지 못하는 동안 한 번만 띄운다. 고치기 전에 기기 시계에 기대지 않는 방법을 조사했고, 그 과정에서 구글이 앱에 ETag를 주지 않는다는 것을 확인했다(Phase 2j 추적 항목, known-issues §42).

## 확정 · 근거

- **먼저 조사했다**(사용자 지시 2026-10-30). 문제의 뿌리가 기기 시각끼리의 비교라는 지적에 따라, 코드를 고치기 전에 논리 시계, 실제 동기화 제품, 드라이브 API, 기준 사본 병합, 삭제 기록 정리를 조사했다. 채택하지 않은 방법과 다시 볼 조건은 ADR-011 「검토한 대안」의 「수정 시각」과 「304일 때 올릴 변경의 판단」에 있다.
- **개발 서버 시험**(2026-10-30, 사용자가 로그인해 진행). 내려받기 5번과 올리기 3번이 모두 200이었고 304는 없었다. 앱 코드가 읽은 `ETag`는 내려받기와 올리기 모두 `null`이었고, Network 탭의 내려받기 응답 헤더에는 `ETag` 줄이 없었다. `Date`는 브라우저에 노출됐다(`Access-Control-Expose-Headers`). 그래서 304 경로와 412 처리는 운영에서 실행되지 않는다.
- **병합 함수로 확인한 것**(2026-10-30, 실제 `store-v2.js`를 유닛 하네스로 실행).
  - known-issues §39가 재현됐다. 시계가 10분 느린 기기가 받은 뒤 고친 편집이 덮어써졌다.
  - 같은 까닭의 새 증상: 시계가 느린 기기에서 방금 받은 북마크를 지우면 다음 병합에서 다시 나타났다.
  - 30일 정리로 지운 삭제 기록은 다음 병합에서 드라이브 파일에서 돌아왔다.
  - 다른 기기의 올리기에 덮어써진 편집은 그 편집을 한 기기의 다음 동기화가 다시 올렸다.
  - `mergeDocs`는 문서 맨 위의 모르는 필드와 `bookmarks` 안의 모르는 필드를 버린다. 그래서 형식에 새 필드를 더하는 방법은 옛 버전과 함께 쓰기 어렵다.
- **기록마다 이전 수정 시각을 본다**(사용자 결정 2026-10-30). 문서 전체의 가장 늦은 시각을 기준으로 하면 304 경로까지 고쳐지지만, 시각이 빠른 기기 하나가 다른 기기가 새로 기록하는 시각을 모두 늦게 만들고, 서로 모르고 고친 두 편집의 결과를 상관없는 기록이 정한다. 삭제 기록은 지우는 북마크의 수정 시각보다 늦은 시각으로 기록한다. 새로 넣는 북마크와 저장된 삭제 기록에 가려진 북마크는 같은 id의 삭제 기록보다 늦은 시각으로 기록한다. 백업에서 되살린 북마크가 시각이 빠른 기기의 삭제 기록에 가려지지 않게 하려는 것이다. 숫자가 아닌 시각은 0으로 본다. 손상된 파일의 숫자 문자열 시각("9999999999999")에 1을 더하면 글자가 이어 붙어, 새 시각이 수천 년 뒤가 되기 때문이다.
- **304 경로는 문서 지문으로 판단한다**(사용자 결정 2026-10-31). 지문은 북마크, 설정, 읽던 위치를 키 순서대로 적은 글에서 계산한 짧은 값이다(cyrb53이라는 53비트 해시). 올린 갈래는 올린 문서의, 병합만 한 갈래는 병합 결과의 지문을 캐시한다. 지문을 계산하지 못하면(수천 단계로 중첩된 필드) 빈 값을 돌려주고, 304에서는 바뀐 것으로 보고 올린다. 빈 값은 캐시에 쓰지 않고 지난번 지문을 지운다. 옛 캐시 키는 지문을 쓰거나 캐시를 지울 때 지운다. 지문은 ETag보다 먼저 쓴다.
- **수정 시각이 같으면 드라이브의 사본을 남긴다**(사용자 결정 2026-10-31). 기록마다 늦은 시각으로 기록하면, 시각이 빠른 기기가 고친 기록을 시계가 느린 두 기기가 서로 모르고 고칠 때 둘 다 같은 시각을 받는다. 그전에 시각이 같을 때 쓰던 규칙(기기 id 순서)은 비교 상대가 마지막으로 올린 기기라, 한 기기만 자기 사본을 남기고 올리지 않아 기기마다 다른 사본이 남았다. 설정과 읽던 위치처럼 드라이브의 사본을 남기면 새 버전을 쓰는 모든 기기가 같은 사본으로 맞춰진다. 내용으로 정한 순서에 따라 남기고 드라이브와 다르면 올리는 안은 올리는 조건까지 바꿔야 해서 쓰지 않았다(ADR-011 「검토한 대안 — 같은 수정 시각」). 폴더의 펼침 상태만 이 기기의 값을 둔다(아래 「리뷰 반영」). 같은 시각의 다른 사본은 「다른 기기의 변경」으로 세지 않는다. 목록은 병합할 때마다 다시 그리고, 옛 절 범위와 옮긴 표기가 같은 시각에 만나는 경우까지 안내할 일은 아니기 때문이다.
- **이 기기에 없는 북마크의 삭제 기록은 「다른 기기의 변경」으로 세지 않는다**(사용자 결정 2026-10-31, 이번 변경과 상관없는 기존 결함). 삭제 기록은 이 기기에 보이는 북마크를 지울 때만 센다. 다른 방법(기기에서 30일 정리를 하지 않기)은 삭제 기록 정책과 함께 정할 일이라 이번에 하지 않았다.
- **오프라인 기기는 드물다고 본다**(사용자 판단 2026-10-31). 비행기 모드의 휴대폰이나 와이파이에 연결되지 않은 노트북 정도가 예외라, 서로 모르고 고친 편집 같은 경우를 위해 설계를 복잡하게 하지 않는다.
- **정하지 않은 것**: 구글 시각 보정(known-issues §39 「고치는 법」), 삭제 기록 정책(§39), 쓰기 보호(§42). 기록마다 파일을 나누는 방법과 변경분만 담은 파일을 올리는 방법은 채택하지 않았다(ADR-011 「검토한 대안 — 수정 시각」).
- **일부러 바꾸지 않은 것**: 옛 절 범위 옮기기(`rewriteBookmarks`, pitfalls §38)와 옛 목록에서 읽은 항목(`_LEGACY_U`)은 수정 시각을 그대로 둔다. 「만든 날짜」와 「수정한 날짜」(`createdAt`, `updatedAt`)는 북마크 정렬에만 쓰는 값이라 기기 시각 그대로다. 저장되는 시각은 1970년부터 센 밀리초라 시간대와는 상관없다. 병합에서 2^53 이상의 시각과 숫자 문자열 시각을 비교하는 일은 손상된 파일에서만 생겨 다루지 않았다(새 시각을 기록할 때는 숫자 문자열을 0으로 본다). 지문 계산은 보통 사용자에게 1-2ms, 북마크 5,000개와 삭제 기록 5,000개에서 약 36ms다(데스크톱의 Node에서 잰 값).
- **함께 적은 것**: 북마크 개수에 상한을 두지 않고, 메모 길이 제한(known-issues §40)과 저장 공간이 차기 전에 미리 알리기(§41)를 할 일로 남겼다(사용자 결정 2026-10-31). 설정 화면에서 성서 본문을 모두 내려받는 기능(오디오 제외)도 할 일로 남겼다(§43, 사용자 결정 2026-10-31). 기기 시계와 수정 시각을 적는 낱말 셋을 `writing.md` 「용어」에 더했다(사용자 교정과 결정 2026-10-31).

## 리뷰 반영

PR을 열기 전에 서브에이전트 셋이 따로 리뷰했다(2026-10-31). 시각 기록 동작, 지문과 304 경로, 테스트와 문서를 맡았고, 리뷰어에게는 코드와 요구만 주었다. 지적마다 코드로 확인한 뒤 고쳤다.

- **깊게 중첩된 필드에서 지문 계산이 호출 스택을 넘겨 동기화가 오류로 끝났다**(실행으로 확인, main은 정상). 계산하지 못하면 빈 값을 돌려주게 했다.
- **수정 시각이 같을 때 기기마다 다른 사본이 남았다**(실행으로 확인). 수정 시각이 같으면 드라이브의 사본을 남기게 했다(위 「확정 · 근거」).
- **30일 지난 삭제 기록이 있으면 앱을 열 때마다 안내가 떴다**(기존 결함, 실행으로 확인). 이 기기에 보이는 북마크를 지우는 삭제 기록만 세게 했다.
- **저장된 삭제 기록에 가려진 북마크를 같은 내용으로 다시 넣으면 계속 가려졌다**(옛 버전이 남길 수 있는 상태). 그런 북마크도 삭제 기록보다 늦은 시각으로 기록하게 했다.
- **테스트가 지키지 않는 동작**: 올리는 동안 고친 것(29c), 지문이 빈 값일 때(29d), 옛 캐시 키 지우기(32), 다른 폴더로 옮긴 북마크, 지문이 설정과 읽던 위치도 보는지를 테스트로 더했다.
- **문서**: 사실과 다른 문장 셋(아키텍처 문서의 캐시, ADR의 `If-Match` 동시성, ADR의 「maxU」)과 부정확한 문장 일곱을 고쳤다. 304 판단의 버린 후보를 ADR 「검토한 대안」에 더했다. 코드 주석 둘의 근거도 고쳤다.
- **고치지 않은 것**: 병합에서 2^53 이상의 시각과 숫자 문자열 시각의 비교(손상된 파일에서만), 지문 계산을 ETag가 있을 때만 하는 것(보통 사용자에게 1-2ms라 급하지 않음).

PR을 연 뒤 코드만 다시 리뷰했다(서브에이전트 하나, 2026-10-31). 여러 기기와 옛 버전 기기를 섞어 실제 코드로 돌려 보았고, 편집을 잃거나 동기화가 멈추는 결함은 없었다.

- **시각이 같아 드라이브의 사본이 남은 설정은 화면에 바로 반영되지 않는다**(실행으로 확인). 시각이 같은 사본은 「다른 기기의 변경」으로 세지 않으므로 설정을 화면에 적용하지 않는다. 늘 적용하는 방법은 오디오 막대를 다시 띄우는 등 부작용이 있어 쓰지 않았다. 시계가 느린 두 기기가 같은 설정을 서로 모르고 바꿔야 생기는 드문 경우라 그대로 두고 known-issues §39에 적었다.
- **삭제 기록과 시각이 같은 항목도 가려진 항목으로 본다**(실행으로 확인). 이 상태는 지금 코드로는 만들어지지 않고, 바꾸면 그 항목이 병합에서 사라지므로 그대로 두었다.
- **시각이 같을 때 기기 id 순서에 따라 남는다고 적은 옛 주석 둘**(`state-machine.js`, `bookmark-core.js`)을 고쳤다.

그다음 코드와 문서, 테스트를 따로 리뷰했다(서브에이전트 둘, 2026-10-31).

- **폴더를 펼치거나 접은 상태가 다음 동기화에서 되돌아갔다**(이번 변경이 만든 퇴행, 실행으로 확인). 펼침 상태는 내용이 아니라서 폴더를 열어도 수정 시각이 그대로라, 시각이 같아 드라이브의 사본이 남으면 드라이브의 옛 값이 돌아왔다. 시각이 같으면 폴더의 펼침 상태만 이 기기의 값을 두게 했다(사용자 결정). 다른 안은 ADR-011 「검토한 대안 — 같은 수정 시각」에 있다. 올릴지는 수정 시각만 비교해 정하므로, 펼침 상태가 달라도 두 기기가 번갈아 올리지 않는다.
- **저장 공간이 찬 기기에서 다른 기기의 변경이 없으면 동기화가 말없이 멈췄다**. 병합 결과를 저장하지 못하면 올리지 않는데, 다른 기기의 변경이 없으면 알리지 않았다. 이제 저장 공간이 차서 거절됐으면 알린다(사용자 결정, 문구는 ADR-015 D7).
- **지문을 계산하지 못하면 지난번 지문이 캐시에 남았다**. 다음 304에서 다시 계산하지 못해도 비교는 틀리지 않지만, 빈 값이면 캐시의 지문을 지우게 했다.
- **테스트가 지키지 않던 동작**: 병합한 뒤 올린 갈래의 지문 캐시(29e), 빈 지문을 캐시하지 않음(29d), 삭제 기록에 이미 가려진 북마크(72c), 숫자 문자열 시각, 폴더의 펼침 상태. 「숫자가 아닌 이전 시각」 테스트는 검사 코드가 없어도 통과했다(`"bad" > 0`이 원래 거짓이다). 다섯 테스트 모두 해당 코드를 되돌리면 실패하는 것을 확인했다.
- **문서**: 사실과 다르거나 빠진 것이 있던 문장 넷(아키텍처 문서의 기기 ID와 412, 북마크 주제 문서의 같은 시각, 장 파일 크기)을 고쳤다. 장 파일 크기로 적은 12MB는 디스크 사용량이었다. 같은 시각의 버린 안을 ADR-011 「검토한 대안」에 더했다. 「용어」 표에 어긋난 낱말(「고른다」, 「판」)과, 옛 목록 옮기기로도 읽히는 「옮긴 북마크」를 고쳤다. 앱이 모르는 필드만 바뀐 항목이 이제 다음 병합에서 드라이브의 사본으로 돌아간다는 것을 known-issues §15.5에 적었다(코드로 판단).

고친 뒤 코드와 문서, 테스트를 다시 따로 리뷰했다(서브에이전트 둘, 2026-10-31). 세 기기로 무작위 편집과 동기화를 180번 돌려, 두 기기가 번갈아 올리지 않고 펼침 상태를 빼면 모든 기기와 드라이브의 내용이 같은 것을 확인했다. 동작 결함은 낮음만 나왔다.

- **펼침 값이 없는 폴더는 다른 기기의 펼침 상태를 받았다**(실행으로 확인). 펼침 값 없이 가져온 폴더는 닫혀 보이는데, 다른 기기에서 그 폴더를 열면 이 기기에서도 열렸다. 이 기기에 펼침 값이 없으면 드라이브의 값도 받지 않게 했다(사용자 결정).
- **저장 공간 안내가 동기화할 때마다 떴다**(실행으로 확인, 장을 다섯 번 옮기자 다섯 번). 저장하지 못하는 상태가 처음 생길 때 한 번만 띄우고, 병합 결과를 저장하면 다시 띄울 수 있게 했다(사용자 결정). 다른 안은 ADR-015 「검토한 대안」에 있다. 문구는 다른 기기의 변경이 있든 없든 「저장 공간이 부족합니다. 불필요한 북마크를 지워야 동기화할 수 있습니다.」 하나로 했다. 다른 기기의 변경이 있을 때 쓰던 문구(2026-10-26)가 너무 길었다(사용자 결정). 북마크 화면에서 저장이 거절될 때의 안내도 「저장 공간이 부족합니다. 불필요한 북마크를 지운 뒤 다시 시도해 주세요.」로 말투를 맞췄다(사용자 결정).
- **테스트**: 저장 공간이 아닌 까닭으로 실패하고 다른 기기의 변경이 없을 때 알리지 않는 것을 지키는 테스트가 없었다(74a를 더함). 새 테스트 셋(74a, 75c, 펼침 값이 없는 폴더) 모두 해당 코드를 되돌리면 실패하는 것을 확인했다. 29e 주석의 사실과 다른 말과 숫자 문자열 테스트의 옛 이름을 고쳤다.
- **문서**: 2026-10-31 전의 버전은 지금도 기기 id를 읽어, 시각이 같을 때 남길 사본을 정한다. 그래서 「어느 기기도 기기 id를 읽지 않는다」와 「모든 기기가 드라이브의 사본으로 맞춰진다」를 고쳤다. known-issues §15.4 요약과 ADR-015 표의 옛 설명, 이 PR이 고친 파일에 전부터 남아 있던 「판」과 「고른다」도 고쳤다(다른 파일의 것은 문장 교정 반복 실행에 맡긴다). 손상된 파일의 글자 시각이 편집을 되돌리는 한계를 known-issues §39에 적었다(이번 변경이 만든 것은 아니다).

바뀐 코드만 다시 리뷰했다(서브에이전트 하나, 2026-10-31). 실제 저장소와 상태 기계가 저장 공간 하나를 함께 쓰는 시뮬레이터로 여러 기기를 흉내 냈다. 높음이나 중간 결함은 없었다.

- **테스트 빈틈 셋**: 드라이브 사본에 펼침 값이 없을 때 이 기기의 값을 지키는 것, 「불러오지 못했습니다」를 실패할 때마다 띄우는 것(74), 다른 까닭의 실패가 끼어도 저장 공간 안내를 다시 띄우지 않는 것(75c). 셋 모두 테스트를 더했고, 해당 코드를 바꾸면 실패하는 것을 확인했다.
- **옛 안내 문구를 인용한 주석**과 겹친 테스트 번호(새로 붙인 75b를 74a로)를 고쳤다.
- **안내가 뜬 뒤 조금 지워도 공간이 모자라면 동기화가 안내 없이 멈춘 채로 남는다**(실행으로 확인). 앱을 다시 열면 다시 알리고 드문 경우라 그대로 두었다(사용자 결정). 탭마다 따로 기억하는 것과 함께 sync 주제 문서와 ADR-015 D7에 적었다.
