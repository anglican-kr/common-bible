## 요약

앱을 시작할 때의 정리가 30일 지난 북마크 삭제 기록을 기기에서 지웠다. 동기화를 켠 동안은 다음 병합이 드라이브에서 그 기록을 다시 넣어 줄어드는 것이 없었고, 동기화를 끈 채 지운 북마크는, 지운 지 30일이 지난 뒤 동기화를 다시 켜면 드라이브에서 되살아났다(known-issues §39). 이제 앱을 시작할 때 북마크 삭제 기록을 지우지 않는다(ADR-011 Phase 2c 「삭제 기록 보존」). 정리 함수의 이름도 `sweepTombstones`에서 `sweepRetiredSettings`로 바꿨다.

삭제 기록을 나중에 안전하게 정리하려고 기준 목록 1단계를 더했다(ADR-011 Phase 2c 「기준 목록」). 마지막으로 내려받아 병합한 드라이브 파일에 살아 있던 북마크 id를, 이 기기가 그 파일에서 처음 본 날별로 묶어 이 기기에만 저장한다(`bible-drive-base-ids`). 1단계는 저장만 하고 병합 판단에는 쓰지 않으므로 병합 결과는 전과 같다. 병합 기록에 2단계 규칙(30일 규칙)이 지웠을 북마크 수만 남긴다. 구글 시각 보정은 하지 않고, 드라이브 파일의 쓰기 보호는 한계로 둔다(known-issues §42). 동기화 파일 형식과 수정 시각의 뜻은 바꾸지 않았다.

## 확정 · 근거

- **사용자가 정한 1단계**(2026-10-31).
  - 기준 목록은 저장만 하고 병합 판단에는 쓰지 않는다. 목록은 내려받은 파일에서 수정 시각이 삭제 기록보다 늦은 항목(폴더 포함)의 id와, id마다 이 기기가 그 파일에서 처음 본 날이다. 처음 본 날별로 묶는다.
  - 병합 결과를 저장한 뒤, 올리기 전에 쓴다. 차례는 병합 결과, 옛 키, 목록, 올리기, 캐시다. 올리기가 실패해도 쓴다. 드라이브가 그대로라는 응답(304), 새 파일 만들기, 옛 형식(v1) 파일을 새 형식으로 올리기, 병합 결과 저장 거절, 사이클 중단에서는 쓰지 않는다.
  - 「파일도 삭제」가 확인됐을 때, 목록 저장이 거절됐을 때, 북마크나 병합 결과의 저장(동기화 저장소, 옛 키)이 저장 공간 부족으로 거절됐을 때 지운다. 마지막 경우에는 목록을 지우고 한 번 더 저장한다. 동기화를 끌 때(「파일 유지」), 앱을 업데이트할 때, 계정을 바꿀 때는 남긴다.
  - 병합 기록에 30일 규칙이 켜져 있었다면 지웠을 북마크 수를 남긴다. 이 규칙은 목록의 파일 id가 지금 내려받은 파일과 같고, 북마크가 이 기기에는 살아 있고 드라이브에는 항목도 삭제 기록도 없으며, 목록에 있고 처음 본 지 30일이 넘었을 때다.
  - 기기의 30일 삭제 기록 정리에서 북마크 부분을 없앤다. 값을 `null`로 바꿔 둔 설정 키를 30일 뒤 지우는 부분은 남긴다.
  - 드라이브 파일 형식, 수정 시각의 뜻, 병합 결과는 바꾸지 않는다. 서버 시각 보정은 하지 않는다. 쓰기 보호는 한계로 둔다.
- **목록 형식**: `{"fileId": "<파일 id>", "at": <마지막으로 쓴 기기 시각>, "days": {"<날 번호>": ["id", …]}}`. 날 번호는 이 기기 시각으로 1970-01-01(협정 세계시)부터 센 날이다. 날짜 글자(「2026-10-31」, 10자)보다 짧고(5자) 빼기만으로 날 수를 센다. id마다 시각을 적는 것보다 작다. 30일 규칙에는 「처음 본 날」만 있으면 되므로 기준 목록의 형식은 2단계에서도 같다. 목록은 살아 있는 북마크의 id만 담으므로, 삭제 기록을 처음 본 날을 어디에 적을지는 정하지 않았다. 2단계 규칙은 「오늘의 날 번호 − 처음 본 날 번호 > 30」으로 세어, 날 단위로 줄인 값으로도 실제로 30일이 지났음을 보장한다. 북마크 id 하나에 약 22자가 든다. 북마크 500개면 10,919자(Safari의 셈으로 약 21KiB), 2,000개면 43,536자(약 85KiB)이고, 동기화 저장소와 옛 키를 합한 크기의 약 6%다(실제 `store-v2.js`로 잼).
- **분석 근거**(2026-10-30, 10-31, 실제 `store-v2.js`와 `state-machine.js`를 기기마다 따로 실행하는 시뮬레이터와 운영처럼 ETag 없는 가짜 드라이브).
  - 30일 정리는 드라이브의 삭제 기록을 줄이지 못했다. 200일 동안 드라이브의 삭제 기록이 그대로였고, 200일 꺼져 있던 기기가 돌아와도 지운 북마크가 되살아나지 않았다. 정리를 멈춰도 올리기 횟수와 안내는 같았고, 2일째부터 120일째까지 기기의 동기화 저장소 쓰기만 165번에서 120번으로 줄었다.
  - 정리가 북마크를 되살린 경우는 둘이다. 동기화를 끈 채 지운 북마크가 40일 뒤 다시 켜면 모든 기기에 돌아왔다. 드라이브가 ETag를 준다면 304 경로가 병합 없이 올려, 기기에서 지운 기록이 드라이브에서도 빠지고 60일 꺼져 있던 기기가 그 북마크를 되살렸다. 두 경우 모두 정리를 멈추면 지운 채로 남았다.
  - 서버 시각으로 잰 긴 기간(180일)이 지나면 삭제 기록을 지우는 안은 그보다 오래(200일) 꺼져 있던 기기가 돌아오면 북마크를 되살렸다. 그래서 2단계는 정해진 기간 대신 기준 목록으로 판단한다.
  - 서로의 편집을 받기 전에 시계가 10분 느린 기기가 3초나 300초 뒤에 같은 북마크를 고치면, 보정하지 않을 때는 먼저 고친 사본이 남고 보정하면 나중에 고친 사본이 남았다. 900초 뒤면 둘 다 나중에 고친 사본이 남았다.
  - 쓰기 보호가 없으면 겹친 동기화에서 먼저 올린 기기의 편집이 파일에서 빠지고, 그 기기의 다음 동기화가 다시 올렸다. 그 기기의 저장소를 비우면 편집이 사라졌다. 같은 기록을 두 기기가 고친 경우는 쓰기를 보호하는 경우(비교 후 교체)와 보호하지 않는 경우의 최종 결과가 같았다. 수정 시각이 늦은 사본이 남는다. 그래서 §42의 「그 편집의 시각이 덮어쓴 사본의 시각보다 이를 때」 문장은 쓰기 보호와 상관없는 일이라 고쳤다.
  - 올리기 직전에 `version`을 다시 묻는 안은, 다른 기기가 확인 전에 올리면 막았지만 확인 뒤 올리기가 끝나기 전에 올리면 그대로 겹쳤다. 겹칠 수 있는 시간이 내려받기 시간만큼만 줄어, §42의 「요청 한 번의 왕복으로 줄인다」 문장을 고쳤다. 내려받을 때의 `version`도 따로 물어야 해서, 요청이 동기화마다 하나, 올릴 때는 둘 늘어난다(구글 사용 한도로 5-10단위).
  - 기준 목록으로 판단하는 규칙 여섯 가지를 시뮬레이션했다. 목록을 바로 쓰기, 하루 조건, 수정 시각 30일 규칙, 수정 시각 30일 규칙에 하루 조건을 더한 것, 1단계(목록을 저장만 함), 30일 규칙이다. 목록을 바로 쓰면 덮어쓴 직후 북마크를 잃었다. 하루 조건은 덮어쓴 뒤 아무도 동기화하지 않은 채 하루가 지나거나 처음 켠 기기가 이틀 뒤 동기화하면 잃었다. 수정 시각 30일 규칙은 처음 켠 기기, 다시 켠 기기, 옛 목록의 항목이 겹친 동기화 안에서 올린 북마크를 잃었다. 30일 규칙은 시계가 10분 틀리거나 시각이 31일 빠른 기기까지 모든 경우에 잃지 않았고, 2단계를 시뮬레이션한 「다른 기기에서 지운 뒤 삭제 기록이 정리된 경우」에는 북마크를 지웠다.
  - 올린 문서로 목록을 만들면 덮어쓰기가 겹칠 때 북마크를 잃었다. 동기화를 끌 때 목록을 지우면 2단계를 시뮬레이션한 경우에 다른 기기에서 지운 북마크가 되살아났다. 파일 id를 보지 않으면 다시 만든 파일과 다른 계정의 파일에서 북마크를 잃었다.
- **반대 방향 판단을 채택하지 않은 까닭**: 이 기기에서 저장이 거절되거나 기기의 자료가 지워져 빠진 북마크를 지운 것으로 보면, 이 기기에서만 생긴 잃음이 모든 기기의 삭제로 퍼진다. 이 기기가 지운 북마크는 1단계부터 삭제 기록으로 남아 목록으로 판단할 일도 없다(ADR-011 「검토한 대안 — 삭제 기록과 기준 목록」).
- **진단 수를 「동기화 진단 정보」에도 보인다**: 병합 기록의 필드 이름은 주변 필드(`hadRemoteChanges`)처럼 `baseWouldDrop`으로 했다. 복사하는 진단 정보는 정한 필드만 찍으므로, 0이 아닐 때 찍게 했다(`debug-log.js`). 그래야 사용자가 보낸 진단 정보로 2단계를 정할 수 있다.
- **목록 저장이 거절되면 진단 기록의 오류 칸에 남긴다**(`BASE_IDS_SAVE_FAIL`). 캐시 저장 실패(`CACHE_SAVE_FAIL`)와 같은 방식이고, 거절되는 동안 한 번만 남긴다(「리뷰 반영」).
- **일부러 바꾸지 않은 것**: 병합 함수(`mergeDocs`)는 기준 목록을 받지 않는다. 「다른 기기의 변경」 판단에서 이 기기에 없는 북마크의 삭제 기록을 세지 않는 규칙은 그대로 둔다. 옛 버전이 지운 삭제 기록이 업데이트 뒤 첫 병합에서 다시 들어오기 때문이다. e2e의 가짜 드라이브(`FakeDrive`)는 운영과 달리 ETag를 보내고 `If-Match`를 지키지만 고치지 않고 그 사실만 적었다.
- **「은퇴 설정」이라는 말을 쓰지 않는다**(사용자 교정 2026-10-31). 「은퇴 설정」은 앱에서 없앤 설정 키의 값을 `null`로 바꿔 두는 일을, 영어 「retired setting」에서 옮겨 부른 말이라 어색했다. 새 이름을 짓지 않고 동작으로 쓰고(「값을 `null`로 바꿔 둔 설정 키」), 주제 문서처럼 사용자에게 보이는 변화를 말하는 곳에서는 이 내용을 뺐다(`docs/writing.md` 「용어」).

## 검증

- 새 테스트를 고치기 전 코드로 돌렸다. main의 `store-v2.js`, `state-machine.js`, `debug-log.js`, `app.js`, `types.d.ts`를 사본에 넣고 이 브랜치의 테스트를 실행했다.
  - 그대로 돌리면 새 테스트 17개 가운데 16개가 실패했다. 실패하지 않은 하나는 「304, 새 파일, v1, 저장 거절, 사이클 중단에서는 쓰지 않는다」(80번)라, 고치기 전에도 쓰지 않으므로 통과한다. 설정 키 정리 테스트는 함수 이름이 바뀌어 실패했다.

## 리뷰 반영

- 1회차(서브에이전트 둘, 2026-10-31). 코드 리뷰는 세 기기 무작위 시나리오 400개와 옛 앱을 섞은 250개를 PR 전과 후로 돌려, 의도한 개선 하나 말고는 결과가 모두 같았다. 문서와 테스트도 리뷰했다. 사용자는 코드 셋을 권장안대로 정했고, 낱말 둘을 정했다(2026-10-31).
  - **가져오기의 크기 검사가 기준 목록을 세지 않는다**: 실제 저장은 저장 공간이 차면 목록을 먼저 지우는데, 검사는 목록까지 세어 저장 공간이 거의 찬 기기에서 전에는 받던 가져오기를 거절했다(리뷰어 실측: 북마크 3,000개 기기에서 182개분). 셀 때 뺄 키는 동기화 저장소가 알려 준다(`projectedBookmarksEntry`의 `givesUp`).
  - 이를 고치며 옛 키(`bible-bookmarks`) 쓰기도 저장 공간 부족으로 거절되면 목록을 지우고 한 번 더 쓰게 했다(구현하며 정함). 검사를 통과한 덮어쓰기를 WebKit의 셈으로 저장해 보니, 동기화 저장소는 목록을 둔 채 저장되고 옛 키 쓰기만 거절되어 옛 키에 이전 목록이 남았다. 앱은 동기화 저장소를 읽으므로 화면은 같지만, 검사를 통과한 목록은 두 사본 모두 저장되게 했다.
  - **기록하는 날이 뒤로 가지 않는다**: 새 id의 날은 오늘과 이전 목록의 `at`의 날 가운데 늦은 쪽이고, `at`도 작아지지 않는다. 기기 시각이 실제보다 이른 동안(배터리가 다 닳은 뒤 시계가 1970년으로 돌아간 휴대폰) 처음 본 북마크가 시계를 고친 뒤 실제보다 오래된 것으로 세어져, 2단계의 30일 보호가 작동하지 않을 수 있었다. 이전 목록이 다른 파일의 것이어도 `at`은 이 기기가 본 시각이라 그대로 쓴다(구현하며 정함).
  - **목록 저장 실패 기록은 처음 한 번만 남긴다**: 저장 공간이 거의 찬 기기에서 동기화마다 쌓여, 진단 정보의 오류 칸(20줄)에서 앞선 오류(`DELETE_UNCONFIRMED` 등)를 밀어냈다. 저장 공간 안내(`_storageFullNoticed`)와 같은 방식으로, 목록을 저장하면 다시 남길 수 있다.
  - **테스트의 빈틈**(변이로 찾음): 80번의 새 파일 만들기가 만든 파일 id를 받는 운영 경로를 지나게 했다. 목록 저장이 거절된 사이클(80a번), 같은 id가 두 날에 있을 때 이른 날을 남기는 것, 삭제 기록을 365일이 지나도 지우지 않는 것을 더했다.
  - **사실과 다른 조건**: 「동기화를 30일 넘게 끈 동안 지운 북마크는 다시 켜면 되살아났다」를 「동기화를 끈 채 지운 북마크는, 지운 지 30일이 지난 뒤 다시 켜면 되살아났다」로 고쳤다. 55일 끄고 50일째에 지우면 되살아나지 않는다(리뷰어가 main 코드로 확인).
  - **문서**: ADR-011 「검토한 대안」에 빠진 둘(기기에서 30일 지난 삭제 기록 지우기, 서버 시각으로 잰 긴 기간)을 더했다. 뒤엣것은 main의 `sync.md`에 후보로 있던 것을 이 PR이 지웠다. 삭제 기록의 크기(지우면 저장소는 줄어든다), 「형식은 1단계와 같다」의 범위(삭제 기록을 처음 본 날은 목록에 없다), ETag 경우의 시제, 이 PR 때문에 낡은 문장(`state-machine.test.js`의 주석, `bookmark.md` §41, ADR-040 「크기 검사」의 「30일 둔다」, `bookmark.test.js`의 주석), 시뮬레이션하지 않은 판단의 출처 표시를 「(코드로 판단)」으로, 「는다」와 「준다」를 「늘어난다」와 「줄어든다」로 고쳤다. 작업 방식이던 원장의 `pr:` 줄 설명은 `workflow.md`로 옮겼다.
  - **낱말**(사용자 결정 2026-10-31): 「흉내 실험」은 「시뮬레이션」, 「흉내 장치」는 「시뮬레이터」로 쓰고 `writing.md`의 그대로 쓰는 말에 더했다. 실험 후보에 붙인 순번 이름(규칙 가, 규칙 나, 규칙 다)은 없애고 내용을 담은 이름으로 바꿨다. 수정 시각 30일 규칙, 1단계(목록을 저장만 함), 30일 규칙이다. 2단계 규칙은 처음에 「처음 본 지 30일 규칙」으로 지었다가 「30일 규칙」으로 줄였고, 채택하지 않은 규칙은 늘 「수정 시각 30일 규칙」으로 써서 구별한다(사용자 결정 2026-11-01).
  - 검증: 새 테스트 6개와 넓힌 테스트 셋을 고치기 전 코드(HEAD)의 사본에서 돌렸다. 코드 셋을 보는 새 테스트 5개(`storage.test.js` 둘, `store-v2.test.js`의 날짜, `state-machine.test.js` 80a, `bookmark.test.js`의 기준 목록)와 `givesUp`을 더 확인하게 한 `store-v2.test.js`의 크기 계산 테스트가 실패했다. 빈틈을 메운 테스트(이른 날, 365일, 80번의 새 파일 id)는 고치기 전에도 통과한다. 동작을 바꾸지 않았기 때문이다. 유닛 1,466개 가운데 1,465개 통과(실패 0, 건너뜀 1), 타입 검사 두 설정 오류 0, 고친 줄과 원장의 문장 검사 `particle`, `tilde`, `term` 0, 사실 토큰 비교(`--strict-counts`) 사라진 토큰과 줄어든 토큰 0이다. 이 리뷰를 반영한 뒤에도 작업 폴더를 8093에 띄워 `test_drive_sync.py`, `test_drive_sync_ios.py`, `test_bookmark*.py` 140개를 다시 돌려 모두 통과했다(3분 59초).
- 2회차(서브에이전트 하나, 2026-11-01, 1회차를 반영한 코드만). 북마크를 잃거나, 동기화가 멈추거나, 병합 결과가 바뀌는 새 경로는 없었다. 찾은 것은 셋이다.
  - **목록을 빼야만 들어가는 가져오기는 저장하기 전에 목록을 지운다**(사용자 결정 2026-11-01): 1회차 반영으로 검사는 목록을 세지 않지만, 저장은 저장 공간이 찰 때만 목록을 지운다. 그래서 검사 한도와 실제 한도 사이의 가져오기는 목록을 남긴 채 저장되어, 가져온 뒤 남겨 둘 64 KiB를 목록이 썼다.
