## 요약

캘린더 보기를 월간과 목록 둘로 정한 결정을 ADR-038에 적고, 그 첫 단계로 월간과 전례독서의 상단 바를 같은 세 칸으로 맞췄다.

- 상단 바의 제목 자리에 왼쪽부터 「오늘」, ‹ 달이나 날짜 ›, 보기 전환 단추가 있다. 「캘린더」 글자와 표 위의 달 이동 줄은 없어졌다.
- ‹ ›는 두 화면에서 같은 자리에 있어, 달력에서 날짜를 눌러도 움직이지 않는다.
- 전례독서의 오른쪽 단추는 그 날짜가 든 달로 간다. 월간의 오른쪽 칸은 목록 보기를 만들 때 채운다.
- 목록 보기는 뒤따르는 PR에서 나누어 만든다(화면, 무한 스크롤, 위치 기억).

## 확정 · 근거

사용자 결정(2026-11-07)이고, 시안은 Design 캔버스로 먼저 보였다.

- 주간과 일간은 만들지 않는다. 목록은 무한 스크롤이고 평일까지 모든 날을 보이며, 줄의 글은 전례독서 제목 영역과 같다. 그래서 목록은 독서 묶음을 받는다.
- 세 화면의 상단 바가 같아야 한다. 배치는 권장안인 「오늘」 왼쪽, 글자 가운데, 전환 단추 오른쪽이다. 11월 5일의 「오늘은 달 오른쪽」을 대신한다. 전환 단추와 「오늘」의 자리를 맞바꾸는 안은 검토하고 버렸다.
- 전례독서 상단 바의 오른쪽 단추는 11월 3일에 뺀 위 단계 단추를 되살린 것이다.
- 목록에서 캘린더 탭을 다시 누르면 목록을 유지하고 오늘 줄로 간다. 코드는 목록 보기 PR에서 넣는다.
- 데스크톱은 전례독서에도 성서 목록 집 단추를 둔다. 상단 바를 같게 하려는 것이고, 탭 바가 없어 이 단추가 입구다.

구현하며 정한 것.

- 달을 옮기면 새 달은 맨 위부터 보인다. 달 이동이 상단 바로 올라와 스크롤한 자리에서 누를 수 있어졌기 때문이다. 전례독서의 날짜 이동과 같다.
- 시안의 계산값과 실제 값이 달라 실측으로 고쳤다. 기본 글자는 휴대폰에서도 18px이고, 「2027년 12월」은 116px이다. 글자 칸은 6.5rem, 짧은 표기일 때 5rem이다. 머리 폭 15.9rem 이하에서 짧은 표기로 바뀌어 폭 320px의 기본 글자는 전체 이름이다. 전에는 폭 356px 이하에서 짧은 표기였다.
- 시안에서 말한 「26.11」 표기는 넣지 않았다. ‹ ›의 탭 영역을 글자 칸과 8px씩 겹치고 전환 단추를 44px로 고정하니, 폭 320px에 글자 24px에서도 「2027.12」와 「26.12.24」가 세 칸과 겹치지 않는다.

일부러 바꾸지 않은 것.

- 실패 화면의 상단 바는 그대로다. 달 이동이 없으니 화면 이름이 제목이다.
- 설정의 기본 캘린더(ADR-041 §10)는 이 PR에 없다. 목록을 만든 뒤에 다시 정한다.

## 검증

- 유닛 `node --test tests/unit/*.test.js`: 1,562건 통과. 타입 검사 `npm run typecheck`: 통과.
- e2e(작업 폴더 서버, Chromium): 상단 바를 그리는 파일을 골라 170건 통과했다. `test_calendar_view.py`, `test_lectionary_view.py`, `test_liturgical_lazy_load.py`, `test_navigation.py`(집 단추), `test_tabbar.py`(캘린더 탭), `test_a11y_axe.py`(두 화면의 접근성)다. 더한 시험은 두 화면의 칸 자리 비교, 오른쪽 단추, 데스크톱 집 단추, 달 이동 뒤 맨 위다.
- 폭 320, 390, 1280px과 글자 18, 20, 24px에서 칸의 좌표를 재어 겹침과 가로 넘침이 없고 ‹ ›가 두 화면에서 같은 자리인 것을 확인했다. 스크린샷도 눈으로 보았다.
- 전체 e2e와 WebKit은 돌리지 않았다. 전체는 13분쯤 걸려 관련 파일만 골랐다(사용자 결정 2026-11-07). 상단 바는 `:has()`와 `@container`를 쓰는데 둘 다 전에도 같은 자리에 쓰던 것이다. 실제 아이폰 확인은 dev 배포 때 한다.
