# feat: 교회력 엔진 B1 이동 패스 · 선택 봉헌 — computeTransfers · seed · activated · 픽스처 소비 · 불변식 · 골든 (ADR-037 §6 · PR 3 둘째)

## 요약

교회력 엔진 B1 의 **둘째 GitHub PR** 이다(PR 3 은 둘로 냈다 — 첫째 #341). 설계서 §6.5 의 연도 단위 이동 패스와 §6.2 의 선택 봉헌을 구현해 엔진 A1 · B1 이 끝났다. `resolveDate` 의 반환 형태는 그대로다 — 비어 있던 패스(PR 2 의 `EMPTY_PASS`)가 채워졌을 뿐이다.

- **이동 패스** `computeTransfers(index, year, seed, activated)`(→ R-6.5-year-pass).
  - 0단계 — 선택 봉헌 선색인(`optionalObservancesOf` — `nearby_sunday` · `sunday_0102_0108` · `sunday_1030_1105` · `easter7_sunday`, 목적지가 그날 자신이면 없음). 켜진 것은 원래 날짜에서 `transferred_out`(`to`), 목적지에서 `transferred_in`(`from`) — 밀린 것이 아니라 택한 것이라 `displacedBy` 가 없다. 꺼진 것은 목적지 주일에 `optional` 로만 얹는다.
  - 1단계 — 날짜 순 충돌 이동. 순위는 승자 판정과 같은 `rankCandidates`(정렬 키 `compareCandidates`)이고, 「밀렸다」는 `settle` 과 같은 함수 `displacerOf(ranked, c, staying)` 다 — 이 PR 에서 `staying` 을 받게 일반화했다(떠난 패자는 남은 패자를 밀지 못한다). 의사 코드의 `rankByPrecedence` · `properCandidates` · `outranks` 는 새로 만들지 않았다.
  - 빈 날(`isFree`) — 그날의 고유 후보 · `guard` 가운데 더 높은 것이 없고(같은 값은 민다 — 연쇄), 도착이 없다(선착순). **해를 넘긴 날짜에서는 이 패스가 이미 그리로 넘긴 도착과 다음 해 좌석(`nextYearSeats`)을 함께 본다** — 의사 코드는 「대신」이라 12월 축일 둘이 같은 1월 날에 앉을 수 있었다(아래 확정 ②).
  - `MAX_SHIFT` 30 을 넘으면 옮기지 않고 `proper` 로 남기며 `defects` 에 적는다. 옮길 고유 관측일이 없는 날은 출발이 생기지 않으므로 순위를 세우지 않고 건너뛴다(결과는 같다).
  - 연도는 코드가 넘기는 값이라 정수가 아니면 throw 한다 — `NaN` 이면 날짜 루프가 끝나지 않는다(설계서 §2 ③, 아래 「발견한 모순」).
- **캐시** `transfersOf(index, y)` — `y−1` 의 seed 없는 임시 패스로 `y` 에 넘어온 도착(spill)을 얻어 seed 로 넘긴 **완전한 패스만** `transferCache` 에 둔다(임시 패스는 넣지 않는다). 두 패스가 같은 활성화 집합을 본다.
- **선택 봉헌 활성화** — 모듈 상태 `activatedOptionals`(블록 밖, 테스트는 prelude) · v1 은 빈 집합. `setActivatedOptionals(ids)`(export)는 집합이 **실제로 바뀔 때만** 패스 캐시를 비운다(C-6.2-7). 채우는 설정 UI 는 범위 밖이다(설계서 미결15).
- **픽스처 소비** — `liturgical-engine.data.test.js` 가 `transfers` · `optionals` 를 소비하고 `winners` 에서 건너뛰던 둘(마티아 · 어린이들 색)을 켰다. activation 케이스는 그 케이스의 `activated` 로 캐시를 새로 만들고 끝나면 ∅ 로 되돌린다. `alsoYears` 는 날짜 단언의 연도만 바꿔 되풀이하고, 연도 범위 단언 `neverDeparts`(1900~2100)를 받는다. skip 둘(T-2032-02-12-ash-wednesday-seollal — 미결13 · T-2024-04-08-annunciation-holy-monday — 미결32)은 그대로다.
- **비워 둔 `displacedBy` 를 채웠다**(엔진 계산값 — 부활절 날짜로 손검증).
  - 루가 2026-10-18 = 연중 29주일 → `grid:ordinary-29-sunday`.
  - 2038 부활 = 4.25 — 마르코는 부활대축일 → `t-부활대축일`(실제 후보 우선), 필립보와 야고보 5.1 은 부활 토요일 → `guard:easter-octave`.
  - 2043 부활 = 3.29 — 수태고지 3.25 는 성 수요일 → `guard:easter-octave`.
  - 2035 부활 = 3.25 — 수태고지는 부활대축일 → `t-부활대축일`.
- **전 연도 검사(불변식)와 이동 결과 기록 파일(골든 덤프)**
  - 불변식 — 1900~2100 의 모든 해에서 「옮겨 온 축일은 그날의 승자다」 · 「성주간 · 부활 8일에는 도착하지 않는다」 · 「이동은 15일을 넘지 않는다」 같은 성질(검토 문서 I-1 ~ I-8)을 단언한다. I-9 는 공개 스위트의 C-4.2-2 · C-4.3-1 · C-4.5-1 이 같은 범위에서 본다.
  - **골든 덤프가 무엇인가** — 엔진이 1900~2100 년에 옮기는 축일 **981건을 한 줄에 하나씩 전부 적어 둔 기록 파일**이다(검토 문서 부록 A 의 I-10). 테스트는 엔진이 새로 계산한 결과를 이 파일과 **글자 그대로** 비교한다 — 나중에 코드나 데이터를 고쳤을 때 어느 해의 이동이 하나라도 바뀌면 테스트가 깨지고, 바뀐 줄이 diff 로 보인다. 「골든」은 「비교 기준으로 삼는 원본」이라는 테스트 용어다.
  - **정답표가 아니라 지금 결과의 사진이다** — 무엇이 맞는지의 기준은 사람이 책자 · 달력으로 확인한 픽스처(`*.cases.json`)이고, 골든 덤프는 결과가 바뀌면 알려 주는 경보 장치다. 바뀐 것이 의도한 변경이면 `UPDATE_GOLDEN=1` 로 파일을 다시 만들고, PR 에서 바뀐 줄을 읽어 확인한다.
  - 한 줄 읽는 법 — `2025-11-30 → 2025-12-01  d1130-사도-성-안드레아  by:t-대림1주일  shift:1` 은 「사도 안드레아 축일이 11.30 에서 12.1 로 옮겨졌고, 밀어낸 것은 대림 1주일이며, 하루 옮겨졌다」이다. 줄은 원래 날짜 순(같으면 옮겨 간 날짜 · id 순)이고, 칸 사이는 두 칸이다.
  - 이 PR 이 정한 것 — 파일 `tests/fixtures/liturgical/transfers-1900-2100.golden.txt`, 범위 1900~2100(불변식과 같다), 선택 봉헌은 모두 끈 상태(`activated = ∅`), 981줄 · 약 89KB. 맨 윗줄(data 서브모듈 sha · 설정)은 기록용이라 비교하지 않는다.
  - 데이터 저장소가 이동 결과를 바꾸는 수정을 내면, 앱의 `sync-data.yml` 이 동기화 PR 을 열기 전에 이 비교에서 멈춘다(facts 불일치와 같은 방식) — 그때는 앱 저장소에서 골든 덤프를 다시 만든 PR 이 데이터 포인터를 올린다.

## 확정·근거

- **사용자 결정(2026-10-11, 코드 전에 물어서 받음)**
  1. PR 을 나누지 않는다. 시제품(1900~2100 실데이터)에서 불변식 위반 · 픽스처 실패가 0 이었고, 패스만 먼저 내면 실데이터 검증 없이 머지된다.
  2. **`isFree` 는 해를 넘긴 1월 날짜에서 「올해 이미 옮겨 앉힌 도착」과 「다음 해 좌석」을 함께 본다**(의사 코드의 「대신」 정정). 합성 표로 재현했다 — 2029-12-30 주일에 X 가 밀리고 12.31 은 명절이 막을 때, 「대신」이면 X 와 12.31 의 Z 가 둘 다 2030-01-01 에, 「함께」면 1.1 · 1.2. 실데이터에는 1900~2100 에 해를 넘긴 이동이 없어 결과는 같다 — 12월에 옮겨지는 축일 다섯(니콜라 · 성모시태 · 스테파노 · 요한 · 어린이들)은 늦어도 12.29 에 앉고, 12.29~12.31 의 축일은 전부 prec 7 · `transferable: false` 다. 설명이 처음에 어려웠다는 지적을 받아 실제 예로 다시 설명하고 재확인받았다.
  3. ADR-037 을 「승인됨 — 구현 완료」로 바꾼다(ADR-036 머리의 「이동 패스 남음」도 B1 완료로).
  4. **본당 축일(주보성인 축일 · 성당축성일 전부)은 기념일과 같은 성격이라 축일 이동에 영향을 주지 않는다** — 밀지도 막지도 옮겨지지도 않는다. 해를 넘긴 이동의 출처로 「본당 · 교구 축일」을 든 내 보고를 사용자가 교정했고, 성당축성일(기도서 주요축일 C)까지 포함하는지 물어 확인받았다. 그래서 패스는 지역 축일을 보지 않고 캐시는 본당 설정에 의존하지 않는다 — `docs/coding-pitfalls.md` §20 · ADR-036 「성인력 보완 영역」(1) · 「검토한 대안 — 성당축성일 · 영명축일의 품계」 C · 설계서 §4.9.
  5. 분당성당 축성일은 9.13(주보성인 성 마르코 — 사용자 제공). 데이터 `liturgical/calendar/parishes.md` 에 분당성당 행이 없어(154 본당 · 이력에도 없음) 새 행 `서울 · 09.13 · 축성 · 마르코` 로 넣었다 — **이 PR 을 연 뒤 별도 data PR**(data#29)로 냈다. 엔진은 `local-observances` 를 아직 싣지 않아 앱 동작과 무관하다.
  6. **축성일 · 축복일 모두 옮기지 않는다.** data#29 를 만들다 파서가 등급표대로 축성 본당 142곳을 `transferable: true` · `next_day` 로 내고 있던 것을 찾아 물었고, 그 data PR 에서 고치기로 했다(`transferable: false` · `transfer_to: null`, 등급은 그대로).
  7. **교구 설립일도 옮기지 않고, 다른 축일과 겹치면 기념만 한다** — 추수감사주일과 같은 `transfer_to: "commemorate_only"`(data#29). 엔진은 이것을 옮기지 않고 밀리면 `commemorated` 로 낸다. 확정 ④ · ⑥ · ⑦ 은 pitfalls §20 · ADR-036 「성인력 보완 영역」(1) · 「검토한 대안」 C · 설계서 §4.9 에 적었다.
- **내가 정해 보고한 방침**: 함수 이름 · 인자(인덱스를 첫 인자로 — 조회 블록의 순수 규약), 옮길 것이 없는 날 건너뛰기, `transferCache` 는 설계대로 연도 키(인덱스 하나용 — 합성 표 테스트는 표마다 새 vm 컨텍스트), `alsoYears` 되풀이(README 가 허용), C-6.5-16 강화, I-9 처리, X-2 · X-3 은 외부 대조를 하지 않았으므로 열어 둔다.
- **실데이터 사실(1900~2100, `activated = ∅`)**: 이동 981건. 최장 15일은 수태고지가 성지주일인 해(1923 · 1934 · 1945 · 1956 · 2018 · 2029 · 2040)와 **요셉이 성지주일인 해**(1967 · 1978 · 1989 · 2062 · 2073 · 2084) — 설계서의 「실측(2025~2050) 최장 15 · 요셉 14」는 범위가 2025~2050 이라 그대로 맞다. 12월 → 1월 이동 0건(I-7a · I-7b 는 빈 spill 끼리 같다 — 깊이 1 의 경로는 합성 표가 본다). 정본은 골든 덤프다.

## 발견한 모순 · 후속

- **의사 코드 `isFree` 의 「대신」** — 위 확정 ②. 설계서 §6.5 의사 코드 · `isFree` 문단을 고쳤다.
- **설계서 §7 ⑥ 연도 경계 합성 케이스** — 「sanctoral 표(12.31 주요축일 + 그날을 차지하는 prec 1)」로 적혀 있었는데, 고정일끼리는 동시 봉헌이라 옮기지 않는다. 점유자는 가변이어야 한다(유닛은 12.31 이 성탄 1주일인 2028).
- **§7 이동 패스 행의 「합성 표는 연도 경계 한 건만」** — 같은 행이 합성 케이스를 여럿 들고 있어 어긋났다. 실제 연도로 만들 수 없는 경로를 열거했다.
- **§6.5 의 정렬 키 재진술 둘** — `guard` 문단의 「(유효 precedence, 범주 사다리, id)」와 `isFree` 문단의 「품계 순 → id 순」에 고유 본기도 키가 빠져 있었다(PR 3 첫째 2회차와 같은 종류). 정본(→ R-6.2-tie-ladder · R-6.2-first-come)을 가리키게 했다.
- **C-6.5-16 의 「31일 연속」 표는 상한 31 을 가르지 못한다** — 31일째도 막혀 있으면 상한이 31 이어도 `defects` 다. 31일째를 비우고, 30일째에 앉는 짝을 더했다.
- **테스트 헬퍼가 잘못된 날짜로도 패스를 먼저 만들어 날짜 루프가 끝나지 않았다** — `resolve("bad")` 의 연도가 `NaN` 이고 연도 접두사가 「0NaN-」으로 맞물렸다. 공개 래퍼는 날짜를 먼저 검사해 닿지 않는 길이지만, 엔진이 정수가 아닌 연도에 throw 하게 하고(§2 ③) 헬퍼도 래퍼처럼 날짜를 먼저 본다.

- **사람이 확인하기 쉽게 — 2025~2035 이동 58건**(검토 문서 부록 A 의 「사제용 발췌」). 골든 덤프의 그 해 줄을 한국어 이름과 요일로 풀었다. 「근거」 열은 그 이동이 **픽스처 케이스** — 2024~2026 책자 · 서울교구 달력 · lectionarypage · 같은 부활절 날짜의 미국 성공회 배치로 확인한 기대값 — 인지, 규칙으로만 나온 결과(**「규칙대로」 30건**)인지를 가른다.
