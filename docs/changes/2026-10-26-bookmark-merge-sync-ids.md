## 요약

PR #359 리뷰에서 넘긴 북마크 결함 둘(known-issues §15.1, §15.2)을 고쳤다.

- **§15.1**: 가져오기의 「병합」이 지금 목록에 있는 id의 폴더를 안의 것까지 건너뛰어, 백업의 그 폴더에 든 새 북마크가 들어오지 않았다. 이제 그 폴더 안으로 들어가 새 항목만 더한다. 폴더의 자리와 이름은 지금 목록을 따른다(ADR-011 Phase 2a가 처음부터 적어 둔 「폴더 `children` 재귀 처리」).
- **§15.2**: 동기화 저장소가 북마크를 일반 객체에 부모 id별로 묶어, `toString` 같은 기본 속성 이름의 id가 하나만 있어도 새로 고친 뒤 장 화면부터 그려지지 않았다. 묶음을 `Map`으로 바꾸고, id로 찾는 곳은 객체가 직접 가진 항목만 보게 했다.

## 확정 · 근거

- §15.4(저장이 실패해도 성공 안내가 뜬다)는 다음 PR로 낸다. 안내 문구, 안내를 보일 동작, 두 사본 가운데 하나만 저장된 경우의 처리를 사용자가 정해야 해서다. 사용자는 §15.1과 §15.2를 먼저 하고 순서대로 가기로 했다(2026-10-26).
- §15.2에 적어 둔 고치는 법은 부모별 묶음 한 곳만 가리켰다. 같은 문서를 id로 찾는 곳을 모두 보니 같은 원인의 결함이 셋 더 있어 함께 고쳤다(pitfalls §4에 사례와 규칙 한 줄을 더했다).
  - 기기끼리 병합(`mergeDocs`)할 때 한쪽에만 있는 그런 id의 북마크가 빠졌다. 없는 쪽에서 물려받은 함수를 읽어 삭제 시각이 NaN이 되었고, 그래서 양쪽 모두 지운 것으로 보았다. 그 id의 삭제 기록도 같은 까닭으로 사라졌다.
  - 그런 id의 북마크를 지워도 삭제 기록이 남지 않아(`_docWithBookmarks`), 다른 기기에서는 지워지지 않았다.
  - 그런 id의 삭제 기록만 새로 받은 동기화를 바뀐 것이 없다고 보아(`state-machine.js`), 「다른 기기에서 변경된 데이터를 불러왔습니다」 안내가 뜨지 않았다. 저장은 바르게 되었다.
- `__proto__` id는 저장하지 않는다. 일반 객체에 넣으면 항목이 되지 않고 프로토타입이 바뀌므로, 병합이 이미 건너뛰던 것(PR #309)에 맞췄다. 그 id의 폴더는 폴더만 빼고, 안의 항목은 폴더가 있던 자리로 올려 저장한다. 전에는 폴더만 사라지고 자식은 부모 id `__proto__`로 남아, 그런 자식이 있으면 목록을 읽다 멈췄다. 옛 판이 남긴 그런 자식은 맨 위에서 읽는다(아래 「리뷰 반영」 1).
- 가져오기 검사(ADR-040)가 기본 속성 이름의 id를 빼는 규칙은 그대로 둔다. 고치기 전 판을 쓰는 기기는 동기화로 받은 그 id에서 여전히 멈춘다.
- 병합은 넘겨받은 지금 목록을 바꾸지 않도록 폴더를 복사해 새 항목을 더한다. 파일 안에서 같은 id가 다시 나오면 북마크는 앞의 것만 들이고, 폴더는 뒤 폴더의 새 항목을 앞 폴더에 더한다. 가져오기 검사가 같은 id를 먼저 빼므로 화면에서는 생기지 않는다.
- 병합 결과도 64단을 넘지 않는다(ADR-040 「폴더」). 64단보다 깊어질 새 폴더는 안의 것까지 들이지 않고, 대화상자가 알리는 뺀 개수에는 들지 않는다. 앱이 내보낸 파일로는 생기지 않는 경우라 알림 문구는 더하지 않았다.
- 「목록을 읽을 수 없게 된 뒤에도 덮어쓰기로 되살린다」 e2e는 `toString` id로 그런 목록을 만들었다. 저장소가 그 id를 읽게 되어, 저장된 문서에 깨진 항목(`null`)을 넣어 재현한다.

## 검증

- 고치기 전 코드에서 새 테스트가 실패하는 것을 먼저 보았다. 유닛은 동기화 저장소 7개, 병합 3개, 상태 기계 1개이고, 리뷰 반영에서 더하거나 바꾼 5개(병합 깊이, 본 기록 둘, `__proto__` 둘)도 그렇다. e2e 둘(`toString` id가 있어도 장 화면과 목록이 그려진다, 같은 id 폴더에 새 북마크가 더해진다)은 main 코드에서 실패했다(장 화면 대기 시간 초과, `['bm-c'] != ['bm-c', 'bm-b']`).
- 유닛 `node --test tests/unit/*.test.js`: 리뷰 반영 뒤 1,382개 가운데 1,381개 통과, 실패 0, 건너뜀 1(데이터 서브모듈을 받은 작업 폴더에서 돌렸다). `npm run typecheck` 통과.
- e2e `pytest tests/e2e/`: 379개 가운데 377개 통과. 실패한 둘은 실행 환경 탓이었고, 환경을 바로잡아 다시 돌리니 통과했다.
  - 8080 포트는 다른 작업 폴더의 서버가 쓰고 있었다. 그래서 이 브랜치의 작업 폴더를 8091에 띄우고, 주소만 바꾼 테스트 사본으로 돌렸다.
  - 긴 주소 테스트(`test_navigation.py`의 repeated-segments): 8091 서버를 시스템 Python 3.13으로 띄워, 255자를 넘는 경로를 확인하다 예외가 나고 빈 응답이 갔다. pyenv 3.14.6으로 다시 띄우니 통과했다.
  - 반절 표 테스트(`test_every_half_verse_follows_the_table`): 테스트 파일 위치를 기준으로 `data/`를 읽는데 사본 옆에 없었다. 링크를 두니 통과했다.
  - 상태 기계를 고친 뒤 `test_navigation.py`, `test_bookmark_export_import.py`, `test_drive_sync*.py`를 다시 돌려 88개가 통과했다.
  - 리뷰 반영 뒤 `test_bookmark*.py`, `test_drive_sync*.py`를 다시 돌려 122개가 통과했다.

## 리뷰 반영

1회차(서브에이전트 리뷰, 2026-10-26). 넷 모두 재현한 뒤 고쳤다. 사용자가 PR을 연 뒤 리뷰를 요청했다.

1. `__proto__` 폴더의 자식이 보이지 않는 데서 끝나지 않고 모든 기기에서 지워졌다. 다음 저장이 그 자식을 삭제 기록으로 바꿨다. main에서는 목록을 읽다 멈췄지만 데이터는 남아 있었다. 그 폴더의 항목을 폴더 자리로 올려 저장하고, 옛 판이 남긴 자식은 맨 위에서 읽게 했다.
2. 같은 id의 폴더를 지금 목록의 자리에서 채우게 되어, 병합 결과가 64단을 넘을 수 있었다(64단 목록 위에 63단 파일이면 127단). 새 폴더가 64단보다 깊어지면 안의 것까지 들이지 않는다.
3. 원장의 「같은 id가 다시 나오면 앞의 것만 들인다」가 폴더에는 맞지 않았다. 문장을 고쳤다.
4. 「최근 본 순」 정렬이 본 기록(일반 객체)을 id로 찾아, 본 적 없는 `toString` id의 정렬 값이 NaN이 되었다. 본 기록을 지우는 함수도 같은 조회였다. `Object.hasOwn`으로 고치고, pitfalls §4의 규칙을 「같은 값을 키로 쓰는 다른 객체도 본다」로 넓혔다.

- 1을 고치다 더 넓은 경우를 찾았다. 한 기기가 지운 폴더에 다른 기기가 넣은 북마크도 부모를 잃고, 다음 저장 때 지워진다. main에서도 같아 이 PR에서는 고치지 않고 known-issues §32로 남겼다. 어디로 살릴지 정해야 한다.
