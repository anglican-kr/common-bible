## 요약

문장 교정 반복 실행의 둘째 단계다. 한 번 실행할 때 할 일을 프로젝트 스킬(`.claude/skills/prose-batch/SKILL.md`)로 적었다. 교정할 파일 194개를 순서대로 적은 진행 목록(`tools/prose/progress.md`)도 만들었다. 다음은 이 스킬로 주제 문서 12개를 교정하는 시험 묶음이다.

## 확정 · 근거

- **한 번에 한 가지만 한다.** 열린 교정 PR이 있으면 그 PR의 검토 의견만 반영하고, 없으면 새 묶음을 연다. 그래서 열린 교정 PR은 늘 하나다. 하루에 여는 교정 PR은 4개까지다(사용자 결정 2026-10-26).
- **묶음의 크기**: 한글 줄 400줄 안팎이고, 진행 목록의 같은 절에 있는 파일끼리 묶는다. 600줄이 넘는 파일은 교회력 검토 문서(1,263줄) 하나이고, 절마다 나눠 한다. 대상은 194개 파일, 13,775줄이라 묶음은 35개쯤이다.
- **교정은 파일마다 서브에이전트가 한다.** 모델은 Sonnet이고, 시험 묶음의 결과를 보고 다시 정한다(사용자 결정 2026-10-26).
- **기계 검사로 막지 못하는 위험을 지시문에 적었다.** 주석 외 코드 비교(`same-code`)는 주석을 모두 지우고 견준다. 그래서 뜻이 있는 주석을 바꿔도 잡지 못한다. JSDoc 태그와 `@ts-` 지시문은 타입 검사가 읽고, `// ── BEGIN X ──` 표시는 유닛 테스트가 코드를 잘라 쓰는 데 쓴다. 이런 주석은 바꾸지 말라고 적었다. JS 파일을 고친 묶음은 타입 검사와 유닛 전체도 돌린다.
- **검토 의견은 사용자 계정이 단 것만 따른다**(사용자 결정 2026-10-26). 교정이 규칙이 될 만하면 `docs/writing.md`와 검사 목록에 더하고, 이미 머지된 묶음에 같은 쓰임이 있으면 함께 고친다.
- **교정 PR의 원장은 「먼저 보실 곳」을 맨 앞에 둔다.** 사용자가 뜻이 달라질 수 있는 고침부터 검토하게 하려는 것이다. 원장 검사(훅과 CI)는 절이 있는지만 보므로 순서를 바꿔도 된다. `docs/changes/README.md`에 적었다.
- **진행 목록은 저장소 안에 둔다.** 클라우드 실행은 이전 실행을 기억하지 못하므로, 교정 PR마다 목록의 상태를 함께 바꾼다.
- 데이터 저장소의 문서는 이 목록에 넣지 않았다. 넣을지는 앱 저장소를 마친 뒤에 정한다.

## 검증

- 스킬에 적은 `gh` 명령 셋을 실제 저장소에서 실행했다. 열린 교정 PR 찾기와 열린 PR이 바꾸는 파일 목록은 지금 둘 다 비었다. 오늘 연 교정 PR 세기는 0을 냈고, 같은 날짜 조건이 오늘 연 PR 9개를 모두 찾았다.
- 새로 쓴 파일(스킬, 진행 목록, 도구 설명과 문서에 더한 줄)은 문장 검사에서 0건이다.
- 문서 검사(`node --test tests/unit/docs-*.test.js tests/unit/liturgical-fixtures.test.js`): 31개 가운데 30개 통과, 1개는 작업 폴더에 데이터 서브모듈이 없어 건너뛰었다. 경로 검사가 스킬에 적은 브랜치 이름의 예(`docs/` 뒤의 글자)를 문서 경로로 읽어 실패했으므로, 그 문장을 바꿨다.
