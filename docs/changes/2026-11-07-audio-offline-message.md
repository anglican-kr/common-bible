## 요약

오프라인에서 오디오가 있는 장을 열면, 그 장의 mp3가 이 기기에 저장되어 있지 않을 때 오디오 바에 「오디오 파일을 준비 중입니다.」가 나왔다. 실제로는 인터넷에 연결하면 바로 들을 수 있는 장이다(known-issues §26). 이제 이 경우에는 「인터넷에 연결하면 들을 수 있습니다.」를 보인다. 오디오가 없는 장(1,492장 가운데 178장)은 그대로 「준비 중」이다. 안내와 판단 차례는 ADR-016 D4에 있다.

## 확정 · 근거

- **사용자 결정(2026-11-07).** 오프라인에서 오디오가 있는 장의 mp3가 이 기기에 없어 불러오지 못하면 「인터넷에 연결하면 들을 수 있습니다.」를 보인다. 오디오가 없는 장은 그대로 「준비 중」이고, 캐시에서 지운 장과 한 번도 듣지 않은 장은 구별하지 않는다. ADR-016 D4가 적었던 「오프라인 캐시에서 정리되었습니다」 안내는 한 번도 듣지 않은 장에는 사실과 다른 문장이라 고르지 않았다(ADR 「검토한 대안」 H).
- **구현하며 정한 것.**
  - **두 안내는 아이콘이 같다.** 새 안내에 아이콘을 따로 만들지 않았다.
  - **오류의 종류로 판단하지 않는다.** Chromium 148에서 재 보니 404, 연결이 끊긴 요청, 오프라인이 모두 `MediaError.code` 4이고 문구도 같았다.
  - **오프라인인지는 서버에 물어 판단한다.** `navigator.onLine`은 인터넷이 없는 와이파이에서도 `true`다. 그래서 `true`일 때는 HEAD 요청을 보낸다. 서비스 워커는 GET만 처리하므로 HEAD 요청은 서버로 바로 가고, `cache: "no-store"`라 브라우저의 HTTP 캐시도 쓰지 않는다. mp3 본문을 받지 않으므로 데이터를 거의 쓰지 않는다. `navigator.onLine`이 `false`이면 묻지 않는다.
  - **5초 안에 응답이 없으면 오프라인으로 본다.** 인터넷이 없는 와이파이에서는 요청이 오래 멈출 수 있다. 확인하는 동안 오디오 바에는 플레이어가 그대로 보인다.
  - **오디오 목록은 캐시의 사본을 먼저 읽는다.** 서비스 워커가 설치할 때 셸 캐시에 저장하고, 온라인으로 앱을 열 때마다 새로 저장하는 사본이다. 네트워크부터 읽으면 인터넷이 없는 와이파이에서 서비스 워커의 네트워크 우선 처리를 오래 기다릴 수 있다. `js/manifest-sync.js`가 IndexedDB에 남기는 스냅숏은 앱을 처음 열고 동기화가 끝나기 전에는 없어서 쓰지 않았다.
  - **목록에 없는 장과 저장된 장은 서버에 묻지 않는다.** 두 경우는 연결해도 들을 수 없어 답이 「준비 중」으로 정해진다.
  - **확인하는 동안 장을 옮기면 그 확인을 버린다.** 확인은 플레이어의 `AbortController` 신호를 받는다. 다른 장으로 옮기거나 플레이어를 끄면 기다리던 요청을 멈추고, 결과가 나와도 안내를 보이지 않는다.
- **일부러 바꾸지 않은 것.**
  - 서버가 응답했는데도 재생하지 못하면(연결이 잠깐 끊겼다 돌아온 경우 등) 지금처럼 「준비 중」이다. 다시 불러오기는 이 결함의 범위 밖이다.
  - 확인하는 동안 플레이어의 재생 단추는 그대로 눌린다. 누르면 화면에는 변화가 없고 콘솔에 오류(「The element has no supported sources.」)가 하나 남는다(측정). 오프라인이면 확인은 캐시를 두 번 읽는 동안에 끝난다.

## 검증

- 유닛 `node --test tests/unit/*.test.js`: 1,621건 통과(새 `tests/unit/audio-player.test.js` 13건). 타입 검사 `npm run typecheck`: 통과.
- e2e(작업 폴더 서버 8093, Chromium) 다섯 파일 69건이 통과했다. 바꾼 코드를 지나는 파일만 골랐다.
  - `test_audio.py` 10건: 새 시험 4건과, 문구까지 확인하게 고친 404 시험.
  - `test_audio_controls.py` 6건: 오디오 오류 처리를 막고 재생 조작을 본다.
  - `test_tabbar.py` 17건: 오디오 바와 탭 바를 함께 본다.
  - `test_liturgical_lazy_load.py` 11건: 화면을 옮기며 오디오 바를 숨긴다.
  - `test_navigation.py` 25건: 장을 옮길 때마다 오디오 오류가 나고 확인이 실행된다.
- 고치기 전 코드(`origin/main`)에서는 새 e2e 셋이 실패했다. 오디오가 있는 장의 오프라인 안내, 인터넷이 없는 와이파이, 경쟁 상태 시험이다. 경쟁 상태 시험은 고치기 전 코드가 서버에 묻지 않아 준비 단계에서 실패했다.
- 고친 코드를 하나씩 망가뜨려 시험이 실패하는지 보았다. `navigator.onLine`만 보기, 오디오 목록 확인 빼기, 저장 확인 빼기, 요청에 신호 전달 빼기는 유닛 시험이 잡았다. 신호 중단 확인 빼기는 e2e 경쟁 상태 시험이 잡았다. 앞의 둘은 e2e도 잡았다.
- **오프라인 e2e가 서비스 워커를 쓰지 않는 까닭.** 이 컴퓨터의 Chromium(Playwright 1.60)은 로컬 개발 서버에서 `sw.js` 설치를 끝내지 못한다. 셸 파일 58개 가운데 서버가 받은 요청은 3개뿐이고, 설치가 멈춘다. 원인 추정과 잰 결과는 `docs/topics/cache-release.md`의 known-issues §6.1에 적었다. 그래서 오프라인 e2e는 다른 시험처럼 서비스 워커를 막고, 서비스 워커가 하던 두 일(장 본문을 내주는 일과 오디오 목록의 사본을 두는 일)을 시험이 대신한다. mp3 요청은 실제로 오프라인에서 실패한다(`context.set_offline`).
- 실제 서비스 워커가 있는 오프라인과 iPhone Safari(WebKit)에서는 확인하지 않았다. 전체 e2e는 사용자 결정(2026-11-07)대로 돌리지 않았다.

## 리뷰 반영

- **Copilot 리뷰(2026-11-07, 줄 의견 1건): 오디오 목록의 본문 읽기가 5초 제한과 장을 떠날 때의 중단 밖에 있었다.** 목록의 캐시 사본이 없어 네트워크에서 받을 때, 요청을 감싸는 함수(`_fetchWithin`)가 응답 머리를 받자마자 타이머와 플레이어의 중단 신호를 풀었다. 그래서 서버가 머리만 보내고 본문에서 멈추면 5초가 지나도 안내가 나오지 않았고, 장을 떠나도 본문 읽기가 남았다. 코드로 확인했다. 이제 이 함수가 응답을 읽는 함수를 받아 본문을 다 읽을 때까지 둘을 지킨다. 유닛 2건(본문이 멈춘 목록, 목록을 받는 중에 장을 떠남)을 더했고, 고치기 전 코드에서 둘 다 실패하는 것을 확인했다. 고친 뒤 유닛 1,623건, 타입 검사, `test_audio.py`와 `test_audio_controls.py` 16건이 통과했다.
