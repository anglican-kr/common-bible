# fix: 옛 판이 저장한 북마크 절 범위를 지금 표기로 옮긴다

## 요약

known-issues §18 첫 항목을 고쳤다. 사용자가 PR #365 작업 중에 「이전 버전 북마크와 하위 호환성도 고민해야 할텐데, 그건 다음 PR에서...」라고 했다. 2026-04-25부터 06-06(#205)까지의 앱은 여러 줄인 절의 일부 줄을 고르면 줄 글자를 그대로 저장했다. main(`f358691`)은 그 글자를 화면에 그대로 보였다. `parseVerseSpec`이 읽지 못하는 표기(「16aa」 · 「7-8a」)는 모아 읽기에서 사라졌고, 합치면 그 절이 빠졌다. main(`f358691`)을 Chromium에서 띄우고, 옛 표기 북마크를 가져오기 파일로 들여 재현했다.

| 저장값 | main의 목록 참조 | main의 모아 읽기 | main의 합치기(1절을 더함) | 이 PR |
|---|---|---|---|---|
| 이사 10 「16aa」 | 이사 10:16aa | 북마크가 사라짐 | 「1」(16절이 빠짐) | 「16」, 합치면 「1,16」 |
| 나훔 1 「7-8a」 | 나훔 1:7-8a | 북마크가 사라짐 | | 「7-8」 |
| 마태 10 「35a」 | 마태 10:35a | 35절 전체 | | 「35」 |
| 창세 27 「20a,20c」 | 창세 27:20a,20c | 20절 전체 | 「1,20a,20c」 | 「20」, 합치면 「1,20」 |
| 1사무 24 「5a」 | 1사무 24:5a | 5ㄱ과 5ㄴ | | 「5」 |
| 이사 7 「8a」 | 이사 7:8a | 8ㄱ과 8ㄴ | | 「8」 |

main에서는 북마크를 열 때의 강조도 달랐다. 「16aa」 · 「7-8a」 · 「8a」는 강조 없이 장만 열렸고, 「35a」는 35절의 첫 줄만 강조했다. 여러 북마크 가운데 합칠 곳을 고르는 대화상자에도 「(35a절)」처럼 글자가 보였다.

### 변경

- **옮기는 규칙.** `verse-spec.js wholeVerseSpec`이 글자를 떼어 절 번호로 만들고 구간으로 잇는다(「3a,5-7」 → 「3,5-7」, 「34,35a」 → 「34-35」). 줄 단위 범위는 절 전체가 된다. 장 데이터는 쓰지 않는다. 글자가 없는 범위와 「all」, 가져오기 검사를 통과하지 못하는 표기는 그대로 둔다.
- **옮기는 때.** 셋이다.
  - 앱을 시작할 때 첫 화면을 그리기 전에 두 사본(`bible-bookmarks` · `bible-bookmarks-v2`)을 옮긴다(`app.js` → `bookmark-core.js migrateStoredBookmarks` → `storage.js rewriteBookmarks`). 이름 규칙에 성서 목록이 필요하므로, 저장된 목록에 옮길 것이 있을 때만 `loadBooks()`를 기다린다. 옮긴 뒤의 시작은 기다리지 않는다.
  - 가져오기는 검사를 통과한 항목을 크기 검사 전에 옮긴다(ADR-040).
  - 동기화 결과는 저장하기 전에 옮긴다(`state-machine.js _applyMergedDoc`, ADR-011). 그때 성서 목록이 아직 없으면 받은 대로 저장하고, 목록을 받은 뒤 저장된 목록을 옮긴다.
- **수정 시각.** 옮길 때 항목의 수정 시각(`_u`)은 올리지 않는다. `rewriteBookmarks`는 `saveBookmarks`를 거치지 않고 두 사본을 고쳐 쓰며, 동기화를 깨우지 않는다. 다음 저장도 내용이 같아 시각을 올리지 않는다.
- **이름.** 그 북마크의 옛 기본 이름(「책 장:옛 저장값」)과 정확히 같을 때만 새 기본 이름으로 바꾼다(`bookmark-core.js migrateLegacyBookmark`). 저장 대화상자와 합치기가 짓는 이름이 이 형식이다.
- **저장과 합치기.** 북마크 저장은 새 함수 `verseNumberSpec`으로 적는다. 고른 줄의 글자를 모두 떼고 절 번호를 구간으로 잇는다.
  - 여러 줄인 병합 절은 「7-8」로 저장된다(known-issues §17, main은 「7」). 앞뒤 절과도 이어진다. 나훔 1장에서 1절부터 2ㄴ까지 고르면 「1-9」이고, main은 「1-7,9」였다. 한 줄인 병합 절도 이어진다(「16,17-18,19」 → 「16-19」). 덮는 절은 같다.
  - `collapseSegmentedVerses`는 지웠다.
  - 합치기(`mergeVerseSpecs`)도 이 함수로 적는다. 옛 표기를 절 번호로 읽고, 범위를 절마다 펼치지 않는다. 그래서 검사 없이 들어온 큰 범위에 합쳐도 멈추지 않는다(known-issues §15).
- 주소 문법과 저장 문법(ADR-010 · 040)은 바꾸지 않았다. 주소의 옛 표기(`/isa/10/16aa`)는 예전처럼 장만 연다.

## 확정 · 근거

- 재현 뒤 네 가지를 물었고, 사용자가 모두 권장안을 골랐다(2026-10-22). pitfalls §38에 적었다.
  - 범위는 (가)다. 저장값을 옮긴다. 읽는 쪽만 고치는 (나)와 둘 다 하는 (다)는 고르지 않았다.
  - 수정 시각은 올리지 않는다.
  - 북마크 이름은 옛 기본 이름과 같을 때만 바꾼다. 지시문의 권장은 「그대로 둔다」였다. 재현에서 한 행에 「이사 10:16aa」와 「이사 10:16」이 함께 보이게 된다는 점과, 합치기가 이미 제목을 다시 짓는다는 점을 보고 권장을 바꿨다.
  - known-issues §17도 함께 고친다. 이미 저장된 「7」은 그대로 둔다.
- 구현 중에 더한 것이 둘이다. 진행 중에 사용자에게 알렸다.
  - 동기화 결과도 옮긴다. 처음에는 동기화로 받은 옛 표기가 다음 시작 때 옮겨지리라 보았다. 그러나 수정 시각이 같은 두 사본은 `mergeDocs`가 기기 id 순서로 하나를 고른다. 그래서 드라이브에 옛 표기가 남아 있으면 기기에 따라 동기화할 때마다 옛 표기가 돌아온다. 실제 `mergeDocs`에 두 사본을 넣어 확인했다. 기기 id가 드라이브 쪽보다 뒤인 기기는 옛 표기를 받는다.
  - 병합 절을 앞뒤 절과 잇는다. §17의 증상은 선택 막대(「1-9절 선택됨」)와 제목(「나훔 1:1-7,9」)이 어긋나는 것이었다. 「7-8」만 고치면 제목이 「나훔 1:1-6,7-8,9」가 되어 여전히 막대와 다르다. 합치기는 이미 이어 적었다.
- 드라이브 동기화는 2026-05-04부터 있었다(`649ff33`). 그래서 옛 판이 올린 기록이 드라이브에 남아 있을 수 있다.
- 옛 판도 여러 줄인 병합 절의 줄을 모두 고르면 첫 번호를 저장했다(`git show 0789632^:js/app/bookmark.js`의 `collapseFullVerseRefs`). 그 「7」은 지금 앱이 저장한 「7」과 구별되지 않아 그대로 남는다.
- main의 합치기는 옛 표기 둘을 합치면 「all」(장 전체)을 돌려줬다(아모 5 「16-17a」와 「16-17b」, 전수에서 157가지). 지금 화면에서는 합치는 쪽이 늘 번호라 이 길이 없다.
- 합치기는 사용자가 고친 제목도 「책 장:합친 범위」로 다시 짓는다. main부터 있던 동작이라 known-issues §19로 넘겼다.

## 검증

- **유닛.** `node --test tests/unit/*.test.js`는 1,358건이다. 1,357건이 통과하고 실데이터 대기 1건은 건너뛴다. 15건이 늘었다(리뷰 반영의 5건 포함).
  - `verse-spec.test.js` +5: `verseNumberSpec`의 저장 표본(인용으로 나뉜 절, 반쪽 절, 병합 절과 앞뒤 절)과 큰 범위, `wholeVerseSpec`의 표본 14가지와 그대로 둘 표기를 본다.
  - `bookmark.test.js` +5: `collapseSegmentedVerses` 테스트 6건을 지웠다(같은 경우를 `verseNumberSpec`이 본다). 합치기 2건(옛 표기, 큰 범위), 옛 판 저장값의 합성 장 전수 1건, `migrateLegacyBookmark` 3건, 시작할 때와 동기화 때 부르는 함수 5건(리뷰 반영)을 더했다. 「3a」와 「3b」를 합친 기대값은 「3a,3b」에서 「3」으로 바꿨다.
  - `storage.test.js` +3: `rewriteBookmarks`가 두 사본을 고치고 수정 시각을 지키는지, 바꿀 것이 없으면 쓰지 않는지, 깨진 사본에서 예외가 새지 않는지 본다. 실제 `store-v2.js`를 같은 컨텍스트에 싣는다.
  - `state-machine.test.js` +2: 병합 결과를 옮긴 뒤 저장하고 옛 키에도 쓰는지, 옮기는 함수가 없어도 저장하는지 본다.
  - 새 테스트와 바뀐 테스트를 main의 `js/`로 돌리면 22건이 실패한다(스크래치에 main의 `js/`를 풀어 확인했다). 71번(옮기는 함수가 없을 때)은 main에서도 통과한다. main의 합치기는 `1-20000000`에서 4.5초 걸린 뒤 실패했다.
  - `npm run typecheck`는 오류가 없다.
- **e2e.** 4건을 더했다. main의 `js/`로는 4건 모두 실패한다.
  - `test_bookmark_read.py`: 옛 표기 북마크 셋을 저장하고 새로 고치면 두 사본이 옮겨지고 수정 시각은 그대로다. 이름은 옛 기본 이름만 바뀐다. 모아 읽기가 세 북마크를 모두 그린다.
  - `test_bookmark_export_import.py`: 옛 표기 파일을 들이면 옮겨 저장되고 목록 참조도 「이사 10:16」이다. 사용자가 지은 이름은 그대로다.
  - `test_bookmark.py`: 나훔 1:7-8만 고르면 「7-8」과 「나훔 1:7-8」로 저장된다. 옮기기 전의 「16aa」에 1절을 합치면 「1,16」이다.
  - `pytest tests/e2e/`는 378건이 모두 통과했다. 리뷰 전 판은 10분 17초, 1회차 반영 뒤는 11분 18초였다. 2회차 반영 뒤에는 북마크, 동기화, 이동의 e2e 5파일 92건을 다시 돌려 모두 통과했다.
- **실데이터 전수.** 스크래치 스크립트(저장소에 넣지 않음)로 앱의 `appendVerses`가 그린 줄 59,784개(1,491장)를 뽑았다. 여러 줄인 번호가 있는 931장에서 옛 판의 저장 함수로 저장값을 만들었다. 줄 하나, 한 줄만 뺀 나머지, 첫 줄과 끝 줄, 장 전체에 흩은 선택이다.
  - 영문 글자가 든 저장값 57,409개를 옮겼다. 모두 가져오기 검사를 통과하고, 같은 줄을 지금 앱으로 저장한 값과 같다. 병합 절의 첫 번호는 위의 한계대로 남긴다.
  - 그 값을 main의 합치기로 합친 58,539개도 옮겼다. 덮는 절 번호가 같고 검사를 통과한다.
  - 지금의 합치기로 같은 짝 58,746개를 합치면, 두 값이 가리키는 절을 모두 덮는다.
- **화면.** 기존 사용자처럼 옛 표기 북마크 여덟 개를 저장소에 둔 채 새로 고쳤다(Chromium, 이 브랜치). 여덟 개 모두 옮겨지고 수정 시각은 그대로였다. 옛 기본 이름은 새 기본 이름이 되었고(「이사 10:16aa」 → 「이사 10:16」), 고친 이름(「내가 고친 이름」)은 그대로였다. 북마크를 열면 절 전체가 강조된다(이사 10:16은 16ㄱ과 16ㄴ). 모아 읽기는 「옛 북마크」 폴더의 여섯 북마크를 모두 그린다(main은 넷). 이사 10의 옮긴 「16」에 1절을 합치면 「1,16」이다. 페이지 오류는 없다.

## 갱신한 문서

- ADR-010: 상태, 「결정」, 「데이터 스키마」의 `VerseSpec`, 「북마크 저장」을 고쳤다. 「옛 저장값」을 더하고 함수 표를 갱신했다. 병합 다이얼로그에 제목을 다시 짓는 동작을 적었다. 「검토한 대안」에 병합 절의 저장 방식 둘과 「옛 저장값」 다섯 항목을 남겼다.
- ADR-040: 상태, 「절 범위」의 옛 판 표기, 「구현」을 고쳤다. 「검토한 대안」의 「옛 판의 절 범위 표기를 뺀다」는 재검토 조건에 닿아 이유를 지금 결론에 맞추고 재검토를 없앴다. 「검증」에 이 PR의 테스트를 더했다.
- ADR-011: Phase 2a의 가져오기 줄과, 「옛 판의 북마크 절 범위 — 병합 결과를 저장하기 전에 옮긴다」 절을 더했다.
- `docs/known-issues.md`: §17 · §18의 첫 항목을 지우고 절 머리에 노트를 남겼다. §15의 합치기 항목은 멈추지 않게 된 것을 적고 남은 것만 남겼다. §15의 「손으로 만든 파일」 항목에서는 합치면 1,000구간을 넘던 문제를 지웠다. §19를 새로 두었다.
- `docs/coding-pitfalls.md` §38: 사용자 결정 넷과 구현 중에 더한 둘을 적었다.
- `docs/status.md`: 한 줄을 더했다.
- `docs/architecture.md`: `verse-spec.js` · `bookmark-core.js` · `storage.js` · `bookmark-modals.js`의 역할과 줄 수를 갱신했다.
- `docs/index.md`: 북마크 행에 pitfalls §38을 더하고, pitfalls 절 수를 고쳤다(34 → 38).
- `CLAUDE.md` · `tests/README.md`: 테스트 건수를 고쳤다. `tests/README.md`는 파일별 건수와 설명도 고쳤다.

## 리뷰 반영

1회차 리뷰는 2026-10-22에 했다. 결과를 보기 전에 범위와 기준을 정해 사용자에게 알렸다. 리뷰어는 읽기 전용으로 둘을 두고, 하나는 코드와 테스트를, 다른 하나는 문서를 맡겼다. 이 PR이 만든 결함, 덜 고친 부분, 문서의 사실 오류와 갱신 누락, 이 PR이 더한 문장의 문체 문제는 고친다. main부터 있던 동작은 known-issues에 적고 넘긴다. 재현하지 못한 추정은 넘긴다. 리뷰는 2회까지 하며, 2회차는 고친 줄만 본다.

고친 것(코드):
- **첫 화면이 성서 목록을 기다렸다.** 리뷰 전 판은 시작할 때마다 `loadBooks()`를 기다린 뒤 첫 화면을 그렸다. 그래서 성서 목록 없이 그리는 캘린더, 전례독서, 모바일의 설정 화면도 `books.json`이 늦으면 같이 늦었다. 리뷰어가 서비스 워커를 막고 `books.json`을 3초 늦춰 재현했다. 캘린더와 설정의 시작 화면이 main은 3.1-3.2초에, 리뷰 전 판은 5.2초에 걷혔다.
  - 이제 `migrateStoredBookmarks`가 저장된 목록에 옮길 것이 있을 때만 성서 목록을 기다린다. 같은 조건에서 다시 재니 캘린더 3.25초, 설정 3.14초로 main과 같았다.
  - 옮길 것이 있는 첫 시작은 여전히 성서 목록을 기다린다. 운영의 서비스 워커는 `books.json`을 셸 캐시에서 먼저 읽으므로(`sw.js`) 이 기다림은 짧다고 보고, 시간 제한은 두지 않았다.
  - `bookmark.js`가 실리지 못해 그 함수가 없을 때도 첫 화면을 그리도록, 호출을 프라미스 안에 넣었다.
- **실제 함수를 테스트가 돌리지 않았다.** 시작할 때와 동기화 때 부르는 두 함수가 마커 블록 밖에 있었고, 동기화 테스트(70번)는 대역을 썼다. 두 함수를 `BOOKMARK_LEGACY` 블록으로 옮기고 `bookmark.test.js`에 5건을 더했다. 옮길 것이 없으면 성서 목록을 받지 않는지, 폴더 안의 옛 표기를 찾는지, 성서 목록을 받지 못하거나 목록을 읽을 수 없을 때 아무것도 바꾸지 않는지, 동기화 문서의 항목을 수정 시각 그대로 옮기는지, 성서 목록이 없을 때 그대로 두는지 본다.

고친 것(코드):
- **동기화가 성서 목록보다 먼저 올 때.** 동기화 결과를 옮기는 함수의 주석은 「동기화는 첫 화면 뒤에 시작하므로 성서 목록이 있다」고 적었다. 1회차 반영 뒤로는 맞지 않는다. 캘린더로 시작하면 첫 화면이 성서 목록을 받지 않는다. 리뷰어가 `books.json`을 늦춰 재현하니, 병합 결과의 「16aa」가 옮겨지지 않은 채 저장되었다. 이제 성서 목록이 없으면 받은 대로 저장하고, 목록을 받은 뒤 시작할 때와 같은 함수로 저장된 목록을 옮기고 목록을 다시 그린다.
- **테스트가 놓친 변이 둘.** 시작할 때의 옮기기가 기다림을 끝낸 뒤에 풀리는지 테스트가 보지 못했다. 대역의 성서 목록이 이미 풀린 프라미스였기 때문이다. 대역이 한 태스크 뒤에 풀리게 바꿨다. `verseSpec`이 없는 북마크가 섞여도 옛 표기를 찾는지 보는 경우를 더했다. 리뷰어가 쓴 두 변이와, 성서 목록이 없을 때의 대체 경로를 지우는 변이를 스크래치에서 돌려, 셋 다 테스트가 잡는 것을 확인했다.
- 주석: `citationVerseSpec`이 북마크의 저장 표기도 설명하던 것을 고쳤다. 북마크는 이제 `verseNumberSpec`으로 적는다. 성서 목록 없이 그리는 설정 화면은 모바일뿐이므로 그렇게 적었다.
