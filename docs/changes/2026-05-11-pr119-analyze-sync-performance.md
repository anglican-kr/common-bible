# perf: visibilitychange 폴 throttle + ETag 관측성

## 동기

실측 sync 디버그 로그 분석에서 Phase 2i 의 `If-None-Match` 304 fast path가 발화하지 않는 사실을 확인했다. visibilitychange 트리거 폴이 1.1s round-trip을 4건 연속 쓰는 패턴이 관찰됨 (+103/+105/+108/+110s, 각 1.1s × 4 = ~4.4s 누적).

```
[+103.460s] SYNC_REQUEST state:IDLE   ← LOCAL_CHANGE 없음
[+103.461s] FIND_FILE_CACHED
[+104.549s] DOWNLOAD http:200          ← 매번 200, 304 안 보임
[+104.550s] MERGE
[+104.551s] SYNC_DONE
[+105.748s] SYNC_REQUEST              ← +2.3s 후 또 1.1s
[+108.213s] SYNC_REQUEST              ← +2.5s 후 또 1.1s
[+110.490s] SYNC_REQUEST              ← +2.3s 후 또 1.1s
```

원인은 두 가지 후보가 있는데(가설 A: Drive `?alt=media` CORS 응답이 ETag 헤더를 노출 안 함, 가설 B: 업로드 응답의 ETag와 미디어 GET ETag가 다른 네임스페이스) 실측 없이 단정 불가.

## 변경

**(a) Throttle for poll-only callers**
- `SyncMachine.requestSync(opts?: { throttleMs })` — 마지막 `_syncCycle` 종료 후 `throttleMs` 안의 호출은 `SYNC_THROTTLED` 로그 남기고 drop.
- `drive-sync.js`: `pollSync()` 추가 (`throttleMs: 15_000`), facade 노출.
- `app.js`: visibilitychange 핸들러를 `requestSync` → `pollSync` 로 교체.
- 사용자 액션 경로(`scheduleUpload` 후 300ms 디바운스 → `requestSync()`, pull-to-refresh → `requestSync()`)는 throttle 미지정 → 영향 없음.
- 내부 dispatch (silent refresh, conflict timer, backoff timer) 는 `requestSync()` 우회 → 영향 없음.

**(b) ETag 관측성**
- `debug-log.js _format()` 에 `etag` / `elapsedMs` / `throttleMs` 필드 dump 노출. 다음 실측 로그에서 etag 캐싱 여부 직접 확인 → 304 미동작 원인 가설 A vs B 가릴 수 있음.

**(c) 회귀 테스트 + 문서**
- `tests/unit/state-machine.test.js` #40-43 (4건): 첫 호출 미적용 / window 안 drop+로그 / throttle 미지정 진행 / SYNCING 중 IDLE 가드 분기 순서.
- `docs/decisions/011-bookmark-sync.md` 에 Phase 2j 섹션 + 헤더 개정 라인 추가.

## 기대 절감

위 4건 폴 사이클 중 1건만 통과, 3건 drop → **~3.3초 절감 / 10초 윈도우**. 사용자 다른 기기 변경의 반영 지연 상한은 throttle window(15s).
