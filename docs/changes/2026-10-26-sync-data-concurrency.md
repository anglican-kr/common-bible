## 요약

데이터 동기화 워크플로(`sync-data.yml`)가 겹쳐 실행되어도 자동 PR을 하나만 만들게 했다. 동시 실행 제한(`concurrency`)과, 같은 포인터로 올리는 자동 PR이 이미 열려 있는지 보는 확인을 함께 넣었다.

## 확정 · 근거

- **일어난 일**(2026-10-26): data#47이 데이터 저장소의 `build.yml`을 고쳤다. `build.yml`은 `paths`에 자기 파일이 있어 머지만으로 빌드가 실행되었다. 그걸 모르고 손으로도 실행해 동기화가 거의 동시에 두 번 실행되었다. 자동 PR #439가 포인터를 올렸고, #440은 #439가 머지되기 전에 체크아웃해 같은 변경을 만들었다가 main에 빈 squash 커밋(`f87d667`)으로 남았다. 앱의 동작에는 영향이 없다.
- **사용자 결정**(2026-10-26): 동시 실행 제한을 둔다.
- **동시 실행 제한만으로는 막지 못한다.** 앞 실행은 PR을 만들고 자동 머지를 켠 뒤 바로 끝난다. PR은 테스트를 기다리느라 그 뒤에 머지된다. 그사이 뒤 실행이 시작되면 아직 옛 포인터인 main을 보고 같은 PR을 다시 만든다. #439는 만든 지 28초 뒤에 머지되었는데, 앞 실행은 PR을 만든 직후에 끝났다. 그래서 같은 포인터로 올리는 자동 PR이 열려 있으면 새로 만들지 않는 확인을 더했다. 이 확인만 두면 두 실행이 동시에 확인하다 둘 다 「없음」으로 볼 수 있으므로, 둘을 함께 둔다.
- **동시 실행 제한의 동작**(GitHub 문서로 확인): 실행이 겹치면 뒤 실행은 기다린다(`pending`). 이미 기다리던 실행이 있으면 그것은 취소되고 새 실행이 그 자리에 들어간다. 남은 실행이 최신 데이터로 동기화하므로 잃는 것은 없다. 실행 중인 것은 취소하지 않는다(`cancel-in-progress: false`).
- **권한과 보안**: 열린 PR을 읽으려고 `pull-requests: read`를 더했다. 확인은 기본 토큰(`github.token`)으로 하고, PR을 만드는 토큰은 바꾸지 않았다. 포크에서 온 PR(`isCrossRepository`)은 보지 않는다. 같은 저장소 PR의 브랜치 이름도 따옴표 안에서 URL의 일부로만 쓰므로 셸 명령으로 실행되지 않는다.
- **함정을 적었다**: `build.yml`을 고치는 데이터 PR은 머지만으로 빌드가 실행되니 손으로 다시 실행하지 않는다(`docs/workflow.md` 「작업 중 함정」).
- **문장 검사 목록에 「불렸다」, 「불려」를 더했다.** 이 원장에 워크플로가 「불렸다」고 썼는데 검사가 찾지 못했다. 「용어」 표는 워크플로에 「실행하다」를 쓰기로 했다. 「불러」는 데이터를 「불러온다」는 바른 쓰임과 겹쳐 넣지 않았다. 같은 줄에 다른 세션이 #438에서 「지나친」, 「옆 항목」, 「이웃」을 더해 충돌했고, 둘을 합쳤다.
- **원장 훅 셋이 작업 폴더에서는 그 폴더를 검사하게 고쳤다**(사용자 허락 2026-10-26).
  - 일어난 일: 이 작업을 하는 동안 다른 세션이 같은 폴더에서 브랜치를 바꿨다. 커밋하지 않은 이 PR의 변경이 그 브랜치로 따라갔다. 커밋 전에 알아채 이 PR의 변경을 작업 폴더(`.claude/worktrees/sync-data-concurrency`)로 옮겼다. 원래 폴더에서는 이 PR의 변경만 되돌렸다.
  - 그런데 원장 훅은 늘 `CLAUDE_PROJECT_DIR`(세션을 시작한 폴더)로 가서 검사한다. 그래서 작업 폴더에서 PR을 열려 하자, 다른 세션이 쓰던 원래 폴더의 브랜치를 보고 「원장 파일이 없다」며 막았다. 커밋 검사도 원래 폴더의 스테이징을 보았고, PR 번호 기입도 원래 폴더의 원장에 적으려 했을 것이다.
  - Claude Code 훅 문서를 보면, 작업 폴더에서는 `CLAUDE_PROJECT_DIR`가 처음 폴더에 남고 훅 입력의 `cwd`가 작업 폴더를 가리킨다. 그래서 세 훅이 `cwd`에서 저장소의 맨 위 폴더를 찾게 했다. 찾지 못하면 예전처럼 `CLAUDE_PROJECT_DIR`를 쓴다.
  - 처음에는 자동 모드의 판단기가 훅 수정을 「자기 안전장치를 스스로 고치는 일」로 보고 막았다. 사용자에게 알리고 허락을 받은 뒤 고쳤다.
  - 이 PR은 고치기 전의 훅에 막혀 GitHub REST API로 열었다(사용자 허락). 훅이 할 검사는 이 작업 폴더를 대상으로 따로 실행해 통과했고, PR 번호는 훅 대신 손으로 적었다.
  - 세션을 여럿 띄울 때는 세션마다 작업 폴더를 쓴다는 규칙을 `docs/workflow.md`에 적었다.

## 검증

- 워크플로를 YAML로 읽어 권한, 동시 실행 제한, 확인 단계의 환경 변수와 스크립트를 확인했다.
- 확인 단계의 스크립트를 `git`과 `gh`를 흉내 낸 함수로 로컬에서 실행했다. 열린 자동 PR과 포인터가 같으면 멈추고, 다르면 진행하고, 바뀐 것이 없으면 멈췄다.
- 스크립트가 쓰는 API를 실제 저장소로 시험했다. 서브모듈 항목의 `sha`가 main의 데이터 포인터(`7c09d0f`)와 같았고, 거르기 조건은 열린 북마크 PR(#438)을 뺐으며, 없는 브랜치는 404로 끝나 「같지 않음」으로 처리된다.
- 실제로 겹친 실행은 다음에 데이터가 바뀔 때 생긴다. 이 PR 뒤 손으로 한 번 실행하면 바뀐 데이터가 없어 새 확인 앞에서 끝나므로, 그 실행으로는 YAML과 권한만 확인된다.
- 고친 훅 셋에 다섯 가지 입력을 넣어 실행했다. 작업 폴더를 가리키면 PR 생성 검사와 커밋 검사가 그 폴더를 보고 통과했다. 원래 폴더를 가리키면 그 폴더(지금 main)를 보고 「main에서는 PR을 만들 수 없다」로 막았다. PR 번호는 작업 폴더의 원장에 적혔고 원래 폴더는 그대로였다. `cwd`가 없으면 셸의 폴더를 썼다.
- 문서 검사 31개 가운데 30개 통과, 1개는 데이터 서브모듈이 없는 작업 폴더라 건너뛰었다. 도구 테스트 26개 통과.
