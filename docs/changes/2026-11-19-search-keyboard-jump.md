## 요약

휴대폰 하단 검색 입력창을 누르면 키보드가 뜨기 전에 입력창을 먼저 올린다. 전에는 최근 검색 화면에서 입력창을 누르면 iOS가 페이지를 위로 밀어, 화면이 위로 튀었다가 0.3-0.5초 뒤 맨 위로 돌아왔다. 키보드 위에 남는 높이를 기기 화면의 크기와 방향마다 기억하고, 다음 포커스에서 그만큼 바로 올린다. ADR-030 §6과 「검토한 대안」을 고쳤다.

## 확정 · 근거

- 사용자 보고(2026-11-19): 아이폰 화면 녹화(4초). 최근 검색 화면에서 입력창을 누르자 키보드가 올라오며 페이지가 위로 밀려 「사랑」, 「세리」, 「사랑하라」 세 줄만 남았다가 다시 맨 위로 내려왔다. 사용자가 이 튀는 동작만 고치고 따로 PR을 내기로 정했다. 키보드가 뜬 뒤 입력창이 최근 검색 목록의 아래 줄을 가리는 것은 이 PR에서 다루지 않는다.
- 원인: iOS는 키보드가 뜰 때 포커스 입력이 키보드에 가려지면 페이지를 밀어 입력을 보이게 한다. 고정 위치 요소는 키보드 아래까지 이어지는 레이아웃 뷰포트에 맞춰 놓인다(WebKit 버그 202120, 207049, 267440). 앱은 키보드 높이를 잰 뒤에야(`visualViewport`의 크기 바뀜) 입력창을 올리고, 밀린 페이지는 `scrollPageTop`이 바로, 다음 프레임, 0.3초 뒤에 되돌렸다. 녹화의 튀는 동작이 이 순서다.
- 사용자 결정(2026-11-19): 키보드의 기억은 단말기별 고유 속성으로 적는다. 고른 안은 기기 화면의 크기와 방향마다 따로 적고, 더 큰 키보드를 잴 때만 고치는 것이다(다른 안은 기기마다 처음 잰 값을 고정하기). 리뷰가 찾은 충돌은 main을 합쳐 풀기로 했다.
- 구현하며 정한 것
  - 입력이 이미 키보드 위에 있으면 iOS가 밀 까닭이 없으므로, 키보드가 뜨기 전에 올린다. 키보드 높이는 뜨기 전에는 알 수 없어 지난번에 잰 값을 기억한다.
  - 키보드 높이가 아니라 키보드 위에 남는 높이(비주얼 뷰포트 높이)를 기억한다. Safari의 도구 막대가 접히고 펴지면 레이아웃 뷰포트 높이(`innerHeight`)가 바뀌지만 키보드 위의 높이는 같다.
  - 기억의 이름은 기기 화면의 크기(`screen.width`, `screen.height`의 짧은 변 x 긴 변)와 방향(`innerWidth`가 `innerHeight`보다 크면 가로)이다. 화면 크기는 도구 막대와 상관없이 기기마다 정해져 있고, iOS는 화면을 돌려도 `screen.width`가 그대로라 짧은 변과 긴 변으로 적는다.
  - 화면 높이의 60%를 넘는 높이는 쓰지도 적지도 않는다. 미리 올렸는데 키보드가 뜨지 않으면 하드웨어 키보드로 표시해 다음 포커스에서 미리 올리지 않고, 키보드가 다시 뜨면 표시를 지운다.
  - 입력을 누르는 순간(`pointerdown`)이 아니라 포커스를 받은 뒤(`focus`)에 올린다. 누르는 순간에 올리면 손가락 아래에서 입력이 움직여 탭이 입력을 누른 것으로 처리되지 않을 수 있다. `focus`는 키보드가 뜨기 전이다.
  - 키보드가 다 뜰 때까지(0.7초) 기억한 높이와 잰 높이 가운데 큰 쪽을 쓴다. 키보드가 올라오는 동안 잰 높이는 작아서, 그대로 따르면 입력창이 다시 내려갔다가 올라간다. 0.7초 뒤에는 잰 높이로 맞추고 기억을 고친다. 기억에는 가장 큰 높이를 잰 순간의 비주얼 뷰포트 높이를 적는다. 키보드가 뜨지 않으면(하드웨어 키보드) 내려온다.
  - 기억이 없는 첫 포커스와 높이가 어긋날 때를 위해 `scrollPageTop`은 남겼다.
  - 기억은 기기에만 둔다(`bible-keyboard-height`, 동기화하지 않음). 저장소를 쓰지 못하면 전처럼 동작한다.

## 검증

- `npm run typecheck` 통과, `node --test tests/unit/*.test.js` 1,961개 통과(`keyboardMemoryKey`, `rememberedLift`, `updatedKeyboardEntry`, `keyboardLift` 유닛을 더했다).
- main을 합친 뒤와 2회차 리뷰 뒤에 e2e `test_tabbar.py` 20개(#610의 시험 포함)를 작업 폴더 서버(8092)에서 돌려 통과했다. 새 시험 `test_search_input_lifts_by_the_remembered_keyboard_before_it_shows`는 기억이 없으면 올리지 않는지, 기억한 높이로 포커스 순간에 올리는지, 키보드가 뜨지 않으면 내려오고 하드웨어 키보드로 표시하는지, 표시한 뒤에는 미리 올리지 않는지, 다른 방향의 기억은 쓰지 않는지, 비주얼 뷰포트가 줄면 이 화면의 이름으로 기억하고 다른 화면의 기억은 남기는지 본다. 포커스 때 올리기와 하드웨어 키보드 표시를 하나씩 빼면 실패한다.
- iOS가 페이지를 미는지는 이 환경에서 볼 수 없다. dev에 올린 뒤 아이폰에서 확인한다. 기억이 생기는 것은 키보드를 한 번 연 뒤라, 확인은 입력창을 두 번째 누를 때부터 한다.

## 리뷰 반영

1회차(로컬 `/code-review medium --fix`, 2026-11-19). 아홉 건을 이렇게 다뤘다.

- 1번: #610이 먼저 머지되어 ADR-030, `docs/topics/routing.md`, `tests/e2e/test_tabbar.py`가 main과 충돌했다. 사용자 결정으로 main을 합치고, 세 파일 모두 두 쪽의 내용을 함께 남겼다(문서는 #610의 줄 뒤에 이 PR의 줄, 시험은 두 시험 함수를 모두).
- 2번, 4번, 5번: 하드웨어 키보드에서 매번 올라갔다 내려오는 것, 덜 올라온 키보드의 높이가 남는 것, 잘못 잰 값을 그대로 쓰는 것이다. 사용자 결정(단말기별 고유 속성)대로 기억을 고쳐 풀었다(위 「구현하며 정한 것」).
- 3번: 기억할 때의 `innerHeight`로 다시 셈하면 그사이 도구 막대가 바뀐 만큼 어긋난다. 가장 큰 높이를 잰 순간의 비주얼 뷰포트 높이를 적는다(리뷰가 고친 것을 새 구조에 옮겼다).
- 6번: 이 PR이 쓴 주석에서 영어 뒤의 조사를 붙여 썼다.
- 7번: e2e가 앱 저장소를 비우는 목록(`CLEAR_APP_STORAGE`)에 `bible-keyboard-height`를 넣었다.
- 8번: 타이머 안의 포커스 확인을 지웠다. 포커스를 잃으면 `endPreLift`가 타이머를 지운다.
- 9번: 기억이 바뀌지 않으면 다시 쓰지 않는다(`updatedKeyboardEntry`가 null).

2회차(로컬 `/code-review medium --fix`, 2026-11-19). 여덟 건 가운데 세 건을 리뷰가 고쳤다.

- 6번: 이 PR의 처음 구현이 적은 한 칸짜리 기억(`{ w, vv }`)을 저장할 때 버린다.
- 7번: 레이아웃 뷰포트 높이를 따로 들던 상태 값을 지우고, 키보드 높이와 비주얼 뷰포트 높이의 합으로 셈한다.
- 8번: 원장의 요약과 「갱신한 문서」를 지금 구현에 맞췄다.
- 1-5번(고치지 않음): 아이폰 실기기에서 본 뒤 정한다(사용자가 dev에서 확인하기로 했다). 1번은 아이폰 가로 화면의 키보드가 화면 높이의 60%를 넘어 기억되지 않을 수 있다는 지적이고, 그러면 가로 화면은 전처럼 튀었다가 돌아온다. 2번은 iPad의 작은 막대가 하드웨어 키보드 표시를 막는다는 지적, 3번은 한 번 크게 잰 기억이 줄지 않는다는 지적, 4번은 키보드가 0.7초 안에 다 뜨지 않으면 하드웨어 키보드로 잘못 표시한다는 지적(다음 포커스에서 지워진다), 5번은 iPad의 창 나누기에서 높이가 어긋난다는 지적이다.
