# 코딩 실수 패턴 (Coding Pitfalls)

이 문서는 본 프로젝트의 git 커밋 이력에서 추출한 **반복 발생하는 실수 패턴**을 카테고리별로 정리한 것이다.
ADR이 "왜 이 결정을 했는가"를 다룬다면, 이 문서는 **"무엇을 조심해야 하는가"** 에 초점을 맞춘다.

## 사용법

- 새 기능을 구현하기 전에 관련 카테고리의 체크리스트를 훑어본다.
- 코드 리뷰 시 동일 패턴이 재발하지 않는지 확인한다.
- 새로운 실수 유형이 발견되면 카테고리를 추가하거나 기존 카테고리에 사례를 덧붙인다 (살아있는 문서).
- 코드 실수만 받는 곳이 아니다 — **사용자 교정**(작업 방식·판단을 바로잡은 것)과 **도메인 확정**(책자·기도서 대조로 굳어진 규칙)도 여기 쌓는다. 항목마다 날짜와 근거(원장 파일·커밋·PR)를 남긴다.

기준 시점: 2026-05-03 (총 99개 커밋, 그중 fix 38개 = 38.4%).

## 1. 비동기 타이밍 경합 — 가장 빈번

여러 비동기 작업이 동시에 진행될 때, 늦게 도착한 stale 콜백이 최신 상태를 덮어쓰는 패턴.

**사례:**
- `21540a0` — `updateAppIcons`: 테마를 빠르게 바꾸면 이전 컬러스킴의 `requestIdleCallback` + `loadOrigIcon` 체인이 뒤늦게 실행되어 새 navy 아이콘을 덮어씀.
- `5c41797` — 북마크 드로어 `open→close→open` 반복 시, 닫힘 애니메이션의 `finalize` 콜백이 새로 열린 드로어를 숨김.
- `fc6d374` — Drive 동기화에서 여러 요청이 동시에 401을 받으면 각자 `_silentSignIn()`을 호출, 재인증 콜백이 다중 실행되어 `_downloadAndMerge` → `_upload`가 중복되며 마지막 요청이 이전 기록을 덮어씀. `_isRefreshing` 플래그로 단일 진행 보장.
- e2e(2026-10-15, #348 리뷰 반영 중 확인) — `html { scroll-behavior: smooth }` 라 테스트의 `window.scrollTo(0, 600)` 은 애니메이트된다. 스크롤 도중 64px 를 넘는 순간 탭 바가 접히고, 그 상태를 보자마자 홈 탭을 누르면 남은 아래쪽 스크롤이 펼친 바를 다시 접는다 — `test_scroll_collapse_and_home_expands_without_nav` 가 누르는 시점에 따라 갈렸다(같은 코드로 통과하던 것이 이날은 매번 실패). 스크롤로 만든 상태를 바로 이어 조작하는 테스트는 `scrollTo({ top, behavior: 'instant' })` 로 경합을 없앤다.

**방어 전략 (상황에 따라 선택):**

| 전략 | 적용 상황 | 구현 |
|------|----------|------|
| Generation 카운터 | 장기 비동기 체인 (이미지 디코드, 파일 페치) | 시작 시 `_gen` 캡처 → 완료 시 `_gen === currentGen` 일 때만 적용 |
| Sequence 번호 + clearTimeout | 타이머 기반 애니메이션 | 새 작업 시작 시 sequence 증가 + 이전 `setTimeout` 명시적 취소 |
| Singleton 플래그 | 토큰 갱신·재인증·일회성 동기화 | `_isRefreshing` 같은 플래그로 진행 중 재진입 차단 |
| Promise.race + timeout | 네트워크/폰트 로드 | `Promise.race([fetch(...), timeout(1500)])` 로 무한 대기 차단 |

**규칙:** 같은 작업이 여러 번 트리거될 수 있으면 "최신 호출만 유효" 또는 "동시에 하나만 유효" 패턴을 처음부터 설계한다.

## 2. SPA 경로 해석 오류 — 2회 반복 재발

상대 경로(`./data/...` 또는 `data/...`)는 현재 URL을 기준으로 해석되므로, History API 라우팅으로 하위 URL(`/bible/john/3`)에서 새로고침하면 자원 로드가 깨진다.

**사례 (같은 버그 형태가 2번 반복):**
- `45eba01` — `index.html`의 상대 경로를 절대 경로로 수정.
- `730aafe` — 같은 버그가 `js/app.js`의 `DATA_DIR` 및 fetch 경로에 또 있어 별도 커밋으로 수정.

**규칙:**
- 모든 자원 경로는 `/`로 시작 (예: `/data/books.json`, `/assets/icons/...`).
- 데이터 페치는 상수화된 `DATA_DIR`을 통해서만 접근한다.
- 검증: 개발 서버에서 `/bible/john/3` 같은 하위 URL에 직접 진입했을 때 모든 자원이 200 OK인지 확인.

관련 ADR: `009-history-api-routing.md`.

## 3. 상태 갱신 누락 — UI 불일치

CRUD 작업 후 의존하는 UI 컴포넌트의 갱신 함수를 호출하지 않아, 데이터는 바뀌었으나 화면에 반영되지 않는 패턴.

**사례:**
- `03d7884` — 북마크 저장/수정/병합/삭제 후 헤더 북마크 버튼의 `has-bookmark` 상태가 갱신되지 않음. 모든 작업점에서 `refreshBookmarkHeaderBtn()` 호출 추가.
- `8762b3c` — long-press로 북마크 저장 시 헤더 아이콘 미갱신. (`03d7884`에서 클릭 경로는 고쳤으나 long-press 경로 누락)
- `ff39997` — division 뷰에서 `updatePageMeta()` 빈 호출이 `setTitleWithDivisionPicker()`가 설정한 제목을 덮어씀.
- `3303176` — 검색 자동 이동에서 내부·외부 `route()`가 둘 다 메타를 설정해 충돌.
- `7808c89` — 장 이동 시 절 선택 모드가 종료되지 않고 inert 셀렉터도 갱신되지 않아, 다음 장에서 비활성 요소가 잔류.

**규칙:**
- CRUD 함수마다 갱신 호출을 명시적으로 작성한다 (중앙 이벤트 시스템이 없는 이상 자동 동기화에 의존하지 말 것).
- **모든 진입점**(클릭, long-press, import, drop 등)에서 동일한 갱신 호출을 한다. 새 진입점을 추가할 때는 기존 진입점의 후처리를 그대로 따라간다.
- 라우팅이 중첩될 수 있으면 메타 설정 책임을 한 레이어로 한정한다.
- **페이지/뷰 전환 시 정리할 모드성 상태를 체크리스트로 관리**: 절 선택 모드, 모달, inert 속성, 임시 이벤트 리스너 등.

## 4. 조건문 논리 오류

방향성 역전, 분기별 검증 누락, 체크 위치 오류처럼 한눈에 보이지 않는 논리 결함.

**사례:**
- `16b70ae` — 폴더 드롭 순환 참조 검사에서 `_isDescendant`의 인자 순서가 반대였음. 실제로는 "드래그 대상이 드롭 위치의 조상인가"를 봐야 하는데 반대로 검사.
- `f154a56` — 같은 순환 참조 검사가 `position === "into"` 분기에만 있고 `before`/`after` 분기에는 누락. 폴더를 자기 조상의 형제로 드롭하면 통과.
- `3b9727f` — 단일 절 범위 초과 체크가 `hlVerseEnd != null` 블록 **내부**에만 있어, 정작 필요한 케이스에서 작동 안 함. 블록 밖으로 이동.

**규칙:**
- 부모-자식 관계 검사 헬퍼는 인자 순서가 헷갈리지 않게 시그니처 위에 한 줄 주석:
  `// _isDescendant(ancestor, candidateId) — candidate가 ancestor의 후손인가?`
- 분기로 갈라진 동일 의도 검증이 있는지 확인. "이 검증이 다른 분기에도 필요한가?"를 한 번 더 묻는다.
- 가드 절은 가능한 한 **분기 시작 시점**에 두고, 분기 내부에 두면 의도하지 않은 패스가 생기지 않는지 확인.

## 5. 모달/접근성 보일러플레이트 누락

모달 생성 시 포커스 트랩 누락, 드래그 시 포인터 이벤트 리스너 위치 오류처럼 "한 번 익히면 반복 적용해야 하는" 보일러플레이트를 빠뜨리는 패턴.

**사례:**
- `9b8a638` — 병합 다이얼로그가 표시되지만 `trapFocus()` 호출이 누락되어 키보드 사용자가 모달 외부로 빠져나갈 수 있었음.
- `5c41797`, `f154a56` — 드래그용 `pointermove`/`pointerup`/`pointercancel`을 행(row) 요소에 붙였더니, 드래그 중 포인터가 행 밖으로 이탈하면 이벤트를 놓쳐 ghost가 잔류. `document` 레벨로 이동, `pointerId` 필터링 추가.
- #348 리뷰(2026-10-15) — 캘린더 칸의 링크 이름(`aria-label`)을 보이는 이름과 다른 값(그날의 대표)으로 만들어, 사계재 · 기념일을 보이는 격자 평일 칸 54곳과 「연중24주」를 보이는 주일 칸 128곳(2025~2027)에서 보이는 글자가 접근 가능한 이름에 없었다 — WCAG 2.5.3 Label in Name, 음성 제어로 「추계재 누르기」가 안 된다. 링크 이름을 보이는 글자에서 만들게 고쳤다.
- #348 리뷰(같은 날) — 달 이동 링크가 `#app` 을 통째로 다시 그려 누른 링크가 사라지자 포커스가 body 로 빠졌다(WCAG 2.4.3) — 달을 넘길 때마다 건너뛰기 링크 · 헤더 · 탭부터 다시 지나와야 했다. 다시 그리기 전에 누른 컨트롤의 자리(`data-focus-key`)를 남기고 새 화면의 같은 자리로 포커스를 돌려준다(`views.js focusPendingBook` 과 같은 꼴). 전례독서 화면(#346)도 같은 결함이었다 — 2026-10-17 그 도우미를 `helpers.js createFocusMemory` 로 올려 두 화면이 함께 쓴다.
- 2026-10-17(전례독서 화면에 옮기며 찾은 것) — 포커스만 돌려주면 모자랐다. 새 장을 받아야 하는 다시 그리기(세트 · 트랙 · 칩 · 카드 · 날짜)는 `route()` 의 스켈레톤이 한 프레임 그려지며 문서가 짧아져 스크롤이 맨 위로 눌린다 — 누른 컨트롤이 아래로 밀리고(모바일 최대 약 250px), 화면 아래쪽 컨트롤이면 화면 밖에 포커스가 남는다(2.4.7). 받을 것이 없는 다시 그리기(같은 장의 본기도 대체안)는 스크롤이 그대로라, 같은 화면 안에서도 누르는 컨트롤마다 달랐다. 누른 때의 스크롤과 **화면 루트 안** 위치를 기억해 돌려준다 — 화면 위치(viewport top)로 재면, 스크롤이 0 으로 눌린 사이 데스크톱 머리의 검색 줄(최대 4rem)이 펼쳐졌다 접히는 것이 섞인다.

**모달 생성 4단계 체크리스트:**

```
□ 표시 전 hidden=true (또는 .hidden 클래스 부여)
□ 표시 직후 trapFocus(modal) 호출, 반환값을 cleanup용으로 보관
□ requestAnimationFrame 안에서 첫 액션 버튼에 .focus()
□ 닫을 때: 트랩 해제 + 임시 이벤트 리스너 제거 + 상태 초기화
```

**드래그 핸들러 규칙:** 포인터 추적은 항상 `document` 레벨. 멀티터치 구분이 필요하면 `pointerId`로 필터링.

**접근 가능한 이름 규칙:** `aria-label` 로 이름을 덮어쓸 때는 보이는 글자를 그대로 넣는다(줄여 보이면 이름도 그 줄임 — 「연중24주」). 보이는 이름과 링크 이름을 서로 다른 함수 · 필드로 만들지 않는다 — 한쪽만 바뀌어 어긋난다. 실데이터가 있으면 「보이는 이름 ⊂ 링크 이름」을 전수로 검사한다(`calendar.data.test.js`).

**다시 그리는 화면의 포커스 규칙:** 링크 · 단추가 자기 화면을 다시 그리면(같은 뷰 안의 이동 · 필터 · 세그먼트) 새 화면의 같은 컨트롤로 포커스를 돌려준다 — 누른 때의 화면 위치에. 공용 도우미 `helpers.js createFocusMemory` 를 화면마다 하나 만들어 쓴다(기억을 화면끼리 나누면 탭 전환에 앞지른 누름의 자리가 다른 화면 컨트롤로 샌다). 키는 선택자 문자열이 아니라 `dataset` 값으로 찾는다(관측일 id 의 콜론 · 한글). 그 컨트롤이 사라졌으면 가장 가까운 대체(「오늘」)로.

## 6. 복합 객체 비교 / 범위 병합

복합 객체를 참조 동등성으로 비교하거나, 범위를 정규화 없이 병합해 중복·누락이 발생하는 패턴.

**사례:**
- `85baf40` — 선택된 절 범위 clamping에서 `clamped[i].end !== hlSegments[i].end` 식으로 비교. 객체가 다른 참조면 내용이 같아도 불일치로 판정. 직렬화 문자열(`"3a,3b,5-7"`) 기반 비교로 교체.
- `fa83d94`, `3b9727f` — 운문 절 병합에서 정수 ref(`3`)와 파트 ref(`3a`, `3b`) 중복 제거 누락. 정수 ref가 이미 커버하는 파트 ref를 별도로 보관.

**규칙:**
- 복합 객체/세그먼트 비교는 **정규화된 직렬 형식**을 거쳐서 비교한다.
- 범위 병합은 (정렬 → 병합 → 중복 제거) 3단계를 명확히 분리하고, 정수 ref와 파트 ref처럼 **포함 관계가 있는 표현**이 섞여 있으면 우선순위를 명시.
- JSON 파싱은 항상 try-catch로 감싸 사용자가 만든 깨진 데이터에 대비.

## 7. PWA 캐시 무효화 — 셸 bump vs 콘텐츠 매니페스트

ADR-021 이후 캐시 무효화는 두 경로로 갈린다:

| 변경 대상 | 무효화 방식 | 호출/자동화 |
|-----------|------------|-------------|
| 셸 (JS/CSS/HTML/icons + `books.json`·`search-meta.json`·매니페스트 2종) | `SHELL_CACHE` 이름 bump (= `"shell-" + APP_VERSION`) | `release.py patch` — `version.json` + `sw-version.js` 한 줄 갱신 |
| 본문 (`/data/bible/*`) 또는 검색 인덱스 (`search-{ot,nt,dc}.json`) | 항목별 lazy 무효화 (콘텐츠 해시 매니페스트 diff) | `common-bible-data` CI 가 `bible-manifest.json` 자동 갱신, 앱은 `js/manifest-sync.js` 가 부팅 시 처리 |
| 오디오 mp3 | 항목별 lazy 무효화 | 같음 (`audio-manifest.json`) |

DATA_CACHE/AUDIO_CACHE 이름 자체는 더 이상 bump하지 않음 (`"data"`, `"audio"` 로 고정). `--bump-data`·`--bump-audio` 플래그는 제거됨.

**사례:**
- `docs/changes/2026-04-30-worklog.md` — `privacy.html` 추가 시 `SHELL_FILES` 등록 + navigation 예외 처리 + 셸 bump가 한 묶음으로 진행되어야 했음 (셸 영역은 매니페스트 적용 후에도 같음).

**SW 변경 체크리스트:**

```
□ 새 파일을 SHELL_FILES 에 추가했는가
□ navigation 요청 처리에서 예외가 필요한 페이지인가 (standalonePages 등)
□ 어느 캐시(shell/data/audio)에 속하는지 sw.js cacheNameFor 라우팅이 맞는가
□ 셸 영역 변경이면 release.py 로 version.json + sw-version.js bump 했는가
□ 본문/오디오 콘텐츠 변경이면 데이터 저장소 CI가 매니페스트를 자동 갱신했는가 (manual gen_manifests.py 실행으로 미리 확인 가능)
```

스크립트 `scripts/release.py`는 셸만 다룬다. 콘텐츠 매니페스트는 데이터 저장소의 `scripts/gen_manifests.py` 책임.

## 8. 폰트/렌더링 특성 오해 — 회귀 사례

브라우저 폰트 로딩 동작을 잘못 이해해, 캐시 무효화 직후 첫 실행에서만 회귀가 보이는 까다로운 패턴.

**사례:**
- `351deef` — `font-display: optional`은 폰트가 100ms 안에 도착하지 않으면 그 세션 동안 시스템 폰트로 락인됨. 캐시 미적중 직후 첫 실행에서 의도한 폰트가 보이지 않다가 앱 재시작 후에야 나타나는 회귀. `swap`으로 변경 (런치 스크린이 FOUT 구간을 가림).
- `d61f879` — `media="print" onload` 트릭으로 @font-face를 동적 삽입하면 first paint 이후에 로드되어 FOUT 발생. blocking `preload as="style"`로 변경.

**규칙:**
- 폰트 규칙은 **first paint 전에 DOM에 있어야** FOUT이 없다.
- 폰트 전략은 **(빠른 네트워크 / 느린 네트워크) × (캐시 적중 / 미적중)** 4가지 조합으로 검증한다. DevTools의 throttling + "캐시 비우고 강력 새로고침"으로 재현.
- 관련 ADR: `007-launch-screen-optimization.md` (개정 블록 참고).

## 9. 글로벌 이벤트 핸들러 협력 부족

전역 인터셉터(예: `document.addEventListener("click", ...)`)가 하위 요소의 자체 핸들러가 이미 처리한 이벤트를 **다시 처리**해 의도치 않은 동작이 발생하는 패턴.

**사례:**
- `d25b8da` — 전역 클릭 인터셉터가 SPA 라우팅을 위해 `<a href>` 클릭을 가로챘는데, `buildSheetPagination`의 `href="#"` 링크는 자체 핸들러에서 `e.preventDefault()`를 이미 호출함. 인터셉터가 `e.defaultPrevented` 미체크로 `route()`를 또 호출.
- #348 리뷰(2026-10-15) — 반대 방향의 같은 결함: 탭 바의 탭 처리기(홈 · 캘린더 · 북마크 · 설정)가 전역 인터셉터의 **수정 키 조건**(⌘ · Ctrl · Shift · Alt · 가운데 단추 → 브라우저에 맡김)을 따르지 않았다. ⌘ · Ctrl-클릭에서 (a) 홈 · 캘린더 탭은 `preventDefault` 뒤 같은 탭에서 이동해 새 탭 열기를 무시했고, (b) 캘린더 · 북마크 · 설정 탭은 인터셉터가 빠져 브라우저가 새 탭을 여는데도 스크롤 복원 요청을 먼저 세워, 그 요청이 남아 다음 링크 이동이 옛 스크롤 위치로 튀었다(e2e 재현 — 장 최상단 대신 600px). 탭 히스토리 도입(`687a071`, ADR-031 — #194)부터 있던 꼴을 캘린더 탭이 그대로 따랐다.

**규칙:**
- 글로벌 이벤트 핸들러는 가장 먼저 `if (e.defaultPrevented) return;` 으로 협력 게이트를 둔다.
- 자체 처리하는 하위 핸들러는 **반드시** `e.preventDefault()` (필요 시 `stopPropagation()`)를 호출해 의도를 표현한다.
- 가능하면 글로벌 인터셉터 스코프를 좁힌다 (예: `closest("a[href]:not([data-internal])")` 같이 명시적 마커).
- 링크에 다는 처리기는 전역 인터셉터와 **같은 조건으로 먼저 빠진다** — 새 탭 · 새 창 클릭은 `window.appHelpers.isModifiedClick(e)` 로 거른다(인터셉터도 이 함수를 쓴다 — 조건이 한 곳). 복원 요청 · 포커스 기억 같은 부수 효과는 이 화면에서 이동이 일어날 때만 남긴다.

## 11. 비동기 race 가드 — 단일 체크포인트의 함정

`async` 함수가 여러 `await` 지점을 거치면, 각 await 사이마다 외부 상태(사용자 의도, 다른 흐름의 결과 등)가 바뀔 수 있다. race 가드를 함수 진입 시점이나 첫 번째 await 직후에만 두면, 그 다음 await가 끝난 시점에 이미 stale한 결정에 따라 상태를 덮어쓰는 패턴.

**사례 (Phase 2h PKCE 마이그레이션 — Bugbot PR #54·#57):**

- `c4d0c72` — `_attemptSilentRefresh`가 `_state` 기반 race 가드만 가짐. 사용자가 silent refresh 진행 중 `signOut()`/`disable()`을 호출하면 `_state`는 그대로(혹은 정상 진행 중인 값)이지만 `localStorage["bible-drive-sync"]`는 `"0"`으로 바뀜 → state 가드만 통과시켜 IDLE/NEEDS_CONSENT로 전이하면 사용자가 끊은 sync를 다시 살림. 해결: `localStorage.getItem(SYNC_ENABLED_KEY) === "0"` 검사 추가.
- `f090c83` — 같은 함수에 race 가드를 진입 시점에만 둠. 그러나 `await refreshAccessToken(...)` 직후 race 가드를 통과한 뒤에도 `await refreshStore.saveRefreshToken(...)` (rotation) 또는 `await refreshStore.clearRefreshToken()` (invalid_grant) 같은 IDB await가 남아있음. 그 IDB await 동안 사용자가 `disable()`을 호출하면 후속 `_transition(IDLE/NEEDS_CONSENT)`이 다시 `SYNC_ENABLED_KEY = "1"`로 덮어씀. 해결: 매 `await` 직후마다 race 가드를 다시 검사. 단계 4 후 `enable()`이 동기적으로 DISABLED를 빠져나가지 않으므로 state-based 가드만으로 cold-start 경로 보호 불가능 — flag-based 가드가 필수.

**규칙:**

- 비동기 함수에서 race 가드는 **모든 await 직후에 재검사**한다. 진입 시점 한 번만으로 충분하다고 가정하지 말 것.
- 사용자 의도를 신뢰성 있게 신호하는 단일 출처(여기서는 `localStorage["bible-drive-sync"]`)를 정해 모든 race 가드가 같은 출처를 참조하게 한다.
- state machine을 단순화하면서 동기 dispatch가 사라졌다면, 기존 state-based race 가드가 더 이상 작동하지 않는지 의심하라. flag-based 가드로 대체하거나 보강해야 할 수 있다.
- 회귀 방어 테스트: 외부 제어 가능한 `Promise`로 await를 hold한 채 `disable()`을 끼워 넣어, 각 await 시점의 race window를 명시적으로 시뮬레이션한다 (`tests/unit/state-machine.test.js` 26a/b/c 참고).

## 12. 콜백 URL 데이터 leak — flow별 transport 격차

OAuth callback이 query string(`?code=...`)으로 오느냐 fragment(`#access_token=...`)으로 오느냐는 flow마다 다르다. URL을 strip하는 코드가 한 flow의 가정 위에 작성됐다면, flow 전환 시점에 새 flow의 callback이 URL bar / 브라우저 히스토리 / 로그에 leak될 수 있다.

**사례 (Phase 2h PKCE 마이그레이션 — Bugbot PR #54-2):**

- `3a7c8ab` — Implicit Flow 시절 IIFE는 `bad_state` / `no_state` / `state_mismatch` fallback에서 `history.replaceState(null, "", location.pathname + location.search)`로 search를 보존했음. Implicit callback은 fragment에 오므로 search는 안전했음. PKCE 도입 후 callback은 query string(`?code=...&state=...`)으로 오므로 같은 fallback이 auth code를 URL bar에 leak.

**규칙:**

- 새 flow로 전환할 때, 기존의 URL strip 로직이 새 flow의 callback shape을 반영하는지 명시적으로 검증한다.
- 기본 원칙: 본인 앱이 query 또는 fragment 기반 라우팅을 안 쓴다면, OAuth fallback에서 `location.pathname`만 남기고 search/hash를 둘 다 폐기하는 게 가장 안전.
- 회귀 방어: callback URL의 `?code=`, `#access_token=` 등이 IIFE 종료 후 `location.search`/`location.hash`에 잔존하지 않는지 e2e 테스트로 직접 검증.

## 13. 마이그레이션 시점의 sessionStorage / localStorage 키 격리

기존 흐름과 새 흐름이 같은 storage 키를 공유하면, 마이그레이션 PR 머지 시점에 진행 중이던 callback이 잘못된 흐름으로 라우팅되거나 완전히 떨어진다. flow별로 별도 키를 사용해 절대 교차 처리되지 않게 격리해야 한다.

**사례 (Phase 2h PKCE 마이그레이션):**

- 단계 2~4 — Implicit Flow는 `bible-drive-redirect-state`, PKCE는 `bible-drive-redirect-state-pkce`로 분리. 단계 4 머지 시점에 진행 중이던 PKCE callback은 새 코드도 같은 `-pkce` 키로 매칭되어 정상 처리됐고, 진행 중이던 Implicit callback은 신코드가 안 봐서 자연 만료(sessionStorage 휘발).
- 단계 4의 함수 rename(`beginRedirectAuthPKCE` → `beginRedirectAuth`)에서 **변수명만 canonical로 인계하고 storage 키 값은 의도적으로 `-pkce` 접미사 유지** — 변수명과 키 값을 동시에 바꾸면 in-flight callback이 떨어짐.

**규칙:**

- 서로 다른 인증 / 라우팅 flow에는 처음부터 다른 storage 키를 부여한다.
- 키 이름을 바꾸는 마이그레이션은 두 단계로: (1) 새 키 사용 시작, 옛 키는 read-only로 유지 → (2) 옛 키 cleanup. 한 PR에 같이 넣지 말 것.
- localStorage 폐기 키는 단계 5처럼 별도 정리 단계에서 `localStorage.removeItem(...)`을 IIFE에 추가해 기존 사용자 디바이스에서 청소한다 (몇 릴리스 후 cleanup 코드 자체도 제거).

## 14. CSS `display` 속성이 `[hidden]` 무력화

`<button hidden>` 같은 HTML5 `hidden` 속성은 user-agent 스타일시트에서 `[hidden] { display: none }`로 처리된다. 그런데 author CSS에서 ID 셀렉터로 `display: flex`(또는 block, grid 등)를 명시하면 specificity가 더 높아 `[hidden]` 규칙을 덮어쓴다 — JS에서 `el.hidden = true`로 설정해도 시각적으로 안 사라지는 회귀.

**사례 (Phase 2h 단계 6):**

- 검색 액션 버튼(`#search-clear`, `#search-history-toggle`)에 `display: flex`가 적용돼 있어, JS의 `$searchClear.hidden = true`가 무력화. 빈 입력 상태에서도 X 버튼이 계속 보였고, 동시에 `dataset.clearHidden="true"` 트리거 규칙이 history toggle을 clear의 위치로 옮겨 두 버튼이 정확히 같은 좌표에 스택. DOM 순서상 clear가 후순위라 사용자에겐 X만 보이고 ▾는 X 뒤에 가려져 "버튼 모양이 이상"한 외양.
- 수정: `#search-clear[hidden], #search-history-toggle[hidden] { display: none; }` 명시 규칙 추가. specificity 동률 이상으로 끌어올려 `[hidden]` 의도 복구.

**규칙:**

- ID 또는 specificity 높은 셀렉터로 `display: ...`를 설정한 요소가 `hidden` 속성을 통해 가려질 수 있다면, **반드시 같은 셀렉터에 `[hidden] { display: none }` 규칙을 명시**한다.
- 점검: `el.hidden = true` 후 DevTools에서 `getComputedStyle(el).display`를 확인해 `none`이 나오는지 검증.
- 전역 회귀 방지가 필요하면 `:where([hidden]) { display: none !important; }` 같은 광역 규칙도 가능하지만 `!important`는 다른 의도된 override를 깨뜨릴 수 있어 피하는 게 좋음. 셀렉터별 `[hidden]` 보강이 더 안전.

## 15. Cache API ↔ IDB sidecar 불일치 + Content-Length 의존

Cache API는 access-time / byte-size 메타데이터를 노출하지 않으므로 LRU·쿼터 추적은 IndexedDB sidecar에 별도 보관하는 패턴이 자연스럽다 (ADR-016). 그러나 두 store가 독립 존재이므로 한쪽만 갱신·소실되면 추적이 영구 어긋난다. 또 Content-Length 헤더에 의존해 byteSize를 기록하면 chunked transfer / gzip / Range 응답에서 0이 들어가 LRU cap이 사실상 무력화된다.

**사례 (2차 보안 감사 — `docs/archive/audit/2026-05-08-second-comprehensive.md` H1·H2·H3):**

- **H1** — `sw.js:139` `byteSize = cl ? Number(cl) : 0`. Content-Length 누락 시 0 기록 → totalSize 합산에서 빠짐 → HARD_CAP 도달 신호 못 받음 → Cache API 무한 누적 → origin-단위 quota 초과 시 DATA_CACHE까지 evict.
- **H2** — `_putAudioAndEnforceCap`이 두 fetch에서 동시 진행되면 `pickEvictions` 결과가 방금 put된 url을 evict 대상에 포함시켜 재생 중 mp3 삭제.
- **H3** — `cache.put` 성공 후 `recordEntry` 실패하면 Cache에 mp3는 있고 IDB 메타는 없는 상태로 영구 누적. DevTools에서 한쪽만 비워도 같은 결과.

**규칙:**

- **byteSize는 Content-Length를 우선하되 무효 시 `response.clone().blob().size`로 폴백한다.** 추가 read 1회 비용을 받아들이는 것이 LRU 정확성 손실보다 항상 낫다. clone()은 `cache.put` 전에 (body 소비 전에) 해야 한다.
- **동시 in-flight URL 추적**: 모듈 레벨 `Set`에 진입 시 add, 종료 시 finally에서 delete. eviction은 이 Set을 filter out — 진행 중 항목이 다른 호출의 cap 정리에 휘말리지 않게.
- **양 store reconcile**: SW `activate` 핸들러에서 `cache.keys()`와 IDB entries 양방향 비교. (a) Cache에 있고 IDB에 없는 항목 → recordEntry로 채움 (byteSize는 blob.size로). (b) IDB에 있고 Cache에 없는 항목 → orphan removeEntries. 비용은 mismatch 수에 비례하며 healthy 상태에선 microsecond.
- **회귀 방어**: 단순 throughput 테스트 외에 (i) Content-Length 누락 응답 (ii) 동시 cap 초과 fetch (iii) IDB·Cache 한쪽 비움 시나리오를 명시적으로 다루는 테스트 케이스 필요.

## 16. 모듈 init 시점 `window.X` facade 미정의 — 로드 순서 race

`<script type="module">` 들은 index.html 의 나열 순서대로 평가된다. 어떤 모듈이 **init(top-level) 코드에서** 다른 모듈이 `window.X` 로 노출하는 함수를 소비하면, 그 함수를 정의하는 모듈이 **뒤에** 실려 있을 때 init 시점엔 `undefined` 다. 한 번 검사하고 즉시 bail 하면 이후 그 함수가 정의돼도 재시도가 없어 상태가 영구히 비어버린다.

**사례:**
- `53cb24d` (#246) — search.js 가 부팅 시 `ensureAliasMap()` 으로 `in:<별칭>` 흡수용 `_aliasMap` 을 예열하는데, `window.loadBooks`(data-fetch.js)는 search.js *뒤*에 로드되는 모듈이라 예열 시점엔 undefined. `if (typeof window.loadBooks !== "function") return` 로 즉시 bail → `_aliasMap` 영구 null → `사랑 in:요한` 입력이 책 칩으로 흡수되지 않고 raw 텍스트로 남는 회귀. 동기 흡수 리팩터가 commit 시점의 `await ensureAliasMap()` 을 부팅 예열로 옮기며 로드 순서 가정을 깬 것이 원인.

**규칙:**
- init 에서 소비하는 `window.X` 가 **뒤에 로드되는 모듈** 소속인지 확인한다. 그렇다면 한 번 bail 하지 말고 정의될 때까지 짧게 대기 후 진행하거나, 소비 시점(이벤트·커밋 핸들러)으로 미룬다.
- 이런 로드 순서 race 는 vm 유닛 하네스가 `window.X` 를 미리 스텁하므로 **유닛 테스트로 안 잡힌다.** 실제 모듈 순서로 로드하는 브라우저 스모크로 검증한다.

## 18. 교회력 조회의 도메인 확정 — 주일과 겹치면 주일 본문 · 성주간과 재의 수요일 주간은 지정 독서 · 여성선교주일은 기념일 (2026-10-10)

전례독서 · 본기도 데이터에는 날짜로만 갈리는 평일 본문이 있다 — 12.17~12.24 「성탄 N일 전」, 12.30 · 12.31 · 1.3~1.5 · 1.7~1.12 「성탄주간」(`type: weekday`, 설계서 §5.4). 그 날짜가 주일이면 날짜 본문과 주일 격자 본문(대림 3 · 4주일 — 12.17 이 주일인 해는 대림 3주일이다 · 성탄 1 · 2주일) 중 어느 것인가가 데이터만으로는 정해지지 않는다.

**사례:**
- #338(`bf46f1a`) — 엔진 A1-b 가 「주일은 날짜 전용 평일 본문을 받지 않는다」로 구현했다(격자 조회 경로 ① 이 `type` 까지 맞춘다). 머지 뒤 사용자 확정: 「주일과 겹치면 주일 본문」(2026-10-10).

**규칙:**
- 날짜 전용 본문은 그날 좌표와 `type` · `season` 이 같을 때만 쓴다 — 주일에는 주일 격자 레코드다(설계서 §5.6 「출처별 조회 경로」).
- 1.7~1.12 는 이 규칙에 걸릴 일이 없다 — 그 사이의 주일은 언제나 주의 세례 주일(연중 1주일)이다(→ 설계서 R-4.5-baptism-ordinary-1).
- 성지주일 이후 주간은 모두 성주간으로 지킨다. 성주간 월~토와 재의 수요일 후 목 · 금 · 토는 특별한 일이 없으면 **지정 독서**를 쓴다(사용자 확정 2026-10-10). 성 목 · 금 · 토는 정의 표의 행이, 성주간 월~수 · 재의 수요일 후 목~토는 이름을 단 격자 후보가 그 독서를 낸다(설계서 §5.5).
- 지정 독서가 데이터에 없으면 먼저 원료(교구 사이트 기사)의 **태그 누락**을 의심한다 — 재의 수요일 후 금요일은 기사(archives/3994)가 있는데 「감사성찬례-전례독서」 태그가 없어 수집되지 않았다(2026-10-10, 사용자 제보). 데이터 저장소 `liturgical/fetch.py` 의 `EXTRA_ARTICLES` 가 그 자리다(선례: 2026-07-13 사순5주 · 연중5주; 이번 건은 data#27).
- 픽스처(책자 · 달력)와 데이터의 성구 범위가 어긋나면 원료 기사의 **오기**를 먼저 의심한다 — 대림 3주일 나해 복음은 「요한 1:6-8, 19-28」이다(사용자 확정 2026-10-11 — 서울교구 2026 달력 12월 면 · RCL). 사이트 기사(archives/3139)가 「19-26」으로 실어 데이터가 그대로 받았고, 엔진 B1 의 픽스처 소비(W-2026-12-13-lucia-on-sunday)가 잡았다. 고칠 자리는 데이터 저장소 `liturgical/readings.py` 의 `SOURCE_FIXES` · `SOURCE_NOTES` 다(선례: 기사 17829 「이사 55:11-5」).
- **여성선교주일은 기념일로만 표시한다** — 해마다 본기도와 독서가 새로 정해져 고정 본문이 없다(사용자 확정 2026-10-10, data#27). 스크랩된 그해 본기도·독서는 싣지 않고(데이터 `coords.VARYING_TEXTS`), 그날은 이름 줄 후보로만 오른다 — 주일 본문은 격자가 낸다(→ 설계서 R-6.1-ineligible).
- **2023 · 2024 「전례독서」 책자의 12.17~12.24(성탄 N일 전) 독서는 신뢰할 수 없다**(사용자 확인 2026-10-11) — 그 구간은 책자 대조의 근거로 쓰지 않는다. 같은 구간의 기존 픽스처 둘(W-2024-12-20-ember-friday-two-sets · W-2024-12-21-ember-ordination-kim)은 책자가 아니라 서울교구 2024 달력 12월 면이 근거다.

## 19. 교회력 품계 · 색의 도메인 확정 — 사계재 날은 자 · 재의 수요일 주간의 축일 · 3.01 은 삼일절 (2026-10-10)

엔진 B1(설계서 §6)을 구현하기 전에 사용자에게 물어 정한 셋이다. 셋 다 지금 규칙만으로는 답이 갈리거나 책자와 어긋나는 자리였다.

**사례:**
- 사계재 날 그 자체의 색 — 2026-09-17 에 「승자의 절기색」(하계재 · 추계재 평일 녹)으로 정했다가, 2025 · 2026 책자가 두 해 연속 [자] · [자/백]으로 인쇄한 것이 확인돼 다시 열렸다(설계서 미결26).

**규칙(사용자 확정 2026-10-10):**

## 20. 교회력 이동의 도메인 확정 — 본당 축일 · 교구 설립일 · 성주간과 부활 8일의 주요축일 (2026-10-11)

엔진 B1 이동 패스(설계서 §6.5)를 구현하며 「12월 축일이 해를 넘겨 1월로 밀리는 일이 어디서 생길 수 있나」를 따지다가, 본당 · 교구 지역 축일(`local-observances` — ADR-036 B2 `scope` 오버레이)이 12월 말에 오면 축일을 밀 수 있다고 잘못 짚었다. 품계만 보면 그렇게 읽힌다 — 데이터(`calendar/parishes.md` 머리)와 ADR-036 「성인력 보완 영역」(1)이 성당축성일을 기도서대로 주요축일 C(prec 4)로 적었기 때문이다.

**사례:**
- 2026-10-11 PR 3 둘째 착수 중 — 「해 넘김 이동은 데이터가 바뀔 때만 생긴다 — 12월 말 prec 7 축일을 옮길 수 있게 바꾸거나, 본당 · 교구 축일이 들어오는 경우」라고 보고했다가 뒤의 갈래를 사용자가 교정했다(축성일까지 포함한다는 것도 확인받았다).
- 같은 날 분당성당 축성일(09.13)을 데이터에 넣다가, 파서가 등급표대로 축성 본당 142곳과 교구 설립일 셋을 `transferable: true` · `next_day` 로 내고 있던 것을 찾았다 — 확정과 어긋나 data#29 에서 고쳤다.

**규칙(사용자 확정 2026-10-11):**
- **본당 축일(주보성인 축일 · 성당축성일 — 축성일 · 축복일 모두)은 기념일과 같은 성격이라 축일 이동에 영향을 주지 않는다** — 다른 축일을 밀지도, 옮겨 온 축일의 자리를 막지도, 스스로 옮겨지지도 않는다. 데이터는 `transferable: false` · `transfer_to: null`(data#29).
- **교구 설립일도 옮기지 않고, 다른 축일과 겹치면 기념만 한다** — 추수감사주일과 같은 `transfer_to: "commemorate_only"`(data#29). 엔진은 `commemorate_only` 를 옮기지 않고, 밀리면 `commemorated` 로 낸다(설계서 §6.2).
- 그래서 이동 패스(→ 설계서 R-6.5-year-pass)는 지역 축일을 보지 않고, 패스 캐시는 본당 설정에 의존하지 않는다(설계서 §4.9).
- **성주간 · 부활 8일에 걸린 주요축일은 책자대로 그날 지킨다**(사용자 결정 2026-10-11 — #343 의 골든 덤프를 사람이 확인하려고 2024 · 2025 · 2026 책자 PDF 와 대조하다 나왔다). 보호 기간 때문에는 옮기지 않고, 그날의 대축일 · 주일에 질 때만 옮긴다. 근거는 책자 두 해다 — 2024-03-25 성 월요일의 성모수태고지(가)를 [백] · 수태고지 독서와 성 월요일 독서를 함께, 2025-04-25 부활 1주 금요일의 성 마르코(나)를 [홍] · 고유 독서만으로 그날에 두었다. 기도서 주요축일(나)-2 「대축일이나 성주간, 부활주간 8일과 겹치지 않는다」와는 어긋나지만 책자 관행을 택했다((가)에는 그런 조항이 없다). #343 까지 엔진은 (가) · (나) 모두 부활 2주일 뒤로 옮겼다(로마 · 미국 성공회 관행) — **#345 에서 책자대로 고쳤다**(설계서 R-6.3-holy-week-guard · 미결32 를 목적지 물음으로 좁힘 · 보호 기간 픽스처 · 골든 덤프 981 → 910줄). 세부 셋(사용자 결정 2026-10-11):

## 23. 머지 전 코드 리뷰의 도메인 확정 — 보호 기간에서 밀린 축일끼리의 순서 · 연쇄 범위가 닿는 곳 (2026-10-14)

PR #347(`824f7ee`)을 머지 전에 코드 리뷰해 지적 15건을 받았다(원장 `docs/changes/2026-10-13-liturgical-engine-booklet-2027.md` 5회차). 사용자 결정 하나와, §22 결정의 범위를 코드가 넘어선 것 하나.

**사례:**
- 보호 기간 목적지(§22 · 설계서 R-6.3-guard-destination) 때문에 부활절이 3.26 인 해(1967 · 1978 · 1989 · 2062 · 2073 · 2084)에는 성지주일(3.19)에 밀린 요셉과 부활밤(3.25 성 토요일)에 밀린 수태고지가 둘 다 부활 2주 월요일(4.3)부터 자리를 찾는다. 엔진은 먼저 밀린 요셉에게 4.3 을 주고 수태고지를 4.4 로 보냈다(선착순 — 미국 성공회 2008 달력). 그런데 설계서 · 검토 문서는 「1900~2100 실데이터에 순서가 갈리는 사례 없음 → 사제에게 묻지 않음」을 전제로 그 물음을 닫아 두었다 — 그 전제는 보호 기간 목적지를 바꾸며 깨졌다. 세 전통이 갈린다: 미국 BCP 1979 「일어난 순서대로」, 영국 Common Worship 「요셉은 부활 2주 월요일로 — 수태고지가 이미 그날로 옮겨졌으면 그다음 첫 빈 날로」(조지 · 마르코는 날짜 순), 로마 「수태고지는 부활 2주 월요일」. 우리 기도서에는 순서 조항이 없고, 일반 원칙은 「주요축일이 다른 축일과 겹칠 경우, 우선하는 축일을 지키고 다른 축일을 옮겨 지킨다」이며 수태고지(주요축일 가 — 연중주일도 이긴다)가 요셉(나 — 모든 주일에 진다)보다 위다.
- 모든 성인의 날을 켠 해(10.30~11.5 사이 주일로 옮겨 지킴) 2025-11-02 에 엔진은 모든 별세자의 날을 그 주일에 「기념만」으로 남겼다 — 그날을 밀어낸 것 가운데 맨 위 하나(옮겨 온 모든 성인의 날)만 보고 연쇄 범위 규칙을 적용했기 때문이다. 그 주일도 별세자의 날을 밀어내므로 종전대로 11.3 으로 가야 한다(2025 책자 11.3 「11월 2일에서 이동」 — 같은 해 11.1 에 「연중 31주일로 이동할 수 있다」를 안내했다). 승천을 켠 해 성모 방문(5.31 = 부활 7주일)도 같은 꼴이다.

**규칙(사용자 확정 2026-10-14):**
- **보호 기간 안에서 밀린 축일이 여럿이면 서열 순으로, 같은 서열이면 원래 날짜 순으로 부활 2주 월요일부터 앉는다**(→ 설계서 R-6.3-guard-order). 사용자: 「2번은 서열 순으로 할게」. 부활 3.26 인 6해는 수태고지 4.3 · 요셉 4.4 다 — 영국 Common Worship 의 요셉 규칙과 같은 결과. 그 밖의 도착끼리는 선착순 그대로다(→ R-6.2-first-come — 1900~2100 에서 둘이 갈리는 것은 이 6해뿐이었다). 최장 이동은 15 → 16일(요셉 3.19 → 4.4).
- **연쇄 범위 규칙(사도 · 복음사가 · 성탄 8일 순교만 연쇄, 그 밖은 기념)은 옮겨 온 축일에만 밀린 축일에 쓴다** — 주일 · 대축일처럼 그날의 다른 후보도 그 축일을 밀어내면 도착이 없었어도 옮겼을 것이므로 종전대로 다음 빈 날로 옮긴다(§22 「이 결정은 도착에 밀리는 경우만 말한다」 — 코드가 그 범위를 넘었던 것을 되돌림, 사용자 「1번 고쳐줘」). 이동 패스와 `settle` 은 같은 함수로 판정한다 — 둘이 따로 판정하다 이 PR 안에서 한 번 어긋났다.
- 연쇄 대상 밖의 주요축일(요셉 · 막달라 마리아 · 성 십자가 · 수태고지 · 성모 방문 · 주의 봉헌 등)이 옮겨 온 축일에**만** 밀릴 때 기념만 하는 것은 **잠정**이다(설계서 미결43 — 1900~2100 실데이터에는 그런 날이 없다). 사용자도 자신이 없어 사제께 묻기로 했다(2026-10-15 「나중에 신부님께 물어보는 걸로」 — 검토 문서 §6 질문지).

## 24. 캘린더 탭의 화면 결정 — 칸 이름 하나 · 선택 봉헌 · 전례년 경계 · 독서 성구 · 목록 범위 · 데스크톱 입구 · 모듈 로드 · 탭 이름 (2026-10-15)

A2 캘린더 탭(ADR-038 §1 · §2 — 하단 탭 바의 캘린더 탭과 `/calendar` 월간 · 주간 · 목록)을 시작하며 잠정안 일곱을 날짜 예와 함께 보였고, 사용자가 「시작」으로 일괄 승인했다(A3 때와 같은 방식 — 잠정 결정을 내려 구현하고 결정 목록을 확인받는다, §21). 원장 `docs/changes/2026-10-15-calendar-tab.md`.

**사례:**
- 한 날에 지키는 것이 여럿인 날이 칸 하나에 다 들어가지 않는다 — 2026-09-29 성 미카엘 ∧ 대한성공회 설립 기념일(동시 봉헌), 사계재 날, 2027-07-26 야고보(7.25 에서 옮겨 옴) ∧ 안나와 요아킴(기념만). 폰의 칸 폭은 한 줄 약 4글자다.

**규칙(사용자 승인 2026-10-15):**
- **월간 칸의 이름은 하나 — 그날의 대표(엔진 `official`)**. 대표가 이름 없는 평일(격자)이면 그날 지키는 이름 있는 후보(사계재 · 기념일), 주일과 고유명 평일(성주간 월~수 · 재의 수요일 후 목~토)은 격자 이름이다. 번호 붙은 주일은 「연중29주」 · 「대림1주」 꼴로 줄인다(ADR-038 §2). 나머지 후보는 주간 · 목록 줄과 전례독서 화면의 칩에서 본다. 예: 2026-09-29 칸 「성 미카엘과 모든 천사들」(줄에 「대한성공회 설립 기념일」) · 2026-09-18 칸 「추계재」(자색) · 2027-07-26 칸 「사도 성 장 야고보」(줄에 「7월 25일에서 옮겨 옴 · 안나와 요아킴 · 기념만」).
- **선택 봉헌(「옮겨 지킬 수 있다」)은 월간 칸에 보이지 않는다** — 칸은 주일 이름 그대로, 주간 · 목록 줄에 보조 이름으로(2026-05-17 「부활7주」 / 줄 「승천대축일 · 5월 14일에서 옮겨 지킬 수 있음」 · 2026-08-09 주의 변모).
- **전례년이 바뀌는 날(대림 1주일)에 표지** — 칸에 「나해」, 그 title · 링크 이름 · 줄에 「나해 시작」(2026-11-29). 엔진의 `liturgicalYearOf` 로 가른다(설계서 미결3).
- **독서 성구는 달력에 싣지 않는다**(설계서 미결41 — 주간 뷰의 정보 밀도) — 달력은 캘린더 묶음(정의 표 약 105KB)만 받고 독서 묶음(약 1.6MB)은 독서 화면에서만 받는다. 주간 줄에는 이름 · 색 · 주기(주일만 「가해」)를 둔다.
- **목록 화면은 오늘부터 8주, 이름 없는 평범한 평일은 건너뛴다** — 주일 · 축일 · 대재일 · 사계재 · 기념일, 끝에 「다음 8주」.
- **데스크톱(넓은 화면 · 마우스)에는 헤더 윗줄에 캘린더 단추**를 둔다 — 하단 탭 바가 없어 주소 말고는 들어갈 길이 없었다(ADR-038 §1 에 없던 범위).
- **`calendar.js` 는 전례독서 모듈처럼 모든 화면에서 받는다**(정적 import) — 두 모듈을 그 화면에 처음 갈 때 불러오는 것은 A2 뒤 별도 PR(`docs/known-issues.md` §6).
- **탭 이름 · 화면 제목은 「캘린더」** — 1단계를 「교회력」으로 보였더니 사용자가 「"교회력"은 "캘린더"로」(2026-10-15). 「교회력 자료를 불러오지 못했습니다」 · 「교회력을 계산할 수 없는 날짜」처럼 화면 이름이 아니라 교회력 자체를 말하는 문구는 그대로다.
- 구현하며 정한 화면의 세부(같은 날 보고 — 확인 대상): 독서 화면의 위 단계는 집이 아니라 꺾쇠(그 날짜의 달 — 모바일에서도 보임), 앞뒤 달 칸은 이름 없이 흐리게, 선택 대체색(장미 · 청)은 달력에 그리지 않는다(DESIGN.md §2 「전례색」).

## 25. 저녁 전례의 도메인 확정 — 성 토요일의 대표는 성 토요일 · 부활밤과 성탄 밤은 저녁 전례 (2026-10-15)

A2 캘린더 탭 1단계(#348) 화면에서 성 토요일(2026-04-04) 칸이 「부활밤」으로 보였다 — 엔진이 그날의 대표를 부활밤(prec 1)으로 내고 색은 성주간 가드로 적색이라 이름과 색이 어긋났다(설계서 미결20 의 잠정). 사용자가 「성 토요일 칸은 "성 토요일"로 보이게 해줘. 미결20에서 무엇을 정해야 하지?」라고 물어, 책자를 대조해 세 가지를 물었다.

**사례:**
- 2024 · 2025 · 2026 「전례독서」 책자 — 성 토요일 칸은 「성(주간) 토요일 [홍] · 감사성찬례 없음」, 부활밤은 「부활밤 예식 [백]」으로 따로(저녁 칸 또는 한 줄). 12.24 칸에 「성탄밤 [백]」, 12.25 칸에는 성탄 새벽 · 낮만. 2027 검토용 초안만 12.25 칸에 성탄밤을 실었다(초안 — §22).
- 칸만 「성 토요일」로 바꾸면 그 칸을 눌러 들어간 전례독서 화면의 제목은 여전히 「부활밤」이다 — 칸 이름은 엔진의 그날 대표를 쓰기 때문이다. 화면에서 따로 고치지 않고 엔진의 모델을 정했다.

**규칙(사용자 결정 2026-10-15 — 「엔진은 "성 토요일"을 기본으로 보여줘야 해. 독서 화면에서 칩으로 부활밤을 보여줄 수 있게 하면 되. 부활밤은 저녁 전례로 보는 게 맞아. 성탄 밤도 12.24 저녁 전례가 되어야 맞겠지」 — 「권장대로」):**
- **성 토요일의 대표 · 색은 성 토요일(적색)이다.** 독서 화면을 열면 성 토요일 독서(욥기 14 …)가 먼저이고, 부활밤은 「부활밤 · 저녁」 칩으로 고른다(고르면 백색 · 부활밤 독서).
- **성탄 밤은 12.24 저녁 전례다** — 12.24 의 「성탄 밤 · 저녁」 칩, 12.25 의 칩은 낮 · 새벽. 12.24 의 대표 · 색은 그날 낮(대림 평일 · 자).
- **저녁 전례는 어떤 판정에도 참여하지 않는다** — 그날의 대표 · 색 · 재분류(`settle`)에도, 축일을 다른 날로 옮기는 이동 패스에도(→ 설계서 R-6.1-evening, 미결20 닫힘). **성 토요일은 성 토요일이 스스로 지킨다** — 우선순위 1(성 목 · 금요일과 같은 칸 — 데이터의 등급 「대축일」, 아래 사용자 교정)이라, 성 토요일에 걸린 주요축일은 성 토요일에 밀려 부활 2주 월요일 뒤로 가고(2062-03-25 수태고지 → 4.3) 축일은 생략된다.
- 시각(일몰 또는 18시 이후)에 따라 저녁 전례를 먼저 보이고 색을 바꾸는 것은 사용자가 「하나의 방법」으로 꺼냈다 — **결정 전**이다(ADR-038 「검토한 대안 — 저녁 전례」 C: 같은 주소가 시각마다 다른 화면이 되고, 일몰은 위치 권한이 필요하다).

**사용자 교정(2026-10-15 — #349 리뷰 반영 중)**: 처음 구현은 「저녁 전례는 그날의 판정에서 빠지지만 이동 패스에서는 부활밤이 성 토요일의 주요축일을 민다」였고, 리뷰가 그날 판정(생략 축일을 민 것 = 보호 기간)과 이동 패스(부활밤)가 다른 모델을 쓴다고 잡았다. 사용자: 「성 토요일은 부활밤에 밀리지 않아. 성 토요일은 무조건 토요일에 있어야 하고, 부활밤을 칩으로 표현하면 될 것 같은데?」 — 부활밤은 칩일 뿐 판정에 끼지 않는다.
- 부활밤을 판정에서 빼기만 하면 성 토요일은 등급이 비어(데이터 「등급 없음」) 축일을 밀 힘이 없다 — 1900~2100 에서 6해(1967 · 1978 · 1989 · 2062 …)에 성모수태고지가 성 토요일의 대표(백색)가 된다(실데이터 시뮬레이션). 그래서 **성 토요일에 우선순위 1** 을 준다 — 같은 시뮬레이션에서 1900~2100 의 모든 날(73,414일) 대표 · 색 · 상태 · 옮겨지는 날짜 차이 0(달라지는 것은 생략 성인이 있는 성 토요일 27일의 칩 순서 — 성 토요일이 앞으로 — 와 옮겨 간 축일의 「밀어낸 것」 기록뿐).
- 자리는 **데이터**(사용자 결정 — 엔진 규칙 대신): `common-bible-data` `liturgical/calendar/temporal.md` 의 성 토요일 등급을 「대축일」로 — 성 목요일(2026-08-29)과 같은 원리(이 표의 등급 칸이 품계와 성격을 함께 정하는데 prec 1 칸은 대축일 · 대재일뿐; 대재일이면 `type` 이 fast 로 뒤집혀 「대재일」이 붙는다). 성격은 이름표(coords — 평일)에서 와서 `type` 은 weekday 그대로이고 소재일 표시도 그대로다. 엔진의 「등급 없는 temporal 평일 행 = 8」 규칙은 지운다.

**칩 줄(사용자 결정 2026-10-15 — 같은 리뷰)**: 휴대폰에서 「부활밤 · 저녁」 칩이 가로 스크롤 줄 끝에 숨었다(320px 에서 12px, 생략 성인이 있는 해는 0px). 사용자: 「칩이 여러 개면 단어처럼 한 행에 여러 개를 그냥 열거하고, 줄이 바뀌면 개행해서 보여주면 되지 않아?」 — **관측일 칩 줄은 줄바꿈**(가로 스크롤 대신). ADR-038 「칩은 후보 전부를 항상 노출」을 글자 그대로 지키고, 저녁 칩뿐 아니라 다른 날 숨던 칩도 함께 보인다.
