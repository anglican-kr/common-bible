# 코딩 실수 패턴 (Coding Pitfalls)

ADR이 "왜 이 결정을 했는가"를 다룬다면, 이 문서는 **"무엇을 조심해야 하는가"** 에 초점을 맞춘다. 처음에는 git 커밋 이력에서 반복된 실수 패턴을 뽑아 만들었다(2026-05-03 기준, 커밋 99개 가운데 fix 38개 = 38.4%).

## 사용법

- 한 주제에만 걸리는 함정은 그 주제 문서(`docs/topics/`)의 「함정」에 있다. 여기에는 절 제목과 대장 줄(「→ topics/…」)만 남는다. 여러 주제에 걸치는 함정은 여기에 전문을 둔다(2026-10-23부터). 글쓰기 교정은 `docs/writing.md`, 작업 방식 교정은 `docs/workflow.md`의 「함정」에 있다.
- 새 기능을 구현하기 전에 주제 문서의 함정과 여기의 공통 함정을 훑어본다. 코드 리뷰 때 같은 패턴이 되풀이되지 않는지 본다.
- 새 함정은 다음 번호(§41부터)를 받는다. 한 주제에만 걸리면 그 주제 문서에, 여럿에 걸치면 여기에, 글쓰기와 작업 방식이면 `writing.md`와 `workflow.md`에 쓴다. 코드 실수뿐 아니라 **사용자 교정**(작업 방식·판단을 바로잡은 것)과 **도메인 확정**(책자·기도서 대조로 굳어진 규칙)도 함정으로 적는다. 항목마다 날짜와 근거(원장 파일·커밋·PR)를 남긴다.
- 코드 주석과 머지된 원장이 「pitfalls §N」으로 가리키므로 번호는 다시 쓰지도 당기지도 않는다.

## 1. 비동기 타이밍의 경쟁 상태 — 가장 빈번

여러 비동기 작업이 동시에 진행될 때, 늦게 도착한 stale 콜백이 최신 상태를 덮어쓰는 패턴.

**사례:**
- `21540a0` — `updateAppIcons`: 테마를 빠르게 바꾸면 이전 컬러스킴의 `requestIdleCallback` + `loadOrigIcon` 체인이 뒤늦게 실행되어 새 navy 아이콘을 덮어씀.
- `5c41797` — 북마크 드로어 `open→close→open` 반복 시, 닫힘 애니메이션의 `finalize` 콜백이 새로 열린 드로어를 숨김.
- `fc6d374` — Drive 동기화에서 여러 요청이 동시에 401을 받으면 각자 `_silentSignIn()`을 호출, 재인증 콜백이 다중 실행되어 `_downloadAndMerge` → `_upload`가 중복되며 마지막 요청이 이전 기록을 덮어씀. `_isRefreshing` 플래그로 단일 진행 보장.
- e2e(2026-10-15, #348 리뷰 반영 중 확인) — `html { scroll-behavior: smooth }` 라 테스트의 `window.scrollTo(0, 600)` 은 애니메이트된다. 스크롤 도중 64px 를 넘는 순간 탭 바가 접히고, 그 상태를 보자마자 홈 탭을 누르면 남은 아래쪽 스크롤이 펼친 바를 다시 접는다 — `test_scroll_collapse_and_home_expands_without_nav` 가 누르는 시점에 따라 갈렸다(같은 코드로 통과하던 것이 이날은 매번 실패). 스크롤로 만든 상태를 바로 이어 조작하는 테스트는 `scrollTo({ top, behavior: 'instant' })` 로 경쟁 상태를 없앤다.

**방어 전략 (상황에 따라 선택):**

| 전략 | 적용 상황 | 구현 |
|------|----------|------|
| Generation 카운터 | 장기 비동기 체인 (이미지 디코드, 파일 페치) | 시작 시 `_gen` 캡처 → 완료 시 `_gen === currentGen` 일 때만 적용 |
| Sequence 번호 + clearTimeout | 타이머 기반 애니메이션 | 새 작업 시작 시 sequence 증가 + 이전 `setTimeout` 명시적 취소 |
| Singleton 플래그 | 토큰 갱신·재인증·일회성 동기화 | `_isRefreshing` 같은 플래그로 진행 중 재진입 차단 |
| Promise.race + timeout | 네트워크/폰트 로드 | `Promise.race([fetch(...), timeout(1500)])` 로 무한 대기 차단 |

**규칙:** 같은 작업이 여러 번 트리거될 수 있으면 "최신 호출만 유효" 또는 "동시에 하나만 유효" 패턴을 처음부터 설계한다.

## 3. 상태 갱신 누락 — UI 불일치

CRUD 작업 후 의존하는 UI 컴포넌트의 갱신 함수를 호출하지 않아, 데이터는 바뀌었으나 화면에 반영되지 않는 패턴.

**사례:**
- `03d7884` — 북마크 저장/수정/병합/삭제 후 헤더 북마크 버튼의 `has-bookmark` 상태가 갱신되지 않음. 모든 작업점에서 `refreshBookmarkHeaderBtn()` 호출 추가.
- `8762b3c` — long-press로 북마크 저장 시 헤더 아이콘 미갱신. (`03d7884`에서 클릭 경로는 고쳤으나 long-press 경로 누락)
- `ff39997` — division 뷰에서 `updatePageMeta()` 빈 호출이 `setTitleWithDivisionPicker()`가 설정한 제목을 덮어씀.
- `3303176` — 검색 자동 이동에서 내부·외부 `route()`가 둘 다 메타를 설정해 충돌.
- `7808c89` — 장 이동 시 절 선택 모드가 종료되지 않고 inert 셀렉터도 갱신되지 않아, 다음 장에서 비활성 요소가 잔류.

**규칙:**
- CRUD 함수마다 갱신 호출을 명시적으로 작성한다 (중앙 이벤트 시스템이 없는 이상 자동 동기화에 의존하지 말 것).
- **모든 진입점**(클릭, long-press, import, drop 등)에서 동일한 갱신 호출을 한다. 새 진입점을 추가할 때는 기존 진입점의 후처리를 그대로 따라간다.
- 라우팅이 중첩될 수 있으면 메타 설정 책임을 한 레이어로 한정한다.
- **페이지/뷰 전환 시 정리할 모드성 상태를 체크리스트로 관리**: 절 선택 모드, 모달, inert 속성, 임시 이벤트 리스너 등.

## 4. 조건문 논리 오류

방향성 역전, 분기별 검증 누락, 체크 위치 오류처럼 한눈에 보이지 않는 논리 결함.

**사례:**
- `16b70ae` — 폴더 드롭 순환 참조 검사에서 `_isDescendant`의 인자 순서가 반대였음. 실제로는 "드래그 대상이 드롭 위치의 조상인가"를 봐야 하는데 반대로 검사.
- `f154a56` — 같은 순환 참조 검사가 `position === "into"` 분기에만 있고 `before`/`after` 분기에는 누락. 폴더를 자기 조상의 형제로 드롭하면 통과.
- `3b9727f` — 단일 절 범위 초과 체크가 `hlVerseEnd != null` 블록 **내부**에만 있어, 정작 필요한 케이스에서 작동 안 함. 블록 밖으로 이동.
- 2026-10-17(PR #353 리뷰 — 원장 `docs/changes/2026-10-17-typecheck-batch-1.md`) — URL 에서 온 값의 검사 둘. `/john/abc` 의 장 번호는 `parseInt` 가 `NaN` 으로 내는데 `chapter < 1 || chapter > count` 가 둘 다 false 라 `john-NaN.json` 을 요청했다(`Number.isInteger` 를 더함). `/constructor` 는 구분 표 `DIVISION_LABELS[name]` 의 참거짓으로 가르다가 일반 객체가 물려받은 이름까지 구분이 됐다(`Object.hasOwn`).

**규칙:**
- 부모-자식 관계 검사 헬퍼는 인자 순서가 헷갈리지 않게 시그니처 위에 한 줄 주석:
  `// _isDescendant(ancestor, candidateId) — candidate가 ancestor의 후손인가?`
- 분기로 갈라진 동일 의도 검증이 있는지 확인. "이 검증이 다른 분기에도 필요한가?"를 한 번 더 묻는다.
- 가드 절은 가능한 한 **분기 시작 시점**에 두고, 분기 내부에 두면 의도하지 않은 패스가 생기지 않는지 확인.
- URL · 저장소에서 온 수는 범위 비교만으로 거르지 않는다 — `NaN` 은 모든 비교에서 false 다. `Number.isInteger`(또는 정규식으로 통째 검사 — `routing.js` 전례독서 쿼리의 `positive`)를 먼저.
- 바깥에서 온 문자열을 일반 객체의 키로 찾을 때는 `Object.hasOwn`(또는 `Map`) — `constructor` · `toString` · `__proto__` 도 참이다.

## 5. 모달/접근성 보일러플레이트 누락

모달 생성 시 포커스 트랩 누락, 드래그 시 포인터 이벤트 리스너 위치 오류처럼 "한 번 익히면 반복 적용해야 하는" 보일러플레이트를 빠뜨리는 패턴.

**사례:**
- `9b8a638` — 병합 다이얼로그가 표시되지만 `trapFocus()` 호출이 누락되어 키보드 사용자가 모달 외부로 빠져나갈 수 있었음.
- `5c41797`, `f154a56` — 드래그용 `pointermove`/`pointerup`/`pointercancel`을 행(row) 요소에 붙였더니, 드래그 중 포인터가 행 밖으로 이탈하면 이벤트를 놓쳐 ghost가 잔류. `document` 레벨로 이동, `pointerId` 필터링 추가.
- #348 리뷰(2026-10-15) — 캘린더 칸의 링크 이름(`aria-label`)을 보이는 이름과 다른 값(그날의 대표)으로 만들어, 사계재 · 기념일을 보이는 격자 평일 칸 54곳과 「연중24주」를 보이는 주일 칸 128곳(2025~2027)에서 보이는 글자가 접근 가능한 이름에 없었다 — WCAG 2.5.3 Label in Name, 음성 제어로 「추계재 누르기」가 안 된다. 링크 이름을 보이는 글자에서 만들게 고쳤다.
- #348 리뷰(같은 날) — 달 이동 링크가 `#app`을 통째로 다시 그려 누른 링크가 사라지자 포커스가 body로 빠졌다(WCAG 2.4.3) — 달을 넘길 때마다 건너뛰기 링크 · 헤더 · 탭부터 다시 지나와야 했다. 다시 그리기 전에 누른 컨트롤의 자리(`data-focus-key`)를 남기고 새 화면의 같은 자리로 포커스를 돌려준다(`views.js focusPendingBook`과 같은 방식). 전례독서 화면(#346)도 같은 결함이었다 — 2026-10-17 그 도우미를 `helpers.js createFocusMemory`로 올려 두 화면이 함께 쓴다.
- 2026-10-17(전례독서 화면에 옮기며 찾은 것) — 포커스만 돌려주면 모자랐다. 새 장을 받아야 하는 다시 그리기(세트 · 트랙 · 칩 · 카드 · 날짜)는 `route()` 의 스켈레톤이 한 프레임 그려지며 문서가 짧아져 스크롤이 맨 위로 눌린다 — 누른 컨트롤이 아래로 밀리고(모바일 최대 약 250px), 화면 아래쪽 컨트롤이면 화면 밖에 포커스가 남는다(2.4.7). 받을 것이 없는 다시 그리기(같은 장의 본기도 대체안)는 스크롤이 그대로라, 같은 화면 안에서도 누르는 컨트롤마다 달랐다. 누른 때의 화면 위치로 돌려준다. 그사이 데스크톱 머리의 검색 줄(최대 4rem)이 펼쳐졌다가 돌아온 뒤 다시 접힌다(스크롤이 0 으로 눌려서) — 스크롤 고정(scroll anchoring)이 있는 브라우저는 그 접힘 동안 내용을 붙잡으므로 **지금 레이아웃에서의 화면 위치(viewport top)**로, 없는 브라우저(Safari 26 까지)는 접힘이 내용을 옮기므로 **화면 루트 안 위치**로 둔다. 루트 안 위치만 쓰던 첫 구현은 장 받기가 0.1초를 넘으면 컨트롤이 그 줄 높이(약 46px)만큼 아래로 내려앉았다 — 로컬 서버는 너무 빨라 보이지 않았고, 위치 e2e 는 그 줄이 없는 모바일뿐이었다(PR #350 리뷰).
- PR #350 리뷰(2026-10-17) — 복원이 포커스를 무조건 옮겨, 새 장을 받는 사이 독자가 머리의 검색 칸으로 옮겨 치던 글자 · Enter 를 누른 세그먼트로 빼앗았다(팝오버를 열었으면 그 밖으로 끌어냈다). 누른 링크와 함께 포커스가 body 로 떨어졌을 때만 돌려준다.
- 2026-10-17(known-issues §10) — 화면마다 `createFocusMemory` 를 잇던 방식은 뷰 루트 밖 컨트롤(성서 목록의 구분 탭 — `route()` 가 슬롯을 비운다)과 `await` 뒤에 그려지는 목록을 덮지 못해, 구분 탭 · 검색의 「← 이전 · 다음 →」는 main 부터 Enter 를 누르면 포커스가 body 로 빠졌다. 라우터로 올렸다(ADR-031 §5) — 전역 `<a>` 인터셉터가 누른 자리를 재고 `route()` 가 시작에서 꺼내 `finally` 에서 돌려준다. 함께 본 것: 검색 결과 화면은 다 그린 뒤 `window.scrollTo(0, 0)`(루트의 smooth)을 호출했다 — 위치 복원이 「이미 제자리」로 보고 지나가면 그 애니메이션이 이어져 누른 링크를 밀 수 있는 순서라 즉시 스크롤로 바꿨다(기본 창 크기에서는 결과가 한 화면이라 드러나지 않았다). 「본문 바로가기」(`#app`)도 같은 인터셉터가 `route()` 로 먹어 포커스가 본문으로 가지 않았다(main 부터) — 페이지 안 링크는 갈라 대상으로 포커스만 옮긴다.
- PR #354 Copilot 1회차(2026-10-17) — 동기화 스낵바(`_showSyncSnackbar` — `drive-sync.js`)는 live region도 `role`도 없는 평범한 `div`라, 동기화 오류 · 재연결 · 「파일도 삭제」 실패 같은 안내 아홉 곳이 화면 낭독기에는 들리지 않았다(WCAG 4.1.3 상태 메시지). 같은 함수를 쓰는 곳 가운데 절 복사(`bookmark-verse-select.js`)만 `announce()`를 따로 호출했다. 해결: 스낵바 함수가 같은 글을 live region(`#a11y-announce`)에도 넣고, 따로 부르던 `announce()`는 지웠다(두 번 읽지 않게).

**모달 생성 4단계 체크리스트:**

```
□ 표시 전 hidden=true (또는 .hidden 클래스 부여)
□ 표시 직후 trapFocus(modal) 호출, 반환값을 cleanup용으로 보관
□ requestAnimationFrame 안에서 첫 액션 버튼에 .focus()
□ 닫을 때: 트랩 해제 + 임시 이벤트 리스너 제거 + 상태 초기화
```

**드래그 핸들러 규칙:** 포인터 추적은 항상 `document` 레벨. 멀티터치 구분이 필요하면 `pointerId`로 필터링.

**상태 메시지 규칙:** 눈에만 보이는 알림(스낵바 · 토스트)은 같은 글을 live region에도 넣는다 — 알림을 띄우는 함수 한 곳에서. 호출하는 쪽마다 `announce()`를 덧붙이면 빠뜨리는 곳이 생기고, 한 곳에서 넣은 뒤에는 따로 호출하면 두 번 읽힌다. 저절로 사라지는 알림(3.5초)이 **유일한** 신호여서는 안 되는 안내 — 되돌릴 수 없는 작업이 끝나지 않았다는 것처럼 놓치면 사용자가 잘못 믿게 되는 것 — 는 다시 찾아갈 화면(설정)에도 남긴다(WCAG 2.2.1, PR #354 사용자 `/code-review` 12번 — 「파일도 삭제」 실패는 Drive 줄 아래 `.settings-drive-note`, 다시 연결할 때까지).

**접근 가능한 이름 규칙:** `aria-label` 로 이름을 덮어쓸 때는 보이는 글자를 그대로 넣는다(줄여 보이면 이름도 그 줄임 — 「연중24주」). 보이는 이름과 링크 이름을 서로 다른 함수 · 필드로 만들지 않는다 — 한쪽만 바뀌어 어긋난다. 실데이터가 있으면 「보이는 이름 ⊂ 링크 이름」을 전수로 검사한다(`calendar.data.test.js`).

**다시 그리는 화면의 포커스 규칙:** 링크 · 단추가 자기 화면을 다시 그리면(같은 뷰 안의 이동 · 필터 · 세그먼트) 새 화면의 같은 컨트롤로 포커스를 돌려준다 — 누른 때의 화면 위치에. 링크에는 `data-focus-key`(새 화면에 같은 컨트롤이 없을 수 있으면 넘겨받을 컨트롤의 `data-focus-fallback`)만 단다 — 재고 돌려주는 것은 라우터다(ADR-031 §5: 인터셉터가 이동 직전에 `focusSpotOf` 로 재고, `route()` 가 시작에서 꺼내 `finally` 에서 `restoreFocusSpot` — 자리는 그 누름의 route 에만 쓰인다). 커밋 뒤 스크롤을 움직이는 뷰는 즉시(`behavior: "instant"`)로 — 부드러운 스크롤이 이어지면 복원한 위치를 민다. 키는 선택자 문자열이 아니라 `dataset` 값으로 찾는다 — 키가 데이터(전례일 id)라 값 비교는 이스케이프가 필요 없다(따옴표 선택자는 키의 `"` · `\` 에서 깨진다; 콜론 · 한글은 따옴표 안에서 문제없다). 그 컨트롤이 사라졌으면 가장 가까운 대체(`data-focus-fallback` — 「오늘」 · 다른 쪽 링크)로. 페이지를 넘기는 컨트롤도 같다 — 검색 결과의 「다음 →」 · 「← 이전」은 새 페이지에서도 **누른 컨트롤 그대로**(사용자 결정 2026-10-17 — 결과 목록 맨 위로 보내는 안 대신: 전례독서의 「다음날」과 같은 규칙이고 Enter 를 거듭 눌러 넘길 수 있다; 마지막 페이지라 「다음 →」이 없으면 「← 이전」). **포커스가 body 일 때만 돌려준다** — 다시 그리는 사이 독자가 다른 데로 옮겼으면 그대로 둔다. 마우스 · 탭으로 누른 복원은 `focus({ focusVisible: false })` — iOS(WebKit)는 탭으로 링크에 포커스를 주지 않아 뒤의 스크립트 포커스에 링을 그린다(책 카드 `43db624` 와 같은 일).

## 9. 글로벌 이벤트 핸들러 협력 부족

전역 인터셉터(예: `document.addEventListener("click", ...)`)가 하위 요소의 자체 핸들러가 이미 처리한 이벤트를 **다시 처리**해 의도치 않은 동작이 발생하는 패턴.

**사례:**
- `d25b8da` — 전역 클릭 인터셉터가 SPA 라우팅을 위해 `<a href>` 클릭을 가로챘는데, `buildSheetPagination`의 `href="#"` 링크는 자체 핸들러에서 `e.preventDefault()`를 이미 호출함. 인터셉터가 `e.defaultPrevented` 미체크로 `route()`를 또 호출.
- #348 리뷰(2026-10-15) — 반대 방향의 같은 결함: 탭 바의 탭 처리기(홈 · 캘린더 · 북마크 · 설정)가 전역 인터셉터의 **수정 키 조건**(⌘ · Ctrl · Shift · Alt · 가운데 단추 → 브라우저에 맡김)을 따르지 않았다. ⌘ · Ctrl-클릭에서 (a) 홈 · 캘린더 탭은 `preventDefault` 뒤 같은 탭에서 이동해 새 탭 열기를 무시했고, (b) 캘린더 · 북마크 · 설정 탭은 인터셉터가 빠져 브라우저가 새 탭을 여는데도 스크롤 복원 요청을 먼저 세워, 그 요청이 남아 다음 링크 이동이 옛 스크롤 위치로 튀었다(e2e 재현 — 장 최상단 대신 600px). 탭 히스토리 도입(`687a071`, ADR-031 — #194)부터 있던 결함을 캘린더 탭이 그대로 물려받았다.

**규칙:**
- 글로벌 이벤트 핸들러는 가장 먼저 `if (e.defaultPrevented) return;` 으로 협력 게이트를 둔다.
- 자체 처리하는 하위 핸들러는 **반드시** `e.preventDefault()` (필요 시 `stopPropagation()`)를 호출해 의도를 표현한다.
- 가능하면 글로벌 인터셉터 스코프를 좁힌다 (예: `closest("a[href]:not([data-internal])")` 같이 명시적 마커).
- 링크에 다는 처리기는 전역 인터셉터와 **같은 조건으로 먼저 빠진다** — 새 탭 · 새 창 클릭은 `window.appHelpers.isModifiedClick(e)` 로 거른다(인터셉터도 이 함수를 쓴다 — 조건이 한 곳). 복원 요청 · 포커스 기억 같은 부수 효과는 이 화면에서 이동이 일어날 때만 남긴다.

## 10. 플랫폼별 quirk 무시

웹 표준대로 작성했지만 iOS Safari, Android, 사용자 환경 설정(예: `prefers-reduced-motion`) 때문에 회귀하는 패턴.

**사례:**
- `f043f78` — 모달 열림 시 `body { overflow: hidden }` 만으로는 iOS Safari의 배경 스크롤이 막히지 않음. `position: fixed` + 현재 스크롤 위치 보존 + 닫을 때 복원 패턴 필요.
- `da21f11` — 드로어 슬라이드 애니메이션이 `prefers-reduced-motion: reduce` 환경에서도 그대로 재생됨. 미디어 쿼리로 비활성화.

**규칙:**
- iOS Safari, Android Chrome 둘 다에서 직접 검증한다 (특히 모달·바텀시트·키보드 노출 동작).

- 스크롤 락 같은 전형 패턴은 **검증된 헬퍼 함수**로 추출해 매번 같은 구현을 쓰게 한다 (구현 노하우가 휘발되지 않도록).

## 11. 비동기 race 가드 — 단일 체크포인트의 함정

`async` 함수가 여러 `await` 지점을 거치면, 각 await 사이마다 외부 상태(사용자 의도, 다른 흐름의 결과 등)가 바뀔 수 있다. race 가드를 함수 진입 시점이나 첫 번째 await 직후에만 두면, 그 다음 await가 끝난 시점에 이미 stale한 결정에 따라 상태를 덮어쓰는 패턴.

**사례 (Phase 2h PKCE 마이그레이션 — Bugbot PR #54·#57):**

- `c4d0c72` — `_attemptSilentRefresh`가 `_state` 기반 race 가드만 가짐. 사용자가 silent refresh 진행 중 `signOut()`/`disable()`을 호출하면 `_state`는 그대로(혹은 정상 진행 중인 값)이지만 `localStorage["bible-drive-sync"]`는 `"0"`으로 바뀜 → state 가드만 통과시켜 IDLE/NEEDS_CONSENT로 전이하면 사용자가 끊은 sync를 다시 살림. 해결: `localStorage.getItem(SYNC_ENABLED_KEY) === "0"` 검사 추가.
- `f090c83` — 같은 함수에 race 가드를 진입 시점에만 둠. 그러나 `await refreshAccessToken(...)` 직후 race 가드를 통과한 뒤에도 `await refreshStore.saveRefreshToken(...)` (rotation) 또는 `await refreshStore.clearRefreshToken()` (invalid_grant) 같은 IDB await가 남아있음. 그 IDB await 동안 사용자가 `disable()`을 호출하면 후속 `_transition(IDLE/NEEDS_CONSENT)`이 다시 `SYNC_ENABLED_KEY = "1"`로 덮어씀. 해결: 매 `await` 직후마다 race 가드를 다시 검사. 단계 4 후 `enable()`이 동기적으로 DISABLED를 빠져나가지 않으므로 state-based 가드만으로 cold-start 경로 보호 불가능 — flag-based 가드가 필수.
- (2026-10-17, PR #353 리뷰 — `docs/changes/2026-10-17-typecheck-batch-1.md`) — 업데이트 토스트 `showUpdateToast`의 「이미 떴나」 검사가 대기 SW에 버전을 묻는 `await`(최대 1.5초) 앞에만 있어, 그 사이 설정의 「업데이트 지금 확인」이 또 호출하면 둘 다 검사를 지나 같은 id의 토스트가 둘 붙었다. 해결: `await` 뒤에 한 번 더 본다. 동기화 레이어 밖에서도 같은 경우가 나온다.
- (2026-10-17, `docs/changes/2026-10-17-sync-signout-inflight.md`) — 동기화 사이클 `_syncCycle()`에는 같은 규칙이 빠져 있었다. 파일 찾기 · 내려받기 · 올리기 대기 중에 `signOut()`이 오면, 대기 뒤에 만든 업로드가 로그아웃 뒤에 더한 북마크까지 담아 `Bearer null`로 나갔다(실제 Drive는 401 — 내려받기 대기였다면 원격 자료를 로컬에 쓰고, 올리기 대기였다면 비운 캐시를 다시 채웠다). e2e는 가짜 Drive가 토큰 없는 요청을 받아 주어 가끔 실패하는 테스트로만 보였다. 해결: 대기마다 `_leftSyncing(at)` — 상태가 SYNCING이 아니면 멈춘다. 여기서는 state-based가 맞다(DISABLE은 SYNCING에서 동기적으로 DISABLED로 전이한다).
- (2026-10-17, 같은 원장 — 머지 전 검토 4번) — 연결 해제의 「파일도 삭제」는 `deleteRemoteFile()`을 기다린 뒤 `signOut()`을 호출해, 지우는 동안 동기화가 그대로 돌았다. 진행 중 사이클의 새 파일 올리기가 지우기 뒤에 도착하면 방금 지운 파일이 되살아났다. 해결: 지우기 전에 사이클을 멈추고, 진행 중 사이클이 이미 보낸 요청이 끝나기를 기다린 뒤(`_cycleDone`) 찾아 지운다.
- (2026-10-17, 같은 원장 — 사용자 `/code-review` 2 · 9 · 10번) — 그 기다림에 상한이 없었고, 토큰은 상태 기계에 둔 채였다. ① 기다리는 동안 앱을 닫으면 켬 표지는 "0"이라 「연결 해제됨」으로 보이지만 폐기하지 않은 refresh token이 IDB에 남았다(다시 「연결」을 누른 뒤 동의를 취소하면 옛 계정이 조용히 다시 연결됐다). ② 그사이 다시 연 설정은 「해제」를 그려 「파일 유지」로 한 번 더 로그아웃할 수 있었고, 그 뒤에도 미리 잡아 둔 토큰으로 찾기 · 지우기가 나갔다. ③ 멈춤은 누른 탭의 상태뿐이라, 연결된 다른 탭은 비워진 공유 캐시를 보고 파일을 다시 만들 수 있었다. 해결: 페이지가 닫혀도 남으면 안 되는 것(IDB refresh token · 켬 표지 · 계정 키)을 네트워크 작업보다 먼저 지우고, 토큰은 상태 기계에서 곧바로 빼 그 함수 안에만 둔다(설정은 곧바로 「연결」). 기다림은 10초까지 — 끝나지 않았으면 지운 뒤 한 번 더 기다렸다 다시 지운다. 다른 탭은 켬 표지의 `storage` 이벤트로 멈춘다. 토큰은 지운 뒤 그 함수가 폐기한다.
- (2026-10-17, 같은 원장 — 사용자 `/code-review` 1 · 7번, main부터) — 사이클은 대기마다 **상태**는 다시 봤지만 **자료**는 다시 읽지 않았다. 시작할 때 읽은 로컬 사본으로 병합한 뒤 `_applyMergedDoc`이 로컬 문서 전체를 덮어써, 찾기 · 내려받기를 기다리는 동안 저장한 북마크 · 설정 · 읽던 위치가 사라졌다. 그사이 들어온 동기화 요청은 SYNCING이라 버려졌고, 304 갈래는 대기 전의 값으로 「변경 없음」을 판정해 그 편집을 올리지 않았다. 해결: 내려받기를 기다린 뒤에 로컬을 읽고(그 읽기와 덮어쓰기 사이에 대기가 없다), 「동기화됨」은 실제로 올린 본문의 값으로 적고, 도는 동안 들어온 사용자 요청은 끝난 뒤 한 번 더 돈다.

**규칙:**

- 비동기 함수에서 race 가드는 **모든 await 직후에 재검사**한다. 진입 시점 한 번만으로 충분하다고 가정하지 말 것.
- 사용자 의도를 신뢰성 있게 신호하는 단일 출처(여기서는 `localStorage["bible-drive-sync"]`)를 정해 모든 race 가드가 같은 출처를 참조하게 한다.
- state machine을 단순화하면서 동기 dispatch가 사라졌다면, 기존 state-based race 가드가 더 이상 작동하지 않는지 의심하라. flag-based 가드로 대체하거나 보강해야 할 수 있다.
- 회귀 방어 테스트: 외부 제어 가능한 `Promise`로 await를 hold한 채 `disable()`을 끼워 넣어, 각 await 시점의 race window를 명시적으로 시뮬레이션한다 (`tests/unit/state-machine.test.js` 26a/b/c · 44-46 참고). e2e에서는 가짜 서버의 응답을 쥐고 있다가 푼다(`test_drive_sync.py` `FakeDrive.hold_list`).
- e2e의 가짜 서버는 토큰 · 권한 검사도 실제처럼 한다 — 다 받아 주는 가짜는 클라이언트의 결함을 가리거나 가끔 실패하는 테스트로 보이게 한다.
- 대기 뒤에 낡는 것은 상태만이 아니다 — 대기 전에 읽은 **자료**(로컬 사본 · 토큰 · 캐시 값)도 낡는다. 덮어쓰는 쓰기는 대기 없이 바로 앞에서 읽은 값으로 한다. 도중에 들어온 요청은 버리지 말고 한 번으로 모아 끝난 뒤 다시 돈다 — 다시 시작은 다음 마이크로태스크에(끝나는 사이클의 `finally` 앞이면 새 사이클이 「아직 도는 중」을 보고 시작되지 못한다).
- 되돌릴 수 없는 작업(원격 삭제) 앞에서는 그것을 되돌릴 수 있는 흐름(진행 중 사이클 · 예약된 올리기)을 먼저 멈추고, **이미 보낸 요청이 끝나기를 기다린다** — 멈추기만 해서는 이미 나간 요청이 뒤늦게 도착하는 것을 막지 못한다. 그 기다림에는 상한을 둔다(멈춘 요청 하나가 로그아웃 전체를 붙잡지 않게). 페이지가 닫혀도 남으면 안 되는 것(자격 증명)은 기다림 · 네트워크 작업보다 먼저 지운다. 멈춤은 탭마다다 — 다른 탭은 공유 표지를 듣게 한다(`storage` 이벤트).
- **동기화 사이클의 확인은 대기마다 한 줄씩 둔다 — 진행 중인 요청을 취소하는 구조(사이클마다 `AbortController`)나 공통 대기 래퍼로 바꾸지 않는다**(사용자 결정 2026-10-17 — 로그아웃 수정의 머지 전 `/code-review`가 「손으로 넣은 확인은 빠뜨리기 쉽다」며 제안했다, 원장 `docs/changes/2026-10-17-sync-signout-inflight.md`). 이유: 같은 파일의 `_attemptSilentRefresh`도 대기마다 다시 본다(위 규칙) · 취소를 넣으려면 OAuth · Drive 전송 함수(`transport.js`)마다 신호를 넘겨야 한다 · 로그아웃 전에 이미 나간 업로드는 로그아웃 전의 편집이라 끝나게 둔다. 빠뜨림은 테스트가 막는다 — 멈추는 자리마다 유닛 하나(`state-machine.test.js` 44-50 — 확인 한 줄을 빼면 그 자리의 테스트가 실패하는 것을 변이 검사로 확인했다). **재검토 조건**: 전송 계층을 다른 이유로 고쳐 요청마다 신호를 받게 될 때, 또는 사이클의 대기가 지금(여섯)보다 크게 늘 때. 리뷰가 같은 제안을 다시 내면 이 줄을 근거로 넘긴다.

## 35. 외부 입력은 타입만 보지 말고, 그 값을 받는 코드가 다룰 수 있는 형식인지 검사한다 — 가져오기 검사가 리뷰마다 샜다 (리뷰, 2026-10-19)

밖에서 들어오는 값(가져오기 파일 · 공유 링크 · 동기화 문서)을 「문자열이다 · 수다 · 배열이다」로만 거르면, 통과한 값이 그 값을 쓰는 코드에서 깨진다. 기준은 타입 선언이 아니라 그 값이 흘러가는 모든 곳이다 — 객체의 키, 주소, 재귀, 배열로 펼치기, 저장 한도.

**사례:**
- PR #359(북마크 가져오기, ADR-040) — 처음 검사는 타입과 「절 범위의 구간이 모두 읽히는가」를 봤다.
  - Copilot 1회차가 두 갈래를 찾았다 — 객체 기본 속성 이름인 id(`toString` — 동기화 저장소가 id를 일반 객체의 키로 써 목록 읽기가 깨진다), 북마크에 붙은 `children`(저장소가 어떤 항목의 자식이든 훑는다).
  - 2회차(Copilot + 자체 리뷰어 셋)가 다시 여섯 갈래를 찾았다 — 큰 수 · 큰 범위 · 공백 · 거꾸로 된 범위의 절 범위(합치기 · 주소 해석 · 강조), `?` · `#` · `..`가 든 폴더 id(모아 읽기 주소), 수천 단 폴더(재귀), `1e400` 날짜(저장하면 `null`), 지금 목록과 종류가 다른 같은 id(동기화가 옛 종류로 되돌림), 저장 한도를 넘는 목록(조용히 실패). 모두 타입은 맞았다.
  - 2회차 뒤 자체 리뷰가 그 크기 검사를 다시 깼다 — 목록 JSON에 둔 고정 예산(600,000자)은 부모 id를 자식마다 되풀이하는 저장 구조(1,000자 id면 21배)를 놓쳐 저장 실패를 들였고, 메모가 긴 자기 백업(2배)은 막았다. 저장할 문서를 쓰지 않고 만들어 재는 것으로 바꿨다.
- 주소의 절 범위(2026-10-21, known-issues §15) — 가져오기 검사가 막은 큰 범위와 되풀이한 구간이 공유 링크로는 그대로 들어왔다. 라우터가 여러 구간을 절 하나하나로 펼쳐, 처음 여는 링크가 시작 화면에서 멈췄다. 같은 절 범위가 파일 · 주소 · 동기화 세 입구로 들어오는데, 검사는 파일 입구에만 있었다. 검사를 `verse-spec.js isWellFormedSpec`으로 옮겨 주소 해석도 같이 쓰게 했다. 검사 없이 이미 저장된 북마크(1.6.4 이하에서 들인 것 — 그 기기에 남은 것 · 동기화로 간 것)는 아직 다시 검사하지 않는다(known-issues §15).
  - 그 PR의 리뷰에서 주소의 앞뒤 쉼표를 걷기로 했다(사용자 결정 2026-10-21). 처음 떠올린 `/^,+|,+$/g`는 쉼표가 길게 이어진 뒤 다른 글자가 오면 제곱 시간이 걸렸다(쉼표 4만 개에 약 1초, 두 배면 네 배). 이 함수는 스크롤 프레임마다 돌아, 그대로 썼다면 막으려던 멈춤을 다른 길로 다시 열었을 것이다. 반복문으로 걷었다.

**규칙:**
- 검사를 쓰기 전에 그 값이 가는 곳을 끝까지 따라가 목록을 만든다 — 객체의 키 · 주소 · 재귀 깊이 · 펼치기 · `JSON.stringify` · 저장 한도. 그리고 각 소비처가 받는 형식을 기준에 넣는다.
- 같은 값이 여러 입구로 들어오면(가져오기 파일 · 주소 · 동기화 문서) 검사를 입구마다 따로 쓰지 말고, 하나를 두고 모두 함께 쓴다. 검사는 그 값을 다루는 모듈에 둔다(절 범위면 `verse-spec.js`). 한 입구를 고칠 때는 다른 입구도 같은 값을 받는지 찾는다.
- 바깥 입력에 쓰는 정규식은 되돌아가기가 제곱이 되지 않는지 본다. 앞이 고정되지 않은 반복(`,+$` · `\s+$`)은 같은 글자가 길게 이어진 뒤 다른 글자가 오면 시작점마다 끝까지 다시 훑는다. 자주 도는 코드(스크롤 · 입력마다)에서는 반복문으로 다듬고, 긴 입력의 시간을 테스트로 묶는다(`tests/unit/routing.test.js`의 「긴 쉼표 줄」).
- 받을 형식은 「앱이 쓰는 형식」으로 정한다(허용 목록). 깨지는 경우를 하나씩 막는 검사(거부 목록)는 다음 리뷰에서 또 샌다. 앱의 직렬화 함수가 만드는 값이 모두 통과하는지는 테스트로 묶는다 — 직렬화가 바뀌면 검사도 바뀌어야 한다(`tests/unit/bookmark.test.js`의 합성 장 테스트).
- 저장 한도 같은 플랫폼 제약은 가장 빠듯한 엔진으로 정한다. Chromium은 localStorage를 문자 수로 세지만, Safari는 바이트로 세고 한글은 한 글자에 2바이트다(ADR-040 「검증」).
- 크기처럼 다른 코드가 만들어 내는 양은 배율로 어림하지 말고, 그 코드로 실제 결과를 만들어 잰다(쓰지 않고) — 어림한 배율은 그 코드가 바뀌거나 입력의 모양이 달라지면 양쪽으로 샌다.

## 부록 B: 같은 시각 효과를 여러 곳에 적용할 때

CSS의 시각 효과(모서리 라운드 평탄화, 강조 색 등)를 인접 요소 사이에 적용할 때, 적용 대상의 **레이아웃 모드**를 가정한 채 작성하면 다른 모드에서 깨진다.

**사례:**
- `b030aa6` — 검색·딥링크 강조에서 연속 절의 모서리를 평탄화하는 규칙이 인라인 본문에는 잘 동작했으나, 시 구절(block) 레이아웃에서는 잘못 평탄화되어 모서리가 부자연스럽게 잘림.

**규칙:** 인라인 / 블록 / flex / grid 등 레이아웃 모드별로 시각 효과를 한 번씩 시각 검증한다. 가능하면 셀렉터에 레이아웃 컨텍스트(`.poetry-block` 등)를 명시.

## 패턴 추가 가이드

새로운 실수 유형을 발견하면 다음 형식으로 추가:

```markdown
## N. 카테고리명 — 짧은 부제 (선택)

한 문단의 패턴 설명.

**사례:**
- `<커밋해시>` — 한 줄 요약.

**규칙:**
- 액션 가능한 규칙 1.
- 액션 가능한 규칙 2.
```

가능하면 실제 커밋 해시를 첨부해 검증 가능하게 한다.
