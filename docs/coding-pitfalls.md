# 코딩 실수 패턴 (Coding Pitfalls)

이 문서는 본 프로젝트의 git 커밋 이력에서 추출한 **반복 발생하는 실수 패턴**을 카테고리별로 정리한 것이다.
ADR이 "왜 이 결정을 했는가"를 다룬다면, 이 문서는 **"무엇을 조심해야 하는가"** 에 초점을 맞춘다.

## 사용법

- 새 기능을 구현하기 전에 관련 카테고리의 체크리스트를 훑어본다.
- 코드 리뷰 시 동일 패턴이 재발하지 않는지 확인한다.
- 새로운 실수 유형이 발견되면 카테고리를 추가하거나 기존 카테고리에 사례를 덧붙인다 (살아있는 문서).
- 코드 실수만 받는 곳이 아니다 — **사용자 교정**(작업 방식·판단을 바로잡은 것)과 **도메인 확정**(책자·기도서 대조로 굳어진 규칙)도 여기 쌓는다. 항목마다 날짜와 근거(원장 파일·커밋·PR)를 남긴다.

기준 시점: 2026-05-03 (총 99개 커밋, 그중 fix 38개 = 38.4%).

## 1. 비동기 타이밍 경합 — 가장 빈번

여러 비동기 작업이 동시에 진행될 때, 늦게 도착한 stale 콜백이 최신 상태를 덮어쓰는 패턴.

**사례:**
- `21540a0` — `updateAppIcons`: 테마를 빠르게 바꾸면 이전 컬러스킴의 `requestIdleCallback` + `loadOrigIcon` 체인이 뒤늦게 실행되어 새 navy 아이콘을 덮어씀.
- `5c41797` — 북마크 드로어 `open→close→open` 반복 시, 닫힘 애니메이션의 `finalize` 콜백이 새로 열린 드로어를 숨김.
- `fc6d374` — Drive 동기화에서 여러 요청이 동시에 401을 받으면 각자 `_silentSignIn()`을 호출, 재인증 콜백이 다중 실행되어 `_downloadAndMerge` → `_upload`가 중복되며 마지막 요청이 이전 기록을 덮어씀. `_isRefreshing` 플래그로 단일 진행 보장.
- e2e(2026-10-15, #348 리뷰 반영 중 확인) — `html { scroll-behavior: smooth }` 라 테스트의 `window.scrollTo(0, 600)` 은 애니메이트된다. 스크롤 도중 64px 를 넘는 순간 탭 바가 접히고, 그 상태를 보자마자 홈 탭을 누르면 남은 아래쪽 스크롤이 펼친 바를 다시 접는다 — `test_scroll_collapse_and_home_expands_without_nav` 가 누르는 시점에 따라 갈렸다(같은 코드로 통과하던 것이 이날은 매번 실패). 스크롤로 만든 상태를 바로 이어 조작하는 테스트는 `scrollTo({ top, behavior: 'instant' })` 로 경합을 없앤다.

**방어 전략 (상황에 따라 선택):**

| 전략 | 적용 상황 | 구현 |
|------|----------|------|
| Generation 카운터 | 장기 비동기 체인 (이미지 디코드, 파일 페치) | 시작 시 `_gen` 캡처 → 완료 시 `_gen === currentGen` 일 때만 적용 |
| Sequence 번호 + clearTimeout | 타이머 기반 애니메이션 | 새 작업 시작 시 sequence 증가 + 이전 `setTimeout` 명시적 취소 |
| Singleton 플래그 | 토큰 갱신·재인증·일회성 동기화 | `_isRefreshing` 같은 플래그로 진행 중 재진입 차단 |
| Promise.race + timeout | 네트워크/폰트 로드 | `Promise.race([fetch(...), timeout(1500)])` 로 무한 대기 차단 |

**규칙:** 같은 작업이 여러 번 트리거될 수 있으면 "최신 호출만 유효" 또는 "동시에 하나만 유효" 패턴을 처음부터 설계한다.

## 2. SPA 경로 해석 오류 — 2회 반복 재발

상대 경로(`./data/...` 또는 `data/...`)는 현재 URL을 기준으로 해석되므로, History API 라우팅으로 하위 URL(`/bible/john/3`)에서 새로고침하면 자원 로드가 깨진다.

**사례 (같은 버그 형태가 2번 반복):**
- `45eba01` — `index.html`의 상대 경로를 절대 경로로 수정.
- `730aafe` — 같은 버그가 `js/app.js`의 `DATA_DIR` 및 fetch 경로에 또 있어 별도 커밋으로 수정.

**규칙:**
- 모든 자원 경로는 `/`로 시작 (예: `/data/books.json`, `/assets/icons/...`).
- 데이터 페치는 상수화된 `DATA_DIR`을 통해서만 접근한다.
- 검증: 개발 서버에서 `/bible/john/3` 같은 하위 URL에 직접 진입했을 때 모든 자원이 200 OK인지 확인.

관련 ADR: `009-history-api-routing.md`.

## 3. 상태 갱신 누락 — UI 불일치

CRUD 작업 후 의존하는 UI 컴포넌트의 갱신 함수를 호출하지 않아, 데이터는 바뀌었으나 화면에 반영되지 않는 패턴.

**사례:**
- `03d7884` — 북마크 저장/수정/병합/삭제 후 헤더 북마크 버튼의 `has-bookmark` 상태가 갱신되지 않음. 모든 작업점에서 `refreshBookmarkHeaderBtn()` 호출 추가.
- `8762b3c` — long-press로 북마크 저장 시 헤더 아이콘 미갱신. (`03d7884`에서 클릭 경로는 고쳤으나 long-press 경로 누락)
- `ff39997` — division 뷰에서 `updatePageMeta()` 빈 호출이 `setTitleWithDivisionPicker()`가 설정한 제목을 덮어씀.
- `3303176` — 검색 자동 이동에서 내부·외부 `route()`가 둘 다 메타를 설정해 충돌.
- `7808c89` — 장 이동 시 절 선택 모드가 종료되지 않고 inert 셀렉터도 갱신되지 않아, 다음 장에서 비활성 요소가 잔류.

**규칙:**
- CRUD 함수마다 갱신 호출을 명시적으로 작성한다 (중앙 이벤트 시스템이 없는 이상 자동 동기화에 의존하지 말 것).
- **모든 진입점**(클릭, long-press, import, drop 등)에서 동일한 갱신 호출을 한다. 새 진입점을 추가할 때는 기존 진입점의 후처리를 그대로 따라간다.
- 라우팅이 중첩될 수 있으면 메타 설정 책임을 한 레이어로 한정한다.
- **페이지/뷰 전환 시 정리할 모드성 상태를 체크리스트로 관리**: 절 선택 모드, 모달, inert 속성, 임시 이벤트 리스너 등.

## 4. 조건문 논리 오류

방향성 역전, 분기별 검증 누락, 체크 위치 오류처럼 한눈에 보이지 않는 논리 결함.

**사례:**
- `16b70ae` — 폴더 드롭 순환 참조 검사에서 `_isDescendant`의 인자 순서가 반대였음. 실제로는 "드래그 대상이 드롭 위치의 조상인가"를 봐야 하는데 반대로 검사.
- `f154a56` — 같은 순환 참조 검사가 `position === "into"` 분기에만 있고 `before`/`after` 분기에는 누락. 폴더를 자기 조상의 형제로 드롭하면 통과.
- `3b9727f` — 단일 절 범위 초과 체크가 `hlVerseEnd != null` 블록 **내부**에만 있어, 정작 필요한 케이스에서 작동 안 함. 블록 밖으로 이동.
- 2026-10-17(PR #353 리뷰 — 원장 `docs/changes/2026-10-17-typecheck-batch-1.md`) — URL 에서 온 값의 검사 둘. `/john/abc` 의 장 번호는 `parseInt` 가 `NaN` 으로 내는데 `chapter < 1 || chapter > count` 가 둘 다 false 라 `john-NaN.json` 을 요청했다(`Number.isInteger` 를 더함). `/constructor` 는 구분 표 `DIVISION_LABELS[name]` 의 참거짓으로 가르다가 일반 객체가 물려받은 이름까지 구분이 됐다(`Object.hasOwn`).

**규칙:**
- 부모-자식 관계 검사 헬퍼는 인자 순서가 헷갈리지 않게 시그니처 위에 한 줄 주석:
  `// _isDescendant(ancestor, candidateId) — candidate가 ancestor의 후손인가?`
- 분기로 갈라진 동일 의도 검증이 있는지 확인. "이 검증이 다른 분기에도 필요한가?"를 한 번 더 묻는다.
- 가드 절은 가능한 한 **분기 시작 시점**에 두고, 분기 내부에 두면 의도하지 않은 패스가 생기지 않는지 확인.
- URL · 저장소에서 온 수는 범위 비교만으로 거르지 않는다 — `NaN` 은 모든 비교에서 false 다. `Number.isInteger`(또는 정규식으로 통째 검사 — `routing.js` 전례독서 쿼리의 `positive`)를 먼저.
- 바깥에서 온 문자열을 일반 객체의 키로 찾을 때는 `Object.hasOwn`(또는 `Map`) — `constructor` · `toString` · `__proto__` 도 참이다.

## 5. 모달/접근성 보일러플레이트 누락

모달 생성 시 포커스 트랩 누락, 드래그 시 포인터 이벤트 리스너 위치 오류처럼 "한 번 익히면 반복 적용해야 하는" 보일러플레이트를 빠뜨리는 패턴.

**사례:**
- `9b8a638` — 병합 다이얼로그가 표시되지만 `trapFocus()` 호출이 누락되어 키보드 사용자가 모달 외부로 빠져나갈 수 있었음.
- `5c41797`, `f154a56` — 드래그용 `pointermove`/`pointerup`/`pointercancel`을 행(row) 요소에 붙였더니, 드래그 중 포인터가 행 밖으로 이탈하면 이벤트를 놓쳐 ghost가 잔류. `document` 레벨로 이동, `pointerId` 필터링 추가.
- #348 리뷰(2026-10-15) — 캘린더 칸의 링크 이름(`aria-label`)을 보이는 이름과 다른 값(그날의 대표)으로 만들어, 사계재 · 기념일을 보이는 격자 평일 칸 54곳과 「연중24주」를 보이는 주일 칸 128곳(2025~2027)에서 보이는 글자가 접근 가능한 이름에 없었다 — WCAG 2.5.3 Label in Name, 음성 제어로 「추계재 누르기」가 안 된다. 링크 이름을 보이는 글자에서 만들게 고쳤다.
- #348 리뷰(같은 날) — 달 이동 링크가 `#app`을 통째로 다시 그려 누른 링크가 사라지자 포커스가 body로 빠졌다(WCAG 2.4.3) — 달을 넘길 때마다 건너뛰기 링크 · 헤더 · 탭부터 다시 지나와야 했다. 다시 그리기 전에 누른 컨트롤의 자리(`data-focus-key`)를 남기고 새 화면의 같은 자리로 포커스를 돌려준다(`views.js focusPendingBook`과 같은 방식). 전례독서 화면(#346)도 같은 결함이었다 — 2026-10-17 그 도우미를 `helpers.js createFocusMemory`로 올려 두 화면이 함께 쓴다.
- 2026-10-17(전례독서 화면에 옮기며 찾은 것) — 포커스만 돌려주면 모자랐다. 새 장을 받아야 하는 다시 그리기(세트 · 트랙 · 칩 · 카드 · 날짜)는 `route()` 의 스켈레톤이 한 프레임 그려지며 문서가 짧아져 스크롤이 맨 위로 눌린다 — 누른 컨트롤이 아래로 밀리고(모바일 최대 약 250px), 화면 아래쪽 컨트롤이면 화면 밖에 포커스가 남는다(2.4.7). 받을 것이 없는 다시 그리기(같은 장의 본기도 대체안)는 스크롤이 그대로라, 같은 화면 안에서도 누르는 컨트롤마다 달랐다. 누른 때의 화면 위치로 돌려준다. 그사이 데스크톱 머리의 검색 줄(최대 4rem)이 펼쳐졌다가 돌아온 뒤 다시 접힌다(스크롤이 0 으로 눌려서) — 스크롤 고정(scroll anchoring)이 있는 브라우저는 그 접힘 동안 내용을 붙잡으므로 **지금 레이아웃에서의 화면 위치(viewport top)**로, 없는 브라우저(Safari 26 까지)는 접힘이 내용을 옮기므로 **화면 루트 안 위치**로 둔다. 루트 안 위치만 쓰던 첫 구현은 장 받기가 0.1초를 넘으면 컨트롤이 그 줄 높이(약 46px)만큼 아래로 내려앉았다 — 로컬 서버는 너무 빨라 보이지 않았고, 위치 e2e 는 그 줄이 없는 모바일뿐이었다(PR #350 리뷰).
- PR #350 리뷰(2026-10-17) — 복원이 포커스를 무조건 옮겨, 새 장을 받는 사이 독자가 머리의 검색 칸으로 옮겨 치던 글자 · Enter 를 누른 세그먼트로 빼앗았다(팝오버를 열었으면 그 밖으로 끌어냈다). 누른 링크와 함께 포커스가 body 로 떨어졌을 때만 돌려준다.
- 2026-10-17(known-issues §10) — 화면마다 `createFocusMemory` 를 잇던 방식은 뷰 루트 밖 컨트롤(성서 목록의 구분 탭 — `route()` 가 슬롯을 비운다)과 `await` 뒤에 그려지는 목록을 덮지 못해, 구분 탭 · 검색의 「← 이전 · 다음 →」는 main 부터 Enter 를 누르면 포커스가 body 로 빠졌다. 라우터로 올렸다(ADR-031 §5) — 전역 `<a>` 인터셉터가 누른 자리를 재고 `route()` 가 시작에서 꺼내 `finally` 에서 돌려준다. 함께 본 것: 검색 결과 화면은 다 그린 뒤 `window.scrollTo(0, 0)`(루트의 smooth)을 불렀다 — 위치 복원이 「이미 제자리」로 보고 지나가면 그 애니메이션이 이어져 누른 링크를 밀 수 있는 순서라 즉시 스크롤로 바꿨다(기본 창 크기에서는 결과가 한 화면이라 드러나지 않았다). 「본문 바로가기」(`#app`)도 같은 인터셉터가 `route()` 로 먹어 포커스가 본문으로 가지 않았다(main 부터) — 페이지 안 링크는 갈라 대상으로 포커스만 옮긴다.
- PR #354 Copilot 1회차(2026-10-17) — 동기화 스낵바(`_showSyncSnackbar` — `drive-sync.js`)는 live region도 `role`도 없는 평범한 `div`라, 동기화 오류 · 재연결 · 「파일도 삭제」 실패 같은 안내 아홉 곳이 화면 낭독기에는 들리지 않았다(WCAG 4.1.3 상태 메시지). 같은 함수를 쓰는 곳 가운데 절 복사(`bookmark-verse-select.js`)만 `announce()`를 따로 불렀다. 해결: 스낵바 함수가 같은 글을 live region(`#a11y-announce`)에도 넣고, 따로 부르던 `announce()`는 지웠다(두 번 읽지 않게).

**모달 생성 4단계 체크리스트:**

```
□ 표시 전 hidden=true (또는 .hidden 클래스 부여)
□ 표시 직후 trapFocus(modal) 호출, 반환값을 cleanup용으로 보관
□ requestAnimationFrame 안에서 첫 액션 버튼에 .focus()
□ 닫을 때: 트랩 해제 + 임시 이벤트 리스너 제거 + 상태 초기화
```

**드래그 핸들러 규칙:** 포인터 추적은 항상 `document` 레벨. 멀티터치 구분이 필요하면 `pointerId`로 필터링.

**상태 메시지 규칙:** 눈에만 보이는 알림(스낵바 · 토스트)은 같은 글을 live region에도 넣는다 — 알림을 띄우는 함수 한 곳에서. 부르는 쪽마다 `announce()`를 덧붙이면 빠뜨리는 곳이 생기고, 한 곳에서 넣은 뒤에는 따로 부르면 두 번 읽힌다. 저절로 사라지는 알림(3.5초)이 **유일한** 신호여서는 안 되는 안내 — 되돌릴 수 없는 작업이 끝나지 않았다는 것처럼 놓치면 사용자가 잘못 믿게 되는 것 — 는 다시 찾아갈 화면(설정)에도 남긴다(WCAG 2.2.1, PR #354 사용자 `/code-review` 12번 — 「파일도 삭제」 실패는 Drive 줄 아래 `.settings-drive-note`, 다시 연결할 때까지).

**접근 가능한 이름 규칙:** `aria-label` 로 이름을 덮어쓸 때는 보이는 글자를 그대로 넣는다(줄여 보이면 이름도 그 줄임 — 「연중24주」). 보이는 이름과 링크 이름을 서로 다른 함수 · 필드로 만들지 않는다 — 한쪽만 바뀌어 어긋난다. 실데이터가 있으면 「보이는 이름 ⊂ 링크 이름」을 전수로 검사한다(`calendar.data.test.js`).

**다시 그리는 화면의 포커스 규칙:** 링크 · 단추가 자기 화면을 다시 그리면(같은 뷰 안의 이동 · 필터 · 세그먼트) 새 화면의 같은 컨트롤로 포커스를 돌려준다 — 누른 때의 화면 위치에. 링크에는 `data-focus-key`(새 화면에 같은 컨트롤이 없을 수 있으면 넘겨받을 컨트롤의 `data-focus-fallback`)만 단다 — 재고 돌려주는 것은 라우터다(ADR-031 §5: 인터셉터가 이동 직전에 `focusSpotOf` 로 재고, `route()` 가 시작에서 꺼내 `finally` 에서 `restoreFocusSpot` — 자리는 그 누름의 route 에만 쓰인다). 커밋 뒤 스크롤을 움직이는 뷰는 즉시(`behavior: "instant"`)로 — 부드러운 스크롤이 이어지면 복원한 위치를 민다. 키는 선택자 문자열이 아니라 `dataset` 값으로 찾는다 — 키가 데이터(관측일 id)라 값 비교는 이스케이프가 필요 없다(따옴표 선택자는 키의 `"` · `\` 에서 깨진다; 콜론 · 한글은 따옴표 안에서 문제없다). 그 컨트롤이 사라졌으면 가장 가까운 대체(`data-focus-fallback` — 「오늘」 · 다른 쪽 링크)로. 페이지를 넘기는 컨트롤도 같다 — 검색 결과의 「다음 →」 · 「← 이전」은 새 페이지에서도 **누른 컨트롤 그대로**(사용자 결정 2026-10-17 — 결과 목록 맨 위로 보내는 안 대신: 전례독서의 「다음날」과 같은 규칙이고 Enter 를 거듭 눌러 넘길 수 있다; 마지막 페이지라 「다음 →」이 없으면 「← 이전」). **포커스가 body 일 때만 돌려준다** — 다시 그리는 사이 독자가 다른 데로 옮겼으면 그대로 둔다. 마우스 · 탭으로 누른 복원은 `focus({ focusVisible: false })` — iOS(WebKit)는 탭으로 링크에 포커스를 주지 않아 뒤의 스크립트 포커스에 링을 그린다(책 카드 `43db624` 와 같은 일).

## 6. 복합 객체 비교 / 범위 병합

복합 객체를 참조 동등성으로 비교하거나, 범위를 정규화 없이 병합해 중복·누락이 발생하는 패턴.

**사례:**
- `85baf40` — 선택된 절 범위 clamping에서 `clamped[i].end !== hlSegments[i].end` 식으로 비교. 객체가 다른 참조면 내용이 같아도 불일치로 판정. 직렬화 문자열(`"3a,3b,5-7"`) 기반 비교로 교체.
- `fa83d94`, `3b9727f` — 운문 절 병합에서 정수 ref(`3`)와 파트 ref(`3a`, `3b`) 중복 제거 누락. 정수 ref가 이미 커버하는 파트 ref를 별도로 보관.
- 2026-10-21(known-issues §5, 2026-04-25부터) — 절 선택이 `data-vref`(절 번호와 줄 글자)를 선택 키로 썼다. 한 장에서 번호가 같은 다른 절(옮겨 실린 절, 그리스어 추가 본문, 에스델 추가 본문, ¶ 구절)은 이 값도 같아서, 하나를 누르면 같은 값의 줄이 모두 선택됐다. 범위는 `indexOf`로 끝을 찾아 앞쪽의 다른 절에서 시작했고, 출처에도 그 번호가 섞였다(이사 40:19-20이 「40:6a,6b,7,19-20」). 줄마다 고유한 `data-vkey`로 선택하고, 저장과 출처는 그 줄의 `data-vref`로 적도록 고쳤다(ADR-010).
- 같은 PR의 리뷰(2026-10-21) — 「한 번호를 여러 절이 함께 쓰는가」를 `data-vref` 중복으로 판정해, 줄 글자가 겹치지 않는 토비 11:15(운문 두 줄인 15절과 중복 표시된 한 줄짜리 15절)를 놓쳤다. 출처가 「11:15a,15b」로 나왔다. 판정을 절 인스턴스 수로 바꿨다.

**규칙:**
- 복합 객체/세그먼트 비교는 **정규화된 직렬 형식**을 거쳐서 비교한다.
- 선택 · 비교 · `indexOf`에 쓰는 키는 그 화면 안에서 **고유한지 먼저 확인**한다. 사람이 읽는 번호(`data-vref`, 절 번호)는 고유하지 않다. 절은 절 인스턴스 키(`verse-spec.js verseInstanceKeys`, DOM id)로, 줄은 줄 키(`data-vkey`, 인스턴스 키와 `data-vref`를 이은 값)로 가린다. 출처 · 저장 · 주소는 번호로 적는다.
- 「같은 것이 여럿인가」는 표시 값의 중복이 아니라 식별자로 센다. 표시 값이 우연히 달라도 다른 대상일 수 있다.
- 범위 병합은 (정렬 → 병합 → 중복 제거) 3단계를 명확히 분리하고, 정수 ref와 파트 ref처럼 **포함 관계가 있는 표현**이 섞여 있으면 우선순위를 명시.
- JSON 파싱은 항상 try-catch로 감싸 사용자가 만든 깨진 데이터에 대비.

## 7. PWA 캐시 무효화 — 셸 bump vs 콘텐츠 매니페스트

**사례:**
- `docs/changes/2026-04-30-worklog.md` — `privacy.html` 추가 시 `SHELL_FILES` 등록 + navigation 예외 처리 + 셸 bump가 한 묶음으로 진행되어야 했음 (셸 영역은 매니페스트 적용 후에도 같음).

## 8. 폰트/렌더링 특성 오해 — 회귀 사례

브라우저 폰트 로딩 동작을 잘못 이해해, 캐시 무효화 직후 첫 실행에서만 회귀가 보이는 까다로운 패턴.

**사례:**
- `351deef` — `font-display: optional`은 폰트가 100ms 안에 도착하지 않으면 그 세션 동안 시스템 폰트로 락인됨. 캐시 미적중 직후 첫 실행에서 의도한 폰트가 보이지 않다가 앱 재시작 후에야 나타나는 회귀. `swap`으로 변경 (런치 스크린이 FOUT 구간을 가림).
- `d61f879` — `media="print" onload` 트릭으로 @font-face를 동적 삽입하면 first paint 이후에 로드되어 FOUT 발생. blocking `preload as="style"`로 변경.

**규칙:**
- 폰트 규칙은 **first paint 전에 DOM에 있어야** FOUT이 없다.
- 폰트 전략은 **(빠른 네트워크 / 느린 네트워크) × (캐시 적중 / 미적중)** 4가지 조합으로 검증한다. DevTools의 throttling + "캐시 비우고 강력 새로고침"으로 재현.
- 관련 ADR: `007-launch-screen-optimization.md` (개정 블록 참고).

## 9. 글로벌 이벤트 핸들러 협력 부족

전역 인터셉터(예: `document.addEventListener("click", ...)`)가 하위 요소의 자체 핸들러가 이미 처리한 이벤트를 **다시 처리**해 의도치 않은 동작이 발생하는 패턴.

**사례:**
- `d25b8da` — 전역 클릭 인터셉터가 SPA 라우팅을 위해 `<a href>` 클릭을 가로챘는데, `buildSheetPagination`의 `href="#"` 링크는 자체 핸들러에서 `e.preventDefault()`를 이미 호출함. 인터셉터가 `e.defaultPrevented` 미체크로 `route()`를 또 호출.
- #348 리뷰(2026-10-15) — 반대 방향의 같은 결함: 탭 바의 탭 처리기(홈 · 캘린더 · 북마크 · 설정)가 전역 인터셉터의 **수정 키 조건**(⌘ · Ctrl · Shift · Alt · 가운데 단추 → 브라우저에 맡김)을 따르지 않았다. ⌘ · Ctrl-클릭에서 (a) 홈 · 캘린더 탭은 `preventDefault` 뒤 같은 탭에서 이동해 새 탭 열기를 무시했고, (b) 캘린더 · 북마크 · 설정 탭은 인터셉터가 빠져 브라우저가 새 탭을 여는데도 스크롤 복원 요청을 먼저 세워, 그 요청이 남아 다음 링크 이동이 옛 스크롤 위치로 튀었다(e2e 재현 — 장 최상단 대신 600px). 탭 히스토리 도입(`687a071`, ADR-031 — #194)부터 있던 결함을 캘린더 탭이 그대로 물려받았다.

**규칙:**
- 글로벌 이벤트 핸들러는 가장 먼저 `if (e.defaultPrevented) return;` 으로 협력 게이트를 둔다.
- 자체 처리하는 하위 핸들러는 **반드시** `e.preventDefault()` (필요 시 `stopPropagation()`)를 호출해 의도를 표현한다.
- 가능하면 글로벌 인터셉터 스코프를 좁힌다 (예: `closest("a[href]:not([data-internal])")` 같이 명시적 마커).
- 링크에 다는 처리기는 전역 인터셉터와 **같은 조건으로 먼저 빠진다** — 새 탭 · 새 창 클릭은 `window.appHelpers.isModifiedClick(e)` 로 거른다(인터셉터도 이 함수를 쓴다 — 조건이 한 곳). 복원 요청 · 포커스 기억 같은 부수 효과는 이 화면에서 이동이 일어날 때만 남긴다.

웹 표준대로 작성했지만 iOS Safari, Android, 사용자 환경 설정(예: `prefers-reduced-motion`) 때문에 회귀하는 패턴.

## 11. 비동기 race 가드 — 단일 체크포인트의 함정

`async` 함수가 여러 `await` 지점을 거치면, 각 await 사이마다 외부 상태(사용자 의도, 다른 흐름의 결과 등)가 바뀔 수 있다. race 가드를 함수 진입 시점이나 첫 번째 await 직후에만 두면, 그 다음 await가 끝난 시점에 이미 stale한 결정에 따라 상태를 덮어쓰는 패턴.

**사례 (Phase 2h PKCE 마이그레이션 — Bugbot PR #54·#57):**

- `c4d0c72` — `_attemptSilentRefresh`가 `_state` 기반 race 가드만 가짐. 사용자가 silent refresh 진행 중 `signOut()`/`disable()`을 호출하면 `_state`는 그대로(혹은 정상 진행 중인 값)이지만 `localStorage["bible-drive-sync"]`는 `"0"`으로 바뀜 → state 가드만 통과시켜 IDLE/NEEDS_CONSENT로 전이하면 사용자가 끊은 sync를 다시 살림. 해결: `localStorage.getItem(SYNC_ENABLED_KEY) === "0"` 검사 추가.
- `f090c83` — 같은 함수에 race 가드를 진입 시점에만 둠. 그러나 `await refreshAccessToken(...)` 직후 race 가드를 통과한 뒤에도 `await refreshStore.saveRefreshToken(...)` (rotation) 또는 `await refreshStore.clearRefreshToken()` (invalid_grant) 같은 IDB await가 남아있음. 그 IDB await 동안 사용자가 `disable()`을 호출하면 후속 `_transition(IDLE/NEEDS_CONSENT)`이 다시 `SYNC_ENABLED_KEY = "1"`로 덮어씀. 해결: 매 `await` 직후마다 race 가드를 다시 검사. 단계 4 후 `enable()`이 동기적으로 DISABLED를 빠져나가지 않으므로 state-based 가드만으로 cold-start 경로 보호 불가능 — flag-based 가드가 필수.
- (2026-10-17, PR #353 리뷰 — `docs/changes/2026-10-17-typecheck-batch-1.md`) — 업데이트 토스트 `showUpdateToast`의 「이미 떴나」 검사가 대기 SW에 버전을 묻는 `await`(최대 1.5초) 앞에만 있어, 그 사이 설정의 「업데이트 지금 확인」이 또 부르면 둘 다 검사를 지나 같은 id의 토스트가 둘 붙었다. 해결: `await` 뒤에 한 번 더 본다. 동기화 레이어 밖에서도 같은 경우가 나온다.

- (2026-10-17, 같은 원장 — 머지 전 검토 4번) — 연결 해제의 「파일도 삭제」는 `deleteRemoteFile()`을 기다린 뒤 `signOut()`을 불러, 지우는 동안 동기화가 그대로 돌았다. 진행 중 사이클의 새 파일 올리기가 지우기 뒤에 도착하면 방금 지운 파일이 되살아났다. 해결: 지우기 전에 사이클을 멈추고, 진행 중 사이클이 이미 보낸 요청이 끝나기를 기다린 뒤(`_cycleDone`) 찾아 지운다.
- (2026-10-17, 같은 원장 — 사용자 `/code-review` 2 · 9 · 10번) — 그 기다림에 상한이 없었고, 토큰은 상태 기계에 둔 채였다. ① 기다리는 동안 앱을 닫으면 켬 표지는 "0"이라 「연결 해제됨」으로 보이지만 폐기하지 않은 refresh token이 IDB에 남았다(다시 「연결」을 누른 뒤 동의를 취소하면 옛 계정이 조용히 다시 연결됐다). ② 그사이 다시 연 설정은 「해제」를 그려 「파일 유지」로 한 번 더 로그아웃할 수 있었고, 그 뒤에도 미리 잡아 둔 토큰으로 찾기 · 지우기가 나갔다. ③ 멈춤은 누른 탭의 상태뿐이라, 연결된 다른 탭은 비워진 공유 캐시를 보고 파일을 다시 만들 수 있었다. 해결: 페이지가 닫혀도 남으면 안 되는 것(IDB refresh token · 켬 표지 · 계정 키)을 네트워크 작업보다 먼저 지우고, 토큰은 상태 기계에서 곧바로 빼 그 함수 안에만 둔다(설정은 곧바로 「연결」). 기다림은 10초까지 — 끝나지 않았으면 지운 뒤 한 번 더 기다렸다 다시 지운다. 다른 탭은 켬 표지의 `storage` 이벤트로 멈춘다. 토큰은 지운 뒤 그 함수가 폐기한다.
- (2026-10-17, 같은 원장 — 사용자 `/code-review` 1 · 7번, main부터) — 사이클은 대기마다 **상태**는 다시 봤지만 **자료**는 다시 읽지 않았다. 시작할 때 읽은 로컬 사본으로 병합한 뒤 `_applyMergedDoc`이 로컬 문서 전체를 덮어써, 찾기 · 내려받기를 기다리는 동안 저장한 북마크 · 설정 · 읽던 위치가 사라졌다. 그사이 들어온 동기화 요청은 SYNCING이라 버려졌고, 304 갈래는 대기 전의 값으로 「변경 없음」을 판정해 그 편집을 올리지 않았다. 해결: 내려받기를 기다린 뒤에 로컬을 읽고(그 읽기와 덮어쓰기 사이에 대기가 없다), 「동기화됨」은 실제로 올린 본문의 값으로 적고, 도는 동안 들어온 사용자 요청은 끝난 뒤 한 번 더 돈다.

**규칙:**

- 비동기 함수에서 race 가드는 **모든 await 직후에 재검사**한다. 진입 시점 한 번만으로 충분하다고 가정하지 말 것.
- 사용자 의도를 신뢰성 있게 신호하는 단일 출처(여기서는 `localStorage["bible-drive-sync"]`)를 정해 모든 race 가드가 같은 출처를 참조하게 한다.
- state machine을 단순화하면서 동기 dispatch가 사라졌다면, 기존 state-based race 가드가 더 이상 작동하지 않는지 의심하라. flag-based 가드로 대체하거나 보강해야 할 수 있다.
- 회귀 방어 테스트: 외부 제어 가능한 `Promise`로 await를 hold한 채 `disable()`을 끼워 넣어, 각 await 시점의 race window를 명시적으로 시뮬레이션한다 (`tests/unit/state-machine.test.js` 26a/b/c · 44-46 참고). e2e에서는 가짜 서버의 응답을 쥐고 있다가 푼다(`test_drive_sync.py` `FakeDrive.hold_list`).
- e2e의 가짜 서버는 토큰 · 권한 검사도 실제처럼 한다 — 다 받아 주는 가짜는 클라이언트의 결함을 가리거나 가끔 실패하는 테스트로 보이게 한다.
- 대기 뒤에 낡는 것은 상태만이 아니다 — 대기 전에 읽은 **자료**(로컬 사본 · 토큰 · 캐시 값)도 낡는다. 덮어쓰는 쓰기는 대기 없이 바로 앞에서 읽은 값으로 한다. 도중에 들어온 요청은 버리지 말고 한 번으로 모아 끝난 뒤 다시 돈다 — 다시 시작은 다음 마이크로태스크에(끝나는 사이클의 `finally` 앞이면 새 사이클이 「아직 도는 중」을 보고 시작되지 못한다).
- 되돌릴 수 없는 작업(원격 삭제) 앞에서는 그것을 되돌릴 수 있는 흐름(진행 중 사이클 · 예약된 올리기)을 먼저 멈추고, **이미 보낸 요청이 끝나기를 기다린다** — 멈추기만 해서는 이미 나간 요청이 뒤늦게 도착하는 것을 막지 못한다. 그 기다림에는 상한을 둔다(멈춘 요청 하나가 로그아웃 전체를 붙잡지 않게). 페이지가 닫혀도 남으면 안 되는 것(자격 증명)은 기다림 · 네트워크 작업보다 먼저 지운다. 멈춤은 탭마다다 — 다른 탭은 공유 표지를 듣게 한다(`storage` 이벤트).
- **동기화 사이클의 확인은 대기마다 한 줄씩 둔다 — 진행 중인 요청을 취소하는 구조(사이클마다 `AbortController`)나 공통 대기 래퍼로 바꾸지 않는다**(사용자 결정 2026-10-17 — 로그아웃 수정의 머지 전 `/code-review`가 「손으로 넣은 확인은 빠뜨리기 쉽다」며 제안했다, 원장 `docs/changes/2026-10-17-sync-signout-inflight.md`). 이유: 같은 파일의 `_attemptSilentRefresh`도 대기마다 다시 본다(위 규칙) · 취소를 넣으려면 OAuth · Drive 전송 함수(`transport.js`)마다 신호를 넘겨야 한다 · 로그아웃 전에 이미 나간 업로드는 로그아웃 전의 편집이라 끝나게 둔다. 빠뜨림은 테스트가 막는다 — 멈추는 자리마다 유닛 하나(`state-machine.test.js` 44-50 — 확인 한 줄을 빼면 그 자리의 테스트가 실패하는 것을 변이 검사로 확인했다). **재검토 조건**: 전송 계층을 다른 이유로 고쳐 요청마다 신호를 받게 될 때, 또는 사이클의 대기가 지금(여섯)보다 크게 늘 때. 리뷰가 같은 제안을 다시 내면 이 줄을 근거로 넘긴다.

## 12. 콜백 URL 데이터 leak — flow별 transport 격차

OAuth callback이 query string(`?code=...`)으로 오느냐 fragment(`#access_token=...`)으로 오느냐는 flow마다 다르다. URL을 strip하는 코드가 한 flow의 가정 위에 작성됐다면, flow 전환 시점에 새 flow의 callback이 URL bar / 브라우저 히스토리 / 로그에 leak될 수 있다.

**사례 (Phase 2h PKCE 마이그레이션 — Bugbot PR #54-2):**

- `3a7c8ab` — Implicit Flow 시절 IIFE는 `bad_state` / `no_state` / `state_mismatch` fallback에서 `history.replaceState(null, "", location.pathname + location.search)`로 search를 보존했음. Implicit callback은 fragment에 오므로 search는 안전했음. PKCE 도입 후 callback은 query string(`?code=...&state=...`)으로 오므로 같은 fallback이 auth code를 URL bar에 leak.

**규칙:**

- 새 flow로 전환할 때, 기존의 URL strip 로직이 새 flow의 callback shape을 반영하는지 명시적으로 검증한다.
- 기본 원칙: 본인 앱이 query 또는 fragment 기반 라우팅을 안 쓴다면, OAuth fallback에서 `location.pathname`만 남기고 search/hash를 둘 다 폐기하는 게 가장 안전.
- 회귀 방어: callback URL의 `?code=`, `#access_token=` 등이 IIFE 종료 후 `location.search`/`location.hash`에 잔존하지 않는지 e2e 테스트로 직접 검증.

## 13. 마이그레이션 시점의 sessionStorage / localStorage 키 격리

기존 흐름과 새 흐름이 같은 storage 키를 공유하면, 마이그레이션 PR 머지 시점에 진행 중이던 callback이 잘못된 흐름으로 라우팅되거나 완전히 떨어진다. flow별로 별도 키를 사용해 절대 교차 처리되지 않게 격리해야 한다.

**사례 (Phase 2h PKCE 마이그레이션):**

- 단계 2~4 — Implicit Flow는 `bible-drive-redirect-state`, PKCE는 `bible-drive-redirect-state-pkce`로 분리. 단계 4 머지 시점에 진행 중이던 PKCE callback은 새 코드도 같은 `-pkce` 키로 매칭되어 정상 처리됐고, 진행 중이던 Implicit callback은 신코드가 안 봐서 자연 만료(sessionStorage 휘발).
- 단계 4의 함수 rename(`beginRedirectAuthPKCE` → `beginRedirectAuth`)에서 **변수명만 canonical로 인계하고 storage 키 값은 의도적으로 `-pkce` 접미사 유지** — 변수명과 키 값을 동시에 바꾸면 in-flight callback이 떨어짐.

**규칙:**

- 서로 다른 인증 / 라우팅 flow에는 처음부터 다른 storage 키를 부여한다.
- 키 이름을 바꾸는 마이그레이션은 두 단계로: (1) 새 키 사용 시작, 옛 키는 read-only로 유지 → (2) 옛 키 cleanup. 한 PR에 같이 넣지 말 것.
- localStorage 폐기 키는 단계 5처럼 별도 정리 단계에서 `localStorage.removeItem(...)`을 IIFE에 추가해 기존 사용자 디바이스에서 청소한다 (몇 릴리스 후 cleanup 코드 자체도 제거).

## 14. CSS `display` 속성이 `[hidden]` 무력화

`<button hidden>` 같은 HTML5 `hidden` 속성은 user-agent 스타일시트에서 `[hidden] { display: none }`로 처리된다. 그런데 author CSS에서 ID 셀렉터로 `display: flex`(또는 block, grid 등)를 명시하면 specificity가 더 높아 `[hidden]` 규칙을 덮어쓴다 — JS에서 `el.hidden = true`로 설정해도 시각적으로 안 사라지는 회귀.

**사례 (Phase 2h 단계 6):**

- 검색 액션 버튼(`#search-clear`, `#search-history-toggle`)에 `display: flex`가 적용돼 있어, JS의 `$searchClear.hidden = true`가 무력화. 빈 입력 상태에서도 X 버튼이 계속 보였고, 동시에 `dataset.clearHidden="true"` 트리거 규칙이 history toggle을 clear의 위치로 옮겨 두 버튼이 정확히 같은 좌표에 스택. DOM 순서상 clear가 후순위라 사용자에겐 X만 보이고 ▾는 X 뒤에 가려져 "버튼 모양이 이상"한 외양.
- 수정: `#search-clear[hidden], #search-history-toggle[hidden] { display: none; }` 명시 규칙 추가. specificity 동률 이상으로 끌어올려 `[hidden]` 의도 복구.

**규칙:**

- ID 또는 specificity 높은 셀렉터로 `display: ...`를 설정한 요소가 `hidden` 속성을 통해 가려질 수 있다면, **반드시 같은 셀렉터에 `[hidden] { display: none }` 규칙을 명시**한다.
- 점검: `el.hidden = true` 후 DevTools에서 `getComputedStyle(el).display`를 확인해 `none`이 나오는지 검증.
- 전역 회귀 방지가 필요하면 `:where([hidden]) { display: none !important; }` 같은 광역 규칙도 가능하지만 `!important`는 다른 의도된 override를 깨뜨릴 수 있어 피하는 게 좋음. 셀렉터별 `[hidden]` 보강이 더 안전.

## 15. Cache API ↔ IDB sidecar 불일치 + Content-Length 의존

Cache API는 access-time / byte-size 메타데이터를 노출하지 않으므로 LRU·쿼터 추적은 IndexedDB sidecar에 별도 보관하는 패턴이 자연스럽다 (ADR-016). 그러나 두 store가 독립 존재이므로 한쪽만 갱신·소실되면 추적이 영구 어긋난다. 또 Content-Length 헤더에 의존해 byteSize를 기록하면 chunked transfer / gzip / Range 응답에서 0이 들어가 LRU cap이 사실상 무력화된다.

**사례 (2차 보안 감사 — `docs/archive/audit/2026-05-08-second-comprehensive.md` H1·H2·H3):**

- **H1** — `sw.js:139` `byteSize = cl ? Number(cl) : 0`. Content-Length 누락 시 0 기록 → totalSize 합산에서 빠짐 → HARD_CAP 도달 신호 못 받음 → Cache API 무한 누적 → origin-단위 quota 초과 시 DATA_CACHE까지 evict.
- **H2** — `_putAudioAndEnforceCap`이 두 fetch에서 동시 진행되면 `pickEvictions` 결과가 방금 put된 url을 evict 대상에 포함시켜 재생 중 mp3 삭제.
- **H3** — `cache.put` 성공 후 `recordEntry` 실패하면 Cache에 mp3는 있고 IDB 메타는 없는 상태로 영구 누적. DevTools에서 한쪽만 비워도 같은 결과.

**규칙:**

- **byteSize는 Content-Length를 우선하되 무효 시 `response.clone().blob().size`로 폴백한다.** 추가 read 1회 비용을 받아들이는 것이 LRU 정확성 손실보다 항상 낫다. clone()은 `cache.put` 전에 (body 소비 전에) 해야 한다.
- **동시 in-flight URL 추적**: 모듈 레벨 `Set`에 진입 시 add, 종료 시 finally에서 delete. eviction은 이 Set을 filter out — 진행 중 항목이 다른 호출의 cap 정리에 휘말리지 않게.
- **양 store reconcile**: SW `activate` 핸들러에서 `cache.keys()`와 IDB entries 양방향 비교. (a) Cache에 있고 IDB에 없는 항목 → recordEntry로 채움 (byteSize는 blob.size로). (b) IDB에 있고 Cache에 없는 항목 → orphan removeEntries. 비용은 mismatch 수에 비례하며 healthy 상태에선 microsecond.
- **회귀 방어**: 단순 throughput 테스트 외에 (i) Content-Length 누락 응답 (ii) 동시 cap 초과 fetch (iii) IDB·Cache 한쪽 비움 시나리오를 명시적으로 다루는 테스트 케이스 필요.

## 16. 모듈 init 시점 `window.X` facade 미정의 — 로드 순서 race

`<script type="module">` 들은 index.html 의 나열 순서대로 평가된다. 어떤 모듈이 **init(top-level) 코드에서** 다른 모듈이 `window.X` 로 노출하는 함수를 소비하면, 그 함수를 정의하는 모듈이 **뒤에** 실려 있을 때 init 시점엔 `undefined` 다. 한 번 검사하고 즉시 bail 하면 이후 그 함수가 정의돼도 재시도가 없어 상태가 영구히 비어버린다.

**사례:**
- `53cb24d` (#246) — search.js 가 부팅 시 `ensureAliasMap()` 으로 `in:<별칭>` 흡수용 `_aliasMap` 을 예열하는데, `window.loadBooks`(data-fetch.js)는 search.js *뒤*에 로드되는 모듈이라 예열 시점엔 undefined. `if (typeof window.loadBooks !== "function") return` 로 즉시 bail → `_aliasMap` 영구 null → `사랑 in:요한` 입력이 책 칩으로 흡수되지 않고 raw 텍스트로 남는 회귀. 동기 흡수 리팩터가 commit 시점의 `await ensureAliasMap()` 을 부팅 예열로 옮기며 로드 순서 가정을 깬 것이 원인.

**규칙:**
- init 에서 소비하는 `window.X` 가 **뒤에 로드되는 모듈** 소속인지 확인한다. 그렇다면 한 번 bail 하지 말고 정의될 때까지 짧게 대기 후 진행하거나, 소비 시점(이벤트·커밋 핸들러)으로 미룬다.
- 이런 로드 순서 race 는 vm 유닛 하네스가 `window.X` 를 미리 스텁하므로 **유닛 테스트로 안 잡힌다.** 실제 모듈 순서로 로드하는 브라우저 스모크로 검증한다.

## 18. 교회력 조회의 도메인 확정 — 주일과 겹치면 주일 본문 · 성주간과 재의 수요일 주간은 지정 독서 · 여성선교주일은 기념일 (2026-10-10)

전례독서 · 본기도 데이터에는 날짜로만 갈리는 평일 본문이 있다 — 12.17~12.24 「성탄 N일 전」, 12.30 · 12.31 · 1.3~1.5 · 1.7~1.12 「성탄주간」(`type: weekday`, 설계서 §5.4). 그 날짜가 주일이면 날짜 본문과 주일 격자 본문(대림 3 · 4주일 — 12.17 이 주일인 해는 대림 3주일이다 · 성탄 1 · 2주일) 중 어느 것인가가 데이터만으로는 정해지지 않는다.

**사례:**
- #338(`bf46f1a`) — 엔진 A1-b 가 「주일은 날짜 전용 평일 본문을 받지 않는다」로 구현했다(격자 조회 경로 ① 이 `type` 까지 맞춘다). 머지 뒤 사용자 확정: 「주일과 겹치면 주일 본문」(2026-10-10).

**규칙:**
- 날짜 전용 본문은 그날 좌표와 `type` · `season` 이 같을 때만 쓴다 — 주일에는 주일 격자 레코드다(설계서 §5.6 「출처별 조회 경로」).

- 성지주일 이후 주간은 모두 성주간으로 지킨다. 성주간 월~토와 재의 수요일 후 목 · 금 · 토는 특별한 일이 없으면 **지정 독서**를 쓴다(사용자 확정 2026-10-10). 성 목 · 금 · 토는 정의 표의 행이, 성주간 월~수 · 재의 수요일 후 목~토는 이름을 단 격자 후보가 그 독서를 낸다(설계서 §5.5).
- 지정 독서가 데이터에 없으면 먼저 원료(교구 사이트 기사)의 **태그 누락**을 의심한다 — 재의 수요일 후 금요일은 기사(archives/3994)가 있는데 「감사성찬례-전례독서」 태그가 없어 수집되지 않았다(2026-10-10, 사용자 제보). 데이터 저장소 `liturgical/fetch.py` 의 `EXTRA_ARTICLES` 가 그 자리다(선례: 2026-07-13 사순5주 · 연중5주; 이번 건은 data#27).
- 픽스처(책자 · 달력)와 데이터의 성구 범위가 어긋나면 원료 기사의 **오기**를 먼저 의심한다 — 대림 3주일 나해 복음은 「요한 1:6-8, 19-28」이다(사용자 확정 2026-10-11 — 서울교구 2026 달력 12월 면 · RCL). 사이트 기사(archives/3139)가 「19-26」으로 실어 데이터가 그대로 받았고, 엔진 B1 의 픽스처 소비(W-2026-12-13-lucia-on-sunday)가 잡았다. 고칠 자리는 데이터 저장소 `liturgical/readings.py` 의 `SOURCE_FIXES` · `SOURCE_NOTES` 다(선례: 기사 17829 「이사 55:11-5」).
- **여성선교주일은 기념일로만 표시한다** — 해마다 본기도와 독서가 새로 정해져 고정 본문이 없다(사용자 확정 2026-10-10, data#27). 스크랩된 그해 본기도·독서는 싣지 않고(데이터 `coords.VARYING_TEXTS`), 그날은 이름 줄 후보로만 오른다 — 주일 본문은 격자가 낸다(→ 설계서 R-6.1-ineligible).
- **2023 · 2024 「전례독서」 책자의 12.17~12.24(성탄 N일 전) 독서는 신뢰할 수 없다**(사용자 확인 2026-10-11) — 그 구간은 책자 대조의 근거로 쓰지 않는다. 같은 구간의 기존 픽스처 둘(W-2024-12-20-ember-friday-two-sets · W-2024-12-21-ember-ordination-kim)은 책자가 아니라 서울교구 2024 달력 12월 면이 근거다.

## 19. 교회력 품계 · 색의 도메인 확정 — 사계재 날은 자 · 재의 수요일 주간의 축일 · 3.01 은 삼일절 (2026-10-10)

엔진 B1(설계서 §6)을 구현하기 전에 사용자에게 물어 정한 셋이다. 셋 다 지금 규칙만으로는 답이 갈리거나 책자와 어긋나는 자리였다.

**사례:**
- 사계재 날 그 자체의 색 — 2026-09-17 에 「승자의 절기색」(하계재 · 추계재 평일 녹)으로 정했다가, 2025 · 2026 책자가 두 해 연속 [자] · [자/백]으로 인쇄한 것이 확인돼 다시 열렸다(설계서 미결26).
- 3.01 은 데이빗 ∧ 삼일절이 prec 7 동률인데, 동률을 `id` 사전순으로 가르면 `d0301-데이빗` < `d0301-삼일절` 이라 **해마다 데이빗이 official** 이 된다 — 고유 본기도 · 독서가 있는 국가 기념일이 공통 본문뿐인 성인 뒤로 밀린다.

**규칙(사용자 확정 2026-10-10):**
- **사계재 날의 색은 책자대로 자다**(미결26 — 모델 (b)). 격자 평일이 이기면 그날 `color` 는 자, 축일이 이기면 `color` 는 축일 색이고 `colors` 에 [자, 축일 색]을 병기한다. 사계재 독서는 여전히 지향(승자 아님 — 설계서 R-6.1-ineligible)이다 — 색과 독서가 다른 축이다.

## 20. 교회력 이동의 도메인 확정 — 본당 축일 · 교구 설립일 · 성주간과 부활 8일의 주요축일 (2026-10-11)

엔진 B1 이동 패스(설계서 §6.5)를 구현하며 「12월 축일이 해를 넘겨 1월로 밀리는 일이 어디서 생길 수 있나」를 따지다가, 본당 · 교구 지역 축일(`local-observances` — ADR-036 B2 `scope` 오버레이)이 12월 말에 오면 축일을 밀 수 있다고 잘못 짚었다. 품계만 보면 그렇게 읽힌다 — 데이터(`calendar/parishes.md` 머리)와 ADR-036 「성인력 보완 영역」(1)이 성당축성일을 기도서대로 주요축일 C(prec 4)로 적었기 때문이다.

**사례:**

**규칙(사용자 확정 2026-10-11):**
- **본당 축일(주보성인 축일 · 성당축성일 — 축성일 · 축복일 모두)은 기념일과 같은 성격이라 축일 이동에 영향을 주지 않는다** — 다른 축일을 밀지도, 옮겨 온 축일의 자리를 막지도, 스스로 옮겨지지도 않는다. 데이터는 `transferable: false` · `transfer_to: null`(data#29).

- 그래서 이동 패스(→ 설계서 R-6.5-year-pass)는 지역 축일을 보지 않고, 패스 캐시는 본당 설정에 의존하지 않는다(설계서 §4.9).

- 데이터 절 번호가 책자와 다른 15건 · 책자 초안 자체의 오류로 보이는 것들(성인 이름의 2주 뒤 반복, 설 · 추석 독서 칸 비어 있음, 사계재 없음, 색 몇 곳).

**규칙(사용자 확정 2026-10-13):**

## 23. 머지 전 코드 리뷰의 도메인 확정 — 보호 기간에서 밀린 축일끼리의 순서 · 연쇄 범위가 닿는 곳 (2026-10-14)

PR #347(`824f7ee`)을 머지 전에 코드 리뷰해 지적 15건을 받았다(원장 `docs/changes/2026-10-13-liturgical-engine-booklet-2027.md` 5회차). 사용자 결정 하나와, §22 결정의 범위를 코드가 넘어선 것 하나.

**사례:**
- 보호 기간 목적지(§22 · 설계서 R-6.3-guard-destination) 때문에 부활절이 3.26 인 해(1967 · 1978 · 1989 · 2062 · 2073 · 2084)에는 성지주일(3.19)에 밀린 요셉과 부활밤(3.25 성 토요일)에 밀린 수태고지가 둘 다 부활 2주 월요일(4.3)부터 자리를 찾는다. 엔진은 먼저 밀린 요셉에게 4.3 을 주고 수태고지를 4.4 로 보냈다(선착순 — 미국 성공회 2008 달력). 그런데 설계서 · 검토 문서는 「1900~2100 실데이터에 순서가 갈리는 사례 없음 → 사제에게 묻지 않음」을 전제로 그 물음을 닫아 두었다 — 그 전제는 보호 기간 목적지를 바꾸며 깨졌다. 세 전통이 갈린다: 미국 BCP 1979 「일어난 순서대로」, 영국 Common Worship 「요셉은 부활 2주 월요일로 — 수태고지가 이미 그날로 옮겨졌으면 그다음 첫 빈 날로」(조지 · 마르코는 날짜 순), 로마 「수태고지는 부활 2주 월요일」. 우리 기도서에는 순서 조항이 없고, 일반 원칙은 「주요축일이 다른 축일과 겹칠 경우, 우선하는 축일을 지키고 다른 축일을 옮겨 지킨다」이며 수태고지(주요축일 가 — 연중주일도 이긴다)가 요셉(나 — 모든 주일에 진다)보다 위다.
- 모든 성인의 날을 켠 해(10.30-11.5 사이 주일로 옮겨 지킴) 2025-11-02에 엔진은 모든 별세자의 날을 그 주일에 「기념만」으로 남겼다 — 그날을 밀어낸 것 가운데 맨 위 하나(옮겨 온 모든 성인의 날)만 보고 연쇄 범위 규칙을 적용했기 때문이다. 그 주일도 별세자의 날을 밀어내므로 종전대로 11.3으로 가야 한다(2025 책자 11.3 「11월 2일에서 이동」 — 같은 해 11.1에 「연중 31주일로 이동할 수 있다」를 안내했다). 승천을 켠 해 성모 방문(5.31 = 부활 7주일)도 같은 경우다.

**규칙(사용자 확정 2026-10-14):**
- **보호 기간 안에서 밀린 축일이 여럿이면 서열 순으로, 같은 서열이면 원래 날짜 순으로 부활 2주 월요일부터 앉는다**(→ 설계서 R-6.3-guard-order). 사용자: 「2번은 서열 순으로 할게」. 부활 3.26 인 6해는 수태고지 4.3 · 요셉 4.4 다 — 영국 Common Worship 의 요셉 규칙과 같은 결과. 그 밖의 도착끼리는 선착순 그대로다(→ R-6.2-first-come — 1900~2100 에서 둘이 갈리는 것은 이 6해뿐이었다). 최장 이동은 15 → 16일(요셉 3.19 → 4.4).
- **연쇄 범위 규칙(사도 · 복음사가 · 성탄 8일 순교만 연쇄, 그 밖은 기념)은 옮겨 온 축일에만 밀린 축일에 쓴다** — 주일 · 대축일처럼 그날의 다른 후보도 그 축일을 밀어내면 도착이 없었어도 옮겼을 것이므로 종전대로 다음 빈 날로 옮긴다(§22 「이 결정은 도착에 밀리는 경우만 말한다」 — 코드가 그 범위를 넘었던 것을 되돌림, 사용자 「1번 고쳐줘」). 이동 패스와 `settle` 은 같은 함수로 판정한다 — 둘이 따로 판정하다 이 PR 안에서 한 번 어긋났다.
- 연쇄 대상 밖의 주요축일(요셉 · 막달라 마리아 · 성 십자가 · 수태고지 · 성모 방문 · 주의 봉헌 등)이 옮겨 온 축일에**만** 밀릴 때 기념만 하는 것은 **잠정**이다(설계서 미결43 — 1900~2100 실데이터에는 그런 날이 없다). 사용자도 자신이 없어 사제께 묻기로 했다(2026-10-15 「나중에 신부님께 물어보는 걸로」 — 검토 문서 §6 질문지).

## 24. 캘린더 탭의 화면 결정 — 칸 이름 하나 · 선택 봉헌 · 전례년 경계 · 독서 성구 · 목록 범위 · 데스크톱 입구 · 모듈 로드 · 탭 이름 (2026-10-15)

A2 캘린더 탭(ADR-038 §1 · §2 — 하단 탭 바의 캘린더 탭과 `/calendar` 월간 · 주간 · 목록)을 시작하며 잠정안 일곱을 날짜 예와 함께 보였고, 사용자가 「시작」으로 일괄 승인했다(A3 때와 같은 방식 — 잠정 결정을 내려 구현하고 결정 목록을 확인받는다, §21). 원장 `docs/changes/2026-10-15-calendar-tab.md`.

**사례:**
- 한 날에 지키는 것이 여럿인 날이 칸 하나에 다 들어가지 않는다 — 2026-09-29 성 미카엘 ∧ 대한성공회 설립 기념일(동시 봉헌), 사계재 날, 2027-07-26 야고보(7.25 에서 옮겨 옴) ∧ 안나와 요아킴(기념만). 폰의 칸 폭은 한 줄 약 4글자다.

**규칙(사용자 승인 2026-10-15):**
- **월간 칸의 이름은 하나 — 그날의 대표(엔진 `official`)**. 대표가 이름 없는 평일(격자)이면 그날 지키는 이름 있는 후보(사계재 · 기념일), 주일과 고유명 평일(성주간 월-수 · 재의 수요일 후 목-토)은 격자 이름이다. 번호 붙은 주일은 「연중29주」 · 「대림1주」처럼 줄인다(ADR-038 §2). 나머지 후보는 주간 · 목록 줄과 전례독서 화면의 칩에서 본다. 예: 2026-09-29 칸 「성 미카엘과 모든 천사들」(줄에 「대한성공회 설립 기념일」) · 2026-09-18 칸 「추계재」(자색) · 2027-07-26 칸 「사도 성 장 야고보」(줄에 「7월 25일에서 옮겨 옴 · 안나와 요아킴 · 기념만」).
- **선택 봉헌(「옮겨 지킬 수 있다」)은 월간 칸에 보이지 않는다** — 칸은 주일 이름 그대로, 주간 · 목록 줄에 보조 이름으로(2026-05-17 「부활7주」 / 줄 「승천대축일 · 5월 14일에서 옮겨 지킬 수 있음」 · 2026-08-09 주의 변모).
- **전례년이 바뀌는 날(대림 1주일)에 표지** — 칸에 「나해」, 그 title · 링크 이름 · 줄에 「나해 시작」(2026-11-29). 엔진의 `liturgicalYearOf` 로 가른다(설계서 미결3).
- **독서 성구는 달력에 싣지 않는다**(설계서 미결41 — 주간 뷰의 정보 밀도) — 달력은 캘린더 묶음(정의 표 약 105KB)만 받고 독서 묶음(약 1.6MB)은 독서 화면에서만 받는다. 주간 줄에는 이름 · 색 · 주기(주일만 「가해」)를 둔다.
- **목록 화면은 오늘부터 8주, 이름 없는 평범한 평일은 건너뛴다** — 주일 · 축일 · 대재일 · 사계재 · 기념일, 끝에 「다음 8주」.
- **데스크톱(넓은 화면 · 마우스)에는 헤더 윗줄에 캘린더 단추**를 둔다 — 하단 탭 바가 없어 주소 말고는 들어갈 길이 없었다(ADR-038 §1 에 없던 범위).
- **캘린더 · 전례독서 · 교회력 엔진 모듈은 그 화면에 처음 갈 때 한꺼번에 불러온다**(동적 `import()` — 2026-10-17, 한꺼번에는 사용자 결정 2026-10-18 「한꺼번에 받기로 진행」, 원장 `docs/changes/2026-10-17-lazy-liturgical-modules.md`). 처음 승인은 「`calendar.js`도 전례독서 모듈처럼 모든 화면에서 받는다(정적 import), 지연 로드는 A2 뒤 별도 PR」이었다(2026-10-15). 이득과 대가는 서비스 워커 캐시가 없는 첫 방문에만 있다 — 첫 화면 느린 4G −390ms, 첫 방문에 캘린더를 바로 열면 +527ms; 재방문은 어느 쪽이든 측정 오차 안(2026-10-17 실측 — 「앱을 열 때마다 해석한다」는 계획의 예상은 틀렸다). 받지 못하면 그 뷰의 제목에 「다시 불러오기」 — 누르면 페이지를 새로 고친다(사용자 결정 2026-10-17 — 브라우저가 실패한 모듈을 새로 고칠 때까지 기억해, 화면을 다시 여는 것만으로는 풀리지 않을 수 있다. DESIGN.md §6 「전체 화면 실패」). 리뷰 반영(2026-10-18 — 사용자 「권장안 수용」): 자료를 받지 못했을 때도 같은 「다시 불러오기」, 날짜를 다시 골라야 하면 「이번 달 캘린더」 — 실패 화면은 `views.js` 하나가 그린다. 바로 열기를 미리 받는 `modulepreload`는 넣었다가 2회차 리뷰에서 되돌렸다 — WebKit이 실패한 미리 받기를 그 탭에 남겼다(사용자 결정 「미리 받기를 되돌린다」, §34). 주소로 바로 들어온 첫 방문이 느린 4G에서 0.16-0.2초 늦는 것은 비용으로 받아들인다.
- **탭 이름 · 화면 제목은 「캘린더」** — 1단계를 「교회력」으로 보였더니 사용자가 「"교회력"은 "캘린더"로」(2026-10-15). 「교회력 자료를 불러오지 못했습니다」 · 「교회력을 계산할 수 없는 날짜」처럼 화면 이름이 아니라 교회력 자체를 말하는 문구는 그대로다.
- 구현하며 정한 화면의 세부(같은 날 보고 — 확인 대상): 독서 화면의 위 단계는 집이 아니라 꺾쇠(그 날짜의 달 — 모바일에서도 보임), 앞뒤 달 칸은 이름 없이 흐리게, 선택 대체색(장미 · 청)은 달력에 그리지 않는다(DESIGN.md §2 「전례색」).

## 25. 저녁 전례의 도메인 확정 — 성 토요일의 대표는 성 토요일 · 부활밤과 성탄 밤은 저녁 전례 (2026-10-15)

A2 캘린더 탭 1단계(#348) 화면에서 성 토요일(2026-04-04) 칸이 「부활밤」으로 보였다 — 엔진이 그날의 대표를 부활밤(prec 1)으로 내고 색은 성주간 가드로 적색이라 이름과 색이 어긋났다(설계서 미결20 의 잠정). 사용자가 「성 토요일 칸은 "성 토요일"로 보이게 해줘. 미결20에서 무엇을 정해야 하지?」라고 물어, 책자를 대조해 세 가지를 물었다.

**사례:**
- 2024 · 2025 · 2026 「전례독서」 책자 — 성 토요일 칸은 「성(주간) 토요일 [홍] · 감사성찬례 없음」, 부활밤은 「부활밤 예식 [백]」으로 따로(저녁 칸 또는 한 줄). 12.24 칸에 「성탄밤 [백]」, 12.25 칸에는 성탄 새벽 · 낮만. 2027 검토용 초안만 12.25 칸에 성탄밤을 실었다(초안 — §22).
- 칸만 「성 토요일」로 바꾸면 그 칸을 눌러 들어간 전례독서 화면의 제목은 여전히 「부활밤」이다 — 칸 이름은 엔진의 그날 대표를 쓰기 때문이다. 화면에서 따로 고치지 않고 엔진의 모델을 정했다.

**규칙(사용자 결정 2026-10-15 — 「엔진은 "성 토요일"을 기본으로 보여줘야 해. 독서 화면에서 칩으로 부활밤을 보여줄 수 있게 하면 되. 부활밤은 저녁 전례로 보는 게 맞아. 성탄 밤도 12.24 저녁 전례가 되어야 맞겠지」 — 「권장대로」):**
- **성 토요일의 대표 · 색은 성 토요일(적색)이다.** 독서 화면을 열면 성 토요일 독서(욥기 14 …)가 먼저이고, 부활밤은 「부활밤 · 저녁」 칩으로 고른다(고르면 백색 · 부활밤 독서).
- **성탄 밤은 12.24 저녁 전례다** — 12.24 의 「성탄 밤 · 저녁」 칩, 12.25 의 칩은 낮 · 새벽. 12.24 의 대표 · 색은 그날 낮(대림 평일 · 자).
- **저녁 전례는 어떤 판정에도 참여하지 않는다** — 그날의 대표 · 색 · 재분류(`settle`)에도, 축일을 다른 날로 옮기는 이동 패스에도(→ 설계서 R-6.1-evening, 미결20 닫힘). **성 토요일은 성 토요일이 스스로 지킨다** — 우선순위 1(성 목 · 금요일과 같은 칸 — 데이터의 등급 「대축일」, 아래 사용자 교정)이라, 성 토요일에 걸린 주요축일은 성 토요일에 밀려 부활 2주 월요일 뒤로 가고(2062-03-25 수태고지 → 4.3) 축일은 생략된다.
- 시각(일몰 또는 18시 이후)에 따라 저녁 전례를 먼저 보이고 색을 바꾸는 것은 사용자가 「하나의 방법」으로 꺼냈다 — **결정 전**이다(ADR-038 「검토한 대안 — 저녁 전례」 C: 같은 주소가 시각마다 다른 화면이 되고, 일몰은 위치 권한이 필요하다).

**사용자 교정(2026-10-15 — #349 리뷰 반영 중)**: 처음 구현은 「저녁 전례는 그날의 판정에서 빠지지만 이동 패스에서는 부활밤이 성 토요일의 주요축일을 민다」였고, 리뷰가 그날 판정(생략 축일을 민 것 = 보호 기간)과 이동 패스(부활밤)가 다른 모델을 쓴다고 잡았다. 사용자: 「성 토요일은 부활밤에 밀리지 않아. 성 토요일은 무조건 토요일에 있어야 하고, 부활밤을 칩으로 표현하면 될 것 같은데?」 — 부활밤은 칩일 뿐 판정에 끼지 않는다.
- 부활밤을 판정에서 빼기만 하면 성 토요일은 등급이 비어(데이터 「등급 없음」) 축일을 밀 힘이 없다 — 1900~2100 에서 6해(1967 · 1978 · 1989 · 2062 …)에 성모수태고지가 성 토요일의 대표(백색)가 된다(실데이터 시뮬레이션). 그래서 **성 토요일에 우선순위 1** 을 준다 — 같은 시뮬레이션에서 1900~2100 의 모든 날(73,414일) 대표 · 색 · 상태 · 옮겨지는 날짜 차이 0(달라지는 것은 생략 성인이 있는 성 토요일 27일의 칩 순서 — 성 토요일이 앞으로 — 와 옮겨 간 축일의 「밀어낸 것」 기록뿐).
- 자리는 **데이터**(사용자 결정 — 엔진 규칙 대신): `common-bible-data` `liturgical/calendar/temporal.md` 의 성 토요일 등급을 「대축일」로 — 성 목요일(2026-08-29)과 같은 원리(이 표의 등급 칸이 품계와 성격을 함께 정하는데 prec 1 칸은 대축일 · 대재일뿐; 대재일이면 `type` 이 fast 로 뒤집혀 「대재일」이 붙는다). 성격은 이름표(coords — 평일)에서 와서 `type` 은 weekday 그대로이고 소재일 표시도 그대로다. 엔진의 「등급 없는 temporal 평일 행 = 8」 규칙은 지운다.

**칩 줄(사용자 결정 2026-10-15 — 같은 리뷰)**: 휴대폰에서 「부활밤 · 저녁」 칩이 가로 스크롤 줄 끝에 숨었다(320px 에서 12px, 생략 성인이 있는 해는 0px). 사용자: 「칩이 여러 개면 단어처럼 한 행에 여러 개를 그냥 열거하고, 줄이 바뀌면 개행해서 보여주면 되지 않아?」 — **관측일 칩 줄은 줄바꿈**(가로 스크롤 대신). ADR-038 「칩은 후보 전부를 항상 노출」을 글자 그대로 지키고, 저녁 칩뿐 아니라 다른 날 숨던 칩도 함께 보인다.

## 27. 타입 검사가 조용히 꺼져 있었다 — `// @ts-check` 가 문 뒤에 있던 파일들, 선언이 데이터 · 코드와 어긋난 채 쌓였다 (2026-10-17)

검사를 파일마다 `// @ts-check` 로 켜던 때(`checkJs: false`)에는 지시문 앞에 `"use strict";` 같은 문(statement)이 있으면 TypeScript 가 지시문을 읽지 않고 그 파일을 **오류 없이** 뺐다 — `npm run typecheck` 가 0 이어도 그 파일은 검사받지 않은 것이었고(앞에 주석만 있는 것은 괜찮다), CI 는 타입 검사를 돌리지 않았다. 검사 밖에서는 `js/types.d.ts` 의 선언이 실제 데이터 · 코드와 어긋나도 아무도 모른다. 2026-10-17(PR #353 리뷰)부터 `checkJs: true` 로 `js/` 전체를 기본으로 검사하고, 필수 CI 「Unit tests」 잡이 타입 검사를 돌린다(ADR-012).

**사례:**
- `lectionary.js`(#346) — 975줄이 검사 밖이었다(원장 `docs/changes/2026-10-12-lectionary-view.md` 3회차 ①).
- 22개 파일(2026-10-15 발견 — `known-issues.md` §7) — 묶음 ① 16개를 켜자 44건(원장 `docs/changes/2026-10-17-typecheck-batch-1.md`): `BookEntry.division` 에 데이터의 `"liturgical"`(전례시편 · 송가)이 없었고, `BibleVerse.chapter_ref` 는 데이터가 정수인데 `string` 이었고, `AppStorage` 에 `loadCiteShow` · `saveCiteShow` 가, Window 에 창 객체 다섯이 빠져 있었고, `parsePath()` 의 전역 선언은 `any` 였다. 그 자체로 실행 결함은 아니었지만 선언을 믿고 짠 새 코드가 틀릴 자리였다.
- 같은 묶음 — JSDoc 블록과 함수 사이에 `const` 하나가 끼어 매개변수 타입이 함수에 붙지 않았고(citations.js `wrapNoteAnchorsInArticle`), `@param {T} [이름] — 설명`(대괄호 이름 바로 뒤 줄표)은 TS 가 「Invalid character」(TS1127)로 읽었다.
- 같은 묶음의 리뷰 — `division` 타입에 `"liturgical"` 을 넣어 선언은 바로잡았지만, 그 값으로 경로를 만드는 곳(`` `/${effectiveDivision(book)}` `` — 헤더 집 단추 · 탭 바 홈)은 그대로라 전례시편 · 송가에서 없는 `/liturgical` 로 갔다(main 부터). 타입은 문자열 이어 붙이기를 막지 않는다.
- 묶음 ②(`views` · `search`, 2026-10-18 — 원장 `docs/changes/2026-10-18-typecheck-batch-2.md`) — `appendVerses`가 `chapter`를 null 기본값으로 받아 `findParallelsStartingAt(…, chapter)`에 넘겼는데, 받는 쪽은 `currentChapter`가 `undefined`일 때만 장 비교를 건너뛴다. null이 오면 모든 범위가 장 비교에 걸려 ※(평행 본문) 표시가 모두 빠진다. 평행 본문을 넘기는 호출부(장 화면)는 장 번호를 늘 함께 넘겨 아직 밟지 않았다 — `number | null`을 `number | undefined` 자리에 넘긴다는 타입 오류가 그 어긋남을 드러냈다.
- 묶음 ③(북마크 모듈 넷, 2026-10-18 — 원장 `docs/changes/2026-10-18-typecheck-batch-3.md`) — 함수와 떨어진 JSDoc이 둘 더 나왔다. `openMergeDialog`의 블록 아래에 `const mergeOverlay`가 끼어 블록이 오버레이 선언에 붙었고(그래서 `fallbackContext = null`이 `null` 타입이 되어 `{ bookId, chapter }`를 넘기는 호출이 걸렸다), `renderBookmarkTree`의 블록은 다른 함수(`_buildEmptyState`) 위에 있어 TS8024(「`target`이라는 매개변수가 없다」)로 드러났다. 객체 리터럴 꾸러미 `window.appBookmark`의 선언(`AppBookmark`)은 verse-spec.js로 옮겨 간 함수 넷을 들고 실제 멤버 스물 가운데 열셋을 빠뜨린 채였다 — 읽는 곳이 없어 아무도 몰랐다.

**규칙:**
- 검사에서 빼는 파일은 첫 줄 `// @ts-nocheck`(어떤 문보다 앞) + 같은 줄에 이유와 고칠 곳. 고치는 PR 이 그 줄을 지운다. 그 줄을 문 뒤에 두면 무시돼 파일이 검사되고 오류로 드러난다 — 빼는 쪽의 실수가 조용하지 않다(ADR-012 「파일 헤더」).
- 검사 장치는 「켜는 쪽」이 아니라 「빼는 쪽」을 명시하게 두고, 필수 CI 에서 돌린다 — 꺼진 줄 모르는 검사가 가장 비싸다. 설정 · 꾸러미 반환 타입을 바꿀 때는 타입 오류를 일부러 하나 넣어 그 파일에서 잡히는지 본다.
- 창 객체 꾸러미(`window.appX = (() => { … })()`)의 IIFE에는 `@returns {AppX}`를 단다 — 인터페이스에 없는 멤버가 받는 쪽이 아니라 정의한 자리에서 걸린다. 객체 리터럴 꾸러미(`const appX = { … }`)에는 `@type {AppX}`를 단다.
- JSDoc 블록과 그 함수 사이에 다른 선언을 두지 않는다 — 블록은 바로 다음 선언에 붙는다. 매개변수 이름이 맞지 않으면 TS8024로 드러나지만, 이름이 우연히 같거나 다음 선언이 `const`면 조용히 엉뚱한 곳에 붙는다(묶음 ① · ③에서 세 번).
- 데이터 모양의 타입을 고칠 때는 파이프라인(`data/src/parser.py` 등)의 필드 타입과 실제 JSON 을 함께 대조하고, 타입을 넓혔으면(새 값) 그 값을 **쓰는 곳**이 새 값을 다루는지 `grep` 으로 함께 본다 — 경로 · 표시 문자열 · 표 색인.
- 선택 매개변수(`@param {T} [x]`)는 `undefined`만 「없음」으로 받는다. 넘기는 쪽이 null을 「없음」으로 쓰면 `!== undefined`로 가르는 받는 쪽과 조용히 갈린다 — 넘기는 쪽의 null 기본값을 없애거나 받는 쪽을 `!= null`로 맞추고, 두 쪽의 타입을 그대로 적어 검사가 잡게 한다.

## 28. 실패를 「없음」 · 「성공」과 같은 값으로 돌려주지 않는다 — 동기화가 오류를 성공으로 쳤다 (2026-10-17)

전송 함수가 실패를 정상 결과와 같은 값(`null` · `doc: null`)으로 돌려주면, 호출부는 그 값의 정상 갈래(「파일 없음」 · 「원격 없음」)로 간다 — 실패가 성공이 되어 재시도도 알림도 없다. 같은 함수 안에서 한 갈래만 실패 검사를 빠뜨려도 같은 일이 난다.

**사례** (원장 `docs/changes/2026-10-17-sync-signout-inflight.md` — 머지 전 검토 1 · 3번, 사용자 `/code-review` 3 · 4 · 5 · 6번):
- `findSyncFileId`(`js/sync/transport.js`)는 어떤 실패든 `null`(「파일 없음」)이었다 — 캐시에 fileId가 없는 사이클에서 목록 요청이 잠깐 실패하면 새 파일을 만들어, 이미 있는 sync.json 옆에 하나가 더 생길 수 있었다. 이제 `{ fileId, fileIds, status }`를 돌려주고 사이클은 실패를 먼저 가른다.
- 내려받기의 403 · 429 · 400은 `doc: null`이라 「원격 없음」으로 읽혀 SYNC_DONE — 재시도가 없고 redirect 시도 횟수까지 0으로 돌렸다.
- v1 문서를 v2로 올리는 업로드만 `!ok` 검사가 없어 5xx도 「동기화됨」(캐시 기록 · SYNC_DONE)이었다 — 다른 업로드 갈래는 모두 있었다.
- 본문을 읽지 못한 2xx 내려받기(받는 도중 연결이 끊겨 `res.json()`이 reject)는 `{ doc: null, status: 200 }`이라 「원격 없음」 성공으로 끝났다 — 찾기에서 고친 결함이 내려받기에 남아 있었다(main부터). 하네스의 기본 스텁이 바로 그 응답을 정상으로 써서 유닛이 보지 못했다. 이제 status 0(실패).
- 실패를 백오프 다섯 번 뒤 OFFLINE으로 보냈는데, OFFLINE은 브라우저 `online` 이벤트로만 빠져나온다 — 연결된 기기에서 HTTP 실패(429 · 5xx)가 이어지면 그 이벤트는 오지 않아 그 세션 내내 동기화가 멈췄다.
- 「파일도 삭제」의 결과가 `true` · `false` 둘뿐이라, 연결돼 있지 않아 아무것도 하지 않은 경우도 `false` — 「삭제하지 못했습니다」라는 거짓 안내가 떴다. `true`는 목록의 첫 파일만 지운 경우에도 나와, 겹친 sync.json이 남아도 「지웠다」였다.

**규칙:**
- 「없음」과 「실패」는 다른 값으로 돌려준다 — 상태 코드를 함께. 호출부는 실패를 먼저 가른 뒤에 「없음」을 읽는다. 본문을 읽지 못한 2xx도 실패다.
- 한 함수의 갈래들이 같은 실패 분류를 쓰는지 나란히 놓고 본다 — 한 갈래만 빠뜨리기 쉽다. 테스트 하네스의 기본 스텁이 「실패 같은 성공」(`doc: null` · 200)이면 그 응답이 정상으로 굳는다.
- 되돌릴 수 없는 작업의 결과는 됨 · 확인 못 함 · 할 일 없음으로 가른다(`true` · `false` · `null`) — 사용자에게는 「확인 못 함」만 알린다. 「됨」은 확인한 만큼만 말한다(목록의 모든 항목 · 캐시된 id · 이 페이지가 만든 id — 목록이 방금 만든 파일을 늦게 보일 수 있다).
- 재시도 분류는 서비스의 안내를 따른다 — Drive는 403 rate limit · 429 · 5xx를 지수 백오프로 다시 시도하라고 한다([오류 처리 안내](https://developers.google.com/workspace/drive/api/guides/handle-errors), 2026-10-17 확인). 이 앱은 상태 코드로만 갈라 실패를 모두 백오프(최대 다섯 번)하고, 그래도 실패하면 네트워크 실패만 OFFLINE, HTTP 실패는 IDLE로 돌아가 다음 요청이 다시 시도한다 — 다시 해도 소용없는 400 · 다른 403은 다섯 번에서 멈춘다(403의 이유를 읽어 가르지는 않는다).
- 실패로 들어가는 상태마다 빠져나오는 길을 적고, 그 길이 오지 않는 경우가 없는지 본다(온라인인 채로 `online` 이벤트를 기다리는 OFFLINE).

## 29. 알림 문구는 결과부터 — 된 것과 안 된 것, 다음 할 일은 화면의 단추 이름으로 (사용자 교정, 2026-10-17)

한 번의 누름이 둘 이상을 하는 동작(연결 해제 + Drive 파일 삭제)이 일부만 실패하면, 문구가 무엇이 실패했는지만 말하고 무엇이 이미 끝났는지는 빠뜨리기 쉽다. 다음 할 일을 「…에서」처럼 자리로 흐리게 가리키면 사용자가 어디를 눌러야 할지 모른다.

**사례:**
- `docs/changes/2026-10-17-sync-signout-inflight.md` — 「파일도 삭제」가 파일을 지우지 못했을 때의 스낵바 초안 「Drive의 동기화 파일을 삭제하지 못했습니다. 다시 연결한 뒤 연결 해제에서 다시 삭제해 주세요.」에 사용자가 「여기 한국어 문장 어색하다?」 — 「다시」가 두 번, 「연결 해제에서」는 어디인지 흐리고, 연결 해제는 이미 됐다는 사실이 없다. 고친 문구: 「연결은 해제했지만 Drive의 동기화 파일은 삭제하지 못했습니다. 다시 연결한 뒤 「파일도 삭제」를 눌러 주세요.」

**규칙:**
- 한 동작이 둘 이상을 하면 된 것과 안 된 것을 함께 말한다(「연결은 해제했지만 … 삭제하지 못했습니다」).
- 다음 할 일은 사용자가 화면에서 보는 단추 · 메뉴 이름 그대로 쓴다(「파일도 삭제」를 눌러 주세요).
- 한 문장에 같은 부사(「다시」)를 되풀이하지 않는다 — 보내기 전에 소리 내어 읽듯 한 번 읽는다.

## 30. PR 제목은 짧게 — 세부는 본문에 (작업 방식 교정, 2026-10-17)

**사례:**
- `docs/changes/2026-10-17-sync-signout-inflight.md` — 첫 제목 「fix: 동기화 사이클 — 도중에 로그아웃하면 멈추고, 실패를 성공으로 치지 않고, 「파일도 삭제」 뒤 파일을 되살리지 않는다 (known-issues §11 · 머지 전 검토)」에 사용자 교정: 「PR 제목은 길지 않고 간결하게 작성해줘」 · 「세부 내용은 PR 본문에 채우면 되니까」. 고친 제목: 「fix: Drive 동기화 — 로그아웃 경합 · 실패 처리 · 「파일도 삭제」」. 앞선 PR(#353 등)도 제목이 길었다.

**규칙:**
- 제목은 무엇을 고쳤는지 한 줄. 절 번호(known-issues §n) · 건수 · 「무엇이 어떻게」는 본문(「요약」 이하)에 쓴다. 커밋 제목도 같은 결로 짧게.
- 저장소 규칙은 `docs/changes/README.md` 「규칙」 첫 줄 — 원장을 쓸 때 거기서 다시 본다.

## 31. 영어 · 한국어가 섞인 문장 — 영어 단어 뒤의 조사 · 용언은 붙여 쓴다 (사용자 교정, 2026-10-17)

영어 단어(코드 이름 · 파일명 · 약어 포함) 바로 뒤의 조사와 용언을 띄어 썼다 — 「`sync.json` 을」, 「OFFLINE 으로」, 「push 되면」. 맞춤법대로 조사와 「-하다 · -되다」는 앞말에 붙는다.

**사례:**
- PR #354(`docs/changes/2026-10-17-sync-signout-inflight.md`)의 `architecture.md` 현행화 중 사용자 교정: 「영어, 한국어가 혼용된 문장에서 영어 단어 뒤에 오는 한국어 조사, 용언은 띄어쓰지 말 것」. 그 PR에서 쓰거나 고친 줄의 418곳과 data 저장소 README · CLAUDE.md(data#33)의 88곳을 붙였다.

**규칙:**
- 조사(을/를 · 이/가 · 은/는 · 의 · 에 · 로/으로 · 와/과 · 도 · 만 · 마다 …)와 서술격 조사는 영어 단어 · 코드 이름에 붙인다: 「`sync.json`을」, 「OFFLINE으로」, 「PR마다」, 「`false`일 때」, 「SYNCING이라」.
- 「-하다 · -되다」 용언도 붙인다: 「push되면」, 「dedup해」, 「push된다」.
- 뒤가 명사 · 관형사 · 독립된 말이면 띄운다: 「HTTP 실패」, 「Google 태그」, 「(`storage` 이벤트) 이 탭도」(「이 탭」의 「이」), 「`pollSync()`를 한 번」(「한 번」의 「한」).
- 기계로 고칠 때는 조사 목록으로 후보를 뽑되, 낱말일 수 있는 「이 · 나 · 도 · 만 · 면 · 일 · 한」은 하나씩 본다. ASCII 그림 안의 줄은 글자 수가 줄어 테두리가 어긋나므로 다시 맞춘다.
- 문서 · 원장 · PR 본문 · 커밋 메시지 · 코드의 한국어 주석과 테스트 이름 · 답글에 모두 적용한다. 이 교정 전에 쓴 문서에는 띄어 쓴 곳이 많이 남아 있다(머지된 원장은 고칠 수 없다).

## 32. 숫자 구간에 물결표(~)를 쓰지 않는다 — 하이픈으로 (사용자 교정, 2026-10-17)

GitHub 마크다운(GFM)은 물결표 하나짜리 쌍(`~…~`)도 취소선으로 읽는다. 한 단락에 구간이 둘 있으면 그 사이가 지워져 보인다.

**사례:**
- PR #354 원장의 `44~50(…), 51~54(…)` 같은 표기 — PR 페이지에서 가운데가 취소선이 됐다. 사용자 교정: 「한국어 문장에서 흔히 숫자 구간 표현에 쓰이는 물결 표시(`~`)는 마크다운 서식 오류를 자주 유발하므로 다른 표현으로 대체 바람」 · 「차라리 영어식 표현인 하이픈이 적절할 듯」.

**규칙:**
- 숫자 · 번호 구간은 하이픈: 「44-50」, 「Phase 2a-2j」, 「1583-9999」. ID 구간은 접두어를 한 번만: 「ADR 001-038」(「ADR-001-038」은 ID처럼 읽힌다).
- 날짜처럼 값 안에 하이픈이 있으면 말로 잇는다: 「2026-05-10부터 10-17까지」, 이어진 이틀은 「2026-05-09 · 05-10」.
- 근삿값도 산문에서는 「약」으로: 「약 6,000줄」. 표의 줄 수 칸(`~330`)처럼 칸마다 하나면 짝이 생기지 않고, 코드 블록 · 인라인 코드 안(`~/projects` 경로)은 서식이 없어 괜찮다.

## 33. 이미 받은 모듈도 `import()`는 한 태스크 뒤에 풀린다 — 다시 그리는 길에서 기다리지 않는다 (리뷰, 2026-10-18)

`await import(…)`는 모듈이 이미 모듈 맵에 있어도 바로(마이크로태스크로) 풀리지 않는다 — Chromium에서는 태스크 하나 뒤에 풀린다(먼저 건 `setTimeout(0)` · `postMessage`가 먼저 돈다 — 실측). WebKit(Playwright 26.4)은 마이크로태스크로 풀어 이 깜박임이 없었다(5번 중 5번 — 2회차 리뷰). 엔진마다 다르니 기다리지 않는 쪽으로 짠다. 그 사이에 브라우저가 한 프레임을 그릴 수 있어, `await` 앞에서 바꿔 둔 화면(「불러오는 중…」)이 매번 번쩍인다. 데이터가 메모리에 있는 다시 그리기는 원래 그리기 전에 끝나던 일이라, 사용자 눈에는 새로 생긴 깜박임이다.

**사례:**
- PR #355 — 캘린더 · 전례독서를 처음 갈 때 받게 바꾸면서 `routing.js`의 분기가 매번 `await loadViewModule(() => Promise.all([import(…)]))`를 거쳤다. 달 이동 · 칩 · 세그먼트 · 날짜 이동마다 `renderLoading()`의 「불러오는 중…」이 한 프레임 그려졌다 — 달 이동 40번 중 40번(main 0번). 그 프레임에 스크롤이 0으로 눌렸다가 포커스 복원이 되돌리고, 데스크톱에서는 접힌 머리가 펼쳐졌다 접혔다. 최종 상태만 보는 e2e는 통과했다.

**규칙:**
- 처음 받은 뒤의 길에서는 `import()`를 기다리지 않는다 — 받은 모듈(또는 쓸 함수)을 변수에 두고 바로 쓴다. 성공만 둔다 — 실패를 두면 다시 시도하지 않는다(`routing.js` `loadedViews`).
- 깜박임은 최종 상태로는 보이지 않는다 — 프레임마다(rAF) 그 요소가 있었는지 세어 본다(`tests/e2e/test_liturgical_lazy_load.py`의 `WATCH_LOADING_FRAMES`).
- 반대로 기다림이 사라지면 「중간 상태」에 기대던 테스트가 깨진다 — 같은 PR에서 「오늘 → 다음날 → 전날」 테스트가 `?track=` 없는 중간 주소를 기다리다 실패했다(트랙 있는 주일, 이동과 주소 고치기가 한 태스크 안에 끝난다). 주소는 경로만 비교한다.

## 34. WebKit의 `modulepreload`는 새로 고쳐도 다시 받지 않는다 — 실패한 미리 받기가 그 탭을 막는다 (리뷰, 2026-10-18)

`<link rel="modulepreload">`로 받은 모듈은 WebKit에서 그 탭의 메모리에 남아, 새로 고침(`location.reload()`)도 같은 주소로 다시 가기도 그것을 다시 쓴다 — 서버에 요청이 가지 않는다. 미리 받기가 실패했으면 실패가 남아 그 탭에서는 화면이 열리지 않고(새 탭에서만 열린다), 성공했으면 서버의 파일이 바뀌어도 옛 것이 돈다. 같은 페이지의 다른 파일(`routing.js` · `style.css`)은 새로 고칠 때 304로 재검증된다. Chromium은 새로 고침이 다시 받는다.

**사례:**
- PR #355 — 공유 링크로 처음 들어온 캘린더 · 전례독서가 늦게 그려지는 것(1회차 리뷰)을 `pre-fetch.js`의 `modulepreload`로 메웠다(느린 4G +198 → +51ms). 2회차 리뷰가 WebKit(Playwright 26.4)에서 calendar.js 첫 요청을 503으로 실패시키자, 「다시 불러오기」를 세 번 눌러도 20초 뒤 새로 고쳐도 서버 요청이 1회 그대로였다. 미리 받기가 없는 판은 새로 고침이 다시 받아 열렸다. 서비스 워커가 없는 WebKit 세션(iOS 인앱 브라우저 등)으로 공유 링크를 여는 — 미리 받기가 도우려던 바로 그 — 경우라 되돌렸다(사용자 결정 2026-10-18).

**규칙:**
- 「새로 고침이 고친다」에 기대는 실패 복구가 있는 모듈에는 `modulepreload`를 걸지 않는다. 걸려면 WebKit에서 「실패 → 새로 고침 → 회복」을 먼저 확인한다.
- 미리 받기 · 캐시 동작은 엔진마다 다르다 — Chromium만 도는 e2e로는 보이지 않는다. 그런 변경은 WebKit으로 한 번 돌린다. 이 클론의 호스트에는 Playwright WebKit이 쓰는 라이브러리가 없어, 2회차 리뷰어는 필요한 패키지를 스크래치에 풀고 `PLAYWRIGHT_BROWSERS_PATH` · `PLAYWRIGHT_SKIP_VALIDATE_HOST_REQUIREMENTS=1`로 띄웠다.

## 35. 외부 입력은 타입만 보지 말고, 그 값을 받는 코드가 다룰 수 있는 형식인지 검사한다 — 가져오기 검사가 리뷰마다 샜다 (리뷰, 2026-10-19)

밖에서 들어오는 값(가져오기 파일 · 공유 링크 · 동기화 문서)을 「문자열이다 · 수다 · 배열이다」로만 거르면, 통과한 값이 그 값을 쓰는 코드에서 깨진다. 기준은 타입 선언이 아니라 그 값이 흘러가는 모든 곳이다 — 객체의 키, 주소, 재귀, 배열로 펼치기, 저장 한도.

**사례:**
- PR #359(북마크 가져오기, ADR-040) — 처음 검사는 타입과 「절 범위의 구간이 모두 읽히는가」를 봤다.
  - Copilot 1회차가 두 갈래를 찾았다 — 객체 기본 속성 이름인 id(`toString` — 동기화 저장소가 id를 일반 객체의 키로 써 목록 읽기가 깨진다), 북마크에 붙은 `children`(저장소가 어떤 항목의 자식이든 훑는다).
  - 2회차(Copilot + 자체 리뷰어 셋)가 다시 여섯 갈래를 찾았다 — 큰 수 · 큰 범위 · 공백 · 거꾸로 된 범위의 절 범위(합치기 · 주소 해석 · 강조), `?` · `#` · `..`가 든 폴더 id(모아 읽기 주소), 수천 단 폴더(재귀), `1e400` 날짜(저장하면 `null`), 지금 목록과 종류가 다른 같은 id(동기화가 옛 종류로 되돌림), 저장 한도를 넘는 목록(조용히 실패). 모두 타입은 맞았다.
  - 2회차 뒤 자체 리뷰가 그 크기 검사를 다시 깼다 — 목록 JSON에 둔 고정 예산(600,000자)은 부모 id를 자식마다 되풀이하는 저장 구조(1,000자 id면 21배)를 놓쳐 저장 실패를 들였고, 메모가 긴 자기 백업(2배)은 막았다. 저장할 문서를 쓰지 않고 만들어 재는 것으로 바꿨다.
- 주소의 절 범위(2026-10-21, known-issues §15) — 가져오기 검사가 막은 큰 범위와 되풀이한 구간이 공유 링크로는 그대로 들어왔다. 라우터가 여러 구간을 절 하나하나로 펼쳐, 처음 여는 링크가 시작 화면에서 멈췄다. 같은 절 범위가 파일 · 주소 · 동기화 세 입구로 들어오는데, 검사는 파일 입구에만 있었다. 검사를 `verse-spec.js isWellFormedSpec`으로 옮겨 주소 해석도 같이 쓰게 했다. 검사 없이 이미 저장된 북마크(1.6.4 이하에서 들인 것 — 그 기기에 남은 것 · 동기화로 간 것)는 아직 다시 검사하지 않는다(known-issues §15).
  - 그 PR의 리뷰에서 주소의 앞뒤 쉼표를 걷기로 했다(사용자 결정 2026-10-21). 처음 떠올린 `/^,+|,+$/g`는 쉼표가 길게 이어진 뒤 다른 글자가 오면 제곱 시간이 걸렸다(쉼표 4만 개에 약 1초, 두 배면 네 배). 이 함수는 스크롤 프레임마다 돌아, 그대로 썼다면 막으려던 멈춤을 다른 길로 다시 열었을 것이다. 반복문으로 걷었다.

**규칙:**
- 검사를 쓰기 전에 그 값이 가는 곳을 끝까지 따라가 목록을 만든다 — 객체의 키 · 주소 · 재귀 깊이 · 펼치기 · `JSON.stringify` · 저장 한도. 그리고 각 소비처가 받는 형식을 기준에 넣는다.
- 같은 값이 여러 입구로 들어오면(가져오기 파일 · 주소 · 동기화 문서) 검사를 입구마다 따로 쓰지 말고, 하나를 두고 모두 함께 쓴다. 검사는 그 값을 다루는 모듈에 둔다(절 범위면 `verse-spec.js`). 한 입구를 고칠 때는 다른 입구도 같은 값을 받는지 찾는다.
- 바깥 입력에 쓰는 정규식은 되돌아가기가 제곱이 되지 않는지 본다. 앞이 고정되지 않은 반복(`,+$` · `\s+$`)은 같은 글자가 길게 이어진 뒤 다른 글자가 오면 시작점마다 끝까지 다시 훑는다. 자주 도는 코드(스크롤 · 입력마다)에서는 반복문으로 다듬고, 긴 입력의 시간을 테스트로 묶는다(`tests/unit/routing.test.js`의 「긴 쉼표 줄」).
- 받을 형식은 「앱이 쓰는 형식」으로 정한다(허용 목록). 깨지는 경우를 하나씩 막는 검사(거부 목록)는 다음 리뷰에서 또 샌다. 앱의 직렬화 함수가 만드는 값이 모두 통과하는지는 테스트로 묶는다 — 직렬화가 바뀌면 검사도 바뀌어야 한다(`tests/unit/bookmark.test.js`의 합성 장 테스트).
- 저장 한도 같은 플랫폼 제약은 가장 빠듯한 엔진으로 정한다. Chromium은 localStorage를 문자 수로 세지만, Safari는 바이트로 세고 한글은 한 글자에 2바이트다(ADR-040 「검증」).
- 크기처럼 다른 코드가 만들어 내는 양은 배율로 어림하지 말고, 그 코드로 실제 결과를 만들어 잰다(쓰지 않고) — 어림한 배율은 그 코드가 바뀌거나 입력의 모양이 달라지면 양쪽으로 샌다.

## 36. 「꼴」을 쓰지 않는다 — 한 낱말이 여러 뜻을 맡아 읽기 어렵다 (사용자 교정, 2026-10-20)

「앱이 쓰는 꼴」 · 「저장될 꼴」 · 「어긋난 꼴」 · 「버린 꼴」처럼, 「꼴」 한 낱말이 문자열의 표기, 데이터의 구조, 예(경우), 버린 설계를 모두 맡았다. 같은 문서 안에서도 뜻이 바뀌어, 읽는 사람이 자리마다 뜻을 짐작해야 했다.

**사례:**
- PR #359 머지 직후 사용자가 ADR-040을 열어 보고 「문서에서 "꼴"이 무엇을 의미하는 지 이해하기 어렵네」라고 했다. 저장소 전체에 144군데(「글꼴」 제외 — 문서 · 주석 · 테스트 이름 · 픽스처 · 도구, 그리고 화면 문구 하나)가 있었고, 사용자 「"꼴"이 쓰인 곳을 찾아서 이해하기 쉽게 수정 바람」으로 자리마다 고쳤다(원장 `docs/changes/2026-10-20-plain-wording-kkol.md`).

**규칙:**
- 그 자리의 뜻을 쓴다. 문자열을 적는 방식(절 범위 「16」 · 「1-5」, 날짜 「12.25」)은 「표기」, 값 · 객체의 모양은 「형식」, 저장소에 실제로 쓰이는 모양은 「저장 구조」, 규칙에 어긋난 예나 사정이 같은 날은 「경우」, 버린 설계는 「안」, 일하는 방법은 「방식」이다. 「X 꼴로 줄인다」는 「X처럼 줄인다」로 쓴다.
- 「글꼴」(폰트)은 바른 낱말이다. 성서 본문의 「꼴」(「네모꼴」 · 「망하는 꼴」)은 본문이므로 건드리지 않는다.
- 보내기 전에 `grep -n "꼴" <파일> | grep -v 글꼴`로 남은 것이 없는지 본다.

## 37. 한국어답게 쓴다 — 완결된 문장으로, 간결하게, 그 분야의 용어로 (사용자 교정, 2026-10-21)

원장과 문서에 명사를 가운뎃점(·), 줄표(—), 「A = B」, 겹친 괄호로 이어 붙인 문장이 많았다. 읽는 사람이 낱말 사이의 관계를 짐작해야 했다. 반대로 풀어 쓰려다 문장이 늘어지거나, 용어 대신 긴 설명을 쓰는 것도 읽기 어렵다.

**사례:**
- 머지된 원장 `docs/changes/2026-10-21-verse-range-link.md`의 「리뷰 반영」 첫 문단. 사용자가 「한국어를 한국어답게 쓰자. 읽어도 무슨 소린지 이해하기 어렵네」라고 했다. 머지된 원장이라 고치지 못한다.
  - 전: 「사용자 「서브 에이전트로 리뷰」. 결과를 보기 전에 범위 · 기준 · 횟수를 정했다 — 읽기 전용 리뷰어 셋(A 주소 · 라우팅, B 모듈 이동 · 부팅 · 테스트, C 문서), 고친다 = 이 PR이 만든 결함 · 덜 고친 것 · 사실 오류, 넘긴다 = main부터 · 문체 · 재현 못 한 가정, 2회차는 고친 줄만 보고 3회차는 없다.」
  - 후: 「사용자가 서브에이전트 리뷰를 요청했다. 결과를 보기 전에 범위와 기준을 정했다. 리뷰어는 읽기 전용으로 셋을 두고, 각각 주소와 라우팅, 모듈 이동과 부팅과 테스트, 문서를 맡겼다. 이 PR이 만든 결함, 덜 고친 부분, 사실 오류는 고친다. main부터 있던 문제, 문체, 재현하지 못한 추정은 후속으로 넘긴다. 리뷰는 2회까지 하며, 2회차는 수정한 줄만 본다.」
- 「개정 블록을 본문에 녹인다」는 비유였다. 사용자가 「녹일지는 무슨 뜻이니」라고 물었다. 「개정 내용을 본문에 반영하고 개정 블록을 삭제한다」로 쓴다.
- 고쳐 쓴 글이 「그 절이 원래 있던 장」처럼 용어를 풀어 늘어졌다. 사용자가 「한국어 문장은 완결된 형태이지만 간결해야 해. 도메인에 맞는 용어를 쓸 것」이라고 했다. 「본래 장」으로 쓴다.

**규칙:**
- 문장은 완결된 형태로 쓰되 간결하게 쓴다. 한 문장에는 한 가지를 말한다.
- 명사를 나열하지 않는다. 조사와 서술어로 관계를 밝힌다. 「고친다 = 결함」이 아니라 「결함은 고친다」다.
- 가운뎃점은 짧은 낱말 두세 개를 나란히 둘 때만 쓴다. 줄표로 덧말을 잇지 않고, 괄호를 겹치지 않는다.
- 그 분야의 용어를 쓴다. 문서 작업은 「반영」 · 「삭제」 · 「갱신」, 성서는 「본문」 · 「장절」 · 「본래 장」이다. 이 저장소에 자리 잡은 말(「옮겨 실린 절」, 「그리스어 추가 본문」)은 그대로 쓴다. 쉽게 쓰겠다고 용어를 긴 설명으로 바꾸지 않는다.
- 비유로 말하지 않는다.
- 사용자의 말은 「사용자가 …라고 했다」로 인용한다.
- 「A 주소 · 라우팅」처럼 기호를 붙여 부르지 않는다.
- 보내기 전에 소리 내어 읽듯 한 번 읽는다. 조사와 서술어 없이 이어진 줄, 같은 말을 되풀이한 줄은 고친다.

## 38. 옛 판이 저장한 절 범위는 지금 표기로 옮긴다 — 수정 시각은 올리지 않는다 (사용자 결정, 2026-10-22)

2026-04-25부터 06-06(#205)까지의 앱은 여러 줄인 절의 일부 줄을 고르면 줄 글자를 그대로 저장했다(「35a」 · 「20a,20c」 · 「16aa」 · 「7-8a」). main(`f358691`)은 그 글자를 북마크 목록과 합치기 대화상자에 그대로 보였다. `parseVerseSpec`이 읽지 못하는 「16aa」 · 「7-8a」는 모아 읽기에서 그리지 않았고, 합치면 그 절을 버렸다(이사 10 「16aa」에 1절을 합치면 「1」). PR #364 뒤의 화면은 줄 글자를 쓰지 않고 반쪽 절을 「8ㄱ」으로 적는다.

**사례:**
- known-issues §18 첫 항목. 사용자가 PR #365 작업 중에 「이전 버전 북마크와 하위 호환성도 고민해야 할텐데, 그건 다음 PR에서...」라고 했다. 다음 PR을 시작하며 화면에서 재현한 뒤(main `f358691`, Chromium) 네 가지를 물었고, 사용자가 모두 권장안을 골랐다.

**결정:**
- 저장값을 옮긴다. 글자를 떼어 번호로 만들고 정규형으로 다시 적는다(「16aa」 → 「16」, 「7-8a」 → 「7-8」, 「20a,20c」 → 「20」). 장 데이터는 쓰지 않는다. 줄 단위 범위는 절 전체로 넓어지며, 이는 북마크를 절 번호 단위로 저장하는 지금 정책(ADR-010)과 같다. 읽는 쪽만 고치는 안은 고르지 않았다. 반쪽 절 「5a」와 줄 「35a」를 가리려면 장 데이터가 필요하고, 표시하는 곳을 하나씩 고쳐야 한다.
- 앱을 시작할 때 저장된 목록을 옮긴다. 가져오기는 들이면서 옮기고, 합치기도 같은 규칙으로 읽는다.
- 옮길 때 수정 시각(`_u`)은 올리지 않는다. 시작할 때의 옮기기는 동기화가 드라이브를 받기 전에 돈다. 시각을 올리면 다른 기기에서 그 북마크를 고친 내용이 이 기기의 옮긴 사본에 밀려 사라질 수 있다.
- 동기화 결과도 저장하기 전에 옮긴다(구현 중에 더함). 처음에는 다음 시작 때 옮겨지리라 보았다. 그러나 수정 시각이 같은 두 사본은 병합이 기기 id 순서로 하나를 고르므로, 드라이브에 옛 표기가 남아 있으면 기기에 따라 동기화할 때마다 옛 표기가 돌아온다. 실제 `js/sync/store-v2.js mergeDocs`에 두 사본을 넣어 확인했다. 기기 id가 드라이브 쪽보다 뒤인 기기는 옛 표기를 받는다.
- 북마크 이름은 옛 기본 이름(「책 장:옛 저장값」)과 정확히 같을 때만 새 기본 이름으로 바꾼다. 사용자가 고친 이름은 그대로 둔다.
- 여러 줄인 병합 절은 「7-8」로 저장한다(known-issues §17 첫 항목). 이미 저장된 「7」은 장 데이터 없이는 병합 절인지 알 수 없어 그대로 둔다.
- 병합 절은 앞뒤 절과 잇는다(구현 중에 더함). 나훔 1장에서 1절부터 2ㄴ까지 고르면 「1-9」다. 「7-8」만 고치면 제목이 「나훔 1:1-6,7-8,9」가 되어, 선택 막대의 「1-9」와 여전히 달랐다.

**규칙:**
- 저장 표기를 바꿀 때는 옛 판이 쓴 값이 저장소와 가져오기 파일과 동기화 문서에 남아 있다고 본다. 옮기는 함수는 하나만 두고, 그 값이 들어오는 곳이 모두 함께 쓴다(§35).
- 사용자 데이터를 옮기기 전에 동기화의 충돌 규칙을 본다. 항목마다 시각이 나중인 사본을 고르는 동기화에서 옮기기가 시각을 올리면 다른 기기의 편집을 덮는다. 시각을 올리지 않으면 같은 시각의 두 사본 가운데 하나를 내용과 상관없이 고르므로, 병합 결과를 받는 길에서도 같은 함수로 옮긴다.

## 부록 B: 같은 시각 효과를 여러 곳에 적용할 때

CSS의 시각 효과(모서리 라운드 평탄화, 강조 색 등)를 인접 요소 사이에 적용할 때, 적용 대상의 **레이아웃 모드**를 가정한 채 작성하면 다른 모드에서 깨진다.

## 패턴 추가 가이드

새로운 실수 유형을 발견하면 다음 형식으로 추가:

```markdown
## N. 카테고리명 — 짧은 부제 (선택)

한 문단의 패턴 설명.

**사례:**
- `<커밋해시>` — 한 줄 요약.

**규칙:**
- 액션 가능한 규칙 1.
- 액션 가능한 규칙 2.
```

가능하면 실제 커밋 해시를 첨부해 검증 가능하게 한다.
