# 코딩 실수 패턴 (Coding Pitfalls)

ADR이 "왜 이 결정을 했는가"를 다룬다면, 이 문서는 **"무엇을 조심해야 하는가"**에 초점을 맞춘다. 처음에는 git 커밋 이력에서 반복된 실수 패턴을 뽑아 만들었다(2026-05-03 기준, 커밋 99개 가운데 fix 38개로 38.4%).

## 사용법

- 한 주제에만 해당하는 함정은 그 주제 문서(`docs/topics/`)의 「함정」에 있다. 여기에는 절 제목과 대장 줄(「→ topics/…」)만 남는다. 여러 주제에 걸치는 함정은 여기에 전문을 둔다(2026-10-23부터). 글쓰기 교정은 `docs/writing.md`, 작업 방식 교정은 `docs/workflow.md`의 「함정」에 있다.
- 새 기능을 구현하기 전에 주제 문서의 함정과 여기의 공통 함정을 훑어본다. 코드 리뷰 때 같은 패턴이 되풀이되지 않는지 본다.
- 새 함정은 다음 번호(§41부터)를 받는다. 한 주제에만 해당하면 그 주제 문서에, 여럿에 걸치면 여기에, 글쓰기와 작업 방식이면 `writing.md`와 `workflow.md`에 쓴다. 코드 실수뿐 아니라 **사용자 교정**(작업 방식과 판단을 바로잡은 것)과 **도메인 확정**(책자와 기도서를 대조해 굳어진 규칙)도 함정으로 적는다. 항목마다 날짜와 근거(원장 파일, 커밋, PR)를 남긴다.
- 코드 주석과 머지된 원장이 「pitfalls §N」으로 가리키므로 번호는 다시 쓰지도 당기지도 않는다.

## 1. 비동기 타이밍의 경쟁 상태 — 가장 빈번

여러 비동기 작업이 동시에 진행될 때, 늦게 도착한 낡은 콜백이 최신 상태를 덮어쓰는 패턴.

**사례:**
- `21540a0`(`updateAppIcons`): 테마를 빠르게 바꾸면 이전 컬러스킴의 `requestIdleCallback`과 `loadOrigIcon` 체인이 뒤늦게 실행되어 새 남색 아이콘을 덮어썼다.
- `5c41797`: 북마크 드로어에서 `open→close→open`을 반복하면, 닫힘 애니메이션의 `finalize` 콜백이 새로 열린 드로어를 숨겼다.
- `fc6d374`: Drive 동기화에서 여러 요청이 동시에 401을 받으면 각자 `_silentSignIn()`을 호출했다. 재인증 콜백이 여러 번 실행되어 `_downloadAndMerge`와 `_upload`가 중복되었고, 마지막 요청이 이전 기록을 덮어썼다. `_isRefreshing` 플래그로 한 번에 하나만 진행하게 했다.
- e2e(2026-10-15, #348 리뷰 반영 중 확인): `html { scroll-behavior: smooth }`라서 테스트의 `window.scrollTo(0, 600)`은 애니메이션으로 움직인다. 스크롤 도중 64px를 넘는 순간 탭 바가 접힌다. 그 상태를 보자마자 홈 탭을 누르면 남은 아래쪽 스크롤이 펼친 바를 다시 접는다. `test_scroll_collapse_and_home_expands_without_nav`가 누르는 시점에 따라 결과가 갈렸다(같은 코드로 통과하던 것이 이날은 매번 실패했다). 스크롤로 만든 상태를 바로 이어서 조작하는 테스트는 `scrollTo({ top, behavior: 'instant' })`로 경쟁 상태를 없앤다.

**방어 전략 (상황에 따라 선택):**

| 전략 | 적용 상황 | 구현 |
|------|----------|------|
| Generation 카운터 | 장기 비동기 체인(이미지 디코드, 파일 가져오기) | 시작할 때 `_gen`을 저장하고, 완료되었을 때 `_gen === currentGen`이면 적용 |
| Sequence 번호 + clearTimeout | 타이머 기반 애니메이션 | 새 작업을 시작할 때 순번을 올리고 이전 `setTimeout`을 직접 취소 |
| Singleton 플래그 | 토큰 갱신, 재인증, 일회성 동기화 | `_isRefreshing` 같은 플래그로 진행 중에 다시 들어오는 것을 막는다 |
| Promise.race + timeout | 네트워크나 폰트 불러오기 | `Promise.race([fetch(...), timeout(1500)])`로 무한 대기를 막는다 |

**규칙:** 같은 작업이 여러 번 트리거될 수 있으면 "최신 호출만 유효" 또는 "동시에 하나만 유효" 패턴을 처음부터 설계한다.

## 3. 상태 갱신 누락 — UI 불일치

CRUD 작업 후 의존하는 UI 컴포넌트의 갱신 함수를 호출하지 않아, 데이터는 바뀌었으나 화면에 반영되지 않는 패턴.

**사례:**
- `03d7884`: 북마크를 저장, 수정, 병합, 삭제한 뒤 헤더 북마크 버튼의 `has-bookmark` 상태가 갱신되지 않았다. 모든 작업 지점에서 `refreshBookmarkHeaderBtn()`을 호출하게 했다.
- `8762b3c`: 길게 눌러서(long-press) 북마크를 저장하면 헤더 아이콘이 갱신되지 않았다. `03d7884`에서 클릭 경로는 고쳤으나 길게 누르는 경로를 빠뜨렸다.
- `ff39997`: 구분(division) 화면에서 `updatePageMeta()`를 인자 없이 호출해, `setTitleWithDivisionPicker()`가 설정한 제목을 덮어썼다.
- `3303176`: 검색 자동 이동에서 안쪽과 바깥쪽 `route()`가 둘 다 메타를 설정해 충돌했다.
- `7808c89`: 장 이동 시 절 선택 모드가 끝나지 않고 `inert` 선택자도 갱신되지 않아, 다음 장에 비활성 요소가 남았다.

**규칙:**
- CRUD 함수마다 갱신 호출을 명시적으로 작성한다(중앙 이벤트 시스템이 없는 한 자동 동기화에 의존하지 않는다).
- **모든 진입점**(클릭, 길게 누르기, 가져오기, 끌어다 놓기 등)에서 같은 갱신 호출을 한다. 새 진입점을 추가할 때는 기존 진입점의 후처리를 그대로 따라간다.
- 라우팅이 중첩될 수 있으면 메타 설정 책임을 한 레이어로 한정한다.
- **페이지나 화면을 바꿀 때 정리할 모드 상태를 체크리스트로 관리한다**: 절 선택 모드, 모달, `inert` 속성, 임시 이벤트 리스너 등.

## 4. 조건문 논리 오류

방향이 뒤집힌 비교, 분기마다 빠진 검증, 잘못된 위치의 검사처럼 한눈에 보이지 않는 논리 결함.

**사례:**
- `16b70ae`: 폴더를 끌어다 놓을 때 순환 참조를 검사하는 코드에서 `_isDescendant`의 인자 순서가 반대였다. 실제로는 "드래그 대상이 드롭 위치의 조상인가"를 봐야 하는데 반대로 검사했다.
- `f154a56`: 같은 순환 참조 검사가 `position === "into"` 분기에만 있고 `before`와 `after` 분기에는 빠져 있었다. 폴더를 자기 조상의 형제로 놓으면 검사를 통과했다.
- `3b9727f`: 단일 절 범위 초과 검사가 `hlVerseEnd != null` 블록 **안**에만 있어, 정작 필요한 경우에 작동하지 않았다. 검사를 블록 밖으로 옮겼다.
- 2026-10-17(PR #353 리뷰, 원장 `docs/changes/2026-10-17-typecheck-batch-1.md`): URL에서 온 값을 검사하는 곳 둘이 문제였다. 하나는 장 번호다. `/john/abc`의 장 번호를 `parseInt`가 `NaN`으로 내는데, `chapter < 1 || chapter > count`가 둘 다 거짓이라 `john-NaN.json`을 요청했다(`Number.isInteger`를 더했다). 다른 하나는 구분 이름이다. `/constructor`는 구분 표 `DIVISION_LABELS[name]`의 참거짓으로 가르다가 일반 객체가 물려받은 이름까지 구분으로 인정됐다(`Object.hasOwn`을 썼다).
- 2026-10-26(known-issues §15.2, 원장 `docs/changes/2026-10-26-bookmark-merge-sync-ids.md`): 동기화 저장소(`store-v2.js`)가 북마크를 일반 객체에 부모 id별로 묶었다. 그래서 `toString` id가 하나만 있어도 목록 전체를 읽지 못했다. 처음 적어 둔 고치는 법은 이 한 곳만 가리켰다. 그러나 같은 객체를 id로 찾는 병합과 삭제 기록에도 같은 결함이 있었다. 병합에서는 한쪽에만 있는 그 id의 북마크가 빠졌고, 그 북마크를 지우면 삭제 기록이 남지 않았다. 같은 PR의 리뷰는 같은 id를 키로 쓰는 다른 객체에서도 같은 조회를 찾았다. 「최근 본 순」 정렬이 읽는 본 기록(`bookmark-core.js`)이다. 묶을 때는 `Map`을, 찾을 때는 `Object.hasOwn`을 쓰도록 고쳤다.

**규칙:**
- 부모-자식 관계 검사 헬퍼는 인자 순서가 헷갈리지 않게 시그니처 위에 한 줄 주석:
  `// _isDescendant(ancestor, candidateId) — candidate가 ancestor의 후손인가?`
- 분기로 갈라진 동일 의도 검증이 있는지 확인. "이 검증이 다른 분기에도 필요한가?"를 한 번 더 묻는다.
- 검사 구문(guard clause)은 가능한 한 **분기 시작 시점**에 둔다. 분기 안에 두면 의도하지 않게 검사를 통과하는 경우가 생기지 않는지 확인한다.
- URL이나 저장소에서 온 수는 범위 비교만으로 거르지 않는다. `NaN`은 모든 비교에서 거짓이다. 먼저 `Number.isInteger`로 검사한다(또는 정규식으로 통째 검사한다. `routing.js` 전례독서 쿼리의 `positive`가 그렇다).
- 바깥에서 온 문자열을 일반 객체의 키로 찾을 때는 `Object.hasOwn`(또는 `Map`)을 쓴다. `constructor`, `toString`, `__proto__`도 참이다.
- 그런 조회 하나를 고칠 때는 같은 값을 키로 쓰는 곳을 모두 본다. 같은 객체만이 아니라, 그 값을 키로 둔 다른 객체도 찾는다. 한 곳에서 예외로 드러난 결함이 다른 곳에서는 알리지 않고 값을 잃고 있을 수 있다.

## 5. 모달/접근성 보일러플레이트 누락

모달을 만들 때 포커스 트랩을 빠뜨리거나, 드래그할 때 포인터 이벤트 리스너를 엉뚱한 위치에 붙이는 것처럼 "한 번 익히면 반복 적용해야 하는" 보일러플레이트를 빠뜨리는 패턴.

**사례:**
- `9b8a638`: 병합 다이얼로그가 표시되지만 `trapFocus()` 호출이 빠져 있어 키보드 사용자가 모달 밖으로 빠져나갈 수 있었다.
- `5c41797`, `f154a56`: 드래그용 `pointermove`, `pointerup`, `pointercancel`을 행(row) 요소에 붙였더니, 드래그 중 포인터가 행 밖으로 벗어나면 이벤트를 놓쳐 ghost가 남았다. 이벤트를 `document`에 붙이고 `pointerId`로 거르게 했다.
- #348 리뷰(2026-10-15): 캘린더 칸의 링크 이름(`aria-label`)을 보이는 이름과 다른 값(그날의 대표)으로 만들었다. 그래서 사계재나 기념일을 보이는 격자의 평일 칸 54곳과 「연중24주」를 보이는 주일 칸 128곳(2025-2027)에서, 보이는 글자가 접근 가능한 이름에 들어 있지 않았다. WCAG 2.5.3(Label in Name) 위반이며, 음성 제어로 「추계재 누르기」가 되지 않는다. 링크 이름을 보이는 글자에서 만들도록 고쳤다.
- #348 리뷰(같은 날): 달 이동 링크가 `#app`을 통째로 다시 그려서 누른 링크가 사라지자 포커스가 `body`로 빠졌다(WCAG 2.4.3). 달을 넘길 때마다 건너뛰기 링크, 헤더, 탭부터 다시 지나와야 했다. 다시 그리기 전에 누른 컨트롤의 자리(`data-focus-key`)를 남기고, 새 화면의 같은 자리로 포커스를 돌려준다(`views.js focusPendingBook`과 같은 방식). 전례독서 화면(#346)도 같은 결함이 있었다. 2026-10-17에 그 도우미를 `helpers.js createFocusMemory`로 옮겨 두 화면이 함께 쓴다.
- 2026-10-17(전례독서 화면에 옮기며 찾은 것): 포커스만 돌려주어서는 모자랐다.
  - **스크롤 위치가 맨 위로 바뀐다**: 새 장을 받아야 하는 다시 그리기(세트, 트랙, 칩, 카드, 날짜)는 `route()`의 스켈레톤이 한 프레임 그려지며 문서가 짧아져 스크롤 위치가 맨 위(0)로 바뀐다. 누른 컨트롤이 아래로 밀리고(모바일 최대 약 250px), 화면 아래쪽 컨트롤이면 화면 밖에 포커스가 남는다(2.4.7). 받을 것이 없는 다시 그리기(같은 장의 본기도 대체안)는 스크롤이 그대로라서, 같은 화면 안에서도 누르는 컨트롤마다 결과가 달랐다.
  - **해결**: 누른 때의 화면 위치로 돌려준다. 그사이 데스크톱 머리의 검색 줄(최대 4rem)이 펼쳐졌다가, 돌아온 뒤 다시 접힌다(스크롤이 0으로 바뀌어서). 스크롤 고정(scroll anchoring)이 있는 브라우저는 그 접힘 동안 내용을 고정하므로 **지금 레이아웃에서의 화면 위치(viewport top)**로 두고, 없는 브라우저(Safari 26까지)는 접힘이 내용을 옮기므로 **화면 루트 안 위치**로 둔다.
  - **처음 구현의 결함**: 루트 안 위치만 쓰던 첫 구현은 장 받기가 0.1초를 넘으면 컨트롤이 그 줄 높이(약 46px)만큼 아래로 내려갔다. 로컬 서버는 너무 빨라 보이지 않았고, 위치 e2e는 그 줄이 없는 모바일뿐이었다(PR #350 리뷰).
- PR #350 리뷰(2026-10-17): 복원이 포커스를 무조건 옮겨서, 새 장을 받는 사이 독자가 머리의 검색 칸으로 옮겨 입력하던 글자와 Enter 입력이 누른 세그먼트로 가 버렸다(팝오버를 열었으면 그 밖으로 끌어냈다). 누른 링크와 함께 포커스가 `body`로 떨어졌을 때만 돌려준다.
- 2026-10-17(known-issues §10): 화면마다 `createFocusMemory`를 연결하던 방식은 뷰 루트 밖 컨트롤(성서 목록의 구분 탭. `route()`가 슬롯을 비운다)과 `await` 뒤에 그려지는 목록을 다루지 못했다. 그래서 구분 탭과 검색의 「← 이전 · 다음 →」는 Enter를 누르면 포커스가 `body`로 빠졌다(이전부터 있던 문제다). 라우터로 옮겼다(ADR-031 §5). 전역 `<a>` 인터셉터가 누른 자리를 재고, `route()`가 시작에서 꺼내 `finally`에서 돌려준다.
  - **함께 본 것**: 검색 결과 화면은 다 그린 뒤 `window.scrollTo(0, 0)`(루트의 smooth)을 호출했다. 위치 복원이 「이미 제자리」로 보고 지나가면 그 애니메이션이 이어져 누른 링크를 밀 수 있는 순서라서 즉시 스크롤로 바꿨다(기본 창 크기에서는 결과가 한 화면이라 드러나지 않았다).
  - **함께 본 것**: 「본문 바로가기」(`#app`)도 같은 인터셉터가 가로채 화면 이동으로 처리해서 포커스가 본문으로 가지 않았다(이전부터 있던 문제다). 페이지 안 링크는 따로 가려내 대상으로 포커스만 옮긴다.
- PR #354 Copilot 1회차(2026-10-17): 동기화 스낵바(`drive-sync.js`의 `_showSyncSnackbar`)는 라이브 영역도 `role`도 없는 평범한 `div`라서, 동기화 오류, 재연결, 「파일도 삭제」 실패 같은 안내 아홉 곳이 스크린 리더에는 들리지 않았다(WCAG 4.1.3 상태 메시지). 같은 함수를 쓰는 곳 가운데 절 복사(`bookmark-verse-select.js`)만 `announce()`를 따로 호출했다. 해결: 스낵바 함수가 같은 글을 라이브 영역(`#a11y-announce`)에도 넣고, 따로 호출하던 `announce()`는 지웠다(두 번 읽지 않게).

**모달 생성 4단계 체크리스트:**

```
□ 표시 전 hidden=true (또는 .hidden 클래스 부여)
□ 표시 직후 trapFocus(modal) 호출, 반환값을 cleanup용으로 보관
□ requestAnimationFrame 안에서 첫 액션 버튼에 .focus()
□ 닫을 때: 트랩 해제 + 임시 이벤트 리스너 제거 + 상태 초기화
```

**드래그 핸들러 규칙:** 포인터 추적은 항상 `document`에서 한다. 멀티터치를 구분해야 하면 `pointerId`로 거른다.

**상태 메시지 규칙:** 눈에만 보이는 알림(스낵바, 토스트)은 같은 글을 라이브 영역에도 넣는다. 알림을 띄우는 함수 한 곳에서 넣는다. 호출하는 쪽마다 `announce()`를 덧붙이면 빠뜨리는 곳이 생기고, 한 곳에서 넣은 뒤에 따로 호출하면 두 번 읽힌다. 저절로 사라지는 알림(3.5초)이 **유일한** 신호여서는 안 되는 안내가 있다. 되돌릴 수 없는 작업이 끝나지 않았다는 것처럼, 놓치면 사용자가 잘못 믿게 되는 안내다. 그런 안내는 다시 찾아갈 화면(설정)에도 남긴다(WCAG 2.2.1, PR #354 사용자 `/code-review` 12번. 「파일도 삭제」 실패는 Drive 줄 아래 `.settings-drive-note`에 다시 연결할 때까지 남는다).

**접근 가능한 이름 규칙:** `aria-label`로 이름을 덮어쓸 때는 보이는 글자를 그대로 넣는다(줄여 보이면 이름도 줄인 대로 넣는다. 「연중24주」가 그렇다). 보이는 이름과 링크 이름을 서로 다른 함수나 필드로 만들지 않는다. 한쪽만 바뀌면 어긋난다. 실데이터가 있으면 「보이는 이름 ⊂ 링크 이름」을 전수로 검사한다(`calendar.data.test.js`).

**다시 그리는 화면의 포커스 규칙:** 링크나 단추가 자기 화면을 다시 그리면(같은 뷰 안의 이동, 필터, 세그먼트) 새 화면의 같은 컨트롤로 포커스를 돌려주고, 컨트롤은 누른 때의 화면 위치에 놓는다. 링크에는 `data-focus-key`(새 화면에 같은 컨트롤이 없을 수 있으면 넘겨받을 컨트롤의 `data-focus-fallback`)만 단다. 위치를 재고 돌려주는 것은 라우터다(ADR-031 §5. 인터셉터가 이동 직전에 `focusSpotOf`로 재고, `route()`가 시작에서 꺼내 `finally`에서 `restoreFocusSpot`을 호출한다. 자리는 그 누름의 `route()`에만 쓰인다). 커밋 뒤에 스크롤을 움직이는 뷰는 즉시(`behavior: "instant"`) 움직인다. 부드러운 스크롤이 이어지면 복원한 위치를 밀기 때문이다. 키는 선택자 문자열이 아니라 `dataset` 값으로 찾는다. 키가 데이터(전례일 id)라서 값 비교는 이스케이프가 필요 없다(따옴표 선택자는 키의 `"`와 `\`에서 깨진다. 콜론과 한글은 따옴표 안에서 문제없다). 그 컨트롤이 사라졌으면 가장 가까운 대체(`data-focus-fallback`. 「오늘」이나 다른 쪽 링크)로 돌려준다. 페이지를 넘기는 컨트롤도 같다. 검색 결과의 「다음 →」, 「← 이전」은 새 페이지에서도 **누른 컨트롤 그대로** 포커스를 둔다(사용자 결정 2026-10-17. 결과 목록 맨 위로 보내는 안 대신 이 규칙으로 정했다. 전례독서의 「다음날」과 같은 규칙이고 Enter를 거듭 눌러 넘길 수 있다). 마지막 페이지라 「다음 →」이 없으면 「← 이전」에 둔다. **포커스가 `body`일 때만 돌려준다.** 다시 그리는 사이 독자가 다른 데로 옮겼으면 그대로 둔다. 마우스나 탭으로 누른 복원은 `focus({ focusVisible: false })`로 한다. iOS(WebKit)는 탭으로 링크에 포커스를 주지 않아서, 뒤의 스크립트 포커스에 링을 그리기 때문이다(책 카드 `43db624`와 같은 일).

## 9. 글로벌 이벤트 핸들러 협력 부족

전역 인터셉터(예: `document.addEventListener("click", ...)`)가 하위 요소의 자체 핸들러가 이미 처리한 이벤트를 **다시 처리**해 의도치 않은 동작이 발생하는 패턴.

**사례:**
- `d25b8da`: 전역 클릭 인터셉터가 SPA 라우팅을 위해 `<a href>` 클릭을 가로챘는데, `buildSheetPagination`의 `href="#"` 링크는 자체 핸들러에서 `e.preventDefault()`를 이미 호출했다. 인터셉터가 `e.defaultPrevented`를 확인하지 않아 `route()`를 또 호출했다.
- #348 리뷰(2026-10-15): 반대 방향의 같은 결함이다. 탭 바의 탭 처리기(홈, 캘린더, 북마크, 설정)가 전역 인터셉터의 **수정 키 조건**(⌘, Ctrl, Shift, Alt, 가운데 단추는 브라우저에 맡긴다)을 따르지 않았다. ⌘나 Ctrl을 누르고 클릭하면 두 문제가 있었다.
  - 홈과 캘린더 탭은 `preventDefault` 뒤 같은 탭에서 이동해 새 탭 열기를 무시했다.
  - 캘린더, 북마크, 설정 탭은 인터셉터가 빠져 브라우저가 새 탭을 여는데도 스크롤 복원 요청을 먼저 등록해 두었다. 그 요청이 남아 다음 링크 이동이 옛 스크롤 위치로 옮겨 갔다(e2e 재현. 장 최상단 대신 600px).
  - 탭 히스토리 도입(`687a071`, ADR-031, #194)부터 있던 결함을 캘린더 탭이 그대로 물려받았다.

**규칙:**
- 글로벌 이벤트 핸들러는 가장 먼저 `if (e.defaultPrevented) return;`으로 협력 게이트를 둔다.
- 자체 처리하는 하위 핸들러는 **반드시** `e.preventDefault()`(필요하면 `stopPropagation()`)를 호출해 처리했음을 알린다.
- 가능하면 글로벌 인터셉터가 다루는 범위를 좁힌다(예: `closest("a[href]:not([data-internal])")`처럼 분명한 표지를 쓴다).
- 링크에 다는 처리기는 전역 인터셉터와 **같은 조건으로 먼저 처리를 그만둔다**. 새 탭이나 새 창을 여는 클릭은 `window.appHelpers.isModifiedClick(e)`로 거른다(인터셉터도 이 함수를 쓰므로 조건이 한 곳에 있다). 복원 요청이나 포커스 기억 같은 부수 효과는 이 화면에서 이동이 일어날 때만 남긴다.

## 10. 플랫폼별 quirk 무시

웹 표준대로 작성했지만 iOS Safari, Android, 사용자 환경 설정(예: `prefers-reduced-motion`) 때문에 회귀하는 패턴.

**사례:**
- `f043f78`: 모달을 열 때 `body { overflow: hidden }`만으로는 iOS Safari의 배경 스크롤이 막히지 않았다. `position: fixed`로 고정하고, 현재 스크롤 위치를 보존했다가 닫을 때 복원하는 방식이 필요했다.
- `da21f11`: 드로어 슬라이드 애니메이션이 `prefers-reduced-motion: reduce` 환경에서도 그대로 재생되었다. 미디어 쿼리로 끄도록 고쳤다.

**규칙:**
- iOS Safari와 Android Chrome 둘 다에서 직접 검증한다(특히 모달, 바텀시트, 키보드가 나타나는 동작).
- 모션을 사용할 때는 항상 `@media (prefers-reduced-motion: reduce)` 분기를 함께 작성한다.
- 스크롤 락처럼 정해진 패턴은 **검증된 헬퍼 함수**로 따로 빼 매번 같은 구현을 쓰게 한다(구현 요령이 사라지지 않게).

## 11. 비동기 경쟁 상태 검사 — 단일 체크포인트의 함정

`async` 함수가 여러 `await` 지점을 거치면, `await` 사이마다 외부 상태(사용자 의도, 다른 흐름의 결과 등)가 바뀔 수 있다. 경쟁 상태 검사를 함수 진입 시점이나 첫 번째 `await` 직후에만 두면, 그다음 `await`가 끝난 시점에 이미 낡은 결정에 따라 상태를 덮어쓰는 패턴이다.

**사례(Phase 2h PKCE 마이그레이션, Bugbot PR #54와 #57):**

- `c4d0c72`: `_attemptSilentRefresh`가 `_state` 기반 경쟁 상태 검사만 갖고 있었다. 사용자가 조용한 갱신(silent refresh) 진행 중에 `signOut()`이나 `disable()`을 호출하면 `_state`는 그대로(혹은 정상 진행 중인 값)이지만 `localStorage["bible-drive-sync"]`는 `"0"`으로 바뀐다. 그런데 상태 검사만 통과시켜 IDLE이나 NEEDS_CONSENT로 전이하면 사용자가 끊은 동기화를 다시 살린다. 해결: `localStorage.getItem(SYNC_ENABLED_KEY) === "0"` 검사를 추가했다.
- `f090c83`: 같은 함수가 경쟁 상태 검사를 진입 시점에만 두었다. `await refreshAccessToken(...)` 직후의 경쟁 상태 검사를 통과한 뒤에도 `await refreshStore.saveRefreshToken(...)`(토큰 교체) 또는 `await refreshStore.clearRefreshToken()`(`invalid_grant`) 같은 IDB `await`가 남아 있었다. 그 `await` 동안 사용자가 `disable()`을 호출하면 뒤이은 `_transition(IDLE/NEEDS_CONSENT)`이 다시 `SYNC_ENABLED_KEY = "1"`로 덮어썼다. 해결: 매 `await` 직후마다 경쟁 상태 검사를 다시 했다. 단계 4 뒤에는 `enable()`이 DISABLED를 동기적으로 빠져나가지 않으므로, 상태 기반 검사만으로는 cold-start 경로를 보호할 수 없다. 플래그 기반 검사가 필수다.
- 2026-10-17(PR #353 리뷰, `docs/changes/2026-10-17-typecheck-batch-1.md`): 업데이트 토스트 `showUpdateToast`의 「이미 떴나」 검사가 대기 중인 서비스 워커에 버전을 묻는 `await`(최대 1.5초) 앞에만 있었다. 그 사이 설정의 「업데이트 지금 확인」이 또 호출하면 둘 다 검사를 지나, 같은 id의 토스트가 둘 붙었다. 해결: `await` 뒤에 한 번 더 확인한다. 동기화 레이어 밖에서도 같은 경우가 나온다.
- 2026-10-17(`docs/changes/2026-10-17-sync-signout-inflight.md`): 동기화 사이클 `_syncCycle()`에는 같은 규칙이 빠져 있었다. 파일 찾기, 내려받기, 올리기를 기다리는 중에 `signOut()`이 오면, 기다린 뒤에 만든 업로드가 로그아웃 뒤에 더한 북마크까지 담아 `Bearer null`로 나갔다. 실제 Drive는 401로 거절한다. 내려받기를 기다리던 중이었다면 원격 자료를 로컬에 쓰고, 올리기를 기다리던 중이었다면 비운 캐시를 다시 채웠다. e2e는 가짜 Drive가 토큰 없는 요청을 받아 주어서 가끔 실패하는 테스트로만 보였다. 해결: 기다릴 때마다 `_leftSyncing(at)`을 호출해 상태가 SYNCING이 아니면 멈춘다. 여기서는 상태 기반 검사가 맞다(DISABLE은 SYNCING에서 동기적으로 DISABLED로 전이한다).
- 2026-10-17(같은 원장, 머지 전 검토 4번): 연결 해제의 「파일도 삭제」는 `deleteRemoteFile()`을 기다린 뒤 `signOut()`을 호출해서, 지우는 동안 동기화가 그대로 돌았다. 진행 중 사이클의 새 파일 올리기가 지우기 뒤에 도착하면 방금 지운 파일이 되살아났다. 해결: 지우기 전에 사이클을 멈추고, 진행 중 사이클이 이미 보낸 요청이 끝나기를 기다린 뒤(`_cycleDone`) 파일을 찾아 지운다.
- 2026-10-17(같은 원장, 사용자 `/code-review` 2, 9, 10번): 그 기다림에 상한이 없었고, 토큰은 상태 기계에 둔 채였다. 세 가지 문제가 있었다.
  - 기다리는 동안 앱을 닫으면 켬 표지는 "0"이라 「연결 해제됨」으로 보이지만, 폐기하지 않은 갱신 토큰(refresh token)이 IDB에 남았다(다시 「연결」을 누른 뒤 동의를 취소하면 옛 계정이 조용히 다시 연결됐다).
  - 그사이 다시 연 설정은 「해제」를 그려, 「파일 유지」로 한 번 더 로그아웃할 수 있었다. 그 뒤에도 미리 받아 둔 토큰으로 찾기와 지우기가 나갔다.
  - 멈춤은 누른 탭의 상태뿐이라, 연결된 다른 탭은 비워진 공유 캐시를 보고 파일을 다시 만들 수 있었다.
  - **해결**: 페이지가 닫혀도 남으면 안 되는 것(IDB의 갱신 토큰, 켬 표지, 계정 키)을 네트워크 작업보다 먼저 지운다. 토큰은 상태 기계에서 곧바로 빼서 그 함수 안에만 둔다(설정은 곧바로 「연결」이 된다). 기다림은 10초까지이고, 끝나지 않았으면 지운 뒤 한 번 더 기다렸다가 다시 지운다. 다른 탭은 켬 표지의 `storage` 이벤트로 멈춘다. 토큰은 지운 뒤 그 함수가 폐기한다.
- 2026-10-17(같은 원장, 사용자 `/code-review` 1, 7번, 이전부터 있던 문제): 사이클은 기다릴 때마다 **상태**는 다시 봤지만 **자료**는 다시 읽지 않았다. 시작할 때 읽은 로컬 사본으로 병합한 뒤 `_applyMergedDoc`이 로컬 문서 전체를 덮어써서, 찾기나 내려받기를 기다리는 동안 저장한 북마크, 설정, 읽던 위치가 사라졌다. 그사이 들어온 동기화 요청은 SYNCING이라 버려졌다. 304 갈래는 기다리기 전의 값으로 「변경 없음」을 판정해 그 편집을 올리지 않았다. 해결: 내려받기를 기다린 뒤에 로컬을 읽는다(그 읽기와 덮어쓰기 사이에 기다림이 없다). 「동기화됨」은 실제로 올린 본문의 값으로 적고, 도는 동안 들어온 사용자 요청은 끝난 뒤 한 번 더 돈다.

**규칙:**

- 비동기 함수의 경쟁 상태 검사는 **모든 `await` 직후에 다시 한다**. 진입 시점 한 번으로 충분하다고 가정하지 않는다.
- 사용자 의도를 믿을 수 있게 알려 주는 단일 출처(여기서는 `localStorage["bible-drive-sync"]`)를 정해, 모든 경쟁 상태 검사가 같은 출처를 읽게 한다.
- 상태 기계를 단순화하면서 동기 dispatch가 사라졌다면, 기존 상태 기반의 경쟁 상태 검사가 더 이상 작동하지 않는지 의심한다. 플래그 기반 검사로 대체하거나 보강해야 할 수 있다.
- 회귀 방어 테스트: 밖에서 제어할 수 있는 `Promise`로 `await`를 붙들어 둔 채 `disable()`을 끼워 넣어, 각 `await` 시점의 경쟁 구간(race window)을 직접 흉내 낸다(`tests/unit/state-machine.test.js` 26a, 26b, 26c, 44-46 참고). e2e에서는 가짜 서버의 응답을 보류했다가 보낸다(`test_drive_sync.py`의 `FakeDrive.hold_list`).
- e2e의 가짜 서버는 토큰과 권한 검사도 실제처럼 한다. 다 받아 주는 가짜 서버는 클라이언트의 결함을 가리거나, 가끔 실패하는 테스트로 보이게 한다.
- 기다린 뒤에 낡는 것은 상태만이 아니다. 기다리기 전에 읽은 **자료**(로컬 사본, 토큰, 캐시 값)도 낡는다. 덮어쓰는 쓰기는 기다림 없이 바로 앞에서 읽은 값으로 한다. 도중에 들어온 요청은 버리지 말고 한 번으로 모아 끝난 뒤 다시 돈다. 다시 시작은 다음 마이크로태스크에서 한다(끝나는 사이클의 `finally` 앞에서 시작하면 새 사이클이 「아직 도는 중」을 보고 시작되지 못한다).
- 되돌릴 수 없는 작업(원격 삭제) 앞에서는 그것을 되돌릴 수 있는 흐름(진행 중 사이클, 예약된 올리기)을 먼저 멈추고, **이미 보낸 요청이 끝나기를 기다린다**. 멈추기만 해서는 이미 나간 요청이 뒤늦게 도착하는 것을 막지 못한다. 그 기다림에는 상한을 둔다(멈춘 요청 하나가 로그아웃 전체를 막지 않게). 페이지가 닫혀도 남으면 안 되는 것(자격 증명)은 기다림과 네트워크 작업보다 먼저 지운다. 멈춤은 탭마다 따로다. 다른 탭이 공유 표지의 변경을 감지하게 한다(`storage` 이벤트).
- **동기화 사이클의 확인은 대기마다 한 줄씩 둔다. 진행 중인 요청을 취소하는 구조(사이클마다 `AbortController`)나 공통 대기 래퍼로 바꾸지 않는다**(사용자 결정 2026-10-17. 로그아웃 수정의 머지 전 `/code-review`가 「손으로 넣은 확인은 빠뜨리기 쉽다」며 제안했다. 원장 `docs/changes/2026-10-17-sync-signout-inflight.md`). 이유는 다음과 같다. 같은 파일의 `_attemptSilentRefresh`도 대기마다 다시 본다(위 규칙). 취소를 넣으려면 OAuth와 Drive 전송 함수(`transport.js`)마다 신호를 넘겨야 한다. 로그아웃 전에 이미 나간 업로드는 로그아웃 전의 편집이라 끝나게 둔다. 빠뜨림은 테스트가 막는다. 멈추는 자리마다 유닛 테스트가 하나씩 있고(`state-machine.test.js` 44-50), 확인 한 줄을 빼면 그 자리의 테스트가 실패하는 것을 변이 검사로 확인했다. **재검토 조건**: 전송 계층을 다른 이유로 고쳐 요청마다 신호를 받게 될 때, 또는 사이클의 대기가 지금(여섯)보다 크게 늘 때. 리뷰가 같은 제안을 다시 내면 이 줄을 근거로 넘긴다.

## 35. 외부 입력은 타입만 보지 말고, 그 값을 받는 코드가 다룰 수 있는 형식인지 검사한다 — 가져오기 검사가 리뷰마다 샜다 (리뷰, 2026-10-19)

밖에서 들어오는 값(가져오기 파일, 공유 링크, 동기화 문서)을 「문자열이다 · 수다 · 배열이다」로만 거르면, 통과한 값이 그 값을 쓰는 코드에서 깨진다. 기준은 타입 선언이 아니라 그 값이 흘러가는 모든 곳이다. 객체의 키, 주소, 재귀, 배열로 펼치기, 저장 한도가 그렇다.

**사례:**
- PR #359(북마크 가져오기, ADR-040): 처음 검사는 타입과 「절 범위의 구간이 모두 읽히는가」를 봤다.
  - Copilot 1회차가 두 가지를 찾았다. 하나는 객체 기본 속성 이름인 id다(`toString`. 동기화 저장소가 id를 일반 객체의 키로 써서 목록 읽기가 깨진다). 다른 하나는 북마크에 붙은 `children`이다(저장소가 어떤 항목의 자식이든 훑는다).
  - 2회차(Copilot과 자체 리뷰어 셋)가 다시 여섯 가지를 찾았다. 큰 수, 큰 범위, 공백, 거꾸로 된 범위가 든 절 범위(합치기, 주소 해석, 강조에서 문제가 됐다). `?`, `#`, `..`가 든 폴더 id(모아 읽기 주소). 수천 단 폴더(재귀). `1e400` 날짜(저장하면 `null`이 된다). 지금 목록과 종류가 다른 같은 id(동기화가 옛 종류로 되돌린다). 저장 한도를 넘는 목록(조용히 실패한다). 모두 타입은 맞았다.
  - 2회차 뒤 자체 리뷰가 그 크기 검사를 다시 깼다. 목록 JSON에 둔 고정 예산(600,000자)은 부모 id를 자식마다 되풀이하는 저장 구조(1,000자 id면 21배)를 놓쳐서 저장 실패를 막지 못했고, 메모가 긴 자기 백업(2배)은 막았다. 저장할 문서를 쓰지 않고 만들어서 재는 방식으로 바꿨다.
- 주소의 절 범위(2026-10-21, known-issues §15): 가져오기 검사가 막은 큰 범위와 되풀이한 구간이 공유 링크로는 그대로 들어왔다. 라우터가 여러 구간을 절 하나하나로 펼쳐, 처음 여는 링크가 시작 화면에서 멈췄다. 같은 절 범위가 파일, 주소, 동기화 세 입구로 들어오는데, 검사는 파일 입구에만 있었다. 검사를 `verse-spec.js isWellFormedSpec`으로 옮겨 주소 해석도 같이 쓰게 했다. 검사 없이 이미 저장된 북마크(1.6.4 이하에서 들인 것. 그 기기에 남은 것과 동기화로 간 것이 있다)는 아직 다시 검사하지 않는다(known-issues §15).
  - 그 PR의 리뷰에서 주소의 앞뒤 쉼표를 떼어 내기로 했다(사용자 결정 2026-10-21). 처음 떠올린 `/^,+|,+$/g`는 쉼표가 길게 이어진 뒤 다른 글자가 오면 제곱 시간이 걸렸다(쉼표 4만 개에 약 1초, 두 배면 네 배). 이 함수는 스크롤 프레임마다 돌아, 그대로 썼다면 막으려던 멈춤을 다른 경로로 다시 만들었을 것이다. 반복문으로 떼어 냈다.

**규칙:**
- 검사를 쓰기 전에 그 값이 가는 곳을 끝까지 따라가 목록을 만든다. 객체의 키, 주소, 재귀 깊이, 펼치기, `JSON.stringify`, 저장 한도가 그 예다. 그리고 그 값을 받는 곳마다 받는 형식을 기준에 넣는다.
- 같은 값이 여러 입구로 들어오면(가져오기 파일, 주소, 동기화 문서) 검사를 입구마다 따로 쓰지 말고, 하나를 두고 모두 함께 쓴다. 검사는 그 값을 다루는 모듈에 둔다(절 범위면 `verse-spec.js`). 한 입구를 고칠 때는 다른 입구도 같은 값을 받는지 찾는다.
- 바깥 입력에 쓰는 정규식은 되돌아가기가 제곱이 되지 않는지 본다. 앞이 고정되지 않은 반복(`,+$`, `\s+$`)은 같은 글자가 길게 이어진 뒤 다른 글자가 오면 시작점마다 끝까지 다시 훑는다. 스크롤이나 입력마다 도는 코드에서는 반복문으로 다듬고, 긴 입력의 시간을 테스트로 확인한다(`tests/unit/routing.test.js`의 「긴 쉼표 줄」).
- 받을 형식은 「앱이 쓰는 형식」으로 정한다(허용 목록). 깨지는 경우를 하나씩 막는 검사(거부 목록)는 다음 리뷰에서 빠뜨린 경우가 또 나온다. 앱의 직렬화 함수가 만드는 값이 모두 통과하는지는 테스트로 확인한다. 직렬화가 바뀌면 검사도 바뀌어야 한다(`tests/unit/bookmark.test.js`의 합성 장 테스트).
- 저장 한도 같은 플랫폼 제약은 가장 빠듯한 엔진으로 정한다. Chromium은 localStorage를 문자 수로 세지만, Safari는 바이트로 세고 한글은 한 글자에 2바이트다(ADR-040 「검증」).
- 크기처럼 다른 코드가 만들어 내는 양은 배율로 어림하지 말고, 그 코드로 실제 결과를 만들어 잰다(저장하지는 않고). 어림한 배율은 그 코드가 바뀌거나 입력의 모양이 달라지면 어느 쪽으로든 어긋난다.

## 부록 A: 변수명 섀도잉

DOM 쿼리 결과에 `el`, `node` 같은 짧은 이름을 쓰면 외부 스코프나 인접 코드의 동명 변수와 컨텍스트가 섞인다.

**사례:**
- `4526614`(`_updateDragIndicators`): `elementFromPoint` 결과를 `el`로 받았는데, 근처 코드의 다른 `el`과 섞여 엉뚱한 요소를 조회했다. 이름을 `hitEl`로 바꿨다.

**규칙:** DOM 쿼리 결과는 컨텍스트가 드러나는 이름을 쓴다. 예: `hitEl`, `targetRow`, `draggedItem`, `dropZone`.

## 부록 B: 같은 시각 효과를 여러 곳에 적용할 때

CSS의 시각 효과(모서리 라운드 평탄화, 강조 색 등)를 인접 요소 사이에 적용할 때, 적용 대상의 **레이아웃 모드**를 가정한 채 작성하면 다른 모드에서 깨진다.

**사례:**
- `b030aa6`: 검색과 딥링크 강조에서 연속 절의 모서리를 평탄화하는 규칙이 인라인 본문에서는 잘 동작했으나, 시 구절(block) 레이아웃에서는 잘못 평탄화되어 모서리가 부자연스럽게 잘렸다.

**규칙:** 인라인, 블록, `flex`, `grid` 등 레이아웃 모드마다 시각 효과를 한 번씩 눈으로 확인한다. 가능하면 선택자에 레이아웃 맥락(`.poetry-block` 등)을 적는다.
