# State-based sync with a stored base copy (three-way merge) and local change detection

Labels used on every finding: **[P]** confirmed from a primary source read in this session (source code, official manual, RFC, vendor engineering blog); **[S]** secondary source (abstract, catalog record, essay describing someone else's product); **[U]** unverified in this session (prior knowledge, not re-read). Inferences are my own reasoning from the cited findings and are listed separately. Research date: 2026-10-30.

Assumed app context (given, not researched): one JSON file in Google Drive appDataFolder holding bookmarks (flat map id -> {parentId, order, ...}), settings, and last reading position; per-record `_u` = editing device's Date.now(); merge keeps max `_u` (ties by device id); tombstones id -> time; uploads with ETag If-Match; on a 304 download the app uploads only if local max `_u` differs from the max cached at last sync; localStorage (Safari about 5 MiB, UTF-16); bookmarks already stored twice; older clients without a base remain in use; 1-4 devices.

## Q1. How do Unison, git, Dropbox, Firefox Sync (dogear), Joplin store and use the base, and what do they do when both sides changed?

### Takeaway
Every mature state-based synchronizer keeps (or derives) a "last agreed state" and classifies changes by comparing each side with it, never by comparing two devices' clocks; Unison even states it only compares timestamps taken on the same host. They differ in what the base holds (full archive with fingerprints, full mirror tree, per-item flags plus a server-assigned timestamp, per-item sync time plus a stored note body) and in the both-changed policy: Unison asks the user, Dropbox and Joplin keep both copies, Firefox picks the side with the more recent edit using ages measured on separate clocks.

### Cited Findings

**Unison (archive)**
- [P] Unison keeps an archive file on each host that "records the state of each path in the replica when it was last synchronized" and compares it with the current replica "to determine which paths have been updated". Its stages are: detect updates against the archive, check false conflicts, show updates, perform actions, then "update its archive files to reflect the new state of the replicas" (last step). — [Unison manual text, src/strings.ml](https://github.com/bcpierce00/unison/blob/master/src/strings.ml)
- [P] Conflict definition: a path conflicts if "(1) it has been updated in one replica, (2) it or any of its descendants has been updated in the other replica, and (3) its contents in the two replicas are not identical." — [Unison manual, strings.ml](https://github.com/bcpierce00/unison/blob/master/src/strings.ml)
- [P] False conflicts: "paths that have been updated on both replicas, but whose current values are identical ... are silently marked as synchronized in the archive files in both replicas." — [Unison manual](https://github.com/bcpierce00/unison/blob/master/src/strings.ml)
- [P] Conflict policy: "Conflicting updates are just displayed"; the user chooses. Options exist to automate: `-prefer xxx` ("choose this replica's version for conflicting changes") and `-copyonconflict` ("keep copies of conflicting files"). — [Unison manual](https://github.com/bcpierce00/unison/blob/master/src/strings.ml)
- [P] Change detection cost: with `fastcheck` "Unison uses file modtimes for a quick first pass to tell which files have definitely not changed; then, for each file that might have changed, it computes a fingerprint of the file's contents and compares it against the last-synchronized contents." Touching a file without changing content "should never affect whether or not Unison does an update." — [Unison manual](https://github.com/bcpierce00/unison/blob/master/src/strings.ml)
- [P] Clocks: "Unison is not bothered by clock skew between the different hosts on which it is running. It only performs comparisons between timestamps obtained from the same host, and the only assumption it makes about them is that the clock on each system always runs forward." — [Unison manual](https://github.com/bcpierce00/unison/blob/master/src/strings.ml)
- [P] "The archive file for each replica is found in the .unison directory on that replica's host", and "Unison maintains a completely different set of archive files for each pair of roots" (so the base is per replica pair, stored on both sides). — [Unison manual](https://github.com/bcpierce00/unison/blob/master/src/strings.ml)

**git**
- [U] git does not store a separate base copy; it computes the common ancestor ("merge base") from the commit graph (`git merge-base`) and runs a three-way merge against it. The base therefore costs nothing extra beyond history that is kept anyway. — [git-merge-base docs](https://git-scm.com/docs/git-merge-base) (not re-read this session)

**Dropbox (Nucleus)**
- [P] Nucleus keeps three trees: "The Remote Tree is the latest state of the user's Dropbox in the cloud", "The Local Tree is the last observed state of the user's Dropbox on disk", "The Synced Tree expresses the last known 'fully synced' state between the Remote Tree and Local Tree." — [Dropbox, Testing sync at Dropbox](https://dropbox.tech/infrastructure/-testing-our-new-sync-engine)
- [P] "you can think of each node in the Synced Tree as a merge base"; "A merge base allows us to derive the direction of a change." Without the Synced Tree a remotely added file could not be distinguished from a file the user deleted locally. Goal: "converge all three trees to the same state." — [Dropbox, Testing sync at Dropbox](https://dropbox.tech/infrastructure/-testing-our-new-sync-engine)
- [P] Nucleus gives files and folders "globally unique identifiers"; the old engine represented moves as delete + add, so "a delete goes through but its corresponding add does not" could lose a moved file. For concurrent offline moves that would create a cycle, Classic duplicated directories, while in Nucleus "the final order depends on which sync engine uploads their move first" (server write order decides). — [Dropbox, Rewriting the heart of our sync engine](https://dropbox.tech/infrastructure/rewriting-the-heart-of-our-sync-engine)
- [S] Dropbox's user-visible conflict policy is a "conflicted copy" that "the user must merge ... manually". — [Kleppmann et al., Local-first software (2019)](https://www.inkandswitch.com/essay/local-first/)

**Firefox Sync bookmarks (SyncedBookmarksMirror + dogear)**
- [P] The mirror "matches the complete tree stored on the Sync server, and stages new bookmarks changed on the server since the last sync. The merger walks the local tree in Places and the mirrored remote tree, produces a new merged tree, then updates the local tree." Merge and application happen "in a single transaction ... A failure at this point aborts the merge and leaves Places unchanged." — [SyncedBookmarksMirror.sys.mjs header](https://github.com/mozilla-firefox/firefox/blob/main/toolkit/components/places/SyncedBookmarksMirror.sys.mjs)
- [P] Dogear is described in its source as "A two-way merger"; it is "ported almost directly from iOS", where a `ThreeWayMerger` "takes a complete 'mirror' tree with the server state after the last sync". "Dogear doesn't store the shared parent for changed items, so we can only do two-way merges." Instead "The `needs_merge` flag notes *that* a bookmark changed, but not *how*. This means we might detect conflicts, and revert changes on one side, for cases that iOS can merge cleanly." The authors call this "a good balance between correctness and complexity" because most users don't "make conflicting changes on multiple devices simultaneously." — [dogear src/merge.rs](https://github.com/mozilla/dogear/blob/master/src/merge.rs)
- [P] How "changed" is computed: local `needs_merge = syncChangeCounter > 0` (a per-row counter in `moz_bookmarks`); remote `needs_merge` = the mirror row's `needsMerge` flag, set when a newly downloaded record is stored and cleared after merge. — [Firefox bookmark_sync/src/store.rs](https://github.com/mozilla-firefox/firefox/blob/main/toolkit/components/places/bookmark_sync/src/store.rs)
- [P] Value conflict policy (`resolve_value_conflict`): changed on both sides -> for valid items "compare timestamps to decide which side is newer" (`local_node.age < remote_node.age` -> local); only local changed -> local; only remote changed -> remote; built-in roots always keep local; if one side is invalid, take the other. For children order on both-changed, "we always use the newer side". — [dogear src/merge.rs](https://github.com/mozilla/dogear/blob/master/src/merge.rs)
- [P] The "age" is a duration measured within one clock domain: local `age = local_time_millis - localModified`; remote `age = remote_time_millis - serverModified` where `serverModified` is the server's record timestamp. — [Firefox store.rs](https://github.com/mozilla-firefox/firefox/blob/main/toolkit/components/places/bookmark_sync/src/store.rs). [U] that `remote_time_millis` is the server's "now" from the response (not confirmed in this session).
- [P] Structure conflict policy (`resolve_structure_conflict`, where to keep a child): if only one side's parent changed, "keep the child in its new parent"; if both parents changed, compare the newer age of child and parent on each side. — [dogear src/merge.rs](https://github.com/mozilla/dogear/blob/master/src/merge.rs)
- [P] Delete vs edit: "If a non-folder child is deleted locally and changed remotely, we ignore the local deletion and take the remote child" (a "revive"); "For folders, we always take the local deletion and relocate remotely changed grandchildren to the merged node." Symmetric rules for remote deletions; deleted and not changed on the other side -> take the deletion. — [dogear src/merge.rs](https://github.com/mozilla/dogear/blob/master/src/merge.rs)

**Joplin**
- [P] Joplin stores per-item, per-sync-target metadata in `sync_items` (`sync_time`, `force_sync`). After an upload it sets `sync_time` to the item's own `updated_time` (`saveSyncTime(syncTargetId, local, local.updated_time, ...)`). For an item that needs sync: no remote and no `sync_time` -> create remote; no remote but `sync_time` set -> conflict ("remote has been deleted, but local has changes"); remote exists and `remoteContent.updated_time > local.sync_time` -> conflict ("both remote and local have changes"), else update remote. — [Joplin Synchronizer.ts](https://github.com/laurent22/joplin/blob/dev/packages/lib/Synchronizer.ts)
- [P] Joplin reads the full remote item to get `updated_time` because file-system timestamps on the target are unreliable ("OneDrive does not appear to have accurate timestamps as lastModifiedDateTime would occasionally be a few seconds ahead"). It throws if a remote item has an `updated_time` more than a day in the future. — [Joplin Synchronizer.ts](https://github.com/laurent22/joplin/blob/dev/packages/lib/Synchronizer.ts)
- [P] Both-changed policy for notes: a conflict note (a copy). Since the conflict auto-merge work (spec committed 2026-10-05), Joplin stores a **base** per sync target in `sync_items.base_body` and `base_title`, "recorded after an upload, after a download, and after a conflict"; the merge is line-based diff3; non-overlapping edits merge, overlapping ones still produce a conflict note. Fallback to a plain conflict note when "there is no recorded base", the item is locked/read-only, decryption fails, or the diff exceeds bounds. — [Joplin conflict_auto_merge.md](https://github.com/laurent22/joplin/blob/dev/readme/dev/spec/conflict_auto_merge.md)
- [P] Joplin's sync-target `info.json` properties carry `updatedTime`, used "to resolve conflicts when two clients perform the same action on the same property". — [Joplin sync spec](https://joplinapp.org/help/dev/spec/sync)

### Inferences
- The common pattern is: classification against a base removes clocks from the three easy cases (only local, only remote, neither). Clocks (or a user prompt, or a deterministic rule) are only consulted in the genuinely concurrent case. Firefox further avoids cross-device clock comparison even there by comparing ages measured on two separate clocks (local clock for local edits, server clock for remote records). For a Google Drive single-file design there is no per-record server timestamp, so that exact trick is not available; only the file-level server `modifiedTime` exists.
- Joplin is a cautionary middle ground: its "remote changed" test is `remote.updated_time > sync_time`, which compares one record's device-stamped time to the last-seen value of the same record. That is effectively a version check, but because it uses `>` on device clocks, an edit from a device whose clock is behind the last-seen stamp would be classified as "unchanged". Equality/inequality against the base (or a hash) does not have this hole.
- Dogear shows the cost of not storing base values: with only "changed" flags, a title edit on one device and a move on another become a record-level conflict and one side is reverted. Storing base field values (as iOS did) allows a field-level merge.

### Gaps
- I did not re-read git documentation or Benjamin Pierce's "What's in Unison?" paper in this session.
- Not verified what `remote_time_millis` is in Firefox (server "now" vs local "now").
- Dropbox Nucleus's per-node conflict policy beyond the cycle example is not described in the two articles read.

## Q2. Minimal metadata for a per-record three-way decision, and storage cost

### Takeaway
A map id -> hash(canonical record) of the last synced document is the smallest base that answers both "did local change?" and "did remote change?" per record, and also encodes "existed at last sync" (key present) for deletion disambiguation. A per-record dirty flag answers only the local half. A full base copy is needed only if you want field-level merges of a record changed on both sides (for example, title edited on one device, moved on another).

### Cited Findings
- [P] Unison compares a content fingerprint against "the last-synchronized contents", using modtimes only as a same-host shortcut; the archive therefore needs fingerprints, not full contents. — [Unison manual](https://github.com/bcpierce00/unison/blob/master/src/strings.ml)
- [P] Dogear's flag-only approach ("notes *that* a bookmark changed, but not *how*") causes conflicts and reverts on one side "for cases that iOS can merge cleanly"; iOS kept a full mirror of the server state. — [dogear src/merge.rs](https://github.com/mozilla/dogear/blob/master/src/merge.rs)
- [P] Joplin stores a full base only for note title and body (the fields it merges); other item types keep only `sync_time`. — [Joplin conflict_auto_merge.md](https://github.com/laurent22/joplin/blob/dev/readme/dev/spec/conflict_auto_merge.md)
- [P] Dropbox's merge base is the per-node Synced Tree, which is what tells "added remotely" apart from "deleted locally". — [Dropbox, Testing sync](https://dropbox.tech/infrastructure/-testing-our-new-sync-engine)

### Inferences
- **Decision table with a hash base** (B = base hash for id or absent, L = hash of local record or absent, R = hash of remote record or absent):
  - L = B and R = B: neither changed.
  - L != B, R = B: only local changed -> keep local, upload.
  - L = B, R != B: only remote changed -> take remote (including a remote deletion when R is absent and B present).
  - L != B, R != B, L = R: both changed identically (Unison's "false conflict") -> no conflict; record as synced.
  - L != B, R != B, L != R: true conflict -> policy (Q5).
  - B absent, L present, R absent: created locally -> upload. B absent, R present, L absent: created remotely -> take. B present, L absent, R = B: deleted locally -> keep deletion (tombstone/omit). B present, L absent, R != B: delete vs edit conflict (dogear: edit wins for leaf items, deletion wins for folders).
- **What each metadata choice can answer:**
  - Global "needs upload" flag: only "anything changed locally?"; no per-record direction; no deletion disambiguation.
  - Per-record dirty flag (or change counter): local direction only. If local is dirty and remote differs, you cannot tell "remote unchanged since last sync" (safe to upload) from "remote also changed" (conflict) without some remote-side base value.
  - Per-record base version embedded in the shared file (a `rev` like CouchDB's): remote direction from `remote.rev != base.rev`; local direction needs a dirty flag or a local rev bump. Concurrent bumps from 3 to 4 on two devices collide unless the rev includes a device id or content hash. [U] CouchDB uses revs of the form N-hash; not re-read this session.
  - Per-record base hash: both directions plus existence. Collisions only matter when an edited record hashes equal to its base (a missed change); with a 53-bit or 64-bit hash this is negligible for this scale.
  - Full base copy: everything above plus field-level merge (title vs parentId vs order), and the ability to rebuild a "remote" view if the server copy is temporarily unreadable.
- **Canonical form is a correctness condition.** The hash must be computed over a canonical serialization (sorted keys, normalized numbers, excluding local-only fields and excluding `_u` if `_u` is rewritten on merge). JSON.stringify key order depends on insertion order, so two equal records can serialize differently and look "changed", which produces spurious uploads and false conflicts (not data loss).
- **Rough storage estimates** (my assumptions: id about 20 characters, bookmark record about 150-250 characters of JSON, localStorage stores UTF-16 so about 2 bytes per character):
  - Hash map entry `"<id>":"<11-char base36 53-bit hash>",` is about 20 + 11 + 6 = 37 characters, about 74 bytes. 500 bookmarks: about 37 KB; 2,000 bookmarks: about 148 KB.
  - Full base copy: equal to the synced document; 500 bookmarks x 200 characters = 100,000 characters, about 200 KB; 2,000 bookmarks: about 800 KB, a third full copy competing for the about 5 MiB Safari budget.
  - Per-record dirty set (ids only, only while dirty): about 23 characters per dirty id, near zero when clean.
  - Global hash of the last synced document: one string, about 20-70 characters.
  - A hybrid that is still small: hash map for all records plus a full copy only of the few fields worth field-merging (for bookmarks: title, parentId, order) would be roughly 40-60 % of a full copy; probably not worth the complexity at this scale.
- Settings and last reading position are single records; for them a hash base and record-level decisions lose nothing.

### Gaps
- No primary source found that quantifies per-record metadata sizes in any of the studied systems (Unison archive sizes, Firefox mirror size); the numbers above are my estimates from assumed record sizes.
- I did not find a maintained, widely used JavaScript library for three-way merge of JSON maps with a published spec; Joplin uses a fork of `node-diff3` for text, which does not apply to records.

## Q3. When the base is lost or untrustworthy, what is the safe fallback?

### Takeaway
The safe default with no base is "assume the base was empty": one-sided records propagate, records that differ on both sides become conflicts resolved by the existing policy (here, the old `_u` rule), and deletions cannot be inferred, so tombstones in the shared file remain necessary. The truly dangerous case is not a missing or old base but a base that contains changes the server never accepted, because that silently turns an unsent local edit into "remote changed, take remote".

### Cited Findings
- [P] Unison: if archives are deleted, unreadable after a format change, or absent on the first run, "it takes a conservative approach: it behaves as though the replicas had both been completely empty at the point of the last synchronization. The effect of this is that, on the first run, files that exist in only one replica will be propagated to the other, while files that exist in both replicas but are unequal will be marked as conflicting." — [Unison manual](https://github.com/bcpierce00/unison/blob/master/src/strings.ml)
- [P] "It is safe to 'brainwash' Unison by deleting its archive files on both replicas. The next time it runs, it will assume that all the files it sees in the replicas are new." After a version upgrade with a new archive format, "the old archive will be ignored (not deleted)" and differences "will show up as conflicts". — [Unison manual](https://github.com/bcpierce00/unison/blob/master/src/strings.ml)
- [P] Unison stops on leftover lock files from an interrupted archive read/write and asks for manual intervention unless `ignorelocks` is set. — [Unison manual](https://github.com/bcpierce00/unison/blob/master/src/strings.ml)
- [P] Unison invariant: "At every moment, the information stored on disk about Unison's private state can be either (1) unchanged, or (2) updated to reflect those paths that have been successfully synchronized." — [Unison manual](https://github.com/bcpierce00/unison/blob/master/src/strings.ml)
- [P] Firefox: "Once upload succeeds, we update the mirror with the uploaded records, so that the mirror matches the server again." — [SyncedBookmarksMirror.sys.mjs](https://github.com/mozilla-firefox/firefox/blob/main/toolkit/components/places/SyncedBookmarksMirror.sys.mjs)
- [P] Firefox/dogear first-sync fallback: content info is attached only to local items that are not `SYNC_STATUS_NORMAL` (never uploaded or merged); dogear will "dedupe local items with content info to remotely changed items with similar contents and different GUIDs" (bookmarks: same title and URL; folders: same title; separators: same position). — [Firefox store.rs](https://github.com/mozilla-firefox/firefox/blob/main/toolkit/components/places/bookmark_sync/src/store.rs); [dogear src/tree.rs](https://github.com/mozilla/dogear/blob/master/src/tree.rs)
- [P] Joplin's auto-merge is skipped and a plain conflict copy is made when "there is no recorded base"; an encrypted download clears the base until decrypted. — [Joplin conflict_auto_merge.md](https://github.com/laurent22/joplin/blob/dev/readme/dev/spec/conflict_auto_merge.md)

### Inferences
- **Fallback for this app with no base** (first sync on a device, cleared storage, base failed to save, base fails a validity check): run the existing `_u` max-wins merge with tombstones. That is exactly what older clients do today, so it is known-safe and needs no new code path; it only loses the clock-independence for that one sync. After one successful sync the base exists and later syncs are clock-free.
- **"Base older than remote" is the normal case**, not an error: the base is some earlier server version; the remote may be many versions ahead. Correctness only requires that the base be a version the server actually held (an ancestor), and that the local data was derived from it.
- **Untrustworthy base checks** worth storing with the base: the Drive file id (a deleted and recreated file means discard the base), the ETag of the version the base represents, the account id, and a generation number shared with the local data so a base written without its matching data write can be detected. If any check fails, treat the base as absent (fallback above).
- **The unsafe case is a base "ahead" of the server.** If the base were advanced before the upload was confirmed and the upload then failed, the next sync sees local = base and remote != base, classifies "only remote changed", and overwrites the local edit with no conflict. Rule: advance the base only after a confirmed successful write (2xx with new ETag) or after a download that was fully applied and saved locally.
- **Deletions without a base**: with an empty base, a record present remotely and absent locally reads as "created remotely" and resurrects a local deletion; only tombstones prevent that. So tombstones must stay in the file format even if base-keeping clients no longer need them among themselves, and they cannot be garbage-collected while base-less clients (old versions, fresh installs) may exist.

### Gaps
- No primary source compared "empty base" vs "fall back to timestamps" quantitatively; the recommendation above is reasoning.
- Not checked whether Google Drive exposes enough revision history (for example `headRevisionId` or the revisions API) to verify that a stored base ETag was ever a real server version; out of my assigned scope.

## Q4. Deciding there is something to upload: dirty flags, outbox, hash of last uploaded document, per-record base

### Takeaway
"Dirty" is safest when it is derived (current local state != base) rather than stored as a separate flag: a derived difference cannot be lost by a crash between "save locally" and "upload", and it naturally keeps edits made during an in-flight upload, provided the base is set to the exact snapshot that was uploaded. Stored flags work only if they are written in the same atomic write as the data, are cleared only after a confirmed upload, and are decremented by the snapshot amount (a counter) rather than reset.

### Cited Findings
- [P] Firefox keeps a per-row `syncChangeCounter` in `moz_bookmarks`, i.e. in the same row and transaction as the edit. On completion, `pushChanges` runs `SET syncChangeCounter = MAX(syncChangeCounter - :syncChangeDelta, 0)` only for records where upload succeeded: "If upload failed, ignore the change; we'll try again on the next sync." and "If the bookmark was updated during the sync, its change counter will still be > 0 for the next sync." — [PlacesSyncUtils.sys.mjs](https://github.com/mozilla-firefox/firefox/blob/main/toolkit/components/places/PlacesSyncUtils.sys.mjs)
- [P] Firefox: "The change counter in Places is the persistent record of items that we need to upload, so, if upload is interrupted or fails, we'll stage the items again on the next sync." Outgoing items stay "flagged as changed in Places, so the next sync can resume cleanly if the upload is interrupted or fails"; an interruption after upload but before the mirror update means "we'll merge them again on the next sync. This is redundant work, but shouldn't cause issues." — [Firefox store.rs](https://github.com/mozilla-firefox/firefox/blob/main/toolkit/components/places/bookmark_sync/src/store.rs); [SyncedBookmarksMirror.sys.mjs](https://github.com/mozilla-firefox/firefox/blob/main/toolkit/components/places/SyncedBookmarksMirror.sys.mjs)
- [P] Joplin documents the in-flight-edit pitfall of using a timestamp as the "synced" marker: an edit at t0 during an upload that started at t0 is never detected because `sync_time` is set to t0; "The solution would be to use something like an etag (a simple counter incremented on every change) to make sure each change is uniquely identified. Leaving it like this for now." — [Joplin Synchronizer.ts](https://github.com/laurent22/joplin/blob/dev/packages/lib/Synchronizer.ts)
- [P] Unison: "It is safe to modify files while Unison is working. If Unison discovers that it has propagated an out-of-date change, or that the file it is updating has changed on the target replica, it will signal a failure for that file." Interrupted propagation leaves paths updated but not marked synced; next run "will detect changes to these paths in both replicas, notice that the contents are now equal, and mark the paths as successfully updated." — [Unison manual](https://github.com/bcpierce00/unison/blob/master/src/strings.ml)
- [P] `localStorage.setItem` throws `QuotaExceededError` "if the storage run out of disk quota or the user declined to grant you more space." — [MDN Storage.setItem](https://developer.mozilla.org/en-US/docs/Web/API/Storage/setItem)
- [P] The Web Locks API lets a script in one tab "acquire a lock, hold it while work is performed, then release it. While held, no other script executing in the same origin can acquire the same lock"; MDN's own example is ensuring "only one tab is syncing data". Baseline widely available since March 2022; secure contexts only. — [MDN Web Locks API](https://developer.mozilla.org/en-US/docs/Web/API/Web_Locks_API)

### Inferences
- **Global hash of the last synced document** directly fixes the current slow-clock bug: on a 304, upload iff `hash(canonical local doc) != storedHash` (stored hash = hash of the document as last uploaded or downloaded and applied). Unlike "max `_u` differs", it detects an edit whose `_u` is smaller than the cached max. Cost: one string. It does not tell which records changed, so it is a trigger, not a merge base.
- **Crash between save and upload**: with derived dirty-ness (local differs from base, or hash differs) nothing is lost; on restart the difference is still there and the next sync uploads. With a separate flag key in localStorage, writing the data and then the flag leaves a window where a crash loses the "needs upload" signal until the next edit; writing the flag first is safe (worst case a no-op upload). An outbox (queue of pending operations) has the same ordering requirement and also grows without bound while offline; with a whole-file sync it adds little over a state diff.
- **Edits during an in-flight upload**: capture the snapshot S to upload; on success set base := S (and its ETag), never base := current local state. Edits made during the request remain local != base and are uploaded next time. This is the state-based equivalent of Firefox's "decrement by the snapshot delta".
- **Flag cleared before upload confirmed**: equivalent to advancing the base early (Q3). Must clear only on a confirmed 2xx.
- **Failed local save (storage full)**:
  - If the merged document cannot be saved locally, do not advance the base. Uploading the merged document is then still safe: on restart local is the old local, base is the old base, remote holds the merge; records changed by others are "only remote changed" and get applied; this device's own changes are present on both sides and resolve as "changed identically".
  - Advancing the base while the local data write failed is unsafe: on restart old local != new base looks like a local edit that reverts the remote, and would be uploaded as a regression.
  - Write order in localStorage (no multi-key transactions): data first, base second, with a shared generation number; on load, if the generations differ, treat the base as absent. A base that fails to save because of quota just means "no base" next time (safe fallback, Q3).
  - Storing the base also consumes quota; if the data write would succeed only by dropping the base, drop the base, not the data.
- **Multiple tabs on one localStorage**: tab B's in-memory state can be older than what tab A synced and saved. If B later writes its stale state, B's data differs from the (new) base and looks like a local edit that reverts A's sync. Mitigations: run the whole sync (read local, read base, download, merge, save, upload, save base) inside one `navigator.locks.request("sync", ...)`; re-read localStorage inside the lock rather than trusting memory; apply user edits as read-modify-write on the stored value, not by writing a whole in-memory document; listen to the `storage` event to refresh other tabs. [U] The `storage` event fires in other same-origin tabs when localStorage changes (not re-read this session).

### Gaps
- No primary source found on how widely used web apps track dirty state over localStorage specifically; the multi-tab analysis is reasoning plus the Web Locks documentation.
- I did not find documentation of Safari's behaviour when a localStorage write fails mid-way (whether the old value is kept intact); `setItem` throwing is documented, partial writes are not.

## Q5. Combining a base with conditional writes (ETag If-Match): clock-free "the edit made after seeing the other device's edit survives"

### Takeaway
If-Match turns the single file into a linear sequence of versions, because a write succeeds only if it was computed from the current version. With a base that is always a real earlier version, any edit made after a device saw another device's edit is classified as "only this side changed" in every later merge and therefore survives, with no clock involved. Clocks or another policy are needed only for edits that are concurrent in the strict sense (neither device had seen the other's edit to that record).

### Cited Findings
- [P] If-Match "is most often used with state-changing methods (e.g., POST, PUT, DELETE) to prevent accidental overwrites when multiple user agents might be acting in parallel on the same resource (i.e., to prevent the 'lost update' problem)." The server "MUST use the strong comparison function" and "MUST NOT perform the requested method if the condition evaluates to false", and may respond 412. It MAY instead answer 2xx if the change "appears to have already been applied" (for example "because the prior response was lost"). — [RFC 9110 §13.1.1](https://www.rfc-editor.org/rfc/rfc9110#section-13.1.1)
- [P] Dropbox Nucleus: with concurrent conflicting moves "the final order depends on which sync engine uploads their move first", i.e. the server's accepted write order decides. — [Dropbox, Rewriting the heart of our sync engine](https://dropbox.tech/infrastructure/rewriting-the-heart-of-our-sync-engine)
- [P] Dogear's both-changed rule falls back to "which side is newer" by age; its only-one-side rules ignore time completely. — [dogear src/merge.rs](https://github.com/mozilla/dogear/blob/master/src/merge.rs)
- [S] Kleppmann et al. note that a server can order communication for CRDT-based apps without being a central authority ("using a server for communication is fine for CRDTs"; servers as "cloud peers"). — [Local-first software](https://www.inkandswitch.com/essay/local-first/)

### Inferences
- **Argument (record r, devices A and B, server versions V1, V2, ...):**
  1. B writes r = b into V1. A downloads V1, merges, saves, and sets base_A = V1 (r = b).
  2. A edits r = a. Locally hash(a) != base_A[r].
  3. Case: A's If-Match V1 succeeds, giving V2 with r = a. When B next syncs, base_B is V1 or older; remote r = a differs from base_B; if B did not touch r since, "only remote changed", B takes a. A's later edit survives regardless of either clock.
  4. Case: B wrote V2 first (A gets 412). A downloads V2 and merges against base_A = V1. If B did not change r in V2 (remote r = b = base), "only local changed", keep a, upload with If-Match V2. A's later edit survives.
  5. Only if B also changed r between V1 and V2 (B had not seen a, A had not seen B's second edit) is it a true conflict, which is the only place a policy (or clock) is needed.
- **Correctness conditions for the argument:** (a) every upload is conditional (If-Match with the ETag of the version that was merged); (b) the base is only ever set to a version the server accepted or served (Q3); (c) the base and the local data move together (Q4); (d) the merge is deterministic so retries converge; (e) the server's ETag changes on every content change (strong comparison per RFC 9110).
- **Lost response after a successful write**: the base is not advanced; the next download returns our own upload; local equals remote, both differ from base, so this is a "changed identically" case and resolves silently (Unison's false-conflict rule). No duplicate or revert.
- **Policy for true conflicts** (both changed, values differ), options:
  - Field-level merge when a full base exists (title from one side, parentId/order from the other); only same-field conflicts remain.
  - Keep `_u` max-wins only for this case. Clock skew then only affects truly concurrent edits, which is a much smaller exposure than today.
  - Deterministic pick (for example remote wins, i.e. the server's earlier-accepted write wins, which mirrors Dropbox's "first upload wins"); or keep both (duplicate the bookmark) for user-visible data, like Dropbox conflicted copies and Joplin conflict notes.
  - Delete vs edit: dogear's rule (edit revives a leaf bookmark; folder deletion wins and changed children are moved to the nearest surviving ancestor) avoids losing user-created content.
  - Tree validity after any merge: a record-level merge of `parentId` can create cycles or orphaned children and duplicate `order` values; a post-merge repair pass (break cycles, reattach orphans, renumber order) is needed, as in dogear's structure rules and Dropbox's cycle example.
- **Compatibility with older clients that keep no base** (they still merge by max `_u`):
  - Old client edits arrive as "remote changed" for new clients and are taken without consulting `_u`, so a slow clock on an old device no longer blocks its edits from reaching new devices.
  - New clients must still write a `_u` that old clients will accept. Writing `_u = max(Date.now(), previous _u of that record + 1)` (a Lamport-style bump over the value it saw) guarantees that an edit made after seeing the record wins under the old clients' max-`_u` rule even if the new device's clock is behind. Without the bump, an old client holding the previous version with a larger `_u` would revert the new edit.
  - An old client's own unsynced edit with a fast-clock `_u` can still beat a new client's later edit at the old client's merge; a base cannot prevent another client's LWW decision. New clients will then see that as "remote changed" and accept it. This exposure lasts until old versions are gone.
  - Old clients' 304 shortcut (upload only if max `_u` changed) keeps working with bumped `_u` values, because every new edit raises that record's `_u` above its previous value.
  - Tombstones must keep their current format and meaning for old clients.

### Gaps
- Not verified in this session whether Google Drive's ETag on files changes on metadata-only updates (which would cause harmless extra 412s) or what Drive returns for a repeated identical upload; outside my scope.
- No primary source found that states this "If-Match + base gives causal survival" property in this exact form; it is my derivation (it is the single-server special case of version-vector reasoning).

## Q6. Academic and engineering references on state-based synchronization with a common ancestor

### Takeaway
The best primary engineering references are Unison's manual (precise invariants for archive handling, crash safety, empty-base fallback, clock independence), Firefox's bookmark mirror and dogear source (tree merge with change flags, delete/edit and structure rules, change counters), Dropbox's Nucleus posts (three trees, Synced Tree as merge base), and Joplin's 2026 auto-merge spec (storing a base per item and falling back when it is missing). On the academic side, the Harmony framework (Foster, Greenwald, Kirkegaard, Pierce, Schmitt) is the closest match: state-based synchronization of tree-structured data against an archive.

### Cited Findings
- [S] "Exploiting Schemas in Data Synchronization" (Foster, Greenwald, Kirkegaard, Pierce, Schmitt; DBPL 2005; Journal of Computer and System Sciences 73(4), 2007, pp. 669-689) presents Harmony, a framework for building state-based synchronizers for tree-structured data (unordered, edge-labeled trees), where conflict recognition is driven by the schema; address books are the case study. — [UPenn repository](https://repository.upenn.edu/cis_papers/344/); [DBPL 2005 PDF](https://senslab.inrialpes.fr/papers/files/DBPL_2005_schema_sync.pdf) (abstract-level only; full text not read)
- [P] Unison manual sections "What is a Conflict?", "Reconciliation", "Invariants" give an operational specification usable as a checklist. — [Unison manual](https://github.com/bcpierce00/unison/blob/master/src/strings.ml)
- [P] Firefox: [SyncedBookmarksMirror.sys.mjs](https://github.com/mozilla-firefox/firefox/blob/main/toolkit/components/places/SyncedBookmarksMirror.sys.mjs), [PlacesSyncUtils.sys.mjs](https://github.com/mozilla-firefox/firefox/blob/main/toolkit/components/places/PlacesSyncUtils.sys.mjs), [bookmark_sync/src/store.rs](https://github.com/mozilla-firefox/firefox/blob/main/toolkit/components/places/bookmark_sync/src/store.rs), [dogear merge.rs](https://github.com/mozilla/dogear/blob/master/src/merge.rs), [dogear API docs](https://docs.rs/dogear/latest/dogear/).
