# 테스트 안내

이 저장소의 자동 시험은 **세 겹(+데이터 한 겹)** 으로 나뉩니다. 각 겹이 잡는 문제가 다르므로, "무엇이 어디서 검증되는가"를 여기 정리해 둡니다. 코드를 직접 읽지 않아도 어떤 시험이 무엇을 보장하는지 파악할 수 있도록 한 것입니다.

> 권위 있는 "지금 무엇이 동작하는가"는 주제 문서(`docs/topics/`)의 「지금 동작」, 결정 배경은 각 ADR([`docs/decisions/`](../docs/decisions/)) 참조.

## 한눈에 보기

| 겹 | 도구 | 무엇을 보나 | 어디서 도나 | 규모 |
|---|---|---|---|---|
| **유닛** | `node --test` (의존성 0) | 순수 로직 — 함수 입출력·상태 계산 + 문서·픽스처의 일관성 | **CI 자동** (PR마다) | 36파일 · 1365케이스 |
| **타입 검사** | `tsc --noEmit` (JSDoc, `js/` 전체 — `checkJs`) | 타입 불일치·오타 | **CI 자동**(「Unit tests」 잡) + 로컬 훅 | 설정 2종(앱·검색 워커) |
| **E2E** | Playwright (실제 브라우저) | 화면·상호작용·모듈 간 배선 | **로컬 전용**(수동) | 30파일 · 378케이스 |
| **데이터** | pytest (`common-bible-data` 서브모듈) | 성경 본문과 검색 인덱스의 일관성 | 그 저장소 CI | 별도 저장소 |

### 각 겹이 "혼자만 잡는" 것 — 왜 셋 다 필요한가

- **유닛**: 정렬·절 범위 계산 같은 순수 로직의 정확성. 빠르고 CI 자동이지만 **화면·브라우저 동작은 못 본다**.
- **타입 검사(tsc)**: JSDoc 타입 오류·오타. CI 가 PR 마다 돌린다. 단, **모듈에서 import을 빠뜨려도 통과**하는 사각지대가 있다(미선언 식별자를 전역으로 간주). 그래서 "tsc 통과 = 안전"이 아니다 — 자세한 사례는 [`docs/known-issues.md`](../docs/known-issues.md) 및 ADR-019 참조.
- **E2E**: 위 사각지대(주입 콜백·모듈 간 import 누락)와 실제 클릭·내비게이션을 **유일하게 잡는 안전망**. 단 로컬에서 수동으로 돌려야 한다(CI 아님).

## 1. 유닛 테스트 — `tests/unit/`

순수 JS 로직을 Node 자체 테스트 러너 + 자체 `vm` 하네스로 검증한다. 의존성 0, CI가 PR마다 자동 실행. 한 모듈 = 한 테스트 파일(`<소스이름>.test.js`). 실데이터(`data/`의 표)를 읽어야 하는 케이스는 `<소스이름>.data.test.js`로 갈라 `haveData` skip 검사를 달고, `engine-data.yml`과 `sync-data.yml`에서 돌린다. 공개 CI의 `Unit tests` 잡은 비공개 `data/` 서브모듈을 받지 않기 때문이다(선례 `liturgical-engine.data.test.js` · `lectionary.data.test.js`, 설계서 §7). 테스트 파일 안은 `// ── <영역> ──` 주석으로 구역을 나눈다(ADR-013). 상세 규약은 [ADR-013](../docs/decisions/013-client-js-unit-tests.md). 예외 둘 — 문서를 읽는 테스트(`docs-*.test.js`: 설계서 facts 블록 ↔ 실데이터, 설계 문서 교차 참조, 저장소 문서의 참조 검사)와 픽스처 테스트(`liturgical-fixtures.test.js`: `tests/fixtures/liturgical/` — 교회력 엔진 실제 연도 기대값의 **기준**, 스키마는 그 README · 설계서 §1.4). 이들이 함께 쓰는 문서 앵커 추출기와 설계서를 읽는 함수(목차와 장 파일을 이어 붙인다)는 `unit/docs-anchors.js` 에 한 벌만 둔다(`harness.js` 처럼 `*.test.js` 글롭 밖의 공용 모듈) — 사본을 두면 곧 어긋난다. 픽스처의 전례일 id 가 실데이터에 실재하는지는 `liturgical-fixtures.data.test.js` 가 `engine-data.yml`·`sync-data.yml` 에서 본다.

```bash
node --test tests/unit/*.test.js          # 전체 (CI와 동일)
node --test tests/unit/storage.test.js    # 개별 파일
```

## 2. 타입 검사 — `tsc`

순수 JS에 JSDoc 주석으로 타입을 달고, `tsc --noEmit`으로 **출력 없이 타입만** 검사한다(ADR-012). "컴파일"이 아니라 타입 검사 용도. `tsc`는 TypeScript Compiler의 약자. `checkJs: true`라 `js/`의 모든 파일이 대상이고, 검사에서 빼야 하는 파일만 첫 줄 `// @ts-nocheck`로 빠진다 — 지금은 없다(2026-10-18). CI의 필수 「Unit tests」 잡이 PR마다 `npm run typecheck`를 돌린다.

```bash
npx tsc -p tsconfig.json --noEmit          # 앱 코드
npx tsc -p tsconfig.worker.json --noEmit   # 검색 워커(Web Worker — 다른 전역 환경). 서비스 워커 sw.js 는 아직 어느 설정에도 없다
```

- 잡는 것: 잘못된 타입 사용, 존재하지 않는 속성 접근, 함수 인자 불일치, 오타.
- **사각지대**: 모듈에서 `import`을 통째로 빠뜨려도, 그 이름이 전역으로 선언돼 있으면 통과시킨다 → 런타임에서야 깨진다. 이 부류는 **로드 스모크/E2E로만** 잡힌다([`docs/known-issues.md`](../docs/known-issues.md)).

## 3. E2E 테스트 — `tests/e2e/`

실제 크롬(Playwright)을 띄워 화면 렌더·클릭·내비게이션·모듈 간 배선을 검증한다. **CI에서는 돌지 않으며**, 기능 개발 후 로컬에서 수동 확인한다.

```bash
# 1. 의존성(최초 1회)
pip install pytest-playwright && playwright install chromium

# 2. 개발 서버(별도 터미널) — SPA-aware 서버여야 History API 경로가 동작
python3 scripts/serve.py 8080

# 3. 실행
pytest tests/e2e/ -v
pytest tests/e2e/test_bookmark_sort.py -q   # 개별 파일
```

> 서버가 `http://localhost:8080`에 떠 있어야 한다. `conftest.py`의 `base_url`이 8080을 하드코딩하므로 다른 포트는 안 된다.

## 4. 데이터 파이프라인 테스트 (서브모듈)

성경 본문(마크다운→JSON)과 검색 인덱스의 일관성 검증은 `common-bible-data` 저장소에 있다(ADR-004). 본 저장소 CI는 실행하지 않으며, 그 저장소의 `validate.yml`이 push마다 자동 실행한다. 로컬에서 보려면:

```bash
cd data && pytest tests/   # 서브모듈 디렉터리
```
